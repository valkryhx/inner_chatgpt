# MCP 工具数在设置页跳动（46 ↔ 35）：口径不一致

日期：2026-11-20
用户：`hx`（`u_c56b8337dd09`）
现象：设置页顶部显示「共 46 个可用工具」，点「重新检测连接」变成 35。

## 0. 结论

**46 = 11 个内置工具 + 35 个 MCP 工具。35 是只有 MCP 的数。**

两个接口各自拼工具列表，口径不同，而前端两处都渲染同一个 `effective.length`：

| 端点 | 触发方式 | 修复前返回 | 组成 |
| --- | --- | --- | --- |
| `GET /me/mcp-effective` | 打开设置页 | **46** | 内置 11 + MCP 35 |
| `POST /me/mcp-servers/probe` | 点「重新检测连接」 | **35** | 只有 MCP 35 |

**不是连接在抖，是两个数在数不同的东西。**

## 1. 46 的构成（实测）

该用户启用的 MCP server 两个：

| server | 工具数 |
| --- | --- |
| `sqlbotmcp` | 12 |
| `falcomm` | 23 |
| **MCP 合计** | **35** |

内置工具 11 个：

```
file_read, file_glob, file_grep, file_write, file_patch, list_files,
code_run, load_skill, memory_list, memory_read, memory_write
```

> 注：前 8 个定义在 `builtin_tools.py`；后 3 个 `memory_*` 由
> `memory_tools.py` 提供，再经 `build_builtin_tools` 调 `build_memory_tools`
> 装配进去。所以「内置工具在哪定义」不是一个文件。（这条是核验脚本
> 抓出来的：首版判据只在 `builtin_tools.py` 里找，误判文档写错了，
> 实际是判据范围选窄了。）

11 + 35 = **46**。`exa` 当时已是 `enabled=0`，不计入。

## 2. 根因（代码坐标）

`backend/app/routers/me.py`：

```python
# 修复前 mcp_effective
return {"tools": [t.name for t in ur.registry.tools], ...}
#                          ^^^^^^^^^^^^^^^^^^^^^ 内置 + MCP 合并后的注册表

# 修复前 mcp_probe
tools = [t.name for t in ts.tools]
#                          ^^^^^^^^ 纯 MCP toolset
return {"ok": True, "servers": servers, "tools": tools}
```

前端 `SettingsModal.tsx` 两处都写 `effective.length`：

- 首屏 `load()` ← `mcpEffective()` → 46
- 点按钮 `probe()` ← `mcpProbe()` → 35

## 3. 修法

### 3.1 后端：统一口径 = 「模型实际拥有的工具面」

`mcp_probe` 并入内置工具，两个端点都额外报出拆分数：

```python
return {"ok": True, "servers": servers,
        "tools": builtin + mcp_names,
        "builtin_count": len(builtin),
        "mcp_count": len(mcp_names)}
```

失败路径也要给内置数（MCP 全挂不等于「一个工具都没有」）。

### 3.2 前端：拆开显示，不再只给总数

```tsx
{mcpState !== 'ready'
  ? '工具数待检测'
  : builtinCount !== null && mcpCount !== null
  ? `MCP ${mcpCount} 个 · 内置 ${builtinCount} 个（合计 ${effective.length}）`
  : `共 ${effective.length} 个可用工具`}
```

效果：

```
全部 2 个 server 已连接
MCP 35 个 · 内置 11 个（合计 46）
```

**为什么非要拆开**：只给总数时，数字一变用户无法判断是「某个 MCP server 掉线」
还是「内置工具变了」。拆开后两种变化在界面上就是不同位置在变。

而 MCP 页面下方的每个 server 行本来就按 server 显示 `已连接 · N 个工具`，
总数与分区必须能对上 —— 现在 35 就是那几行之和。

## 4. 验证

真机实测（修复后）：

```
--- mcp-effective ---  tools 总数: 46 | builtin: 11 | mcp: 35
--- mcp-probe     ---  tools 总数: 46 | builtin: 11 | mcp: 35 | ok: True
```

两边完全一致。

测试：`backend/tests/test_mcp_tool_count_consistency.py`（6 条）。

## 5. ★ 反向确认抓出的一处假判据（值得记）

首版测试用**源码字符串**判断：

```python
assert "build_builtin_tools" in body
```

反向确认把 probe 里的**调用**删掉后，测试仍然全绿 —— 因为那个字符串还留在
内层 helper `_builtin_names` 的**定义**里。

> **源码里出现某个名字，在「用了」和「只定义没用」两种状态下读数相同
> ⇒ 那不是判据。**

改成行为测试：mock `build_user_toolset` 与 `build_builtin_tools`，
真正调用 `mcp_probe`，断言返回的 `tools` 同时含内置与 MCP 的名字。
再跑反向确认，两个用例都能变红。

（`docs/probes/20261120-MCP工具数口径反向确认.py`，4 个用例）

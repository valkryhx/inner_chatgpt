## 3. 压缩：短会话不划算，长会话真省

### 3.1 长会话（`compact_long.py`，5 轮 × 1200 字）

```
压缩前：10 条消息 / 5666 tokens
压缩后：11 条消息 / 4201 tokens
已压缩 4 条较早消息 → 摘要约 646 tokens；保留 7 条（最近 6 条 + 1 条摘要）
```

| 编号 | 断言 | 实测 |
|---|---|---|
| L-1 | 返回 `compacted=true` | 是 |
| L-2 | `used_tokens` 严格下降 | 5666 → 4201 |
| L-3 | 压缩比 < 0.8 | **0.74（省 26%）** |
| L-4 | 压缩后仍能对话 | 成功 |

### 3.2 短会话（`compact_deep.py`，5 轮极短问答）

| 编号 | 断言 | 实测 |
|---|---|---|
| Z-0 | 造够消息（≥8 条） | 10 条 |
| Z-1 | `compacted=true` | 已压缩 6 条 → 摘要 140 tokens |
| Z-2 | 掉了消息且保留尾部 | dropped=6 kept=7 |
| Z-3 | **短会话不要求 token 下降**，但消息数必须减少 | 184 → 188（见下） |
| Z-4 | 有可见摘要消息 | 1 条 `role=system` |
| Z-5 | **压缩后模型仍能复述哨兵** | 找到 `9de34f` |
| Z-6 | 连续两次压缩不清空历史 | 13 → 14 条 |

### 3.3 「压了反而变大」不是缺陷

第一次 Z-3 断言「token 必须下降」，实测 **184 → 188**（涨了 4）。

查证：摘要 304 字 / 175 tokens，而被压掉的 6 条极短问答合计只有约 60 tokens。
**摘要有固定开销**（要复述用户目标、已完成事项、未完成待办），
内容太短时压缩必然不划算。这是设计如此，不是 bug。

因此判据改成按场景分流：
- 内容够长（`dropped × 平均每条 token > 摘要 token`）→ 断言 token 下降；
- 内容太短 → 只断言「消息数减少 + 摘要存在」，并在详情里写明为什么 token 会涨。

**Z-5 是这组最关键的一条**：只验「条数变了、token 低了」会被「删光历史」骗过。
必须让模型复述压缩前埋的哨兵，才能证明摘要真的进了上下文。

## 4. UX 观察（非缺陷，记录以备改进）

1. **`keep=6` 是条数阈值，与 token 无关**。所以「6 条消息 / 4664 tokens」时会回
   「消息太少，无需压缩」。对齐 GenericAgent 的设计，但对用户是反直觉的
   —— 他会觉得这么多字应该能压。可考虑在提示里带上 token 数：
   「消息较少（6 条 / 4664 tokens），无需压缩」。
2. **超窗时 `percent` 不夹取**。`ContextUsageOut.percent` 可以 >100，
   UI 原样显示成 `110.2%`。正常路径下硬线裁剪会先触发，所以见不到；
   但显示层夹到 100% 更稳妥。
3. 空态文案「还没有会话」+「查看全部会话」+ MCP 状态行齐全，新用户不会懵。

## 5. 未能复现：`440.8k / 400.0k · 110.2%`

### 5.1 现象

第一次 `ui_acceptance`（`runId 1794716902-4d4b`）的截图 06/07/08 页脚显示
`440.8k / 400.0k · 110.2%`。放大截图逐字核对过，不是误读。

### 5.2 排查

| 方向 | 做法 | 结果 |
|---|---|---|
| 后端是否真返回 440k | 用**同一份库**起后端，逐个会话打 `/context` | 最大 4200；两个相关会话是 86 / 105 |
| 库里是否有巨大会话 | 155 个会话的 history 全算一遍 | 最大 **8889 tokens** |
| 是否有 base64 图片 | 扫 history 找 `data:image` | 0 处 |
| 是否前端状态串了 | Playwright 录制每次 `/context` + 页脚对照（v2/v3） | 7 次响应全与页脚一致 |
| 是否「停止 + 切会话」触发 | 复制第一次的 prompt（12000 字长文）+ 停止 + 新建（`context_big.py`） | 全程 ≤ 0.1k，**未复现** |

### 5.3 结论（2026-11-15 当日已更正）

**已复现，成因已定案**，见 `docs/20261115-上下文用量超100%的成因与自动压缩时机核实.md`。

原推测（「隔离库是遗留副本，某会话历史与前端状态错配」）**是错的**。真实成因是：

软线压缩被有意推迟到**本轮结束之后**（`HLZ_SOFT_COMPACT_DEFER` 默认开，P4 为不推迟首个 token），
所以「一轮结束 → 后台压缩完成」之间存在窗口，`/context` 读到的是**压缩前**的真实值。
而 `App.tsx:874` 只在 `done` 后 180ms 刷一次页脚，压缩要几十秒，**页脚不会自动再刷**——
于是那个偏高数字就停在界面上了。它是真读数，不是前端串了状态。

30k 窗口实测复现 **121.42%**（一轮从 87.84% 跳到 121.42%，单轮增幅 1 万 > 剩余空间 3.6k）；
150k 窗口实测最大 90.88%（剩余空间 1.5 万，单轮增幅不够大就冲不过去）。

关键判据是**「单轮增幅 vs 剩余空间」**，不是窗口绝对值——所以 400k 窗口下要出现 440k，
需要单轮输出约 4 万 token，虽然罕见但完全可能。

功能不受影响：在 >100% 的窗口期发消息，2.3s 成功、有真实回复、随后回落到 50%；
停手不发消息，30 秒内后台压缩也会自己跑完（37389 → 12099，-68%）。

保留了 `context_probe.py` 与 `context_big.py` 两个可复跑探针，
并把「页脚与 `/context` 一致」「无超窗」做成 `ui_acceptance.py` 的常驻断言
（F-2 / F-2b / P-4b）——下次再出现会被直接抓住。

**F-2b 的判据需要跟着改**：现在它断言「不出现 >100% 的显示」，但在软线赛后跑的设计下，
这个状态会真实存在。该断言应改为「页脚数字与最近一次 `/context` 响应一致」，
而不是「数字必须 <100%」——后者会把正常设计判成缺陷。

## 6. 期间纠正的两处判据错误（留档）

1. **「压缩失败 / 压缩成功 550 → 127 字」**：我一度以为是产品文案冲突。
   实际这两个字符串在 `frontend/src` 与 `frontend/dist` 里**都不存在**——
   它们是模型自己输出的正文（那条会话是 1~400 列表任务）。
   **教训：看到不认识的文案先 grep 源码，不要假设是产品字符串。**
2. **`L-1` 首次失败**：只跑 3 轮 = 6 条消息，正好等于 `keep=6`，
   压缩器回「无需压缩」，核心路径一行没跑到。改成 5 轮（10 条）才真正验到。

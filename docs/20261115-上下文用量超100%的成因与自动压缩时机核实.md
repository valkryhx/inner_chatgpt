# 上下文用量为什么会显示 90%+ / 超过 100%：自动压缩的真实时机核实（2026-11-15）

> 日期：2026-11-15　状态：机制已定案；「>100%」已复现；三处 UX 修复已落地并真机 8/8 验证
> 触发：用户怀疑「上限 400k，理论上不该出现 440k / 400k，到 90% 就该压缩」
> 工具：`tools/turn_job_verify/autocompact_150k.py`、`overwindow_behavior.py`、`deferred_compact_live.py`、`ctx_settle_ui.py`（Playwright）

---

## 0. 一句话

用户的直觉（「到 90% 就该压缩，不该出现 >100%」）**在单轮增幅小的前提下成立，在单轮增幅大时不成立**。
软线压缩被有意推迟到**本轮结束之后**（P4，为了不让摘要的几秒推迟首个 token），
所以「一轮结束后 → 后台压缩完成前」存在一个窗口，里面 `/context` 会读到超过软线、甚至超过 100% 的值。
**这个窗口是显示问题，不是功能问题**：同样的窗口期里发消息，2.3s 成功、有真实回复、随后用量回落到 50%；
停手不发消息，30 秒内后台压缩也会自己跑完（37389 → 12099，-68%，且产出的是摘要而非硬裁）。

## 1. 结论先行：三种读数的成因

| 读数 | 是否正常 | 成因 |
|---|---|---|
| 84.74%（150k 窗口，14 轮缓慢爬升） | 正常 | 每轮约 +1 万 token，跨线前一瞬的正常值 |
| 90.81% / 90.88%（刚跨软线） | 正常 | 软线本身就在 90%，刚跨过就是这个数 |
| **121.42%**（30k 窗口，一轮从 87.84% 跳到 121.42%） | **正常但反直觉** | 单轮增幅（约 1 万 token）大于剩余空间（30k 窗口下只剩 3.6k），一跳就过 100% |

**关键判据不是「窗口多大」，而是「单轮增幅 vs 剩余空间」**：
- 400k 窗口、单轮 +1 万 → 从 90% 到 100% 还有 4 万空间，要连跳 4 轮才会超，几乎不可能；
- 30k 窗口、单轮 +1 万 → 从 87.84% 到 100% 只剩 3.6k，一轮必超。

所以 `440.8k / 400.0k · 110.2%` 那次是**单轮输出特别长**（约 4 万 token）撞上剩余空间不足，
不是误读、也不是前端串了状态。

## 2. 机制：软线压缩为什么不在赛前跑

`backend/app/routers/chat.py:472-511` 的注释写得很清楚：

```python
# P4：默认**不在赛前做**，而是记下「本轮结束后补跑」（见 deferred_compact）。
# 理由：软线不影响本轮能否开始（硬线才是正确性问题），而且它的输入
# 「历史 + 本轮输入」在本轮结束后完全等价——赛后压与赛前压结果相同。
# 赛前做的话，摘要的几秒会推迟首个 token（实测超软线 +5~9s）。
```

于是赛前只做两件事：

1. `soft_deferred_n += 1`（只记数，不压缩）；
2. `preempt()` 取消上一轮还在飞的赛后压缩，然后跑**硬线兜底**（`enforce_hard_limit`，纯裁剪、不调 LLM）。

软线压缩本身由 `deferred_compact.schedule_soft_compact()` 在 `done` 之后登记成后台任务。

**这是一个有意的权衡，不是疏漏**：摘要要调一次 LLM，几秒到几十秒；
放在赛前就是「每次超线都多等几秒才看到第一个字」。P4 把它挪到赛后，首帧从 5859ms 降到秒级以内。

## 3. 实测证据

### 3.1 30k 窗口：确实能超过 100%，但功能不受影响

`autocompact_150k.py --window 30000`（runId `1794719482` 系列）：

```
第 1 轮后：used=8644   pct=28.81%
第 2 轮后：used=17034  pct=56.78%
第 3 轮后：used=26352  pct=87.84%
第 4 轮后：used=36427  pct=121.42%   ← 跨过软线 27000，且超过 100%
⚑ 跨线后那轮收到 compaction: trigger=hard_trim 36427 → 10100
```

`overwindow_behavior.py`（runId `1794719482-0981`）**就在这个 >100% 的窗口里立刻发下一条**：

| 断言 | 结果 | 实测 |
|---|---|---|
| W-0 制造出 >100% 的窗口期 | OK | `33686 / 30000 = 112.29%` |
| W-1 这个窗口里仍能发送（不报错/不超时） | OK | **耗时 2.3s** |
| W-2 这一轮有真实回复内容 | OK | 回复 **118 字** |
| W-3 之后用量回到软线以下 | OK | `15127 < 27000`（50.42%） |
| W-4 历史没被抹空 | OK | 11 条消息 |

**结论：>100% 的窗口期对用户是透明的**——能发、有回复、之后自动回落。

### 3.2 150k 窗口：全程没到 100%

`autocompact_150k.py --window 150000`（runId `1794719745-01cb`）：

```
第 13 轮后：used=127113 pct=84.74%
第 14 轮后：used=136212 pct=90.81%   ← 刚跨过软线 135000
```

全程最大 **90.88%**，A-3（从未 ≥100%）通过。原因见 §1：150k 下剩余空间 1.5 万，而脚本一跨线就改发短句（+113 token），没有再给一次大幅增长的机会。

### 3.3 软线压缩最终是**成功**的（脚本判据错了）

150k 那轮 A-2 / A-4 报失败：

```
[FAIL] A-2 跨过软线后触发了压缩  | 跨线=True；compaction 事件 0 次；used 136212 → 136325
[FAIL] A-4 压缩后用量回到软线以下  | used=136325 < soft=135000
```

但直接查库（`session_history`）：

```
co_a4cd1d92b954  msgs=17 tokens=60631
   sources: ['summarization', '-', '-', ...]     ← 摘要消息在
updated_at = 13:29:42
```

**压缩发生在脚本读完数字之后几秒**：136212 → 60631，降 **55%**，摘要消息 `_source="summarization"` 确实写进了历史。

所以 A-2 / A-4 是**我的判据问题**：脚本在 `c.stream()` 返回后立刻读 `/context`，
而赛后压缩是 fire-and-forget 的后台任务，此时还没跑完。这不是产品缺陷。
判据已改成「断言前轮询等待」（`--wait`，默认 90s），重跑结果见 §3.4。

### 3.4 停手等待：后台压缩确实自己跑完，且产出的是摘要（不是硬裁）

`deferred_compact_live.py --window 40000`（runId `1794720623-5af2`，**4/4 全过**）：

```
第 4 轮后 used=37389 pct=93.47%
  [OK] C-0 充到软线以上  | used=37389 >= soft=36000
        等  0s：used=37389 pct=93.47% 摘要=False 硬裁=False (8 条)
        等  3s：used=37389 pct=93.47% 摘要=False 硬裁=False (8 条)
        等 10s：used=37389 pct=93.47% 摘要=False 硬裁=False (8 条)
        等 30s：used=12099 pct=30.25% 摘要=True  硬裁=False (3 条)   ← 压缩完成
        等 60s：used=12099 pct=30.25% 摘要=True  硬裁=False (3 条)
  [OK] C-1 等待期间用量自己降下来  | 37389 → 12099（降 25290，-68%）
  [OK] C-2 降幅来自软线摘要而不是硬裁  | 见 summary 消息
  [OK] C-3 等待后仍能正常对话  | 成功
```

**三个要点**：

1. 压缩**完全不需要用户再发消息**——用户在 `done` 之后停手，30 秒后自己完成；
2. 0s / 3s / 10s 三次采样都没变化，说明摘要的 LLM 调用就在 10–30 秒之间完成，与 `deferred_timeout_from_env`（默认 60s）相符；
3. **C-2 是这条最关键的设计**：只看 used 下降会被硬线裁剪骗过。这里同时核对了
   `session_history` 里 `_source` 的值——出现 `summarization` 而不是 `hard_trim`，
   证明走的是软线摘要路径。

## 4. 两个真实的「看不见」问题（不是 bug，但值得记）

### 4.1 用户永远收不到「压缩发生了」的通知

`compaction` 这个 SSE 事件**只在赛前路径发出**（`chat.py:491` 软线赛前分支、`:509` 硬线）。
赛后软线压缩发生在 `done` 之后，那时 SSE 流已经关了，**没有任何事件能通知用户**。

后果：用户看不到「刚刚压了」，只能通过页脚数字突然变小来猜。若压缩失败，更是完全静默
（`deferred_compact._run()` 里 `except Exception: logger.warning(...)`，不冒到用户面前）。

### 4.2 页脚数字会长时间停在压缩前的偏高值

`App.tsx:874` 在 `done` 之后 **180ms** 刷新一次 `/context`。
而赛后压缩通常要几十秒。所以页脚会停在「压缩前」那个数上，
直到用户切会话、再发一条、或重新加载页面才刷新。

**这正是 `440.8k / 400.0k · 110.2%` 能在截图里被拍到的原因**——
那个数字在当时是真的，只是几秒后就会降下来，而页脚不会自动再刷。

> 前一版文档（`docs/20261115-挑剔用户UI验收-卡顿多功能压缩与UX.md` §5）
> 把这记为「未复现」并推测「前端状态串了」。**那个推测是错的**，
> 此处更正：数字是真的，成因是「赛后压缩 + 页脚不自动刷新」，
> 与前端状态无关。同条件没复现出来，是因为我查的都是历史很短的新会话。

### 5.1 为什么不直接把窗口拉大 / 把软线挪回赛前

- **拉大窗口**不解决问题：判据是「单轮增幅 vs 剩余空间」，窗口越大剩余空间越多，
  但真正的问题（页脚不刷新、用户无感）一点没变；
- **挪回赛前**会让首个 token 重新多等 5~9s（P4 之前的状态），是明确倒退。

### 5.6 我在清理时又误删了一次（同源错误，留档）

清那 15 行时，我写了：

```sql
delete from session_generations
where user_id='u1' and generation_id like 'g_a2a_%'
  and user_id not in (select id from users)
```

自认为三个条件同时成立才安全。实际删了 **686 行**，而计划只有 12 行 ——
备份里 963 行中有 **674 行 user_id 就是 `u1`**（历史遗留账号，不在 users 表里），
其中大量 `generation_id` 带 `g_a2a_` 前缀。三个条件同时成立，被一起删了。

**与 2026-11-15 上午那次数据丢失完全同源**：拿「字段看着像测试」当删除判据，
而不是「备份里没有 + 明确指向不存在的实体」。**备份是唯一可信参照。**

已用 `--backup` 整表恢复，25 张表重新 `ALL MATCH`。
一条值得记住的判据：**删除前先算「备份里有多少行会被命中」**，
命中数远大于计划数就立刻停手 —— 这次如果先算这一步，就不会删。

### 5.4 这一轮里我自己制造的两个判据 bug（留档）

第一版 `ctx_settle_ui.py` 报了 G-4 / G-4b 失败，查证后**是脚本的错**：

1. **页脚解析崩溃**：`float(f.split(" / ")[0].replace("k",""))` 撞上前缀中文
   （`Hlaudz 可能会出错…`）抛 `ValueError`，被 `except: continue` 吞掉 ——
   于是「到 85% 停手」从未生效，`peak_pct` 永远是 0。改用正则精确取三段数字。
2. **「整理中」只在错误的时间窗口采样**：它真实出现在**充量循环第 6 轮**
   （日志里有 `41.2k / 40.0k · 100.0%（整理中…）`），而脚本只在最后的
   90 秒观察循环里检查，那时压缩早已结算。改成**每一轮结束后都采样 6 次**。

两个 bug 都是「观测器自己坏了」，与产品无关。这类错误在本项目反复出现
（见 `docs/20261115-挑剔用户UI验收…md` §6），所以修好后把它固化成可复跑的回归用例。

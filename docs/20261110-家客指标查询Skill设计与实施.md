# 家客指标查询 Skill（jiake-metric-query）设计与实施

> 日期：2026-11-10　状态：已实施　交付物：`work/jiake-metric-query.zip`（6 个文件 / 8 个条目）
> 关联：`docs/20261105-Skill目录包导入与公用技能设计与实施.md`（zip 导入与三层技能模型）

## 0. 结论

为 `sqlbot_mcp`（家客指标查表 MCP）实现了一套**静态技能包** `jiake-metric-query`：

- 与 agent / MCP **形态解耦、内容相关**：包里没有脚本、没有 URL、没有 agent 名，
  只有「业务语义 → 工具参数」的映射规则与实测契约；
- 渐进披露：`SKILL.md` 正文 6.4 K 字符进 `load_skill`，索引只占系统提示词一行；
  细节放在 4 份 `references/` 与 2 份 `assets/` 快照，模型按需用 `file_read` 读；
- 已装入公用层 `backend/skills_shared/`，所有用户可用，同时保留 zip 供界面导入。

## 1. 为什么需要它

`sqlbot_mcp` 是**专有业务领域**的 MCP：635 个指标、三张表、特定的粒度与区域编码约定。
只靠工具描述（每个一两句话）模型能查，但会稳定地踩同一批坑。实测确认的问题：

| 问题 | 模型不做指引时的典型表现 |
|---|---|
| 635 个指标里哪个是"千兆占比" | 凭印象编 `metric_ids`，或反复试错 |
| 占比指标量纲是 0–1 | 把 `0.397312` 说成 "0.4%"（应为 39.7%） |
| `zone_names` 多值是 AND | 对比广东+浙江 → 0 行 → 回答"没有数据" |
| `metric_compare` 的 delta = A − B | A/B 传反 → 把增长说成下降 |
| 演示数据不满足业务恒等式 | 用「分档之和 = 总数」校验 → 断言"数据有问题" |
| `run_readonly_sql` 的表白名单与单语句约束 | 直接写多语句 / 用不在库里的列（`module_name`、`unit`） |

这些**都是业务口径与工具边界知识**，不是模型推理能力问题——
正是 Skill 该承载的东西。MCP 给"能查"，Skill 给"会查"。

## 2. 解耦设计（形态解耦、内容相关）

| 维度 | 做法 |
|---|---|
| 无脚本 | 全部查询走 MCP 工具；包里没有 `.py`/`.sh`，不需要执行环境 |
| 无地址 | 不写 `http://127.0.0.1:8765`，只用「sqlbot MCP 的 12 个工具」这样的逻辑指代 |
| 无 agent 名 | 不出现 Hlaudz / GenericAgent 等调用方名字 |
| 用 `${SKILL_DIR}` | 附属文件路径写成 `${SKILL_DIR}/references/...`，加载时由平台替换成实际目录 |
| 快照与实时分离 | `assets/*.csv` 明确标注为"某一时点快照"，只用于猜关键词，落参数必须实时确认 |

换 MCP 实现时只需改 `references/tool-contract.md`；换数据源时改 `references/data-shape.md`
与 `assets/*.csv`；`SKILL.md` 的方法论（三步流程、口径陷阱）保持不变。

### SKILL.md 的 7 节

1. **三步固定流程** —— 定位指标 → 定区域时间 → 选工具，每步给参数表；
2. **工具选择矩阵** —— 10 种问题形态各对应哪个工具；
3. **口径陷阱** —— 7 条（量纲、A/B 方向、演示数据、层级、滞后、空结果排查）；
4. **`run_readonly_sql` 逃生口** —— 约束表 + 列名 + 写法要点；
5. **图表产出** —— `chart_spec` 的三步与硬约束；
6. **回答结构** —— 结论/口径/表格/变化/不确定项，以及 4 条禁止；
7. **自查清单** —— 8 个勾选项，回答前过一遍。

## 4. 内容来源：全部实测，不写推测

包里的每条结论都来自真实调用，而不是读代码猜：

| 结论 | 验证方式 |
|---|---|
| 指标字典**实际只有 2 列**（无 `module_name`/`unit`） | `PRAGMA table_info` + `table_schema()` 交叉 |
| `gran=1/3` 在演示库中 0 行 | `run_readonly_sql count(*)` 实测 |
| 占比量纲 0–1 | `metric_latest` 返回 `0.397312` 等 6 个占比指标逐个看 |
| `zone_names` 多值是 AND | `["广东","浙江"]` → 0 行；`["广东"]` → 1 行；`zone_ids=[106,108]` → 2 行 |
| `delta = A − B` | 两组 A/B 对调实测，符号相反 |
| 2+3+4 ≠ 1（34.9 亿 vs 1.14 亿） | `metric_latest` 四个指标同月取数 |
| 32 省之和 = 全国（巧合） | `level=1` 求和 vs `zone_ids=[99]` |
| 剧本 G 的跨指标 SQL 可跑 | `run_readonly_sql` 实跑返回 5 行 |
| `chart_spec` 长度不匹配会报错 | 故意传 1 个类目 + 2 个值 |
| 省级加总**精确等于**全国（汇总链路正确） | 3 个指标 × 32 省求和 vs `zone_ids=[99]`，差值 < 1 |
| 占比指标与绝对数指标互相矛盾 | `千兆用户占比 0.397312 × 总用户数 ≈ 4,534 万` vs `1000M及以上 = 1.1645 亿`（差 2.57 倍） |
| 省级「三档之和/总数」在 1.20（北京）~ 8.50（安徽）倍乱跳 | K3 真实对话中模型用 SQL 逐省算出 |

最后两条是**真实 LLM 跑 K3 时由模型自己发现的**，反过来补进了 Skill——
这是「Skill 指导模型」与「模型反馈 Skill」的闭环。

### 5.2 真实 LLM 对照验证（`work/_skill_llm_e2e.py` + `work/_skill_ab_clean.py`）

**对照必须干净**：Skill 装在公用层时，所有用户都能看到它，包括"对照组"。
第一版对照因此失效（两组都 `load_skill`）。第二版把目录改名到 `skills_shared/_stash_xxx`
仍失效——**改名后还在同一个扫描根下**，`_scan()` 照样扫得到，且索引按 frontmatter 的 `name`
注册（不是目录名）。第三版把 skill 移到 `work/`（扫描根之外）+ **重启后端清空 runtime 缓存**
才得到干净对照。这一步本身就是一个值得记录的坑。

三个问题分别针对三个最容易踩的坑：

| 用例 | 考察点 | 有 skill | 无 skill（干净对照） |
|---|---|---|---|
| K1 多省对比 | 是否用 `zone_ids` 而非多值 `zone_names` | 6 次调用 / 43.0s / 用 `zone_ids` | 6 次调用 / 33.6s，答对 |
| K2 千兆占比 | 0–1 量纲换算 | 4 次调用 / 25.3s | 6 次调用 / 8.8s，答对 |
| K3 档位恒等式 | 是否误判"数据有问题" | **12 次调用 / 124s** | **23 次调用 / 232s**，答对 |

**结论（诚实版）**：

1. 这三道题**模型本身都能做对**，包括干净对照——不能夸大成"没有 skill 就查不出"。
2. 差距主要在**效率与路径**：K3 一致性分析，有 skill 用 **12 次工具调用 / 124 秒**，
   无 skill 用 **23 次调用 / 232 秒**（接近一倍）。skill 让模型一开始就站在正确口径假设上，
   不用反复试错。
3. skill 的真实价值在**防错**而非补能力：它把「占比是 0–1」「zone_names 多值是 AND」
   「演示数据恒等式不成立」「市级不能加总」这些**一次踩坑要花几分钟才能自证**的知识前置了。
4. 无 skill 组 B1 一度**幻觉出一条不存在的规则**：「`month` 参数需要填 `2026-07-01`
   这种完整日期，填 `2026-07` 会返回空结果」。实测两种格式都返回 1 行——这正是
   没有权威契约时模型会"总结"出错误规则的风险，`references/tool-contract.md` 正是为此存在。

### 5.3 模型反过来修正了 Skill

K3 的两轮真实对话中，模型自己发现了两个我原先没写的事实：

1. **占比指标与绝对数指标互相矛盾**：`千兆用户占比 0.397312 × 总用户数 ≈ 4,534 万`，
   而 `1000M及以上 = 1.1645 亿`，差 2.57 倍；
2. **省级「三档之和/总数」在 1.20（北京）~ 8.50（安徽）倍之间乱跳**。

第三条（市级加总只有省级的 1/5）是我根据对照组的输出复核后补的。
三条都已写进 `SKILL.md` §3。这是「Skill 指导模型」与「模型反馈 Skill」的闭环。

## 6. 放置位置的建议（回答"放哪个目录"）

三种都支持，按用途选：

| 方式 | 位置 | 适用 |
|---|---|---|
| **公用层（已采用）** | `backend/skills_shared/jiake-metric-query/` | 想给所有用户用；随仓库分发；界面上只读，不会被用户改坏 |
| 界面 zip 导入 | `backend/data/skills/<user_id>/` | 单用户试用、或个人定制覆盖公用版 |
| 内置层 | `backend/skills_builtin/` | 认为它属于产品本体的一部分，和 `data-analysis` 同级 |

**为什么选公用层**：它是"专有业务领域知识"，该对所有用户生效；
同时保留 zip，便于没有仓库写权限的人自行导入。注意：
`skills_shared` 用 `invalidate_all()` 让所有用户立刻看到（`POST /skills/shared/import`），
直接 `cp` 到目录则需要重启后端才能作用于已缓存的 runtime。

## 9. 已知限制

1. **快照会过期。** `assets/*.csv` 是 2026-11-10 的快照；指标增删后需重新生成。
   包内已明确要求"落参数前必须实时 `metric_search`"，但模型仍可能直接用快照里的 id。
2. ~~`zone_names` 缺陷未在 MCP 侧修复~~ —— **2026-11-11 已在 sqlbot 侧修复**
   （`_zone_conds` 从 `and_` 改为 `or_`）。Skill 里对应的"已知缺陷 + 绕法"已改为
   "两种写法都可用"。同时 sqlbot 还修了另外 13 个问题（含 4 个 P0），
   详见 `sqlbot_mcp/docs/20261111-缺陷修复记录.md`。
   Skill 的 `tool-contract.md` 已同步新行为（hints / warnings / limit 夹取 /
   granularities_with_data / compare 支持 zone_names 与 level）。
3. **演示数据是随机生成的**（2+3+4 ≠ 1）。Skill 里写清了这一点，
   但它同时意味着"演示数据上的业务分析结论没有业务意义"，正式使用需换生产库。
4. **不覆盖写操作**：sqlbot 全程只读，Skill 也只描述查询。

## 9.1 下游 MCP 的修复（2026-11-11）

写这套 Skill 的过程反过来暴露了 sqlbot MCP 自身的 14 个缺陷，已在 sqlbot 仓库修复：

| 级别 | 问题 |
|---|---|
| P0 | `limit=-1` 返回 74 万行；`zone_names` 多值是 AND（两省对比返回 0 行）；CTE 一律被拒；`%` 搜出全表 |
| P1 | MySQL/PG 的 Decimal/date 无法 JSON 序列化（换库即全线失败）；compare 缺 zone_names/level；参数错误抛原生异常；未知表名静默返回全量 |
| P2 | time_options 全表 count；同月对比静默 0；空结果无诊断；FOR UPDATE 被静默改写后放行；SQLite 无语句超时 |

sqlbot 单测 22 → 83，4 组反向确认，真实 HTTP 复验 23 项、真实 LLM 回归 21 项全通过。
受益于此，Skill 可以删掉两处"绕法"说明：

- `zone_names` 多值不再需要改写成 `zone_ids`；
- 空结果有 `hints`，`time_options` 直接给 `granularities_with_data`，
  Skill 里的排查清单相应简化。

## 0. 结论与范围

**做法：读侧用 attachment 通道（复用现有 `message_injector`），写侧用后台 forked 子代理
（复用现有 `subagent` 运行时），存储用每用户目录 + DB 索引。**

三条硬约束先写在最前面：

| 约束 | 落地方式 |
|---|---|
| **区分用户**（用户明确要求） | 物理隔离 `backend/data/memories/<user_id>/`，路径解析统一走 `workspace._resolve_under()`；DB 表 `memories` 每行必带 `user_id`，所有查询强制带 `user_id` 条件 |
| **不破坏现有契约** | 不新增 SSE 事件名；复用 `message_injected`；前端只加一种 `INJECTED_KINDS` 前缀 |
| **不让记忆拖慢首 token** | 读侧走已有的「每轮开头注入」点，且**只在有内容时**注入；写侧完全后台，不阻塞本轮 |

## 1. 为什么是 attachment 通道（而不是塞进 system prompt）

CC 侧的结论（调研文档 §0、§1.5）：记忆是 attachment producer，不是 hook，也不是
system prompt 的一部分。理由对 Hlaudz 同样成立：

| | 塞 system prompt | attachment 通道 |
|---|---|---|
| 何时算 | 装配时一次算好 | **每轮按需算** |
| 能否关 | 难（要改装配逻辑） | 容易（producer 返回空数组） |
| 能否计量 | 难 | 每条可单独计时/计体积 |
| 会不会膨胀 | **会**（记忆越攒越多，直接挤爆上下文） | 不会（有预算 + 扣留） |
| 用户能看到吗 | 看不到 | **能看到**（前端已有 `injected_message` 渲染） |

最后一条对本项目是决定性的：Hlaudz 的前端已经有 `InjectedNote` 组件（可折叠、
带来源标签），`message_injected` 事件也已经在 `chat.py` 里持久化成
`{"type": "injected_message"}` block。**记忆注入直接复用它，前端改动只有一行分类规则。**

### 1.1 Hlaudz 现成的注入点（不需要新建管线）

**注入点的真实位置是 `backend/app/agent_loop.py:353`**（不是早期版本的 `:305`——`:305` 是
`_flush_injector()` 里的 `guard.flush()` 收尾，不是通道本身）：

```python
# agent_loop.py:353-363（每轮模型调用前）
if self.message_injector is not None:
    guard = self._injector_guard_now()
    injected, inject_timed_out = await guard.collect()
    if inject_timed_out:
        yield {"type": "injector_timeout", "timeout_s": self._injector_timeout_s}
    for msg in injected:
        history.append(msg)
        yield {"type": "message_injected", "text": msg.get("content", "")}
```

这个钩子**每轮模型调用前**都跑一次，正好是 CC 里 `dc(...)` producer 的执行时机。
现有使用者有三个：

| 注入器 | 位置 | 注入什么 |
|---|---|---|
| `_steer_aware` 用户插话 | `sse.py:106`（装）/ `:82`（`_ensure_steer_injector` 定义） | `steer_queue` drain |
| subagent 通知 | `subagent/host.py:162` | 子代理完成通知 |
| team 收件箱 + 通知 | `subagent/session.py:299` | teammate 消息 |

**记忆是第四个使用者**，加在同一个 fold 点。这是最小改动，也是契约最稳的做法
（不改事件名、不改 `AgentLoop` 签名、不改前端块类型）。

#### ⚠️ 注入通道已经被 `InjectorGuard` 包过一层，方案必须尊重它的语义

`agent_loop` 不再直接调用 `message_injector`，而是通过 `backend/app/injector_guard.py`
的 `InjectorGuard.collect()`。这个 wrapper 有三条**与记忆注入直接相关**的语义：

| 语义 | 实现 | 对记忆注入的约束 |
|---|---|---|
| **支持异步注入器** | `collect()` 里 `if not inspect.isawaitable(raw)` 才走同步快路，否则 `ensure_future` + `shield` | §3.3 的 `compose_injectors` **不能拒绝 awaitable**（旧草稿里的 `raise TypeError` 是错的，会直接打断团队路径） |
| **超时不丢消息** | `wait_for(shield(task))` 超时后把 task 留给下一轮，`collect()` 下一轮优先取它 | 记忆注入若慢，本轮只是「没有记忆」，下一轮会补上——**这正是 §3.5 延迟注入想要的语义，不用自己实现** |
| **上一轮迟到结果优先** | `if self._task is not None and self._task.done(): return 它, False`，不再调用注入器 | 组合层的「每轮都跑一遍」假设不成立：某一轮可能拿到的是上一轮的结果。记忆块要能容忍晚一轮 |

默认超时 8s（`DEFAULT_INJECTOR_TIMEOUT_S`），必须大于 DB 的 `busy_timeout=5000ms`；
可用 `HLZ_INJECTOR_TIMEOUT_S` 调整。**记忆注入的预算是「不能接近 8s」**——
它只该做一次文件读 + 一次 DB 查询（§7 的 S-M5 测的就是这条）。

前端分类规则在 `frontend/src/components/MessageList.tsx:446` 的 `INJECTED_KINDS`，
现在是三条（steer / 子代理完成 / 团队消息），加 `[记忆]` 是第四条。

## 2. 数据模型（每用户隔离的落点）

### 2.1 目录布局与记忆类型

```
backend/data/memories/<user_id>/
    private/                 # scope = private
        MEMORY.md            # 入口索引：标题 + 一行 description + 指向文件，不存正文
        <slug>.md            # 单条记忆：frontmatter + 正文
    team/                    # scope = team（第一版不启用，仅留目录）
        <team_key>/
            MEMORY.md
            <slug>.md
    .index.db                # 可选：仅用于快速列举的 SQLite 索引（正文永远在 .md）
```

> **目录按 `scope` 分，不按 `type` 分。** 记忆的「类型」写在 frontmatter 的
> `metadata.type` 里（CC 原文：`type: user | feedback | project | reference`），
> 而「作用域」决定物理落点。本方案第一版只有私有记忆，所以 `private/` 下平铺，
> `type` 只影响注入排序与提示词，不影响路径。

#### 四类记忆与各自的默认作用域（v3 §5.7，按 CC 原文对齐）

| type | 记什么 | 默认 scope | CC 原文 |
|---|---|---|---|
| `user` | 关于这个人：称呼、角色、语气、长期偏好 | **always private** | `<scope>always private</scope>` |
| `feedback` | 用户对工作方式的纠正**和确认** | private（明显是全项目约定才 team） | 见下方「确认也算反馈」 |
| `project` | 跨会话的项目状态：做到哪、遗留什么、谁在做什么 | private 或 team，**强烈倾向 team** | — |
| `reference` | 外部资源指针：URL、看板、工单号 | **usually team** | `<scope>usually team</scope>` |

**关键修正**：作用域**不是**「private / team 自由两档」，而是**每类自带默认值**。
CC 的四类定义（`m0293:3849` 的 `dho`）里，`user` 硬编码 always private、`reference`
硬编码 usually team，中间两类才谈得上选。照抄「两档自由选」会丢掉这个方向性。

Hlaudz 现在没有团队/组织概念，所以：**四类全部落 `private/`**，`<scope>` 段仍写进提示词
（保留语义给未来的 team 层），但代码不按它分目录。`team/` 目录第一版不创建。

> 旧版写的是 `personal` / `project` 两个目录 + `fact/preference/feedback/project` 四种 kind，
> 那是把 CC 的「作用域」和「类型」混成了一层，已废弃。

#### `MEMORY.md` 是入口，不是注入源

CC 把 `MEMORY.md` 排除出**目录扫描候选集**（`B3e()` 的 `excluded: Set(["MEMORY.md"])`，
v3 §3 第 11 条），只让模型用工具按需读。我们照抄：自动注入只注入「最近 N 条 / 关键词命中的条目」，
入口文档靠 `memory_list` + `memory_read` 读。

⚠️ 注意别把这条和另一件事混了：`MEMORY.md` **作为索引仍然会进上下文**，
在 CC 里走的是 `instructions` attachment（见 §3.5）。「排除出候选集」说的是
**别把它当成一条普通记忆重复注入两遍**，不是「它永不进上下文」。

### 2.2 DB 表（索引 + 审计，正文不入库）

```sql
CREATE TABLE IF NOT EXISTS memories (
    id          TEXT PRIMARY KEY,
    user_id     TEXT NOT NULL,           -- ← 隔离的关键：每行必带
    scope       TEXT NOT NULL DEFAULT 'private',    -- private | team（默认值按 type 推导，见下）
    team_key    TEXT NOT NULL DEFAULT '',           -- scope='team' 时才用
    slug        TEXT NOT NULL,           -- 文件名（不含 .md）
    title       TEXT NOT NULL DEFAULT '',
    description TEXT NOT NULL DEFAULT '', -- 一行描述：给相关性选择器读，不是给人读的
    tags        TEXT NOT NULL DEFAULT '[]',  -- JSON 数组，用于关键词命中
    kind        TEXT NOT NULL DEFAULT 'user', -- user | feedback | project | reference
    path        TEXT NOT NULL,           -- 相对 memories/<user_id>/ 的路径
    created_at  INTEGER NOT NULL,
    updated_at  INTEGER NOT NULL,
    hit_count   INTEGER NOT NULL DEFAULT 0,
    last_hit_at INTEGER NOT NULL DEFAULT 0,
    UNIQUE (user_id, scope, team_key, slug)   -- ← 同用户同作用域内唯一
);
CREATE INDEX IF NOT EXISTS idx_memories_user ON memories (user_id, scope, updated_at DESC);
```

三处改动相对旧版：

1. **`kind` 枚举换成 CC 的四类**（`user | feedback | project | reference`），默认 `user`。
   旧的 `fact/preference/feedback/project` 是把类型和作用域混了，见 §2.1。
2. **`summary` 改名 `description`**。这不是改着玩：CC 的 frontmatter 注释原文是
   「used to decide relevance **in future conversations**, so be specific」
   （`m0293:3847`，v3 §5.3 复核确认），它的消费者是**相关性选择器**，不是渲染器。
   叫 `summary` 会让人以为「短就行」，实际要求是「具体到能判断相关性」。
3. **`project_key` 改名 `team_key` 且默认空**。旧版的 `project_key` 是「代码库」维度，
   CC 没有这个概念（它的维度是 private/team 两种作用域）；Hlaudz 要预留的是
   **团队**维度，不是项目维度。

> `scope` 的默认值由 `kind` 推导，不由调用方随便填：
> `user → private`（强制）、`reference → team`（默认，可覆盖）、
> `feedback`/`project` 默认 `private`、显式指定才 `team`。
> 第一版因为无团队层，`write_memory()` 里直接强制 `scope='private'`、`team_key=''`。

**为什么正文不入库**：

1. 与 CC 一致（记忆是 `.md`，模型能 `file_read` / `file_patch` 直接改）；
2. 用户可以在设置页直接编辑/删除（文件即真相，不会出现「库里有、文件没了」的分裂）；
3. 单条记忆可能几千字，塞进 SQLite TEXT 会让 `session_history` 那套接口变重。

**为什么还要 DB**：列举（「我这个用户有哪些记忆」）、排序（最近更新/最常命中）、
审计（谁在什么时候写的）都需要索引，扫目录做不了高效排序。

### 2.3 隔离的三道保证

| 层 | 保证 | 实现 |
|---|---|---|
| 路径 | 写不进别人的目录 | `workspace._resolve_under(memories_root(user_id), candidate)` —— 已存在且经过测试（`PathSecurityError`） |
| 查询 | 读不到别人的行 | 所有 `db.*_memory()` 函数**签名第一个参数就是 `user_id`**，SQL 里 `WHERE user_id = ?` 是硬条件 |
| 注入 | 上下文里不混入他人记忆 | 注入器在装配时绑定 `user_id`（来自 `AgentContext`），**不读请求参数** |

第三条最容易出错：注入器必须是**闭包捕获 `user_id`**，不能在函数里从
`sessions` 表反查——那会在 A2A / 子代理路径上取到错误的主体。
`subagent/session.py:299` 的 `_lead_injector` 已经用 `team_ctx.user_id` 闭包，
记忆注入器照同样的写法。

### 3.3 注入器：链式组合，不覆盖

`sse.py` 里现有的 `_ensure_steer_injector()`（`sse.py:82`，在 `:144` 被调用）是**直接赋值**
`loop.message_injector`，并且用 `loop._steer_aware` 标记「本注入器已经 drain 过用户队列」
（team 路径 `subagent/session.py:312` 也置这个标记），避免同一条消息被两个注入器各取一次。

加记忆时不能改它的语义，也不能简单地再赋一次值（后赋的会覆盖前面的）。
必须加一层组合，并且**尊重 `_steer_aware`**。

**组合层必须支持异步注入器**——现有三个注入器里 `subagent/host.py:162` 的
`node.drain_pending` 和 team 的 `_lead_injector` 都可能是协程，
`InjectorGuard.collect()` 本来就是按 `inspect.isawaitable` 分路的。组合层若拒绝 awaitable，
装上去会直接打断团队路径：

```python
# 新文件 backend/app/memory_inject.py
async def compose_injectors(*fns):
    """按顺序跑多个注入器，结果拼接。任一失败不影响其他。

    必须返回协程：注入点（InjectorGuard.collect）对 awaitable 走异步路，
    组合层统一成协程是最省心的形态——同步注入器在里面直接调用即可，
    不需要调用方判断。
    """
    async def _combined() -> list[dict[str, Any]]:
        out: list[dict[str, Any]] = []
        for fn in fns:
            try:
                got = fn()
                if inspect.isawaitable(got):
                    got = await got
                out.extend(got or [])
            except Exception:
                logger.warning("注入器失败，跳过：%s", fn, exc_info=True)
        return out
    return _combined
```

> 旧草稿这里写的是 `raise TypeError("compose_injectors 只接受同步注入器")`，
> **是错的**：会让团队/子代理路径的异步注入器在组合后被当成异常吞掉，
> 表现为「记忆能注入、团队消息静默消失」。

注意 `_steer_aware` 的语义是「**已经有**注入器在 drain 用户插话队列」，
不是「不许再装注入器」。所以记忆注入器的安装不能因为 `_steer_aware` 为真就跳过——
它只会导致「记忆永远不注入」。正确做法是把记忆注入器**包在现有注入器外面**：

```python
existing = loop.message_injector
loop.message_injector = compose_injectors(memory_fn, existing) if existing else memory_fn
```

**注意 `InjectorGuard` 的惰性绑定**：`agent_loop.py:160` 的 `_injector_guard_now()`
会在发现 `message_injector` 换了新对象时重建 guard（比较 `_injector_guard_for is self.message_injector`）。
所以包装必须在 `run_stream` 之前完成——在轮中途改 `message_injector` 会丢掉进行中的后台 task。


装配顺序（在 `subagent/session.py` 与 `sse.py` 两处分别改，语义保持一致）：

```
[记忆] -> [steer 用户插话] -> [子代理通知] -> [team 收件箱]
```

记忆放最前面，理由：它是「背景知识」，应该出现在用户新指令之前；
后面的都是「本轮新发生的事」，放在更靠近当前指令的位置更符合注意力分布。

#### ⚠️ 同一条记忆在一个 generation 内只注入一次

注入器挂在 `agent_loop.py:353` 的 **`while turn` 循环里**，不是每 generation 一次。
一个用户轮次如果触发 10 次模型调用（读文件、跑测试、改代码……），
同一批记忆就会被 append 进 history **10 次**。

后果不是「浪费 token」那么简单：模型会看到 10 段几乎相同的记忆，
容易把它当成强调指令，行为变得僵化。而且每次重复都占预算。

**CC 怎么处理的**：靠 `Mvi` 的 `THn` 过滤（`m0591:153994`），
即拿 `readFileState` 里「已经进过上下文的路径」逐条过滤——
**去重的键是「路径集合」，不是布尔标志**（见 `docs/20261114-CC319记忆触发时机核实.md` §5.1）。

**Hlaudz 照抄这个键**，用 per-generation 的 slug 集合：

```python
_injected_slugs: set[str] = set()      # per-generation，闭包持有

def memory_injector() -> list[dict]:
    if not _enabled():
        return []
    candidates = _select(...)                                  # §3.2 的选择
    fresh = [m for m in candidates if m.slug not in _injected_slugs]   # ← 逐条过滤
    if not fresh:
        return []                                              # 没新增内容 → 本轮不注入
    _injected_slugs.update(m.slug for m in fresh)
    return [{"role": "user", "content": _format(fresh), "_volatile": True}]
```

**为什么不用布尔标志**：第一轮注入了 A，第三轮后台提取产生了 B，
布尔标志会让 B 永远注入不进去。用 slug 集合就没有这个问题。

`_injected_slugs` 的生命周期绑定在 `message_injector` 闭包上，而闭包在每次
`run_agent_stream` 里重建（`sse.py:144` 每轮调用 `_ensure_steer_injector`），
所以天然是 per-generation 的。

> 注意「本轮没有新内容」时**不能**停止尝试：下一轮后台写完新记忆后仍要能注入。
> 逐条过滤天然满足这点——`fresh` 为空就不注入，非空就注入新的那几条。
> 这与 §3.7 的「未 settle 就留到下一次模型调用」是同一原则。

### 3.6 预算单位：code unit 不是字节（v3 §1.3）

v2 全文把索引 cap 写成「25 KB 字节」，**错了**。源码里那个变量名就叫 `byteCount`，
但它取的是 `trimmed.length`——JS 字符串长度，即 **UTF-16 code unit**：

```js
// m0194_0x11642aa3.js:15-23
function z2e(t) {
  let trimmed = t.trim();
  return { trimmed, lineCount: Dt(trimmed, "\n") + 1, byteCount: trimmed.length };  // ← .length
}
```

`LEr()`（`m0293:4448`）用 `byteCount > Gee` 判断，`Gee = 25000`。源码把它命名成 `byteCount`
是**起错的名字**，v2 照抄了这个名字。

旁证（方法论 §1 的优先级：提示词原文 > 变量名）：`LEr` 的超限文案（`m0293:4478`）写的是
`` `everything after the first ${w.length} characters of line 1 was cut off` ``
—— 面向用户的字符串说 `characters`，不是 `bytes`。

**两个 cap 单位不同，别混：**

| cap | 常量 | 单位 | 计法 | 中文含义 |
|---|---|---|---|---|
| 索引（`MEMORY.md`） | `Gee = 25000` | **UTF-16 code unit** | `.length` | ≈ 25,000 个汉字 |
| 单文件召回 | `Ibe = 4096` | **真字节** | `Buffer.byteLength` | ≈ 1,300 个汉字 |

行数 cap 都是 `W2e = 200` 行（`m0194:9-14` 的 `lm/YF/Gee/W2e/Ibe` 五个常量）。

**对 Hlaudz 的直接后果**：若按「25 KB 字节」实现中文索引截断，
**中文索引会在约 1/3 处被截**（UTF-8 下一个汉字 3 字节，25000 code unit ≈ 75 KB）。
这是可见的功能缺失，不是精度问题。

配置项相应改成两个独立常量，不要用一个 `MEMORY_INDEX_BUDGET` 混着：

```python
MEMORY_INDEX_MAX_LINES   = 200        # 行数 cap，两种场景共用
MEMORY_INDEX_MAX_CHARS   = 25_000     # ← code unit（Python 里 len(str) 就是 code point，中文场景够用）
MEMORY_RECALL_MAX_BYTES  = 4_096      # ← 真字节，len(s.encode("utf-8"))
```

> Python 的 `len(str)` 数的是 **code point**，与 JS 的 UTF-16 code unit 在 BMP 内一致；
> 只有 emoji / 扩展区汉字（surrogate pair）会差一倍。记忆文本这两个都罕见，
> 第一版按 code point 实现即可，在注释里写明这个差异。

### 3.7 并发预取：LLM 相关性选择器 + 首帧不等（**可选增强，默认关闭**）

#### 为什么增强形态值得做（但不是必须）

关键词命中的根本问题是**它不知道用户在问什么**。用户问「上次那个报错怎么解决的」，
一条标题为「构建失败处理」的记忆应该命中，但两者没有共同词。
选择器把「记忆清单 + 本轮查询」送一次小模型，让它输出选中项。

代价很实在：**每次模型调用多一次小模型调用**。所以必须先量（S-M6/S-M7）再决定。

```js
if (xt && xt.settledAt !== null && xt.consumedOnIteration === -1) {
  let R = Mvi(xt.screen(await xt.promise, [...N, ...ie, ...it]), ...);
  for (let j of R) { let ae = createRecord(j, D); yield ae, it.push(ae); }
  xt.consumedOnIteration = turnCount - 1;
}
```

三个条件缺一不可：**已 settle**（算完了）、**还没消费过**、在工具步骤之后。
若首帧回来时选择器还没算完（`settledAt === null`），**这一轮就不注入**，
留到下一轮再看 —— 这就是「不拖慢首 token」的全部秘密。

#### 入口条件（`Ivi` 开头，逐条对齐）

| 条件 | CC 原文 | Hlaudz 落法 |
|---|---|---|
| 有选择器 | `if (!h) return`（`n.memorySelector`） | `HLZ_MEMORY_SELECTOR=1` 才创建句柄 |
| 非子代理 | `n.agentId` → 不跑 | 注入器里判断 `ctx.agent_id`，子代理直接返回 `[]` |
| 特定 querySource 不跑 | `Gzr = {extract_memories, auto_dream, memdir_relevance, prompt_suggestion, compact}` | 记忆提取器、dream、选择器自己、压缩都不触发自身 |
| 有被测文本 | `findLast(m => m.type==="user" && !m.isMeta)` | 取最后一条非注入的 user 消息 |
| 非空白查询 | `if (!N \|\| !/\s/.test(N.trim())) return` | 纯单字/空串不跑（省一次模型调用） |
| 会话字节预算 | `jzr(e).totalBytes >= MAX_SESSION_BYTES(61440)` → 不跑 | 整会话累计召回上限 60 KB |

`Gzr` 那条防的是**自激**：选择器自己若触发选择器，会无限递归。

#### Hlaudz 实现：`backend/app/memory_prefetch.py`

现有 `message_injector` 是**每轮同步返回**的形态，装不下「启动→稍后消费」。
所以预取句柄**不能**放进注入器，必须挂在 `AgentLoop` 的轮循环上，对齐 CC 的两个点：

```python
# backend/app/memory_prefetch.py
class PrefetchHandle:
    """预取句柄。不 await，只启动；消费时若未完成则返回空。"""
    __slots__ = ("promise", "settled_at", "consumed_on_iteration")

    def __init__(self, coro):
        self.promise = asyncio.ensure_future(coro)
        self.settled_at: float | None = None
        self.consumed_on_iteration: int = -1
        self.promise.add_done_callback(lambda _t: setattr(self, "settled_at", time.monotonic()))

    async def take(self, turn: int) -> list[dict]:
        """消费：已 settle 且未消费过才返回内容，否则空。"""
        if self.settled_at is None or self.consumed_on_iteration != -1:
            return []
        self.consumed_on_iteration = turn
        try:
            return await self.promise
        except Exception:
            logger.warning("记忆预取失败，本轮不注入", exc_info=True)
            return []


def start_prefetch(ur, history: list[dict], *, query_source: str) -> PrefetchHandle | None:
    """入口闸全部通过才返回句柄，否则 None（对齐 CC 的 Ivi 早退）。"""
    if not _enabled() or not _selector_enabled():
        return None
    if getattr(ur.ctx, "agent_id", ""):        # 子代理不跑
        return None
    if query_source in _NO_SELF_TRIGGER:       # 防自激
        return None
    query = _last_user_text(history)
    if not query or not re.search(r"\s", query.strip()):
        return None
    if _session_bytes(history) >= MAX_SESSION_BYTES:
        return None
    return PrefetchHandle(_select_and_read(ur, history, query))
```

在 `agent_loop.py` 的轮循环里挂两个点（对齐 CC 的 `:7294` 与 `:10602`）：

```python
# 轮循环开始前（首帧之前）—— 只启动，不等待
prefetch = start_prefetch(self, history, query_source=self.query_source)

while turn < self.max_turns:
    turn += 1
    ...  # 模型调用、工具执行

    # 工具步骤之后 —— 若预取已 settled 且未消费，注入
    if prefetch is not None:
        for msg in await prefetch.take(turn):
            history.append(msg)
            yield {"type": "message_injected", "text": msg.get("content", "")}
```

**为什么挂在 `AgentLoop` 而不是注入器**：注入器每轮开头就要返回值，
而预取的意义正是「这一刻可能还没有值」。挂在轮循环上才能表达
「第一轮工具步骤后再看」。

#### 选择器本身：JSON schema 输出，最多 5 条

CC 的 `QGr`（`m0591:151472`）是一次结构化输出调用，要点：

- 输入 = `- [type] filename (ISO时间): description` 格式的清单（`T7r()`，`m0591:68862`）
  + 本轮查询；
- 输出 JSON schema `{selected_memories: [...]}`，**硬上限 5 条**（`.slice(0, 5)`，`:153870`）；

- 给 thinking 留 `VGr = 512` 额外 token（`:151504`）；
- 系统提示词 `KGr`（`:151404`）含三句硬约束，**逐字可抄**：
  1. 最多 5 条；

#### 会话级字节预算（防「记忆越聊越多」）

`j0n.MAX_SESSION_BYTES = 61440`（`m0591:151688`），`jzr`（`:153878`）统计
**整个会话累计**注入过的 `relevant_memories` 内容长度。超了就**不再召回**，

#### 首句免责（必须照抄）

`Zoo.relevant_memories`（`m0591:229587`）的第一句是硬约束：

> `Retrieved for possible relevance — use only if it actually applies to what the user asked.`

中文版：**「以下内容仅为可能相关，确实适用于用户当前问题才使用。」**
没有这句，模型倾向于把召回结果当既定事实全盘套用。

#### 遥测：`hidden_by_first_iteration`

CC 的 `[Symbol.dispose]` 里记这个指标（`:153967`）：

```js

```

它直接度量「预取白做了」——settle 了但首轮没赶上。Hlaudz 记同名指标到日志，
用来判断预取预算（选择器用什么模型、超时多少）是否合理。

#### 与 §3.2 关键词排序的关系

两者不是二选一：

| 场景 | 用哪个 |
|---|---|
| 选择器关闭（`HLZ_MEMORY_SELECTOR=0`，**默认**） | **§3.2 的关键词 + 优先级排序**（同步、零成本） |
| 选择器开启且已 settle | **§3.7 的 LLM 选择结果**（更准） |
| 选择器开启但没算完 | §3.2 兜底，或留到下一次模型调用 |

**默认走 §3.2**，与 CC 的默认形态一致。§3.7 是可选增强，
必须先量清楚它对 TTFT 和成本的影响（S-M6 / S-M7）再决定是否打开。

#### ⚠️ 预取是**每次模型调用**一次，不是每次 generation 一次

这一点初稿也写错了，已按核实文档 §5.1 更正。

`Ivi` 的调用点在 `Wc`（query 主生成器，`m0848:7294`），而 `Wc` **每次模型调用都会重新进入**。
所以一次用户轮次里如果触发 10 次模型调用（读文件、跑测试、改代码……），
预取就会**启动 10 次**，选择器也会**被调用 10 次**。

那么重复注入是怎么避免的？靠 `Mvi` 的 `THn` 过滤（`m0591:153994`）：

```js
let S = y.memories.filter(w => !THn(n, w.path, s));   // n.readFileState：已进过上下文的路径
```

**去重的键是「路径集合」**（`readFileState`），不是布尔标志。
一条记忆进过一次上下文后，后续模型调用再预取到它会被滤掉。

**对 Hlaudz 的含义**：§3.3 里「一个 generation 只注入一次」的写法要改成
**按 slug 集合去重**：

```python
_injected_slugs: set[str] = set()      # per-generation

def memory_injector() -> list[dict]:
    candidates = _select(query_hint=..., ...)
    fresh = [m for m in candidates if m.slug not in _injected_slugs]   # ← 逐条过滤
    if not fresh:
        return []
    _injected_slugs.update(m.slug for m in fresh)
    return [{"role": "user", "content": _format(fresh), "_volatile": True}]
```

布尔标志的问题：第一轮注入了 A，第二轮记忆更新产生了 B，布尔标志会让 B 永远注入不进去。
用 slug 集合就没有这个问题。

#### 成本提醒：选择器会让「每次工具步骤」都多一次模型调用

这是不默认打开它的**主要理由**，比「多花点钱」严重得多：
一个复杂任务 10 次模型调用 = 10 次额外的小模型调用。若选择器用主模型，
成本直接翻倍。真要开，必须：
1. 用**独立的小模型**（`HLZ_MEMORY_SELECTOR_MODEL` 必须指定，不允许留空用主模型）；
2. 加**每 generation 的次数上限**（建议 3 次，不是 10 次都跑）；
3. 用 `hidden_by_first_iteration` 监控「预取白做了」的比例。

## 4. 写侧：后台 forked 子代理

### 4.1 为什么不能「同步写」

CC 用 `post_turn_memory` 后台任务（调研文档 §1.5），原因有二：

1. **写记忆要跑模型**（判断该记什么、怎么组织），同步做会直接加在用户等待时间上；
2. **写记忆可能失败/被拒**（权限、hook），不能影响主对话的成败。

Hlaudz 已有同等能力：`SubagentHost`（P2）+ `ProcessLease` + 停止级联。
**写记忆的子代理可以完全复用这套，不需要新运行时。**

### 4.1.1 CC 到底什么时候写（`docs/20261114-CC319记忆触发时机核实.md` §1）

**不是常驻后台，是「每个用户轮次结束」尝试一次。** 调用链：

```
模型停止输出
  → Jd()                     m0848:3829   ← 停止钩子阶段
    → executeExtractMemories  m0848:3852
      → ir()                  m0832:1250
        → ar()                m0832:1259  ← 闸门
          → Le()              m0832:922   ← 真正的四道闸
```

**而且文件模式下还有一道外层闸**（核实文档 §1.2）：

```js
if (!I && !v("tengu_passport_quail", !1) && !er()) return;   // m0832:1278
```

`tengu_passport_quail` **代码默认 false**。所以严格说：CC 是「每轮尝试，
但默认配置下多数情况被这一行挡掉」。这一点 v2/v3 都没记录。

**没有常驻后台循环、没有 idle 检测。** 文件模式下也没有 `idle_flush`
（那是 MCP 模式专属，`m0832:860` 的 `q()`）。

**是不是模型自己决定何时写？** **看开关**，这一点初稿说得太简单了。

`V$t()`（`m0191:2591`）决定「谁来写」：

```js
function V$t() {
  if (fet() !== null) return !0;                    // ① MCP 模式恒真
  if (!v("tengu_passport_quail", !1)) return !1;     // ② 旗标，默认 false
  return !ye() || v("tengu_slate_thimble", !1);      // ③ 交互会话
}
```

`ye()`（`m0040:5124`）= `!isInteractive()`。所以**默认交互式 CLI 里 `V$t()` 是 false**。

两种形态（核实文档 §4）：

| | `V$t()` 真（自动提取） | `V$t()` 假（**默认**） |
|---|---|---|
| 谁写 | 代码在轮次结束派 fork 子代理 | **模型自己在对话里调 `memory_write`** |
| 时机 | 后台，用户无感 | 前台，占当前轮工具步骤 |
| 约束来源 | 提取提示词（§4.5） | 主 `SYSTEM_PROMPT` 的 auto-memory 段 |

**所以「模型自己决定何时写」在默认配置下反而是对的**——代码那一层被 `tengu_passport_quail`
挡掉了，只剩模型主动调工具这条路。

**Hlaudz 的取舍：两者都要。** CC 的两形态是互补而非二选一，但对 Hlaudz 更合适的是
两态并存——模型随时可 `memory_write`（M2 的显式工具），后台每 N 轮兜底提取（M4，
捕获模型没主动记的）。Web 用户的对话轮次更碎，只靠模型自觉漏记率会高。

**没有常驻后台循环、没有 idle 检测。** 文件模式下也没有 `idle_flush`
（那是 MCP 模式专属，`m0832:860` 的 `q()`）。

### 4.1.2 它挂在 hook **阶段**里，但不是 hook 机制

这个区分重要，因为它决定 `settingsHooksOff` 一类的开关会不会误伤。

**时机上**：`Jd` 由 `Ea` 调用，而 `Ea` 的对外名是 `throughStopHooks`（`m0848:10414`）。
`Jd` 开头两道闸（`:3830` 的 `_n()`、`:3834` 的 `settingsHooksOff`）——
**`settingsHooksOff` 为真时记忆提取也不会跑**。

**机制上**：它不走 hook 引擎、不读用户 `settings.json` 里的 `Stop` 配置、
不参与 `blockingErrors` 判定。它是在那个**阶段**里的一次普通函数调用。

**执行上**：`sA({...})` 起一次独立的模型调用（fork 子代理），有自己的 turns 和工具集。

一个「轮次收尾」阶段里并挂了五件互不相关的事（`m0848:3849-3876`）：

| # | 事情 | 行号 |
|---|---|---|
| 1 | post-turn summary | `:3849` |
| 2 | **记忆提取** | `:3852` |
| 3 | **dream 合并** | `:3859` |
| 4 | prompt suggestion | `:3850` |
| 5 | brief mode 强制检查 | `:3864` |

**每件各自 try/catch，互不影响**（`:3853-3858` 就是提取的那段）。这是有意的设计：
摘要失败不该拖累记忆提取。

**Hlaudz 的落法**：

```python
# agent_loop.py 的轮次结束处（yield done 之前）
async def _on_turn_end(self) -> None:
    """一轮结束时的侧边任务。每件独立 try/except，互不影响。"""
    for task in (self._maybe_extract_memories, self._maybe_dream):
        try:
            await task()          # 内部各自判断闸门，不满足立即返回
        except Exception:
            logger.warning("[turn_end] %s 失败", task.__name__, exc_info=True)
```

**别做成「一个失败全跳过」**——CC 的五件事各自独立，这是有意的。

Hlaudz 没有 `settingsHooksOff` 这种全局开关，但**应当有等价物**：
`HLZ_MEMORY_DISABLED=1` 时提取与 dream 都不跑（排障时的第一道出口）。

### 4.2 四道闸门（顺序照抄 CC 的**文件模式**路径）

⚠️ **先纠正一个容易踩的坑**：CC 的八道闸门不是平铺的，也不是「1–4 通用、5–8 仅 MCP」。
按源码逐行看 `Le()`（`m0832:922`–`:1050`），**`first_look` 属第 8 道，且唯一调用点在

完整归属（`config_2 = fet()`，来自 `CLAUDE_CODE_POST_TURN_MEMORY_CONFIG`；为 `null` 即文件模式）：

> 若照旧方案实现，等于给文件模式凭空加了一道 CC 没有的闸，且默认 `shadow` 时它不拦，

```python
# backend/app/memory_write.py
async def maybe_extract_memories(ur, session_id: str, generation_id: str,
```

#### 若将来要加 `first_look`（可选增强，非对齐项）

CC 的 `first_look` 是**为 MCP 模式省钱**设计的（MCP 模式下每轮都可能有大量新消息）。
Hlaudz 第一版不加。将来若要加，注意它的三个细节：

- 三模式 `off` / `shadow` / `enforce`（`:1015` 读配置、`:1094` shadow 日志、`:1034` enforce 判定）；
- 硬超时 `jt = 20000`（20s，`:330`）、`maxRetries: 0`（`:458`）——不重试是刻意的，
  这闸是省钱用的，重试会让它自己变贵；
- **失败方向保守**：模型没按格式答出布尔值 → **不跳过**
  （`:467` 的日志原文 `"the pass is not skipped"`）。漏存一条记忆的代价，比多花一次模型调用高。

#### 闸 2 必须 CJK 友好（这是中文产品的必需品，不是优化）

CC 的实现（调研文档 §1.5）：

```js
Et = 2;  // 一个汉字算两个词
bt(e, r) { return Pe(e) >= r || Tt(e) >= r * Et; }
```

Hlaudz 版本：

```python
_CJK_RE = re.compile(r"[\u4e00-\u9fff\u3040-\u30ff\u0e00-\u0e7f]")
def _prose_word_count(text: str) -> int:
    """英文按空格分词 + 中日韩字符按 2 字算 1 词。"""
    latin = len([w for w in text.split() if w.strip()])
    cjk = len(_CJK_RE.findall(text))
    return latin + cjk // 2
```

**不这么做的后果**：`minProseWords = 50` 时，一段 200 字的中文对话会被算成
「1 个词」（`split()` 只切出 1 个元素），**记忆永远不写**。这是必须在前端产品
验证时专门测的一项（见 §7 的 S-M2）。

### 4.3 子代理能用的工具（闭世界）

对齐 CC 的 `z$t`（v3 §3 第 33 条：`XIs` 与 `z$t` 是**两个不同集合**，前者含 read、
后者是写入子集）与 Hlaudz 的 `capabilities.py` 原则：

```python
# 写入子代理：CC 的 z$t 子集（只有写侧）
MEMORY_WRITE_TOOLS = frozenset({"memory_write", "memory_str_replace", "memory_append"})

# 客户端对外的三件套（CC 的 Nji，m0290:8）
MEMORY_CLIENT_TOOLS = frozenset({"memory_list", "memory_read", "memory_write"})
```

记忆写入子代理的 registry **只有写侧工具**，拿不到 `code_run` / MCP / `file_write`。
这样即使模型被记忆内容里的文本诱导，也没有越权工具可用——**prompt 不是安全边界，
工具 schema 才是**（`capabilities.py` 的注释原文）。

> ⚠️ 旧的写法把 `memory_delete` 也放进写入子代理的工具集。v3 §6.2 复核后改为：
> **写入子代理只给 `z$t` 里的写侧三件**（`memory_write` / `memory_str_replace` /
> `memory_append`），不给 `memory_delete`；对外契约只声明 `Nji` 的三件套
> （`memory_list` / `memory_read` / `memory_write`）。删除通过 write 覆盖内容实现。
> 理由：CC 客户端已知名单 `Nji`（`m0290:8`）里**没有 delete**，
> 而 `memory_delete` 只在服务端可能下发的 `z$t` 里——把它写进对外契约属于**超出 CC 的承诺**。

### 4.4 写完之后：读缓存失效（这条最容易漏）

CC 的 `K8n`（调研文档 §1.5）做两件事：

1. **重同步 `readFileState`**（`requireReadBeforeWrite: true`）——否则主代理下次写
   这个文件会被「写前必读」门禁拦住（因为它不知道后台写过）；
2. **排 `pendingMemoryUpdate`** —— 下一轮通过 `memory_update` attachment 告知模型
   「我刚记了这些」。

Hlaudz 对应实现：

```python
# 写完记忆文件后
from .read_registry import ReadRegistry   # 现有模块
read_registry.record(path, complete=True)  # ← 主动登记为「已读」，绕过下一次门禁

# 并把「写了什么」排进注入队列（下一轮随记忆块一起注入）
memory_notice_queue.push(user_id, session_id, {"slug": slug, "title": title})
```

关于 `ReadRegistry`：注意它的注释写着「一次 generation 一份；不跨会话复用」。
所以后台写入的登记必须写到**该会话当前 generation 的 registry**，或者接受
「下次读一次即可」的降级。第一版取后者（简单、不会错），并在文档记下这个取舍。

### 4.5 写入子代理的提示词

必须显式约束三件事，否则模型会写出一堆无用记忆：

```
你在为一个用户整理长期记忆。

只有以下四类值得记（type 字段与 CC 原文 `type: user | feedback | project | reference` 对齐）：
1. user      —— 关于这个人：称呼、角色、语气、长期偏好（always private）
2. feedback  —— 用户对工作方式的纠正**和确认**（见下方「确认也算反馈」）
3. project   —— 跨会话的项目状态：做到哪、遗留什么、谁在做什么
4. reference —— 外部资源指针：URL、看板、工单号（usually team）

不要记：
- 本次任务的具体内容（那是会话历史的事）
- 你已经能从代码/文件里读到的信息
- 任何可能过期的临时状态

每条记忆一个文件，frontmatter 包含一行 description（<= 60 字，写给相关性选择器看，
要具体到能判断「这条和下一轮的提问是否相关」）。已存在的记忆优先 str_replace 更新，
不要重复新建同名条目。
```

#### 确认也算反馈（v3 §5.4 复核确认，v2 §14.3 正确）

**这是产品级行为差异，不是措辞。** CC 的原文（`m0293:3856` 的 `Qn` 提示词）写得很明确：

> Record from failure AND success: if you only save corrections, you will avoid past mistakes
> but drift away from approaches the user has already validated, and may grow overly cautious.

`<when_to_save>` 还给了三种确认信号，**逐字可抄**：

- `"yes exactly"`
- `"perfect, keep doing that"`
- `"accepting an unusual choice without pushback"`（用户对你一个反常规的选择没吭声）

只记纠正的后果是模型**越用越保守**——它会不断避开风味不明但正确的做法。
这个偏差单靠测「记没记住」是测不出来的，要测「三轮之后模型的表达是否变得畏缩」。

### 4.6 第二条写路径：`auto_dream` —— 跨会话合并（**前一版完全缺失**）

提取（§4.2）负责「把本轮的新事实写进去」；`auto_dream` 负责**翻旧账**：
去重、合并碎片、删掉被推翻的事实、维护索引。两者职责不同，**不能互相替代**——
提取时的同 slug 比对只能防「同名重复新建」，压不住「三条记忆讲同一件事」。

#### CC 的触发条件（`xXs`，`m0833:197`）

**先澄清一个常见误解：dream 不是「空闲时触发」。** CC 里没有空闲检测、没有系统空闲回调。

它的触发点和提取器**完全一样**——都在 `Jd()`（轮次结束）里，紧挨着（`m0848:3859`）：

```js
if (!toolUseContext_5.agentId && (V$t() || qn.isLaptopExtractActive(...))) {
  let ke = qn.executeExtractMemories(G, ...);      // 提取
  ...
}
if (!toolUseContext_5.agentId) PXs(G, ...);        // ← dream，就在下一行
```

所以准确说法是：**每个轮次结束都尝试一次，但内部有三道硬时间闸**，
实际表现成「隔天在某次轮次结束后悄悄跑」——这是产品语义上的「空闲」，不是机制上的。

```
① he()   —— 五道前置：不在远端 / 非 SDK 入口 / 文件记忆开 / 非工具模式 / xEt() 开关
② minHours    —— 距上次合并 ≥ 24h（默认，tengu_onyx_plover 可覆盖）
③ 扫描节流     —— 距上次扫描 ≥ 10 分钟（ce = 600000），避免频繁 stat
④ minSessions —— 期间被触碰过的会话数 ≥ 5（不含当前会话）
⑤ 权限闸      —— LGr 判断写入会不会被规则拒绝
⑥ 文件锁      —— sZs() 拿不到就跳过（多进程/多窗口防撞车）
⑦ items 可读   —— before === "newer" / unreadable 时跳过并给提示
```

配置默认 `{minHours: 24, minSessions: 5}`（`se`，`m0833:177`）。

`he()` 里的 `aY()`（= SDK 入口判定，v3 §1.5 已澄清）对 Hlaudz 反而是好消息：
**Web 服务不是 SDK 入口，这条前置天然通过**。

#### dream **不**做「从失败中学习」

这点要说清楚，因为容易被误解成「dream 会提炼经验教训」：

| 你想的 | 实际归属 |
|---|---|
| 合并记忆碎片 | ✅ dream Phase 3「merging into existing topic files」 |
| 删掉被推翻的事实 | ✅ dream Phase 3「deleting contradicted facts」 |
| 整理索引 | ✅ dream Phase 4（**提取器完全不碰索引**） |
| **把「做错又成功」的经验提炼出来** | ❌ **不是 dream**。这是**提取器**的 `feedback` 类型（「Record from failure AND success」，§4.5） |

dream 明确**只整理已有记忆，不新增「这轮学到了什么」**。它的输入是「记忆目录现状」，
不是「最近的对话内容」（Phase 2 的 transcript 搜集是可选且窄范围的）。

#### dream 提示词是四阶段的（`Q()`，`m0833:54`）

这段**逐字可抄**，它比提取提示词更能防止记忆腐化：

```markdown
# Dream: Memory Consolidation

You are performing a dream — a reflective pass over your memory files. Synthesize what
you've learned recently into durable, well-organized memories so that future sessions
can orient quickly.

## Phase 1 — Orient
- ls the memory directory to see what already exists
- Read MEMORY.md to understand the current index
- Skim existing topic files so you improve them rather than creating duplicates
- If a sessions/ subdirectory exists, review recent entries there

## Phase 2 — Gather recent signal
1. **Existing memories that drifted** — facts that contradict something you see now
2. **Transcript search** — grep the JSONL transcripts for narrow terms only
Don't exhaustively read transcripts. Look only for things you already suspect matter.

## Phase 3 — Consolidate
For each thing worth remembering, write or update a memory file...
Focus on:
- Merging new signal into existing topic files rather than creating near-duplicates
- Converting relative dates ("yesterday", "last week") to absolute dates
- Deleting contradicted facts — if today's investigation disproves an old memory, fix it

## Phase 4 — Prune and index
Update MEMORY.md so it stays under 200 lines AND under ~25KB. It's an **index**, not a dump
— each entry should be one line under ~150 characters: `- [Title](file.md) — one-line hook`.
Never write memory content directly into it.
- Remove pointers to memories that are now stale, wrong, or superseded
- Demote verbose entries: if an index line is over ~200 chars, it's carrying content that
  belongs in the topic file
- Add pointers to newly important memories
- Resolve contradictions — if two files disagree, fix the wrong one
```

四个设计点值得单独注意：

1. **Phase 2 的「只 grep 窄关键词」**：明确禁止通读 transcript——那会把成本撑爆。
2. **「相对日期转绝对日期」**：不转的话，「昨天」一周后就无意义了。
3. **「删掉被推翻的事实」**：这是**减**记忆，多数实现只做增。
4. **索引是索引**：`- [Title](file.md) — one-line hook`，每行 ≤150 字符，绝不写正文。
   这与 §3.5/§3.6 的 200 行 / 25000 code unit 上限是同一套约束。

#### 梦里的工具闸更严（`NGr`，`m0832:616`）

dream 跑起来时**只能**做这些（比提取子代理还窄）：

| 允许 | 条件 |
|---|---|
| 读类工具（`ze`/`_r`/`Qr`） | 允许，但受 `blockReadsOutsideWorkingDirectories` 约束 |
| shell（`Me`/`kt`） | **只允许只读命令**（`ls`/`find`/`grep`/`cat`/`stat`/`wc`/`head`/`tail` 等） |
| shell 删除 | **只允许删 `.md`**，且必须在记忆目录内、不能进 `.git`/`agents` 等保护子目录；`rm` 只许 `-f` |
| 写文件（`dt`/`Yt`） | 只允许**记忆目录内**（`FUe(path, memoryDir)`） |
| MCP 工具 | **一律拒绝** |
| 其他一切 | 拒绝（`tool_not_allowed`） |

Windows 上还有一条额外限制：命令里**不许出现 `..`**，哪怕是引号或反斜杠拆开的。

#### 写后清算：「确实写了」vs「可能写了」

`finally` 里（`m0833:334`）区分两个集合：

```js
let dreamWrote    = new Set([...H].filter(([k]) => !V || !j.has(k)).map(([, k]) => k)),
    mayHaveWritten = new Set([...H].filter(([k]) =>  V && j.has(k)).map(([, k]) => k));
```

`H` = 「被允许写入的路径 → toolUseId」（`onWriteAllowed` 收集），
`j` = 「确认写完的 toolUseId」。**允许写 ≠ 写成功**——工具被批准后可能失败/超时。
这个区分决定崩溃恢复时要不要重试、锁要不要归还。

成功后产出 `verb: "Improved"` 的系统消息（`:356`），并走 `K8n` 重同步读缓存（同 §4.4）。

#### Hlaudz 的落法

**触发时机用一个后台巡检任务，不是每轮检查。** Hlaudz 有 `lifespan`（`main.py:25`）
和 `RuntimeHub.startup`，但没有周期任务。选最省的做法：

```python
# backend/app/memory_dream.py
# 挂到 lifespan 里：app.state.dream_task = asyncio.create_task(_dream_loop())

async def _dream_loop() -> None:
    """每 10 分钟醒一次，条件够了就跑一次 dream。"""
    while True:
        await asyncio.sleep(_scan_interval())        # 默认 600s，对齐 CC 的 ce
        try:
            await _tick()
        except asyncio.CancelledError:
            raise
        except Exception:
            logger.warning("[dream] 巡检失败", exc_info=True)


async def _tick() -> None:
    now = time.time()
    if now - _last_consolidated_at() < _min_hours() * 3600:      # 默认 24h
        return
    for user_id in await db.list_active_user_ids():              # 逐用户独立
        touched = await db.sessions_touched_since(user_id, _last_consolidated_at())
        touched = [s for s in touched if s != _current_session_id()]
        if len(touched) < _min_sessions():                        # 默认 5
            continue
        lock = _try_acquire_lock(user_id)                         # 见下
        if lock is None:
            continue                                              # 别的进程在跑
        try:
            await _run_dream(user_id, touched)
            await _mark_consolidated(user_id, now)
        finally:
            lock.release()
```

**三个必须自己做对的地方：**

| 点 | 做法 | 为什么 |
|---|---|---|
| **锁用 DB 行 + 心跳，不用文件** | `memory_dream_state` 表里 `lock_pid` / `lock_at` 两列，一个 `UPDATE ... WHERE` 完成判断+抢占；`LOCK_STALE_MS = 30 分钟` | CC 用 `.consolidate-lock` 文件（`m0809:17`），但文件锁在 Web 服务里不好处理（多 worker、容器重启后 PID 视图不同）。DB 行是原子的，且与 `last_consolidated` 同表，少一处不一致 |
| **按用户串行** | 状态存 **per-user 行**，不是全局 | 一个用户的 dream 不能因为另一个用户刚跑过而被跳过 |
| **先快照后跑** | 跑之前记下 `MEMORY.md` 的 mtime 与各文件清单 | 并发提取（§4.2）可能同时在写。dream 结束后要能判断「我改的这个文件，期间别人改过没有」 |

#### ⚠️ 中断恢复：CC 会「从头重跑」，Hlaudz 必须做得更好

核实文档 §6 查清了 CC 的真实行为，它有两个我们必须改的缺陷：

**CC 的做法**（`m0809`）：状态全在 `.consolidate-lock` 一个文件里，两行 `PID \n lastConsolidatedAt`。
抢锁条件是「文件 mtime < 1h **且** PID 还活着」，所以进程崩溃后锁不会卡死（PID 死了就能抢）——
这点它对。

**但有三个问题：**

1. **`lastConsolidatedAt` 只在成功后更新**。dream 被 kill 时它停留上次成功时刻，
   下次条件满足就**从头再跑**，20 分钟的模型调用全白费。
2. **完全没有进度保存**。走路一半摔了就全丢。
3. **`mayHaveWritten` 只解决进程内 abort**。那个 `Map` 在进程里，kill 后直接消失，
   对崩溃完全无效。

**Hlaudz 的做法**（三处改进）：

```sql
CREATE TABLE IF NOT EXISTS memory_dream_state (
    user_id            TEXT PRIMARY KEY,
    last_consolidated  INTEGER NOT NULL DEFAULT 0,   -- 上次**成功**完成
    last_attempt       INTEGER NOT NULL DEFAULT 0,   -- 上次**开始**（诊断反复崩溃）
    last_status        TEXT    NOT NULL DEFAULT 'idle',  -- idle|running|failed|interrupted
    lock_pid           INTEGER NOT NULL DEFAULT 0,
    lock_at            INTEGER NOT NULL DEFAULT 0
);
```

| 改进 | 做法 | 收益 |
|---|---|---|
| **① 多记两个字段** | `last_attempt` + `last_status` | 连续 5 次 attempt 都失败 → 能诊断出「每次都在同一个地方崩」，CC 完全看不到这个 |
| **② 启动时主动收敛** | 服务启动调 `recover_dream_state()`，把所有 `lock_pid != 0` 的行清掉，`running` → `interrupted` | **不能只靠锁过期**：服务刚重启时锁可能还很新（< 30min），但进程已不存在。这与本项目已有的 `team_store.recover_stale_runtime("server restart")`（`main.py:52`）和 `mark_stale_running_as_errored`（`main.py:38`）是同一类问题，用同一套解法 |
| **③ 把 Phase 4 拆成幂等步骤** | Phase 3 写完文件后**立刻更新一次** `last_consolidated`；Phase 4（索引重建）独立成一个可随时重跑的任务 | 被 kill 在 Phase 4 之前，下次只需重跑索引重建（很便宜），不用重跑整个 Phase 3（很贵） |

> **③ 是 Hlaudz 相对 CC 的改进，不是对齐。** CC 是 CLI，重启频率低，「反正会重跑」可接受；
> Hlaudz 是 Web 服务，部署/OOM/手动重启频繁得多，这个代价不可接受。

#### 启动时**不要**立刻补跑 dream

即使检测到「距上次成功已超 24h」，也**不要**在启动时补跑：

- 启动时正要连 MCP、建连接池，dream 会抢资源，拖慢首批用户的首帧；
- 用户此刻可能正在等响应。

正确做法：**启动时只收敛状态（清锁），把「跑不跑」交给下一次轮次结束时的常规判定**
（与 §4.1.2 的 `_on_turn_end` 一致）。

**并发与提取子代理冲突**：这是 Hlaudz 比 CC 更需要小心的地方。CC 的 dream 与提取
都跑在同一个 CLI 进程里，靠 `j0n` 的会话预算与 `H`/`j` 集合协调。
Hlaudz 是多用户后台服务，梦里可能与「某一轮对话刚触发的提取」撞车。**规则**：

- dream 持锁期间，**提取照常跑**（它写单条记忆，冲突面小）；
- 但 **dream 自己不加锁就不写**，而是把要写的改动记成 `dreamWrote`/`mayHaveWritten`，
  与 CC 的 `deferCappedRunWrites` 同形态；
- 同一用户的两次 dream 绝不并发（锁保证）。

**索引维护归属**：`MEMORY.md` 的**唯一改写者是 dream**。提取子代理只写单条 `<slug>.md`，
不碰索引。这样索引的格式一致性只在一个地方保证。

**配置**：

| 变量 | 作用 | 默认 |
|---|---|---|
| `HLZ_MEMORY_DREAM_ENABLED` | 总开关 | `1` |
| `HLZ_MEMORY_DREAM_MIN_HOURS` | 距上次合并的最小间隔 | `24` |
| `HLZ_MEMORY_DREAM_MIN_SESSIONS` | 期间需要的最少会话数 | `5` |
| `HLZ_MEMORY_DREAM_SCAN_INTERVAL` | 巡检间隔（秒） | `600` |

**明确不做**：`auto_dream` 不读 transcript。CC 允许 `grep` JSONL，Hlaudz 的
`session_history` 在 SQLite 里，让模型写 SQL 风险太高。第一版**只做「Orient + Consolidate
+ Prune」三阶段**（Phase 2 的 transcript 搜集省掉），代价是 dream 看不见
「上一轮对话里说过但没被提取的记忆」——这是可接受的损失，因为提取本来就该抓住那些。

## 5. 工具面（模型可主动读写）

**对外只声明三个工具**（对齐 CC 客户端的已知名单 `Nji = ["memory_list","memory_read","memory_write"]`，
`m0290:8`，v3 §3 第 30 条）：

| 工具 | 作用 | 对齐 CC | 关键细节 |
|---|---|---|---|
| `memory_list` | 列出记忆，**分页** | `Pv`，`m0816:2988`（schema `:2956`） | 入参 `store` / `path_prefix` / `cursor`；默认页 **50**（`Hi = 50`）；出参含 `entries` / **`remaining`** |
| `memory_read` | 读一条记忆全文 | `qQr`，`m0591:75850`（schema `rJo` `:75831`） | 入参 `store` / `path`；`shouldDefer:!1`、`backgrounding:"never"`、`maxResultSizeChars: 1/0` |
| `memory_write` | 新建或更新一条记忆 | `z$t` 的 write/append | 带 **`if_version`** 做 CAS（§5.1） |

**没有 `memory_delete`。** 旧版把它列进了对外契约，但 CC 客户端的 `Nji` 里没有它——
它在服务端的 `z$t` 集合里（`m0191:2338`，写入子集），属于「服务端可能下发、客户端未承诺」的操作。
对外承诺 delete 会**超出 CC 的契约**，而且删除一条记忆用 write 覆盖成空即可。

> `memory_list` **必须实现分页**，这是 v3 §1.2 更正的核心：v2 把 `memory_list` 的行号
> 指到了 `memory_read` 的 schema（`m0591:75831` 只有 `store` + `path`），照那个实现会
> 漏掉 `cursor` / `remaining` / 默认页 50。而当记忆超过一屏时，`cursor` 是**唯一的续读路径**。

### 5.1 `memory_write` 的 CAS（对齐 CC 的 `if_version`）

CC 的 `memory_write` 带乐观并发控制（`m0394:1554`）：

- 入参可带 `if_version`；版本令牌 = **内容 sha256 前 12 位**（`mWe`，`:1516`）；
- 出参 `outcome: ok | conflict | missing | refused | failed`，
  冲突时返回 `currentVersion` + `currentContent`，调用方可据此重放；
- 单文档上限 **100 KB**（`:1553`）。

Hlaudz 照抄这条**不是过度设计**：写侧是后台子代理、读侧是主对话，
两者并发改同一条记忆是真实会发生的（用户在设置页手改 + 后台在写）。
没有 CAS 就是后写覆盖前写，且**用户的手改会静默丢失**。

```python
def write_memory(user_id, *, slug, title, description, body, kind="user",
                 if_version: str | None = None) -> WriteResult:
    cur = _read_version(path)                 # sha256(content)[:12]
    if if_version is not None and if_version != cur:
        return WriteResult(outcome="conflict",
                           current_version=cur, current_content=_read(path))
    ...
```

### 5.2 工具裁剪：子代理拿不到记忆工具

**三个工具只在 root agent 的 registry 里。** 理由：子代理如果也需要记忆，应该由 root
决定给它什么上下文，而不是让它自己翻用户的隐私记忆。所以这三个**照
`ORCHESTRATION_TOOLS` 的方式，从子代理 registry 里裁掉**，但语义上不属于「编排」，
另开一个集合：

```python
# capabilities.py
ORCHESTRATION_TOOLS = frozenset({...})   # 现有
MEMORY_TOOLS = frozenset({"memory_list", "memory_read", "memory_write"})
CHILD_EXCLUDED = ORCHESTRATION_TOOLS | MEMORY_TOOLS   # 子代理两者都拿不到
```

`build_capability_profile()` 里的 `available - ORCHESTRATION_TOOLS` 改成
`available - CHILD_EXCLUDED`。

> 这条有争议，记下取舍：也可以让子代理只读（`memory_read` / `memory_list`）。
> 第一版取「全禁」，因为子代理的记忆需求尚未被真实场景验证，先不给权限，
> 等有 e2e 案例再放开——**加权限比收权限容易得多**。
>
> 注意区分两个不同的授权面：**写入子代理**（§4.3）拿的是 `z$t` 写侧三件
> （`memory_write` / `memory_str_replace` / `memory_append`），它是为了写记忆而**专门派生**的，
> 不是普通子代理；**普通子代理**（`spawn_agent` 派生的）拿不到任何 `memory_*`。
> 这两件事不要混。

## 6. 与其他系统的关系

### 6.1 与 compaction 的关系（必须处理）

`compaction.enforce_soft_limit()` 会压掉老消息。**记忆不能跟着被压掉**——
它是以 `injected_message` block 形式存在历史里的，而 compaction 处理的是正文。

要确认的点：`compaction.py` 在压缩时是否保留 `injected_message` block。
如果保留，历史里的记忆块会越积越多（每轮注入一条）；如果丢弃，模型在压缩后
就「忘了」记忆。

**方案**：注入的记忆块**不进 `session_history` 持久化**（只在当前轮的内存 history 里）。
这样：
- 每轮都是重新计算的最新记忆（不会积累陈旧副本）；
- compaction 完全不受影响（压缩的是正文，不会碰到记忆副本）；
- 代价是刷新页面后看不到历史记忆注入记录（**可接受**：它是上下文，不是对话产物）。

⚠️ **不能只改 `chat.py`**。核实后发现「一轮的模型 history」有 **6 个持久化出口**，
其中 3 个在 `agent_loop.py` 自己身上（行号已按当前代码核对，每处都是
`if self.user_id: set(user_id, ...) else: set(...)` 的两行分支，所以写「N/N+2」）：

| 位置 | 时机 |
|---|---|
| `sse.py:140/142` | 用户消息 append 后立刻存一次 |
| `agent_loop.py:323/325` | 每轮开头 `sanitize()` 修复了悬空 tool_call 后 |
| `agent_loop.py:456/458` | 每轮 `assistant` 消息 append 后 |
| `agent_loop.py:514/516` | 每个 tool 结果 append 后 |
| `compaction.py:199/300/354` | 压缩写回 |
| `chat.py:711/713` | `message_injected` 的**展示块**（`blocks`，不是模型 history） |

**真正的分界**：`chat.py:711` 存的是 `messages.blocks`（给前端渲染的展示结构），
而 `agent_loop` / `sse.py` 存的是 `session_history`（模型看到的对话）。
两者是**不同的表**。

所以正确的做法是：

1. **模型 history 侧**：注入的记忆 dict 带一个私有标记（`"_volatile": True`），
   在 `HistoryStore` 的**两个写入口**统一剥离：
   - `set()`（`history_store.py:105` 定义，`:110` 的 `json.dumps(payload)` 之前）
   - `append()`（`history_store.py:121` 定义，`:142` 的 `history.extend(...)` 之前）

   这两个函数是 `session_history` 表的**全部运行期写出口**（已核对全仓
   `INSERT INTO session_history` 只出现在 `history_store.py:115` 与 `:144`，
   两处都在 set/append 内部）。在这里剥离，`agent_loop` 的 3 处 `set()`、
   `sse.py` 的 1 处、`compaction.py` 的 3 处全部自动生效——**不需要在每个调用点各改一次**
   （那是 7 处遗漏风险，而且是「改了新的忘了旧的」这类典型回归）。
2. **展示侧**：`chat.py:711` **照旧** append `injected_message` block 并在 SSE 里发出。
   这样用户当轮能看到「记忆进来了」，刷新后看到的是历史记录里的那一条——
   与现在的子代理通知/团队消息行为完全一致，**不改契约**。

修正后的结论：**实施时不需要改 `chat.py` 的任何逻辑**，只需在
`HistoryStore.set()` 里加一层剥离。这比原设想更安全（不动 SSE 契约文件）。

> 取舍说明：记忆块会留在 `messages.blocks` 里（展示侧），但不会进
> `session_history`（模型侧）。所以第二轮模型看到的是**新算的记忆**，不是上一轮
> 的副本——这正是我们要的「每轮重新计算」。而用户翻历史时仍能看到当时注入过什么。

### 6.2 与 A2A 的关系

A2A 调用面（P6）有 `tool_policy` 三档（`backend/app/tool_policy.py`）。记忆工具应该：

- `full`：全部可用（`allows()` 对 full 直接返回 True）；
- `read_only`：只剩 `memory_list` / `memory_read` —— 需要把它们加进
  `tool_policy.py:24` 的 `READ_ONLY_TOOLS`（当前是
  `{"file_read", "list_files", "load_skill"}`）。注意该常量同时决定 `describe()`
  的文案，加完要把 `POLICY_READ_ONLY` 的描述文字一并更新；
- `chat_only`：全部不可用（`allows()` 对 chat_only 直接返回 False，无需改动）。

**读侧注入对 A2A 同样生效**，但注入的必须是**该 token 所属用户**的记忆。
因为注入器闭包捕获的是 `AgentContext.user_id`，而 A2A 的 token 绑定 user_id，
所以天然正确——**但要有测试锁住**（§7 的 S-M4）。

### 6.3 与 Skill 的关系（容易混淆）

两者都是「每轮注入 + 按需加载」，但语义完全不同：

| | Skill | 记忆 |
|---|---|---|
| 内容 | 怎么做某类任务（可执行的流程） | 关于用户/项目的稳定事实 |
| 谁写 | 用户/开发者（导入技能包） | **模型自动写**（后台子代理） |
| 存储 | `SKILL.md`，双轨 builtin/shared/user | `memories/<user_id>/private/*.md` |
| 注入 | L1 索引（名字+描述）进 **system prompt** | 索引走 **instructions attachment**，正文按需读 |

**不要把记忆塞进 skill 索引**——skill 索引在 system prompt 里（装配时一次算好），
而记忆每轮都在变，塞进去会让 prompt 缓存彻底失效。这正是 CC 自己在记忆这块
选 attachment 而不选 system prompt 的原因（§3.5）。

| 阶段 | 内容 | 验证 | 预估 |
|---|---|---|---|

| **M4** | 写侧后台子代理（四道闸门 + 提示词 + 读缓存同步） | L1 M-6/M-7 + **S-M1/S-M2** | 大 |

**M1–M3 可以先只做「手工可用」**（用户手动加记忆文件，验证注入有效），
拿到真实体感再决定 M4 的写入策略——避免一上来就把自动写入做复杂。

**M3.5 是可选增强，M4.5 是必需项** —— 这两者性质不同，别混：

- **M3.5（选择器）可选**。核实后确认：CC 默认的文件记忆形态**根本不跑选择器**
  （`lSe()` 默认 false，见 `docs/20261114-CC319记忆触发时机核实.md` §2.4）。
  M3 的关键词排序已经是一个完整可用的读侧。做 M3.5 的唯一理由是「命中率更高」，
  代价是**每次模型调用多一次小模型调用**（一个 10 步任务就是 10 次）。
  所以它必须有明确的量化收益证明（S-M6）才值得开，且默认值保持 `0`。
- **M4.5（dream）必需**。只有提取没有合并，三个月后你会有一堆
  「同一件事讲了五遍、三条互相矛盾」的记忆，注入进去比不注入更糟。
  这是 CC 自己也要做的整理，不是优化。

**M3 是唯一改 `chat.py` 的阶段**，按 AGENTS.md §2.1 必须跑完整 e2e（S0+S1+S5 至少）。

> M1 从「小」提到「中」：多了 `cursor` 分页与 `if_version` CAS 两件事。
> 这两件都不是能事后补的——分页改了 `list_memories` 的返回类型，
> CAS 改了 `write_memory` 的调用约定，等 M3 再补要改一圈调用点。

**依赖关系**：M1 → M2 → M3 必须顺序；M3.5 依赖 M3 的注入落点；
M4 可与 M3.5 并行（一个改写侧一个改读侧）；M4.5 依赖 M4（要先有提取产生的记忆可合并）。

**最小可用集（若只想先跑起来）**：M1 + M2 + M3 + M4。四步跑完就有
「手工/自动写入 + 关键词注入 + 每用户隔离」的完整闭环；
M3.5 与 M4.5 可以按实测效果再排。

| `HLZ_MEMORY_RECALL_MAX_BYTES` | 单文件召回 cap（**真字节**，`len(s.encode())`） | `4096` |
| `HLZ_MEMORY_EVERY_N_TURNS` | 每 N 轮尝试写入（闸 3） | `3` |
| `HLZ_MEMORY_MIN_PROSE_WORDS` | prose 闸门阈值（CJK 2 字 = 1 词） | `50` |
| `HLZ_MEMORY_AUTO_WRITE` | 自动写入总开关（0 = 只能模型显式调用 `memory_write`） | `1` |
| `HLZ_MEMORY_SELECTOR` | **LLM 相关性选择器**（0 = 只用关键词排序，见 §3.7） | `0`（不计划默认打开） |
| `HLZ_MEMORY_SELECTOR_MODEL` | 选择器用的模型（**打开时必须指定，不允许回落到主模型**） | 空 |
| `HLZ_MEMORY_SELECTOR_MAX` | 选择器最多选几条 | `5` |
| `HLZ_MEMORY_SESSION_MAX_BYTES` | 整个会话累计召回上限（对齐 CC 的 61440） | `61440` |
| `HLZ_MEMORY_DREAM_ENABLED` | **`auto_dream` 合并总开关**（§4.6） | `1` |
| `HLZ_MEMORY_DREAM_MIN_HOURS` | 距上次合并的最小间隔 | `24` |
| `HLZ_MEMORY_DREAM_MIN_SESSIONS` | 期间需要的最少会话数 | `5` |
| `HLZ_MEMORY_DREAM_SCAN_INTERVAL` | 巡检间隔（秒） | `600` |

**三个 cap 的单位不同，不能合成一个变量**（v3 §1.3）：
索引按 `code unit` 计（`Gee = 25000`）、单文件召回按真字节计（`Ibe = 4096`）。
CC 内部就是两套口径并存，源码把它们都命名成 `byteCount` 是**起错了名字**。
若 Hlaudz 图省事用一个「25KB 字节」的索引 cap，**中文索引会在 1/3 处被截**。

**`HLZ_MEMORY_AUTO_WRITE=0` 是重要的降级出口**：自动写入如果误记了糟糕的东西，
关掉它比回滚代码快。

> 没有 `HLZ_MEMORY_FIRST_LOOK_MODE`。`first_look` 是 CC 的 MCP 模式专属闸（§4.2），
> 文件模式没有这道闸，本方案不加。将来要加时再补这个开关。

## 10. 风险与未决项

| 风险 | 影响 | 缓解 |
|---|---|---|
| 记忆被污染（模型记错、记住噪声） | 之后每轮都注入错的上下文，**比不记更糟** | ① 前端设置页可查看/删除每条记忆；② `hit_count` + `last_hit_at` 让「从没被用到的记忆」可识别；③ `HLZ_MEMORY_AUTO_WRITE=0` 降级 |
| 注入的记忆与用户当轮说法冲突 | 模型犹豫或按旧偏好行事 | 注入块写明「记忆可能过时，以用户当前说法为准」 |
| 后台子代理与主轮抢连接池 | 连接池紧张时追加压力 | 写侧用**独立的低优先级客户端**，或复用但受 `HLZ_LLM_POOL_CEILING` 约束（已有自动扩容，见连接池文档 §4.5） |
| `[记忆]` 前缀与用户真实发言冲突 | 用户自己说「[记忆] xxx」会被误分类 | 前缀判定只在 `injected_message` block 内做（不是扫描所有文本），且注入方是我们自己 |
| 记忆越攒越多 | 即使有预算，DB 查询与文件扫描变慢 | 超过 `HLZ_MEMORY_MAX_ENTRIES`（建议 500）时，按 `last_hit_at` 淘汰最久未用的 |

**未决**（需要你决定，不阻塞 M1–M3 开工）：

1. **`team` 作用域第一版要不要做？** 我建议**不做**。理由：Hlaudz 现在是单用户维度
   （多用户但无团队概念），`team_key` 怎么算没有好答案。表结构已预留 `scope` + `team_key`，
   将来加不用改表。注意这和旧版问的「`project` 作用域」不是同一件事——CC 的维度是
   private/team，没有「项目」这个作用域。
2. **记忆要不要用户可见可编辑？** 我建议**要**（设置页新增一个 tab，与「我的 Skills」并列）。
   模型自动写的东西如果用户看不见，出了错没法纠正。
3. **`MEMORY.md` 入口文档要不要？** CC 有，但那是给「记忆 store 有多份文档」的场景。
   第一版只有几十条记忆，`memory_list` 就够了。建议**先不做**。
4. **索引注入要不要做 `changed` 增量？**（§3.5）建议**第一版不做**，每轮全量发。
   理由：注入产物不持久化（§6.1），全量发不会累积；增量需要额外在 `AgentContext` 上维护
   版本戳，是优化不是功能。记在这里是**已知与 CC 的差异**，条目多了再补。
5. **选择器用哪个模型？**（§3.7）建议先用**当前会话模型的便宜档**或独立的低配模型，
   要看 S-M6/S-M7 的实测数据再定。这是唯一会增加**每次对话固定成本**的机制
   （一次额外的小模型调用），所以必须先把 TTFT 与命中率都量出来。
6. **dream 要不要做 Phase 2（transcript 搜集）？**（§4.6）第一版不做（见 D-8）。
   如果实测发现「提取漏掉的东西太多」，再考虑让 dream 读 `session_history` 的
   摘要而非原始 transcript。

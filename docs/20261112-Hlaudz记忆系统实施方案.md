## 0. 结论与范围

**做法：读侧用 attachment 通道（复用现有 `message_injector`），写侧用后台 forked 子代理
（复用现有 `subagent` 运行时），存储用每用户目录 + DB 索引。**

三条硬约束先写在最前面：

| 约束 | 落地方式 |
|---|---|
| **区分用户**（用户明确要求） | 物理隔离 `backend/data/memories/<user_id>/`，路径解析统一走 `workspace._resolve_under()`；DB 表 `memories` 每行必带 `user_id`，所有查询强制带 `user_id` 条件 |
| **不破坏现有契约** | 不新增 SSE 事件名；复用 `message_injected`；前端只加一种 `INJECTED_KINDS` 前缀 |
| **不让记忆拖慢首 token** | 读侧走已有的「每轮开头注入」点，且**只在有内容时**注入；写侧完全后台，不阻塞本轮 |

**明确不做**（与 CC 一致，避免过度设计）：

- 不做向量库 / embedding 检索。记忆是 `.md` 文件，按用户 + 作用域 + 关键词命中。
- 不在每轮都写记忆。四道闸门（§4.2）压频率。
- 不做「组织级记忆」。CC 有 `CLAUDE_CODE_DISABLE_ORG_MEMORY`，那是企业需求，Hlaudz 现在是
  单用户维度，先不上。**但表结构预留 `scope` + `team_key` 字段**，将来加 `team` 不用改表。
- **不做账号记忆/远端记忆拉取**。v2 §7 描述的「每轮首帧前 `await` 账号记忆」在 CC 本 build
  里是死代码（`yIe` 恒 `null`，v3 §4.4），没有可对齐的行为，不做。

## 1. 为什么是 attachment 通道（而不是塞进 system prompt）

CC 侧的结论（调研文档 §0、§1.5）：记忆是 attachment producer，不是 hook，也不是
system prompt 的一部分。理由对 Hlaudz 同样成立：

| | 塞 system prompt | attachment 通道 |
|---|---|---|
| 何时算 | 装配时一次算好 | **每轮按需算** |
| 能否关 | 难（要改装配逻辑） | 容易（producer 返回空数组） |
| 能否计量 | 难 | 每条可单独计时/计体积 |
| 会不会膨胀 | **会**（记忆越攒越多，直接挤爆上下文） | 不会（有预算 + 扣留） |
| 用户能看到吗 | 看不到 | **能看到**（前端已有 `injected_message` 渲染） |

最后一条对本项目是决定性的：Hlaudz 的前端已经有 `InjectedNote` 组件（可折叠、
带来源标签），`message_injected` 事件也已经在 `chat.py` 里持久化成
`{"type": "injected_message"}` block。**记忆注入直接复用它，前端改动只有一行分类规则。**

### 1.1 Hlaudz 现成的注入点（不需要新建管线）

`backend/app/agent_loop.py:305`：

```python
if self.message_injector is not None:
    injected = self.message_injector() or []
    ...
    for msg in injected:
        history.append(msg)
        yield {"type": "message_injected", "text": msg.get("content", "")}
```

这个钩子**每轮模型调用前**都跑一次，正好是 CC 里 `dc(...)` producer 的执行时机。
现有使用者有三个：

| 注入器 | 位置 | 注入什么 |
|---|---|---|
| `_steer_aware` 用户插话 | `sse.py:106` | `steer_queue` drain |
| subagent 通知 | `subagent/host.py:162` | 子代理完成通知 |
| team 收件箱 + 通知 | `subagent/session.py:299` | teammate 消息 |

**记忆是第四个使用者**，加在同一个 fold 点。这是最小改动，也是契约最稳的做法
（不改事件名、不改 `AgentLoop` 签名、不改前端块类型）。

⚠️ 注意一个已存在的坑：`loop._steer_aware` 标记的作用是「本注入器已经 drain 过用户队列」，
避免装两个注入器导致同一条消息被取两次。加记忆注入时**不能覆盖** `message_injector`，
必须是**链式组合**（见 §3.3 的 `_compose_injectors`）。

## 2. 数据模型（每用户隔离的落点）

### 2.1 目录布局与记忆类型

```
backend/data/memories/<user_id>/
    private/                 # scope = private
        MEMORY.md            # 入口索引：标题 + 一行 description + 指向文件，不存正文
        <slug>.md            # 单条记忆：frontmatter + 正文
    team/                    # scope = team（第一版不启用，仅留目录）
        <team_key>/
            MEMORY.md
            <slug>.md
    .index.db                # 可选：仅用于快速列举的 SQLite 索引（正文永远在 .md）
```

> **目录按 `scope` 分，不按 `type` 分。** 记忆的「类型」写在 frontmatter 的
> `metadata.type` 里（CC 原文：`type: user | feedback | project | reference`），
> 而「作用域」决定物理落点。本方案第一版只有私有记忆，所以 `private/` 下平铺，
> `type` 只影响注入排序与提示词，不影响路径。

#### 四类记忆与各自的默认作用域（v3 §5.7，按 CC 原文对齐）

| type | 记什么 | 默认 scope | CC 原文 |
|---|---|---|---|
| `user` | 关于这个人：称呼、角色、语气、长期偏好 | **always private** | `<scope>always private</scope>` |
| `feedback` | 用户对工作方式的纠正**和确认** | private（明显是全项目约定才 team） | 见下方「确认也算反馈」 |
| `project` | 跨会话的项目状态：做到哪、遗留什么、谁在做什么 | private 或 team，**强烈倾向 team** | — |
| `reference` | 外部资源指针：URL、看板、工单号 | **usually team** | `<scope>usually team</scope>` |

**关键修正**：作用域**不是**「private / team 自由两档」，而是**每类自带默认值**。
CC 的四类定义（`m0293:3849` 的 `dho`）里，`user` 硬编码 always private、`reference`
硬编码 usually team，中间两类才谈得上选。照抄「两档自由选」会丢掉这个方向性。

Hlaudz 现在没有团队/组织概念，所以：**四类全部落 `private/`**，`<scope>` 段仍写进提示词
（保留语义给未来的 team 层），但代码不按它分目录。`team/` 目录第一版不创建。

> 旧版写的是 `personal` / `project` 两个目录 + `fact/preference/feedback/project` 四种 kind，
> 那是把 CC 的「作用域」和「类型」混成了一层，已废弃。

#### `MEMORY.md` 是入口，不是注入源

CC 把 `MEMORY.md` 排除出**目录扫描候选集**（`B3e()` 的 `excluded: Set(["MEMORY.md"])`，
v3 §3 第 11 条），只让模型用工具按需读。我们照抄：自动注入只注入「最近 N 条 / 关键词命中的条目」，
入口文档靠 `memory_list` + `memory_read` 读。

⚠️ 注意别把这条和另一件事混了：`MEMORY.md` **作为索引仍然会进上下文**，
在 CC 里走的是 `instructions` attachment（见 §3.5）。「排除出候选集」说的是
**别把它当成一条普通记忆重复注入两遍**，不是「它永不进上下文」。

### 2.2 DB 表（索引 + 审计，正文不入库）

```sql
CREATE TABLE IF NOT EXISTS memories (
    id          TEXT PRIMARY KEY,
    user_id     TEXT NOT NULL,           -- ← 隔离的关键：每行必带
    scope       TEXT NOT NULL DEFAULT 'private',    -- private | team（默认值按 type 推导，见下）
    team_key    TEXT NOT NULL DEFAULT '',           -- scope='team' 时才用
    slug        TEXT NOT NULL,           -- 文件名（不含 .md）
    title       TEXT NOT NULL DEFAULT '',
    description TEXT NOT NULL DEFAULT '', -- 一行描述：给相关性选择器读，不是给人读的
    tags        TEXT NOT NULL DEFAULT '[]',  -- JSON 数组，用于关键词命中
    kind        TEXT NOT NULL DEFAULT 'user', -- user | feedback | project | reference
    path        TEXT NOT NULL,           -- 相对 memories/<user_id>/ 的路径
    created_at  INTEGER NOT NULL,
    updated_at  INTEGER NOT NULL,
    hit_count   INTEGER NOT NULL DEFAULT 0,
    last_hit_at INTEGER NOT NULL DEFAULT 0,
    UNIQUE (user_id, scope, team_key, slug)   -- ← 同用户同作用域内唯一
);
CREATE INDEX IF NOT EXISTS idx_memories_user ON memories (user_id, scope, updated_at DESC);
```

三处改动相对旧版：

1. **`kind` 枚举换成 CC 的四类**（`user | feedback | project | reference`），默认 `user`。
   旧的 `fact/preference/feedback/project` 是把类型和作用域混了，见 §2.1。
2. **`summary` 改名 `description`**。这不是改着玩：CC 的 frontmatter 注释原文是
   「used to decide relevance **in future conversations**, so be specific」
   （`m0293:3847`，v3 §5.3 复核确认），它的消费者是**相关性选择器**，不是渲染器。
   叫 `summary` 会让人以为「短就行」，实际要求是「具体到能判断相关性」。
3. **`project_key` 改名 `team_key` 且默认空**。旧版的 `project_key` 是「代码库」维度，
   CC 没有这个概念（它的维度是 private/team 两种作用域）；Hlaudz 要预留的是
   **团队**维度，不是项目维度。

> `scope` 的默认值由 `kind` 推导，不由调用方随便填：
> `user → private`（强制）、`reference → team`（默认，可覆盖）、
> `feedback`/`project` 默认 `private`、显式指定才 `team`。
> 第一版因为无团队层，`write_memory()` 里直接强制 `scope='private'`、`team_key=''`。

**为什么正文不入库**：

1. 与 CC 一致（记忆是 `.md`，模型能 `file_read` / `file_patch` 直接改）；
2. 用户可以在设置页直接编辑/删除（文件即真相，不会出现「库里有、文件没了」的分裂）；
3. 单条记忆可能几千字，塞进 SQLite TEXT 会让 `session_history` 那套接口变重。

**为什么还要 DB**：列举（「我这个用户有哪些记忆」）、排序（最近更新/最常命中）、
审计（谁在什么时候写的）都需要索引，扫目录做不了高效排序。

### 2.3 隔离的三道保证

| 层 | 保证 | 实现 |
|---|---|---|
| 路径 | 写不进别人的目录 | `workspace._resolve_under(memories_root(user_id), candidate)` —— 已存在且经过测试（`PathSecurityError`） |
| 查询 | 读不到别人的行 | 所有 `db.*_memory()` 函数**签名第一个参数就是 `user_id`**，SQL 里 `WHERE user_id = ?` 是硬条件 |
| 注入 | 上下文里不混入他人记忆 | 注入器在装配时绑定 `user_id`（来自 `AgentContext`），**不读请求参数** |

第三条最容易出错：注入器必须是**闭包捕获 `user_id`**，不能在函数里从
`sessions` 表反查——那会在 A2A / 子代理路径上取到错误的主体。
`subagent/session.py:299` 的 `_lead_injector` 已经用 `team_ctx.user_id` 闭包，
记忆注入器照同样的写法。

### 3.2 选择策略：预算 + 优先级 + 扣留

直接搬 CC 的三条（调研文档 §1.4）：


**扣留记账**要有出口，否则「记忆有 40 条但只注入了 10 条」用户无从得知：

### 3.3 注入器：链式组合，不覆盖

`sse.py` 里现有的 `_ensure_steer_injector()`（`sse.py:82`，在 `:144` 被调用）是**直接赋值**
`loop.message_injector`，并且用 `loop._steer_aware` 标记「本注入器已经 drain 过用户队列」
（team 路径 `subagent/session.py:312` 也置这个标记），避免同一条消息被两个注入器各取一次。

加记忆时不能改它的语义，也不能简单地再赋一次值（后赋的会覆盖前面的）。
必须加一层组合，并且**尊重 `_steer_aware`**：

```python
# 新文件 backend/app/memory_inject.py
def compose_injectors(*fns):
    """按顺序跑多个注入器，结果拼接。任一抛异常不影响其他（同 CC 的 dc 语义）。"""
    def _combined() -> list[dict[str, Any]]:
        out: list[dict[str, Any]] = []
        for fn in fns:
            try:
                got = fn() or []
                if inspect.isawaitable(got):
                    # 注入点支持 awaitable（agent_loop 会 await），但组合层不混用
                    raise TypeError("compose_injectors 只接受同步注入器")
                out.extend(got)
            except Exception:
                logger.warning("注入器失败，跳过：%s", fn, exc_info=True)
        return out
    return _combined
```

注意 `_steer_aware` 的语义是「**已经有**注入器在 drain 用户插话队列」，
不是「不许再装注入器」。所以记忆注入器的安装不能因为 `_steer_aware` 为真就跳过——
它只会导致「记忆永远不注入」。正确做法是把记忆注入器**包在现有注入器外面**：

```python
existing = loop.message_injector
loop.message_injector = compose_injectors(memory_fn, existing) if existing else memory_fn
```


装配顺序（在 `subagent/session.py` 与 `sse.py` 两处分别改，语义保持一致）：

```
[记忆] -> [steer 用户插话] -> [子代理通知] -> [team 收件箱]
```

记忆放最前面，理由：它是「背景知识」，应该出现在用户新指令之前；
后面的都是「本轮新发生的事」，放在更靠近当前指令的位置更符合注意力分布。

### 3.4 注入内容的形状

```
[记忆] 这个用户的偏好与背景（历史积累，供参考，不要逐条复述给用户）
- 称呼：用户希望被叫「老徐」（user，2026-11-10）
- 语言：始终用中文回答，代码注释也用中文（user，2026-11-08）
- 格式：这个项目不要用 Markdown 表格（feedback，2026-11-09）
- 环境：本机是 Windows，Git Bash 在 D:\Git\bin\bash.exe（user，2026-11-05）
（另有 8 条记忆因预算未注入，可用 memory_list 查看）
```

三条设计要点：

1. **前缀 `[记忆]`**：前端 `INJECTED_KINDS` 靠前缀分类，加一条规则即可
   （`test: t => t.startsWith('[记忆]')`，`label: '记忆'`，`mark: '◈'`）。
2. **明确写「不要逐条复述」**：否则模型会把记忆当任务清单念一遍给用户听
   （CC 的 `nested_memory` 也有类似提示）。
3. **带 type 和日期**：type 让模型知道这条的分量（`user` 是长期底色、`feedback` 是明确的
   行为纠正、`project` 可能已过时），日期让模型判断时效。

> 块尾那行「另有 N 条」不要省。CC 的 `withheld_memory` 渲染虽然为空（v3 §3 第 14 条），
> 但它的**欠账表**（`BT`，v3 §3 第 16 条）真实存在——「扣留了但不告知」和
> 「扣留了并告知」是两种产品。前者用户永远不知道记忆没生效。

### 3.5 索引注入通道：走 attachment，不进 system prompt（v3 §1.1 / §5.2）

**这是 v3 复核推翻 v2 的一处，也是最容易做错的一处。**

v2 §3.2/§3.3.1 的结论是「`MEMORY.md` 每次会话都进系统提示词，证据完整」。文本渲染那段没错，
但**投递通道认错了**。CC 的真实分叉在 `m0848:1227-1228`：

```js
let E = SUo(s.messages) ?? gm(s.messages);
if (E === "inline") return gl(S);        // ← 只有这条才把 claudeMd 留在 userContext
```

`SUo`（`:1181`）= `n0n() ? cD(e)?.contextRendering : void 0`；`gm`（`:1189`）=
`n0n() && L6t(e) !== void 0 ? "announced" : void 0`。而 `n0n()` **默认 true**
（v3 §4.6：`n0n()` → `su()` → `SPs("tengu_foamy_spring")`，reader 未注册时 `return !0`）。

所以默认走 **`announced`** 分支：`:1286` 把 `claudeMd` 从 `userContext` 里
`delete I.claudeMd`，转成 `instructions` 列表，`:1446` 作为 attachment 发出。
只有显式设了 `contextRendering === "inline"` 才留在 system prompt 的 `blocks.claudeMd`。

**Hlaudz 的落法：**

| 方案 | 何时可用 | 代价 |
|---|---|---|
| **✅ attachment（默认）** | 总是 | 无。`kAt`（`m0591:10977`）的 `if (!e.changed) return WQe(e.files)` 支持**增量**：只有索引文件变了才补发差异 |
| ⚠️ system prompt | **仅当会话内索引不变** | 一旦写侧改了 `MEMORY.md`，下次请求就得全量换 system，**prompt cache 全灭** |

本方案**已选定 attachment 通道**（§1 的表格就是这么写的，`message_injector` 就是 attachment
producer）。索引这块不要另开一条路塞进 `SYSTEM_PROMPT`——那是 v2 的错误结论。

**实现要点（对应 CC 的 `changed` 增量）：**

Hlaudz 的 `message_injector` 现在每轮都返回完整内容。要做增量，需要在注入器里记住
「上一轮发过的索引版本」，只在 `(mtime, size, 条目数)` 变化时发新副本：

```python
# 每 session 一份（放 AgentContext 上，与 read_registry 同生命周期）
_last_index_stamp: tuple[int, int, int] | None = None

def _memory_index_attachment():
    stamp = (index_mtime, index_size, entry_count)
    if stamp == ctx._last_index_stamp and not force_full:
        return []                      # 没变 → 不发，等价于 CC 的 e.changed === false
    ctx._last_index_stamp = stamp
    return [create_instructions_attachment(files=[...], changed=True)]
```

**第一版可以不做增量**（每轮全量发索引），因为 `message_injector` 的产物本来就不持久化到
`session_history`（§6.1），不会累积。但要知道这是**与 CC 的已知差异**，
记在 §10 的未决项里，条目多了再补。

### 3.6 预算单位：code unit 不是字节（v3 §1.3）

v2 全文把索引 cap 写成「25 KB 字节」，**错了**。源码里那个变量名就叫 `byteCount`，
但它取的是 `trimmed.length`——JS 字符串长度，即 **UTF-16 code unit**：

```js
// m0194_0x11642aa3.js:15-23
function z2e(t) {
  let trimmed = t.trim();
  return { trimmed, lineCount: Dt(trimmed, "\n") + 1, byteCount: trimmed.length };  // ← .length
}
```

`LEr()`（`m0293:4448`）用 `byteCount > Gee` 判断，`Gee = 25000`。源码把它命名成 `byteCount`
是**起错的名字**，v2 照抄了这个名字。

旁证（方法论 §1 的优先级：提示词原文 > 变量名）：`LEr` 的超限文案（`m0293:4478`）写的是
`` `everything after the first ${w.length} characters of line 1 was cut off` ``
—— 面向用户的字符串说 `characters`，不是 `bytes`。

**两个 cap 单位不同，别混：**

| cap | 常量 | 单位 | 计法 | 中文含义 |
|---|---|---|---|---|
| 索引（`MEMORY.md`） | `Gee = 25000` | **UTF-16 code unit** | `.length` | ≈ 25,000 个汉字 |
| 单文件召回 | `Ibe = 4096` | **真字节** | `Buffer.byteLength` | ≈ 1,300 个汉字 |

行数 cap 都是 `W2e = 200` 行（`m0194:9-14` 的 `lm/YF/Gee/W2e/Ibe` 五个常量）。

**对 Hlaudz 的直接后果**：若按「25 KB 字节」实现中文索引截断，
**中文索引会在约 1/3 处被截**（UTF-8 下一个汉字 3 字节，25000 code unit ≈ 75 KB）。
这是可见的功能缺失，不是精度问题。

配置项相应改成两个独立常量，不要用一个 `MEMORY_INDEX_BUDGET` 混着：

```python
MEMORY_INDEX_MAX_LINES   = 200        # 行数 cap，两种场景共用
MEMORY_INDEX_MAX_CHARS   = 25_000     # ← code unit（Python 里 len(str) 就是 code point，中文场景够用）
MEMORY_RECALL_MAX_BYTES  = 4_096      # ← 真字节，len(s.encode("utf-8"))
```

> Python 的 `len(str)` 数的是 **code point**，与 JS 的 UTF-16 code unit 在 BMP 内一致；
> 只有 emoji / 扩展区汉字（surrogate pair）会差一倍。记忆文本这两个都罕见，
> 第一版按 code point 实现即可，在注释里写明这个差异。

## 4. 写侧：后台 forked 子代理

### 4.1 为什么不能「同步写」

CC 用 `post_turn_memory` 后台任务（调研文档 §1.5），原因有二：

1. **写记忆要跑模型**（判断该记什么、怎么组织），同步做会直接加在用户等待时间上；
2. **写记忆可能失败/被拒**（权限、hook），不能影响主对话的成败。

Hlaudz 已有同等能力：`SubagentHost`（P2）+ `ProcessLease` + 停止级联。
**写记忆的子代理可以完全复用这套，不需要新运行时。**

### 4.2 四道闸门（顺序照抄 CC 的**文件模式**路径）

⚠️ **先纠正一个容易踩的坑**：CC 的八道闸门不是平铺的，也不是「1–4 通用、5–8 仅 MCP」。
按源码逐行看 `Le()`（`m0832:922`–`:1050`），**`first_look` 属第 8 道，且唯一调用点在
`if (config_2)`（MCP 模式）分支内**（`:1016`）。文件模式下 CC **根本没有 `first_look` 这道闸**。

完整归属（`config_2 = fet()`，来自 `CLAUDE_CODE_POST_TURN_MEMORY_CONFIG`；为 `null` 即文件模式）：

| 闸 | 条件 | 位置 | 适用模式 |
|---|---|---|---|
| 1 | 本区间内已有过直写（`Nt`）→ 跳过 | `:938` | 通用 |
| 2 | prose 不足（`Dt`/`$t`）→ 跳过 | `:950` | 通用 |
| 3 | `turns++ < every_n_turns` → 本轮不跑 | `:963` | 通用 |
| 4 | 权限规则会拒绝写入（`LGr`）→ 跳过 + 提示 | `:976` | **仅文件模式**（`config_2 ? void 0 : LGr(...)`，MCP 下直接 `void 0` 跳过该闸） |
| 5 | 期间有新轮次（`V5() !== promptIndex`）→ 跳过 | `:997` | 仅 MCP |
| 6 | 工具调用被 hold（`o8e`）→ 跳过 | `:1001` | 仅 MCP |
| 7 | `when_overage === "skip"` → 跳过 | `:1005` | 仅 MCP |
| 8 | `first_look` 答 `no`/`empty` → 跳过 | `:1034` | 仅 MCP |

**Hlaudz 是文件模式，所以只实现 1–4 这四道**（闸 4 在本方案里正好生效，因为 `config_2` 为空）。

> 旧版方案把 `first_look` 当「闸 3」并给了 `shadow` 默认——**那是 MCP 模式的行为**。
> 若照旧方案实现，等于给文件模式凭空加了一道 CC 没有的闸，且默认 `shadow` 时它不拦，
> 白付一次模型调用。本版已删。

```python
# backend/app/memory_write.py
async def maybe_extract_memories(ur, session_id: str, generation_id: str,
                                 *, turn_count: int, recent_messages: list[dict]) -> None:
    # 闸 1：本区间内主代理已经直接写过记忆 → 跳过（避免和直写打架）
    if _already_wrote_in_range(recent_messages): return
    # 闸 2：prose —— 最近窗口内必须有足够自然语言（tool-only 轮次不值得记）
    if not _has_enough_prose(recent_messages): return
    # 闸 3：频率 —— 每 N 轮才跑一次（默认 3，HLZ_MEMORY_EVERY_N_TURNS）
    if turn_count % _every_n() != 0: return
    # 闸 4：权限 —— 写入目标会被现有权限规则拒绝时不做（CC 的 LGr）
    if _permission_would_refuse(ur, generation_id): return
    # 通过 -> 派后台子代理
    await host.spawn_background(task="extract_memories", ...)
```

#### 若将来要加 `first_look`（可选增强，非对齐项）

CC 的 `first_look` 是**为 MCP 模式省钱**设计的（MCP 模式下每轮都可能有大量新消息）。
Hlaudz 第一版不加。将来若要加，注意它的三个细节：

- 三模式 `off` / `shadow` / `enforce`（`:1015` 读配置、`:1094` shadow 日志、`:1034` enforce 判定）；
- 硬超时 `jt = 20000`（20s，`:330`）、`maxRetries: 0`（`:458`）——不重试是刻意的，
  这闸是省钱用的，重试会让它自己变贵；
- **失败方向保守**：模型没按格式答出布尔值 → **不跳过**
  （`:467` 的日志原文 `"the pass is not skipped"`）。漏存一条记忆的代价，比多花一次模型调用高。

#### 闸 2 必须 CJK 友好（这是中文产品的必需品，不是优化）

CC 的实现（调研文档 §1.5）：

```js
Et = 2;  // 一个汉字算两个词
bt(e, r) { return Pe(e) >= r || Tt(e) >= r * Et; }
```

Hlaudz 版本：

```python
_CJK_RE = re.compile(r"[\u4e00-\u9fff\u3040-\u30ff\u0e00-\u0e7f]")
def _prose_word_count(text: str) -> int:
    """英文按空格分词 + 中日韩字符按 2 字算 1 词。"""
    latin = len([w for w in text.split() if w.strip()])
    cjk = len(_CJK_RE.findall(text))
    return latin + cjk // 2
```

**不这么做的后果**：`minProseWords = 50` 时，一段 200 字的中文对话会被算成
「1 个词」（`split()` 只切出 1 个元素），**记忆永远不写**。这是必须在前端产品
验证时专门测的一项（见 §7 的 S-M2）。

### 4.3 子代理能用的工具（闭世界）

对齐 CC 的 `z$t`（v3 §3 第 33 条：`XIs` 与 `z$t` 是**两个不同集合**，前者含 read、
后者是写入子集）与 Hlaudz 的 `capabilities.py` 原则：

```python
# 写入子代理：CC 的 z$t 子集（只有写侧）
MEMORY_WRITE_TOOLS = frozenset({"memory_write", "memory_str_replace", "memory_append"})

# 客户端对外的三件套（CC 的 Nji，m0290:8）
MEMORY_CLIENT_TOOLS = frozenset({"memory_list", "memory_read", "memory_write"})
```

记忆写入子代理的 registry **只有写侧工具**，拿不到 `code_run` / MCP / `file_write`。
这样即使模型被记忆内容里的文本诱导，也没有越权工具可用——**prompt 不是安全边界，
工具 schema 才是**（`capabilities.py` 的注释原文）。

> ⚠️ 旧的写法把 `memory_delete` 也放进写入子代理的工具集。v3 §6.2 复核后改为：
> **写入子代理只给 `z$t` 里的写侧三件**（`memory_write` / `memory_str_replace` /
> `memory_append`），不给 `memory_delete`；对外契约只声明 `Nji` 的三件套
> （`memory_list` / `memory_read` / `memory_write`）。删除通过 write 覆盖内容实现。
> 理由：CC 客户端已知名单 `Nji`（`m0290:8`）里**没有 delete**，
> 而 `memory_delete` 只在服务端可能下发的 `z$t` 里——把它写进对外契约属于**超出 CC 的承诺**。

### 4.4 写完之后：读缓存失效（这条最容易漏）

CC 的 `K8n`（调研文档 §1.5）做两件事：

1. **重同步 `readFileState`**（`requireReadBeforeWrite: true`）——否则主代理下次写
   这个文件会被「写前必读」门禁拦住（因为它不知道后台写过）；
2. **排 `pendingMemoryUpdate`** —— 下一轮通过 `memory_update` attachment 告知模型
   「我刚记了这些」。

Hlaudz 对应实现：

```python
# 写完记忆文件后
from .read_registry import ReadRegistry   # 现有模块
read_registry.record(path, complete=True)  # ← 主动登记为「已读」，绕过下一次门禁

# 并把「写了什么」排进注入队列（下一轮随记忆块一起注入）
memory_notice_queue.push(user_id, session_id, {"slug": slug, "title": title})
```

关于 `ReadRegistry`：注意它的注释写着「一次 generation 一份；不跨会话复用」。
所以后台写入的登记必须写到**该会话当前 generation 的 registry**，或者接受
「下次读一次即可」的降级。第一版取后者（简单、不会错），并在文档记下这个取舍。

### 4.5 写入子代理的提示词

必须显式约束三件事，否则模型会写出一堆无用记忆：

```
你在为一个用户整理长期记忆。

只有以下四类值得记（type 字段与 CC 原文 `type: user | feedback | project | reference` 对齐）：
1. user      —— 关于这个人：称呼、角色、语气、长期偏好（always private）
2. feedback  —— 用户对工作方式的纠正**和确认**（见下方「确认也算反馈」）
3. project   —— 跨会话的项目状态：做到哪、遗留什么、谁在做什么
4. reference —— 外部资源指针：URL、看板、工单号（usually team）

不要记：
- 本次任务的具体内容（那是会话历史的事）
- 你已经能从代码/文件里读到的信息
- 任何可能过期的临时状态

每条记忆一个文件，frontmatter 包含一行 description（<= 60 字，写给相关性选择器看，
要具体到能判断「这条和下一轮的提问是否相关」）。已存在的记忆优先 str_replace 更新，
不要重复新建同名条目。
```

#### 确认也算反馈（v3 §5.4 复核确认，v2 §14.3 正确）

**这是产品级行为差异，不是措辞。** CC 的原文（`m0293:3856` 的 `Qn` 提示词）写得很明确：

> Record from failure AND success: if you only save corrections, you will avoid past mistakes
> but drift away from approaches the user has already validated, and may grow overly cautious.

`<when_to_save>` 还给了三种确认信号，**逐字可抄**：

- `"yes exactly"`
- `"perfect, keep doing that"`
- `"accepting an unusual choice without pushback"`（用户对你一个反常规的选择没吭声）

只记纠正的后果是模型**越用越保守**——它会不断避开风味不明但正确的做法。
这个偏差单靠测「记没记住」是测不出来的，要测「三轮之后模型的表达是否变得畏缩」。

## 5. 工具面（模型可主动读写）

**对外只声明三个工具**（对齐 CC 客户端的已知名单 `Nji = ["memory_list","memory_read","memory_write"]`，
`m0290:8`，v3 §3 第 30 条）：

| 工具 | 作用 | 对齐 CC | 关键细节 |
|---|---|---|---|
| `memory_list` | 列出记忆，**分页** | `Pv`，`m0816:2988`（schema `:2956`） | 入参 `store` / `path_prefix` / `cursor`；默认页 **50**（`Hi = 50`）；出参含 `entries` / **`remaining`** |
| `memory_read` | 读一条记忆全文 | `qQr`，`m0591:75850`（schema `rJo` `:75831`） | 入参 `store` / `path`；`shouldDefer:!1`、`backgrounding:"never"`、`maxResultSizeChars: 1/0` |
| `memory_write` | 新建或更新一条记忆 | `z$t` 的 write/append | 带 **`if_version`** 做 CAS（§5.1） |

**没有 `memory_delete`。** 旧版把它列进了对外契约，但 CC 客户端的 `Nji` 里没有它——
它在服务端的 `z$t` 集合里（`m0191:2338`，写入子集），属于「服务端可能下发、客户端未承诺」的操作。
对外承诺 delete 会**超出 CC 的契约**，而且删除一条记忆用 write 覆盖成空即可。

> `memory_list` **必须实现分页**，这是 v3 §1.2 更正的核心：v2 把 `memory_list` 的行号
> 指到了 `memory_read` 的 schema（`m0591:75831` 只有 `store` + `path`），照那个实现会
> 漏掉 `cursor` / `remaining` / 默认页 50。而当记忆超过一屏时，`cursor` 是**唯一的续读路径**。

### 5.1 `memory_write` 的 CAS（对齐 CC 的 `if_version`）

CC 的 `memory_write` 带乐观并发控制（`m0394:1554`）：

- 入参可带 `if_version`；版本令牌 = **内容 sha256 前 12 位**（`mWe`，`:1516`）；
- 出参 `outcome: ok | conflict | missing | refused | failed`，
  冲突时返回 `currentVersion` + `currentContent`，调用方可据此重放；
- 单文档上限 **100 KB**（`:1553`）。

Hlaudz 照抄这条**不是过度设计**：写侧是后台子代理、读侧是主对话，
两者并发改同一条记忆是真实会发生的（用户在设置页手改 + 后台在写）。
没有 CAS 就是后写覆盖前写，且**用户的手改会静默丢失**。

```python
def write_memory(user_id, *, slug, title, description, body, kind="user",
                 if_version: str | None = None) -> WriteResult:
    cur = _read_version(path)                 # sha256(content)[:12]
    if if_version is not None and if_version != cur:
        return WriteResult(outcome="conflict",
                           current_version=cur, current_content=_read(path))
    ...
```

### 5.2 工具裁剪：子代理拿不到记忆工具

**三个工具只在 root agent 的 registry 里。** 理由：子代理如果也需要记忆，应该由 root
决定给它什么上下文，而不是让它自己翻用户的隐私记忆。所以这三个**照
`ORCHESTRATION_TOOLS` 的方式，从子代理 registry 里裁掉**，但语义上不属于「编排」，
另开一个集合：

```python
# capabilities.py
ORCHESTRATION_TOOLS = frozenset({...})   # 现有
MEMORY_TOOLS = frozenset({"memory_list", "memory_read", "memory_write"})
CHILD_EXCLUDED = ORCHESTRATION_TOOLS | MEMORY_TOOLS   # 子代理两者都拿不到
```

`build_capability_profile()` 里的 `available - ORCHESTRATION_TOOLS` 改成
`available - CHILD_EXCLUDED`。

> 这条有争议，记下取舍：也可以让子代理只读（`memory_read` / `memory_list`）。
> 第一版取「全禁」，因为子代理的记忆需求尚未被真实场景验证，先不给权限，
> 等有 e2e 案例再放开——**加权限比收权限容易得多**。
>
> 注意区分两个不同的授权面：**写入子代理**（§4.3）拿的是 `z$t` 写侧三件
> （`memory_write` / `memory_str_replace` / `memory_append`），它是为了写记忆而**专门派生**的，
> 不是普通子代理；**普通子代理**（`spawn_agent` 派生的）拿不到任何 `memory_*`。
> 这两件事不要混。

## 6. 与其他系统的关系

### 6.1 与 compaction 的关系（必须处理）

`compaction.enforce_soft_limit()` 会压掉老消息。**记忆不能跟着被压掉**——
它是以 `injected_message` block 形式存在历史里的，而 compaction 处理的是正文。

要确认的点：`compaction.py` 在压缩时是否保留 `injected_message` block。
如果保留，历史里的记忆块会越积越多（每轮注入一条）；如果丢弃，模型在压缩后
就「忘了」记忆。

**方案**：注入的记忆块**不进 `session_history` 持久化**（只在当前轮的内存 history 里）。
这样：
- 每轮都是重新计算的最新记忆（不会积累陈旧副本）；
- compaction 完全不受影响（压缩的是正文，不会碰到记忆副本）；
- 代价是刷新页面后看不到历史记忆注入记录（**可接受**：它是上下文，不是对话产物）。

⚠️ **不能只改 `chat.py`**。核实后发现「一轮的模型 history」有 **6 个持久化出口**，
其中 3 个在 `agent_loop.py` 自己身上：

| 位置 | 时机 |
|---|---|
| `sse.py:140/142` | 用户消息 append 后立刻存一次 |
| `agent_loop.py:275/277` | 每轮开头 `sanitize()` 修复了悬空 tool_call 后 |
| `agent_loop.py:411/413` | 每轮 `assistant` 消息 append 后 |
| `agent_loop.py:469/471` | 每个 tool 结果 append 后 |
| `compaction.py:161/251/296` | 压缩写回 |
| `chat.py:663` | `message_injected` 的**展示块**（`blocks`，不是模型 history） |

**真正的分界**：`chat.py:663` 存的是 `messages.blocks`（给前端渲染的展示结构），
而 `agent_loop` / `sse.py` 存的是 `session_history`（模型看到的对话）。
两者是**不同的表**。

所以正确的做法是：

1. **模型 history 侧**：注入的记忆 dict 带一个私有标记（`"_volatile": True`），
   在 `HistoryStore` 的**两个写入口**统一剥离：
   - `set()`（`history_store.py:105`，`json.dumps(payload)` 之前）
   - `append()`（`history_store.py:121`，`history.extend(new_messages)` 之前）

   这两个函数是 `session_history` 表的**全部运行期写出口**（已核对全仓
   `INSERT INTO session_history` 只出现在 `history_store.py:115` 与 `:144`；
   `:65`/`:76` 是一次性迁移语句，不在常规路径上）。在这里剥离，`agent_loop` 的 3 处 `set()`、
   `sse.py` 的 1 处、`compaction.py` 的 3 处全部自动生效——**不需要在每个调用点各改一次**
   （那是 8 处遗漏风险，而且是「改了新的忘了旧的」这类典型回归）。
2. **展示侧**：`chat.py:663` **照旧** append `injected_message` block 并在 SSE 里发出。
   这样用户当轮能看到「记忆进来了」，刷新后看到的是历史记录里的那一条——
   与现在的子代理通知/团队消息行为完全一致，**不改契约**。

修正后的结论：**实施时不需要改 `chat.py` 的任何逻辑**，只需在
`HistoryStore.set()` 里加一层剥离。这比原设想更安全（不动 SSE 契约文件）。

> 取舍说明：记忆块会留在 `messages.blocks` 里（展示侧），但不会进
> `session_history`（模型侧）。所以第二轮模型看到的是**新算的记忆**，不是上一轮
> 的副本——这正是我们要的「每轮重新计算」。而用户翻历史时仍能看到当时注入过什么。

### 6.2 与 A2A 的关系

A2A 调用面（P6）有 `tool_policy` 三档（`backend/app/tool_policy.py`）。记忆工具应该：

- `full`：全部可用（`allows()` 对 full 直接返回 True）；
- `read_only`：只剩 `memory_list` / `memory_read` —— 需要把它们加进
  `tool_policy.py:24` 的 `READ_ONLY_TOOLS`（当前是
  `{"file_read", "list_files", "load_skill"}`）。注意该常量同时决定 `describe()`
  的文案，加完要把 `POLICY_READ_ONLY` 的描述文字一并更新；
- `chat_only`：全部不可用（`allows()` 对 chat_only 直接返回 False，无需改动）。

**读侧注入对 A2A 同样生效**，但注入的必须是**该 token 所属用户**的记忆。
因为注入器闭包捕获的是 `AgentContext.user_id`，而 A2A 的 token 绑定 user_id，
所以天然正确——**但要有测试锁住**（§7 的 S-M4）。

### 6.3 与 Skill 的关系（容易混淆）

两者都是「每轮注入 + 按需加载」，但语义完全不同：

| | Skill | 记忆 |
|---|---|---|
| 内容 | 怎么做某类任务（可执行的流程） | 关于用户/项目的稳定事实 |
| 谁写 | 用户/开发者（导入技能包） | **模型自动写**（后台子代理） |
| 存储 | `SKILL.md`，双轨 builtin/shared/user | `memories/<user_id>/private/*.md` |
| 注入 | L1 索引（名字+描述）进 **system prompt** | 索引走 **instructions attachment**，正文按需读 |

**不要把记忆塞进 skill 索引**——skill 索引在 system prompt 里（装配时一次算好），
而记忆每轮都在变，塞进去会让 prompt 缓存彻底失效。这正是 CC 自己在记忆这块
选 attachment 而不选 system prompt 的原因（§3.5）。

## 9. 配置项（全部有默认可跑）

| 变量 | 作用 | 默认 |
|---|---|---|
| `HLZ_MEMORY_ENABLED` | 总开关（0 = 完全关闭，注入器返回空） | `1` |
| `HLZ_MEMORY_INJECT_BUDGET` | 每轮注入的**字符**预算（`len(str)`，即 code point） | `2000` |
| `HLZ_MEMORY_INJECT_MAX` | 每轮最多注入条数 | `12` |
| `HLZ_MEMORY_INDEX_MAX_CHARS` | 索引 cap（**code unit / code point**，不是字节，见 §3.6） | `25000` |
| `HLZ_MEMORY_INDEX_MAX_LINES` | 索引行数 cap | `200` |
| `HLZ_MEMORY_RECALL_MAX_BYTES` | 单文件召回 cap（**真字节**，`len(s.encode())`） | `4096` |
| `HLZ_MEMORY_EVERY_N_TURNS` | 每 N 轮尝试写入（闸 3） | `3` |
| `HLZ_MEMORY_MIN_PROSE_WORDS` | prose 闸门阈值（CJK 2 字 = 1 词） | `50` |
| `HLZ_MEMORY_AUTO_WRITE` | 自动写入总开关（0 = 只能模型显式调用 `memory_write`） | `1` |

**三个 cap 的单位不同，不能合成一个变量**（v3 §1.3）：
索引按 `code unit` 计（`Gee = 25000`）、单文件召回按真字节计（`Ibe = 4096`）。
CC 内部就是两套口径并存，源码把它们都命名成 `byteCount` 是**起错了名字**。
若 Hlaudz 图省事用一个「25KB 字节」的索引 cap，**中文索引会在 1/3 处被截**。

**`HLZ_MEMORY_AUTO_WRITE=0` 是重要的降级出口**：自动写入如果误记了糟糕的东西，
关掉它比回滚代码快。

> 没有 `HLZ_MEMORY_FIRST_LOOK_MODE`。`first_look` 是 CC 的 MCP 模式专属闸（§4.2），
> 文件模式没有这道闸，本方案不加。将来要加时再补这个开关。

## 10. 风险与未决项

| 风险 | 影响 | 缓解 |
|---|---|---|
| 记忆被污染（模型记错、记住噪声） | 之后每轮都注入错的上下文，**比不记更糟** | ① 前端设置页可查看/删除每条记忆；② `hit_count` + `last_hit_at` 让「从没被用到的记忆」可识别；③ `HLZ_MEMORY_AUTO_WRITE=0` 降级 |
| 注入的记忆与用户当轮说法冲突 | 模型犹豫或按旧偏好行事 | 注入块写明「记忆可能过时，以用户当前说法为准」 |
| 后台子代理与主轮抢连接池 | 连接池紧张时追加压力 | 写侧用**独立的低优先级客户端**，或复用但受 `HLZ_LLM_POOL_CEILING` 约束（已有自动扩容，见连接池文档 §4.5） |
| `[记忆]` 前缀与用户真实发言冲突 | 用户自己说「[记忆] xxx」会被误分类 | 前缀判定只在 `injected_message` block 内做（不是扫描所有文本），且注入方是我们自己 |
| 记忆越攒越多 | 即使有预算，DB 查询与文件扫描变慢 | 超过 `HLZ_MEMORY_MAX_ENTRIES`（建议 500）时，按 `last_hit_at` 淘汰最久未用的 |

**未决**（需要你决定，不阻塞 M1–M3 开工）：

1. **`team` 作用域第一版要不要做？** 我建议**不做**。理由：Hlaudz 现在是单用户维度
   （多用户但无团队概念），`team_key` 怎么算没有好答案。表结构已预留 `scope` + `team_key`，
   将来加不用改表。注意这和旧版问的「`project` 作用域」不是同一件事——CC 的维度是
   private/team，没有「项目」这个作用域。
2. **记忆要不要用户可见可编辑？** 我建议**要**（设置页新增一个 tab，与「我的 Skills」并列）。
   模型自动写的东西如果用户看不见，出了错没法纠正。
3. **`MEMORY.md` 入口文档要不要？** CC 有，但那是给「记忆 store 有多份文档」的场景。
   第一版只有几十条记忆，`memory_list` 就够了。建议**先不做**。
4. **索引注入要不要做 `changed` 增量？**（§3.5）建议**第一版不做**，每轮全量发。
   理由：注入产物不持久化（§6.1），全量发不会累积；增量需要额外在 `AgentContext` 上维护
   版本戳，是优化不是功能。记在这里是**已知与 CC 的差异**，条目多了再补。

## 1. 为什么这三件事单测测不到

`backend/tests/` 现有 1012 项测试，覆盖的是**判定逻辑**：闸门函数给定输入返回什么、
`acquire_lock` 的 SQL 在单进程无竞争时对不对、API 返回什么形状。

它们原理上测不到三类东西：

| 类别 | 单测为什么测不到 | 只能靠什么 |
|---|---|---|
| **渲染** | `npm run build` 通过 != 页面能用。组件可能挂在 `undefined` 上、CSS 把按钮挤出可视区、tab 切换白屏 | 真浏览器 |
| **真并发** | 单测的「并发」多是 `asyncio.gather` 两个协程，共享同一事件循环。真实竞态发生在两个写者各自走完整路径时，每个 `await` 都是换手点 | 构造真实交错 |
| **跨进程** | `UPDATE ... WHERE` 的原子性只在两个独立进程同时执行时才被检验 | 起真进程 |

### 2.2 三个「只有真浏览器能发现」的设计点

**① 按钮在可视区内。** `bounding_box()` 检查 `x/y` 非负、右边界不超视口、
宽高 > 阈值。CSS 布局错误在 `tsc` 和 `vite build` 都不报错。

**② 原生 `confirm()` 要显式接管。** 前端删除用的是 `window.confirm()`，
Playwright **默认自动取消**对话框 —— 不 `page.on("dialog", accept)` 的话
点删除什么都不会发生。第一版没接，会被误判成「删除功能坏了」。

**③ 落库核对不能用列表文本。** 第一版断言「改完描述后旧描述不该出现在列表里」
失败了。原因：种子数据里 `title == description`，改 description 后标题仍含原文。
**那是测试的错，不是产品的错**。改成用 API 核对 `description` 命中 + `content`
非空 + `title` 未被误改。

### 2.5 一次误报的排查记录（值得记住）

第一次跑 `--keep` 后，`m02_dream.png` 显示「1 条记忆 / 已跑 1 次」，
而预置是 6 条。怀疑「dream 在 UI 打开前自己跑了」。查证过程：

1. 写 `work/_dream_timeline.py` 单独起服务，等 20 秒观察巡检 ——
   `runs` 始终 0，证明巡检不会自行触发（默认 600s 间隔 + 24h/5 会话闸）。
2. 在 `ui_dream.py` 里加 debug 打印「页面文字 vs API total」。干净重跑后
   两者都是 6，`runs` 标签不出现。
3. 结论：那张图是上一次运行残留的同名文件，本次未覆盖（`--keep` 保留了目录，
   而我当时没清）。清空 `work/memory_ui_shots/` 后三次重跑均无复现。

**教训写进了脚本注释**：断言要看「页面 vs API 一致性」，不要靠肉眼比对截图。

### 2.6 顺带钉住的语义

排查中发现一个「碰巧成立」的行为：`last_consolidated=0`（从没跑过）时，
`now - 0` 远大于 24h，时间闸天然放行。这**是设计意图**（首次整理不该等一天），
但没人写过，容易被后来者当 bug「修」掉。已补：

## 3. dream 与提取并发写（`tools/memory_verify/concurrent_write.py`）

### 3.1 六个场景

| 场景 | 构造 | 首轮结果 |
|---|---|---|
| C-1 同 slug 盲写 | dream 与提取同时写 `shared`，各带标记 | OK：最终是其中一方的**完整**内容，无交错 |
| C-1b CAS 保护 | 带过期 `if_version` 写 | OK：`outcome=conflict`，不静默覆盖 |
| C-2 delete 与提取 | dream 读快照后提取写 `late`，dream 再删 `dup` | OK：未点名的 `late` 完好 |
| **C-2b 盲删竞态** | dream 读旧版 → 提取补新事实 → dream 按旧快照删 | ❌ **RISK：新事实随文件一起消失** |
| C-3 索引一致性 | 并发写 5 条 + 重建索引 | 首轮 RISK（见 3.3） |
| C-4 双 dream 互斥 | 两个 `acquire_lock` | OK：第二个被拒 |

### 3.2 C-2b：修掉的真实缺陷（本轮最重要）

**现象**：`memory_delete` 只有「先写后删」闸，没有版本检查。dream 在 Phase 1
用 `memory_list` 看到 `dup`（描述说它是重复项），Phase 2 期间提取器给 `dup`
补了一条新事实，dream 按旧快照执行 delete —— **新事实跟着文件一起没了**。

**根因**：`delete_memory(user_id, slug)` 是无条件 unlink。它没有 `if_version`
参数，也没有「读过没有」的概念。

**修法**（`memory_dream._build_delete_tool`）加两道**代码级**闸：

1. **先读后删**：`budget.seen` 记录模型 `memory_read` 读到的 version。
   没读过就删 → `refused`。理由：`memory_list` 的 `version` 是**空串**
   （`_row_to_spec(with_version=False)`），所以「只看了描述」不算读过 ——
   而描述只是索引，正文里可能有 list 看不到的事实。
2. **读后未变**：读到的 version ≠ 当前 version → `conflict`，并返回
   `currentContent` 让模型重读确认。

**为什么不靠 prompt**：提示词里已经写了「先 memory_read」，但模型会忘。
而 `budget.seen` 是我们**确定性**知道的（由 `_wrap_seen_tracker` 包
`memory_read` / `memory_list` 收集），不依赖模型配合。

**为什么不要求模型传 `if_version`**：多一个模型必须记住的约定，就多一种
「模型没照做 → 数据丢了」的失败路径。

**复验**：C-2b 从 `RISK` 变 `OK`（`outcome=refused`）；
`S-M8` 真机重跑仍 5→1、内容保留、44.8s —— **模型自然地先读再删，没卡住**。

### 3.3 C-3：索引一致性的正确判据

首轮判 RISK 的理由是「并发期间索引 6 行 / 实际 9 条」。复查后判定**判据错了**：

- `rebuild_index` 是「reconcile → 读表 → 写文件」三步快照，任何快照式重建
  在写文件期间都可能有新条目落盘。要消除它只能给整个记忆写路径加全局锁 ——
  代价远大于收益，因为：
- **`MEMORY.md` 目前没有任何运行期读取者**（`grep -rn index_path app/` 可验证）。
  注入走 DB（`select_with_stats`），这个文件只给人看。

所以真正要验的是**收敛性**：并发期允许陈旧，安静下来重建一次必须精确一致。
改成两阶段判据后通过：

```
并发期快照 5 行（允许），安静重建后 9 行 = 实际 9 条
```

同时保留硬判据：**任何阶段都不许有指向不存在文件的幽灵行**。

> ⚠️ 这条前提在将来会变。方案 §3.5 计划把 `MEMORY.md` 作为 attachment 注入，
> 那时它就有运行期读取者了，届时要重新审视「并发期允许陈旧」是否还成立。

### 3.4 C-1 说明了什么

两个写者都**不带** `if_version` 时，结果必然是「后写覆盖先写」——文件系统层面
无法避免。可接受的原因是：

- 提取器写的是**不同 slug**（它写「本轮新事实」），与 dream 的「合并已有条目」
  目标基本不重叠；
- 真要防，靠 `if_version`（C-1b 证明有效），而 `memory_write` 工具本来就鼓励带。

判据只要求「不出现**交错拼接**」—— 那才是文件损坏，比覆盖严重得多。

## 4. 跨进程锁竞争（`tools/memory_verify/multi_process_lock.py`）

### 4.1 为什么不是「uvicorn --workers 2」

`backend/run.py` 是**单 worker**（`uvicorn.run()` 未传 `workers=`）。
当前部署形态里不存在多 worker。所以「多 worker 锁竞争」的实质问题是：

> **DB 行锁在跨进程时真的互斥吗？**

这跟进程是不是 uvicorn worker 无关。两个独立 Python 进程同时抢同一行，
就是对锁语义最直接的检验，而且比启动多 worker 更可控（能精确控制时序、
能直接读 DB 断言、不受 Windows spawn 模式干扰 —— 实测 `workers=2` 在
`multiprocessing.spawn` 下要先 `if __name__ == '__main__'`，而 `run.py`
的 `uvicorn.run` 在模块顶层，直接跑会 `RuntimeError`）。

### 4.2 四个场景

| 场景 | 构造 | 结果 |
|---|---|---|
| P-1 跨进程互斥 | 2 进程同时 `acquire_lock`，各 hold 1s | ✅ 恰好 1 个成功 `[False, True]` |
| P-2 崩溃后语义 | A 抢到后被 SIGKILL，B 立刻抢；再把 `lock_at` 改老 31 分钟后抢 | ✅ 新鲜锁不误抢（`False`），过期可抢（`True`） |
| P-3 真串行 | 4 进程**持续重试** 6 秒，每个成功后 hold 0.15s | ✅ **35 次成功抢锁、4 个进程、持锁窗口两两不重叠** |
| P-4 收敛救崩溃 | A 崩溃留新鲜锁 → `recover_dream_state()` → B 抢 | ✅ 挡并发（`False`）→ 收敛后立刻可抢（`True`） |

### 4.3 P-3 的一次判据改进

第一版让输的进程直接退出，结果只有 **1/4** 成功 —— 那只证明「抢不到」，
没证明「串行」。改成输的人**重试 6 秒**后，每个进程都会多次拿到锁，
再检查所有成功者记录的 `[start, end]` 窗口两两不重叠。
重叠 = 两个进程同时认为自己持锁 = 互斥失效，这才是要抓的东西。

### 4.4 P-2 揭示的一个边界（如实记录）

P-2 里「A 被 SIGKILL 后，锁仍新鲜时 B 抢不到」是**预期行为**，不是缺陷：
DB 行锁无法判断持锁进程是否还活着（`lock_pid` 只是记录，不是探测）。
这正是 `recover_dream_state()` 存在的理由 —— P-4 证明它能在**不依赖
30 分钟过期**的情况下把锁救回来。

若将来要做「检测持锁 PID 是否存活」，需要注意多 worker / 容器的 PID 视图
不可靠（这正是方案 D-9 选 DB 行而非文件锁的原因）。当前选择是
「启动时收敛 + 30 分钟兜底」，实测足够。

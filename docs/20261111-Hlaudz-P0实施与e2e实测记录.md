## 3. 真实 LLM e2e（湛卢）

命令：`cd backend && python -m tests.e2e.run --case S0`（或 S1、S2、S5、S7、S8）

| 场景 | runId | 耗时 | 工具序列 | 结果 |
| --- | --- | --- | --- | --- |
| S0 负对照 | `1794286859-0102` | 4.6s | current_time | PASS |
| S8 工具选择 | `1794286870-a93a` | 8.3s | file_grep → list_files → file_glob → file_grep | PASS |
| S1 subagent 基础 | `1794286886-2e9d` | 14.2s | spawn → wait → read → close | PASS |
| S5 team 基础 | `1794286905-1019` | 42.5s | task_create×2 → spawn_teammate → wait → read → task_get → task_update×2 → task_list → close | PASS |
| S2 subagent 并行 | `1794286968-11f8` | 14.4s | spawn×3 → wait → read×3 | PASS |
| S7 取消 | `1794286988-1b5f` | 11.4s | spawn×2 → close → wait → read | PASS |

关键证据：

1. **S8 证明工具策略生效**——模型用 `file_grep` 找 TODO，**一次都没用 `code_run`**；
   改动前它只会 `code_run`（`forbid_tools` 会直接失败）。
2. **S0 负对照**——「今天几号」没有触发任何搜索/派发工具，说明 S8 不是碰巧。
3. **S2 计数断言**——`spawn_agent` 恰好 3 次，没有重复派活。
4. **S5 数据审计**——两个 team 任务终态都是 `completed`，任务 A 由 teammate 完成、
   B 由 root 完成，version 从 0→2，无悬挂、无 zombie running。
5. **S7 审计**——两个子代理 `subagent_end` 都是 `completed`（第二个在被关闭前已跑完），
   `close_agent` 返回 `{"ok": true, "closed": ["second"]}`。

现场全部保留在 `backend/tests/e2e/runs/<runId>/`（events.jsonl / summary.json / messages.json）。

### 3.1 为什么这轮一个缺陷都没抓到

按 skill 的规则，全绿且零缺陷要先把「断言太宽」排除掉。已做三件事：

1. 每条 e2e 都有 `forbid_tools` 或 `tool_counts` 的负向断言，不是只看"跑通了"；
2. 两条关键实现路径做了变异验证（§2.2），确认测试能变红；
3. 深入审计了 S5/S7 的原始事件与任务板终态，不是只看 summary 的 PASS。

诚实的结论：**这一轮改动的范围（工具层 + 提示词）本来就不太可能引出 subagent 链路缺陷**，
S1/S2/S5/S7 只是回归确认。真正的链路压力测试（S3 超时、S6 规模、steer、通知注入）
要等 P2 实施时才有意义。

## 4. 行为变更（需要知晓）

| 变更 | 影响 | 处理 |
| --- | --- | --- |
| 写前必读 | 覆盖已存在文件前必须先 `file_read`；append / 新文件放行 | 既有测试 `test_builtin_tools_file_roundtrip` 已按新语义加一次读取 |
| `code_run` 输出不再二次截断 | 改由预算层统一处理（30K 上限 + 落盘） | 前端按文本渲染，无影响 |
| `file_read` 结果走预算 | 超大文件会落盘并返回路径 | 模型可用 `file_read` 读回落盘文件 |
| 工具并发 | 多个只读调用可能同时执行 | 事件顺序保持原序；写类仍串行 |

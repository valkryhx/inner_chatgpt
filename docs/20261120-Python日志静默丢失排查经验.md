# Python 服务日志「静默丢失」排查经验

> 日期：2026-11-20
> 起因：沙箱服务端到端探针报「池层真的建了槽」失败，但池行为完全正确。
> 结论：**不是 uvicorn 的 bug，是我对 logging 默认行为的误判。**
> 适用范围：任何「用 uvicorn/gunicorn 起、自己 `logging.getLogger(__name__)`」的 Python 服务。

---

## 0. 一句话

**`logging.getLogger("x.y")` 打的 INFO 默认会消失，且不报错、不警告。**
根因是 root logger 默认 level = WARNING、默认没有 handler。
`--log-level info` 只调整 uvicorn 自己的 logger，**不会**改变 root 的 level。

---

## 1. 现场：一个"服务对、但看不到"的假失败

端到端探针断言「日志里出现『建槽』」，结果拿不到：

```
[FAIL] 池层真的建了槽（日志有「建槽」）
       — INFO: 172.17.0.1:49664 - "POST /v1/exec HTTP/1.1" 200 OK
         INFO: Application startup complete.
         INFO: Uvicorn running on http://0.0.0.0:8021
```

`/v1/exec` 全部返回 200、槽确实建了、内存确实涨了——**行为全对，只是日志没出来**。

这类失败最耗时间，因为：
- 业务断言全过，只有"可观测性"断言红
- 很容易误判成"功能没实现"，去改本来正确的代码
- 也容易反过来：把探针改松（比如改成 `logs.count("建槽") <= 10`），
  于是这个探针**再也不会有价值**

## 2. 机制（本机实测，非推测）

### 2.1 uvicorn 只配它自己的 logger

```python
from uvicorn.config import LOGGING_CONFIG
LOGGING_CONFIG["loggers"]        # ['uvicorn', 'uvicorn.access', 'uvicorn.error']
'root' in LOGGING_CONFIG         # False      ← 关键：没有 root
LOGGING_CONFIG["disable_existing_loggers"]   # False
```

`disable_existing_loggers=False` 意味着它**不会破坏**你已经配好的 logger，
但也**不会**帮你配。所以应用 logger 保持 Python 的默认状态。

### 2.2 Python 的默认状态是什么

```
root.level            = WARNING      ← 不是 INFO
root.handlers         = []           ← 空的
logging.lastResort    = <handler>    ← level 也是 WARNING
myapp.demo.propagate  = True         ← 往 root 传
myapp.demo.level      = NOTSET       ← 取 root 的 WARNING
```

于是 `logger.info(...)` 的路径是：

```
logger.info() → level 判定（NOTSET → root 的 WARNING）→ INFO < WARNING → 直接丢弃
```

**它在 level 判定那一步就被丢了，根本走不到 handler。** 这就是为什么
"加 handler"和"设 level"**两件都要做**，只做一件没用。

### 2.3 决定性对照实验（同一个 app，只差一段配置）

```python
# app_mod.py
import logging
logger = logging.getLogger("sandbox_service.demo")

def emit_all():
    logger.info("A_BARE_INFO")
    logger.warning("B_BARE_WARNING")
```

```python
# main.py —— 有 _configure()
def _configure():
    root = logging.getLogger("sandbox_service")
    if root.handlers:
        return
    h = logging.StreamHandler()
    h.setFormatter(logging.Formatter("%(levelname)s %(name)s: %(message)s"))
    root.addHandler(h)
    root.setLevel("INFO")
_configure()
```

| 场景 | `A_BARE_INFO` 是否出现 |
| --- | --- |
| 无 `_configure()`，`--log-level info` | ❌ **0 次** |
| 无 `_configure()`，`--log-level debug` | ❌ **0 次** |
| 有 `_configure()` | ✅ 1 次 |

**两个关键否定结论**（都实测过，不是"我没搜到"）：

1. **`--log-level info` 救不了** —— 它只改 `uvicorn*` 三个 logger 的 level。
2. **`--log-level debug` 也救不了** —— 同上。root 仍是 WARNING。

而 `logger.warning()` **一直能出来**（走 `logging.lastResort`，它的 level 是 WARNING）。
所以现象是「warning 有、info 没有」，很容易被误读成"info 被某个 filter 吃了"。

## 3. 为什么这个坑难被自己发现

| 原因 | 说明 |
| --- | --- |
| **不报错** | logging 的设计就是"静默丢弃"，没有异常、没有警告 |
| **warning 能出来** | 于是"日志功能是好的"这个印象成立，只是"info 不显示" |
| **本地 `python -m uvicorn` 时偶发能出** | 如果之前有人 `logging.basicConfig()` 过，root 就被配好了——**换个入口就变** |
| **容器里更难查** | `docker logs` 里只有 uvicorn 那几行，看不出少了什么 |
| **测试里看不出来** | 单测通常 caplog 或直接调函数，不经过 uvicorn 的 logging 初始化 |

---

## 4. 正确做法

### 4.1 在自己的包根 logger 上显式配置（推荐）

```python
logger = logging.getLogger(__name__)


def _configure_logging() -> None:
    root = logging.getLogger("sandbox_service")   # ← 包根，不是 __name__
    if root.handlers:                              # ← 幂等：避免 reload/多测例重复加
        return
    handler = logging.StreamHandler()
    handler.setFormatter(
        logging.Formatter("%(asctime)s %(levelname)s %(name)s: %(message)s")
    )
    root.addHandler(handler)
    root.setLevel(os.environ.get("HLZ_SANDBOX_LOG_LEVEL", "INFO").upper())


_configure_logging()   # 模块加载时执行
```

三个要点：

1. **配包根**（`sandbox_service`）而不是 `__name__`（`sandbox_service.main`）——
   这样 `sandbox_service.pool`、`sandbox_service.executor.bwrap` 的日志一并覆盖，
   否则每加一个模块就要记得再加一次。
2. **必须 `if root.handlers: return`** —— 否则 pytest 多测例 import、
   uvicorn `--reload` 都会重复加 handler，日志变成每行打印 N 遍。
3. **level 可配**（`HLZ_*_LOG_LEVEL`）—— 生产想静音、排查想开 DEBUG。

### 4.2 反面做法（不要用）

```python
logging.basicConfig(level=logging.INFO)   # ← 动 root
```

**不行**，两个原因：
- 它给 **root** 加 handler，会和 uvicorn 的 handler 叠加 → 同一条日志打两遍
- 库代码动 root 是越权行为，调用方可能已经配好了自己的 root

### 4.3 如果是库（不是应用）

**什么都别配**，只 `logger = logging.getLogger(__name__)`，
让调用方决定输出。库动 root 是最常见的"为什么我的日志格式被搞乱了"来源。

## 5. 排查清单（下次遇到"日志没出来"）

按顺序，每一步都是**可执行的验证**，不是"想一想"：

1. **确认是 level 还是 handler**
   ```python
   lg = logging.getLogger("your.pkg")
   print(lg.level, lg.handlers, lg.propagate, logging.getLogger().level)
   ```
   - `handlers == []` 且 `propagate == True` → 靠 root；root 没 handler 就没输出
   - `level` 是 `NOTSET(0)` → 取父级；父级若 WARNING，INFO 直接丢

2. **确认 `--log-level` 有没有用**（它只管 uvicorn 自己的 logger）
   打一条 `logger.warning()`：出来但 INFO 不出来 → 就是 level 问题

3. **确认是不是容器/重定向丢了**
   `docker logs` 与容器内 `2>&1` 各看一次（uvicorn 的 access log 走 stderr）

4. **确认不是 caplog 掩盖**
   单测里 `caplog` 能拿到日志不代表真实运行时能看到——它绕过 level 判定

## 6. 这次踩坑的完整时间线（供参考"多久能发现"）

| 步 | 动作 | 耗时 |
| --- | --- | --- |
| 1 | 端到端探针报「池层真的建了槽」失败 | — |
| 2 | 怀疑池没接上，读 `main.py` 确认 `_get_pool()` 被调用 | 短 |
| 3 | 怀疑 `logger.info` 写错位置 | 短 |
| 4 | 怀疑 uvicorn 吞了日志 → **误判成「uvicorn 的坑」** | 中 |
| 5 | 读 `uvicorn.config.LOGGING_CONFIG`，发现没有 `root` 键 | 短 |
| 6 | 写对照实验（有/无 `_configure()`） | 中 |
| 7 | 确认 `--log-level info/debug` 都救不了 | 短 |

**关键转折在第 5 步**：从"猜 uvicorn 有 bug"变成"读它的配置"。
前者会让人去搜 workaround，后者才指向真因。

> ⚠️ 本经验文档的第一版结论是「**uvicorn 不给 app logger 配 handler 是个 bug**」——
> **这是错的**。uvicorn 刻意不碰应用 logger 是**正确设计**（库/框架不该替应用
> 决定日志去 哪）。写成"bug"会误导后来人去找 workaround 而不是自己配 logger。
> 订正记在这里，因为**错误模式比正确结论更有复用价值**。

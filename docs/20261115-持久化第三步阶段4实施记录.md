## 0. 一句话

静默超时补一帧 `: keep-alive`，真机在 40 秒 `code_run` 空档里按 **3 秒**准点到达线上；
顺带修掉一个**会让 job 永久泄漏、续看挂死**的真 bug，以及一个**刷新后接到死流**的真 bug。

---

## 1. 为什么现在做（相对阶段 2 的判断变了）

阶段 2 记录里写的是「实测能撑过 36s 空闲，暂不需要」。那个结论成立的**前提是直连 uvicorn**。

核实两个成熟项目后发现两家都默认开着：

| | 值 | 形态 |
|---|---|---|
| LibreChat | **25s** | 静默计时（安静满 25s 才发） |
| Aivory | **25s**（通知流）/ **15s**（生成流） | 固定 ticker |

Aivory 的理由直接写在注释里（`messages_handlers.go:2009`）：「§6.2: 15s heartbeat to keep
proxies from closing the SSE channel」——**它不赌部署形态**。LibreChat 更具体
（`keepalive.ts:82-84`）：「Cloudflare drops a response after 100 s without bytes」。

一旦前面挂 nginx（`proxy_read_timeout` 默认 60s）或 Cloudflare（100s），36s 的余量不够，
而且被切的是**续看连接**——用户看到内容停住，正是阶段 2 刚修好的那个体验。

**所以要抄的是 LibreChat 的「静默计时」，不是 Aivory 的固定 ticker。** 固定 ticker 在
高速输出时是纯浪费：我们一轮几千帧，25s 内根本不会安静，心跳一帧都不需要发。

## 2. 心跳实现

`Subscriber.drain()` 里把 `await queue.get()` 换成 `await asyncio.wait_for(queue.get(), idle)`，
超时就 yield 一帧 `: keep-alive\n\n`：

```python
try:
    item = await asyncio.wait_for(self.queue.get(), idle)
except asyncio.TimeoutError:
    if self.overflow:
        return
    yield _HEARTBEAT_FRAME
    continue
```

四条设计约束（每条都有测试钉住）：

| 约束 | 为什么 |
|---|---|
| 心跳**不经过** `publish()` | 于是不占 `seq`、不进重放缓冲 —— 它不是真事件，游标不该被它推进 |
| 心跳是**纯注释行**（无 `id:` / `data:` / `event:`） | 带 `id:` 会让前端 `parseFrame` 把它当游标（`api.ts` 的 `onSeq`），下次从 after=999 回来就跳过中间所有真实事件 |
| 静默计时而非固定 ticker | 有帧在流动时一帧都不发 |
| `HEARTBEAT_IDLE_S <= 0` 时关闭 | 直连 uvicorn 时心跳只是噪音，得关得掉 |

默认 15 秒（`HLZ_TURNJOB_HEARTBEAT_IDLE_S`）。

### 2.1 `wait_for` 会不会丢帧

这是关键担心：超时取消的是 `queue.get()`，队列项会不会一起没了？

实测 30 轮 × 200 帧、超时压到 1ms（几乎每帧都撞超时）：**丢帧 0 轮**
（`tools/turn_job_verify/lifecycle_probes.py` 的 P4）。CPython 3.13 上取消的是外层 future，
队列项留在原位。另有交错场景测试（每帧间隔远大于心跳阈值）钉住「真实帧不丢、顺序不乱」。

## 3. 顺带修掉的两个真 bug

### 3.1 job 在「尚未开始执行」时被取消 → 永久泄漏（严重）

`start_job` 原来的收口只有 `_wrapped` 的 `finally`。但实测
（`tools/turn_job_verify/lifecycle_probes.py` 的 P1）：

```
A 已开始后取消： ['body-entered', 'finally']
B 未开始就取消： []
```

**协程体一行都没执行就 cancel 的话，`finally` 根本不跑。** 于是：

```
表里还有这个 job 吗 : True      ← 永远留在 _JOBS
live_job_count()    : 1        ← 永不下降
drain 结果          : 超时 —— 永久挂住，永远等不到结束
```

`/stop` 抢在首帧之前到达就是这个窗口。后果是 job 表泄漏 + 续看端拿到一个永远不产出帧的
job 并挂死。

修法：`start_job` 里加 `task.add_done_callback(_reap)` 兜底。先验证了 done_callback 在
「未启动即取消」时**仍会触发**（该脚本 P2：`done(cancelled=True)`），
所以它是与执行路径无关的唯一收口。`finish()` 幂等，两条路径都调无害。

### 3.2 同一会话两个未 finish 的 job → 刷新接到死流（严重）

`get_live_job_for_session` 原来是「扫到第一个未结束的就返回」。这个窗口真实存在
（该脚本 P5 复现）：

```
_event_stream finally → await release_generation()   ← DB 租约此刻已空
_run_job finally      → unregister / 清 reservation
_wrapped finally      → job.finish() 摘出 _JOBS
```

中间那段 `await` 里新请求已经能抢到租约并建新 job。`_JOBS` 是 dict 且旧键先插入，
`for ... return` 会**稳定返回正要收尾的旧 job**：

```
此刻 _JOBS        : ['g-new', 'g-old']
get_live_job 取到 : g-old        ← 错
应该取到          : g-new
```

表现就是「刷新后一直转圈、内容不动」——看着像阶段 2 没生效，其实是接错了代。

修法：job 加 `started_at`（模块级 `itertools.count` 单调序），挑代际最新的。不用字符串比
`generation_id`（随机 id 不可比），也不用挂钟（同毫秒可能建两个）。

**这一条是 LibreChat `generationCreatedAt` 栅栏的等价物。** 它那样做是因为它的
`streamId === conversationId`（一个会话一个流，没有别的寻址方式）；我们的 job key 本来
就带 `generation_id`，所以材料是有的——只是查找函数没用上。

## 5. 三处我判断错、靠实测纠正的地方

写下来是因为它们都属于「看起来对、实测不对」：

1. **「心跳憋在缓冲区 40 秒」** —— 第一版真机探针用 `res.read(256)`，而
   `io.BufferedReader.read(n)` 会**循环补齐到 n 字节**才返回。15 字节的心跳要攒够 256
   字节才吐一次，于是看起来像「41s 一起到」。改用 `read1()` 后真相是逐帧到达。
   **探针的读取方式会伪造出「缓冲」现象**，这类错误比代码 bug 更难发现。

2. **「阶段 2 已经够了」** —— 36s 余量只在直连时成立。这个判断本身没错，但它依赖一个
   没写下来的前提（无反向代理）。两家都默认开心跳，不是因为他们测到了 bug，而是因为
   不该赌部署形态。

3. **「`get_live_job_for_session` 取第一个」** —— 我上一轮说这是「缺 LibreChat 的
   `generationCreatedAt` 栅栏」，措辞不准确：我们的 job key 里本来就有 `generation_id`，
   缺的不是栅栏材料，是查找函数没用上它。改起来只有几行。

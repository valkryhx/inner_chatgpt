- 日期：2026-11-11
- 分支：`feat/ga-cc-alignment`
- 模型：湛卢（`moma/deepseek-latest-flash`）

## 0. 结论

压测抓到 **1 个真实功能缺陷**，已修复并验证：

> **teammate 产生的事件永远进不了 lead 的 SSE 流。**
> `TeamHost.events_since()` 只推进游标、不发布事件，导致前端 team 面板
> 看到的是「任务一直 pending / in_progress」，而数据库里其实已经全部完成。

规模场景的定量证据：13 个任务全部 `completed`（DB），但 SSE 只收到 16/43 条事件，
缺 27 条（其中 20 条 `task_updated`）——**面板正确率 30%**。

修复后复跑：SSE 与 DB 完全一致，任务终态检查通过。


### 1.4 S10 长任务（>10 分钟）

第一次运行（`1794290004-77d2`）**失败**，暴露的是一个产品限制，不是偶发缺陷：

```
subagent_runs: long_sleep_runner  status=stopped  error="timeout: 超过 300s"
```

子代理的墙钟超时是 `SUBAGENT_TIMEOUT_S`，默认 **300 秒**；而任务需要 660 秒。
子代理在 300 秒被强制停止，模型只能拿到 `stopped` + timeout 错误。

**决策**：

- 默认提到 **1800 秒（30 分钟）**——300 秒会静默杀掉合法的长任务；
  30 分钟仍能兜住失控任务；
- `spawn_agent` 新增 `timeout_seconds`，可按次覆盖（0 = 用默认）；
- 环境变量 `SUBAGENT_TIMEOUT_S` 仍然优先，便于部署侧统一调整。

**测试**（`test_subagent_timeout.py`，3 条）：

| 用例 | 断言 |
| --- | --- |
| `test_default_timeout_supports_long_tasks` | 默认 ≥ 1800s |
| `test_spawn_timeout_override` | `spawn(timeout_s=0.3)` → 1 秒内变 stopped 且 error 含 timeout |
| `test_spawn_agent_schema_has_timeout_seconds` | 工具 schema 暴露该参数 |

**第二次运行（修复后）**：

```
runId=1794290904-a3bd   763.5s   PASS
tools = spawn_agent → wait_agent ×4 → read_agent_result
subagent: completed，723s，4 轮，无 timeout、无 error
```

关键证据：

- `wait_agent` 被调用 **4 次**（每次超时后继续等），**没有重新 spawn**——
  提示词「超时不是失败」在 12 分钟的时间尺度上依然成立；
- 子代理把 660 秒拆成 590s + 75s 两段 `code_run`（每段都在自己的 timeout 内），
  累计 665 秒后打印 `LONG DONE`，说明模型会主动规避单次工具超时；
- 审计：`subagent_started = 1 / ended = 1 / completed`，`zombie_running = []`。

## 2. 缺陷：teammate 事件进不了 lead 的 SSE

### 2.1 现象

team 面板上，13 个任务里 11 个显示 `pending`、2 个显示 `in_progress`，**一个都没有变成完成**。
但直接查库：13 个任务全是 `completed`。

### 2.2 根因

```python
# backend/app/team_host.py（修复前）
async def events_since(self, since_seq=0, limit=200):
    rows = await team_store.events_since(self.scope, since_seq, limit)
    for row in rows:
        self._observed_seq = max(self._observed_seq, int(row["event_seq"]))
    return rows           # ← 只推进游标，从不 publish
```

`backend/app/subagent/session.py` 把 lead 的每个 team 工具包了一层：

```python
async def observed(args, _original=original):
    try:
        return await _original(args)
    finally:
        await team_host.events_since(team_host._observed_seq)   # 拉取但不广播
```

于是：

1. teammate 在自己的 `TeamHost` 实例里 `_emit()` 写库（正常）；
2. lead 调用任意 team 工具时拉到这些行；
3. **游标被推高，但事件没有进 SSE buffer**；
4. 下一轮 `events_since` 从新游标开始 → **这些事件永远不再出现**。

「拉取即丢弃」比「不拉取」更糟：不拉取至少还能在下一次全量刷新时补上。

### 2.3 修复

```python
for row in rows:
    self._observed_seq = max(self._observed_seq, int(row.get("event_seq", 0)))
    self._publish_event(row)      # ← 加上这一行
```

### 2.4 测试

新增 `test_events_since_publishes_teammate_events`：

```
teammate scope 写一条 task_updated
→ lead.events_since(0)
→ 断言 sink 收到 1 条且 type == task_updated
```

RED（修复前）：sink 收到 0 条。
GREEN（修复后）：1 条。

### 2.5 另一个缺陷：通知让模型「去读全文」，但新 generation 读不到

跨回合通知打通后，cross-turn e2e 的 history 里出现了：

```
[任务通知] 以下子代理已经结束，结果可直接使用；需要全文请 read_agent_result。
- calc_6x7 已completed：- 6*7 = 42 ...
```

模型照着做，结果：

```
read_agent_result → [工具执行错误] 未知子代理: calc_6x7
list_agents       → 当前没有子代理
```

**根因**：通知持久化了，`SubagentRegistry` 没有。它是每个 generation 新建的内存结构，
新回合里旧节点根本不存在，`read_result` 只查内存，查不到就报「未知子代理」。
结果是通知承诺了一条走不通的路。

**修复**：`read_result` 在内存找不到时回退到 DB 的最近一次 run
（`get_latest_run_by_name(user_id, session_id, name)`），返回 `source: "db"`，
并附一句「该子代理属于上一轮，结果来自持久化记录」。

**连带修掉一个 KeyError**：工具层拼 header 用的是 `out['name']`，
而 DB 回退的返回体一开始没有 `name` 字段，导致第二轮直接 `KeyError: 'name'`。
现在回退返回体补齐 `name` / `error`。

**测试**：
- `test_read_result_falls_back_to_db_in_new_generation`
- `test_read_result_unknown_name_still_errors`（负对照：不存在的名字仍报错）
- `test_read_agent_result_tool_works_across_generation`（工具层拼 header 不崩）
- 反向确认：删掉 `name` 字段 → 工具层用例变红

## 5. 结论与遗留

### 5.1 这轮压测的价值

- S3 证明超时语义正确（不杀子代理、不重复 spawn）；
- S6 暴露了一个**单测原理上测不到**的缺陷：事件写进了库、游标也推进了，
  只是没广播——只有跑真实链路并用「SSE vs DB」对比才能发现；
- 顺带把 e2e 断言从「工具出现过」升级为「任务终态正确」，
  否则 S6 在修复前也会 PASS（事实上它确实 PASS 了）。

### 5.2 遗留

| 项 | 说明 |
| --- | --- |
| 并发槽位压测 | ✅ S9 已跑：6 个同轮派发，2 个被拒后模型自行 close 补派 |
| 长时间运行 | ✅ S10 已跑 12.7 分钟单任务，无异常；更长时间（>1 小时）仍未验证 |
| 跨回合通知 | ✅ 已实现：`subagent_notifications` 表 + 每轮补载（见 P2 记录 §5） |
| `team_end` 的到达时机 | 生成收尾即写，前端是否需要在流关前展示，待 UI 确认 |

> 所有命令都在本机实测过（Windows + Docker Desktop 27.4.0）。

## 0. 一页速查

```bash
# ---- 1. 起 2 个实例 ----
cd backend
export POSTGRES_PASSWORD=eval123 HLZ_HTTP_PORT=8080
docker compose -f deploy/docker-compose.yml -p hlzscale up -d --scale app=2

# ---- 2. 看状态 ----
docker compose -f deploy/docker-compose.yml -p hlzscale ps
docker logs hlzscale-app-1 2>&1 | grep -E "startup instance|cluster enabled"

# ---- 3. 扩到 3 个（必须重启 nginx）----

# ---- 4. 验证粘性 ----
for i in $(seq 10); do
  curl -s -D- -o /dev/null -H "Cookie: hlz_sticky=FIXED" \
    http://127.0.0.1:8080/api/health | grep -i "^x-hlz-instance"
done | sort | uniq -c      # 必须只有 1 行

# ---- 5. 清理 ----
docker compose -f deploy/docker-compose.yml -p hlzscale down -v
```

## 1. 涉及的全部镜像

| 镜像 | 用途 | 谁提供 | 说明 |
| --- | --- | --- | --- |
| `hlz-app:test`（compose 里叫 `hlzscale-app`） | **Hlaudz 后端**（FastAPI + uvicorn） | 本仓库 `backend/deploy/Dockerfile` 构建 | 多副本，无固定端口，靠 nginx 暴露 |
| `postgres:16-bookworm` | 业务数据库 | Docker Hub | 所有副本共用，**必须** |
| `redis:8-alpine` | 多实例协调（锁 / 心跳 / 停止 / 插话 / 失效广播） | Docker Hub | 不配它 = 退化成单实例 |
| `nginx:alpine` | 入口 + 粘性负载均衡 | Docker Hub | 开源版没有 `sticky` 指令，用 `hash $cookie_...` 实现 |
| `hlz-sandbox:latest`（可选） | **用户代码沙箱**（跑 bash / python） | `backend/sandbox/Dockerfile` 构建 | 与后端镜像**完全无关**；多实例下默认关闭（`HLZ_SANDBOX_MODE=off`） |

### 1.1 后端镜像怎么构建

```bash
cd backend
docker build -f deploy/Dockerfile -t hlz-app:test ..
```

镜像大小约 **584 MB**（主要是 Python 依赖）。

> ⚠️ **必须**有仓库根的 `.dockerignore`。没有它时构建上下文 346 MB
> （`backend/data/` 占 328 MB），而且 `data/` 里有异常权限位的文件，
> docker 打包直接报 `archive/tar: unknown file mode ?rwxr-xr-x`。
>
> `.gitignore` 对 `docker build` **无效** —— Docker 不看它。这是两套独立机制。

镜像内的关键事实：

- 基础镜像 `python:3.12-slim`，清华源
- `tini` 作为 PID 1（否则容器收到 SIGTERM 时 uvicorn 不跑 lifespan shutdown，实例不从心跳表注销）
- `CMD python -m uvicorn app.main:app --host 0.0.0.0 --port 8000`
- **不用 `--workers`**：多副本靠 compose/K8s 横向扩，单容器内多 worker 会让「一个实例」这个概念失效（owner/心跳是进程级的）

### 1.2 沙箱镜像（可选，多实例下默认关）

```bash
cd backend
docker build -f sandbox/Dockerfile -t hlz-sandbox:latest .
```

多实例下打开它的前提：**每个实例独占一台机器**。因为容器只存在于本机 Docker
daemon 里，多个实例共享一台机器时它们的沙箱容器会互相干扰（虽然已按 owner 隔离，
但资源竞争仍在）。

打开方式：

```bash
HLZ_SANDBOX_MODE=auto docker compose ... up -d     # 或 on
```

### 2.4 `HLZ_INSTANCE_ID`：什么时候必须设

**默认留空是正确的**（`--scale` 下每个副本的 hostname 天然不同）。

必须显式设的场景：**编排器让所有副本的 hostname 相同**。容器里 PID 恒为 1，
这时所有副本的 owner 都会是 `web-0:1` —— 撞车后表现为**随机数据分叉**（不报错）。

| 环境 | 怎么写 |
| --- | --- |
| `docker compose --scale` | 留空 |
| K8s | `valueFrom: {fieldRef: {fieldPath: metadata.name}}` |
| 其他编排器 | 任何**每个副本唯一**的字符串 |

> ❌ **绝对不要写** `HLZ_INSTANCE_ID: ${HOSTNAME}` —— compose 的 `${...}`
> 从**宿主 shell** 插值，所有副本拿到同一个值，等于「保证撞车」。
>
> 真撞了会被检测到并打 `WARNING: 实例标识冲突...`（按 owner 节流 5 分钟），
> 但**不会拒绝启动** —— 拒绝启动会把配置错误升级成全站不可用。

## 4. 扩容

### 4.1 从 2 扩到 3

```bash
docker compose -f deploy/docker-compose.yml -p hlzscale up -d --scale app=3
docker restart hlzscale-nginx-1        # ⚠️ 必须
```

### 4.2 为什么必须重启 nginx

nginx **只在启动时**解析一次 upstream 的 DNS。`--scale app=3` 后 compose 内网
对服务名 `app` 返回 3 个 A 记录，但**已在运行的 nginx 不会重新解析**。

实测（不重启）：60 个不同 cookie 全部打到老实例（`60/60`）。
重启后：`29/31`（2 副本）或 `22/20/18`（3 副本）。

```bash
# 验证
for i in $(seq 60); do
  curl -s -D- -o /dev/null -H "Cookie: hlz_sticky=c$i" \
    http://127.0.0.1:8080/api/health | grep -io "x-hlz-instance.*"
done | sort | uniq -c
```

期望看到 3 行，各约 20 次。

### 4.3 扩容失败排查

| 症状 | 原因 | 修法 |
| --- | --- | --- |
| 新副本 `Restarting` | 看 `docker logs`：多半是 PG 建表竞态 | 已在代码里用 DDL advisory lock 修掉（§6.1）；若仍出现看日志 |
| 新副本起来了但收不到流量 | nginx 没重启 | `docker restart hlzscale-nginx-1` |
| `sorry, too many clients already` | PG 连接数不够 | compose 已设 `max_connections=200`；实例数 × 8 + 余量 < 200 |
| 所有副本 owner 相同 | `HLZ_INSTANCE_ID` 被设成同一个值 | 留空，或改成每副本唯一（§2.4） |

## 5. 怎么区分不同实例（重点）

有**五个互相独立**的视角，排查时按需选用。

### 5.1 `/api/health` 的 `instance` 字段

```bash
curl -s http://127.0.0.1:8080/api/health | python -m json.tool
```

```json
"instance": "7cbfd1678082:7"
```

格式 `<容器 hostname>:<实例标识>`。**这是最直接的方式** —— 不用登服务器。

完整字段表：

| 字段 | 含义 | 排查用途 |
| --- | --- | --- |
| `instance` | 本次请求落到谁 | 「我改了配置为什么没生效」→ 先看两次请求是否落到不同实例 |
| `cluster.enabled` | 有没有配 Redis | `false` = 单实例模式，所有协调能力走进程内 |
| `cluster.live_instances` | 心跳表里还活着几个 | 期望 = 副本数；少了说明有实例挂了或心跳没刷新 |
| `cluster.leader` | 本实例是否 leader | 见 §5.3 |
| `cluster.leader_election` | 选举状态 | `on` / `off`（单实例）/ `starting`（配了 Redis 但选举没启动） |
| `cluster.instance_id` | `HLZ_INSTANCE_ID` 的值 | 没注入时是 PID |

### 5.2 `X-HLZ-Instance` 响应头

每个响应都带（`HLZ_INSTANCE_HEADER=0` 可关）：

```bash
curl -sI http://127.0.0.1:8080/api/health | grep -i x-hlz-instance
# x-hlz-instance: 7cbfd1678082:7
```

**为什么不翻 nginx 日志**：Git Bash 会把容器内路径 `/var/log/...` 转成
Windows 路径（`D:/Git/var/log/...`），`docker exec cat` 直接失败；
而且要比对时间戳。响应头更直接，DevTools 里也能看到。

### 5.3 日志里的 `[<标识>]` 前缀 + 按实例分文件

**这一层是多实例排查的主力** —— 三个副本共享同一个 `appdata` 卷，
日志必须能归属。

```bash
docker exec hlzscale-app-1 sh -c 'ls -1 /app/backend/data/logs/ | grep "^app-"'
```

实测输出（**两个独立文件**）：

```
app-7cbfd1678082-7.log
app-b0d40973c2bc-7.log
```

文件名格式 `app-<hostname>-<实例标识>.log`。
**必须带 hostname**：没注入 `HLZ_INSTANCE_ID` 时标识就是 PID，
而两个容器的 Python PID **可能相同**（实测都是 7）—— 只按 PID 命名会撞文件。

每行人读日志都带实例前缀：

```bash
docker logs hlzscale-app-1 2>&1 | tail -3
# [7] INFO  11:46:24 app.main: cluster enabled=True live=2 ...
#  ↑ 这里的 [7] 是 uvicorn 的 worker 序号，不是实例标识
```

> 注意：`docker logs` 里的 `[7]` 前缀是 **uvicorn 打的进程序号**，不是我们的
> 实例标识。我们的实例标识在 **`app.log` 文件内**的行首
> （`[7cbfd1678082:7] INFO ...`）。两者不要混。

结构化事件（`team-<日期>.jsonl`）里是 `instance` 字段，可按实例过滤：

```bash
docker exec hlzscale-app-1 sh -c \
  'grep "\"instance\": \"7cbfd1678082:7\"" /app/backend/data/logs/team-*.jsonl | tail -5'
```

### 5.4 Redis 里的心跳表

```bash
docker exec hlzscale-redis-1 redis-cli zrange hlz:instances 0 -1 withscores
```

```
1) "7cbfd1678082:7"
2) "1763...   ← 最后心跳时间（毫秒时间戳）
3) "b0d40973c2bc:7"
4) "1763..."
```

**注意只有一把键 `hlz:instances`**（不是每台机器一个）。
心跳超过 90s 未刷新就被判定死亡，下次有人查时自动剔除。

### 5.5 容器列表

```bash
docker compose -f deploy/docker-compose.yml -p hlzscale ps
docker ps --filter "name=hlzscale-app-" --format '{{.Names}}\t{{.Status}}'
```

这是「有几个进程」的**唯一权威**来源 —— §5.1/§5.4 都可能因心跳过期而滞后。

### 5.6 五个视角的关系

```
docker ps                    真实有几个容器
      ↓ (每个容器一个进程)
hlz:instances (Redis)        活着的 owner 集合（90s 心跳窗口）
      ↓ (owner = hostname:标识)
/api/health .instance        这一条请求落到谁
      ↓
app-<host>-<tag>.log         它的日志
X-HLZ-Instance  响应头       同上，但不用登服务器
```

排查顺序建议：**先 `docker ps` 看容器数 → 再 `curl health` 看集群视图 →
最后翻对应实例的日志文件**。

## 6. 用户粘性测试方法

### 6.1 为什么必须粘性

一次生成是**持续几十秒到几分钟的 SSE 长连接**。长连接天然落同一上游，
问题在**下一个请求**：

| 场景 | 不粘性会怎样 | 现状 |
| --- | --- | --- |
| 第二个标签页发新消息 | 另一实例把 A 正在跑的 generation 判死 | 已修：owner 判活，返回 409 |
| 中途插话 | 另一实例不知道有活跃回合，另起一轮 | 已修：跨实例总线 |
| 改 MCP / LLM 配置 | 只有本实例失效 | 已修：版本号广播，2s 生效 |
| runtime 缓存（MCP 连接） | 各实例各一份，无法共享 | 粘性避开 |

**技术上不粘也能跑**，但粘性避免上面每一类「短暂不一致」。

### 6.2 三层验证（从轻到重）

#### A. 一行命令：粘性是否生效

```bash
for i in $(seq 10); do
  curl -s -D- -o /dev/null -H "Cookie: hlz_sticky=FIXED" \
    http://127.0.0.1:8080/api/health | grep -io "^x-hlz-instance.*"
done | sort | uniq -c
```

| 结果 | 含义 |
| --- | --- |
| 只有 1 行，计数 10 | ✅ 粘性生效 |
| 2-3 行，各 3-5 次 | ❌ 粘性失效（在轮询） |

**真实踩过**：`hash $cookie_hlz_sticky consistent` + `server app:8000`
在 `--scale` 下会精确轮询。原因是 ketama 环按 server **名字**建点，
DNS 解析出的 3 个 A 记录**共用同一个名字** → 三点重合 → 退化成 round-robin。
去掉 `consistent` 就好了（详见报告 §9.3）。

#### B. 分散性：不同 cookie 要落到不同实例

```bash
for i in $(seq 60); do
  curl -s -D- -o /dev/null -H "Cookie: hlz_sticky=c$i" \
    http://127.0.0.1:8080/api/health | grep -io "x-hlz-instance.*"
done | sort | uniq -c
```

期望：2 副本约 `29/31`，3 副本约 `22/20/18`。
只有 1 行 = 完全没分流（nginx 没重启 / cookie 没下发）。

#### C. 浏览器里验证（最接近真实用户）

1. 打开 `http://127.0.0.1:8080/api/health`
2. DevTools → Application → Cookies → 应看到 `hlz_sticky=<32 位 hex>`
3. 刷新多次，`instance` 字段**始终相同**
4. 复制该 cookie 值，用 curl 带同一个值打 10 次 → 全部同一实例

```bash
# 用浏览器里看到的真实 cookie 值
COOKIE="hlz_sticky=<从 DevTools 复制>"
for i in $(seq 5); do
  curl -s -D- -o /dev/null -H "Cookie: $COOKIE" \
    http://127.0.0.1:8080/api/health | grep -io "x-hlz-instance.*"
done | sort | uniq -c
```

### 6.3 完整的自动化验证

```bash
cd backend
python tests/manual/compose_scale_e2e.py
```

真起 `docker compose --scale app=2/3`（nginx + PG + Redis + 副本），
10 项检查：副本数、分散性、owner 唯一、粘性、cookie 下发、Redis 登记、
登记成员=访问集合、无撞车告警、启动清扫没全员执行。

### 6.4 粘性 cookie 的机制

nginx 开源版**没有 `sticky` 指令**（那是 Plus / OpenResty 的）。
开源版做法是用 `hash` 把 cookie 值映射到上游。

**但 `hash` 只能读，不能设** —— cookie 必须由应用下发：

```
Set-Cookie: hlz_sticky=<32 位 hex>; HttpOnly; Max-Age=2592000; Path=/; SameSite=lax
```

实现在 `app/main.py` 的 `_ensure_sticky_cookie`，挂在 `/api/health`
（前端启动第一个必然访问的端点，且不需要登录）。已带则不重复下发。

> **没有这个 cookie 会怎样**：所有请求的 cookie 都是空串，空串哈希是固定值，
> 全部落到同一上游。不报错，但负载均衡完全失效 —— 典型的静默失效。

`secure=False` 是刻意的：HTTP 部署时设 `True` 浏览器会直接丢弃，
粘性静默失效，比没有更糟。

### 6.5 为什么用 cookie 而不是 `ip_hash`

| 方案 | 失效场景 |
| --- | --- |
| `ip_hash` | 移动网络 / 代理池（出口 IP 变）、NAT 后一群人共享一个 IP、前置 CDN 时 `$remote_addr` 是 CDN 地址 |
| `hash $cookie_...` | 只在浏览器不带 cookie 时退化（首屏），之后一直稳定 |

## 8. 常见故障对照表

| 症状 | 根因 | 修法 |
| --- | --- | --- |
| `POSTGRES_PASSWORD is missing` | 没设环境变量 | `export POSTGRES_PASSWORD=...` |
| 构建报 `archive/tar: unknown file mode` | 缺 `.dockerignore` | 见 §1.1 |
| 构建报 `"/backend": not found` | compose `context` 写错 | 应是 `../..`（相对 `deploy/`） |
| nginx 重启循环：`"upstream" directive is not allowed here` | `nginx.conf` 缺 `events{}`/`http{}` 外壳 | 见 `deploy/nginx.conf` 顶部说明 |
| 新副本启动即退出：`duplicate key ... pg_type_typname_nsp_index` | 多实例同时建表（PG `IF NOT EXISTS` 非原子） | 已用 DDL advisory lock 修（§9.1） |
| `live_instances` 一直是 1（但确实起了多个） | 心跳表按机器分键 | 已改成单一全局键（§9.2） |
| 两个副本日志写进同一个文件 | 文件名只用了 PID，两容器 PID 相同 | 已加上 hostname（§9.3） |
| `leader: true` 两边都是 | elector 从未启动，`is_leader` 短路返回 True | 已改成如实反映（§9.4） |
| 同一 cookie 精确轮询（3 个一次） | `hash ... consistent` + 同名 peer | 去掉 `consistent`（§9.5） |
| 扩容后新副本零流量 | nginx 只在启动时解析 DNS | `docker restart hlzscale-nginx-1` |
| 全部 cookie 落同一实例 | 应用没下发 `hlz_sticky` | 看 `/api/health` 响应有无 `set-cookie` |
| `sorry, too many clients already` | PG 连接数 < 实例数 × 池大小 | 调 `max_connections` |

## 9. 本次真跑修掉的六个 bug（供排查时对照）

### 9.1 PG 建表竞态（两个副本同时启动必现）

**症状**：一个副本 `Application startup failed. Exiting.`

```
duplicate key value violates unique constraint "pg_type_typname_nsp_index"
DETAIL: Key (typname, typnamespace)=(users, 2200) already exists.
```

**根因**：PG 的 `CREATE TABLE IF NOT EXISTS` **不是原子的** —— 先查后建，
两步之间没有锁。SQLite 不会这样（DDL 拿库级写锁）。

**修法**：`executescript` 用 `pg_advisory_xact_lock` 包住整个脚本
（scope `hlz:ddl:init`，30s 超时后放弃但仍继续 —— DDL 是幂等的）。

### 9.2 跨机看不到彼此

**症状**：`/api/health` 报 `live_instances: 1`（实际 2 个）；跨实例判活失效，
会**随机数据分叉**。

**根因**：心跳表按 `hlz:instances:<hostname>` 分键。`--scale` 下每个副本
hostname 不同 → 各写各的键 → 看不到彼此。

**修法**：改为**单一全局键** `hlz:instances`，机器维度靠 owner 的
`<hostname>:` 前缀表达（`live_owners(machine=...)` 给本机视图）。

### 9.3 两个容器的日志撞文件

**症状**：共享卷上只有一个 `app-7.log`，两个进程交错写。

**根因**：文件名只用实例标识；没注入 `HLZ_INSTANCE_ID` 时标识是 PID，
**两个容器的 Python PID 可能相同**（实测都是 7）。

**修法**：文件名加 hostname → `app-<hostname>-<tag>.log`。

### 9.4 `leader` 字段撒谎

**症状**：两个副本的 health 都报 `leader: true`。

**根因**：读的是 `get_elector().is_leader`，而 elector **从未 `start()`** ——
它的 `_redis` 还是 `None`，`is_leader` 短路返回 `True`。

**修法**：加 `is_running` 标志，`is_leader` 三态处理
（单实例 True / 配了 Redis 但未启动 False / 在跑看循环值），
health 增加 `leader_election` 字段说明状态。

### 9.5 粘性静默失效

**症状**：同一 cookie 精确轮询 3 个副本，报错为零。

**根因**：`hash ... consistent` 的 ketama 环按 server **名字**建点，
`server app:8000` 解析出的 3 个 A 记录共用同一个名字 → 三点重合。

**修法**：去掉 `consistent`（或用三个显式不同名的 peer）。

### 9.6 nginx 配置缺外壳

**症状**：nginx 进重启循环，`"upstream" directive is not allowed here`。

**根因**：`nginx.conf` 写成了片段，被挂到主配置位置。

**修法**：补 `events{}` / `http{}` 外壳。

## 11. 已知限制

| 限制 | 影响 | 何时处理 |
| --- | --- | --- |
| leader election 未启用 | `leader_election: "starting"`；不影响功能（启动清扫用独立租约） | 有需要时在 lifespan 里 `await get_elector().start()` |
| `HLZ_INSTANCE_ID` 重复只告警不拒绝启动 | 两个副本仍可能撞 owner | 取舍见 §2.4 |
| 沙箱容器只能同机共享 | 多机时各管各的 | 需要时再设计 |
| 停止 / 插话有 1s / 200ms 轮询延迟 | 用户感知不到，但不是即时 | 高频场景换 pubsub |
| 未做实例间任务迁移 | 实例挂了它正在跑的生成会断 | 引入 job queue 时一起做 |
| Windows 上无法验证优雅注销 | `taskkill`/`send_signal` 都不跑 lifespan shutdown | 靠心跳过期兜底 |
| 未压测 > 100 并发 | 按单机单进程验证过 | 上线前压测 |

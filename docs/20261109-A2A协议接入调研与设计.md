# A2A 协议接入调研与设计（Hlaudz / inner_chatgpt）

> 日期：2026-11-09
> 状态：调研 + 设计；**本轮不改任何代码，也不改 GenericAgent（GA）**。
> 目标：回答四个问题：A2A 现在到底怎么样、Hlaudz 有没有必要做、GA 能不能调用、按用户隔离该怎么设计。

> **实施状态（2026-11-10）：Phase 1 非流式 MVP + `SendStreamingMessage` / `SubscribeToTask` 已落地，见 `docs/20261110-A2A-MVP实施记录.md` 与 `docs/20261110-A2A使用文档.md`。**

## 0. 结论先行

1. **如果只是 Hlaudz ↔ 本地 GA：不需要 A2A。** 现在的 ACP（Zed 的 Agent Client Protocol）已经覆盖“客户端驱动本地 agent”这个场景，ACP 更轻、更贴近本机子进程模型。
2. **如果目标是“让别的智能体调用 Hlaudz”：值得做 A2A，而且现在做正合适。** A2A 在 2026-03 发布稳定版 v1.0，已有 150+ 组织、5 种语言 SDK、Google/Microsoft/AWS 云平台集成；agent-to-agent 这一层的标准之争基本结束，A2A 是事实标准。
3. **不需要为了 A2A 改 GA 的核心。** Hlaudz 做 A2A server，GA 继续做 ACP server；两者是不同层，不冲突。GA 要调用 Hlaudz 的 A2A 接口，用 `code_run` 里的 Python HTTP 客户端即可，GA 核心不用改。
4. **你的“每个用户一个 URL/token”直觉是对的。** A2A v1.0 原生支持多租户（`tenant` + URL 路由）；建议每个用户一个不可枚举的 `agent_id`、独立 Bearer token、独立配额，token 与路径/租户三方绑定，坚决不做“一个全局可调用入口”。
5. **工作量属于“中等适配”，不是从零造协议。** 复用现有 sessions/messages/SSE/stop/runtime，MVP（SendMessage + GetTask + CancelTask + AgentCard + 每用户 token）大约 6–10 人日；做到生产可用（流式、并发、审计、测试）约 2–3 周；完整 v1.0（Subscribe、push、签名卡、v0.3 兼容）约 3–4 周。

## 1. 2026 年的异构智能体互操作版图

先厘清一个常见混淆：**“ACP”现在至少有两个完全不同的东西。**

| 名字 | 是谁的 | 解决哪一层 | 现状（2026-11） | 采用度 | 对你的意义 |
| --- | --- | --- | --- | --- | --- |
| **MCP**（Model Context Protocol） | Anthropic 发起，Linux Foundation / AAIF 治理 | agent ↔ 工具/数据 | 事实标准，生态最大 | 极高，生产基础设施 | Hlaudz/GA 已经在用；不是 agent-to-agent 协议 |
| **A2A**（Agent2Agent） | Google 发起，2025-06 捐给 Linux Foundation | agent ↔ agent（跨框架、跨组织、长任务） | **v1.0.0 于 2026-03-12 发布**，稳定、生产就绪；后续 1.0.x | 150+ 组织，Google/Microsoft/AWS 集成，5 语言 SDK | **要做“被别的 agent 调用”，选它** |
| **Zed ACP**（Agent Client Protocol） | Zed Industries + JetBrains 社区 | editor/IDE ↔ 本地 coding agent | v0.13.x，仍未 1.0；Zed 1.0、JetBrains 已内置，60+ agent | 编辑器领域真实发货 | **你和 GA 现在用的就是它**；不解决跨网络 agent 调用 |
| **IBM ACP**（Agent Communication Protocol） | IBM Research / BeeAI | agent ↔ agent（REST 风格） | **2025-08 并入 A2A，Repo 归档、停止开发** | 已退场 | 不要为新项目选它；历史资料要标注“已合并” |
| **AGNTCY** | Cisco 发起，Linux Foundation | agent 发现、身份、可观测性、消息基础设施 | 活跃，但采用偏早期；重心是 A2A 底座 | 65+ 支持组织，实际生产证据少 | 未来可作为目录/身份层，不是现在的首选 |
| **ANP**（Agent Network Protocol） | 社区 / W3C Community Group | 去中心化 agent 网络（DID、JSON-LD） | 1.1 规范 + 参考实现，生产案例少 | 实验性 | 观察即可，不建议现在投入 |
| **AG-UI** | CopilotKit 等 | agent ↔ 用户界面 | 预稳定；MS Agent Framework、Google ADK、AWS Strands 等集成 | 前端层采用上升 | 与“agent 调 agent”不是同一层；Hlaudz 前端可另评估 |
| **框架内置 handoff** | OpenAI Agents SDK、Microsoft Agent Framework、LangGraph、CrewAI 等 | 应用内编排 | 成熟，但 handoff 是框架私有 | 高 | 不是跨厂商 wire protocol；它们大多同时支持 MCP/A2A |

一句话版：

- **MCP 是工具层，A2A 是 agent 协作层，Zed ACP 是编辑器接入层，AG-UI 是用户界面层。**
- 2025 年那场“agent-to-agent 协议大战”已经收敛：IBM ACP 并入 A2A，AGNTCY 转向底座，ANP 仍是研究/实验路线；**A2A 是唯一同时具备稳定规范、跨云平台集成和多家框架支持的选择**。
- A2A 的“成熟”要分两层看：**规范和生态集成成熟**；**深度生产案例仍在早期**（厂商公布“production use”，但多数不点名客户）。所以它是“值得押注的标准”，不是“已经像 HTTP 一样无处不在”。

参考：[1] A2A 规范、[2] v1.0 发布说明、[3] Linux Foundation 一周年新闻、[4] IBM ACP 合并公告、[5] Zed ACP、[6] 协议版图综述。

## 2. A2A v1.0 速览（只列实现会用到的部分）

### 2.1 传输与版本

- 抽象协议定义了三种绑定：**JSON-RPC 2.0**、**gRPC**、**HTTP+JSON/REST**。Hlaudz 做 JSON-RPC 最省事，也最容易和现有 FastAPI 路由共存。
- 客户端每个请求应带 `A2A-Version: 1.0`；空值按 v0.3 兼容处理。服务端不支持时返回 `VersionNotSupportedError`。
- 非流式响应用 JSON；流式响应用 **SSE**（`text/event-stream`）。
- v1.0 的重要变化：枚举从 kebab-case 改为 `SCREAMING_SNAKE_CASE`；去掉 `kind` 判别字段，改用 JSON 成员名做 oneof 判别；`preferredTransport`/`additionalInterfaces` 合并成 `supportedInterfaces[]`；`tenant` 进入所有请求消息。

### 2.2 核心对象

- **AgentCard**：能力发现。必填 `name`、`description`、`supportedInterfaces`、`version`、`capabilities`、`defaultInputModes`、`defaultOutputModes`、`skills`。
- **AgentInterface**：`{url, protocolBinding, protocolVersion, tenant?}`；`tenant` 是该接口的默认租户。
- **Task**：`{id, contextId, status, artifacts?, history?, metadata?}`；一个任务有生命周期。
- **Message**：`{messageId, role, parts[], contextId?, taskId?}`；`role` 是 `ROLE_USER` / `ROLE_AGENT`。
- **Part**：文本是 `{text, mediaType?}`；另有 file/data 变体。
- **Artifact**：`{artifactId, name?, parts[], description?}`；最终答案、文件、结构化结果都放这里。
- **StreamResponse**：oneof `task` / `message` / `statusUpdate` / `artifactUpdate`，每次 SSE 事件只能有一个。
- **TaskStatusUpdateEvent**：`{taskId, contextId, status}`；v1.0 已去掉 `final` 字段，终态直接看 `status.state`。
- **TaskArtifactUpdateEvent**：`{taskId, contextId, artifact, append?, lastChunk?, index?}`。

### 2.3 JSON-RPC 方法（v1.0 大小写敏感）

| 方法 | 用途 | Hlaudz MVP |
| --- | --- | --- |
| `SendMessage` | 发送消息，创建/继续任务；默认阻塞到终态或需要输入 | ✅ |
| `SendStreamingMessage` | 同上，但用 SSE 持续推送 | ✅ |
| `GetTask` | 按 `id` 查任务状态 | ✅ |
| `ListTasks` | 按 context/status 分页列任务 | 第二阶段 |
| `CancelTask` | 取消进行中的任务 | ✅ |
| `SubscribeToTask` | 订阅已有任务的后续事件 | 第二阶段 |
| `CreateTaskPushNotificationConfig` 等 4 个 | Webhook 推送配置 | 第三阶段 |
| `GetExtendedAgentCard` | 认证后取扩展 AgentCard | 可选 |

> v0.3 的 `message/send`、`message/stream`、`tasks/get`、`tasks/cancel`、`tasks/resubscribe` 是小写斜杠风格。**新实现只做 v1.0**；如果客户端的 A2A SDK 仍是 v0.3，再在路由层加别名，不要一开始就维护两套语义。

### 2.4 任务状态

```
TASK_STATE_SUBMITTED
TASK_STATE_WORKING
TASK_STATE_INPUT_REQUIRED
TASK_STATE_AUTH_REQUIRED
TASK_STATE_COMPLETED
TASK_STATE_FAILED
TASK_STATE_CANCELED
TASK_STATE_REJECTED
```

Hlaudz 当前只需要前三个 + `COMPLETED` / `FAILED` / `CANCELED`；`INPUT_REQUIRED` 可以等到把 `AskUserQuestion` 一类交互映射进来再做。

### 2.5 AgentCard 示例（每用户一份）

```json
{
  "name": "Hlaudz Agent",
  "description": "A self-hosted agent that can chat, use tools, and delegate to GenericAgent via ACP.",
  "supportedInterfaces": [
    {
      "url": "https://hlaudz.example.com/a2a/ha_7f3c9d2e",
      "protocolBinding": "JSONRPC",
      "protocolVersion": "1.0",
      "tenant": "ha_7f3c9d2e"
    }
  ],
  "version": "1.0.0",
  "capabilities": {
    "streaming": true,
    "pushNotifications": false,
    "extendedAgentCard": false
  },
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["text/plain"],
  "skills": [
    {
      "id": "general-agent",
      "name": "General Agent",
      "description": "Chat, coding, file and tool tasks in the user's workspace.",
      "tags": ["chat", "coding", "tools"]
    }
  ],
  "securitySchemes": {
    "bearer": {
      "httpAuthSecurityScheme": {
        "scheme": "bearer",
        "bearerFormat": "opaque"
      }
    }
  },
  "securityRequirements": [
    {"schemes": {"bearer": {"list": []}}}
  ]
}
```

注意：

- `url` 和 `tenant` 都用同一个不可枚举的 `agent_id`，但**URL 不是认证**；没有 Bearer token 一律 401。
- AgentCard 本身可以公开（不含用户隐私）；如果你要求连能力都不公开，就改为“卡片也要 token”，但这就偏离 A2A 的公开发现惯例，需在文档里明确。
- 不要在卡片里放 username/email/模型 key/内部路径。

### 2.6 多租户的三种做法

A2A v1.0 明确支持三种路由方式：

1. **URL 子路径**：每个 agent 一个前缀，卡片各自广告自己的 `url`。← **推荐你用这个**。
2. **认证头路由**：网关看 token 转发到后端，请求体不变。
3. **请求体 `tenant`**：所有消息带可选 `tenant`，网关/服务端据此路由。

三者可以组合。你的诉求是“每个用户自己的 URL”，所以用 **URL 子路径 + `tenant` + token 三方绑定**：

```
/a2a/{agent_id}/.well-known/agent-card.json
/a2a/{agent_id}/            ← JSON-RPC endpoint
```

`agent_id` 用随机值（如 `ha_` + 16 hex），不要用 `user_id`、邮箱、用户名。这样即使 URL 泄露，也不能靠猜遍历用户；真正的安全边界仍是 token。

## 3. Hlaudz 现在缺什么、要不要补

### 3.1 现状（已有可复用资产）

- `backend/app/auth.py:85` 的 `get_current_user`：JWT access token + DB `status`/`token_ver` 校验。
- `backend/app/routers/sessions.py:30`：创建会话；`backend/app/db.py:37`/`:49`：sessions/messages 表。
- `backend/app/routers/chat.py:332`：`_event_stream`，已经产出 `message_start` / `text_delta` / `thinking_delta` / `tool_start` / `tool_result` / `subagent_*` / `done` / `error` 等 UI SSE 事件。
- `backend/app/routers/chat.py:654`：`send_message`，负责 generation lease、消息落库、StreamingResponse。
- `backend/app/routers/chat.py:714`：`stop_generation`，已经做了“协作式 stop → ACP 优雅停 → 硬取消 → 子 agent/进程清理 → 终态收敛”的完整顺序。
- `backend/app/quota.py:36` 起：全局/用户/团队/子 agent/ACP 的多级配额。
- `docs/20261109-ACP-client驱动GenericAgent实施记录.md`：Hlaudz 作为 ACP client 驱动 GA 的完整实现与 E2E 证据。

**缺口不是“不会跑 agent”，而是“没有面向外部 agent 的任务契约”**：

- 现有 `POST /api/sessions/{id}/messages` 需要用户 JWT，返回的是 UI 形状的 SSE（`event: text_delta`），不是 A2A 的 `StreamResponse`。
- 没有 AgentCard、没有 `taskId/contextId` 的持久映射、没有 `GetTask/ListTasks`、没有每用户可撤销的机器 token。
- 没有把“外部调用者”与“网页登录用户”区分开的权限/配额/审计。

### 3.2 必要性判断

| 你的真实目标 | 建议 |
| --- | --- |
| 只是让 Hlaudz 调本地 GA 干活 | **不需要 A2A**；现有 ACP 已经够，而且更合适 |
| 让 GA 反过来调 Hlaudz | 可以加 A2A，但也可以先用 Hlaudz 的普通 HTTP+token；A2A 的价值在标准化 |
| 让别的厂商/框架的 agent 发现并调用 Hlaudz | **值得做 A2A**；这是它的主场 |
| 把 Hlaudz 做成“多用户 agent 服务” | **值得做 A2A + 每用户 token/URL/配额**；不做的话迟早要自造一套不兼容的 API |
| 只做内部两三个固定 agent 的互调 | 自定义 HTTP + 共享密钥更简单；A2A 的发现/任务生命周期是额外复杂度 |

结论：**A2A 不是“必须”，但对“被外部智能体调用”这个目标是“最省长期成本”的选择。** 建议等 GA 升级完成后再排期，先做 opt-in、默认关闭的适配层，不影响现有网页/ACP 路径。

## 4. 目标架构：每用户一个 A2A 身份

### 4.1 总体链路

```text
外部 Agent / A2A Client
        │
        │  POST /a2a/{agent_id}          Authorization: Bearer hlz_a2a_...
        │  A2A-Version: 1.0              Content-Type: application/json
        ▼
┌─────────────────────────────────────────────────────────────┐
│ FastAPI: backend/app/routers/a2a.py                         │
│  1. token 哈希查表 → user_id + agent_id                      │
│  2. 校验 path.agent_id == token.agent_id                    │
│  3. 校验 body.tenant == agent_id（若提供）                   │
│  4. JSON-RPC 分发                                           │
└───────────────────────┬─────────────────────────────────────┘
                        │
                        ▼
┌─────────────────────────────────────────────────────────────┐
│ backend/app/a2a/service.py                                  │
│  - task 生命周期 / 幂等 / 状态映射                          │
│  - 复用 sessions + messages + generation lease              │
│  - 调用 chat._event_stream(...) 消费现有 SSE                 │
└───────────────────────┬─────────────────────────────────────┘
                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
   SQLite DB       RuntimeHub        GA ACP client
   sessions        generation         (现有 backend/app/acp)
   messages        leases / stop
   a2a_tasks
```

**关键原则：A2A 是“适配层”，不是第二套 agent 内核。** 任务执行、工具、子 agent、ACP、停止逻辑全部复用现有代码；A2A 只负责协议翻译、任务持久化、认证和配额。

### 4.2 对外端点

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/a2a/{agent_id}/.well-known/agent-card.json` | 该用户的 AgentCard；可公开，返回通用能力 |
| `POST` | `/a2a/{agent_id}` | JSON-RPC endpoint：`SendMessage` / `SendStreamingMessage` / `GetTask` / `ListTasks` / `CancelTask` / `SubscribeToTask` |
| `GET` | `/.well-known/agent-card.json` | **不提供全局可调用卡片**；返回 404 或一段“请使用你的 per-user card URL”的说明 |

> 为什么不给全局卡片：A2A 的卡片必须广告一个可调用的 `url`。如果全局卡片广告一个“总入口”，就正好变成你明确不要的“一个总接口”；如果广告一个目录服务，那又是一个额外的全局 agent。**每用户卡片 + 直接配置 URL 更干净。** 代价是客户端不能只靠域名级 well-known 自动发现，需要用户把卡片 URL 交给对方；这和“每个用户独立 token”的模型一致。

### 4.3 每用户身份与 token

**Agent 身份**

- 每个用户一个 `a2a_agents` 行；`agent_id = "ha_" + secrets.token_hex(8)`。
- `agent_id` 是公开路由标识，不是秘密；不要用 username/email。
- 一个用户未来可以有多个 agent（例如“个人助手”“代码助手”），MVP 先一人一个。

**Token**

- 格式：`hlz_a2a_` + `base64url(32 random bytes)`；只在创建时显示一次。
- 存储：**只存 SHA-256 哈希**，不存明文；`prefix` 存前 12 字符用于 UI 识别。
- 校验：`Authorization: Bearer <token>` → SHA-256 → 查 `a2a_tokens.token_hash` → 检查 `revoked_at` / `expires_at` / 用户 `status`。
- 不做 bcrypt：32 字节随机 token 熵足够，SHA-256 可以索引，性能更好；关键是**不要记录明文**。
- 不复用网页登录 JWT：登录 JWT 短时效、和 `token_ver` 全局绑定，不适合外部长期集成；A2A token 需要独立撤销、独立 scope、独立 last-used。
- 可选升级：OAuth2 client credentials / mTLS；MVP 用 opaque Bearer 即可，AgentCard 已声明 `bearer`。

**数据表（建议）**

```sql
CREATE TABLE IF NOT EXISTS a2a_agents (
    id          TEXT PRIMARY KEY,
    user_id     TEXT NOT NULL UNIQUE,
    agent_id    TEXT NOT NULL UNIQUE,
    created_at  INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS a2a_tokens (
    id           TEXT PRIMARY KEY,
    user_id      TEXT NOT NULL,
    agent_id     TEXT NOT NULL,
    name         TEXT NOT NULL DEFAULT '',
    token_hash   TEXT NOT NULL UNIQUE,
    prefix       TEXT NOT NULL DEFAULT '',
    scopes       TEXT NOT NULL DEFAULT '["chat"]',
    created_at   INTEGER NOT NULL,
    last_used_at INTEGER,
    expires_at   INTEGER,
    revoked_at   INTEGER
);

CREATE TABLE IF NOT EXISTS a2a_tasks (
    task_id       TEXT PRIMARY KEY,
    context_id    TEXT NOT NULL,
    user_id       TEXT NOT NULL,
    agent_id      TEXT NOT NULL,
    session_id    TEXT NOT NULL,
    message_id    TEXT NOT NULL,
    generation_id TEXT NOT NULL,
    state         TEXT NOT NULL,
    artifacts     TEXT NOT NULL DEFAULT '[]',
    error         TEXT NOT NULL DEFAULT '',
    created_at    INTEGER NOT NULL,
    updated_at    INTEGER NOT NULL
);
```

索引：`a2a_tokens(token_hash)`、`a2a_tasks(user_id, agent_id, context_id, created_at)`、`a2a_tasks(state)`。

### 4.4 路径 / token / tenant 三方绑定（防越权）

每个请求按顺序检查：

1. `Authorization` 存在且 Bearer 格式正确；否则 `401`。
2. token 哈希命中且未撤销/未过期；否则 `401`。
3. `token.user_id` 对应用户 `status == active`；否则 `403`。
4. `path.agent_id == token.agent_id`；否则 `403`（防止拿自己的 token 打别人的 URL）。
5. 如果请求体带 `tenant`，必须等于 `token.agent_id`；否则 `403`（防止租户伪造）。
6. `contextId`/`taskId` 必须属于该 `user_id + agent_id`；否则 `404`（不要返回 403，避免枚举）。

这六步是 A2A 多租户的安全底线。**不要只依赖 URL 难猜**；URL 只是路由，token 才是身份。

### 4.5 权限 scope（比“能不能调”更重要）

外部 agent 能驱动 Hlaudz 的工具链，这比“读一个 API”危险得多。建议 token 带 scope，默认最小：

| scope | 允许 | 默认 |
| --- | --- | --- |
| `chat` | 发消息、读任务/结果 | ✅ |
| `files:read` | 读用户 workspace 文件 | ❌ |
| `files:write` | 写/改 workspace 文件 | ❌ |
| `tools:run` | 执行 code_run/命令类工具 | ❌ |
| `agent:spawn` | 创建子 agent / 调 ACP GA | ❌ |
| `admin` | 管理 token/查看审计 | 仅网页 JWT，不给 A2A token |

落地方式：A2A 任务在构造 `AgentContext`/工具策略时带上 scope，工具层按 scope 拒绝；不要只靠提示词说“请不要执行”。如果现有工具层没有统一策略点，MVP 可以先只开放 `chat`（禁用危险工具），后续再逐项放开。

### 4.6 配额与审计

- 每用户最大并发 A2A 任务：`INNER_A2A_MAX_ACTIVE_TASKS_PER_USER`（建议 2）。
- 全局最大并发：`INNER_A2A_MAX_ACTIVE_GLOBAL`（建议 8–16）。
- 单请求体上限（例如 1 MB）、单条消息长度上限、单任务最长运行时间。
- 外部调用消耗的是**该用户自己的模型配置和额度**；token 页面要明确提示这一点。
- 记录：token id、agent_id、task_id、method、状态、耗时、错误码；**不记录消息正文和 key**（或按用户配置脱敏）。
- 失败/限流返回 A2A 标准错误，不要泄露内部堆栈。

## 5. 对外 API 设计（MVP）

### 5.1 非流式 `SendMessage`

请求：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "SendMessage",
  "params": {
    "tenant": "ha_7f3c9d2e",
    "message": {
      "messageId": "msg-client-001",
      "role": "ROLE_USER",
      "parts": [{"text": "帮我把这个仓库的测试跑一遍，并总结失败原因"}],
      "contextId": "ctx-optional-existing-session"
    },
    "configuration": {
      "returnImmediately": false,
      "historyLength": 20
    }
  }
}
```

响应（成功，任务已创建/更新）：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "task": {
      "id": "task_9f2c...",
      "contextId": "sess_abc123",
      "status": {
        "state": "TASK_STATE_COMPLETED",
        "timestamp": "2026-11-09T12:34:56.000Z"
      },
      "artifacts": [
        {
          "artifactId": "answer",
          "name": "answer",
          "parts": [{"text": "测试全部通过，共 243 个用例……"}]
        }
      ]
    }
  }
}
```

实现要点：

- `returnImmediately` 默认 `false`：A2A 规范要求阻塞到终态/中断态。Hlaudz 任务可能很久，建议服务端加 `INNER_A2A_SYNC_TIMEOUT_S`（如 60s）：超时后返回当前 `TASK_STATE_WORKING` 的 Task，客户端再用 `GetTask` 轮询；不要让 HTTP 连接无限挂起。
- `returnImmediately: true`：创建任务后立刻返回 `SUBMITTED`/`WORKING`。
- `messageId` 做幂等键：同一 `(agent_id, contextId, messageId)` 重复发送，返回第一次的 task，不重复执行。
- `contextId` 缺省时创建新 Hlaudz session；提供时必须是该用户已有 session（否则 404），这样多轮对话可以延续。
- 最终文本放一个 artifact（`artifactId: "answer"`）；工具轨迹/思考不要塞进最终 artifact，放 `status.message` 或 `metadata`。

### 5.2 流式 `SendStreamingMessage`

请求同 `SendMessage`，响应是 SSE，每个 `data:` 是一个 JSON-RPC result：

```text
data: {"jsonrpc":"2.0","id":2,"result":{"task":{"id":"task_9f2c...","contextId":"sess_abc123","status":{"state":"TASK_STATE_WORKING","timestamp":"..."}}}}
data: {"jsonrpc":"2.0","id":2,"result":{"statusUpdate":{"taskId":"task_9f2c...","contextId":"sess_abc123","status":{"state":"TASK_STATE_WORKING","timestamp":"...","message":{"messageId":"m1","role":"ROLE_AGENT","parts":[{"text":"开始执行测试"}]}}}}}
data: {"jsonrpc":"2.0","id":2,"result":{"artifactUpdate":{"taskId":"task_9f2c...","contextId":"sess_abc123","artifact":{"artifactId":"answer","parts":[{"text":"测试全部通过"}]},"append":true,"lastChunk":false,"index":0}}}
data: {"jsonrpc":"2.0","id":2,"result":{"statusUpdate":{"taskId":"task_9f2c...","contextId":"sess_abc123","status":{"state":"TASK_STATE_COMPLETED","timestamp":"..."}}}}
```

实现要点：

- 第一条发 `task`（当前状态），让客户端拿到 taskId。
- 文本增量用 `artifactUpdate` + `append: true`；最后一块 `lastChunk: true`。也可以累积到结束只发一次完整 artifact，但那样就失去流式意义。
- 工具/子 agent 进度用 `statusUpdate.message`（简短），不要每个 token 都发 status。
- 终态必须发一次 `statusUpdate`（`COMPLETED`/`FAILED`/`CANCELED`），然后关闭 SSE。
- 客户端断开时，**不要自动取消任务**（A2A 语义允许后台继续 + `GetTask`/`SubscribeToTask`）；但要在任务表记录“无订阅者”，并按配置决定是否继续。Hlaudz 现有 `_event_stream` 在客户端断开时会取消生成，需要显式改为“A2A 任务由后台任务持有，SSE 只是订阅者”，这是实现里最容易踩的坑。

### 5.3 `GetTask` / `ListTasks` / `CancelTask`

```json
{"jsonrpc":"2.0","id":3,"method":"GetTask","params":{"tenant":"ha_7f3c9d2e","id":"task_9f2c...","historyLength":20}}
{"jsonrpc":"2.0","id":4,"method":"ListTasks","params":{"tenant":"ha_7f3c9d2e","contextId":"sess_abc123","pageSize":20}}
{"jsonrpc":"2.0","id":5,"method":"CancelTask","params":{"tenant":"ha_7f3c9d2e","id":"task_9f2c..."}}
```

- `GetTask` 从 `a2a_tasks` + `messages` 组装 Task；终态后仍可查。
- `ListTasks` 只返回该 token 的 `user_id + agent_id` 范围，支持 `contextId`、`status`、`pageSize`（1–100）、`pageToken`。
- `CancelTask` 复用 `stop_generation` 的顺序：`request_stop` → `stop_acp_generation`（≤2s）→ `cancel_generation` → 子 agent → code_run → 收敛终态。不要另写一套取消逻辑。
- 取消后任务状态 `TASK_STATE_CANCELED`；已经终态的任务返回 `TaskNotCancelableError`。

### 5.4 任务与 Hlaudz 会话的映射

| A2A | Hlaudz | 说明 |
| --- | --- | --- |
| `contextId` | `sessions.id` | 一个 A2A 会话 = 一个 Hlaudz session |
| `taskId` | `a2a_tasks.task_id` | 一个用户消息 + 一次生成 |
| `messageId` | `messages.id`（或客户端 id 映射） | 幂等键 |
| `generationId` | `team_store` lease / RuntimeHub | 复用现有停止/并发控制 |
| `Artifact` | assistant `content` + `blocks` | 最终答案进 artifact；工具轨迹可进 metadata |
| `TaskStatus` | `messages.status` | `streaming/complete/stopped/error` 映射 |

**状态映射表**

| Hlaudz | A2A |
| --- | --- |
| 任务刚创建，尚未开始 | `TASK_STATE_SUBMITTED` |
| `messages.status == streaming` / generation live | `TASK_STATE_WORKING` |
| `complete` | `TASK_STATE_COMPLETED` |
| `stopped` | `TASK_STATE_CANCELED` |
| `error` / runtime 初始化失败 | `TASK_STATE_FAILED` |
| 等待用户补充（未来） | `TASK_STATE_INPUT_REQUIRED` |
| 权限/凭据不足（未来） | `TASK_STATE_AUTH_REQUIRED` |

> `messages.status` 的取值来自 `backend/app/db.py` 和 `chat.py` 的现有写入逻辑；实现时以真实枚举为准，不要凭空新增。

## 6. 实现落点（建议的文件结构）

```text
backend/app/a2a/
  __init__.py
  config.py        # INNER_A2A_* 环境变量、默认关闭
  models.py        # Pydantic：AgentCard / Task / Message / Part / StreamResponse / JSON-RPC
  auth.py          # Bearer 解析、token 哈希查表、path/tenant 绑定
  tokens.py        # 生成/撤销/轮换 token；只存哈希
  tasks.py         # a2a_tasks CRUD、状态映射、幂等
  service.py       # SendMessage / CancelTask / GetTask 的业务编排
  stream.py        # 现有 SSE → A2A StreamResponse 翻译
  cards.py         # 每用户 AgentCard 生成
backend/app/routers/a2a.py       # /a2a/{agent_id} 与 token 管理 API
backend/app/routers/me.py        # 或在 me 下增加 /api/a2a/tokens（复用 JWT）
```

**复用而不是重写：**

- `chat._event_stream`：任务执行 + 事件源；A2A 层只消费，不复制 agent loop。
- `chat.stop_generation`：把函数体抽成 `stop_turn(user_id, session_id, generation_id, message_id)`，`/api/.../stop` 和 A2A `CancelTask` 都调用它。**不要复制停止顺序**，否则两条路径迟早不一致。
- `team_store.acquire_generation` / `release_generation`：并发和租约；A2A 任务也要遵守“一个 session 同时一个 generation”。
- `auth.get_current_user`：只用于网页 token 管理 API；A2A 请求走独立的 Bearer 校验，**不要复用 `get_current_user`**（它期望登录 JWT）。
- `quota.QuotaManager`：新增 A2A 信号量，或者把 A2A 活跃任务映射到现有的用户/全局并发门禁。

**建议新增的网页 API（用登录 JWT，不是 A2A token）**

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/a2a/agent` | 当前用户的 agent_id、卡片 URL、A2A endpoint |
| `GET` | `/api/a2a/tokens` | 列出 token（只显示 prefix/last_used，不显示明文） |
| `POST` | `/api/a2a/tokens` | 创建 token（name/scopes/expires）；响应中一次性返回明文 |
| `POST` | `/api/a2a/tokens/{id}/revoke` | 撤销 |
| `POST` | `/api/a2a/tokens/{id}/rotate` | 轮换（旧 token 立即失效） |

**配置项**

```text
INNER_A2A_ENABLED=false                 # 默认关闭，避免升级即暴露
INNER_A2A_PUBLIC_BASE_URL=              # 例如 https://hlaudz.example.com
INNER_A2A_SYNC_TIMEOUT_S=60             # 非流式等待上限
INNER_A2A_MAX_ACTIVE_TASKS_PER_USER=2
INNER_A2A_MAX_ACTIVE_GLOBAL=16
INNER_A2A_MAX_BODY_BYTES=1048576
INNER_A2A_TASK_RETENTION_DAYS=30
```

**测试清单（按 TDD，先红后绿）**

1. 无 token → 401；token 撤销/过期 → 401；用户被禁用 → 403。
2. 用 A 的 token 打 B 的 `/a2a/{agent_id}` → 403；body.tenant 不匹配 → 403。
3. A 的 token 查 B 的 taskId/contextId → 404（不是 403，防枚举）。
4. 同一 `messageId` 重复 `SendMessage` → 只执行一次，返回同一 task。
5. `SendMessage` 正常完成 → `COMPLETED` + `answer` artifact；模型错误 → `FAILED`。
6. `CancelTask` → `CANCELED`，且 ACP/子 agent/code_run 都被清理（复用现有 stop 测试）。
7. 客户端中途断开 `SendStreamingMessage` → 任务按配置继续或取消，`GetTask` 可查；不能留下永久 streaming。
8. 服务重启 → 上次 `WORKING/SUBMITTED` 的任务收敛为 `FAILED` 或可恢复状态，不能永远卡住。
9. 并发超限 → 标准 A2A 错误/429，不影响网页和 ACP 路径。
10. SSE 每个 `data:` 都是合法 JSON-RPC `result`，且 `StreamResponse` 只有一个成员。

## 7. GA 能不能调用 A2A？需不需要改 GA？

### 7.1 先分清“谁调谁”

| 场景 | 需要什么 | GA 是否要改 |
| --- | --- | --- |
| Hlaudz 调 GA（现有） | Hlaudz 做 ACP client，GA 做 ACP server | **不需要** |
| 外部 agent 调 Hlaudz | Hlaudz 做 A2A server | **不需要动 GA** |
| Hlaudz 把 A2A 任务转给 GA 执行 | Hlaudz A2A → 内部 ACP → GA | **不需要**；A2A 只是 Hlaudz 的前门 |
| GA 主动调 Hlaudz | GA 做 A2A client（或普通 HTTP 客户端） | **核心不需要改**；用 `code_run` 即可 |
| 外部 agent 直接调 GA | GA 做 A2A server，或加 A2A→ACP 网关 | 需要新增，**不建议现在做** |

### 7.2 GA 作为 A2A client 的现实做法

GA 现在有 `web_fetch` 和 `code_run`：

- `web_fetch` 只支持 **GET**、只把内容转文本，不带自定义 Authorization 头，**不适合** A2A 的 POST + Bearer + SSE。源码见 `genericagent/resources/assets/tools_schema.json` 的 `web_fetch` 定义。
- `code_run` 是 Python 执行器，子进程 `env=os.environ.copy()`（`genericagent/core/handler.py` 的 `code_run`），所以可以用 `httpx`/`requests` 发 POST、带 `Authorization`、解析 SSE。**GA 核心不用改。**

推荐给 GA 的调用方式（不把 token 写进 prompt）：

1. 在 GA 进程环境里放 `HLAUDZ_A2A_URL` / `HLAUDZ_A2A_TOKEN`（专用、最小 scope、可轮换）。
2. GA 的 `code_run` 里用 Python：
   - 简单任务：`SendMessage` + `returnImmediately: true`，轮询 `GetTask` 直到 `COMPLETED`。
   - 需要实时进度：`SendStreamingMessage`，用 `httpx.stream` 逐行解析 `data:`。
3. 不要在任务文本/提示词里回显 token；不要用 `web_fetch` 传 token。
4. 这只是“GA 能调”，不是“GA 原生支持 A2A”。如果以后要把 A2A client 做成 GA 的一等工具，再在 GA 侧加一个薄工具/skill；那是 GA 升级后的事，本轮不做。

### 7.3 不建议让 GA 直接做 A2A server

GA 已经是 ACP server，ACP 的模型是“本地客户端启动子进程、单用户、stdio”，和 A2A 的“网络、多租户、HTTP、长任务”不是一回事。让 GA 再实现一套 A2A server 会带来：

- 两套会话/任务/权限模型；
- token/租户/配额要重做；
- 与 Hlaudz 的 ACP 链路重复。

更合理的拓扑是：**外部 agent → Hlaudz(A2A) → Hlaudz 内部 ACP → GA**。GA 保持“执行器”角色，Hlaudz 做“对外的 agent 门面”。

## 9. 风险与取舍

### 9.1 协议与生态风险

- **v1.0 仍是新标准**：2026-03 才稳定，SDK/客户端实现质量参差；先用官方 Python SDK 或按规范做契约测试，不要只对自家客户端“能跑”。
- **v0.3 兼容**：老客户端可能发 `message/send`、小写状态、带 `kind` 的 Part。MVP 只做 v1.0，文档写明；确有客户再在路由层加别名。
- **发现方式**：不做全局 well-known 卡片，客户端必须拿每用户卡片 URL；这牺牲了“域名级自动发现”，换来隔离。若未来要做目录，另建目录服务，不要把它变成可执行的总入口。
- **A2A 的“生产采用”要打折看**：150+ 组织、云平台集成是真的；但很多是“支持/集成公告”，深度生产案例不点名。把它当“值得押注的标准”，不要当“已经无处不在”。

### 9.2 工程风险

- **客户端断开 ≠ 取消任务**：A2A 允许后台继续；现有 `_event_stream` 是请求绑定的，必须改成“任务持有 + 订阅者”模型，否则 `GetTask`/`SubscribeToTask` 语义不对。
- **长任务与 HTTP 超时**：反代/网关要关闭缓冲（现有 SSE 已带 `X-Accel-Buffering: no`），并设置合理 read timeout；非流式要有 `returnImmediately`/超时降级。
- **取消竞态**：复用现有 stop 顺序，但 A2A 任务表的状态更新必须在取消后仍然落库；参考 `docs/20261109-ACP-client驱动GenericAgent实施记录.md` §10 的 cancel-safe 写法。
- **服务重启**：`RUNNING` 任务要有收敛策略（失败/可恢复），不能永久 `WORKING`。
- **单实例假设**：SQLite + 进程内 RuntimeHub 只适合单副本；多副本要外置任务/租约。

### 9.3 安全风险（最重要）

- **外部调用者能驱动工具**：这是“把 agent 的 shell/文件能力暴露给网络”。默认只给 `chat` scope；`tools:run/files:write/agent:spawn` 必须显式授权，并在工具层强制。
- **token 泄露**：只存哈希、只显示一次、支持撤销/轮换/过期；不要放 query string、日志、prompt。
- **越权/枚举**：path/token/tenant 三方绑定；跨用户 task/context 返回 404；限流；不要用自增 id 做 agent_id。
- **提示词注入**：外部 agent 传来的文本是不可信输入；Hlaudz 的工具权限不能由模型“自己决定”，必须由 scope/策略层决定。
- **计费**：外部调用消耗用户模型额度；token 页面明确提示，并加每用户/每日上限。

## 10. 推荐决策

1. **现在不写代码。** 你的 GA 正在升级，A2A 也不是“今天不上线就损失”的功能；先保留这份设计，等 GA 升级完成后再做。
2. **做，就做 v1.0 JSON-RPC MVP，不做“大而全”。** 首期只做 `SendMessage` + `SendStreamingMessage` + `GetTask` + `CancelTask` + `ListTasks` + 每用户 AgentCard/token；`SubscribeToTask`/push 放后面。
3. **每用户 URL + token 是正确方向。** 用 `/a2a/{agent_id}` + `tenant` + Bearer 三方绑定；不做全局可调用入口。这既符合 A2A v1.0 的多租户设计，也符合你的安全直觉。
4. **GA 不动。** Hlaudz 做 A2A server，内部继续用 ACP 调 GA；GA 要调 Hlaudz 时用 `code_run` + env token 即可。等 GA 升级完，再评估是否给它加一个薄 A2A client 工具。
5. **如果只是 Hlaudz↔GA，不要上 A2A。** 这句话要保留：A2A 的价值在“外部异构 agent 的互操作”，不是“本地两个 agent 说话”。本地场景 ACP 更合适。

**建议的下一步（等你确认）**：GA 升级完成后，按本文档写一份 `docs/2026xxxx-A2A接入实施计划.md`，用 TDD 分 Phase 1–3 执行；第一步只做“关闭开关下的表结构 + token 管理 + AgentCard”，不碰现有 chat 路径。

## 11. 附：没有现成外部智能体时，怎么验证 A2A

这是一个很现实的问题：A2A 是“给外部 agent 调”的，但 MVP 刚做完时，手头不一定有第二个 agent。**不需要为此再写一个新的 HTTP 智能体。** 最合适的“外部调用方”就是 Claude Code 本身，配合官方的 A2A CLI。

### 11.1 Claude Code 原生支持 A2A 吗？

**没有原生 A2A client。** 截至 2026-10，Claude Code 还没有把 A2A 作为一等连接类型；社区 issue 仍在开放（anthropics/claude-code#104852）。官方推荐的 coding harness 路径是：

> **Claude Code（Agent） + `a2a` CLI（工具） + A2A Skill/Plugin**

也就是说：Claude Code 仍然是“大脑”，`a2a` CLI 是它的“手”；不需要另起一个 LLM agent 服务。A2A CLI 是官方 A2A 项目维护的 v1.0 客户端，支持 AgentCard 发现、JSON-RPC/REST/gRPC、流式、异步任务、取消、任务列表和 JSON 输出。

### 11.2 安装与接入 Claude Code

Windows 可以用 WinGet：

```powershell
winget install a2aproject.a2acli
a2a version
```

然后给 Claude Code 安装官方 A2A Skill：

```bash
npx skills add https://github.com/a2aproject/a2a-cli --skill a2a-cli
```

或者用 Claude Code 插件市场：

```text
/plugin marketplace add a2aproject/agent-plugins
/plugin install a2a-cli@a2a-plugins
```

> Skill/Plugin 只负责教 Claude Code 怎么用 `a2a`，**不会替你安装二进制**；先装 CLI。

### 11.3 对 Hlaudz 的实际调用

假设 Hlaudz 已实现 `POST /a2a/{agent_id}`，用户在设置页拿到：

```text
Agent URL:  https://hlaudz.example.com/a2a/ha_7f3c9d2e
Token:      hlz_a2a_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
Tenant:     ha_7f3c9d2e
```

Claude Code 里可以这样调用（token 建议放环境变量/配置文件，不要写进命令历史）：

```bash
export A2ACLI_AUTH="Bearer hlz_a2a_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"

# 1. 先看卡片，确认协议版本/能力/认证方式
a2a card get https://hlaudz.example.com/a2a/ha_7f3c9d2e

# 2. 发一条消息，阻塞到完成
a2a send -a https://hlaudz.example.com/a2a/ha_7f3c9d2e \
  --tenant ha_7f3c9d2e \
  "帮我总结这个仓库的测试失败原因" -o json

# 3. 流式看进度
a2a send -a https://hlaudz.example.com/a2a/ha_7f3c9d2e \
  --tenant ha_7f3c9d2e --stream \
  "跑一遍测试并实时告诉我进度"

# 4. 长任务：先拿 taskId，再轮询
a2a send -a https://hlaudz.example.com/a2a/ha_7f3c9d2e \
  --tenant ha_7f3c9d2e --async "分析这个数据集"
a2a task get -a https://hlaudz.example.com/a2a/ha_7f3c9d2e \
  --tenant ha_7f3c9d2e <task-id> --wait --timeout 120s

# 5. 取消
a2a task cancel -a https://hlaudz.example.com/a2a/ha_7f3c9d2e \
  --tenant ha_7f3c9d2e <task-id>
```

> `-a` 可以给 host/origin（自动拼 `/.well-known/agent-card.json`）、完整卡片 URL，或本地卡片文件。每条请求都会带 `--tenant`，和 Hlaudz 的 path/token/tenant 三方校验对齐。

### 11.4 这条链路证明了什么

```text
Claude Code（外部异构 Agent）
   │  a2a CLI + Bearer token（每用户）
   ▼
Hlaudz A2A endpoint（/a2a/{agent_id}）
   │  内部 ACP
   ▼
GenericAgent（本地执行器）
```

一次成功的 `a2a send` 就能同时证明：

- 外部 agent 能发现并调用 Hlaudz；
- 每用户 URL/token/tenant 生效，换 token 或换路径会被拒绝；
- 任务生命周期（`SendMessage` → `GetTask`/流式 → `CancelTask`）可用；
- Hlaudz 能把任务继续交给 GA 执行，且不需要改 GA。

### 11.5 其他可选方案

| 方案 | 适用 | 评价 |
| --- | --- | --- |
| **Claude Code + `a2a` CLI** | 最贴近真实外部 agent，且零额外 agent 服务 | **首选** |
| **A2A Inspector**（官方 Web UI） | 手工调试卡片/JSON-RPC/流式 | 适合排查协议细节，不是长期调用方 |
| **另一个 Claude Code / Codex / Gemini CLI** | 想演示“两个异构 agent 互调” | 用同一个 `a2a` skill 即可；成本低 |
| **`a2a server --echo`** | 先验证 Hlaudz 作为 client 的代码（如果以后做 A2A client） | 只适合自测，不是外部 agent |
| **`a2a-adapter claude --port 9010`** | 反向：把 Claude Code 暴露成 A2A server，让 Hlaudz 调它 | 第三方适配器；不是本项目当前方向 |

**结论：不用造新的 HTTP 智能体。** 用 Claude Code + 官方 `a2a` CLI 就是最真实的“外部智能体调用 Hlaudz”验收方式；等 Hlaudz 的 A2A MVP 落地后，我可以直接用这条链路做 E2E，并把请求/响应/任务状态留成证据。

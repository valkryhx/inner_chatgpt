# 排查经验：从"卡住"到根因的四路交叉

日期：2026-11-20
适用范围：Hlaudz（及任何"前端看不到真相"的后端服务）

## 0. 这份文档纠正一个常见误记

事后回看容易总结成**"靠后台 log 找到的 bug"**。不准确。

真实的定位过程是**四路交叉**，日志只是其中一路，而且它**误导过我一次**。
只记"看日志"会让人下次只开日志，然后卡在"日志里全是 200 OK"。

| 路 | 拿到什么 | 什么时候是唯一有效信号 |
| --- | --- | --- |
| ① 现象（用户/前端） | "卡住了"、"状态是 X" | 起点。但**从不指向根因** |
| ② 结构化状态（DB） | 谁跑了几轮、什么状态、任务 owner | 日志打不出这层聚合 |
| ③ 日志 | 具体错误类型、HTTP 码、重试 | 状态对但行为不对时 |
| ④ 文件系统（stat / find） | 权限位、属主、时间戳、内容 | 日志说"成功"但结果不对时 |

**铁律：任何一路单独看都不够。** 下面每一节都是"只有某一路能看见"的例子。

---

## 1. 第一路（现象）从来只说"症状"

hx 的原话：

> 子代理跑了 66 分钟没有出结果，明明就刚刚建立啊，而且任务没有人认领

这句话里三件事，**没有一件是根因**：

- "66 分钟" → `started_at` 没被清零的显示问题，不是真的跑了 66 分钟
- "刚刚建立" → 用户感受，实际子代理确实在跑
- "任务没人认领" → 那条任务有 `blocked_by`，本来就不该被认领

**从症状直接跳到修复，修的一定不是根因。**
正确做法：症状 → 结构化状态 → 找到"哪一环断了" → 才看看哪一路能证明它。

## 2. 第二路（DB）回答"谁在哪一步"

一眼看出分工的查询：

```sql
-- 子代理：谁跑了几轮、什么终态
SELECT name, status, turns, (finished_at-started_at)/1000 AS secs
FROM subagent_runs WHERE session_id='<sid>' ORDER BY started_at;

-- 任务：谁认领了、卡在什么状态
SELECT substr(subject,1,20), status, owner_agent_id
FROM team_tasks WHERE session_id='<sid>';

-- 依赖：为什么某条任务"没人认领"
SELECT task_id, blocked_by FROM team_task_deps WHERE team_id='<tid>';
```

本次实测结果（`session co_8abfb27422c8`，**排查中途的快照**）：

```
researcher_a | stopped  | 10 轮 | 128s
writer_b     | stopped  |  4 轮 |  85s
writer_c     | stopped  | 16 轮 | 202s

研究任务 = completed（owner=root）
撰写任务 = pending（owner 空）
```

**这张表就把"卡住"翻译成了可查的问题**：三个 writer 都起了、都死了、
任务回到 pending。比日志里翻 200 行有用得多。

> ⚠️ 日志**打不出这层聚合**。日志是事件流，"三个 writer 先后起停"
> 要自己拼；DB 是终态快照，一眼可见。这是为什么 DB 是第二路而不是第三路。

### 2.1 ★ DB 快照必须标明「什么时候取的」

上面那张表我**一开始当成了终态写进结论**，结果是错的。回查终态：

```
researcher_a | stopped | 10 轮 | 128s
writer_b     | stopped |  4 轮 |  85s
writer_c     | stopped | 16 轮 | 202s
writer_d     | stopped |  9 轮 |  90s
writer_e     | stopped | 18 轮 | 168s      ← 又起了两个

撰写任务 = completed（owner=sub:writer_e）
产物：writer_d/reports/trump_report.md、writer_e/reports/trump_report.writer_e.md
```

注意这里是 **5 条 run = 1 个 researcher + 4 个 writer**。
（本文档第一版写成「5 个 writer」，核验脚本按 `name LIKE 'writer%'` 数出 4，
才发现少数了一个。**手数名册必然出错，必须让 SQL 数。**）

**这不是"卡住"，是"极其低效地完成了"**：

- 终态是 `completed`，任务确实被认领、确实写出来了
- 但中间换了 **4 个 writer**，最少的 4 轮就死，最多的 18 轮
- 每一轮都是一次真实 LLM 调用

所以「卡住」这个描述本身就错了一半 —— 用户看到的是"很久没结果"，
实际是"一直在重试"。**症状的措辞和真相可以差这么远。**

> 教训：DB 是**会变的**。任何写进文档/结论的表，必须标注取样时刻
> （或写成 `SELECT ... -- at 10:31`），否则下一个读者会以为那是终态。
> 本条是本文档自己踩的坑，保留在正文里而不是藏在失误表。

## 3. 第三路（日志）证明"行为对不对"

DB 告诉你 writer 死了，但**没告诉你为什么**。这一步才轮到日志。

本次的关键三行：

```
# 沙箱侧：写入成功
2026-11-20 10:29:33 INFO sandbox_service.main: 文件写入 ... writer_c/reports/trump_report.md chars=22381
INFO:     172.21.0.5:48042 - "POST /v1/write HTTP/1.1" 200 OK

# app 侧：LLM 上游挂了
WARNING app.llm_client: LLM 请求失败，1.0s 后重试（第 1/4 次）：HTTP 502 ...
```

**两条日志合起来才排出 507 的嫌疑**：写入 200 OK、app 侧无 PermissionError
⇒ 权限问题已解决 ⇒ 卡点换了地方。

### 3.1 ★ 日志会误导：一个真实的假信号

同一次排查里，我一开始数到：

```bash
docker logs ...-sandbox-1 | grep -ciE "507|Permission denied"
# → 1
```

看着像"还有 1 次 507"。实际那条是**历史容器残留日志**（上一个会话
`co_03e31d11894f` 的）。

**修法：日志一律带时间窗。**

```bash
docker logs <c> --since 20m | grep -c ...
docker logs <c> --since 3m  | grep -cE "502|LLM 请求失败"
```

不带 `--since` 的计数，在“容器跨多个测试会话复用”时**必然掺假**。

### 3.2 日志的另一类坑：只配了一半

`uvicorn` 只配置 `uvicorn.*` 的 logger，**不会**给业务模块配 handler。
于是 `logger.info("建槽 ...")` 全部被丢弃 —— 服务行为是对的，只是看不到。

第一版服务就是这样：端到端探针拿不到“池有没有真的建槽”的证据，
排查方向一度偏到“池没工作”。

**判定方法**：故意打一条 `logger.error`，如果日志里没有，就是没配。

## 4. 第四路（文件系统）揭穿"日志说成功"

这一路是本次最有价值的发现，也是最容易被忽略的。

### 4.1 日志说 200 OK，磁盘上确实是错的

`code_run` 的写入日志一切正常。但 `stat` 出来：

```
DIR  0o2755    ← 组不可写
FILE 0o644     ← 组不可写
```

正常应该是 `2775` / `0664`（共享组约定）。

**没有第四路，这个缺陷永远不会被发现** —— 因为：
- 日志：200 OK，无异常
- DB：`completed`，无 error
- 前端：文件确实生成了

三路全绿，问题在第四路。

### 4.2 第四路的常规工具

```bash
# 权限逐级核对（最能定位"哪一层坏了"）
docker exec <app> sh -c 'find <dir> -type d -exec ls -ld {} \;'

# 属主异常（65534 = linux overflow uid, bwrap uid 未映射的产物）
docker exec <app> sh -c 'find <root> \( -uid 65534 -o -gid 65534 \) | head'

# 内容是否真的是预期的
docker exec <app> sh -c 'tail -c 500 <file>'
```

### 4.3 「日志说修好了」≠「修好了」

本次有一条探针报 FAIL，我差点去改代码。真相是探针**读到了历史遗留文件**：

```
mkdir(exist_ok=True) 不清已存在的目录
→ 权限是上一轮（umask 还是 022 时）建的
```

**探针造现场前必须先删干净**，否则验的是上一轮的结果。

## 5. 走完四路之后：怎么确认修对了

### 5.1 判据必须能区分两种状态

本次试过三个判据，前两个都不成立：

| 判据 | 为什么不行 |
| --- | --- |
| "文件有没有被写出来" | 假绿：容器里路径不存在，代码抛 FileNotFoundError，也被当成"没写出来" |
| "网络是不是被阻断" | 假信号：app 容器本身也没有外网，两边都不通 |
| **"app 的环境变量有没有漏进沙箱"** | ✅ 有效：bwrap 用 `--clearenv`，能明确区分 |

**判据的检验方法**：这个信号在「修好」和「没修好」两种状态下**取值不同吗**？
如果两种状态读数一样，它就不是判据。

### 5.2 三路全绿后仍要跑真机

单测绿 ≠ 链路通。本次全量 1676 passed 之后，真机仍发现
「写完了没正确收尾」。

真机探针要能复现**用户的完整序列**，不是一个点。本次最有效的一条是：

```
遗留目录 → file_write → code_run → file_patch
```

因为 `file_patch` 同时依赖"目录组可写"和"文件组可写"，
只测前两步任一步都会漏掉另一半。

## 6. 排查清单（下次直接用）

### 第一步：把症状翻译成可查的问题

- [ ] 用户说"卡住" → 查 `subagent_runs.status / turns / finished_at`
- [ ] 用户说"没人认领" → 先查 `team_task_deps.blocked_by`（可能本就不该认领）
- [ ] 用户说"跑了很久" → 核对 `started_at` 是否留了上一轮的值

### 第二步：定位"哪一环断了"

按链路顺序，每环找一个判据：

```
LLM 调用 → 工具调用 → 沙箱分流 → 服务执行 → 磁盘落盘 → 任务状态
```

本次断点是「沙箱分流成功后，磁盘权限不对」——前四环全绿，第五环错。

### 第三步：给每一路都开一眼

| 路 | 最少要做的 |
| --- | --- |
| DB | `subagent_runs` + `team_tasks` + `team_task_deps` |
| 日志 | `docker logs --since 20m`（**必须带时间窗**） |
| 文件系统 | `find -type d -exec ls -ld`（权限逐级） |
| 前端 | 只在声称"用户能看到"时才需要 |

### 第四步：修了之后

- [ ] 有一个**能区分两种状态**的判据（不是"没报错"）
- [ ] 探针造现场前**删干净**（否则验的是历史）
- [ ] 真机跑**用户的完整序列**，不是一个点
- [ ] 反向确认：把修复拿掉，测试必须变红

## 7. 本轮的失误清单（错误模式比结论更有复用价值）

| 失误 | 后果 | 怎么防 |
| --- | --- | --- |
| 日志计数没带时间窗 | 把历史容器的 507 当成本次的，方向偏了一轮 | `docker logs` 一律带 `--since` |
| 探针读历史文件 | 改了修复仍报旧值，误判"修复无效" | 造现场前 `rmtree` |
| 判据选错两次 | "文件写出来没" / "网络通不通" 都是假信号 | 先问"两种状态读数不同吗" |
| 只盯 `file_write` | 用户其实绕道 `code_run` 写了文件，坑推到后面才炸 | 按**创建者**逐个数，不是按"工具"数 |
| 以为删代码就够了 | 工具描述还写着"硬门禁"，模型做无谓步骤 | 行为改动必须同步文案 + 守卫测试 |
| 手数行号 | 两处差 1-4 行，断言坐标全错 | 期望值让脚本打印后再填 |
| **把 DB 中途快照写成"终态"** | 结论「任务 pending、3 个 writer」全错，实际是「completed、4 个 writer」 | 快照必须标注取样时刻；写结论前重新取样一次 |
| **手数名册** | 写成"5 个 writer"，实际 4 个（5 是 run 总数，含 researcher） | **数量一律让 SQL 数**（`count(*) ... LIKE 'writer%'`），不靠眼睛 |

**最后一条是元教训**：这份文档自己也可能有手数错。凡正文写了行号/坐标/数量，
都必须有脚本能复算 —— 本文档配 `docs/probes/20261120-排查经验文档核验.py`
（8 项）+ `…核验反向确认.py`（4/4）。

## 8. 这份文档自己是怎样被验的

| 步骤 | 做了什么 | 抓到了什么 |
| --- | --- | --- |
| 写完初稿 | 把文档里每条 SQL / shell 命令抽成核验脚本 | 3 条 SQL + 2 条 shell 全部能跑 |
| 加终态断言 | 断言「5 个 writer / owner=writer_e」 | **抓到「5 个 writer」应为 4 个** |
| 加反向确认 | 故意把期望值改错，看能否变红 | 4/4 变红，证明断言有因果力 |
| 重取样 | 回查终态，发现「pending」是中途快照 | 结论从「卡住」改为「低效完成」 |

**没有这一步，这份文档会带着两处错误结论流传下去** ——
而"排查经验"类文档的错误代价特别高：下一个人会照着错结论去排查。

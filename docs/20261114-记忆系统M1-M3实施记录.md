## 2. M1：存储层

### 2.1 关键实现选择

**文件是真相，DB 是索引。** 正文永远在
`backend/data/memories/<user_id>/private/<slug>.md`，SQLite 只存
「列举 / 排序 / 命中统计」需要的字段。理由（方案 §2.2）：模型能用 `file_read` 直接改；
用户在设置页手改不会出现「库里有、文件没了」的分裂。

**`_reconcile()` 是必须的，不是优化。** 方案 §8 的最小可用集明确支持
「用户手动加一个 `.md`」。只信 DB 会让手写的记忆永远不可见。所以每次列举/选择前
先扫目录，用文件 `mtime` 做增量 upsert，并删掉「DB 有、文件没了」的行。
记忆条数是几十量级，一次 `scandir` + 几次 `stat` 可忽略。

**`version` 现算，不缓存进 DB。** 版本令牌 = 内容 sha256 前 12 位（对齐 CC 的 `mWe`）。
缓存在 DB 里一旦落后，会让「明明没别人改」的写入被误判成冲突 —— 版本只能从文件算。

**两套预算口径，必须分开**（v3 §1.3）：

| 项 | 单位 | 默认 | 实现 |
|---|---|---|---|
| 索引 cap | **code point** | 25000 | `len(str)` |
| 注入预算 | **code point** | 2000 | `len(str)` |
| 单文件召回 | **真字节** | 4096 | `len(s.encode())` |

按字节实现索引 cap 会让中文索引在 1/3 处被截（25,000 汉字 ≈ 75 KB）。

**`merge` 参数：两个调用方需要相反的语义。**

- 模型侧（`merge=True`）：留空 = 沿用。模型最常给的形态就是 slug + content，
  把元数据抹掉会毁掉相关性判断。
- 设置页（`merge=False`）：用户点了「清空描述」就必须真的清空。

这不是过度设计 —— 第一版只有一个默认值时有 1 项测试直接变红（
`test_patch_can_clear_field_explicitly`）。同理，`_parse_memory_file` 只在
**frontmatter 里压根没有 `description` 这个键**时才回落到正文首行；写了空值表示
「作者明确表示没有描述」。

### 2.2 隔离的三道保证（方案 §2.3）

| 层 | 实现 | 测试 |
|---|---|---|
| 路径 | `_resolve_under(root, candidate)`，越界抛 `PathSecurityError` | `test_m1_*` |
| 查询 | 每个公开函数首参是 `user_id`，SQL 里 `WHERE user_id=?` | `test_m2_list_is_per_user` |
| 注入 | 注入器闭包捕获 `user_id`，不从请求参数反查 | `test_injector_is_user_scoped` |

> 注意第一道有**两层**：`validate_slug`（字符集 + 拒绝 `..`）与
> `_resolve_under`（`resolve()` 后校验包含关系）。反向确认时发现：
> 只删第二层测试仍全绿，因为第一层已经挡住了全部已知输入。
> 所以补了 `test_m1_path_layer_is_a_second_line_of_defense` —— 把第一层短路掉，
> 直接验证第二层。**这是「正向测试覆盖不到某层」的典型例子。**

### 2.3 `cursor` 分页

按 `slug` 升序（不是 `updated_at`）。理由：`cursor` 要能稳定续读，
按时间排序时两次调用之间只要有写入，游标就会漂移，翻页会漏条目或重复条目。
CC 的 cursor 语义也是「上一次返回的最后一个 path」。

设置页要「最近更新优先」的直觉，在**当前页内**由接口层按 `updated_at` 倒序即可，
翻页语义仍由 cursor 保证。

带 `query` 过滤时不走 SQL `LIMIT`（过滤在内存里做），否则分页会漏条目。

## 3. M2：三件套工具

对外只声明 `memory_list` / `memory_read` / `memory_write`（对齐 CC 的
`Nji = ["memory_list","memory_read","memory_write"]`，`m0290:8`）。

**没有 `memory_delete` 工具。** CC 客户端没有承诺它，对外多承诺就是超出契约；
删除能力只出现在给界面用的 REST 路由与设置页 UI 里。

**子代理拿不到任何 `memory_*`。** 用 `build_builtin_tools(..., include_memory=False)`
在**装配处**就不生成，而不是事后过滤 —— prompt 里写「不要用」从来不是安全边界。
`capabilities.py` 里另立 `MEMORY_TOOLS` 集合与 `CHILD_EXCLUDED`，
语义上把它与「编排工具」区分开（一个是防递归，一个是隐私）。

**A2A 档位**：`read_only` 增加 `memory_list` / `memory_read`（纯读，
且按 token 绑定的 user_id 隔离），`memory_write` 不进。`describe()` 文案同步更新。

## 4. M3：读侧注入

### 4.1 注入点：复用现成的 `message_injector`，不新建管线

`agent_loop.py` 的轮循环在每次模型调用前跑一次注入器，外面包着 `InjectorGuard`
（8s 超时、`shield` 不丢消息）。记忆只接进这条管线 —— 不改 SSE 契约、不改 `chat.py`。

索引走 attachment 而非 system prompt 是 v3 §1.1 的核心结论（CC 默认走 `announced`
分支把 `claudeMd` 从 `userContext` 删掉转成 `instructions` attachment）。
理由在此处同样成立：索引每轮都可能变，塞 system prompt 会让 prompt cache 全灭。

### 4.2 组合，不覆盖

`sse.py` 原来是直接赋值 `loop.message_injector = _inject`，
team 路径用 `subagent/session.py` 的 `_lead_injector`。直接再赋一次会覆盖前面的。

实现：`wrap_with_memory(existing, memory_fn)` → `combine((a, b))`，返回**协程**。

> **必须支持异步注入器**：`host.drain_pending` 与 `_lead_injector` 都是协程，
> `InjectorGuard.collect()` 本来就按 `inspect.isawaitable` 分路。
> 组合层若拒绝 awaitable，会表现为「记忆能注入、团队消息静默消失」。
> 反向确认时把这一条改回去，`test_m8_compose_supports_async_injector` 立刻变红。

**`_steer_aware` 不是「不许再装注入器」**，它的语义是「已有注入器在 drain 用户插话队列」。
因为 `_steer_aware` 为真就跳过记忆注入，后果是「记忆永远不注入」。
`sse.py:107` 的注释已写明这点，并有 `test_install_does_not_skip_on_steer_aware` 锁住。

**team 路径不重复装。** `subagent/session.py` 装好后打 `_memory_aware` 标记，
`sse.py` 见到标记只补 `set_query_hint`（本轮的检索线索），不再装第二个 ——
两个 `MemoryInjector` 各有自己的 `_injected_slugs`，同一批记忆会被注入两遍。

### 4.3 slug 集合去重（不是布尔标志）

注入器挂在 `while turn` 循环里。一个用户轮次触发 10 次模型调用，同一批记忆会被
append 10 次 —— 模型会把它当强调指令，行为变僵。

去重键用 per-generation 的 **slug 集合**（CC 用 `readFileState` 的路径集合，
timing 文档 §5.1）。布尔标志的问题：第一轮注入了 A，第三轮后台写了 B，
布尔标志会让 B 永远注入不进去。

`test_new_memory_written_mid_turn_is_injected_next_model_call` 锁的就是这条：
轮中途写入的 B 必须在**下一次模型调用**时补注入，且不重复 A。

### 4.4 不进 `session_history`

注入块带 `"_volatile": True`，在 `HistoryStore.set()` / `append()` **统一剥离**。

为什么在存储层而不是各调用点：`session_history` 有 6 个持久化出口
（`sse.py:140/142`、`agent_loop.py:323/325`、`:456/458`、`:514/516`、
`compaction.py:199/300/354`、`chat.py:711/713`），逐个改是典型的
「改了新的忘了旧的」回归源。而全仓 `INSERT INTO session_history` 只出现在
`history_store.py` 的两个函数里，在那里剥离能一次覆盖全部。

展示侧（`messages.blocks` 的 `injected_message`）**照旧**，所以用户当轮能看到
「记忆进来了」，刷新后也能在历史里看到当时注入过什么 —— 与子代理通知行为一致。

### 4.5 预算扣留要报出去

`select_with_stats()` 额外返回扣留条数，块尾渲染成
`（另有 N 条记忆因预算未注入，可用 memory_list 查看）`。

CC 的 `withheld_memory` 渲染虽然为空（v3 §3 第 14 条），但它的欠账表真实存在。
**「扣留了并告知」和「扣留了不告知」是两种产品。**

单条放不下时**跳过它继续试更短的**，而不是「到此为止」——
一条 800 字的记忆不该让后面五条 60 字的记忆全部进不来。

## 5. 前端

### 5.1 注入块渲染

`MessageList.tsx` 的 `INJECTED_KINDS` 加一条 `[记忆]` → `{label: '记忆', mark: '◈'}`。
展开时用逐条列表（`ul.memory-lines`）而不是一整段 `pre-wrap`：
它是「这个用户的 N 条背景」，不是一段话。

### 5.2 设置页「我的记忆」tab

与「我的 Skills」并列。功能：状态条（条数 / 预算 / 三个开关状态）、
筛选、分页加载、新增/编辑/删除、编辑时带 `version` 做 CAS。

**这个 tab 是自动提取的前置条件。** 自动写入是唯一会「自己长东西」的机制，
用户看不见内容又没有删除入口时，一批来路不明的文本会被注入进每个会话 ——
这个组合不能上线（方案 §9 的硬约束）。

页面在 `auto_write=false` 时显式说明「只有模型主动调用 `memory_write` 才会新增，
而且你能当轮看到那一步」，而不是让用户误以为系统在偷偷记。

### 6.5 顺带修掉的既有缺陷：steer 注入器跨代失效（**高**）

**这是在验证「注入器组合」时被探针抓到的，与记忆无关，但同在一个函数里。**

现象（可复现，非猜测）：同一个 `ur.loop` 连续跑两代对话，
**第二代收不到用户中途插话**。

```
$ python work/_probe_steer_gen2.py
gen1: ['[用户在你执行过程中补充的消息] 第一代插话']  ✅
gen2: []  ❌
```

根因有两层：

1. `_ensure_steer_injector` 靠 `_steer_aware` **只装一次**。而 `ur` 是
   `RuntimeHub` 按 `(user, model)` **缓存**的，`loop` 跨会话跨代复用；
   注入器闭包捕获的是第一代的 `generation_id`，于是第二代的队列键
   永远不会被读。已在干净 HEAD（`git show HEAD:backend/app/sse.py`）上复现同样结果，
   **确认是既有缺陷，不是本次引入**。
2. 修第一层时又暴露出设计问题：如果「谁装谁包一层」，记忆注入器会把
   **第一代的 steer 注入器**记成自己的 baseline，第二代重建时把它拼回去，
   插话照样失效。

最终设计：**槽位 + 单一重建函数**。

```python
loop._memory_injector   ← 本代的 MemoryInjector（每代新建）
loop._steer_injector    ← 本代的 steer 注入器（每代新建）
loop._injector_base     ← 我们介入之前的原始注入器（只记一次）

def rebuild_message_injector(loop):   # memory_inject.py
    loop.message_injector = combine([记忆, steer, base])
```

并引入 `_steer_owner` 区分「谁在 drain 队列」：

- `"plain"` → 每代重装（闭包里的 generation 要更新）；
- `"team"` → 本函数让位（`subagent/session.py` 的 `_lead_injector` 已经在 drain，
  再装一个会让同一条插话被取两次）。

这两件事必须分开表达 —— 旧代码用一个 `_steer_aware` 布尔同时承担两者，
是缺陷的结构性原因。

**验证**：修后探针两代都收到；新增
`test_steer_works_across_generations_on_cached_loop` 与
`test_injector_is_rebuilt_each_generation_but_not_duplicated`。
反向确认：把「每代重装」改回「只装一次」，这两条立刻变红。

> 两条既有测试（`test_injector_is_idempotent`、`test_team_loop_is_not_double_wired`）
> 锁的是旧语义，已按新语义改写。**改测试不是为了让测试变绿** ——
> 旧语义（只装一次）本身就是缺陷，保住它等于保住 bug。

### 6.9 性能：一次被 e2e 抓出来的真回归

**S-M5 第一次跑出 496ms，远超 100ms 首帧预算。** 这是 e2e 才抓得到的 ——
单测全绿，因为没有用例在「刚写完 30 条记忆」这个状态下量耗时。

三个根因，逐个修：

| # | 问题 | 实测 | 修法 |
|---|---|---|---|
| 1 | `_reconcile` 对**每个文件**读全文算 sha256 | 300 条 → 366ms | 先 `stat` 拿 `(mtime, size)`，只对变了的文件读全文 |
| 2 | `_row_to_spec` 为**每行**读全文算 `version` | 300 条 → 200ms+ | 默认不算 version，只有 CAS 路径（`get_memory`/`write_memory`）才传 `with_version=True` |
| 3 | `_upsert_row` 每条新开一个 SQLite 连接 | 33 条 → 496ms | 批量 `executemany` + 一次 commit |

另加一处：`size` 也存进 DB，`_reconcile` 不再为已知行 stat 文件
（那等于同一份信息问两遍 FS）。

**结果**（300 条记忆，取中位数）：

```
前:  366.4ms (100 条: 67.3ms / 50 条: 36.8ms)
后:   15.8ms (稳定态)  29.1ms (33 条全新首次)  9.0ms (第二次)
```

**回归锁**：`test_injector_cost_bounded_with_many_memories`（300 条 < 150ms）与
`test_reconcile_does_not_reread_unchanged_files`（未变化的文件读取次数必须为 0）。
反向确认：把「只读变化的文件」改回「逐个读全文」，这两条立刻变红。

> 这里有个方法论上的点：**「记忆条数是几十条量级，代价可忽略」是我的猜测，
> 而且是错的**。写这句话时没量过。e2e 一跑就露了。第一版 S-M5 还只测了
> 真实 TTFT 且没有对照组（首次 3165ms 明显是冷启动），那样的数字支撑不了
> 任何结论 —— 改成直接量注入器本身（本地，不涉网络）才是准确答案。

## 7. 与方案的差异

| 方案原定 | 实际 | 原因 |
|---|---|---|
| `write_memory(..., scope=...)` 支持 team | 只实现 private，传 team 直接 `ValueError` | 无团队记忆层。**抛错而不是静默回落**，让想用的人立刻知道没实现，而不是写了三条发现进了私有目录 |

## 8. M4 后半：后台提取（已完成）

### 8.1 编排：`memory_extract.py`

分工是刻意分层的：

| 模块 | 职责 | 有无副作用 |
|---|---|---|
| `memory_write.py` | 四道闸门 + 提示词 | 无（纯函数，好测） |
| `memory_extract.py` | 读 history → 判闸 → 派提取 → 收尾登记 | 有 |
| `agent_loop.py` | 只提供 `on_turn_end` 钩子 | 无，**不 import 记忆模块** |

`agent_loop` 不认识记忆，这样记忆关掉时核心里不会留死代码。

### 8.2 为什么不用 `SubagentHost.spawn`

`spawn` 是给「模型主动派活」用的，它有四个副作用，每一个都不该出现在后台提取上：

1. **抢 `subagent_lease` 配额** —— 提取会挤掉用户真正派的子代理；
2. **发 `subagent_start` / `subagent_end` 事件** —— 前端会弹一张卡片，
   用户看到「Agent 正在整理记忆」，而他根本没要求这件事；
3. **写 `subagent_runs` 行** —— 侧链表被大量「记忆提取」run 撑满；
4. **结果进 `read_agent_result` 可读集合** —— 模型能读到自己的提取过程，
   下次提取就会看到上次的提取结论，形成反馈回路。

所以直接构造一个一次性的 `AgentLoop`：同构（同一个 client、同样的墙钟语义），
但不进 registry、不占配额、不发事件。

### 8.3 fire-and-forget 是硬要求，不是优化

`on_turn_end` 在 `yield done` **之前**被 await。如果同步等提取跑完，
一次最长 90 秒的提取会让 SSE 卡在结尾 —— 用户看到的是「每轮结束都要等几十秒」，
比不提取糟得多。

所以钩子只做三件事：判「有没有正在跑的」→ 快照 history → `create_task` 后立刻返回。

三个约束都有测试锁：

| 约束 | 为什么 | 测试 |
|---|---|---|
| 不阻塞 | SSE 不能卡在结尾 | `test_hook_does_not_block_the_turn` |
| history 快照 | 循环结束后 history 还会被 append | `test_hook_snapshots_history` |
| 每用户限并发 | 叠加只浪费钱，且两个提取器写同批 slug 会冲突 | `test_hook_limits_concurrency_per_user` |
| 不随本轮取消 | 用户点停止不该打断已开始的提取（它只写库，无可见输出） | 代码路径（独立 task，不挂父取消） |

### 8.4 闭世界工具集

提取子代理**只有 `memory_write` 一个工具**。拿不到 `code_run` / `file_write` / MCP /
`memory_list` / `memory_read` —— prompt 不是安全边界，工具 schema 才是。

> 方案 §4.3 说给 `z$t` 写侧三件（`memory_write` / `memory_str_replace` / `memory_append`）。
> Hlaudz 第一版只有 `memory_write`（对外只承诺 `Nji` 三件套），所以这里也是只有一个。
> 将来加了 str_replace / append 再同步加进来。

`_WriteRecorder` 包一层记录「这次到底写了哪些 slug」，且**只记 `outcome=ok`** ——
冲突/被拒不算写了。没有这个记录，出了问题只能翻文件和模型日志猜。

## 11. M4.5：`auto_dream` 合并（已完成）

> 实现：`backend/app/memory_dream.py`（约 700 行）
> 测试：`backend/tests/test_memory_dream.py`（33 项）+ `work/_dream_mutation.py`（8 条变异）

### 11.1 与方案的两处偏差（都是实测后改的）

**① dream 多一个 `memory_delete` 工具（对外三件套不变）。**

方案 §5 说对外只承诺 `memory_list` / `memory_read` / `memory_write`。第一版
严格照做，结果发现**合并根本做不完整**：三条重复只能写成一个保留者，
另外两条变成无人认领的残留。想靠「写空内容」绕过也不行 —— `write_memory`
的 merge 语义是「留空=沿用」，写不空。

所以 dream 的 registry 里额外挂 `memory_delete`，**只在 dream 里存在**：

```
root registry    memory_list / memory_read / memory_write     ← 契约不变
提取子代理        memory_write
dream           memory_list / memory_read / memory_write / memory_delete
```

`test_dream_registry_has_delete_but_root_does_not` 钉住这件事：
`MEMORY_TOOL_NAMES` 里**不许**出现 `memory_delete`。

**② 提示词按实际工具面重写，没有照抄 CC 的 `Q()`。**

CC 的 dream 提示词里 Phase 1 说「列出记忆目录」「读 MEMORY.md」，Phase 4 说
「更新 MEMORY.md」，那需要 Read/Glob/Write/Edit 与只读 shell。Hlaudz 的 dream
**没有文件工具**（见 11.3），所以：

| CC 提示词 | Hlaudz 的现实 | 改法 |
|---|---|---|
| 列出记忆目录 | 只有 `memory_list` | 改成「调 `memory_list`，有 `next_cursor` 就继续翻」 |
| 读 MEMORY.md | 模型无法读也无法写索引 | Phase 4 整段删掉，改成「索引由代码重建，你不用管」 |
| 合并多条 → 删旧的 | 没有 delete 工具 | 加上 delete，并把「先写后删」写进提示词与代码 |

照抄 CC 的后果是模型反复尝试不存在的工具、把 16 轮预算烧光 —— 第一版就是
这么失败的（35 秒、0 写入、0 删除）。

### 11.2 四处设计点

| 点 | 做法 | 理由 |
|---|---|---|
| **触发** | 后台巡检任务（`lifespan` 里 `start_dream_loop`），默认 600s 醒一次 | 方案 §4.6：dream 不是「空闲触发」，CC 里它和提取器在同一位置被尝试，靠三道时间闸压成隔天级。Hlaudz 不挂在用户轮次上，语义等价但更省 |
| **闸门** | 24h（距上次**成功**合并）+ 期间 5 个会话 + 开关 + 硬停用 | 对齐 CC 的 `he()` 与 `minHours`/`minSessions`；`aY()`/`rr()` 两道对 Web 服务恒通过，不实现（方案 D-10） |
| **锁** | DB 行 `lock_pid`/`lock_at`，一个 `UPDATE ... WHERE` 完成判断+抢占，`LOCK_STALE_MS=30min` | 文件锁在多 worker / 容器重启后 PID 视图不可靠（方案 D-9） |
| **启动收敛** | `recover_dream_state()`：清所有锁，`running`→`interrupted` | **不能只靠锁过期** —— 刚重启时锁可能还很新，但进程已死。与 `team_store.recover_stale_runtime` 同一套解法 |

### 11.3 三处相对 CC 的改进

**① `last_attempt` + `last_status` + `runs` + `last_error`。** CC 只有
`lastConsolidatedAt`，「连续五次在同一处崩溃」完全看不见。现在设置页能直接
显示「已跑 6 次 · 上次失败 · 原因：超过 300s 未完成」。

**② Phase 4 拆成 `index_pending` 标记。** Phase 3 一成功就推
`last_consolidated` 并置 `index_pending=1`；索引重建成功后清零。
被 kill 在重建之前时，下一轮巡检**只补重建**（不调模型，几毫秒），
不用重跑整个 Phase 3（几十秒）。方案 §4.6 ③ 明确说这是改进而非对齐：
CC 是 CLI、重启频率低；Web 服务部署/OOM 频繁得多。

**③ 索引重建由代码做，不由模型做。** 模型无论有没有动文件，`run_phase4`
都会跑一遍 `ms.rebuild_index()`。理由：模型写的 markdown 索引格式不可靠
（容易把正文搬进去），而重建是幂等的、很便宜。

### 11.4 「先写后删」是代码级闸，不只靠提示词

`memory_delete` 在**本次 dream 一条都没写成功**时直接拒绝：

```python
if budget.writes == 0:
    return {"outcome": "refused", "note": "先 memory_write 合并，再删"}
```

prompt 里已经写明顺序，但「内容真的丢了」不可逆，不能只靠 prompt。
`budget.writes` 由 `_wrap_write_counter` 统计，**只有 `outcome == "ok"` 才 +1**
（冲突/超配额不算写了）。另有 `HLZ_MEMORY_DREAM_MAX_DELETES`（默认 20）
防模型「大扫除」。

三条关键信息（姓徐 / 不喜欢全名 / 叫老徐）全在，相对日期变成了「此前」。
**「条数下降」必须同时满足 `content_preserved` 才算通过** —— 一个「删了但没合并」
的实现也能让条数下降，那是数据丢失不是整理。

**幂等复验**（同一用户连点两次）：第一次 `written=['dup-x'] deleted=['dup-y']`，
第二次 `written=[] deleted=[] index_rebuilt=True`，`runs=2`。没有重复动作、
没有报错。

**后台巡检链路复验**：以 `DREAM_MIN_HOURS=0 DREAM_MIN_SESSIONS=1
DREAM_SCAN_INTERVAL=15` 重启，预置 3 条重复记忆 + 1 个会话，不调 API，
等巡检自然跑到该用户 —— `p-1.md` 保留（含哨兵 `PATROL_SENTINEL`），
`p-2`/`p-3` 被合并删除，`MEMORY.md` 索引 1 行与磁盘一致。

**启动收敛复验**：手工把 `lock_pid=999999 / lock_at=现在 / last_status=running`
写进 DB（即「进程已死但锁还很新」），重启后端 —— 日志出现
`[dream] 启动收敛：1 个用户的状态被清理（server restart）`，
DB 变成 `lock_pid=0 / last_status=interrupted / last_error='server restart'`，
`index_pending` 保留等待补建。**这证明它不是靠 30 分钟过期。**

### 11.6 前端

设置页「我的记忆」tab 新增 dream 区块（`.memory-dream`）：状态说明
（「每 24 小时且期间有 5 个会话活动时自动整理一次」）、「立即整理」按钮、
状态标签（上次整理时间 / 上次失败 / 上次被中断 / 索引待重建 / 已跑 N 次）、
执行结果（写入几条、删除几条、索引是否重建、耗时）。

「立即整理」用**独立**的 `dreaming` 状态，不复用保存/删除的 `busy`：
它可能跑几十秒，共用 busy 会让所有按钮变灰，用户以为界面卡死。

**⚠️ 本区块未做 Playwright 截图验证** —— 与 M1–M3 的 `MemorySection`
同样只过了 `npm run build` + `tsc --noEmit`。L3 判据里这只到「机制已触发」，
不能声称「用户能看到」。

# 模型名改为端点真实发现（去除前端硬编码）

> 日期：2026-11-12 ｜ 状态：已实施并通过三层验证
> 起因：hx 在湛卢网关下选了「qwen3-max」→ 403「权限不足，无法访问该资源」

## 1. 问题与根因

设置页的「模型名」下拉，选项来自前端硬编码的 `MODEL_PRESETS`：

```ts
const MODEL_PRESETS = ['deepseek-v4.1-flash', 'qwen3-max', 'glm-4.6', ...]
```

这些是**厂商短名**，不是任何具体网关的模型 ID。湛卢网关的 `/models` 返回 34 个模型，
全部带前缀（`moma/qwen3.7-max`、`zhanlu/deepseek-v4-pro`），**`qwen3-max` 一个都不存在**。

网关对「不存在的模型 ID」的响应是 **403 + 「权限不足，无法访问该资源」**——
措辞把「模型名不存在」伪装成「key 没权限」，极具误导性。这也是排查花了很久的原因：
单向怀疑 key，实际改对模型 ID 后立刻恢复。

**结论**：模型名是端点的事实，不是前端能猜的常量。必须来自端点自己的 `/models`。

## 2. 设计

### 2.1 后端：端点探测

`backend/app/model_discovery.py`（新建）

```python
async def list_remote_models(base_url: str, api_key: str) -> dict[str, Any]:
    """永远不抛异常，返回 {ok, models, error, hint, endpoint}"""
```

- **URL 候选**：`{base}/models`，若 base 不以 `/v1` 结尾再试 `{base}/v1/models`，去重保序。
- **形状兼容**：`{"data":[...]}` / `{"models":[...]}` / `{"result":[...]}` / 裸数组；
  每项取 `id` → `model` → `name`，去重排序，忽略 `null` / 数字 / 空串。
- **鉴权失败快速返回**：401/403 不再试其它前缀，直接给可读 hint
  （「该端点拒绝 /models 查询或权限或路径不对…可直接手填模型 ID」）。
- **200 但无模型 = 失败**：端点回了空列表也不是成功，不能给用户一个空下拉。
- **永不抛异常**：网络错误也转成 `{ok: false, error: "ConnectError: ..."}`。

### 2.2 后端端点

`POST /api/me/llm-models-probe`（`backend/app/routers/me.py`）

- 入参 `ProbeModelsIn { base_url, api_key, config_id }`。
- **编辑既有配置时前端不回传 key**（只显示掩码）→ 允许用 `config_id` 取库里的原值，
  但强制 `get_llm_config(user["id"], ...)` 按 user_id 隔离，防越权取他人 key。
- 出参 `ProbeModelsOut { ok, models[{id, owned_by}], error, hint, endpoint }`。

### 2.3 前端：下拉即发现

`frontend/src/components/SettingsModal.tsx`

- **删除 `MODEL_PRESETS`**，`emptyLlm.model` 从 `'deepseek-v4.1-flash'` 改为 `''`。
- 下拉选项按优先级合成：① 端点真实列表 ② 用户已保存配置里出现过的模型名 ③ 当前表单值；
  末尾固定一个「自定义模型 ID…」允许手填（端点不支持 `/models` 的兜底）。
- **自动探测三条触发路径**（都不用先知道要点按钮）：
  1. key 输入框**失焦** → 立刻探测（鼠标去点下拉的那一刻就发出去）
  2. 下拉 `onFocus` / `onMouseDown` → 兜底（部分环境点 select 不触发 focus）
  3. 输入停顿 700ms → 防抖预取
- **同一 `(base_url, api_key, editingId)` 组合只探测一次**（`probedRef` 指纹），
  避免用户反复点开下拉反复打端点（实测 `/models` 耗时 0.45–4.4s）。
- ~~自动探测失败静默~~ → **已改：失败必须可见**。第一版对自动探测失败静默处理，
  结果端点没加载 / 走到旧后端时代理 404 时，用户只看到几条旧选项、完全不知道列表没拉全
  （实测就是这样被误判成「只能识别 3-4 个模型」）。
  现在任何失败都显示 `HTTP 4xx + hint`，用户能立刻知道是 key / 路径 / 端点的问题。
- **失败不钉指纹**：只有探测成功才记录 `(base_url, key, editingId)` 指纹，
  失败允许下次重试（否则一次抖动就永久锁死，再也不自动拉取）。
- **换 Base URL 立刻清空旧列表**：否则会把 A 家的模型名存进 B 家的配置。
- **保存校验**：模型名为空直接拦下并提示（以前能存下去，到对话才炸且报错位置很远）。
- 当前填的值不在真实列表里时，显示「实际调用会被拒绝」的警告。

### 3.4 一个真实踩坑（已修）

第一版只在 `onFocus` 触发探测，headless Chromium 下点 select 不一定触发 focus，
且 `/models` 要 0.5–4s，用户「点开下拉时列表还是空的」——即使数据最终到了，
下拉弹层打开期间浏览器不会重绘 option，用户看到的仍是空列表。
**修法**：把触发提前到 key 输入框失焦（鼠标移向下拉的路上），
并补 `onMouseDown` 兜底 + 700ms 防抖预取。

## 4. 未纳入 / 已知限制

- **不做自动改写旧配置**：库里已经存了短名的配置（如 hx 的 `qwen3-max`）不会自动修，
  需要用户在设置里重新选一次。理由：自动改模型名等于替用户选择，且没有唯一正确答案
  （`moma/` 与 `zhanlu/` 是两套不同的路由）。可在下拉里看到警告提示后自行改。
- **端点不支持 `/models` 时**（部分自建网关）：下拉只剩「自定义模型 ID…」，需手填。
  这是有意的降级——猜测名字比手填更糟。
- **探测结果不缓存到库**：每次打开设置页重新查。当前 `/models` 实测 0.45–4.4s，
  有 700ms 防抖 + 指纹去重；若将来端点变慢可考虑加 TTL 缓存。
- **`/models` 无鉴权也可查**：部分网关的 `/models` 不需要 key，此时前端仍要求
  先填 key 才自动探测（`form.api_key || editingId` 守卫）。保守做法，避免
  未配置时打开设置页就发探测请求。

## 6. 前情关联

hx 的 403 是本次的直接触发：配置 `model='qwen3-max'`（前端硬编码短名），
网关真实 ID 是 `moma/qwen3.7-max`。当时手工改库 + 重启修好，
同时发现 **runtime 缓存键 `(user_id, model_id)` 不含配置版本** ——
但那只是绕开 API 直接改库才会遇到的路径；走设置页保存会调用
`hub.invalidate(user_id)`，无需重启。本次未改动该缓存机制。

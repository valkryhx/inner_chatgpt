### 1.1 关键约束：不动 `_event_stream`

设计阶段核出 A2A 直接调用 `chat._event_stream`（`a2a/service.py:193`），且 A2A 自己
就是 `asyncio.create_task`（`service.py:273`）。若把 `_event_stream` 改成「建 job 返回
订阅流」，A2A 会被套两层 job 且 `_parse_frame` 全部失配。

所以解耦包在 `guarded_stream`（只有一个调用方）外层：

```text
guarded_stream()                                  # StreamingResponse body = 订阅者
   └─ job = start_job(...)                        # job 跑真正的生成
        └─ async for chunk in _event_stream(...)  # 原样不动
```

`test_a2a_still_consumes_raw_event_stream` 钉住签名与 async-generator 性质。

### 1.2 `register_generation` 必须在 job 任务里

`cancel_generation` 读 `_generation_tasks[key]`，值来自 `asyncio.current_task()`。
登记成请求任务的话，请求一返回任务就 finished，`/stop` 取消不到正在跑的生成 ——
**停止按钮会变成没反应**。

而前端的停止逻辑（`App.tsx:457`）是「本地置 stopped + abort + 调 `/stop`」三件并行：
解耦后 abort 不再杀 job，**停止的及时性全压在 `/stop` 上**，所以这一条从「值得注意」
升级成「必须钉住」。

### 1.3 上界

| 项 | 值 | 理由 |
|---|---|---|
| 单订阅者排队字节 | 4 MB | 超了只关这一个订阅者，不丢别的订阅者的内容 |
| 单 job 订阅者数 | 8 | 双标签页 + 余量 |
| 无订阅者的 job | **不杀** | 用户关标签页 ≠ 取消任务；结果照常落库 |
| job 生命周期 | 跟生成走，`finish()` 即摘表 | 不做额外 TTL —— 它本来就随生成结束而消失 |

### 2.3 两处测试缺陷（变异测试抓出来的，值得记下）

**① M2 漏过：断言命中了 `unregister_generation` 的子串**

原断言是 `"register_generation" in runner_body`。但 `unregister_generation` 也含
这个子串，所以把真正的 `register_generation` 挪走、只留 `unregister` 也能通过。

修法：匹配调用形态 `"register_generation(user[" in ...`，并加一条反向断言
「runner 之外不得出现该调用」。另补一条**运行时**测试直接比对 task 身份。

**② M4 漏过：`get_job()` 自己按 `finished` 过滤**

原断言是 `get_job(...) is None`。但 `get_job` 内部就有
`if job.finished: return None` —— 只要 `finish()` 设了 `finished` 标志，即使从表里
没摘掉也返回 None。测的是「不可见」，不是「已删除」。

修法：直接查 `_JOBS` 字典本身。

**这两条是同一类错误：断言落在一个会「自己变绿」的代理指标上。** 变异测试的价值
就在这里 —— 单看测试全绿完全看不出来。

## 3. 三个探针 bug（都是「诊断错误」而非产品缺陷）

真机验证花了三轮才拿到干净结论，三次都是探针自己错：

**① `taskkill //PID` 从 Python 调用时静默失败**

`//PID` 是 Git Bash 的转义写法，只在 bash 里才会被转成 `/PID`。从 Python
`subprocess.run` 直接调用时，taskkill 收到 `//PID` 不认，返回非 0，而我丢弃了输出。
结果旧进程根本没死，「重启后仍是 streaming」看起来像缺陷。

**② 生成太快，杀进程时已经跑完**

deepseek-flash 实测 6000 字约 3 秒。第一版有 `await asyncio.sleep(3)` —— 正好等于
生成时间，杀的时候已经 `complete`。第二版改成断开立即杀，仍然失败，因为
`Get-NetTCPConnection` 这个 PowerShell 查询**本身要 1-2 秒**，查完再杀又晚了。
最终版把 PID 查询提到生成开始之前。

**③ 「3 秒后应仍是 streaming」的断言本身没有意义**

最初我 `await asyncio.sleep(3)` 后断言 `status == "streaming"`。这只是假设模型
还没写完，不是产品性质。改成立刻采样。

**教训**：真机探针对时序的假设必须显式，而且「失败」先怀疑探针——这三次全部是探针问题
（与第二步那次「`t.cancel()` 把崩溃做成了用户停止」同类）。

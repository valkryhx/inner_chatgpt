# 沙箱 MVP 设计与实施（分步骤）—— Sandbox Manager + 两用户容器 + 工具分流

> 日期：2026-11-18　状态：**设计待实施**　分支：`feat/sandbox-mvp`
> 上游讨论稿：`docs/20261118-与gpt讨论沙箱.md`（含附录 A：CC 源码调研结论回灌）
> 前序方案：`docs/20261111-code_run容器隔离方案.md`（**暂不实施**，本方案是它的 MVP 落地版）
> 相关调研：`docs/20261112-Anthropic沙箱方案调研与多租户适用性.md`、`docs/20261112-gVisor多租户沙箱调研.md`

## 0. 一句话

**在 `backend/app/sandbox/` 新建一个进程内的 Sandbox Manager（Python，不引外部服务），
用已可用的 Alpine + Python 镜像为 2 个用户各起一个常驻容器，把 `code_run` 与「文件写」类工具
按白名单分流过去，其余工具（Skill / MCP / 记忆 / 记忆读侧 / 团队编排）继续进程内调用。
用 `HLZ_SANDBOX_MODE` 三档开关控制，默认 `off` 时行为与现在完全一致。**

## 2. 铁律（本 MVP 不可违背）

沿用项目 `AGENTS.md` §0 的八条，另加本次四条：

1. **默认关闭，且关闭时行为逐字节一致。** `HLZ_SANDBOX_MODE` 默认 `off`，
   `off` 时 `_run_code_impl` / `_write_impl` / `_patch_impl` 的代码路径与现在**完全相同**。
2. **绝不静默降级。** 容器不可用时：要么明确失败（`strict`），要么降级并在**工具结果里写明**
   「本次未隔离」（`auto`）。不允许"看起来成功了但没隔离"。
3. **身份不由模型决定。** `user_id` 只来自服务端认证上下文，**不能**来自工具参数；
   不接受模型传 `container_id` / `sandbox_id`。
4. **不破坏既有契约。** `code_run` / `file_write` / `file_patch` 的工具名、参数 schema、
   返回文本格式不变；SSE 事件名不变。

## 3. 目标与非目标

### 3.1 目标（MVP 的 DoD）

| # | 目标 | 验收判据 |
| --- | --- | --- |
| G1 | Sandbox Manager 可独立启停 | `sandbox/manager.py` 能探测 Docker、按需起 2 个容器 |
| G2 | 两用户容器物理隔离 | 用户 A 容器内读不到 `workspaces/u_B`、`app.db`、`.env`、宿主 D 盘 |

| G5 | 其余工具不走容器 | `load_skill` / `file_read` / MCP / 记忆 / 团队编排行为**零变化**（回归测试钉住） |

### 3.2 非目标（明确不做，避免范围蔓延）

- ❌ **不做 gVisor / Firecracker**（你的决定；M4 再说）
- ❌ **不做每会话一容器**（每用户一容器，与 `workspaces/<user_id>/` 对齐）
- ❌ **不做镜像依赖补齐**（Alpine + Python 现成镜像，能力收窄已知并接受）
- ❌ **不做网络白名单代理**（沿用 `--network none`；需要时的逃生口见 §6.4）
- ❌ **不做前端可视化**（复用现有工具步骤 UI）
- ❌ **不做 A2A / subagent / team 的独立容器**（它们继承 root 的容器）
- ❌ **不做持久化卷 / MinIO**（workspace 是 bind mount，本来就是宿主目录）

## 5. 工具分流设计（本 MVP 的核心决策）

### 5.1 哪些工具走容器、哪些不走

你要求「按照划分，该走 sandbox 就走 sandbox，不走 sandbox 的工具继续普通方式调用」。
划分依据只有一条：**这个工具的语义是否等价于「在用户的工作目录里执行任意代码/任意文件操作」**。

| 工具 | 走容器 | 依据 |
| --- | --- | --- |
| `code_run` | ✅ **必须** | 执行任意用户代码，是隔离的第一优先级 |
| `file_write` | ✅ **是** | 落盘路径若在容器内，必须与 `code_run` 看到的是**同一个 workspace**，否则两套视图会造成"写了但跑不到" |
| `file_patch` | ✅ **是** | 同上，它是写的变体 |
| `file_read` | ❌ 不走 | **读 Skill 目录 + 读仓库**是产品既有能力（§8.2 论证），容器里没有这些挂载点。读路径已由 `safe_read_path` 约束，风险面小于执行面 |
| `file_glob` / `file_grep` | ❌ 不走 | 与 `file_read` 同源（`file_search.py`），只读、有预算层 |
| `list_files` | ❌ 不走 | 只读目录，且 agent 需要看到 workspace 全貌 |
| `load_skill` | ❌ 不走 | 读 `skills_builtin/` / `skills_shared/` / `skills/<uid>/`，都在宿主 |
| `memory_*` | ❌ 不走 | 走 `memory_store.py`（文件 + DB 索引），与执行环境无关 |
| MCP 工具 | ❌ 不走 | 外部 server，本来就在平台进程里 |
| 团队/子代理编排工具 | ❌ 不走 | 纯编排，不碰用户代码 |

**为什么不把读类也搬进容器**（这是最容易做错的地方）：

1. **容器里没有 Skill 目录和仓库**。`safe_read_roots()` 允许读 `skills_builtin/`、`skills_shared/`、
   用户私有 skills、以及项目仓库（`20261111-workspace沙箱逃逸修复方案.md` §3.3 论证过为什么把仓库
   暴露进 workspace 是错误的）。要把这些全挂进容器 = 把半个宿主挂进去，隔离就白做了。
2. **读的风险面显著小于执行面**。读越权是信息泄露（严重），执行越权是**主动拿控制权**（更严重）。
   MVP 先堵执行面，读面沿用现有 `safe_read_path` + 后续单独一期。
3. **CC 也是这么分的**（`docs/20261118-CC沙箱机制调研.md` §2）：它的沙箱只包 Bash，
   Read/Write 走权限系统。**但注意反面**：CC 有权限系统兜底，而本项目 `run_guard.py` 的审计
   一行 `subprocess` 就能绕——所以**写类必须跟 `code_run` 一起进容器**，否则容器被
   `file_write` 写出容器边界（写到宿主绝对路径）就形同虚设。

> **一句话**：`code_run` 进容器是为了「关住执行」，`file_write`/`file_patch` 跟着进是为了
> 「不让写操作从旁边绕过去」。读类留下是因为它的收益（agent 能用）大于风险。

### 5.2 分流在哪一层实现（避免散开）

**唯一判定点：`sandbox/policy.py` 的 `should_use_sandbox(tool_name, user_id)`。**
所有装配点只问这一句，不各自判断（教训来自记忆 M5 缺陷：判据散开必漏一处）。

```python
# backend/app/sandbox/policy.py（示意，实施时按此写真实代码）
SANDBOXED_TOOLS = frozenset({"code_run", "file_write", "file_patch"})

def sandbox_enabled() -> bool:
    """总开关：off / auto / strict。"""
    return _MODE != "off"

def should_use_sandbox(tool_name: str, user_id: str) -> bool:
    """这个工具、这个用户，本次调用是否走容器。"""
    if not sandbox_enabled():
        return False
    if tool_name not in SANDBOXED_TOOLS:
        return False
    return _user_in_mvp_scope(user_id)   # MVP：白名单 2 个用户
```

### 5.3 三档开关的语义（`HLZ_SANDBOX_MODE`）

| 档位 | 容器可用时 | 容器不可用时 | 用途 |
| --- | --- | --- | --- |
| `off`（默认） | 不用容器 | 不用容器 | 与现在完全一致；全量回归基线 |
| `auto` | 走容器 | **降级进程内 + 工具结果写明「未隔离」** | 开发/灰度 |
| `strict` | 走容器 | **直接失败**（不降级） | 生产/验证隔离 |

`auto` 的降级必须留痕（铁律 2）：工具结果首行加
`[sandbox] 本次未隔离：<原因>（当前模式 auto）`，并写一条 `logging.warning`。

### 5.4 用户范围（MVP 只 2 个）

```bash
HLZ_SANDBOX_MVP_USERS=u_c56b8337dd09,u_343a46896bff   # hx, xh；逗号分隔；空 = 全部（不推荐）
```

- **为什么不是全部 241 个**：MVP 要能"只影响两个人"，其余 239 人行为零变化，出问题影响面可控。
- **留好升级路径**：把白名单判据换成「全部」即全量上线，其它代码不动。

## 6. Sandbox Manager 架构

### 6.1 目录与职责

```
backend/app/sandbox/
├── __init__.py
├── config.py      # 环境变量 + 默认值（镜像、TTL、上限、超时、模式、白名单）
├── policy.py      # 唯一分流判定点（§5.2）
├── probe.py       # 启动自检：docker 可达？镜像存在？cgroup 可用？
├── runtime.py     # 单容器生命周期：ensure / exec / stop / destroy
├── pool.py        # 每用户注册表 + 懒创建 + TTL 回收 + 全局上限 LRU
├── manager.py     # 对外唯一门面：exec_code / write_file / patch_file / stop / shutdown
└── errors.py      # SandboxUnavailable / SandboxExecError / SandboxTimeout
```

**为什么分成 7 个文件而不是 1 个**：`runtime`（怎么用容器）与 `pool`（管几个容器）
是两件会各自演化的事，混一起会导致"改 TTL 逻辑必须动 exec 代码"。这是
`20261111` 方案 §3.7 已经定下的划分，本 MVP 沿用。

### 6.2 生命周期

```
工具调用（should_use_sandbox == True）
   │
   ├─ manager.exec_code(user_id, ...)
   │
   └─ pool.acquire(user_id)
        │
        ├─ 该 user 有 live 容器？── 是 ──> 更新 last_used ──> 返回
        │
        └─ 否
             ├─ 全局数量已达 SANDBOX_MAX_CONTAINERS？── 是 ──> LRU 淘汰一个（destroy）
             └─ runtime.create(user_id)（docker run -d）
                  └─ 失败 ──> auto: 降级进程内 / strict: 抛错
```

**参数默认值**（`config.py`，全部可用环境变量覆盖）：

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `HLZ_SANDBOX_MODE` | `off` | `off` / `auto` / `strict` |
| `HLZ_SANDBOX_IMAGE` | `python:3.12-slim` | 已定（§4.1 实测） |
| `HLZ_SANDBOX_IDLE_TTL_S` | `900` | 空闲 15 分钟销毁 |
| `HLZ_SANDBOX_MAX_CONTAINERS` | `4` | MVP 只 2 用户，留一倍余量 |
| `HLZ_SANDBOX_CREATE_TIMEOUT_S` | `30` | 创建超时 |
| `HLZ_SANDBOX_EXEC_TIMEOUT_S` | `120` | 单次 exec 上限（工具自身 timeout 更小时取小） |
| `HLZ_SANDBOX_MVP_USERS` | 空 | 逗号分隔白名单 |

### 6.3 镜像与容器规格

**镜像**：用本机已可用的 Alpine + Python 镜像（`HLZ_SANDBOX_IMAGE` 指定，默认 `python:3.12-alpine`
或本地已有的等价 tag）。**不含 matplotlib / pandas / docx** —— 这是已知能力收窄（§9.2）。

**容器启动参数**（沿用 `20261111` 方案 §3.2 + §3.6 的实测结论）：

```python
args = [
    "run", "-d", "--rm",
    "--name", f"hlz_sbx_{safe(user_id)}",
    "--label", "hlz.sandbox=1",                    # 便于启动时清扫残留
    # 隔离
    "--network", "none",
    "--cap-drop", "ALL",
    "--security-opt", "no-new-privileges",
    # 资源
    "--memory", "1g", "--memory-swap", "1g",
    "--cpus", "1",
    "--pids-limit", "256",
    # 文件系统：只挂该用户 workspace
    "-v", f"{user_workspace(user_id)}:/ws",
    "--tmpfs", "/tmp:size=256m,mode=1777",
    # 环境变量必须显式给全（Docker Desktop 会继承宿主 HOME）
    "-e", "HOME=/tmp", "-e", "TMPDIR=/tmp", "-e", "XDG_CACHE_HOME=/tmp/.cache",
    "-e", "PYTHONUNBUFFERED=1",
    "-w", "/ws",
    IMAGE, "sleep", "infinity",
]
```

> ⚠️ **Windows 上不加 `--user`**（`20261111` §3.5 实测：`--user 1000:1000` 会让 pip 报
> `Read-only file system: '/D:'`）。代价是容器内是 root，靠 `--cap-drop ALL` +
> `no-new-privileges` + `--network none` 约束。**部署到 Linux 时应恢复 `--user`**，这条写进 §9.1 风险。

**挂载边界（MVP 最重要的验证点）**：

- 只挂 `workspaces/<user_id>/` → `/ws`
- **不挂** `backend/`、`backend/data/`、项目仓库、宿主家目录
- 于是容器内 `/ws/../app.db`、`/d/git_codes`、`/c/Users` 全部 `No such file`（`20261111` §4.3 已实测）

### 6.4 网络策略（MVP）

`--network none`。后果与对策：

| 场景 | MVP 行为 | 对策 |
| --- | --- | --- |
| 纯计算 / 文件处理 | ✅ 正常 | — |
| `pip install` | ❌ 失败（无 DNS） | MVP 明确不支持；需要时走 §9.2 的镜像补齐，或后续开白名单代理 |
| 访问内网/公网 | ❌ 不可能 | 这是 MVP 的安全收益，不是缺陷 |

**不做「临时开网」参数**。理由：那等于给模型一个绕过隔离的开关，与铁律 3 冲突。
真需要联网时应该走「受控代理 + 域名白名单」（CC 的做法），那是独立一期。

### 6.5 停止与回收

| 场景 | 行为 | 实现 |
| --- | --- | --- |
| 用户点 `/stop` | 终止容器内进程，**不销毁容器** | `docker exec <cid> sh -c 'pkill -f <marker>'`；3s 后仍活则 `docker kill` → 重建 |
| 单次 exec 超时 | 同上（杀该次进程） | exec 内包 `timeout`，或 exec 后 pkill marker |
| 空闲 TTL | `docker rm -f` | 后台协程每 60s 扫一次 |
| 后端重启 | 清理所有 `hlz.sandbox=1` 残留容器 | `probe.cleanup_orphans()`（lifespan 启动时） |
| 应用关闭 | 全部销毁 | `manager.shutdown()` 挂 lifespan |

**进程标记法**：每次 exec 传 `marker=<uuid>` 环境变量，pkill 按 marker 精确匹配，
避免误杀同容器里其它会话的进程（同用户多会话共享容器，`20261111` §2.3 已承认）。

### 7.2 `file_write` / `file_patch` 的接缝

```python
async def file_write(args):
    path = str(args.get("path", ""))
```

**必须保住的语义**（逐个核对，漏一个就是回归）：

| 语义 | 现状实现 | 容器内如何等价 |
| --- | --- | --- |
| 路径越界拒绝 | `safe_workspace_path` → `_resolve_under` | 容器内路径同样要校验；**但校验仍在宿主进程做**（不能用容器内的路径判定当作安全保证） |

| 子代理写根隔离 | `root=".subagents/<session>/<agent>"` | 映射到 `/ws/.subagents/...`，同一套相对路径逻辑 |
| 返回文本格式 | `_write_impl` 的固定文案 | 必须一致 |
| 文件模式权限 | `mode` 参数 | 容器内 root 写，文件属主会是 root；**已知差异**（§9.1 记录） |

> ⚠️ **最容易做错的一点**：不要以为「在容器里跑 `cat > /ws/x` 」就等于隔离了。
> 路径校验必须在**宿主进程**做（`safe_workspace_path`），容器只负责执行。
> 容器内再校验是纵深，不是替代。

## 10. 实施细节补充（容易踩的坑，先写下来）

### 10.1 `code_type` 在容器内的映射

现有 `_run_code_impl` 支持 `python` / `powershell` / `bash` / `sh` / `shell`。容器内：

| `code_type` | 容器内可行？ | 方案 |
| --- | --- | --- |
| `python` / `py` | ✅ | `python -u /tmp/<uuid>.py`（脚本经 stdin 或挂载传入） |
| `bash` / `sh` / `shell` | ✅（Alpine 有 `sh`，**可能没有 bash**） | 统一用 `sh -c`；若镜像有 bash 则优先 bash |
| `powershell` / `ps1` / `pwsh` | ❌ Alpine 无 | **明确报错**：`[sandbox] powershell 在沙箱内不可用，请改用 python 或 sh` |

**不要把不支持的类型静默降级成 python** —— 那会让用户拿到错误的执行结果。

**脚本传递方式**（两个选择，实施时二选一）：

- **A. 写入 workspace 临时文件**：`/ws/.tmp/<uuid>.py`，执行后删除。简单，但会在用户 workspace 留痕。
- **B. stdin 传入**：`docker exec -i <cid> python -u - < /tmp/xxx`。不留痕，但要处理 stdin 编码。
- **推荐 B**，因为 A 会污染用户的 `list_files` 结果（且 `/ws/.tmp` 需要额外清理逻辑）。

### 10.1.1 脚本传递方案的实测结论（2026-11-18，四次试错后定稿）

> 本节是**实测记录**，不是设计推演。四种方案在同一环境（Docker Desktop 4.37.1 /
> Windows / `python:3.12-slim`）逐个试过。

| 方案 | 结果 | 具体现象 |
| --- | --- | --- |
| `containers.run(exec_run, stdin=True)` + 写 socket | ❌ | 返回的 socket 是**输出**通道；写入 stdin 后读输出阻塞到超时 |
| 低层 `api.exec_start(socket=True)` | ❌ | 本机拿不到可写句柄：输出为空、`exec_inspect` 的 `ExitCode = -1` |
| `put_archive` 写容器内 `/tmp`（tmpfs） | ❌ | **返回 `True` 但文件不存在**：`ls -la /tmp` 为空。tmpfs 上的 archive 解包在 Docker Desktop 上失效 |
| **写宿主 workspace 下的 `.hlz_tmp/`（bind mount 双向可见）** | ✅ | exec 94~109 ms，输出/退出码/stderr 全部正确 |

**最终实现**（`runtime.exec_python`）：

1. 在**宿主** `workspaces/<user_id>/.hlz_tmp/` 下写 `.py`（`newline="\n"`）；
2. 容器内经 bind mount 读同一文件：`/ws/.hlz_tmp/_hlz_<uuid>.py`；
3. `python -u` 执行，输出按 UTF-8 `errors="replace"` 解码（与进程内路径一致）；
4. `finally` 里**在宿主侧删文件**（不依赖容器内 `rm`，超时/取消也能清掉）。

**为什么不用容器内 `/tmp`**：本机实测 tmpfs 传不进去（上表第三行）。
如果换到纯 Linux 宿主，`put_archive` 到 tmpfs 是可用的，但 MVP 以本机为准，
且 workspace 方案在两种宿主上都成立——**选它是因为它跨平台一致**。

**代价**：`.hlz_tmp/` 会短暂出现在用户的 `list_files` 里。
项目既有惯例已用 `.` 前缀表隐藏（`.subagents` / `.tmp`），且正常路径在 `finally` 删干净；
超时/崩溃路径由 `pool.reap_idle()` 兜底清扫。

### 10.2 输出解码与预算

现有进程内路径：`(stdout or b"").decode("utf-8", errors="replace")`，然后走
`_with_budget(user_id, "code_run", raw)`。

容器模式必须**完全一致**：
1. `docker exec` 的输出同样按 UTF-8 解码（`errors="replace"`）
2. 同样经过 `_with_budget`（不能在 manager 里另做一套预算）
3. `format_code_run_header` 的 `exit_code` 要拿到容器内进程的真实退出码
   （`docker exec` 的返回码 = 容器内进程退出码，可直接用）

### 10.3 临时文件清理

- 进程内模式用 `tempfile.mkstemp` 写宿主 `/tmp`，`finally` 里删。
- 容器模式如果用 A 方案（写 `/ws/.tmp`），必须在 `finally` 里 `docker exec rm`，
  且**即使 exec 超时/取消也要删**。B 方案（stdin）没有这个问题。
- **额外的坑**：容器是常驻的，如果清理失败，`/ws/.tmp` 会累积。建议
  `pool.reap_idle()` 时顺带清一次 `/ws/.tmp`。

### 10.4 与 `process_registry` 的关系

`ProcessLease` 是进程内停止机制。容器模式需要平行的 `ContainerLease`：

```python
# 关键：/stop 时要能找到"这个 user 的这个 session 正在跑的那次 exec"
class ContainerLease:
    user_id: str
    session_id: str
    generation_id: str
    agent_id: str
    container_id: str
    marker: str        # uuid，用于 pkill 精确匹配
    started_at: float
```

`ProcessLease` **不删除**（`off` 模式还要用）。两者并存，由 `policy` 决定用哪个。

### 10.5 后端重启后的残留容器清扫

后端崩溃时容器可能还活着（`--rm` 只在容器正常退出时生效）。启动时：

```python
# probe.cleanup_orphans() —— 挂在 FastAPI lifespan 启动阶段
for c in client.containers.list(all=True, filters={"label": "hlz.sandbox=1"}):
    c.remove(force=True)
```

**为什么按 label 而不是按名字前缀**：名字前缀可能与人手建的容器撞；
label 是本方案独占的命名空间，且 `docker ps --filter label=` 可查。

**注意**：如果将来支持多进程（`workers=N`），这里会**误杀别的 worker 的容器**。
MVP 是单 worker，安全；多 worker 时需要给 label 加 `worker_id`（记进 §9.3）。

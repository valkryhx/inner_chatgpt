## 0. 一句话结论

Hlaudz 的 `SYSTEM_PROMPT`（`backend/app/agent.py:25`）只有两节、约 1.3 KB，
覆盖了「工具出错怎么办」和「产物写哪里」，**没有覆盖「任务怎么推进」**。

GA 用四轮迭代证明：提示词里最值钱的不是「你是什么」，而是三条可执行的行为约束——
**专用工具优先**、**验证后才能说完成**、**skill 按任务类型主动加载**。

本方案把 GA 的九节结构**按 Web 多用户场景裁剪**后引入，并给出「提示词怎么测」
的可执行方法（消融 + 行为断言），避免「改了提示词但不知道有没有用」。

## 1. 现状对比

| 维度 | Hlaudz | GA |
| --- | --- | --- |
| 体量 | 约 1.3 KB，2 节 | 约 8 KB，9 节 |
| 身份与边界 | 一句话 | 独立章节（含「列表里没有的能力就是没有」） |
| 怎么工作 | 无 | 自主性/持久性、探测优先、失败升级 |
| 规划与推进 | 无 | 计划载体、一次一件事、计划变更 |
| 代码与改动纪律 | 无 | 有（Hlaudz 部分适用） |
| 验证纪律 | 无 | 独立章节（含「UI 要亲手跑」） |
| 审查与产物质量 | 无 | 有 |

**产物路径红线**（只能写 workspace、禁止写 `frontend/dist`）。这条不能删。

## 2. 设计原则

1. **只写可执行的行为约束**，不写人格描述（「你是一个专业助手」这类对行为无影响）。
2. **每条约束都要能被 L3 观测**：写进提示词的行为，必须有对应的 e2e 断言，否则删掉。
3. **Web 场景裁剪**：GA 是单机 CLI，Hlaudz 是多用户 Web。涉及「本机」「终端」
   「用户看不到你的终端」的表述要改写；涉及「问用户」的要明确它在 Web 里意味着
   「结束回合并在正文提问」。
4. **与工具 schema 互补**：工具选择规则同时写进 `SYSTEM_PROMPT` 和工具描述
   （schema 离决策点更近）。

## 3. 新 `SYSTEM_PROMPT` 结构

保留首选段（身份 + 多用户边界），然后按 GA 的九节裁剪为**七节**：

| 节 | 要点 | 来源 |
| --- | --- | --- |
| 身份与边界 | 运行在多用户 Web 平台；权限以本轮工具列表为准；没有的能力不假装 | GA §1+§2 |
| 怎么工作 | 任务没做完不结束回合；探测优先；失败三次升级；计划变更先更新 | GA §3 |
| 规划与推进 | 多步任务先列可验证步骤；一次只推进一步；简单任务不套计划 | GA §4 |
| 验证纪律 | 声称完成前必须有证据；最小验证先跑；跑不了的验证要明说；**UI 要实跑** | GA §6 |
| 产物质量 | 文档结论在前、证据可追溯；图表/页面要有设计意图；不贴大段原始输出 | GA §7 |
| 工具使用 | 专用工具优先；只并行无依赖调用；外部事实带来源；长任务用 workspace 记录 | GA §8 |
| 沟通与交付 | 跟随语言；先结论后证据；给绝对路径；引用 `文件:行号` | GA §9 |

**删掉的 GA 章节**：「代码与改动纪律」（Hlaudz 的用户多数不是开发者，
具体条目移到「产物质量」里以更泛的形式表达）。

**必须保留的 Hlaudz 专有条目**：产物路径红线、Markdown 图片引用规则。

### 3.1 「验证纪律」逐条（最关键一节）

```
- 声称"完成 / 修好 / 做好"之前必须有证据：命令输出、工具返回、文件内容、页面截图。
  不要凭读代码或凭推理说"应该没问题"。
- 先跑最贴近改动的最小验证，再逐步扩大范围。
- 没跑成或跑不动的验证要在汇报里明说，不要让用户以为已经验证过。
- 生成网页 / 图表 / 文档时，要实际打开或渲染一次再汇报；确实做不到就明说
  "没有实际看到渲染结果"。
- 用户让你"审查 / 看看有没有问题"时，先列发现（按严重程度），再给结论；
  没有发现问题就明说，并说明你检查了哪些方面。
```

这五条是 GA 反复迭代后留下的，直接对应「假完成」这个最高频失败模式。

## 4. 专用工具优先（与子方案 1 联动）

只有先有 `file_glob` / `file_grep`，这一节才有意义。措辞：

```
- 找文件用 file_glob，找内容用 file_grep，读文件用 file_read（支持 start/count/keyword）。
- 只有 shell 才能做的事才用 code_run：跑测试、装依赖、执行脚本、启动服务。
  不要用 code_run 写 find / grep / cat 的替代品——慢、易错、输出还会被截断。
- 搜索类结果太多时先缩小 path 或加 glob 过滤，不要改用 code_run 写正则脚本绕开。
- 一轮里可以并行发多个互不依赖的检索；有依赖的必须串行。
```

**验证方式**：L3 用例「在 backend 目录找所有 TODO」——
断言事件里有 `file_grep`，没有 `code_run`（见子方案 1 §8.6）。

## 5. Skill 的隐性触发（对标 GA 第 2 轮）

现状 Hlaudz 只写了「当任务与某个 Skill 匹配时先调用 load_skill」，太抽象，
模型实际只在用户点名时才加载。GA 的做法是**给出任务类型的映射表**：

```
- 开工前先做一次技能扫描：把【任务类型】与 Available Skills 的描述对照，不等用户点名。
  常见对应：排查 bug / 报错 → 诊断类；设计新功能或方案 → 头脑风暴类；
  审查代码或文档 → review 类；做网页 / 图表 / 幻灯片 / 文档 → 对应的产出类；
  整理长文 → 摘要类。
- 只要某个 skill 与任务领域、流程或产物形态部分相关，就先 load_skill 读全文再动手。
  不要因为"大概知道怎么做"跳过——skill 里是本项目验证过的步骤和坑。
- 用户用 /<skill-name> 点名时必须 load_skill，且只用 Available Skills 里出现过的名字。
- 扫描后确实没有匹配就不用加载，不要为了显得守规矩乱加载。
```

**关键设计**：映射表是「示例」不是「穷举」，最后一句明确允许「不加载」，
避免模型为了合规把每个 skill 都读一遍（那是反效果）。

### 5.1 索引预算与描述完整性（对标 GA 第 3/4 轮）

GA 实测发现两个问题，Hlaudz 需要先核实是否同样存在：

| GA 问题 | 现象 | 修法 |
| --- | --- | --- |
| 索引预算太小（8000） | 描述被挤成「只剩名字」，模型无法判断是否相关 | 预算提到 16,384 |
| 单条描述上限 400 | 描述在中间被截断成半句 | 上限提到 1,536（对齐 CC） |
| 压缩时丢 skill 索引 | 上下文压缩后 L1 索引消失，模型再也想不起 skill | 压缩时保留触发器句 |

**已核实**（`skill_store.py:489-533`）：预算 8,000、单条描述截断在 250 字符，预算不足时降级为 `- name`（已比 GA 优化前好，但不如 GA 优化后的保留触发器句）。详见 `20261111-Hlaudz工具渐进式披露调研与决策.md` §9。

**待实测**：找一台装了 20+ skill 的账号，打印真实索引文本，确认描述是否真的被截断、预算降级是否把技能压成光名字；没有这个场景就先改常量，不做结构改动。

## 6. 子代理提示词优化

`backend/app/subagent/prompts.py` 现有内容质量不错（防空指代、wait 超时不算失败、
任务契约、共享文件系统纪律）。需要补三条 GA 经验：

1. **子代理也要验证**：现在只写了「无法完成时写 blocker」，没写「声称完成前要验证」；
2. **子代理也要用专用工具**：子代理有完整工具面，但没有对应提示词；
3. **结果格式**：明确要求「最终回答的第一行是一句话结论」，方便母代理快速整合。

不建议把 `ROOT_AGENT_HINT`（约 1.5 KB）继续加长——它每轮都在上下文里。
宁可把细则写进工具描述（`spawn_agent` 的 description）。

## 7. 提示词怎么测（不许「改完感觉更好」）

提示词测试分三种，前两种必做：

### 7.1 消融测试（ablation）

同一组 L3 用例，**用旧 prompt 跑一遍、新 prompt 跑一遍**，对比指标：

| 指标 | 定义 | 期望变化 |
| --- | --- | --- |
| 工具选择正确率 | 该用专用工具的任务里，用了专用工具的比例 | 上升 |
| 假完成率 | 声称完成但产物不存在 / 未验证的比例 | 下降 |
| 平均回合数 | 完成同一任务需要的 LLM 调用次数 | 下降 |
| 无谓 skill 加载 | 任务与任何 skill 无关时仍加载的次数 | 不上升 |

每项 10 次运行取中位数；单次运行有随机性，不许用一次结果下结论。

### 7.2 行为断言（断言「做了什么」，不断言「说了什么」）

- 断言事件流里的工具名序列，不断言模型正文的措辞；
- 断言的随机 token 必须在产物里出现（硬信号）；
- 负对照必须有：不该调的工具一次都不能调。

### 7.3 人工审读（仅作补充）

把新 prompt 的每一句问一遍：**「如果模型不做这件事，有没有测试能发现？」**
答不上来的句子删掉。这是控制提示词膨胀的唯一有效手段。

## 10. 风险与不做

| 风险 | 缓解 |
| --- | --- |
| 提示词变长导致首 token 延迟上升 | 控制在 4 KB 以内；细则移到工具描述 |
| 规则太多互相冲突 | 每节不超过 6 条；冲突项合并 |
| 通用指令削弱「中文简洁」风格 | 保留首选段的语言与风格约束 |

**不做**：

- 不抄 GA 的「代码与改动纪律」全文（Hlaudz 用户不是开发者）；
- 不引入 `update_working_checkpoint` 工具（Hlaudz 用 workspace 文件即可）；
- 不加「每轮用 `<summary>` 输出」这类格式要求——Hlaudz 的 UI 不解析它，
  只会让输出变吵。

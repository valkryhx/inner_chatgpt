# A2A 中断现场（持久化第一步：可观测）

> 日期：2026-11-14　状态：**第一步已完成**（可观测）。第二/三步（续跑、事件流持久化）未开工
> 前序调研：`docs/20261114-LibreChat与Aivory的agent-runtime池化调研.md`

---

## 0. 结论

重启后 A2A 任务**不能只说「server restart」**。改造前后对比（真实库里的两条）：

```text
改造前：error = "server restart"                snapshot = {}
改造后：error = "任务被中断（server restart）：第 1 步，最后执行的是 code_run，
                 已成功执行 0 个工具，已生成 0 字。可以用同一 contextId "
        snapshot = {"steps":1,"tools_run":0,"last_tool":"code_run","partial_chars":0}
```

**这一版不恢复执行，只让中断说得清。** 恢复是第二步，需要这一步的现场作起点。

---

## 1. 为什么先做「可观测」而不是直接做「可恢复」

调研两个成熟项目（LibreChat / Aivory）后的判断：它们**都不持久化活的连接对象**，
持久化的都是**可序列化的状态**。这决定了改造顺序。

问题要拆成三层，混在一起谈会得出「加个 Redis 就行」的错误结论：

| 层 | 是什么 | 能否持久化 |
|---|---|---|
| ① 连接对象 | httpx client、MCP session、GA 子进程 | **永远不能**。活套接字，重启即死，只能重建 |
| ② 重建它所需的状态 | 用户配置、模型选择、MCP server 列表、skill | **已在 DB**，这块没问题 |
| ③ 正在跑的活的状态 | 跑到第几步、已生成什么、子代理在哪 | **部分在 DB**（消息内容 250ms 快照），但缺少「进度」维度 |

**「连接信息持久化」这个说法实际指向 ③，不是 ①。** 因为 ① 原理上做不到，② 已经做好了。

③ 里最便宜、风险最低、收益最直接的一步是：**把现场记下来，让中断可解释**。
它不改执行模型、不改 SSE 契约、不改任何现有状态机 —— 纯增量。

## 2. 实现

### 2.1 新增 `snapshot` 列

```sql
ALTER TABLE a2a_tasks ADD COLUMN snapshot TEXT NOT NULL DEFAULT '{}'
```

老库平滑升级（`init_tables` 里 `PRAGMA table_info` 判断后 ALTER，
与既有的 `tool_policy` 迁移同一手法）。**迁移前已备份 DB**
（`backend/data/_backup/app.db.20261114-223824`）。

存四个字段，每个都对应一个具体问题：

| 字段 | 回答什么问题 |
|---|---|
| `steps` | 跑了几个模型轮次 —— 重跑要花多少钱 |
| `tools_run` | 成功执行了几个工具 —— **有多少副作用真的发生了** |
| `last_tool` | 断在哪一步 |
| `partial_chars` | 已产出多少正文 —— 有多少可救 |

**不存每条文本增量**：正文已经在 `messages` 表按 250ms 落库，
这里重复存只会让表膨胀，重启后没有额外价值。

### 2.2 写入时机：工具边界 + 收尾各一次

```python
elif event == "tool_start":
    snap_steps += 1
    snap_last_tool = name
    snap_dirty = True
    await _flush_snapshot()
elif event == "tool_result":
    if not payload.get("is_error"):
        snap_tools += 1
        await _flush_snapshot()
```

**为什么在工具边界写，不每个 token 写**：正文由 `messages` 表负责，
这里补的是「进度」这个 `messages` 表没有的维度。写太频纯属浪费。

**为什么 `finally` 里还要再写一次**：工具边界那次算的 `partial_chars` 是**当时**的，
之后的正文增量还没算进去。异常退出时这一次尤其重要 —— 它就是能说出
「已生成多少」的唯一依据。这条是测试抓出来的：第一版只在工具边界写，
`test_run_task_writes_snapshot_at_tool_boundaries` 红了（`partial_chars=0`）。

**失败的工具不算 `tools_run`**：它没有产生副作用。但 `last_tool` 仍记它 ——
因为「最后试图做什么」也是有用的信息。`test_failed_tool_not_counted_as_run` 钉住这个区分。

### 2.3 恢复说明：有现场说现场，没现场说实话

```python
def _describe_interruption(snap, reason):
    if not snap:
        return (f"任务被中断（{reason}）：没有进展记录。"
                "无法确定已执行到哪一步，建议重新提交；"
                "如果上次可能已产生写入，请先自行核对结果。")
    ...
    if tools:
        parts.append("。注意：中断前执行的工具可能已经产生了实际影响"
                     "（文件写入、命令执行），重新提交前请先核对")
```

两个刻意的设计：

1. **没有现场时不许编造**。写「没有进展记录」，不是编一个「第 0 步」。
   测试用正则 `r"第\s*[1-9]\d*\s*步"` 禁掉任何伪造的步数。
2. **有工具执行过就提醒核对副作用**。这是「中断」与「失败」的关键区别：
   失败通常什么都没发生，中断可能已经写了一半文件。

### 2.4 恢复只动未完成的任务

`mark_interrupted_tasks` 的 WHERE 是 `state IN ('SUBMITTED','WORKING')`。
已 COMPLETED / CANCELED 的任务不能被改写 —— `test_recovery_only_touches_unfinished_tasks` 钉住。

## 3. 验证

### 3.1 L1（8 项，`backend/tests/test_a2a_interrupt_snapshot.py`）

| 测试 | 钉什么 |
|---|---|
| `test_snapshot_persisted_during_run` | 进展写进 DB，不是只活在内存 |
| `test_snapshot_survives_process_kill` | 换新连接能读到（模拟 kill -9，不做优雅关闭） |
| `test_restart_message_describes_progress` | 说明含步数 / 工具名 / 字数，且不再是裸 `server restart` |
| `test_restart_message_without_snapshot_is_still_honest` | 没现场时如实说，不编造 |
| `test_recovery_only_touches_unfinished_tasks` | 不碰已终态 |
| `test_snapshot_column_migrates_on_old_db` | 老库平滑升级、不丢行 |
| `test_run_task_writes_snapshot_at_tool_boundaries` | **接线**：service 层真的调了 `update_snapshot` |
| `test_failed_tool_not_counted_as_run` | 失败工具不算执行过 |

最后两条是「接线测试」：前几条测 store 层能力，这两条测 service 层**有没有用它**。
缺了它们，「加了 `update_snapshot` 但忘了调用」测试抓不到。

### 3.2 L3 真机（`work/_probe_persistence.py`）

流程：提交 90 秒任务 → 跑到第 1 步（`code_run`）→ 杀后端 → 重启 → 查。

**重启前**（直接查 DB）：

```json
{"steps": 1, "tools_run": 0, "last_tool": "code_run", "partial_chars": 0, "at": 1794667590844}
```

**重启后**（A2A GetTask）：

```text
state = TASK_STATE_FAILED
error = 任务被中断（server restart）：第 1 步，最后执行的是 code_run，
        已成功执行 0 个工具，已生成 0 字。可以用同一 contextId ...
```

**升级路径也验了**：把一条老任务（`snapshot='{}'`）改回 WORKING 再触发恢复，
得到的是「没有进展记录…建议重新提交」，**没有编造步数**。

### 3.3 页面侧对照（顺手确认，不是本次改动）

同一轮实测里也确认了：**网页侧的内容本来就不会丢** —— 每 250ms 落库，
重启后消息还在（`assistant.status` 由启动自愈收敛为 `stopped`）。

> 第一版探针在这里误报过「页面侧丢失 1 条 assistant」。根因是探针用了
> `time.sleep(12)` 阻塞事件循环，导致 fire-and-forget 的后台流压根没跑起来。
> 改成 `await asyncio.sleep(12)` 后正常。**测试自身的 bug 也是个需要排查的假设**。

### 3.4 全量

A2A 四个测试文件 46 项通过；后端全量 **1086 passed**。

| 独立项：RuntimeHub 上限 | 空闲过期 + 硬上限 | 见调研文档 §3 |

**第二步的关键缺口**：目前 `snapshot` 记的是「跑到第几步」，但**不知道那一步的 tool_call
有没有悬空**。续跑前必须确认最后那个 `code_run` 是否已执行完 —— 否则会重复执行副作用。
`agent_loop.sanitize_pending_tool_calls` 是现成的工具，但要先确认它在 A2A 路径上也被调用。

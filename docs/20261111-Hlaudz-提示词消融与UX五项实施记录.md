## 2. 消融实验怎么做的

### 2.1 变体开关

`app/agent.py`：

```python
_PROMPT_VARIANTS = {"new": SYSTEM_PROMPT, "legacy": SYSTEM_PROMPT_LEGACY}

def select_system_prompt() -> str:
    variant = (os.environ.get("HLAUDZ_PROMPT_VARIANT") or "new").strip().lower()
    return _PROMPT_VARIANTS.get(variant, SYSTEM_PROMPT)

def compose_system_prompt(skill_block: str = "") -> str:
    return select_system_prompt() + skill_block + "\n\n" + ROOT_AGENT_HINT
```

三个刻意的设计：

1. **env 在调用时读，不在 import 时读**。`build_user_model(system_prompt=SYSTEM_PROMPT)`
   这种默认参数会在 import 时冻结，切变体失效——所以改成 `compose_system_prompt()` 现算。
2. **未知值回落 new**：拼错变量名不会把生产拖回旧提示词。
3. **旧提示词单独成文件且注明「是基线，不许改」**，避免有人顺手优化掉对照组。

### 2.2 用例怎么设计（不测「聪明不聪明」，只测提示词里写死的那些约束）

| 用例 | 任务 | 判据 | 对应提示词条款 |
| --- | --- | --- | --- |
| `glob_only` | 列出工作区所有 .py | 必须 `file_glob`；**不许** `code_run` | 「找文件用 file_glob…不要用 code_run 写 find 的替代品」 |
| `grep_only` | 搜索含 TODO 的位置 | 必须 `file_grep`；**不许** `code_run` | 同上 |
| `calc_code_run` | 1..100 平方和 | 必须 `code_run`，正文含 `338350` | 「需要计算优先 code_run，不要心算」 |
| `fib_20` | 斐波那契第 20 项 | 必须 `code_run`，正文含 `6765` | 同上 |
| `write_then_read` | 写 a.txt 再读回确认 | 必须 `file_write` + `file_read`，正文含 hello | 「声称完成前必须有证据」 |
| `no_skill_needed` | 「一天多少小时」 | **不许** `load_skill` / 任何工具 | 「扫描后确实没有匹配就不用加载」 |
| `honest_unknown` | Hlaudz 3.0 发布日期 | 不许出现 `YYYY-MM-DD` 形态日期；必须出现「查不到/无法核实」 | 「无法证实就写未证实，不要编造」 |

指标全部从 SSE 事件自动算，不做人工判读：

- **tool_ok**：期望工具出现且禁用工具没出现；
- **skill_load**：无谓加载 skill 的次数（本批任务都不需要 skill）；
- **rounds**：工具轮次（≈ 回合数，越少越直接）；
- **pass**：全部判据通过。

### 2.3 一个必须防的坑：端口

第一版实验同时跑了两份进程，第二个进程连上了第一个的 8011 实例，
结果「new」和「legacy」的数据混在一张表里，读出来几乎全是失败——**那是实验污染，不是模型结论**。
现在 `start_server()` 启动前必须 `_port_free()`，端口被占直接报错退出。

### 2.4 运行方式

## 3. 子代理 UX 五项

五项共同点：**视图逻辑抽成纯函数**（`frontend/src/subagentView.ts`），
用 `node --test` 直接测，组件只负责渲染。这样不用起浏览器就能验证判据。

| # | 问题 | 做法 | 验证 |
| --- | --- | --- | --- |
| 1 | 同一 agent 可能出现两行（断线重连 / 事件重放重复下发 start） | `mergeStart()` 按 `agent_id` 合并；`mergeStatus()` 保证状态单调，终态不会被 `running` 覆盖 | `tests/subagentView.test.ts` 4 条 |
| 2 | team 面板可能静默截断 | 任务/消息/动态各上限 200 行，超出显示「另有 N 个未显示」 | `capList()` 单测 + 面板渲染 |
| 3 | 关闭中的成员仍显示「运行中」 | 后端 `_stop_node` 先置 `stopping` 并广播 `subagent_status`；chat.py 透传；前端加「停止中」 | `test_close_running_publishes_stopping_status` + 真实 S13 |
| 4 | 看不到子代理跑了多久 | 卡片记录 `startedAt` / `endedAt`，运行中每秒刷新显示「已运行 1:23」，结束后固定为「耗时 1:23」 | `elapsedMs` / `formatDuration` 单测 |
| 5 | 失败只有一行 error | 改成 `<details>`：「失败原因：xxx 报错」，展开是最后一条工具错误原文（最多 220px 滚动） | `lastToolError()` 单测 |

### 3.1 第 3 项顺手抓到的真缺陷

`stopping` 一开始只加在 `host._publish()`，但 `app/routers/chat.py` 的 SSE 是**显式分支链**
（`elif et == "subagent_start" / "subagent_event" / "subagent_end"`），
没写进分支的事件会被**静默丢弃**——前端永远收不到，而且没有任何报错。

`test_event_stream_builds_subagent_block` 因此加了断言：喂一条 `subagent_status`，
必须出现 `event: subagent_status`。先红后绿，并做了反向确认。

### 3.2 端到端实证（S13，湛卢真模型）

```
subagent_start  sub:slow_sleeper role=teammate
subagent_status sub:slow_sleeper status=stopping
subagent_end    sub:slow_sleeper status=stopped
```

`[PASS] S13 subagent-stopping-state 158.8s tools=['spawn_agent','close_agent','list_agents']`

这条链是「模型真的调了 close_agent → 后端真的广播了 stopping → SSE 真的发出去了」，
不是构造得出的推断。

### 3.3 一个刻意的降级

耗时只在**当前这次会话的实时流**里显示：`startedAt` / `endedAt` 记在前端内存。
刷新页面后，历史子代理卡片读的是后端持久化的 block，没有起始时间，**就不显示耗时**——
而不是拿消息创建时间凑一个看起来对、其实错的数字。`elapsedMs()` 对缺 `startedAt` 返回 `null` 正是为此。

## 5. 消融结果

> 3 轮 × 7 用例 × 2 变体。原始数据：`backend/tests/e2e/runs/ablation-<ts>/report.md`（含逐用例 checks 与正文尾部）。

### 5.0 先排除污染：一次 502 把「new」的尾巴打掉

第一次 3 轮跑完，`new` 的正确率明显低于 `legacy`。逐条查现场发现不是提示词的问题：

```
new/write_then_read#2,3   rounds=2/0  text=""  done=error
new/no_skill_needed#1-3   rounds=0    text=""  done=error
new/honest_unknown#1-3    rounds=0    text=""  done=error
```

全量扫描 events.jsonl 里含 `502 Bad Gateway` 的运行：**8 条，全部落在 `new`；`legacy` 0 条**。

事件里的错误原文：
`HTTP 502: <html><head><title>502 Bad Gateway</title></head>... nginx/1.26.3`

上游网关 502，模型根本没被调用。这 6 条必须剔除，否则会得出「新提示词更差」的假结论
——而这正是需要 A/B 时最容易犯的错：把基础设施故障读成效果差异。

处理：`new` 变体整批重跑（21 次），`legacy` 那批没有 502，保留。

### 5.1 汇总（各 21 次；已剔除 502 样本）

| 变体 | 有效次数 | 工具选择正确率 | 全通过率 | 无谓 skill 加载 | 平均轮次 | 平均耗时 |
| --- | --- | --- | --- | --- | --- | --- |
| legacy（改造前） | 21 | 100% | 95% | 0 | 2.0 | 55.7s |
| new（当前） | 21 | 100% | 100% | 0 | 2.0 | 44.6s |

### 5.2 逐用例

| 用例 | legacy | new | legacy 轮次 | new 轮次 | legacy 耗时 | new 耗时 |
| --- | --- | --- | --- | --- | --- | --- |
| glob_only | 3/3 | 3/3 | 1.0 | 2.0 | 36.3s | 41.7s |
| grep_only | 3/3 | 3/3 | 3.0 | 3.0 | 46.9s | 28.8s |
| calc_code_run | 3/3 | 3/3 | 1.0 | 1.0 | 34.5s | 37.2s |
| fib_20 | 2/3 | 3/3 | 5.0 | 4.0 | 132.7s | 72.3s |
| write_then_read | 3/3 | 3/3 | 2.0 | 2.0 | 88.7s | 43.1s |
| no_skill_needed | 3/3 | 3/3 | 0.0 | 0.0 | 18.1s | 18.6s |
| honest_unknown | 3/3 | 3/3 | 2.0 | 2.0 | 32.8s | 70.9s |

### 5.3 结论（只写数据能支撑的）

1. **在「工具选择 / 不无谓加载 skill / 不编日期」这几条上，新提示词没有变差**：
   两边都是 100% 工具选择正确、0 次无谓 skill 加载。这是本轮唯一能下的硬结论。
2. **总通过率 95% → 100%、平均耗时 55.7s → 44.6s，不能算「新提示词更好」**。
   唯一那次失败是 `legacy/fib_20#2` 把第 20 项算成 4181（F(19)）——模型的 off-by-one，
   换一次采样就可能翻过来。n=3 的样本撑不起这种结论。
3. **`glob_only` 反而多用了 1 轮**（1.0 → 2.0）：新提示词写「找文件用 file_glob」
   之后，模型多做了一次确认性调用。这是提示词带来的真实副作用，代价很小，但要记账。
4. **`honest_unknown` 慢了一倍**（32.8s → 70.9s）：新提示词要它「先探测再回答」，
   它就去 workspace 里搜了一轮。行为是对的（结论仍是「查不到」），成本是时间。
5. **新提示词真正想改善的两件事，这批用例测不到**：
   「没做完不要结束回合」「声称完成必须有证据」需要**多步、可失败、有中途放弃诱惑**的任务
   （例如依赖缺失、网络失败、需要重试），而不是一次调用就能完成的小任务。
   要量化这两条，得另设计一批用例——本轮不做，记在总纲 §8。

> 一句话：这次消融证明的是「改造没有引入回归」，而不是「改造带来了提升」。
> 把 44.6s 说成改造收益是不诚实的，样本量与任务形态都不支持。

## 3. 逐条修复

### 3.1 BUG-01 子代理启动 100% 失败（P0）

**根因**：`SubagentRegistry.create_child()` 把子代理角色写成 `"teammate" if team_id else parent_ctx.role`。根代理是 `lead`，`spawn_agent` 不传 `team_id` 时子代理被标成 `lead`，`TeamHost` 因此拿不到 teammate 权限，`build_teammate_tools()` 直接抛错。

**改动**：

- `create_child()`：只要父/子任一带着 `team_id`，`effective_role` 恒为 `teammate`，并给 `parent_ctx.child(..., role="teammate")` 传入同一角色；
- `SubagentRuntime.build()`：`ctx.team_id` 非空时显式构造 `TeamScope(..., role="teammate")`，兼容旧上下文/自定义调用方。

**复验**：`python work/claude_test_and_review/_repro_subagent_role.py` →

```text
parent role: lead team: team_x
child role: teammate team: team_x node.role: teammate
from_agent role: teammate
build_teammate_tools: OK
```

### 3.2 BUG-02 客户端断开泄漏 Team 配额（P0）

**根因**：请求任务被 anyio/Starlette 取消时，`CancelledError`（`BaseException`）会打断清理链上的每个 `await`；原 `finally` 里的 `release_lifecycle()`/`stop_all()` 都是异步动作，一次 await 即被中断，per-user Team 租约（`USER_MAX_ACTIVE_TEAMS=1`）永久占住。

**改动**：

1. `TeamHost.release_lifecycle_now()`：同步、幂等、不 await；
2. `SubagentHost.stop_all_now()`：同步 `set + cancel` 所有存活子代理，随后 `stop_all()` 再做 ≤1.5s 的受控 join；
3. `chat._cleanup_turn()`：**先**做三件同步动作（释放 Team 租约、取消子代理、注销 hub），**再**进入可被取消的异步阶段；
4. 异步阶段任一 await 被 `CancelledError` 打断时，转 `asyncio.create_task(_settle_turn(...))` 在新任务（脱离 cancel scope）中补完 `close_all` / `team status` / `release_generation`；
5. `team_end` 只在一条路径发出（中断即交给 settle），避免重复事件。

**复验**：`python work/claude_test_and_review/_verify_bug02.py`（claude4，真实 LLM，客户端在读 200 字节后直接断开，不做 stop）：随后新会话可正常 `team_start` → `['team_start']`。

### 3.3 BUG-03 `team_unavailable` 被静默丢弃（P1）

**根因**：`mergeTeamEvent()` 在没有已有 Team 快照时直接 `return prev`，`team_unavailable` 既不入面板也不提示。

**改动**：

- `mergeTeamEvent()` 特判 `team_unavailable`：即使 `team === null` 也保留事件（去重 + 按 `event_seq` 排序）；
- `onEvent` 收到 `team_unavailable` 时设置 `teamError`（取 `payload.error`），收到新的 `team_start` 或下一次发送时清空；
- 主区新增 `.team-warn` 警示条：「Team 本轮不可用：<原因>」，可关闭。

**复验**：用 Playwright `route` 把 `POST /messages` 替换为一段含 `team_unavailable` 的真实 SSE 帧（帧体内层即 TeamEvent，符合 `parseFrame` 的 `team_event` 约定），页面出现：

### 3.6 BUG-06 压缩后仍高于软线（P2）

**根因**：`enforce_soft_limit` 只用 `soft*0.5` 选保留尾部，摘要由模型自由发挥；摘要本身可能接近甚至超过软线，`after_tokens = summary + preserved > soft`，于是下一轮再次触发。

**改动**（`compaction.enforce_soft_limit`）：

1. `LLMClient.run(..., max_tokens=)` 支持单次输出上限；摘要调用按「恢复预算 − 尾部 token」封顶（≥128）；
2. 摘要后仍 `after > soft` 时，把保留尾部的最老一半折叠进下一次摘要（最多重试 2 次，绝不从 tool 消息开始）；
3. 仍不达标时做最后一次确定性尾部裁剪（`_tail_keep_from`），保证 `after_tokens <= soft`；
4. 自动/手动压缩的 `dropped/kept` 与摘要卡统一口径。

**复验**：新增 `work/claude_test_and_review/_verify_bug06.py`（claude8，`context_window=8000 / auto=1200 / hard=1800`，6 轮真实 LLM）：

```text
turn 4: auto before=1237 after=508  (soft=1200)
turn 6: auto before=1402 after=601  (soft=1200)
auto compactions: 2   problems(after > soft): []   RESULT: PASS
```

说明：软线阈值被压到 1200 tokens 时，一轮回答本身就可能占窗口的 30%，因此「每隔一轮触发一次」属于预期；关键不变量「每次压缩后都低于软线」已成立。

## 5. 风险与未决项

1. **压缩触发只看「已有历史 + 本轮用户输入」**：模型本轮输出不可预知，极小软线（如 1200 tokens）下仍可能「隔轮触发」。属预期行为，不变量已改为「压缩后必低于软线」。
2. **删除摘要的最后一档**（`_tail_keep_from`）会在极端情况下丢弃部分保留尾部原文而不摘要；仅当摘要本身超出恢复预算且二次折叠无效时触发。
3. **MCP 导入的 HTTP 状态码**仍为 200（契约保持），错误通过 `ok/errors` 表达；若未来要改 400，需要同时改前端与自测脚本。
4. `team_panel_open` 旧全局键不再读取，历史值残留无害；如需要可在后续版本清理。
5. 本次复验使用真实「湛卢」模型；`claude8` 账号与 `bug06-*` 会话为测试数据，可随时清理。

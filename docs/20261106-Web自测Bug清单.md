## 2. 详细缺陷

### BUG-01（P0）普通子代理 100% 启动失败

**现象**：任何一次 `spawn_agent`（根代理派生普通子代理）都在第 0 轮失败，子代理卡状态 `errored`，`turns=0`，模型无法完成任务；`spawn_teammate`（Team teammate）却正常。

**复现（真实 LLM）**：

1. 以 `claude / 12345678` 登录，新建会话。
2. 发送：「请派生一个子代理（task_name=calc），让它用 code_run 计算 17*23，等它结束后告诉我结果。必须真实调用 spawn_agent 和 wait_agent。」
3. 观察：出现 2 张子代理卡片，均显示「通用 · 失败」；模型最终如实报告内部错误。

**证据**：

- 会话 `subagent-test`（用户 `claude`）的回复原文：
  `已真实调用 spawn_agent(task_name=calc) → 状态 errored，0 轮，错误：ValueError: build_teammate_tools requires a teammate TeamHost`
- 截图：`work/claude_test_and_review/shots/15-subagent-error.png`
- SSE 原始帧：`work/claude_test_and_review/runs/api_20261106_175552/subagent_frames.json`
  （其中 `subagent_end` 的 `status=errored`，`error=ValueError: build_teammate_tools requires a teammate TeamHost`）

**最小静态复现**（无需 LLM，已执行）：

```text
parent role: lead team: team_x
child role:  lead team: team_x node.role: general   # ← 应为 teammate
from_agent role: lead
build_teammate_tools FAILS: ValueError build_teammate_tools requires a teammate TeamHost
```

脚本：`work/claude_test_and_review/_repro_subagent_role.py`

**根因**：

1. `backend/app/subagent/registry.py::create_child` 在 `team_id` 参数为空、但父上下文已带 team 时，把 `role=parent_ctx.role`（`lead`）传给 `AgentContext.child`。
2. `backend/app/subagent/context.py::child` 中 `role=role if (team_id or self.team_id) else self.role`，此时 `self.team_id` 非空，于是子上下文 `role` 被设成 `lead`。
3. `backend/app/subagent/runtime.py::SubagentRuntime.build` 看到 `ctx.team_id` 非空，就 `TeamScope.from_agent(...)`（`lead`）后调用 `build_teammate_tools(...)`；该函数要求 `role == "teammate"`，直接抛 `ValueError`，子代理在第 0 轮退出。

**修复建议**（任选其一，建议都做）：

- `create_child` 里始终以 `role="teammate"` 创建子上下文（无线程时 `context.child` 会自动继承父 role，不受影响）。
- `SubagentRuntime.build` 构造 teammate 用 `TeamScope(..., role="teammate")`，不要依赖 `from_agent` 从 ctx 推断。
- 给 `build_teammate_tools` 的调用加防御：只在该子代理确实以 teammate 身份参与 Team 时才注入协作工具。

**验证方法**：修复后重跑上述 prompt，期望 `subagent_end.status=completed` 且结果含 `391`；或运行 `_repro_subagent_role.py` 期望 `child role: teammate` 且 `build_teammate_tools: OK`。

### BUG-02（P0）客户端断开泄漏 Team 配额租约（用户级永久）

**现象**：生成过程中浏览器断连（关闭标签、刷新、`AbortController.abort()`，前端的「停止」按钮第一步就是 abort）后，该用户的下一次生成永远收到 `team_unavailable`，Team 面板再也不出现；且同一用户其它会话也受影响。只有重启后端进程（清空进程内 `QuotaManager`）才恢复。

**复现（两条路径，均已验证）**：

- A：**仅断开**（模拟关标签/刷新）：POST `/api/sessions/{sid}/messages` 后读取少量 SSE 字节并关闭连接；等 6s 后新建会话发送「只回答 OK」→ `team_event: ["team_unavailable"]`；再等 15s 重试仍是 `team_unavailable`。
- B：**断开 + 调 /stop**（UI「停止」的真实顺序）：同样结果。

脚本：`work/claude_test_and_review/_test_lease2.py`、`_test_lease3.py`；对应用户 `claude3`（`u_0dbeed1f0de7`）。

**对照（正常路径不泄漏）**：

- 正常完成的多轮对话：每轮都会 `team_start`，配额正常释放。
- 仅调用 `/stop`、不 abort 连接：下一轮仍 `team_start`（`_test_lease.py`）。
- 重启后端后：同一用户恢复 `team_start`（`_test_lease.py` 复跑）。

**影响**：

- Agent Team（P3 核心能力）在用户按过一次「停止」或刷新过页面后即永久失效。
- 同类取消路径还会跳过 `_event_stream` 的 finally 清理：子代理宿主不会 `close_all()`、`hub.unregister_subagent_host()` 不执行，可能留下后台运行中的子代理、持有 subagent/code_run 配额与内存（进程内泄漏），以及 DB 侧 `session_generations` 残留 active（后续 GET/发送时才被动收敛）。

**根因（建议按此修）**：

`backend/app/routers/chat.py::_event_stream` 的 `finally` 里，`await turn.host.close_all()`、`await turn.team.set_status(...)`、`await turn.team.release_lifecycle()` 都放在 `try/except Exception` 内。客户端断连时 Starlette/anyio 的取消范围会在这些 `await` 上再次抛出 `asyncio.CancelledError`，而它继承自 `BaseException`，不会被 `except Exception` 捕获；于是后续清理（尤其同步的 `lease.release()`）被跳过，`QuotaManager` 的用户级 semaphore 永久 -1。

同时 `/stop` 端点只收敛 DB（`converge_generation_facts`），不释放进程内 Team 租约；租约完全依赖生成器的 finally，一旦 finally 被取消打断就泄漏。

**修复建议**：

1. 在 `_event_stream` 的 `finally` 第一行、任何 `await` 之前，同步释放 Team 生命周期租约（`turn.team.release_lifecycle()` 内部是同步 `Lease.release()`；可拆一个不 await 的 `release_now()`）。
2. 清理段用 `except BaseException` 或 `contextlib.suppress(BaseException)` 包裹每个 await，保证后续步骤仍执行；或把清理放到独立的 `asyncio.create_task` + `asyncio.shield` 中。
3. 更好的做法：把「活跃 Team lease」登记到进程内 registry（键 `user_id/session_id/generation_id`），`/stop` 端点和断连清理都能直接释放；并在 `guarded_stream` 的 finally 里兜底释放。
4. 给 `stop_subagent_generation`/host 注册表也加同样的兜底，避免断连遗留后台子代理。
5. **可观测性**：`prepare_turn_team` 捕获异常后只 `buffer.put(team_unavailable)`，没有服务端日志；`_event_stream` 的清理段也全部 `except Exception: pass`。建议至少 `logger.warning(..., exc_info=True)`，否则这类泄漏在线上只能靠用户“Team 不出现了”才发现。

**验证方法**：干净进程下用 `_test_lease3.py`：A 段应得到 `team_start`（当前是 `team_unavailable`）；或手写 socket：发消息→读 200 字节→close→新会话发送，观察 `team_event`。

### BUG-03（P1）`team_unavailable` 被前端静默丢弃

**现象**：Team 创建失败时后端会发 `team_event {type:"team_unavailable", payload:{error:...}}`，但前端 `mergeTeamEvent` 在「当前没有 team 快照」时直接 `return prev`（`frontend/src/App.tsx`），既不展示错误，也不创建占位；面板只是显示「未启动 / 发送消息后，Lead 会自动建立本轮 Agent Team」，用户完全不知道 Team 已经坏了。

**复现**：在 BUG-02 的泄漏状态下，任一会话发送消息，观察右侧 Team 面板：整个生成过程与结束后都没有任何错误提示；网络面板中后端确实发了 `team_unavailable`。

**证据**：截图 `shots/16-team-unavailable.png`；SSE 事件 `team_event` 的 `data.type` 为 `team_unavailable`。

**修复建议**：`mergeTeamEvent` 对 `team_unavailable` 建立一条可见状态（例如面板内红色提示 + event 列表项），或在 App 层 `setError(...)` 一次；同时 Team 按钮上可加失败标记。更好的做法是 BUG-02 修复后此状态几乎不出现，但仍应保留可见的错误出口。

### BUG-04（P2）停止后 Team 面板显示「已过期」而非「已停止」

**现象**：用户点「停止」后，Team 面板状态显示「已过期」，而会话/消息是「已停止」；DB 中 `team_runs.status='stale'`。

**复现**：生成中点击「停止」→ 约 250ms 后前端 `GET /sessions/{id}/team` → 面板「已过期」。

**证据**：会话 `co_b3d7a66462cb`（`stop-test` 系列）DB：`team_runs.status='stale'`；截图 `shots/09-after-stop.png`。

**根因**：停止端点的 `converge_generation_facts(status="stopped")` 只把仍然 `active` 的 team 行改成 `stopped`；但生成器被取消时 finally 未完成（BUG-02），此时若 team 行仍为 `active`、generation 行已被释放，`GET /team` 的 `converge_orphaned_active_teams` 会把它标成 `stale`（设计里 stale 表示「进程遗留」，不是用户停止）。

**修复建议**：BUG-02 修复后应自然消失；另可在 `converge_orphaned_active_teams` 之前优先读 `session_generations.status`（`stopped` → 写 `stopped`），或让停止端点同时把该代 team 标 `stopped`（它已做，但被并发 GET 抢先置 stale）。

### BUG-05（P2）非法 mcp.json 的错误详情被吞

**现象**：在「设置 → 我的 MCP」粘贴非法 JSON 后点保存，后端返回 `200 {ok:false, errors:["JSON 解析失败: ..."], skipped:[...]}`；前端只用 `r.message` 作为提示（蓝/中性 notice），完全不展示 `errors`，用户看到的是「解析到 0 个 server…忽略 1 个无效项」，像成功一样。

**复现**：设置 → 我的 MCP → 输入 `{ invalid json` → 保存（按 name 合并）。

**证据**：截图 `shots/05-mcp-invalid.png`；API 响应见 `_suite_api.py` H3。

**修复建议**：`SettingsModal.saveJson` 在 `r.ok === false || r.errors.length > 0` 时用红色错误框展示 `r.errors.join('\n')`，并保留「已导入 0 个」的中性提示区分成功/失败。

### BUG-06（P2）低阈值下每轮重复自动压缩（已知遗留复现）

**现象**：给会话配置 `context_window=8000, auto_compact_tokens=1200, hard_limit_tokens=1800` 后：

- 第 4 轮触发 `auto`：`before_tokens=1544 → after_tokens=1235`（仍 > 1200）。
- 第 5 轮再次触发 `auto`：`before_tokens=1846 → after_tokens=1419`（仍 > 1200）。
- `/sessions/{id}/context` 返回 `used_tokens=1442, auto_compact_tokens=1200, remaining_to_compact=0, compacted=true`。
- 用户可见两张摘要卡，且以后每轮都可能继续摘要，近期细节持续被吃掉。

**证据**：脚本 `_test_soft_compact.py`、`_test_hard_trim.py` 输出。

**根因**：`compaction.enforce_soft_limit` 的恢复目标 `target = soft * 0.5` 只用于「保留尾部」的选择，最终 `after_tokens = summary + preserved` 仍可能高于软线；而 `AUTO_MIN_KEEP_MESSAGES=2` 与按 token 累加的保留策略不足以把结果压到软线以下。文档 `docs/20261104-上下文压缩方案与进度.md` §7.1 已记录，尚未实现。

**修复建议**：保留尾部按「压缩后总量 ≤ soft*0.5」反推而非固定 token 累加；或在摘要后检查 `after_tokens`，仍超软线则继续压缩更早消息；同时把硬线判断放到软线之前（当前软线先跑，硬线可能永远轮不到）。

### BUG-07（P3）Team 面板展开时顶栏会话标题被挤成 2–3 字

**现象**：1280px 宽、Team 面板展开（300px）时，顶栏标题只剩 `请调…` / `comp…`；标题本可以占用更多空间。

**证据**：截图 `shots/03-streaming.png`、`shots/07-compact-ui.png`。

**根因**：`.main-header .title { flex: 1; overflow:hidden; text-overflow:ellipsis }` 是唯一可收缩项，而模型选择器 `max-width: 260px` + badge + 两个按钮的最小宽度把标题压到接近 0；`overview` 的 `overflow:hidden` 又让自动最小宽度变为 0。

**建议**：给标题设 `min-width: 120px`；中窄屏隐藏 badge（已有 900px 断点）并给模型选择器更小上限；Team 面板展开时把 badge 换成短标签或隐藏。

### BUG-10（P3）生成中上下文条显示 0.0k

**现象**：流式生成期间底部显示「上下文 0.0k / 400.0k · 0.0%」，本轮结束后才变成真实值（如 1.8k / 0.4%）。流式时用户会误以为没有上下文。

**证据**：截图 `shots/19-team-live.png`（生成中 0.0k）与 `shots/20-team-panel-live.png` / 结束后的 1.8k。

**建议**：流式期间用本地估算（已有 token 估算接口/函数）或显示「统计中…」，不要显示 0.0k。

### BUG-11（P3）压缩提示与摘要卡口径不一致

**现象**：`/compact` 后顶部提示「已压缩 3 条较早消息 → 摘要约 137 tokens，保留最近 6 条」，而消息流里的摘要卡显示「保留 7 条 · 压缩 4 条」。两个数字都来自后端不同字段（`preserved` vs `kept = preserved + summary`，以及本次/累计的 dropped 不同），用户会困惑。

**证据**：截图 `shots/07-compact-ui.png`；`_test_compact2.py` 输出。

**建议**：统一文案口径（例如都写「保留最近 N 条（含摘要卡）」并在前后端用同一计数），或提示里明确「本次压缩 X 条 / 累计 Y 条」。

### BUG-12（P3）会话 PATCH 校验缺失

**现象**：

- `PATCH /api/sessions/{id}` 传 `model_id: "llm_does_not_exist"` 返回 200 并原样保存；真正发送时才回退默认模型，UI 下拉显示「（该配置不可用）」。
- `PATCH` 传 `title: ""` 或 `"  "` 返回 200 并保存空/空白标题，侧栏出现空标题项。

**证据**：`_suite_api.py` B4/B6。

**建议**：`model_id` 非空时校验属于当前用户（否则 400/404）；标题 `trim()` 后为空则拒绝或回退默认标题。

### BUG-13（P3）每轮都创建 Team，0 任务也显示「已完成」

**现象**：任何一次普通对话（哪怕不涉及协作）都会创建本轮 Team 并立刻结束，Team 面板显示「已完成 · 0 任务 0 进行中 0 消息」。用户会疑惑「团队什么时候跑过？」。

**证据**：任意会话的 `team_event: team_start`（每个 chat 回合都有）；截图 `shots/01-workbench.png`、`shots/16-team-unavailable.png`。

**说明**：这是 P3 的既定设计（root 即 lead，每轮隔离 Team）。如果保留该设计，建议面板在「0 任务 0 消息」时显示「本轮未发生协作」而不是空任务板 + 已完成；或延迟到第一次 team 工具调用才建 Team。

### BUG-14（P3）localStorage 偏好跨账号共享

**现象**：`team_panel_open` 存在 `localStorage`，同一浏览器切换账号后沿用上一个账号的展开状态（本次 `claude` 展开后，`claude2` 登录即为展开，导致我误点一次把面板关掉）。

**建议**：key 加用户维度（如 `team_panel_open:<user_id>`），或接受为产品选择并在文档说明。

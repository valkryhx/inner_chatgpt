# Markdown `![](...)` 图片渲染修复

> 日期：2026-11-05
> 状态：已完成
> 范围：前端 Markdown / 原生 HTML 图片渲染 + 后端 workspace 图片鉴权接口 + code_run 产物边界

## 1. 问题

用户反馈前端无法通过 `![alt](path)` 显示图片。排查后确认是**两个独立原因叠加**：

| 原因 | 表现 |
|---|---|
| `react-markdown` 默认 URL 过滤器只允许 `http(s)/ircs/mailto/xmpp` | `D:\...` 被当成未知协议，`src` 直接被清空 |
| 图片放在用户 workspace 内，`<img>` 无法携带 `Authorization` | 相对路径 `chart.png` 经 SPA fallback 返回 `index.html`；即使拼绝对 URL 也会 401 |

此外，workspace 是**每用户隔离**的，不能简单把 `backend/data/workspaces` 挂成静态目录，否则会造成跨用户读取。

## 2. 方案

### 2.1 后端：鉴权媒体接口

新增 `GET /api/me/workspace-image?path=...`（`backend/app/routers/media.py`）：

- 复用 `safe_read_path()`：只允许读取当前用户 workspace 与可见 Skill 目录；
- 支持路径形态：
  - `chart.png` / `images/chart.png`
  - `workspace/chart.png` / `/workspace/chart.png`
  - `/images/chart.png`（按 workspace 相对路径）
  - `D:/...`、`D:\...`、`file:///D:/...`
- 仅允许图片 MIME（png/jpg/jpeg/gif/webp/bmp/avif/svg），单文件上限 25MB；
- 响应头：`Cache-Control: private, max-age=60`、`X-Content-Type-Options: nosniff`；
  SVG 额外加 `Content-Security-Policy: default-src 'none'; ...; sandbox`；
- 越界 → 403，不存在 → 404，非图片 → 415，过大 → 413。

### 2.2 前端：MarkdownImage 组件

新增 `frontend/src/components/MarkdownImage.tsx`，把图片分为两类：

| 类型 | 处理 |
|---|---|
| `http(s)` / `data:` / `blob:` | 原样交给 `<img>` |
| workspace 本地路径（相对、Windows 绝对、`file:`、`/workspace/`） | 带 Bearer token `fetch` 接口 → `URL.createObjectURL(blob)` → `<img>` |

组件卸载时 `abort` 请求并 `revokeObjectURL`，避免内存泄漏；加载中显示占位，
失败显示「图片加载失败 + 原因」，不会静默空白。

`Markdown.tsx`：

- 新增 `urlTransform={safeMarkdownUrl}`，放行相对路径 / `file:` / Windows 盘符路径；
- 链接 `a` 仍只允许安全协议；
- `img` 统一交给 `MarkdownImage`。

### 2.3 样式

- `.md-image`：块级、上下 12px；
- 图片：`max-width:100%`、自适应高度、细边框、圆角；
- 加载中：虚线占位；失败：可见错误文案（不再只有一个裂图图标）。

### 3.5 原生 HTML `<img>` 与 Windows 路径补测（2026-11-05）

真实测试暴露出模型会绕过 Markdown 语法，直接输出原生 `<img>`；这条路径此前被
`react-markdown` 丢弃。修复如下：

- `frontend/package.json` 新增 `rehype-raw`、`rehype-sanitize`；
- `Markdown.tsx` 用 `rehypeRaw → rehypeSanitize` 解析并清洗原始 HTML；
- 只放行 `img/figure/figcaption/details/summary/kbd/mark` 和图片必要属性；
- `onerror`、`<script>`、`iframe`、`style/class` 等继续移除；
- `src` 协议白名单增加 `file:`、`blob:` 与 Windows 盘符（单字母协议），
  仍拒绝 `javascript:` / `vbscript:`；
- 所有 `<img>` 最终仍交给 `MarkdownImage`，本地路径统一走 Bearer 鉴权接口。

真实页面会话 `co_80712f2fae0b` 验证了 5 张合法图片同时加载：

### 3.6 产物不得写入 `frontend/dist` / 源码目录

仅靠系统提示约束不够，`code_run` 现在有两层防护：

1. 执行前静态拒绝包含 `frontend/dist`、`frontend/src` 的代码；
2. Python 子进程在 `runpy` 前安装 `sys.addaudithook`，拦截 workspace 外
   的 `open(write)`、`os.rename/replace/remove`、`shutil` 最终落盘等；
   `TMP/TEMP/TMPDIR` 也固定在当前 workspace 的 `.tmp`。

验证：

```text
workspace 内写入       -> 成功
写入 tmp 外的路径      -> PermissionError，文件未创建
frontend/dist 写入      -> [工具执行错误]，执行前拒绝
```

注意：这是**进程内误操作防护**，不是 OS 级安全沙箱；生产环境仍应使用
容器、独立账户或系统 sandbox 隔离不可信代码。

## 4. 已知边界

1. 图片必须位于当前用户的 workspace 或可见 Skill 目录内；仓库源码目录、其他用户目录一律拒绝。
2. 暂不支持私有对象存储 / CDN 签名 URL；如后续接入，只需扩展 `safe_read_path` 的根目录。
3. SVG 以 `<img>` 方式加载并附加 sandbox CSP；不将其内联进 DOM，避免脚本执行。
4. 远程 `http://` 图片在 HTTPS 页面下会被浏览器按混合内容拦截（浏览器策略，不是本项目 bug）。
5. Markdown 图片 alt 文本保留；未做图注/灯箱（如需要可作为后续增强）。

# A2A 长任务语义：同步窗口超时必须可恢复（实施记录）

> 日期：2026-11-14　状态：**已完成**
> 起因：M5 收尾时核对「Hlaudz 被 A2A 调用时显不显得无能」，发现同步窗口默认 60s
> 而实测多步任务 105s —— 大多数像样的任务都会撞上超时分支。
> 关联：`docs/20261110-A2A使用文档.md` §0.0 / §5.1 / §5.2 / §6.4

---

## 0. 结论与选型

问题：同步 `SendMessage` 默认只等 60 秒，而一次会调工具的任务实测 **105 秒级**。
调用方拿到的是一个 `TASK_STATE_WORKING` 的 body，且**里面没有任何提示**说明
「这是还在跑」还是「它挂了」，也不知道下一步该调什么。

两条路：

| 方案 | 做法 | 失败模式 |
|---|---|---|
| A | 把同步超时默认拉到 300s | 代理/网关先断（多为 60–100s）→ 调用方**连 task id 都拿不到**，任务还在后台跑并占配额 = 真失控 |
| **B（采纳）** | 保持短窗口，把它变成一个**明确的、可恢复的中间态** | 拿到干净的 `WORKING` + task id + 进度入口 |

**B 更稳，理由是失败模式的差别，不是偏好**：

1. **任务独立于 HTTP 请求**。`_spawn` 用 `asyncio.create_task`，同步等待只是
   在循环里轮询 `store.get_task`。超时返回 `WORKING` + task id，是协议定义的可恢复态；
   A 的失败态则是「连接错误 + 没有 handle」，后台任务仍在跑。
2. **A 治不了病**。长任务的天花板不是 300s，是子代理的 `SUBAGENT_TIMEOUT_S=1800`
   与 ACP 的 `INNER_ACP_PROMPT_TIMEOUT_S=1800`。60→300 只是把悬崖挪个位置，
   6 分钟的任务照样掉下去。同步 HTTP 原理上表达不了 30 分钟的任务。
3. **同步等待目前没有断连检测**（`service.py` / `router.py` 里没有
   `request.is_disconnected`）。客户端死了，循环仍轮询到 deadline；
   A 把这段浪费窗口从 60s 拉成 300s。

## 1. 实现

### 1.1 超时返回改成自解释的（`service.py`）

`_with_still_running(task)` 给**提交语义**的返回补三样东西：

```json
{
  "status": {"state": "TASK_STATE_WORKING", "message": {"parts": [{"text": "任务仍在运行，不是失败。…"}]}},
  "stillRunning": true,
  "poll":      {"method": "GetTask",         "params": {"id": "task_xxx"}},
  "subscribe": {"method": "SubscribeToTask", "params": {"id": "task_xxx"}}
}
```

三个设计点：

- **`stillRunning` 是机器可读的**，调用方不必解析中文；
- **`poll` / `subscribe` 直接给出可执行的方法与参数** —— 调用方拿到就能照做，
  不用回去翻协议文档；
- **文案里明说「不要重发」**。重发同一条 `messageId` 会幂等命中拿回同一个任务，
  但调用方若换了 `messageId` 就会**真的跑第二遍**，白烧一遍 token。

### 1.2 哪些返回带它、哪些不带

| 返回路径 | 带 `stillRunning`？ | 理由 |
|---|---|---|
| `SendMessage` 同步超时 | ✅ | 这是最需要说清「没死」的路径 |
| `SendMessage` + `returnImmediately` | ✅ | 主动异步同样需要进度入口 |
| 幂等重放且任务未结束 | ✅ | 重放最容易让人以为「没反应」 |
| `SendMessage` 同步完成 | ❌ | 已经完成了，加标志会让调用方白等 |
| `GetTask` | ❌ | 这是**查询**，`state` 已经说清；加了语义反直觉 |

### 1.3 顺带补的真缺口：调用方原本无法控制同步窗口

`configuration.syncTimeoutS` 之前**根本没被读取**。写 e2e 时假设它存在才发现。

新增 `_clamp_sync_timeout()`，**关键在「夹上限」**：

```python
SYNC_TIMEOUT_CAP_S = 280.0
return min(seconds, SYNC_TIMEOUT_CAP_S)
```

为什么不让调用方随便填大数：同 A 方案的理由 —— 同步等待占着连接，
超过代理空闲超时只会让调用方连 task id 都拿不到。所以**调用方可以调，
但调不到有害的程度**。280 略小于常见的 300s 代理上限。

`None` / 空串 / 非数字 / 0 / 负数 / NaN → 返回 `None`（用服务端默认），不抛异常。

### 2.2 L3 真机（S-M6，runId `1794661186-7fe1`）

工具：`backend/tests/e2e/memory_a2a_cases.py S-M6`。

流程：给一个**极短**同步窗口（`syncTimeoutS: 0.5`）保证走到超时分支 →
照返回里的 `poll` 用 `GetTask` 续取 → 等到终态。

7/7 通过：

| 断言 | 实测 |
|---|---|
| 首次返回 `TASK_STATE_WORKING` | ✅ |
| `stillRunning: true` | ✅ |
| `poll.method == GetTask` | ✅ |
| `subscribe.method == SubscribeToTask` | ✅ |
| 文案含「仍在运行」 | ✅ |
| 按 poll 续取能到终态 | ✅ `TASK_STATE_COMPLETED` |
| 续取到的产物含哨兵 | ✅ `42` + `AM5c4e17` |

**最后两条是关键**：前五条只证明「回答里写了字」，后两条才证明
「照着那个提示做，真的能拿到结果」。

> 首次跑 `recovered_has_sentinel` 红了。排查是**测试的解析写错**：
> `GetTask` 返回的是 task 本身（`result` 层），不是 `SendMessage` 的
> `{"task": {...}}` 包装，我误用了按 `result.task` 取产物的辅助函数。
> 产品行为一直是对的（`final_state` 当时就是 `COMPLETED`）。

## 3. 未覆盖 / 后续

| 项 | 说明 |
|---|---|
| **同步等待的断连检测** | 目前客户端断开后仍轮询到 deadline。不影响正确性（任务独立），但浪费一次连接的等待窗口。要做的话在 `send_message` 的轮询循环里查 `request.is_disconnected` —— 需要把 `Request` 传到 service 层，属于接口改动 |
| **`syncTimeoutS` 的 A2A 官方字段名** | 用的是 `configuration.syncTimeoutS`。A2A v1.0 规范对 `configuration` 内的键没有强制约定，若将来对齐官方 SDK 需复核 |
| **`INNER_A2A_SYNC_TIMEOUT_S` 默认值** | 仍是 60s，没动。理由是「秒回 or 明确转异步」比「卡 3 分钟」体验更好；若真实调用方普遍期望长窗口，可调到 90–120s 再看 |

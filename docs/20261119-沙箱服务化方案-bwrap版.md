# 沙箱服务化方案（bwrap 运行时）

> 日期：2026-11-19　状态：**方案（未实施）**
> 前序：`docs/20261119-沙箱服务化评估.md`（评估：该拆，运行时选 B）
> 本文回答三件事：**怎么拆**、**开关怎么兼容**、**要不要上 MinIO**
>
> 决策已定：**运行时用 bubblewrap（bwrap），沙箱做成独立服务，与 app 解耦。**
> 保留 `HLZ_SANDBOX_MODE` 开关，兼容「不用池」与「用池」两种形态。

---

## 0. 一句话结论

**拆，用 bwrap，不要 MinIO（现在）。**

- bwrap 让沙箱服务**不需要 docker.sock**，逃逸门槛从「一条命令」变成「要内核漏洞」；
- 「池」在 bwrap 下**不是省创建成本**（6ms），而是**省 Python 导入成本**（1161ms）——
  所以池的形态要重新设计，不能照搬 Docker 容器池；
- **MinIO 现在不需要**：单机 + 共享卷已经覆盖前两个需求，
  只有「跨机器」才需要，而当前没有跨机器的部署需求；
- **`HLZ_SANDBOX_MODE` 的 `off` 分支必须逐字节保持现状**——这是兼容性的核心约束。

## 1. 先看三个实测数据（它们决定了架构）

| 测什么 | 结果 | 对架构的含义 |
| --- | --- | --- |
| bwrap 空转 | **6 ms**（对照裸 python 19ms） | bwrap 开销可忽略，**不需要为省创建成本做池** |
| `import pandas` | 618 ms | 冷进程昂贵 |
| `import pandas + matplotlib` | **1161 ms** | 用户可感知的等待 |
| 同进程复用（已导入） | **1 ms** | 池的全部价值在这里 |
| fork 后子进程可见父进程内存 | **是**（COW） | 预热池**会跨租户泄漏**，不能简单复用父进程 |

**关键推论**：Docker 容器池省的是 624ms 创建成本；bwrap 没有这个成本。
所以「池」必须重新定义——见 §4。

## 2. 为什么「包要装在 app 镜像里」是错的（订正）

> 这是本文档对前一份评估里一句错误表述的订正。

评估文档 §7.6 写了「选 B 意味着放弃『沙箱镜像是独立镜像』这个隔离层，包清单只剩 app 镜像一份」。
**这句只在「bwrap 跑在 app 容器内」这一种部署形态下成立，不是 bwrap 的要求。**

bwrap 不提供 rootfs，它只把**已存在的目录**按你给的布局 bind 进新命名空间。
所以「用谁的 `/usr`」完全取决于 **bwrap 从哪个进程启动**：

```
bwrap 跑在 app 容器内      → 用 app 的 /usr    → 包要装 app 镜像（这才是我说的情况）
bwrap 跑在沙箱服务容器内    → 用服务的 /usr    → 包装沙箱服务镜像，app 一个包都不用加
bwrap + --ro-bind /opt/rootfs / → 用 /opt/rootfs → 服务容器本身可以极小，多套 rootfs 并存
```

**实测验证**（同一个 bwrap，只改 bind 源）：

```
C. bwrap --ro-bind /opt/sbx-rootfs /   →  numpy=无  pandas=无  matplotlib=无
D. bwrap --ro-bind /usr ...            →  numpy=有  pandas=有
```

同一台机器、同一个 bwrap，包从「有」变「无」——证明运行时文件系统**完全独立于 app**。

**结论：`hlz-sandbox` 那一层完整保留**，只是从「Docker 容器根文件系统」
变成「沙箱服务容器根文件系统」。包清单（`backend/sandbox/Dockerfile`）继续维护，
`tests/test_image_dependencies.py` 的校验目标改成「沙箱服务镜像 vs requirements」。

**它对的地方**（本方案接受，不再争辩）：

> bwrap / Seatbelt：**独立内核攻击面 ❌ 共享宿主内核**、**cgroup 资源上限 ❌ 全模块 0 处命中**、
> **uid/user ns 真正切换 ❌**
>
> 「CC 那套不是『更轻的容器』，是另一个维度……它解决的是『同一用户，别让 agent 把机器搞坏』，

**但内核攻击面那一条改参数改不掉。** 这是选 bwrap 就接受的代价。

### 2.5.3 本方案的取舍依据：用户是内部可信的

> **决策（2026-11-19，用户确认）：用户是内部用户，走「先 bwrap，后补 gVisor」。**

那条文档的威胁模型是「**不可信的用户代码**」，所以它要求内核边界。我们的实际情况不同：

| | 不可信用户（那份文档的假设） | **内部可信用户（我们的实际）** |
| --- | --- | --- |
| 主要风险 | 有人故意攻内核 | 模型写错代码搞坏工作区 / 误删文件 / 死循环 |
| 内核边界 | **必需** | 有价值，但非阻断 |
| 跨租户读文件 | 致命 | 不能有（已解决：只 bind 自己子树） |
| 资源失控 | 致命 | 需要（已解决：prlimit） |
| 结论 | gVisor | **bwrap 起步** |

**所以本方案不否认那份文档的结论，只是把它的适用条件写明了。**
将来用户变成外部不可信时，按 §9.5 换 Executor 实现即可——接口不变。

**同时，本机现在也上不了 gVisor**（实测）：`/dev/kvm` 不存在，
Docker Desktop 的 runtime 只有 `runc` / `nvidia`，加不了自定义 runtime。

### 2.5.4 关于持久化：两边都对，取决于是否跨机器

那份文档把 MinIO 列进技术选型表。它画的架构是单机 `Linux Host` + `Docker Engine`，
但没说单机还是多机。

实测事实：三个 app 实例共享同一个 `appdata` 卷（同一 inode 330768）。
**同机多实例 → 共享卷已够；跨机器 → 才需要对象存储。**

Aivory 同款判断（`docker-compose.yml` §4.5-F 注释）：
「No S3/OSS/MinIO needed ... multi-replica deployments must use S3/OSS」。

**所以本方案不反对 MinIO，只是把它放到了「跨机器时才做」的位置（阶段 4），
并且现在就把 `ArchiveBackend` 接口留出来**——将来加实现，不动调用方。

## 3. 服务边界：拆什么、留什么

### 3.0 为什么要参考 Aivory：抄它的「外壳」，不抄它的「内核」

Aivory 的 `sandbox-service/` 是本仓库能找到的最贴近的实现（独立服务 + HTTP + 文件持久化）。
但**它有两个点我们不该抄**，且它自己的代码里就承认了第一个：

| | Aivory | 我们 | 依据 |
| --- | --- | --- | --- |
| 协议 `/sessions` `/exec` `/files` | ✅ | **照抄** | 形状对：会话 + 执行 + 文件三个动作 |
| 稳定归档 key（会话 id 非实例 id） | ✅ 踩坑后修的 | **照抄** | `app.py:224` 注释写明了修法 |
| local 卷默认 + S3 可选 | ✅ | **照抄** | 正是「先不上 MinIO」的实现 |
| 探测/回收/并发上限这些护栏 | ✅ 很完整 | **照抄** | `SANDBOX_MAX_*` 一整组 |
| **执行内核：每次新起 python** | ❌ 慢 | **改** | 5 次调用 5528 ms，见 §4 |
| **权限：挂 docker.sock** | ❌ 等于 root | **改 bwrap** | 它的 compose 注释自称 F1 风险 |

Aivory 的 `docker-compose.yml` 里那段 SECURITY NOTE 原文：

```
This service mounts /var/run/docker.sock and uses it to create/start/exec
containers. That socket is root-equivalent on the host: anyone who can drive
it (i.e. anyone who reaches this service) can take over the host ...
The architecture REQUIRES the socket, so it is intentionally kept
```

**「架构上需要这个 socket」——只有当你用 Docker 当沙箱运行时才成立。** 我们选 bwrap，这一句就不适用了（§7.3 有实测：同一个服务不挂 sock 也能隔离）。

所以结论：**走 Aivory 的路线，但把它的约束换成我们的**——

```
Aivory 路线 = 独立服务 + HTTP 协议 + 卷/S3 双后端 + 稳定归档 key + 完整护栏
我们的差别 = 执行内核换成 bwrap + 纯净 fork（快 7 倍，且不需要 root 等价权限）
```

## 4. 「池」在 bwrap 下要重新设计（这是最容易照抄错的地方）

### 4.0 先回答一个容易含糊的问题：是「一个沙箱」还是「沙箱池」？

**是池，而且必须是池。** 依据不是「多用户所以要多份」，而是**隔离单位本来就按用户切**：

```
❌ 一个沙箱服务所有用户
   bwrap 只 bind 一个 /ws 目录 → A 和 B 的 workspace 要么同一个（互相看得见）
   要么得在同一个挂载树里共存 → 等于没有隔离

✅ 每个用户一份隔离环境（= 池里的一个「槽」）
   槽固定绑定该用户的 workspace，槽之间不共享文件系统、不共享内存
```

实测佐证（§5.3）：只 bind 自己的目录时 A 读不到 B；bind 父目录就泄漏。

**但「池」在这里的含义和 Docker 容器池不同**——见 4.1。

### 4.0.1 为什么不能「一个共享父进程按请求切换 workspace」

这条路看起来最省内存（一个预热进程服务所有用户），我实测过，**走不通**：

```
A. 有 --cap-drop ALL:  CapEff=0   unshare(CLONE_NEWNS)=EPERM  bind=EPERM
B. 不 drop cap:        CapEff≠0   unshare(CLONE_NEWNS)=EPERM  bind=EPERM
```

原因：`bwrap --unshare-all` 已经用掉了那次 `CAP_SYS_ADMIN`，子进程无法再 `unshare(CLONE_NEWNS)`
创建新的 mount namespace 去重挂 `/ws`。**所以 workspace 必须在 bwrap 启动时就绑定好，运行期改不了。**

由此推出三条硬结论：

1. **槽 = 用户**，一个槽绑定一个 workspace，生命周期内不变；
2. **槽的数量上限 = 并发用户数上限**，不能靠「一个槽轮换服务多个用户」省内存；
3. 换用户的 workspace 只能**销毁槽再重建**（付 1.2s 预热成本）。

### 4.1 Docker 容器池 vs bwrap 的差别

```
Docker 池解决的问题：
  docker run 624ms  →  池化后 0ms   ← 建容器贵
  
bwrap 的现实：
  bwrap 启动 6ms    →  不池也就 6ms  ← 建沙箱不贵
  但 import pandas 618ms / +plt 1161ms  ← Python 导入贵
```

**所以 bwrap 下的「池」不是「一组待用沙箱」，而是「一组已预热的 Python 解释器」，每个绑一个用户。**

### 4.2 四种池形态，只有第四种同时满足「快」「安全」「行为不变」

> 注意：这四种讲的都是**单个槽内部**怎么执行。无论选哪种，
> **槽本身都是「一用户一个」**（§4.0.1 已证明不能一个槽轮换服务多人）。

| 形态 | 做法 | 每次 exec | 问题 |
| --- | --- | --- | --- |
| **A. 槽内不预热**（Aivory 做法） | 每次 `bwrap python3 -c ...` | **1105 ms** | 用户可感知；5 次调用 5528ms |
| **B. fork 复用被污染过的父进程** | 父进程预导入 + 执行过用户代码 + `fork()` | 8 ms | ❌ **跨租户泄漏**（见 4.3） |
| **C. 长活 REPL** | 槽里跑一个常驻交互式解释器 | 1 ms | ❌ 变量跨 exec 残留、崩了带脏状态 |
| **D. 纯净父进程 + fork** ★ | 父进程**只预热、永不执行用户代码**；每次 exec 从它 `fork()` | **8.8 ms** | ✅ 无 |

**D 的实测结果**：

```
父进程预热 import pandas+matplotlib : 1248 ms（一次性，每用户）
用户 A exec（试图塞 LEAK 变量）      : 6.2 ms
用户 B exec（查 A 留下的 LEAK）      : 4.7 ms → 返回「干净」
用户 B 用 pandas                    : 11.8 ms → sum=6（证明预热生效）
用户 B 用 numpy                     : 11.4 ms → 499999500000
父进程自己被污染了吗                  : 没有（干净）
```

**5 次调用总耗时对比**：

```
Aivory 路线（每次新进程）   : 5528 ms  (平均 1105 ms/次)
纯净 fork 路线（D）         : 745 ms 预热 + 44 ms = 789 ms  (平均 8.8 ms/次)
```

**7 倍差距，而且「用户变量不跨 exec 保留」的行为与现在完全一致**
（现在每次 exec 也是 `python -c` 全新进程，见 §11 证据表），所以没有任何行为取舍。

### 4.3 B（fork 复用被污染的父进程）为什么不能用

实测：

```
父进程预热时塞 {"user_A_secret": "A的数据"}
fork 出的「用户 B」子进程读到: {'user_A_secret': 'A的数据'}      ← 泄漏
```

`fork` 是写时复制：子进程**能读到**父进程的**全部**内存状态。
如果父进程服务过用户 A，之后 fork 给用户 B 的子进程就读得到 A 残留的模块级变量、
`lru_cache`、第三方库的全局缓存。这与多实例 MCP 那次「串名」是同一类问题。

**D 的关键在于：父进程从头到尾一行用户代码都没执行过。** 它只有
「Python 解释器 + 预导入的标准库/三方库」这份干净内存，不含任何用户数据。

### 4.4 D 的进程模型

```
池 = 一组「槽」，每个槽 = 一个用户
槽 = bwrap 进程 + 里面一个纯净父解释器 + 该用户的 /ws 挂载

  创建:  bwrap 启动 + import 依赖            ≈ 1200 ms（一次性）
  执行:  父进程 fork() → 子进程跑用户代码      ≈ 9 ms
        子进程写结果到 pipe → 退出（os._exit，不跑 atexit）
  回收:  空闲 HLZ_SANDBOX_IDLE_TTL_S（默认 900s）→ 整槽销毁 + 归档

并发上限: HLZ_SANDBOX_MAX_SLOTS（新名，默认 3；原 MAX_CONTAINERS 保留作别名）
溢出策略: HLZ_SANDBOX_OVERFLOW（默认 queue，见 §4.7.3）
```

**必须遵守的三条**（否则 D 退化成 B 或有隐患）：

1. **父进程绝不 `exec`/`eval` 用户代码**，只能 `fork` 后由子进程执行。
2. **子进程必须 `os._exit()`**，不能正常退出——否则会跑父进程的 atexit/lockfile 释放逻辑。
3. **父进程的 preload 清单必须固定**，不能按用户请求动态 import（那会把用户数据带进父进程）。

> 关于「变量持久性」：D 下 `x=1` 之后的下一次 exec 读不到 `x`，**与现状一致**。
> 若将来要 ChatGPT 式持久变量，那条路是「长活 REPL」，需要单独解决状态污染与崩溃恢复——
> 不要为了它牺牲掉 D 的隔离性。

### 4.5 内存预算：一个槽到底占多少（这决定池的上限）

**实测数据**（本机 Docker Desktop，用 `MemAvailable` 差值测，最权威）：

| 预导入清单 | 单进程 RSS |
| --- | --- |
| 空解释器 | 9.5 MB |
| + numpy | 30.1 MB |
| + numpy + pandas | 71.6 MB |
| + numpy + pandas + matplotlib | **89.0 MB** |

**但 RSS 相加会重复计算共享库页**，实测 5 个槽：

```
5 个进程 RSS 相加     : 443 MB   ← 高估（每个都把自己的 .so 算一遍）
5 个进程 PSS 相加     : 308 MB   ← 接近真实
系统 MemAvailable 变化: 243 MB   ← 最权威
```

**所以每个槽的真实增量约 49 MB**（不是 89 MB）。按此推算：

| 槽数 | 真实占用 |
| --- | --- |
| 10 | ≈ 0.47 GB |
| 30 | ≈ 1.42 GB |
| 100 | ≈ **4.74 GB** |
| 300 | ≈ 14.2 GB |

> ⚠️ 上面是**第一轮**（5 个槽压测）的口径，单槽 ≈49 MB。
> §4.7.5 又按「1 / 2 / 3 槽」重新测了一遍，得到**单槽边际 ≈53 MB**。
> 两者量级一致（差 8%），差异来自测量点不同（3 槽时共享页还没摊薄完）。
> **规划用哪一个都行，但要知道这是估算，不是精确值。**

**结论：一人一槽在内网规模下可行**（100 并发用户约 4.7~5.3 GB），
但必须有两道闸：

1. **`HLZ_SANDBOX_MAX_SLOTS`**（默认 3，见 §4.7.5）——超了按 `OVERFLOW` 策略处理，不是无限开
2. **`HLZ_SANDBOX_IDLE_TTL_S`**（默认 300s，见 §4.7.5）——空闲回收，避免「开过就一直占着」

> ⚠️ 这两个数必须**按真实负载调**，别照抄。上面的表是在「预导入 pandas+matplotlib」
> 的前提下测的；如果某个部署只预导入 numpy，单槽降到约 30 MB 量级。
>
> ⚠️ 更要紧的是**池的并发争用**：`MAX_SLOTS` 个槽、更多的人同时用，就有人在排队
> 等预热。这是 §10 待决策第 3 条要按实际用户数定的。

### 4.6 池与「多实例」的关系

```
app 实例 ×3  ──HTTP──►  沙箱服务（单副本）
                          └── 池：按需扩缩容
```

- **池在服务里，不在 app 里**——所以 3 个 app 实例共享同一份池（现在每实例各建各的，3 份池）
- 用户请求打到哪个 app 实例无所谓，只要都走同一个沙箱服务
- 这也意味着**沙箱服务本身要能被 3 个 app 实例安全并发调用**（§10 第 5 条）

### 4.7 动态扩缩容：能扩什么、不能扩什么

> 这一节回答「池是不是能自己动态扩缩容」。

#### 4.7.1 不能：预先建「通用槽」给任意用户

槽在 **bwrap 启动时就绑定好了 workspace**，运行期改不了。实测两条路都不通：

```
有 --cap-drop ALL:  CapEff=0   unshare(CLONE_NEWNS)=EPERM  bind=EPERM
不 drop cap:        CapEff≠0   unshare(CLONE_NEWNS)=EPERM  bind=EPERM
```

原因（§4.0.1）：`bwrap --unshare-all` 已经用掉那份 `CAP_SYS_ADMIN`，
子进程无法再 `unshare(CLONE_NEWNS)` 去重挂 `/ws`。

**所以槽是「专属」的，不是「通用」的**：不存在「建 8 个通用槽，谁来都能用」。

#### 4.7.2 能：按需建、按需回收——而且比 Docker 便宜

实测成本（本机 Docker Desktop）：

| 操作 | 成本 | 备注 |
| --- | --- | --- |
| **建空槽 + 销毁** | **27 ms** | 这是扩缩容的真实成本 |
| 空槽 + `import numpy` | 281 ms | |
| 空槽 + `numpy+pandas` | 686 ms | |
| 空槽 + `numpy+pandas+matplotlib` | 852 ms | |
| 已有槽再执行一次 | **8.8 ms** | 模块已在内存 |
| （对照）`docker run` | 624 ms | 现在 Docker 池要省的就是这个 |

**关键结论：bwrap 的建槽成本是 Docker 的 1/23，所以「动态扩缩容」在 bwrap 下更容易，不是更难。**

#### 4.7.3 槽满了怎么办：`HLZ_SANDBOX_OVERFLOW` 开关

槽数达到 `MAX_SLOTS` 之后又来了一个新用户，有三种可能的行为。
**这个选择没有唯一正确答案，取决于槽够不够用**，所以做成开关：

```bash
HLZ_SANDBOX_OVERFLOW=queue    # 默认
HLZ_SANDBOX_OVERFLOW=evict
HLZ_SANDBOX_OVERFLOW=reject
```

| 取值 | 行为 | 代价 | 适用场景 |
| --- | --- | --- | --- |
| **`queue`**（默认） | 排队等一个槽空出来，**不淘汰任何槽** | 第 N+1 个用户等前面的人跑完（通常几秒）；超时报错 | **槽少（`MAX_SLOTS ≤ 5`）、单机资源紧**。淘汰一个槽要 27ms+852ms 重新预热，比等几秒更亏 |
| **`evict`** | 淘汰**最久未用的空闲槽**（先归档），再建新槽 | 被淘汰的用户下次调用要重新预热（≈880ms）；忙碌槽不淘汰 | 槽多（`MAX_SLOTS ≥ 8`）、用户多但每个用得少 |
| **`reject`** | 立刻返回「沙箱繁忙」，不排队 | 用户直接看到失败，需要自己重试 | 上层已有自己的重试/排队机制，不想在这里再叠一层 |

**三者的共同点（无论选哪个都一样）**：

1. **忙碌中的槽永不淘汰**——否则会掐断正在跑的代码
2. **淘汰前必须归档该用户的 workspace**（§7.5 稳定 key）
3. **空闲 TTL 到期一律销毁**——这个不受 overflow 影响

**怎么选**（给当前部署的建议）：

```
MAX_SLOTS = 3（单机、最多 3 并发）
  → 用 queue
     理由：3 个槽已经等于并发上限，overflow 只在「第 4 个人来了」时触发；
           淘汰等于频繁重建（27ms + 852ms），而排队通常只要几秒。
```

```
MAX_SLOTS = 30（多用户、单次调用短）
  → 用 evict
     理由：让 30 个人随时能进，比让第 31 个人干等更合理；
           被淘汰的人下次进来重新预热 880ms，可接受。
```

```
沙箱服务前置了自己的队列 / 有 SDK 重试
  → 用 reject
     理由：不再叠一层排队，避免「双重排队」导致超时算不准。
```

#### 4.7.4 扩缩容模型（含 overflow 分支）

```
请求到来（user_id, code）
  │
  ├─ 池里有该 user_id 的槽吗？
  │    ├─ 有 → 直接用                              ≈ 8.8 ms
  │    └─ 没有 ↓
  │
  ├─ 当前槽数 < HLZ_SANDBOX_MAX_SLOTS？
  │    ├─ 是 → 建新槽（绑该用户 workspace）         ≈ 27 ms + 首次导入
  │    └─ 否 ↓（已达上限，看 overflow 开关）
  │
  ├─ HLZ_SANDBOX_OVERFLOW 的三种分支：
  │    ├─ queue  ── 等到有槽空出（或超时）→ 建槽
  │    │            等待时长写进结果的 queue_wait_ms
  │    ├─ evict  ── 有空闲槽？
  │    │            ├─ 有 → 归档它 → 销毁它 → 建新槽 ≈ 54 ms
  │    │            └─ 没有（全忙）→ **退化成 queue**
  │    │                           （busy 槽永不淘汰，这是硬规则）
  │    └─ reject ── 立刻 503「沙箱繁忙」，建议客户端重试
  │
  └─ 空闲 TTL 到期 → 销毁槽 + 归档                  ≈ 27 ms
```

**四个要点**：

1. **扩容 = 按需建槽**。不要预建一批空槽等着——27 ms 不值得，而且预建的空槽没绑用户，用不上。
2. **`MAX_SLOTS` 是保护阀**，不是要提前分配的大小。
3. **`evict` 在没有空闲槽时自动退化成 `queue`**——因为「不许淘汰忙碌槽」是硬规则，
   不是可配置项。这个退化必须写日志，否则运维会以为开关没生效。
4. **`queue` 和 `evict` 都要报 `queue_wait_ms`**，这样「要不要调大 `MAX_SLOTS`」有数据支撑。

#### 4.7.5 内存预算：按「单机 / 最多 3 并发」实测算

> 这一节给的是**当前部署**的预算，不是通用结论。换机器要重测。

实测（本机，用 `MemAvailable` 差值，最权威）：

| 状态 | 占用 |
| --- | --- |
| **1 个槽常驻**（已预热 pandas+matplotlib，空闲） | **27 MB** |
| 2 个槽 | 90 MB |
| **3 个槽（并发满）** | **143 MB** |
| 单槽边际成本 | **≈ 53 MB** |

**加上执行余量**（跑代码时子进程自己还要占内存）：

| 每槽执行余量 | 3 槽峰值 |
| --- | --- |
| +50 MB | 293 MB |
| **+100 MB** | **443 MB** ← 建议按这个规划 |
| +200 MB | 743 MB |

**当前部署的推荐配置**：

```bash
HLZ_SANDBOX_MAX_SLOTS=3            # = 测试的最大并发数
HLZ_SANDBOX_OVERFLOW=queue         # 槽少，排队比淘汰划算
HLZ_SANDBOX_IDLE_TTL_S=300         # 单机省内存：5 分钟空闲就回收
HLZ_SANDBOX_PRELOAD=numpy,pandas,matplotlib
```

**峰值内存约 443 MB**（3 槽 + 执行余量）。这个量级单机完全放得下。

> ⚠️ 之前文档里写「单槽约 47 MB / 49 MB」是另一台机器的口径，本次实测是 **53 MB**。
> 量级一致，但**具体数字必须在本机重测**——它随 Python 版本、pandas 版本、镜像里的库大小变化。
> 重测方法：见 §11 的证据表（`mem_budget.py` 的测法：开 N 个槽，读 `/proc/meminfo` 的 `MemAvailable` 差值）。

#### 4.7.6 关于「初始化 1 个槽」

有人会想「启动时先建 1 个槽等着」。**不建议**，理由：

- 槽是**专属**的（§4.7.1），启动时不知道会是谁来用，建出来的槽绑不上人
- 空槽建起来只有 27 ms 的价值，而它会**常驻占 27 MB**
- 第一个请求进来时现建，用户完全感知不到（27 ms + 首次 import 852 ms，
  而这 852 ms 本来就要付）

**唯一合理的「预建」形态**：为「**第一个请求进来的用户**」建槽后**不按空闲 TTL 回收**，
让他后续调用一直是 8.8 ms。这是个可选优化（`HLZ_SANDBOX_PIN_FIRST_SLOT=1`），
但单机测试场景下没必要——先让它能被回收，省 27 MB。

#### 4.7.7 一个必须知道的限制

槽是专属的，所以「扩缩容」只能扩「**同时活跃的用户数**」，不能扩成「一个槽服务很多人」。

| `MAX_SLOTS` | 100 个用户同时用时的结果 | 常驻内存 |
| --- | --- | --- |
| **3（当前配置）** | 3 个在跑，97 个排队 | ≈ 0.16 GB |
| 8 | 8 个在跑，92 个排队 | ≈ 0.4 GB |
| 30 | 30 个在跑，70 个排队 | ≈ 1.4 GB |
| 不设限 | 谁都能跑 | 内存不可控 ❌ |

（内存按 §4.7.5 的实测口径：单槽边际 ≈53 MB。）

**当前部署只有 3 个并发用户，所以 `MAX_SLOTS=3` 是够的。**
用户量上来时再调，不要现在就按 100 用户规划——那是浪费内存。

#### 4.7.8 明确不做的

- ❌ **不做「预建一批通用空槽」**——槽绑不上用户，用不上（§4.7.1）
- ❌ **不做「一个槽轮换服务多用户」**——`unshare` 被拒，技术上做不到（§4.7.1）
- ❌ **不做「无上限动态扩」**——内存会失控，必须有 `MAX_SLOTS`
- ❌ **不做跨机器的池共享**——池在单进程内存里；要多机就得多副本 + 每副本各自的池（§4.6）
- ❌ **不做「忙碌槽可被淘汰」**——`evict` 只在有空闲槽时生效，全忙时自动退化成 `queue`（§4.7.4）

## 5. 路径：共享卷（不要 MinIO 的关键）

### 5.1 现状已经天然满足

实测：

```
三个 app 实例都挂 hlzscale_appdata -> /app/backend/data
从沙箱侧写入的文件，app-1 和 app-3 立刻可见（同一 inode 330768）
```

**所以沙箱服务只要也挂这个卷，路径问题自动消失**——不需要任何跨层推算：

```
app     看到  /app/backend/data/workspaces/u_xxx/
沙箱服务 同时也挂  appdata:/app/backend/data  （或只挂 workspaces 子树）
bwrap    --bind /app/backend/data/workspaces/u_xxx /ws
```

这与评估文档 §4.3 的**方案 C（共享卷 + 约定路径）**一致，且实测证明可行。

### 5.2 目录约定

```
appdata 卷
└── workspaces/
    └── <user_id>/            ← 用户根（file_read/file_write 和沙箱都指向这里）
        ├── .subagents/       ← 子 agent 工作目录
        ├── uploads/          ← 用户上传
        └── outputs/          ← 模型产物
```

**路径由服务算，不由 app 传**（评估文档 §4.3 方案 A）——因为两边看到的是同一个卷，
服务内用 `user_id` 就能算出路径，不存在「app 算的是容器内路径」的问题。
`_reject_unsafe_segment` 的规范化逻辑跟着搬进服务。

### 5.3 多租户隔离：只 bind 自己那棵子树

实测（这是必须做对的）：

```
bind 整个 /ws        →  读到别的用户文件 ✗
只 bind /ws/u1       →  读不到 ✓
```

**每条 bwrap 命令只 `--bind <该用户目录> /ws`，绝不 bind 父目录。**

## 6. 开关兼容：`HLZ_SANDBOX_MODE` 怎么保留

### 6.1 现有语义（必须先保住）

```python
# app/sandbox/config.py:30
VALID_MODES = ("off", "auto", "strict")
```

| mode | 行为 | 兼容要求 |
| --- | --- | --- |
| `off`（默认） | 完全不进沙箱，走进程内 `subprocess` | **必须逐字节保持现状** |
| `auto` | 优先沙箱；不可用时退回进程内，结果首行标「本次未隔离」 | 服务不可达时也要能降级 |
| `strict` | 优先沙箱；不可用时直接失败 | 服务不可达时报错 |

### 6.2 服务化后开关要做的事

`HLZ_SANDBOX_MODE` 的语义**不变**，但它现在还要决定「走哪条执行路径」：

```
off      →  进程内 subprocess（现状，不动）
auto     →  沙箱服务 HTTP  ──失败──►  进程内 subprocess + 降级说明
strict   →  沙箱服务 HTTP  ──失败──►  抛错
```

**新增三个开关，与 mode 正交**：

```bash
# ① 执行后端：inproc（进程内 docker）| service（独立沙箱服务）| bwrap-local（本地 bwrap，开发用）
HLZ_SANDBOX_BACKEND=service        # 服务化后默认

# ② 沙箱服务地址与鉴权
HLZ_SANDBOX_SERVICE_URL=http://sandbox:8021
HLZ_SANDBOX_SERVICE_TOKEN=<签名密钥>

# ③ 池（只在 backend=service 时有意义）
HLZ_SANDBOX_MAX_SLOTS=3            # 保护阀：同时最多几个槽 = 同时能服务几个人
HLZ_SANDBOX_OVERFLOW=queue         # 槽满时怎么办：queue | evict | reject（§4.7.3）
HLZ_SANDBOX_IDLE_TTL_S=300         # 空闲多久回收槽
HLZ_SANDBOX_PRELOAD=numpy,pandas,matplotlib
```

### 6.2.1 三个开关的完整取值表

**① `HLZ_SANDBOX_MODE`**（决定「用不用沙箱」）

| 取值 | 行为 | 服务不可达时 | 默认 |
| --- | --- | --- | --- |
| `off` | 完全不进沙箱，进程内 subprocess | — （根本不调服务） | ✅ |
| `auto` | 优先沙箱；失败退回进程内 | 降级，结果首行标「本次未隔离」 | |
| `strict` | 优先沙箱；失败直接报错 | 抛异常，不降级 | |

**② `HLZ_SANDBOX_BACKEND`**（决定「用哪个实现执行」）

| 取值 | 用什么 | 何时用 | 默认 |
| --- | --- | --- | --- |
| `inproc` | 现有 Docker（`runtime.py`） | **回滚路径**，不删 | |
| `service` | HTTP 调沙箱服务 | 服务化之后 | ✅ |
| `bwrap-local` | 进程内直接 bwrap | 本地开发，不起服务也能测 | |

> `backend` 只在 `mode != off` 时被读取。`mode=off` 时后端配置被完全忽略。

**③ `HLZ_SANDBOX_OVERFLOW`**（决定「槽满了怎么办」，详见 §4.7.3）

| 取值 | 槽满时 | 优点 | 缺点 | 默认 |
| --- | --- | --- | --- | --- |
| `queue` | 阻塞等槽空出（带超时） | 不浪费已预热的槽 | 第 N+1 个用户变慢 | ✅ |
| `evict` | 淘汰最久未用的**空闲**槽（先归档） | 新用户快（≈54ms） | 被淘汰者下次重新预热 ≈880ms | |
| `reject` | 立刻 503 | 不双重排队 | 用户看到直接失败 | |

> **非法取值一律退回 `queue`**（与 `mode` 非法退回 `off` 的兜底思路一致，但更安全：
> 退回 `queue` 保证请求最终能成功，退回 `reject` 会直接失败）。

### 6.2.2 三个开关的组合矩阵

| 场景 | MODE | BACKEND | OVERFLOW | 效果 |
| --- | --- | --- | --- | --- |
| 现状（默认） | `off` | 任意 | 任意 | 走进程内，后两个开关完全被忽略 |
| 灰度放量 | `auto` + `MVP_USERS` | `service` | `queue` | 白名单走沙箱，其余进程内 |
| 单机满负荷测试 | `strict` | `service` | `queue` | 3 槽，第 4 个排队 |
| 多用户、调用短 | `auto` | `service` | `evict` | 槽多时新用户不用等 |
| 上层已有队列 | `auto` | `service` | `reject` | 不叠第二层排队 |
| 出问题回滚 | `auto` | **`inproc`** | 任意 | 一个变量切回 Docker，不动镜像 |

### 6.3 为什么「开关」和「后端」必须分开

如果把两者合成一个开关，会失去这些组合：

| 想做的事 | mode | backend | 说明 |
| --- | --- | --- | --- |
| 现状，不用沙箱 | `off` | 任意 | 后端配置被忽略 |
| 灰度：白名单用户走服务 | `auto` + `MVP_USERS` | `service` | 逐步放量 |
| 本地开发调试 | `auto` | `bwrap-local` | 不起服务也能测 |
| 回滚到 docker 方案 | `auto` | `inproc` | 保留旧路径 |

**回滚能力是硬要求**：服务化上线后如果出问题，要能一个环境变量改回 `inproc`，
不用回滚镜像。所以 `runtime.py` 的 Docker 实现**不删**，只是不再是默认。

### 6.4 `off` 分支的兼容测试（必须写）

```python
def test_off_mode_never_touches_sandbox_service(monkeypatch):
    """mode=off 时，即使服务地址配了也不许发请求。"""
    # 关键：不是「服务返回了什么」，而是「根本没发请求」
    ...
```

> ⚠️ 判定「没发请求」必须**观察网络层**（mock 掉 httpx 后断言 0 次调用），
> 不能只看输出——输出对了但偷偷发了请求，同样是违规（会多一次跨服务依赖）。

## 7. MinIO：现在不需要（附判据）

### 7.1 三个问题，只有第三个需要对象存储

| 问题 | 为什么 | 最小解法 | MinIO |
| --- | --- | --- | --- |
| ① 沙箱进程重启后 workspace 还在吗 | `/ws` 是 tmpfs，重启即丢 | 卷 + tar 归档 | **不需要** |
| ② 多个沙箱服务副本之间共享吗 | 单机多副本 = 同一台机器同一块盘 | **共享卷已够** | **不需要** |
| ③ 跨机器（真分布式）共享吗 | 不同机器本地盘互不可见 | 对象存储 / NFS | **需要** |

### 7.2 当前部署形态落在 ①②之间

实测事实：

```
三个 app 实例共享同一个 appdata 卷（同一 inode 330768）
workspace 总量 116 KB（6 个用户）
app 镜像里没有 minio / boto3（全仓 0 命中）
```

**只要沙箱服务和 app 在同一台机器，共享卷就够。** 加 MinIO 会多一个服务、多一套鉴权、
多一处故障点，却解决不了当下的任何问题。

### 7.3 Aivory 也这么做（同源证据）

Aivory 的 `sandbox-service/docker-compose.yml` 里 local 归档后端的注释写得很直接：

```
§4.5-F zero-config workspace persistence: the admin `storage_provider`
defaults to "local", so reaped /workspace tarballs are archived here (the
named volume below) and RESTORED when the conversation runs code again ...
No S3/OSS/MinIO needed. ... Single-node only (a plain volume isn't shared
across replicas); multi-replica deployments must use S3/OSS.
```

**它把「local 卷」和「S3/OSS」做成两个后端，靠配置切换**，默认 local。
这正是推荐做法——先 local，需要跨机器时再切 S3。

### 7.4 但现在就要把接口留出来

不做 MinIO ≠ 不用设计。归档后端要抽象成可切换的：

```python
class ArchiveBackend(Protocol):
    def put(self, key: str, data: bytes) -> None: ...
    def get(self, key: str) -> bytes | None: ...
    def delete(self, key: str) -> None: ...

class VolBackend:      # 现在实现这个（共享卷 + tar）
class S3Backend:       # 将来实现（minio / 阿里云 OSS）
```

`HLZ_SANDBOX_ARCHIVE_BACKEND=vol|s3`，默认 `vol`。
这样将来上 MinIO 只是加一个实现类，不动调用方。

### 7.5 归档时机（照 Aivory 的稳定 key 做法）

Aivory 踩过一次坑并在代码里写明了修法：

```
Workspace tarballs are keyed by THIS (conversation id), not the ephemeral
session id, so a workspace survives session recycle (§4.5-C G2 fix):
every create mints a fresh session uuid, but the reaper archives — and the
next create restores — under the same stable key.
```

**归档 key 必须是稳定标识（用户 id + 会话 id），不能是进程/沙箱实例 id。**
否则「回收后再唤起」永远恢复不到上次的工作区。

```
归档时机：
  · 空闲回收时（idle TTL 到期）
  · 服务优雅关闭时
  · 显式 DELETE 会话时
恢复时机：
  · 该用户下次执行代码、且本地无缓存时
```

## 8. 完整 bwrap 命令模板（把它当成规范）

这条命令是 §7.4 那份探针验证过的，五个坑全部规避：

```bash
bwrap \
  --unshare-all \
  --clearenv \
  --cap-drop ALL \
  --setenv PATH /usr/local/bin:/usr/bin:/bin \
  --setenv HOME /tmp \
  --setenv LANG C.UTF-8 \
  --setenv TZ Asia/Shanghai \
  --setenv MPLCONFIGDIR /tmp/mpl \
  --setenv PYTHONUNBUFFERED 1 \
  --ro-bind /usr /usr \
  --ro-bind /lib /lib \
  --ro-bind /lib64 /lib64 \
  --ro-bind /bin /bin \
  --ro-bind /sbin /sbin \
  --tmpfs /etc \
  --ro-bind /etc/fonts /etc/fonts \
  --bind "$USER_WORKSPACE" /ws \
  --tmpfs /tmp \
  --proc /proc \
  --dev /dev \
  --chdir /ws \
  prlimit --as="$MEM_BYTES" --cpu="$CPU_SECONDS" --fsize="$FSIZE_BYTES" \
  python3 "$SCRIPT"
```

**逐项都有实测依据**：

| 参数 | 为什么必须 | 不加会怎样（实测） |
| --- | --- | --- |
| `--unshare-all` | 容器内无 CAP_SYS_ADMIN，只靠 userns | 不加就 `Operation not permitted` |
| `--clearenv` | 防 app 密钥泄漏 | 实测 `DB_PASSWORD` 原样传进沙箱 |
| `--cap-drop ALL` | 清空能力 | 否则 `chroot` 能成功（实测） |
| 最小挂载集 | 防读 app 源码/`.env` | `--ro-bind / /` 实测读得到 `.env` |
| `--tmpfs /etc` | 防 bwrap 自动建可写 `/etc` | 不加时 `/etc/hosts` 写得进去（实测） |
| `--bind <用户目录>` | 只暴露自己那棵子树 | bind 父目录实测跨租户泄漏 |
| `prlimit` | bwrap 自身不做资源限制 | 无 `--help` 资源参数 |

### 8.1 已知限制（必须写进运维文档）

| 限制 | 原因 | 缓解 |
| --- | --- | --- |
| **没有独立内核攻击面** | bwrap 只用 namespace，共享宿主内核 | **接受**（内部可信用户，见 §2.5）；换 Executor 实现即可上 gVisor |
| **没有 cgroup 组总量** | bwrap 不碰 cgroup | `NPROC × AS` 才是真实上限，别当总量 |
| `RLIMIT_NPROC` 在 root 下失效 | 内核不对 root 执行 | **服务容器跑非 root**（实测 uid1000 下拦在第 18 个） |
| `prlimit --as` 是 per-process | 没有 cgroup 组总量 | 同上 |
| `--uid 1000` 是假降权 | userns 内映射，内核视角仍 0 | 别指望它，靠「容器本身非 root」 |
| 无独立 rootfs（若用宿主 `/usr`） | bwrap 不造 rootfs | 要么服务镜像带包，要么 `--ro-bind /opt/rootfs /`（实测可行） |

## 8.2 Executor 接口：让运行时可选（这是选 A 的关键）

> 选 A（先 bwrap 后 gVisor）的唯一技术前提：**执行层必须是可替换的实现，不能写死。**

### 8.2.1 接口定义

```python
# backend/sandbox_service/executor/base.py
from typing import Protocol

class ExecResult(NamedTuple):
    exit_code: int
    stdout: str
    stderr: str
    duration_ms: int
    truncated: bool


class Executor(Protocol):
    """执行用户代码的唯一边界。

    所有运行时差异（bwrap / gVisor / runc）都藏在这一个接口后面。
    上层（HTTP 层、池、归档）只依赖它，不知道底下是什么。
    """

    async def start(self, user_id: str) -> None:
        """准备该用户的执行环境（预热/建沙箱/起容器）。"""

    async def exec(
        self, user_id: str, code: str, *,
        code_type: str = "python",      # python | sh
        timeout_s: float = 120.0,
        cwd: str = "",
    ) -> ExecResult: ...

    async def destroy(self, user_id: str) -> None:
        """回收（归档由上层负责，这里只清执行环境）。"""

    async def health(self) -> tuple[bool, str]:
        """自检。返回 (ok, reason)。"""
```

### 8.2.2 三个实现

| 实现 | 文件 | 用什么 | 何时用 |
| --- | --- | --- | --- |
| `BwrapExecutor` | `executor/bwrap.py` | bwrap + 纯净 fork | **阶段 1 起** |
| `GVisorExecutor` | `executor/gvisor.py` | `docker run --runtime=runsc` | 用户变不可信时 |
| `InprocExecutor` | `executor/inproc.py` | 现有进程内 subprocess | `HLZ_SANDBOX_MODE=off` / 回滚 |

**`off` 模式下走 `InprocExecutor`**——这样开关和实现就统一了（见 §6）。

### 8.2.3 换运行时需要改什么（验收这个接口是否真的可替换）

上 gVisor 时**应该只改这些**：

1. 新增 `executor/gvisor.py`（约 200 行，`docker run` + `exec`）
2. `HLZ_SANDBOX_EXECUTOR=gvisor`
3. 无

**不应该改**：HTTP 层、池、归档、app 侧客户端、工具 schema。

> 若将来换实现时需要改 §1~§8 里的任何东西，说明这个接口没抽对。

#### 3.2 任务清单

| # | 任务 | 细节 | 验收 |
| --- | --- | --- | --- |
| 3.1 | 实现纯净 fork 槽 | 父进程**只预热、永不执行用户代码**（§4.2 D） | 用户 B 读不到用户 A 塞进模块的变量 |
| 3.2 | 子进程必须 `os._exit()` | 不跑父进程 atexit | 父进程状态不被污染 |
| 3.3 | 空闲回收 | `HLZ_SANDBOX_IDLE_TTL_S`（默认 900s） | 超时后槽被销毁 |
| 3.4 | `VolBackend` 归档 | tar 到 `<appdata>/sandbox-archives/` | 重启后能恢复 |
| 3.5 | 稳定 key | `<user_id>/<session_id>.tgz`（**不是**实例 id） | 回收再唤起能恢复上次工作区 |
| 3.6 | **动态扩缩容**（§4.7.4） | 按需建槽 + `MAX_SLOTS` 保护阀 | 见 3.3 的扩缩容测试 |
| 3.7 | **`OVERFLOW` 三分支**（§4.7.3） | `queue` / `evict` / `reject` 三个取值都要实现 | 见 3.3 的 overflow 测试 |
| 3.8 | 淘汰 / 排队前先归档 | 淘汰一个用户的槽会丢他的 workspace | 淘汰后能恢复 |

**3.1 的三条铁律**（写进代码注释，不能只写文档）：

1. 父进程绝不 `exec`/`eval` 用户代码
2. 子进程必须 `os._exit()`，不能正常退出
3. 预导入清单固定，不按用户请求动态 import

**3.6 / 3.7 的模型**（照 §4.7.4 实现，不要自己发挥）：

```
有该用户的槽              → 直接用
没槽 & 槽数 < MAX         → 建新槽
没槽 & 槽数 = MAX         → 按 OVERFLOW 分支：
    queue  → 等（带超时）→ 建槽，结果带 queue_wait_ms
    evict  → 有空闲槽？ 是→归档+销毁+建新槽 ；否→退化成 queue（记日志）
    reject → 立刻 503，不排队
```

**`OVERFLOW` 三个取值的含义**（实现时必须让它们行为真的不同，不能都退化成 queue）：

| 取值 | 槽满时 | 用户看到什么 |
| --- | --- | --- |
| `queue` | 阻塞等待，直到有槽空出或超时 | 慢，但最终成功 |
| `evict` | 淘汰最久未用的**空闲**槽 | 快（≈54ms），但被淘汰者下次要重新预热 |
| `reject` | 立刻返回 503 | 立刻失败，需要客户端重试 |

#### 3.4 不做什么

- ❌ 不做「保留 Python 变量」（形态 C，见 §4.2；要做得单独设计）
- ❌ 不引入 MinIO（阶段 4）
- ❌ 不在每次 exec 后归档（太贵，只空闲回收 / 淘汰时归档）
- ❌ **不预建一批通用空槽**（槽绑不上用户，用不上，见 §4.7.1）
- ❌ **不做无上限动态扩**（内存失控，必须有 `MAX_SLOTS`）
- ❌ **不淘汰忙碌中的槽**（会掐断正在跑的代码）

## 9.5 将来上 gVisor 的检查清单

> 留着这一节，是为了让「换实现」变成机械操作，不是重新设计。

1. **先验证 runsc 能跑起来**（别等写完才发现 syscall 不兼容）
   - `docker run --runtime=runsc python:3.12-slim python3 -c "import pandas"`
   - 验证清单：起进程、`/proc` 读取、`fork/exec`、写文件、matplotlib 出图

3. 实现 `GVisorExecutor`，只碰 `executor/gvisor.py`
4. 重置「池」的语义：gVisor 下**建容器不再便宜**（`docker run` 级，不是 bwrap 的 27 ms），

   这正是 Docker 池本来的形态。**§4.7 的实时扩缩容模型不能直接套到 gVisor 上。**
5. **重跑 bwrap 那套隔离断言**（探针可复用，改一下执行器即可）

**不要做的**：不要为了将来能上 gVisor 而在阶段 1 就引入 docker.sock。
`GVisorExecutor` 需要 sock，但那是**阶段 4 的沙箱服务**需要，
不是现在的 app 需要——app 侧永远是 HTTP 客户端。

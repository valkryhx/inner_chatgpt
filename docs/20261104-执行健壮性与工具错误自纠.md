# 执行健壮性：工具错误自纠（ReAct）与悬空 tool_call 自愈

> 背景：LLM 能力有限，一次工具参数写错是常态。系统必须能把「工具报错」当作观察回喂模型、
> 让它改参/换工具继续尝试（ReAct），而不是整轮中断、更不该把会话搞坏。
> 参考：GenericAgent 的循环与提示词（`genericagent/core/loop.py`、`resources/assets/sys_prompt.txt`）。
> 更新：2026-11-04。

## 一、问题复现与根因（真实事件）

- 现象：test 用户问「2026年1月 全国家宽用户数」，assistant 消息 `status=error`、正文为空；
  随后追问「为何中断了」「继续」也全是空 error，**整个会话中毒**，报
  `OpenAIInvalidRequestError: 400 - tool calls and tool results do not match`。
- 直接触发：模型给 `metric_latest` 传了它不存在的参数 `month` →
  `ToolError: Unexpected keyword argument 'month'`（当时 `metric_latest` 只能取最新，不能指定月）。
- 为什么会整轮失败并级联：
  1. `mcp_client._wrap` 里 `await client.call_tool(...)` 直接抛 `fastmcp.exceptions.ToolError`；
     langgraph `ToolNode` 默认 `_default_handle_tool_errors` **只吞 `ToolInvocationError`**，
     其它异常一律 re-raise → 工具节点抛错 → `_event_stream` 捕获 → 整轮 `status=error`。
  2. 抛错发生在「AI 已发 tool_calls、tool 结果未回填」之间，checkpoint 留下**悬空 tool_call**；
     下一轮把这段历史发给模型 → 400（tool calls 与 tool results 不匹配）→ 再失败 → 继续污染。

## 二、修复（三步，已经在代码中）

### 1) 工具异常一律转成可自纠文本（不再冒泡）
`backend/app/mcp_client.py`
- 新增 `_call_tool_safe(client, name, kwargs, schema)`：`try/except Exception`，把异常格式化为
  `[工具执行错误] <类型>: <消息>`；若判定为**参数校验类**错误，追加
  `[参数校验失败] ... 本次可用参数: [...]` 及针对性提示（如「指定某月请用 metric_series 的 month」）。
- `_wrap` 的 `_call` 改走 `_call_tool_safe`；`StructuredTool.from_function(...,
  handle_tool_error=True, handle_validation_error=True)` 作为第二道保险。

**效果**：工具报错变成一条 tool 结果回到模型上下文，模型据此改参/换工具继续，**不会中断整轮**。

### 2) 提示词加入通用失败升级策略（ReAct）
`backend/app/agent.py` 的 `SYSTEM_PROMPT`（**通用，不涉及任何具体业务/工具名**）新增：
- 参数以系统实际提供的为准，不要臆造参数名；不确定先探测。
- 工具调用失败是正常现象：先读错误再决定下一步。
- 失败升级：第 1 次读错误改参数 → 仍失败换等价工具/换思路 → 再失败如实告知用户；**禁止原样重复同一失败调用**。
- 多步任务边做边核对上一步结果。

（以上取自 GenericAgent `sys_prompt.txt` 第 16-18 行的「调用前推演 / 探测优先 / 失败升级」，通用化后写入。）

### 3) 悬空 tool_call 自愈
`backend/app/agent.py: UserRuntime.sanitize_pending_tool_calls(session_id)` +
`backend/app/routers/chat.py`（每轮 agent 运行前调用）：
- 检查 checkpoint 末尾：若最后一条带 `tool_calls` 的 AI 消息存在**缺失的 tool 结果**，判定为悬空。
- 若其后没有新的非 tool 消息：先尝试**补跑**这些缺失工具（能跑通就保住进展）。
- 否则用 `RemoveMessage` 截断该悬空 AI 消息，退回上一个完整轮次。
- 修复成功时向前端发一个 `healed` SSE 事件（可选展示）。

**效果**：历史里已中毒的会话在下次发消息时自动修复，不再 400；新会话从根上不再产生悬空。

## 三、MCP 侧配套（减少犯错、提升可自纠）
`sqlbot_mcp`
- `metric_latest` 增加可选 `month`（`YYYY-MM`）：不传取最新一期；传则取该月值。
  这样模型「想按某月取值」时有顺手的原子工具，不必绕。
- 工具描述明确区分：`metric_latest`（单点/最新）vs `metric_series`（时间序列，支持 start/end_month）。

## 四、防御性增强（对齐 GA 的 max_turns）
`UserRuntime.config()` 增加 `recursion_limit`（默认 48，可用 `AGENT_RECURSION_LIMIT` 覆盖）：
给足多步探测/自纠的步数，同时防止失控循环耗尽 token。LLM 传输层重试沿用既有
`max_retries`（默认 3）。

## 五、验证（证据）
- 直接调包裹后端工具：非法参数返回 `[工具执行错误] ... [参数校验失败] 本次可用参数...`（字符串，
  不抛异常）；`metric_latest(..., month="2026-01")` 正常返回 2026-01 值。
- 原失败问句「2026年1月 全国家宽用户数」重跑：`done status=complete`，答案
  「112,982,266 户（约 1.13 亿户）」正确。
- 已中毒会话 `co_4aec4ecf3898` 再发消息：自动自愈、`complete` 正常回答；
  checkpoint 中悬空 AI 消息已被移除，无 400。

## 六、边界与后续
- 工具级重试次数由模型自行决定（按错误信息改参再试）；不做无脑自动重试同一调用（避免重复副作用）。
- `recursion_limit` 是最外层步数上限；真正的「死循环」仍可能消耗较多 token，后续可加「同一工具同参
  连续 N 次失败即强制停并回报」的硬闸。
- 该健壮性对所有 MCP 工具通用（不止 sqlbot），属于平台能力而非某个业务。

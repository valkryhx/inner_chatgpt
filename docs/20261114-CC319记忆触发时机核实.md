> **本文推翻了 `docs/20261112-Hlaudz记忆系统实施方案.md` §3.7 与 §3.3 的两处推断**，见 §5。

## 0. 一句话回答

| 问题 | 答案 |
|---|---|
| 写记忆是常驻后台一直跑吗？ | **不是常驻**。它挂在「一个用户轮次结束」这个钩子上，每轮都会**尝试**一次，但前面有闸（默认配置下有一道直接短路，见 §1.2）。真正跑起来是**一次模型调用（fork 子代理）**，跑完就结束 |
| 是模型自己决定何时写吗？ | **看开关**。`V$t()` 为真时由代码的钩子 + 闸门决定时机、模型只决定「写什么」；`V$t()` 为假（**默认**）时模型得在对话里自己调 `memory_write`。详见 §4 |
| 写记忆是 hook 机制吗？ | **不是**。它是「挂在 hook 阶段（`throughStopHooks`）上的一次侧边 fork 子代理调用」。时机上属 hook 阶段（所以 `settingsHooksOff` 会关掉它），机制上不走 hook 引擎、不读用户 hook 配置。详见 §5 |
| 什么时候读记忆？ | **每次模型调用时**都尝试。CC 有两条读路径：`AutoMem`（索引，装配时读）+ `relevant_memories`（LLM 选择器，并发预取）。**不是每轮对话一次，是每次模型调用一次** |
| 每次会话都触发记忆吗？ | **尝试是每次，真跑不是**。见 §1.2 与 §2.2 的闸门，绝大多数轮次会被挡掉 |
| `auto_dream` 是实时的吗？ | **完全不是**。它在同一个轮次结束钩子上被**尝试**，但内部有 24 小时 + 5 会话 + 10 分钟扫描节流三道硬闸（§3.2）。实际是「隔天级别」的后台整理 |
| dream 做什么？ | 不只是「整理碎片」——四阶段：Orient（看现状）、Gather（找漂移的事实）、**Consolidate（合并/删被推翻的/相对日期转绝对）**、**Prune（维护索引）** |
| dream 中途被 kill / 服务重启，下次会自动跑吗？ | **会重跑，但不是续跑。** 状态在 `.consolidate-lock`（PID + lastConsolidatedAt），而后者**只在成功后更新**，所以中断后它停在上次成功时刻 → 下次条件满足就**从头再来**，无进度保存。锁本身不会卡死（PID 死了就能抢）。详见 §6 |
| 本项目没有 hook，要不要为了记忆提前补？ | **不补。** 记忆只需要「轮次结束的执行点」（`agent_loop` 循环已有）+「一个全局禁用开关」，不需要 hook 引擎 / 用户配置 / `blockingErrors`。`AGENTS.md` 里 hooks 排在 P4 未开始，提前补会打乱顺序且收益为零。详见 §7 |

## 1. 写侧：`extractMemories` 的真实触发链

### 1.1 触发链（一行一层，全部有行号）

```
模型停止输出
  → Jd()                    m0848:3829   ← 停止钩子阶段的收尾生成器
    → executeExtractMemories  m0848:3852 → 导出的 Pha (m0832:1323)
      → J.of(host).extractor  m0832:1303 = (p,E) => Z(ir(p,E))
        → ir()                m0832:1250  ← 真正的入口
          → ar()              m0832:1259  ← 闸门与调度
            → Le()            m0832:922   ← 闸门本体
```

**关键点：`Jd` 不是「每次模型调用」的钩子，是「这一轮对话结束」的钩子。**
它在 `stopHookActive` 阶段执行，名字也说明了这点——`throughStopHooks`（`m0848:10414`）。
所以我上一轮说「每轮都跑」不准确，应当说**每个用户轮次（turn）结束跑一次**。

### 1.2 `ar()` 的短路闸（`m0832:1259`）

```js
async function ar(context_3, appendSystemMessage_2) {
  Q();                                   // 清掉 idle 定时器
  let A = fet(),                         // ← MCP 模式配置，null = 文件模式
    I = A !== null;
  ...
  if (!I && !v("tengu_passport_quail", !1) && !er()) return;   // ← 文件模式下最关键的一道
  if (!I && !fh()) { ...; return; }                             // 文件记忆没开 → 不跑
  if (!I && Aue()) return;                                      // 特殊读取模式 → 不跑
  if (rr() !== null) return;                                    // 远端会话 → 不跑
  if (b) { ...stash 成 trailing...; return; }                   // 已在跑 → 排队尾随
  await Le({ context: context_3, appendSystemMessage: appendSystemMessage_2 });
}
```

**`v("tengu_passport_quail", !1)` 这个 flag 默认是 `false`**（`v(e, n)` 的第二个参数是默认值，
`m0191:39396`）。`er()` 也默认 false（要求 `EXTRACTOR_RUNS_FOR_PROMOTER` 且 promoter 开着）。
`Aue()` 是特殊读取模式（要求 `blockReadsOutsideWorkingDirectories` 等）。

**所以要诚实地说**：在**默认配置 + 文件模式**下，要走到 `Le()` 需要
`tengu_passport_quail` 被服务端动态开关打开。这不是「每轮必跑」，而是
**「每轮尝试一次，绝大多数情况被这一行挡掉」**。

> 这一点很重要：v2 §8.2 说「`post_turn_memory` 只在 `config_2.declareTask` 时注册」，
> 指的是 MCP 模式。文件模式的开关实际是 `tengu_passport_quail`，v2/v3 都没提。

### 1.3 还有一条 `idle_flush` 路径

`Le()` 的第 3 道闸（`turns++ < every_n_turns`）没通过时，如果 MCP 模式配了
`idleFlushSeconds`，会挂一个 `setTimeout`（`m0832:860` `q()`），到点触发 `ee()` → `Le({trigger:"idle_flush"})`。
**这是 MCP 模式专属**（`q()` 的第一个参数是 `config_2`，文件模式下不调用）。

文件模式下没有 idle flush。所以文件模式的写侧只有「轮次结束尝试」这一条路。

### 1.4 `Le()` 的四道闸（文件模式）回顾

| 闸 | 条件 | 行号 | 效果 |
|---|---|---|---|
| 1 | 本区间内已有直写（`Nt`） | `:938` | 跳过——主代理自己已经写过，别重复 |
| 2 | prose 不足（`$t`） | `:950` | 跳过——tool-only 轮次没啥可记 |
| 3 | `turns++ < every_n_turns` | `:963` | 本轮不跑，累加到下次 |
| 4 | 权限规则会拒绝写入（`LGr`） | `:976` | 跳过并提示 |

通过后 `await sA({...})` 跑一次 fork（`m0832:1060` 附近），本质是**一次独立的模型调用**，
`maxTurns: 5` 硬编码（`:1184`）。

## 2. 读侧：两条路径，都是「每次模型调用」

### 2.1 `AutoMem`：索引，装配时读（不是触发式）

`m0591:70580` 的 `if (fh() && !Aue())` 位于 **attachment 装配函数**里，
每次组装上下文都会跑一次。它读 `MEMORY.md`，按方案 §3.5/§3.6 的 cap 截断
（`docs/20261112-Hlaudz记忆系统实施方案.md`），
作为 `instructions` attachment（announced 渲染）发出。

**没有闸门、没有 LLM 调用**——纯文件读 + 字符串处理。所以它不影响 TTFT 的量级。

### 2.2 `relevant_memories`：LLM 选择器，**每次模型调用都启动一次预取**

这是最重要、也最容易搞错的一点。

**`Ivi` 的调用点在 `Wc`（query 主生成器）里**（`m0848:7294`），
而 `Wc` 是**每次模型调用**都会重新进入的生成器 —— 它被 `y = s.through(Wc(e, n, r, s))`
（`m0848` 内）包在一个 `while (!0)` 循环里，每轮把控制权交回去。

**所以「预取」不是每个 generation 一次，是每次模型调用一次。**

那么重复注入是怎么避免的？靠**两个**机制：

1. **`consumedOnIteration`** —— 句柄自己的字段，只能消费一次（`m0848:10602`）；
   但它**只作用于同一个句柄**，下次模型调用是新句柄，所以它不防跨调用重复。
2. **`Mvi` 的 `THn` 过滤**（`m0591:153994`）—— 这个是**跨调用**生效的：

```js
function Mvi(e, n, r, s) {
  let h = pMe.of(r);
  return e.map(y => {
    if (y.type !== "relevant_memories") return y;
    let S = y.memories.filter(w => !THn(n, w.path, s));   // ← 过滤掉"这轮已经读过"的
    for (let w of S) n.set(w.path, { content: w.content, timestamp: w.mtimeMs, ... });
    return h.recordSurfaced(S.map(w => w.path)), S.length > 0 ? { ...y, memories: S } : null
  }).filter(y => y !== null)
}
```

`THn(n, path, s)` 查的是 `n.readFileState` —— **已经进过上下文（读过/注入过）的路径会被滤掉**。
也就是说：**同一条记忆在一次会话里只会被注入一次**，靠的是这个 state，不是靠注入器自己的标志。

还有第三层保护：`Ivi` 入口的**会话字节预算**（`jzr` 累计 ≥ 61440 就不再有新召回）。

### 2.3 入口六道闸（`Ivi`，`m0591:153923`）

| 闸 | 代码 | 说明 |
|---|---|---|
| 1 | `if (!h \|\| n.agentId \|\| Gzr.has(r)) return` | 没有 selector / 子代理 / 自激 querySource |
| 2 | `let y = fh() && lSe()` | **文件记忆开 且 工具存储模式开**（见 §2.4） |
| 3 | `if (!y && !S) return` | `S = yIe?.isAccountRecallOn() === !0` —— 恒 false（v3 §4.4） |
| 4 | `findLast(type==="user" && !isMeta)` | 必须有真实用户消息 |
| 5 | `if (!N \|\| !/\s/.test(N.trim())) return` | 纯单字/空查询不跑 |
| 6 | `if (jzr(e).totalBytes >= MAX_SESSION_BYTES) return` | 会话累计 ≤ 61440 |

### 2.4 ⚠️ 默认配置下选择器**不运行**

第 2 道闸 `y = fh() && lSe()`：

```js
function lSe() {                                    // m0191:2576
  if (v("tengu_moth_copse", !1)) return !0;         // ← 默认 false
  return tMs();
}
function tMs() {
  return !!process.env.CLAUDE_MEMORY_STORES?.trim(); // ← 默认未设置
}
```

**`tengu_moth_copse` 默认 `false`，`CLAUDE_MEMORY_STORES` 默认空 → `lSe()` 返回 false
→ `y` 为 false → 若 `S`（账号召回）也是 false（本 build 恒 false）→ `Ivi` 直接 return。**

**结论：在默认的文件记忆模式下，CC 根本不跑 LLM 相关性选择器。**

这与我上一轮写的「§3.7 是读侧主路径」直接冲突。正确表述应当是：

- `relevant_memories` 是**代码里最完整的召回机制**，但它受 `lSe()` 门控；
- `lSe()` 的语义是「**MCP 记忆库模式 / 实验旗标**」（v3 §3 第 9 条：`lSe()` 判据是
  `tengu_moth_copse` 或 `CLAUDE_MEMORY_STORES` 非空，且它同时决定「剥离 AutoMem」）；
- 也就是说 **`lSe()` 为真时，`AutoMem` 被剥离、改用工具存储 + 选择器**（两条路径互斥，
  这正是 v3 §3 第 34 条「互斥开关」的意思）。

所以 CC 实际有**两套读侧形态**，不是一套：

| 形态 | 触发条件 | 索引怎么进 | 选择器 |
|---|---|---|---|
| **文件记忆（默认）** | `fh()` 真、`lSe()` 假 | `AutoMem` → `instructions` attachment | **不跑** |
| **工具存储/MCP** | `lSe()` 真 | `AutoMem` 被剥离（`zTe`/`gos`） | **跑**（`relevant_memories`） |

## 3. `auto_dream` 的真实时机

### 3.1 触发链

```
Jd()                       m0848:3829  （轮次结束）
  → PXs(G, appendSystem)    m0848:3859  ← 与 extractMemories 同一位置
    → B.of(host).runner     m0833:409 = xXs 注册的 runner（m0833:201）
      → 各道时间闸           m0833:197-270
```

**它是「轮次结束时尝试」，不是「空闲时触发」。** 没有 idle 检测、没有系统空闲回调。
所谓「空闲」是**产品语义上的**——因为它的闸是 24 小时 + 5 个会话，
所以实际表现成「隔天在某个轮次结束后悄悄跑」，用户感知上像「空闲时整理」。

### 3.2 三道时间闸（`xXs`，`m0833:197`）

```js

    u = ge();                       // 恒 false（调试用，m0833:194）

```

再加**文件锁**（`sZs`，`:249`）与**权限闸**（`LGr`）。

### 3.3 `he()` 的五道前置（`m0833:187`）

```js
function he() {
  if (rr() !== null) return !1;   // 远端会话不跑
  if (aY()) return !1;            // SDK 入口不跑
  if (!fh()) return !1;           // 文件记忆没开不跑
  if (Aue()) return !1;           // 特殊读取模式不跑
  return xEt();                   // 总开关

```

### 3.4 dream 做什么（四阶段，`Q()`，`m0833:54`）

用户的直觉「合并碎片、提炼有价值信息、把做错又成功的经验提炼出来」——
**方向对，但 CC 的 dream 只做了前一半**：

| 用户以为的 | CC 实际做的 |
|---|---|
| 合并碎片 | ✅ Phase 3「Merging new signal into existing topic files rather than creating near-duplicates」 |
| 提炼有价值的信息 | ✅ 部分：Phase 2「Existing memories that drifted」+ Phase 3「Deleting contradicted facts」 |
| **把做错又成功的经验提炼出来** | ❌ **不做**。「从失败中学习」是**提取器（`extractMemories`）**的职责（`feedback` 类型："Record from failure AND success"），不是 dream 的 |
| 整理索引 | ✅ Phase 4「Prune and index」——**这是 dream 独有的**，提取器不碰索引 |

dream 明确**只整理已有记忆**，不新增「这一轮学到了什么」。它的三个核心动作是：

1. **合并近似条目**（不新建重复）；
2. **删掉被推翻的事实**（今天发现旧的错了 → 改源头）；
3. **相对日期转绝对日期**（「昨天」→「2026-11-13」）。

这三点恰好是「只增不减」的实现会烂掉的地方。

## 4. `tengu_passport_quail` 开与不关分别是什么行为

问题：这个开关开了和关了什么区别？答案不是「开=有记忆、关=没记忆」，
而是**它决定「谁来写记忆」**——代码自动提取 vs 模型主动调工具。

### 4.1 开关的完整判据（`V$t`，`m0191:2591`）

```js
function V$t() {
  if (fet() !== null) return !0;                          // ① MCP 模式恒真
  if (!v("tengu_passport_quail", !1)) return !1;           // ② 旗标，默认 false
  return !ye() || v("tengu_slate_thimble", !1);            // ③ 交互会话 或 slate_thimble
}
```

`ye()`（`m0040:5124`）= `!t().host.launchOptions.isInteractive()` —— 即**非交互**返回 true。

逐项展开：

| 场景 | `fet()` | `passport_quail` | `ye()`（非交互） | `V$t()` |
|---|---|---|---|---|
| MCP 模式 | 非 null | — | — | **true** |
| 默认 CLI（交互） | null | **false** | false | **false** |
| 旗标开 + 交互会话 | null | true | false → `!ye()` = true | **true** |
| 旗标开 + 非交互（如 `-p`） | null | true | true → `!ye()` = false | 看 `tengu_slate_thimble` |

**所以默认的交互式 CLI 里 `V$t()` 是 false。** 这推翻了上一轮我说「CC 每轮结束会自动写记忆」的
隐含假设——**默认情况下它不会自动提取**。

### 4.2 开关关掉时，写记忆改走「模型主动调工具」

`V$t()` 为 false **不代表不能写记忆**。这条链的每一层都是「或」关系，前一层不成立时
还有别的入口：

```js
// m0832:1254（ir 里）
if (V$t() || er()) await ar(p, E);

// m0832:1278（ar 里，文件模式的第二道）
if (!I && !v("tengu_passport_quail", !1) && !er()) return;
```

而 `lSe()`（`m0191:2576`）的语义是「**MCP 记忆库 / 工具存储模式**」——
它同时决定两件事：**剥离 `AutoMem` 索引** + **打开 `relevant_memories` 选择器**
（v3 §3 第 9、34 条）。

所以两种形态的真实差别是：

| | `V$t()` = true（自动提取开） | `V$t()` = false（默认） |
|---|---|---|
| 谁写记忆 | **代码自动**：每轮结束派 fork 子代理 | **模型自己**：在对话里主动调 `memory_write` |
| 写的前提 | 四道闸通过 | 模型判断「这事值得记」 |
| 提取器工具 | `z$t` 写侧三件 | 不跑 |
| 写入时机 | 轮次结束后，后台 | 对话过程中，前台（占当前轮的工具步骤） |
| 记忆质量 | 由提取提示词约束（§4.5） | 由主 SYSTEM_PROMPT 的 auto-memory 段约束 |
| 用户感知 | 无感（后台跑） | 能看到 `memory_write` 工具步骤 |

**关键推论**：`passport_quail` 关掉时，记忆系统**不会消失**，只是从
「后台自动」退化成「前台工具调用」。这与 v2 §9.1 说的「`he()` 的四道前置：不在远端 /
无 override / 自动记忆开 / 非工具模式 / `xEt()` 开关」是同一件事的另一个侧面。

### 4.3 对 Hlaudz 的含义

Hlaudz 没有「交互 vs 非交互」的区别（全是 Web 会话），也没有远程动态旗标
（`v("tengu_*")` 是 CC 的服务端下发机制）。所以**不要照抄 `V$t()` 这套三层判据**，
它解决的是 CC 特有的「CLI 可能被 SDK/远程调用」问题。

Hlaudz 应当用的判据是简单的两态：

```python
def auto_extract_enabled() -> bool:
    return _env_bool("HLZ_MEMORY_AUTO_WRITE", True)   # 默认开
```

但**保留一个重要的设计取舍**：CC 的两形态说明「自动提取」与「模型主动写」是
**互补**的，不是二选一。Hlaudz 最好的形态是**两者都有**：

- 模型在对话中随时可以 `memory_write`（M2 的工具，显式、即时）；
- 后台每 N 轮兜底提取（M4，捕获模型没主动记的）。

这与 CC 的默认形态（只有前者）不同，但对 Hlaudz 更合适——Web 用户的对话轮次更碎，
漏记的成本更高。

## 5. 记忆写入是 hook 机制吗？——不是，是「共享阶段里的侧边调用」

这是个容易误解的点，值得单独说清。

### 5.1 它确实挂在 hook **阶段**里

调用链的顶层是 `Jd`，而 `Jd` 由 `Ea` 调用（`m0848:10071-10074`）：

```js
async function* Ea(toolUseContext_14, j) {
  let ge = yield* Jd(N, ie, systemPrompt_8, ..., queryContext, stopHookActive_5, ...);
```

而 `Ea` 的对外名字是 **`throughStopHooks`**（`m0848:10414`）：

```js
if (va) return yield* wd({ throughStopHooks: () => Ea(updatedToolUseContext_2, {...}) });
```

所以 `Jd` 运行在**「停止钩子阶段」**。`Jd` 开头还有两道闸（`m0848:3830` 的 `_n()`、
`:3834` 的 `settingsHooksOff`）：

```js
if (_n() && !abortController.signal.aborted) return {...};       // 全局禁用
if (options.settingsHooksOff || querySource_6 === "agent_summary") return {...};
```

**`settingsHooksOff` 为真时，记忆提取也不会跑。** 这是「它挂在 hook 阶段」的直接证据。

### 5.2 但它不是 hook 机制本身：三种机制的区分

| 机制 | 是什么 | 记忆提取是不是 |
|---|---|---|
| **用户配置的 Hooks** | 用户在 `settings.json` 里写的 `Stop`/`PreToolUse` 等 shell 命令，由 hook 引擎执行、可返回 `blockingErrors` 阻止续跑 | ❌ 不是。提取不读用户 hook 配置，也不受 `blockingErrors` 影响 |
| **Hook 阶段**（`throughStopHooks`） | 一个**执行时机**：模型停止输出后、本轮收尾时。里面可以挂任意多件事 | ✅ **是**。提取、dream、post-turn summary、prompt suggestion 都挂在这里 |
| **侧边路径**（fork 子代理） | 提取**实际执行**的形态：`sA({...})` 起一个独立的模型调用，有自己的 turns 和工具集 | ✅ **是** |

**准确说法：记忆写入是「挂在 hook 阶段上的一次 fork 子代理调用」，
既不是用户 hook，也不是常驻后台。**

### 5.3 `Jd` 里到底挂了哪几件事（`m0848:3829-3880`）

一个「轮次收尾」阶段里塞了至少五件互不相关的事：

| # | 事情 | 调用 | 行号 |
|---|---|---|---|
| 1 | post-turn summary（会话摘要） | `yield* zd(...)` | `:3849` |
| 2 | **记忆提取** | `qn.executeExtractMemories(...)` | `:3852` |
| 3 | **dream 合并** | `PXs(G, ...)` | `:3859` |
| 4 | prompt suggestion（下一句建议） | `C7s(G, T?.lastResult)` | `:3850` |
| 5 | brief mode 强制检查 | 内联逻辑 | `:3864-3876` |

**这五件事共享同一个「时机」，但互相独立**：任何一件失败都不影响其他
（每件都有自己的 try/catch，`m0848:3853-3858` 那个就是 `executeExtractMemories` 的）。

所以「记忆是 hook 吗」这个问题，准确答案分三层：

- **时机上**：是的，它在停止钩子阶段（`throughStopHooks`），所以 `settingsHooksOff` 会关掉它；
- **机制上**：不是，它不走 hook 引擎、不读用户 hook 配置、不参与 `blockingErrors`；
- **执行上**：是**侧边 fork**，一次独立模型调用，有自己完整的 turns。

### 5.4 对 Hlaudz 的落法

Hlaudz 没有 hook 阶段这个概念（`agent_loop` 是显式循环）。对应的落点：

```python
# agent_loop.py 的轮次结束处（yield done 之前）
async def _on_turn_end(self) -> None:
    """一轮结束时的侧边任务。每件独立 try/except，互不影响。"""
    for task in (self._maybe_extract_memories, self._maybe_dream):
        try:
            await task()          # 内部各自判断闸门，不满足立即返回
        except Exception:
            logger.warning("[turn_end] %s 失败", task.__name__, exc_info=True)
```

**注意别做成「一个失败全跳过」**——CC 的五件事各自独立，这是有意的设计：
摘要失败不该拖累记忆提取。

Hlaudz 没有 `settingsHooksOff` 这种全局开关，但**应当有一个等价物**：
`HLZ_MEMORY_DISABLED=1` 时，提取与 dream 都不跑（这是排障时的第一道出口）。

## 6. dream 中途退出/服务重启后会不会自动续跑

**答案：会重试，但不是「接着上次的进度继续」，而是「从头再跑一遍」。**
这一点必须说清，因为它决定了 Hlaudz 的状态该存什么。

### 6.1 CC 的状态全在 `.consolidate-lock` 一个文件里（`m0809`）

```js
var g = ".consolidate-lock",      // 记忆目录下的文件
    y = 3600000;                  // 锁年龄上限 1 小时

function c(e) { return A(e, g); }             // 锁文件路径
function h(e, n) { return `${e ?? ""}
${n}`; }  // 内容：PID 
 lastConsolidatedAt
```

**文件内容是两行**：第一行是持有者 PID，第二行是 `lastConsolidatedAt`（毫秒时间戳）。
载入时（`b()`）：

```js
function b(e, n) {
  let [a = "", r = ""] = e.split("\n"),
      o = parseInt(a.trim(), 10),              // PID
      i = r.trim() === "" ? NaN : Number(r.trim());   // lastConsolidatedAt
  return {
    holderPid: Number.isFinite(o) ? o : void 0,
    lastConsolidatedAt: Number.isFinite(i) ? i : n     // ← 回落到文件 mtime
  };
}
```

注意 `lastConsolidatedAt` 缺失时**回落到文件 mtime**。这个设计让「进程写了 PID 但没来得及
写时间戳就崩了」也能得到一个合理的时间。

### 6.2 抢锁逻辑（`L()`，`m0809:60`）

```js
async function L(e, n) {
  let r = c(e), o, i;
  try {
    let [s, w] = await Promise.all([p(r), f(r, "utf8")]);
    o = s.mtimeMs;                             // 文件 mtime
    i = parseInt(w.trim(), 10);                // 文件里的 PID
  } catch {}                                   // ← 文件不存在 = 没有锁
  if (o !== void 0 && Date.now() - o < y) {    // 锁还很新（< 1 小时）
    if (i !== void 0 && El(i))                 // 且 PID 还活着
      return t(`[autoDream] lock held by live PID ${i} ...`), null;   // → 拿不到
  }
  await P(e, { recursive: !0 }), await k(r, String(process.pid));    // 否则抢
  let u = await f(r, "utf8");
  if (parseInt(u.trim(), 10) !== process.pid) return null;           // 抢完复核
  return o ?? 0;
}
```

**判定是「两个条件都成立才拒绝」**：锁文件 mtime 在 1 小时内 **且** 那个 PID 还活着。

所以进程崩溃后的行为是：

| 崩溃后经过 | 锁文件 mtime | 原 PID | 结果 |
|---|---|---|---|
| 立即重启 | < 1h | **已死** | `El(pid)` 为 false → **直接抢到锁**，可以跑 |
| 1 小时后重启 | > 1h | 无关 | **直接抢到锁**，可以跑 |
| 原进程还活着 | < 1h | 活 | 拒绝（正确行为） |

**所以锁本身不会永久卡死。** 这一点 CC 做得对——不用人工删锁文件。

### 6.3 但「会不会真的跑」取决于 `lastConsolidatedAt`，而它只在**成功**后才更新

`xXs` 的判定链（`m0833:213-232`）：

```js
let E = await sTt(...);              // 读 lastConsolidatedAt
let O = (Date.now() - E) / 3600000;
if (!u && O < a.minHours) return;    // ← 距上次成功 < 24h → 不跑
```

而 `lastConsolidatedAt` 的写入点只有两处：

| 场景 | 是否更新 | 代码 |
|---|---|---|
| dream **成功完成** | ✅ 更新为 now | `gVt(priorMtime, ...)` 只在成功后调用 |
| dream **中途崩溃/被中断** | ❌ **不更新** | 没有 finally 里的更新 |
| 成功但结算失败（`skipped`/`failed`） | ✅ 回滚到 `priorMtime` | `m0833:348` 的 `claimLockGiveBack` → `gVt(priorMtime, ...)` |

**关键结论：dream 被中断后，`lastConsolidatedAt` 停留在「上次成功」的时刻。
所以下次启动时，如果距今已超过 24h，它会重新跑一遍——从零开始，不是续跑。**

好消息是「会重跑」；坏消息是：
- **没有进度保存**。跑了 20 分钟被 kill，这 20 分钟的模型调用全白费；
- **可能重复写**。如果中断前已经写了几个文件，重跑时 Phase 1 会看到它们（至少不会写出重复），
  但 Phase 3 的「合并」判断会基于一个中间状态的记忆库，可能做出不同的合并决定。

### 6.4 那 `mayHaveWritten` 是干什么用的

`m0833:334` 的结算逻辑只在**同一个进程内**有意义：

```js
let dreamWrote    = new Set([...H].filter(([k]) => !V || !j.has(k)) ...),   // 确定写了
    mayHaveWritten = new Set([...H].filter(([k]) =>  V && j.has(k)) ...);   // 可能写了
```

`H` 是「被允许写但没收到完成确认」的路径。**进程被 kill 时这个 Map 直接消失**，
所以它解决的是「工具调用成功但会话被 abort」这种**进程内**的中断，
不是「进程崩溃」。CC 没有跨进程的进度持久化。

### 6.5 对 Hlaudz 的落法

Hlaudz 是 Web 服务，重启比 CLI 频繁得多（部署、OOM、手动重启）。所以这一块不能照抄 CC
的「无进度保存」，至少要做三件事：

**① lastConsolidatedAt 存 DB，不存文件 mtime**

CC 用文件 mtime 是为了省一个存储位置，但 Hlaudz 有 SQLite：

```sql
CREATE TABLE IF NOT EXISTS memory_dream_state (
    user_id            TEXT PRIMARY KEY,
    last_consolidated  INTEGER NOT NULL DEFAULT 0,   -- 上次**成功**完成的时间
    last_attempt       INTEGER NOT NULL DEFAULT 0,   -- 上次**开始**的时间
    last_status        TEXT    NOT NULL DEFAULT 'idle',  -- idle|running|failed
    lock_pid           INTEGER NOT NULL DEFAULT 0,
    lock_at            INTEGER NOT NULL DEFAULT 0
);
```

多两个字段的理由：
- `last_attempt` 让「反复崩溃」可诊断（连续 5 次 attempt 都失败 → 记录并停一段时间）；
- `last_status` 让前端/日志能看出「上次 dream 是崩了还是跑完了」。

**② 锁用 DB 行 + 心跳，不用文件**

文件锁在 Web 服务里不好处理（多 worker、容器重启后 `/proc` 视图不同）。
用 DB 行替代：

```python
async def try_acquire_dream_lock(user_id: str, pid: int) -> bool:
    now = int(time.time() * 1000)
    # 一个 UPDATE 完成「判断 + 抢占」，避免读写分离的竞态
    rows = await db.execute(
        """UPDATE memory_dream_state SET lock_pid=?, lock_at=?, last_attempt=?, last_status='running'
           WHERE user_id=?
             AND (lock_pid=0 OR lock_at < ? OR lock_pid=?)""",   # 无锁 / 陈旧 / 自己重入
        (pid, now, now, user_id, now - LOCK_STALE_MS, pid),
    )
    return rows > 0
```

`LOCK_STALE_MS` 取 30 分钟（比 CC 的 60 分钟短——Web 服务重启更频繁，
留 30 分钟已经够宽容）。

**③ 崩溃恢复要靠「启动时清理」，不能靠「锁过期」**

服务启动时必须主动收敛上一次留下的 running 状态，这与本项目已有的做法一致
（`main.py:36` 的 `mark_stale_running_as_errored("server restart")`、
`team_store.recover_stale_runtime`）：

```python
async def recover_dream_state() -> None:
    """启动时调用：把所有 lock_pid != 0 的行收敛掉。

    不能只依赖 lock 过期：服务刚重启时 lock 可能还很新（< 30min），
    但持有它的进程已经不存在了。这与 team_store.recover_stale_runtime
    是同一类问题，用同一套解法。
    """
    await db.execute(
        "UPDATE memory_dream_state SET lock_pid=0, lock_at=0, "
        "last_status=CASE WHEN last_status='running' THEN 'interrupted' ELSE last_status END "
        "WHERE lock_pid != 0"
    )
```

**④ 不做「续跑」，但要做一个改进：把 Phase 4 拆出来**

CC 的四阶段里，Phase 3（Consolidate，写文件）和 Phase 4（Prune，改索引）是分开的。
Hlaudz 可以把它们做成**两个独立的可恢复步骤**：

- Phase 3 写完文件后立刻更新一次 `last_consolidated`（部分完成的进度）；
- Phase 4 单独一个「索引重建」任务，可以随时跑、幂等。

这样即使 dream 被 kill 在 Phase 4 之前，下次只需要重跑索引重建（很便宜），
不用重跑整个 Phase 3（很贵）。

> 这一条是 Hlaudz 相对 CC 的**改进**，不是对齐。理由是 Web 服务的重启频率高一个量级，
> 「反正会重跑」的代价在这里不可接受。

### 6.6 是否需要在启动时「立刻补跑一次」

**不需要，而且不应该。** 理由：

- dream 的闸是 24h + 5 会话，重启时通常两个条件都不满足；
- 启动时补跑会与「冷启动连 MCP」「建连接池」抢资源，拖慢首批用户；
- 用户此时可能正在等首帧。

正确做法：**只在启动时收敛状态（清锁），把「要不要跑」交给下一次轮次结束时的常规判定。**
这与 §5.3 里说的「Jd 里五件事各自独立」一致——不要让 dream 变成启动阻塞项。

## 7. 本项目还没有 hook 机制，要不要提前补

**结论：不补，也不该补。** 记忆系统不需要 hook 机制，理由如下。

### 7.1 本项目现状

全仓搜 `hook` 只有一处命中，且无关：

```
backend/app/run_guard.py:80:sys.addaudithook(_audit)
```

那是 Python 的审计钩子（用来拦危险 os 操作），与 CC 的用户可配置 hooks
（`settings.json` 里的 `Stop` / `PreToolUse` / `PostToolUse` shell 命令）完全不是一回事。

`AGENTS.md:98` 记录 P4 计划里确实有 hooks，但**排在计划模式和 goal 之后，未开始**。

### 7.2 为什么记忆系统不需要它

CC 的记忆提取**挂在 hook 阶段里，但本身不是 hook**（详见 §5）。
它需要的东西只有两样：

| CC 依赖 | Hlaudz 对应物 | 已有？ |
|---|---|---|
| 一个「轮次结束」的执行点 | `agent_loop` 的 `while` 循环末尾（`yield done` 之前） | ✅ 循环结构本来就有 |
| 一个全局禁用开关 | `HLZ_MEMORY_DISABLED` | 新增一个环境变量即可 |
| hook 引擎、用户 hook 配置、`blockingErrors` | —— | ❌ **不需要** |

记忆提取要的是「在轮次结束时能不能插一脚」，而 `agent_loop` 是显式循环，
插一脚比 CC 还容易。CC 之所以把它挂在 `throughStopHooks` 里，是因为它的架构就是
把「收尾阶段」做成了一个 hook 容器——**那是它的实现方式，不是记忆机制的需求**。

### 7.3 提前补 hook 的代价

1. **hook 引擎本身不小**：要设计配置格式、进程隔离、超时、stdout 协议、
   `blockingErrors` 语义、安全边界（用户写的 shell 在服务端跑 = 远程代码执行面）。
2. **它会把 P4 的排序打乱**。`AGENTS.md` 明确写了 P4 是「计划模式 → goal → hooks」，
   记忆系统插队不应该连带改变这个顺序。
3. **收益为零**：记忆系统用不到它的任何独有能力。

**如果将来真要做 hook**（P4 按原计划），记忆提取可以作为它的一个内置 hook 挂上去；
但那是「先有 hook，再让记忆用它」，不是「为了记忆先造 hook」。

### 7.4 唯一值得提前做的一件小事

CC 的 `settingsHooksOff` 会连记忆提取一起关掉。Hlaudz 没有这个开关，
但**应当有一个等价的排障出口**，这一点已经在方案里加了：`HLZ_MEMORY_DISABLED=1`。

这只要一个环境变量，不是 hook 机制。

## 9. 对我上一轮（方案 §3.7）的更正

上一轮我写「§3.7 并发预取是读侧主路径」，这是**错的**。两处更正：

### 9.1 「每次 generation 一次」→ 实际是「每次模型调用一次」

预取在 `Wc` 里，`Wc` 每次模型调用都重新进入。所以：
- 预取句柄是 **per-模型调用** 的，不是 per-generation；
- 跨调用去重靠 **`Mvi` 的 `THn`（readFileState）**，不是靠句柄自己的
  `consumedOnIteration`（那只管同一次调用内）。

因此我在方案 §3.3 写的「`_memory_injected` 标志 + generation 内只注入一次」这个设计
**方向是对的但理由错了**：Hlaudz 没有 `readFileState` 这种跨调用的「已注入路径」表，
所以确实需要自己实现去重；但去重的**键**应当是「记忆 slug 的集合」而不是一个布尔标志，
否则「第一轮注入了 A，第二轮新增了 B」这种情况 B 会被漏掉。

### 9.2 「读侧主路径」→ 默认配置下**不运行**

`lSe()` 默认 false，所以默认的文件记忆模式**根本没有选择器**。正确的定位是：

- **CC 的默认形态 = 只有 `AutoMem` 索引**（零 LLM 成本）；
- **选择器是「工具存储/MCP 记忆库」形态的配套**，与 `AutoMem` 互斥。

这对 Hlaudz 的含义变了：选择器不该是「读侧必经」，而应当是一个**可选的第二形态**。
更合理的 Hlaudz 设计是：

| Hlaudz 形态 | 触发条件 | 索引 | 选择器 | 成本 |
|---|---|---|---|---|
| **默认** | `HLZ_MEMORY_SELECTOR=0` | 哪个都行 | **不跑** | 零模型调用 |
| **增强** | `HLZ_MEMORY_SELECTOR=1` | 同上 | 每轮跑一次 | 每轮一次小模型调用 |

**并且默认应当是 `0`**——与 CC 一致，也让 M3 就能上线可用版本，M3.5 作为可选增强。
这与方案当前「M3.5 不做读侧就是残的」的说法矛盾，需要改。

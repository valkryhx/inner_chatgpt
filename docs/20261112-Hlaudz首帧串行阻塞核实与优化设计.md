# Hlaudz 首帧串行阻塞：核实结论与优化设计

> 日期：2026-11-12　状态：**核实完成（含真实实测）+ 优化设计**
> 触发：怀疑「Hlaudz 的 turn runtime 装配是同步的，可能有缺陷」，要求充分核实四点后写方案。
> 结论：**四点全部成立，且第 1、2 点已用真实后端量化**——最坏情况首帧被推迟 **5.1 秒**。

## 0. 核实结论速览

| # | 待核实点 | 结论 | 证据强度 |
|---|---|---|---|
| 1 | 首帧前有串行阻塞 | **成立**。`message_start` 之前串了 5 类 await，其中一类会**真调 LLM** | **实测**：超软线时 `message_start` 从 719ms → **5859ms** |
| 2 | 装配是串行的，不是并行批次 | **成立**。`build_turn_runtime` 内两个 await 顺序执行；注入点逐轮串行 | 代码核实 |
| 3 | 注入点没有时间预算 | **成立**。`message_injector` 调用无 `wait_for` / 无 timeout | 代码核实（全文件 grep 无 timeout） |
| 4 | 慢件不能延后 | **成立**。没有 CC 那种 `late_memory_context` + `afterToolStep` 的延期通道 | 代码核实 |

**这不是「理论上的不足」，而是用户能直接感知的等待。** 下面每条都给可复核的现场。

## 1. 四点逐条核实

### 1.1 点一：首帧前有串行阻塞（已实测）

`chat.py` 的 `_event_stream` 里，`yield frame("message_start")` 出现在 **`:511`**，
而在此之前已经串了这些 await：

| 行号 | 操作 | 会不会真调 LLM |
|---|---|---|
| `:397-399` | `db.add_message` × 2（写用户行 + 占位行） | 否 |
| `:409` | `hub.get_user_runtime()` → `UserRuntime.build()` | 否，但**首次要连全部 MCP server** |
| `:441` | `enforce_soft_limit()` | **会！内部 `_summarize()` 调 `ur.model.client.run()`** |
| `:450` | `enforce_hard_limit()` | 否（只裁剪） |
| `:459` | `sanitize_pending_tool_calls()` | 否 |
| `:519` | `build_turn_runtime()` | 否（ACP 预检走线程） |
| `:530` | `prepare_turn_team()` | 否 |

`enforce_soft_limit` 这一条是关键。`compaction.py:216`：

```python
summary = await _summarize(
    ur, SUMMARY_PROMPT.format(extra="", messages=_dialog_text(old)),
    max_tokens=min(4096, cap),
)
```

而 `_summarize`（`compaction.py:55`）就是一次完整的模型调用：

```python
res = await ur.model.client.run(
    [{"role": "user", "content": prompt}], max_tokens=max_tokens
)
```

**实测证据**（`tools/probe_soft_compact_blocking.py`，真实后端 + 真实 LLM，两次独立复现）：

```
soft_limit = 115200 tokens

第一次测量：
  A 空历史:      message_start =   719.0 ms
  B 超软线历史:  compaction    =  5797.0 ms    ← 摘要调用的完成时刻
                 message_start =  5859.0 ms
  差 +5140ms

第二次测量（干净复现）：
  A 空历史:      message_start =   625.0 ms
  B 超软线历史:  compaction    =  6031.0 ms
                 message_start =  6094.0 ms
  差 +5469ms
```

两次都在 5 秒以上，方向一致。注意 `compaction` 事件在 `message_start` **之前**
5.8–6.0 秒就发了——说明摘要调用完整跑完才轮到首帧。
**用户点发送后，5 秒多界面什么都不显示。**

而且这段最糟的地方在于：**它发生在"用户最需要反馈"的时刻**（刚点发送），
而它的产出（摘要）对用户本轮问题毫无帮助。

#### 次级问题：`get_user_runtime` 冷启动要连 MCP

`runtime.py:130` → `UserRuntime.build()` → `agent.py:322`：

```python
self.toolset = await build_user_toolset(user_id)
```

首次（或 `(user_id, model_id)` 缓存失效后）要连全部 MCP server 并 `list_tools`。
实测空历史那组 719ms 里就包含了这部分（本次该用户 MCP 工具数为 0，所以偏快）。
真实多 MCP server 用户的冷启动会更慢。

### 1.2 点二：装配串行，不是并行批次

`build_turn_runtime` 是 `async def`（不是「同步函数」——上次我说"同步装配"不准确，
准确说法是"**串行执行且在关键路径上**"）。函数体内的真 await 只有两个：

```python
session.py:204    bridge = await asyncio.to_thread(manager.preflight)      # ACP 预检
session.py:228    await host.load_pending_notifications()                   # 补载通知
```

（其余 `await` 都在嵌套闭包里，装配时不执行——这点必须说清，否则会高估成本。）

两个 await 之间**没有依赖关系**，却顺序执行。且 §1.1 的 7 个调用之间也没有
依赖（`enforce_hard_limit` 依赖 `enforce_soft_limit` 的结果吗？**不依赖**——
一个查软线一个查硬线，各自读 DB、各自写回）。

**代价的量级**：单看这两个 await 不算大（实测 `team_event` 437ms 减 `message_start`
218ms ≈ 219ms）。真正的成本在 `enforce_soft_limit` 的 LLM 调用上。但结构问题是真的：
**再加第三件慢事（比如记忆检索），就是纯串行叠加，没有任何并行化手段。**

### 1.3 点三：注入点没有时间预算

`agent_loop.py:305`：

```python
if self.message_injector is not None:
    try:
        injected = self.message_injector() or []
        if inspect.isawaitable(injected):
            injected = await injected        # ← 裸 await，没有 wait_for
```

全文件 grep `timeout` / `wait_for`：**零命中**。所以：

- 注入器慢多久，这一轮就等多久；
- 注入器**卡死**（比如 DB 锁、网络挂起），**整轮永不结束**——没有任何兜底；
- 每轮模型调用前都跑一次，300 轮最多付 300 次。

CC 的对比（`m0591:151723`）：整个 attachment 组装有 **1 秒硬 abort**
（`setTimeout((Sn) => Sn.abort(), 1000, Re)`）。Hlaudz 连单点超时都没有。

现有注入器里已经有异步 IO：`_lead_injector` 的 `_drain()` 里有
`await team_store.consume_inbox(...)`（`session.py:255`）——**读数据库**。
数据库在本机很快，但这是"目前恰好很快"，不是保证。

### 1.4 点四：慢件不能延后

CC 有一条专门的延期通道（`m0591:151789`）：

```js
...S?.afterToolStep && ls(y) === "main" && i.CLAUDE_CODE_MEMORY_CONTEXT_NO_WAIT
    ? [dc("late_memory_context", async () => yxi(n.session.host, N))] : [],
```

关键在 `S?.afterToolStep`：**延迟到工具步骤之后才计算**，完全不占首 token。

Hlaudz 没有对应能力。核实结果：

- `agent_loop.py` 里 `message_injector` 只在 `while` 循环**开头**调用（`:305`），
  工具执行之后**没有二次注入点**；
- grep `after_tool` / `post_tool` / `afterTool`：**零命中**。

所以任何「慢但可以晚点给」的上下文（记忆检索、代码库索引、MCP 资源预取）
现在只有两个选择：**阻塞首帧**，或者**干脆不做**。这是结构性的缺失。

## 2. 为什么这是「重大缺陷」而不是小瑕疵

用户的原话是「我一直不知道 hlaudz 的核心 chat 居然有这个不足」。把它说准：

**Hlaudz 的慢，不是"模型慢"，而是"在模型开始思考之前，平台先花了一笔时间"。**
这笔时间：

1. **不可见**——没有事件告诉用户"正在压缩历史""正在连接 MCP"，
   界面就是空白。用户会以为卡了。
2. **不可配**——没有开关、没有超时、没有降级。慢就是慢到底。
3. **会随使用变长**——历史越长，`enforce_soft_limit` 越可能触发；MCP 越多，
   冷启动越慢。**这是个会自我恶化的缺陷**。
4. **与本轮任务无关**——摘要旧历史、连 MCP、补载上次通知，
   全都不是"回答用户这个问题"所需要的。

第 3 点最值得警惕：单测永远发现不了它（单测用短历史、假 MCP），
只有真实用户在长会话里才会遇到，而且表现是"用久了就变慢"。

## 3. 优化设计

### 3.0 设计原则

三条，按优先级：

| 原则 | 含义 |
|---|---|
| **首帧优先** | `message_start` 必须在**极短时间**内发出（目标 < 300ms），任何非必需工作都移到首帧之后 |
| **有预算** | 每个可阻塞点都有超时，超时就降级（宁可少一点上下文，不能卡住用户） |
| **可观测** | 每段耗时都要能被看见——先有度量，再谈优化 |

### 3.1 改造一：把前奏拆成「必需」与「可延后」两段（核心）

**现状**：7 件事全在 `message_start` 之前顺序做完。

**改造**：按「本轮回答是否必需」重新划分。

| 事项 | 归类 | 理由 |
|---|---|---|
| `db.add_message` × 2 | **必需** | 用户要立刻看到自己发的消息 |
| `get_user_runtime`（热缓存） | **必需** | 没有 client 就没法调模型 |
| `sanitize_pending_tool_calls` | **必需** | 不修就 400，整轮失败 |
| `message_start` 事件 | **必需（最早）** | 首帧 |
| `enforce_hard_limit` | **必需，但可在首帧后** | 正确性要求（不裁就超窗），但不必在首帧前 |
| `enforce_soft_limit` | **可完全延后** | 内部调 LLM，最贵；摘要不影响本轮能否开始 |
| `get_user_runtime`（冷启动连 MCP） | **可延后** | 可以先发首帧，MCP 连上后再更新工具表 |
| `build_turn_runtime`（ACP 预检、补载通知） | **可延后** | 同上 |
| `prepare_turn_team` | **可延后** | 同上 |

**目标顺序**：

```
请求 -> add_message(2次) -> [sanitize] -> yield message_start   ← 目标 < 300ms
      -> parallel{ hard_limit, build_turn_runtime, prepare_turn_team }
      -> soft_limit（可延到本轮结束）
      -> 送模型
```

关键点：`message_start` 提到 `build_turn_runtime` **之前**。这样即使后面要花
1 秒，用户也已经看到界面有反应了。

⚠️ **一个必须核对的前提**：`message_start` 的 payload 只需要 `message_id`，
而 `message_id` 在 `:829` 就生成了（`message_id = db.new_id("msg")`），
位于 `_event_stream` 调用之前。所以提前发**不需要改事件契约**。
但 `turn` 相关的注册（`hub.register_subagent_host`、`_register_acp_manager`）
必须在 `build_turn_runtime` 之后——这部分顺序不变，只是整体后移。

另外注意：`message_start` 在文件里有**两处** yield——`:383` 是「停止已在
pre-stream 阶段到达」的早退分支，`:511` 是正常路径。改造时要保证两条路径行为一致。

### 3.2 改造二：软/硬线压缩并行，且软线不阻塞首帧

```python
# 现在的（串行）
soft = await enforce_soft_limit(...)     # 调 LLM，几秒
trimmed = await enforce_hard_limit(...)
healed = await ur.sanitize_pending_tool_calls(session_id)

# 改后
healed = await asyncio.wait_for(ur.sanitize_pending_tool_calls(session_id), timeout=SANITIZE_TIMEOUT_S)
# 首帧之后再做压缩，且两者并行（它们互不依赖）
soft_task = asyncio.create_task(enforce_soft_limit(...))
hard_task = asyncio.create_task(enforce_hard_limit(...))
```

但要小心 **`enforce_soft_limit` 与 `enforce_hard_limit` 都写 `session_history`**，
并行会丢失更新。核实细节（这点容易判断错，必须说准）：

`HistoryStore` **有**按 `(user_id, session_id)` 的锁（`history_store.py:36`），
但它只包住**单次 `set()` 的写入**（`:115`），而 `enforce_soft_limit` 的
「读 → 算 → 写」是**跨多次调用的序列**：

```
messages = await ur.store.get(...)        # :189  读（无锁）
... 计算 keep_from / 调 LLM 摘要 ...       # 中间还有几秒的 await
await ur.store.set(..., [sm, *preserved]) # :161  写（有锁）
```

`get()`（`:83`）**完全不加锁**。所以两个压缩并行时：

```
软线: get(历史A) ────────[调 LLM 3-5 秒]──────── set(基于A的结果)
硬线:      get(历史A) ── set(基于A的裁剪)                  ↑ 覆盖掉硬线的裁剪
```

**硬线的裁剪会被软线的写回整段覆盖**——这不是"锁不够"，是"读-改-写没有原子性"。
后果很实际：硬线刚裁下去的消息又回来了，下一次请求仍然超窗。

所以**不能简单并行**。正确做法二选一：

**方案 A（推荐）**：软线**不阻塞首帧**，但**仍然串行**——
把它挪到 `message_start` 之后、送模型之前，并且加超时。顺序保持「先硬后软」，
因为硬线是**正确性**要求（超窗就 400），软线是**优化**。

**方案 B**：给压缩加一把会话级「压缩互斥锁」（`compaction_lock(user_id, session_id)`），
包住整个读-改-写序列，让并行的调用排队而不是互相覆盖。

**建议**：A + B 都做。A 解决首帧，B 消除这个已经存在的真实隐患
（现在靠"调用顺序恰好是串行"隐式保证，一旦有人并行化就出事）。

### 3.3 改造三：注入点加超时预算

```python
# agent_loop.py:305
INJECTOR_TIMEOUT_S = _env_float("HLZ_INJECTOR_TIMEOUT_S", 3.0)

if self.message_injector is not None:
    try:
        raw = self.message_injector() or []
        if inspect.isawaitable(raw):
            raw = await asyncio.wait_for(raw, timeout=INJECTOR_TIMEOUT_S)
    except asyncio.TimeoutError:
        logger.warning("注入器超时（%ss），本轮跳过注入", INJECTOR_TIMEOUT_S)
        raw = []
        # 可选：发一个 injector_timeout 事件让前端知道
    except Exception:
        raw = []
```

三个细节：

1. **超时后不是失败**，是「这一轮少一点上下文」。绝不能让注入器卡死整轮；
2. **要记日志**——否则"为什么模型没看到团队消息"无法排查；
3. **是否发事件给前端**：建议发（复用 `message_injected` 的兄弟事件或加个 warning），
   但**这属于契约变更**，要单独评估。第一版只记日志 + 服务端 warning。

### 3.4 改造四：为「慢件延后」留一个通道

这是四点里最需要设计的一项，也是唯一**当前没有对应实现**的。

**最小实现**：在 `AgentLoop` 里增加一个「工具步骤之后」的注入时机。

```python
# agent_loop.py 循环内，工具执行完毕之后
if self.message_injector is not None and self._inject_after_tools:
    deferred = self.message_injector(after_tool_step=True)
    ...
```

但这会**改 `AgentLoop` 与注入器的契约**（注入器现在是无参调用）。
两个做法：

| 做法 | 成本 | 风险 |
|---|---|---|
| 给注入器传 `after_tool_step` 关键字 | 小 | 现有 3 个注入器都要改签名（或用一个 shim 兼容无参调用） |
| 新增独立的 `deferred_injector` 属性 | 中 | 两套并行机制，容易混 |

**推荐前者**，用 `inspect.signature` 探测：接受参数的传参，不接受的保持无参调用。
这样现有注入器**零改动**，新注入器可以声明需要 `after_tool_step`。

**谁会用这个通道**：第一版只有记忆检索（见记忆方案 §3.2）。
在不做记忆之前，**这个通道可以先不实现**——但要在文档里留位，
避免以后又把它塞到首帧前。

> **落地建议**：改造一/二/三 现在就做（纯收益，不改契约）；
> 改造四等记忆模块真正接入时再做（那时候才有真实需求驱动设计）。

### 3.5 改造五：可观测——先能量出来

没有度量就没法验证优化是否有效。建议加**结构化日志一行**：

```
chat.prelude user=u_xxx session=co_xxx
  add_msg=12ms runtime=8ms sanitize=3ms soft=0ms hard=1ms
  build_turn=214ms team=2ms inject=1ms first_frame=241ms
```

用现有 `logging_setup`，`logger.info` 一行，字段化。
这样以后任何"变慢了"都能一眼定位到是哪一段。

**这一条应该最先做**——它成本最低，而且是后面所有优化的验收标准。

## 4. 与 CC 的对照（验收标准）

| 能力 | CC 2.1.319 | Hlaudz 现状 | 目标 |
|---|---|---|---|
| 首帧时机 | 组装完再发（但它有 1s 硬上限） | **组装完再发，无上限** | 首帧 < 300ms，组装后移 |
| 上下文计算的惰性 | 是（函数） | 部分 | 保持 |
| 并行 | `Promise.all` 两组并行 | 串行 | 无依赖项并行 |
| 时间预算 | **1s 整体 abort** | **无** | 单点超时 + 整体上限 |
| 慢件延期 | **有（afterToolStep）** | **无** | 留通道（记忆接入时实现） |
| 单 producer 失败隔离 | 有（`dc` 内 try/catch） | 有（注入器级） | 保持 |
| 耗时遥测 | `tengu_attachment_compute_duration` | **无** | 结构化日志 |

**注意一个反直觉的点**：CC 的 `message_start` 语义和 Hlaudz 不同——CC 没有
Hlaudz 这种"先发 message_start 再算"的机制，它是**整体算完再一次性吐**。
但它用 **1 秒硬上限**兜住了最坏情况。Hlaudz 反而是"想先发首帧，但首帧前面
又串了一堆东西"，两头的好处都没占到。这是要改的核心。

### 5.0 P1–P3 实际结果（真机实测）

| 指标 | 改造前 | P1 后（可见） | P3 后 |

## 6. 一个必须澄清的取舍

**首帧提前会不会让用户看到"假的已经开始"？**

会。`message_start` 之后如果还要等 5 秒才出 token，用户看到的是"界面有反应，
但没内容"。这比"完全空白 5 秒"好，但仍不理想。

**所以 P4（压缩移到首帧后）比 P3 更重要**：P3 只是把空白换成"有反应的空白"，
P4 才是真的把等待从关键路径上移走。两者要做，但**不能只做 P3 就宣称解决**。

另一个取舍：**压缩挪到首帧后，本轮上下文会先用"未压缩"的历史跑吗？**
硬线裁剪**必须**在送模型**之前**完成，否则超窗 400。所以准确的顺序是：

```
message_start  ->  hard_limit（必需，但在首帧后）  ->  soft_limit  ->  送模型
```

注意这里顺序是**先硬后软**，与现状（先软后硬）相反。理由：

- **硬线是正确性要求**：不裁就超窗，整轮失败；
- **软线是优化**：它调 LLM 生成摘要，慢且不影响本轮能否开始。

先硬线裁到窗内，软线再做摘要——即使软线超时被跳过，本轮也能正常跑。
反过来（先软后硬）则意味着：软线花 5 秒做摘要，硬线才裁，两头都没省。

**软线能否本轮跳过？** 可以。摘要旧历史对本轮回答影响很小，
`HLZ_SOFT_COMPACT_DEFER=1`（默认开）时：本轮只保证硬线，软线延迟到**本轮结束后**
再做。这样最省——用户完全感知不到摘要的存在。

但要注意：如果一直跳过软线，历史会持续贴着硬线跑，每轮都触发硬线裁剪。
所以「延迟」不是「永不」——必须在本轮 `done` 之后真的执行一次。

### 8.2 P2：注入器超时预算

| 文件 | 改动 |
|---|---|
| `backend/app/injector_guard.py` | 新增。`InjectorGuard`：超时 + `shield` + 迟到结果下轮补交 + 收尾 `flush` |
| `backend/app/agent_loop.py` | 注入点改用 guard；`run_stream` 包一层保证任何出口都 flush；`_injector_guard_now()` 惰性绑定 |
| `backend/tests/test_injector_guard.py` | 16 条 |
| `backend/tests/test_agent_loop_injector_timeout.py` | 7 条 |

**两个关键决定（都来自核实，不是猜的）**：

1. **不能用裸 `asyncio.wait_for`**。超时会 cancel 注入器，而
   `team_store.consume_inbox` 是 `commit()` 之后才 `return rows`
   （`team_store.py:788` → `:794`）。cancel 打在 commit 之后 = 消息已标
   consumed 却注入不出去 = **静默丢消息**，比"卡住"更难查。改用 `shield`，
   超时只是「本轮不等」，任务继续跑完，结果由下一轮取走。
2. **默认超时 8s 而非 3s**。所有 DB 连接的 `PRAGMA busy_timeout` 都是 5000ms，
   注入器最多会合法地等 5 秒锁。超时设在 5s 以下 = 把正常锁等待当卡死。

**残余风险（已知）**：若超时恰好发生在最后一轮、且后台任务在 2s 收尾宽限内
没跑完，那批已 consume 的消息仍会丢。`flush()` 会打 `logger.error` 明确记录，
不会沉默。窗口很窄（要求超时正好落在最后一轮）。

### 8.3 P3：首帧提前 + 压缩互斥锁

| 文件 | 改动 |
|---|---|
| `backend/app/routers/chat.py` | `event_id` 与 `frame()` 提到最前；`message_start` 从压缩之后移到压缩之前 |
| `backend/app/compaction.py` | 新增 `compaction_lock(user_id, session_id)`；`manual_compact` / `enforce_soft_limit` / `enforce_hard_limit` 三个入口全部持锁 |
| `backend/tests/test_compaction_lock_and_prelude_order.py` | 10 条 |

**为什么压缩锁是 P3 的一部分而不是"顺手优化"**：实测确认 `HistoryStore` 有按
`(user_id, session_id)` 的锁，但它只包住**单次 `set()`**，而压缩是「读 → 算 → 写」
跨多次调用（`get()` 完全不加锁）。并发时：

```
软线: get(A) ──[调 LLM 3-5s]── set(基于 A 的摘要)
硬线:      get(A) ── set(基于 A 的裁剪)          ↑ 覆盖掉硬线的裁剪
```

硬线刚裁掉的消息会"复活"，下次请求仍超窗。现在靠调用顺序隐式保证，
一旦并行化就踩坑。P3 之后首帧提前让这类并行变得自然，所以必须先把锁加上。

**真机验证（`tools/probe_soft_compact_blocking.py`，同一场景）**：

```
改造前:  compaction = 6250ms   message_start = 6094ms
改造后:  message_start =  531ms   compaction = 6250ms   ← 压缩仍在跑，只是晚于首帧
```

首帧 6094ms → **531ms**，且 `compaction` 事件仍出现在流里（没有被跳过）。
e2e：S0 / S1 / S5 全 PASS，三个 runId 的 audit 均 `checks_failed: []`。

### 8.4 P4：软线压缩延到赛后

| 文件 | 改动 |
|---|---|
| `backend/app/deferred_compact.py` | 新增。赛后压缩调度（幂等）+ `preempt()` 抢占 + 超时 + 失败静默 |
| `backend/app/routers/chat.py` | 赛前软线压缩改为受 `HLZ_SOFT_COMPACT_DEFER` 开关控制；`done` 之后调度赛后压缩；硬线裁剪前抢占 |
| `backend/tests/test_deferred_compaction.py` | 17 条 |

**为什么赛后压缩是等价且安全的**（这是 P4 成立的前提，必须说清）：

`enforce_soft_limit` 的输入是「历史 + 本轮输入」。本轮结束后，本轮输入已经进了
历史，所以「赛后压」与「赛前压」的输入完全相同、结果等价。而软线压缩**不影响
本轮能否开始**——硬线（超窗）才是正确性问题。所以它根本不需要在关键路径上。

**P4 引入的新风险与对策**：赛后压缩持有着 `compaction_lock`，用户若立刻发下一条，
那一轮开头的硬线裁剪要抢同一把锁 —— 上一轮的摘要（最长 60s）会把新一轮首帧又拖垮。
这等于把 P3 的成果还回去。对策：

1. **硬线裁剪前先 `preempt()`** 取消在飞赛后压缩（取消安全：软线压缩幂等）；
2. 赛后压缩本身有 60s 墙钟上限；
3. 只在本轮 `status == "complete"` 时调度——停止/错误时不压，
   否则会把用户主动中断的半截上下文摘要掉。

**真机验证**（同一超软线场景）：

```
P3:  compaction = 6250ms   message_start = 531ms    soft 段 = 4100ms（赛前摘要）
P4:  compaction =  687ms   message_start = 406ms    soft 段 = 不存在
     ↑ 687ms 是硬线裁剪（赛前、必须保留），不是软线摘要
```

日志字段（`prelude-*.jsonl`）直接印证：

```
co_ffd11d7af8ad: first_frame=94   soft=None   soft_deferred_n=2   hard=281
                 ↑ 软线段消失        ↑ 赛后调度了      ↑ 硬线仍在赛前
```

e2e：S0 / S1 / S5 全 PASS，三个 runId 的 audit 均 `checks_failed: []`
（`1794538859-5206` / `1794538878-0325` / `1794538942-01ad`）。

# Agent 停止卡死与陈旧租约自愈

> 日期：2026-11-06 ｜ 状态：已实施并通过单测、构建与真实 LLM E2E ｜ 分支：feat/agent-team-scope-quota

## 1. 现象

用户在一次 Agent Team 测试中看到主代理正在撰写文档，界面一直在“执行中”，点击「停止」也无法结束；由于前端仍认为本轮处于 streaming，输入框保持禁用，用户无法发送下一条消息。刷新或稍后再发消息时，后端又可能返回 `409 generation_active`。

这个问题包含两个相互叠加的故障：

1. **停止信号是协作式的，无法打断阻塞中的 await。**
2. **数据库里的 active generation 租约没有随异常路径收敛，形成“陈旧租约”。**

只修其中一个都不够：只取消任务而不收敛 DB，会让下一轮继续 409；只释放 DB 租约而不取消任务，则后台 LLM/工具仍在运行并继续写历史。

## 2. 现场证据与根因

### 2.1 卡住的 assistant 消息

数据库中曾有一条 `status=streaming` 的 assistant 消息，内容为“在。文档正在生成，我直接把它做完。”，blocks 末尾是：

- `file_write`
- `call-9908fb2a-f896-482f-9440-1e7e08ecd64a`
- `path=build_docx.py`
- **没有对应的 `tool_result`**

说明这一轮在工具调用之后没有走完正常的 tool_result → 下一轮模型 → done 路径。SSE 请求任务、消息状态与 generation 租约三者没有在同一个清理路径里收敛。

### 2.2 旧实现的停止链路

旧实现中 `/stop` 主要调用 `request_stop()`，它只做 `asyncio.Event.set()`。`AgentLoop` 只在以下位置检查该事件：

- 两次模型轮次之间；
- 同一轮多个工具调用之间；
- LLM 流式读行的循环里。

但如果任务正卡在以下 await 上，事件永远没有机会被检查：

- LLM HTTP 响应体读取；
- 工具内部的网络/进程 await；
- `wait_agent` 等长等待；
- 前置的 runtime 构建、上下文压缩或 sanitize。

因此「停止」表现得像没有生效，SSE 连接、消息和租约都停留在运行态。

### 2.3 陈旧租约导致 409

`session_generations` 上有一个部分唯一索引，只允许同一 `(user_id, session_id)` 同时存在一条 `status='active'` 的记录。旧进程如果在 SSE 断开、任务取消或异常退出时没有执行 finally，active 行会永久保留。

之后用户再次发送消息：

1. `acquire_generation()` 插入新 active 行；
2. 唯一索引报冲突；
3. 接口返回 `409 generation_active`；
4. 前端无法继续输入。

内存中实际上已经没有对应任务，但 DB 不知道；单看 DB 也无法区分“真的在运行”与“上一次进程/连接留下的幽灵租约”。

### 2.4 前端停止顺序加重了问题

旧前端 `stop()` 先 `await api.stop(...)`，成功后才 abort 本地 fetch。只要后端被某个 await 卡住，用户就会一直看到「停止」按钮和禁用输入框。

即使本地 abort 了，旧 `finally` 也可能在没有校验 generation 的情况下清空新一轮的 `abortRef` / `streaming` 引用，带来“停止后立刻发送导致白屏/互相覆盖”的竞态。


## 3. 设计：三层停止 + 双源活性判定

### 3.1 三层停止模型

| 层 | 机制 | 作用 |
|---|---|---|
| 协作层 | `asyncio.Event` | 在轮次边界/流式读行处优雅退出，保留已生成内容 |
| 强制层 | `asyncio.Task.cancel()` | 打断 LLM socket、工具 await、`wait_agent` 等阻塞点 |
| 资源层 | `stop_code_runs` + `SubagentHost.stop_all()` | 杀掉 code_run 子进程树、取消子代理并短暂 join |

停止接口同时触发三层，不能只做其中一层。

### 3.2 进程内 generation registry

`backend/app/runtime.py` 维护三张按 `(user_id, session_id, generation_id)` 索引的注册表：

- `_stop_events`：协作停止标志；
- `_generation_tasks`：实际执行 StreamingResponse 的 asyncio Task；
- `_generation_reservations`：HTTP 请求已拿到 DB 租约、但 streaming task 尚未开始迭代的交接窗口。

新增接口：

- `register_generation()`：登记 event + 当前 task；若停止意图已提前到达，event 直接为 set；
- `cancel_generation()`：set event 并 cancel task；
- `reserve_generation()` / `release_generation_reservation()`：覆盖请求被接受但尚未消费 body 的窗口；
- `is_generation_live()` / `has_active_generation()`：判断某个 DB generation 是否真有进程内执行体。

**关键原则：数据库租约不是活性事实，进程内 task registry 才是活性事实。**

### 3.3 reservation TTL

`StreamingResponse` 的构造与首次迭代之间存在一个很短的空窗。若不做 reservation，两标签页同时发送时，第二个请求可能把第一个请求误判为陈旧租约。

但 reservation 也不能永久存在：如果客户端拿到响应却从不读取 body，它会成为新的“幽灵”。因此给 reservation 30 秒 TTL；超时后自动视为不活跃。

### 3.4 停止意图“墓碑”

停止可能在 `register_generation()` 之前到达，例如用户刚发送就立刻点击停止，此时任务还在 runtime 构建或压缩阶段。

实现上用 `_stop_requested` 集合记录显式停止意图：`request_stop()` / `cancel_generation()` 即使暂时找不到 task，也会写入该集合；之后 `register_generation()` 返回一个已经 `set()` 的 event，`_event_stream` 在 prelude 前直接落一条 stopped 消息并返回。

### 3.5 更早登记 task

新代码在 `guarded_stream()` 刚进入时就调用 `register_generation()`，而不是等到 `_event_stream` 完成 runtime 构建、压缩、sanitize 之后。这样即使卡在前置阶段，`/stop` 也能 cancel 到实际 task。

## 4. 陈旧租约自愈

### 4.1 发送时的单次重试

`send_message()` 遇到 `acquire_generation()` 返回 False 时：

1. 查当前 active generation；
2. 用 `is_generation_live()` 判断它是否真有进程内 task/reservation；
3. 若**不活跃**，调用 `team_store.converge_generation_facts(..., status='stale')`；
4. 把该会话遗留的 streaming 消息收敛为 stopped；
5. 重试一次 acquire；
6. 仍失败才返回 409。

这样单标签页异常断开、代理超时、进程级异常都不会永久封死会话。

### 4.2 为什么必须有 generation 级收敛函数

`converge_generation_facts()` 在一个 `BEGIN IMMEDIATE` 事务里同时处理：

- `session_generations`：active → stopped/stale；
- `team_tasks`：该 generation 下 `in_progress` → `pending`，清空 owner，`version+1`；
- `team_runs`：active → stopped/stale。

任务 `version+1` 是为了让旧 CAS 持有者无法在停止后继续完成/改写任务。只更新 generation 而不更新任务，会让 TeamPanel 永远显示“进行中”，并且旧 worker 仍可能把任务写成 completed。

### 4.3 读路径也做自愈

只在发送时自愈还不够：用户刷新页面后若只看历史，TeamPanel 可能一直显示“运行中”。因此：

- `GET /api/sessions/{id}`：若无 live generation，则收敛 active lease 与 streaming 消息；
- `GET /api/sessions/{id}/team`：若无 live generation，则收敛 active generation / orphan active team 后再返回快照；
- 新增 `converge_orphaned_active_teams()`：处理“generation 已经不存在，但 team_runs 仍是 active”的崩溃窗口。

## 5. 停止接口的最终语义

`POST /api/sessions/{id}/stop`：

1. `generation_id` 缺失时从 DB 读取 active generation；
2. 设置协作 event；
3. `cancel_generation()` 取消实际 task；
4. 级联 `stop_subagent_generation()`；
5. **无论 hub 是否存在，都调用 `stop_code_runs()`**；
6. 最多等待 ~1 秒，让被取消的生成器落增量快照；
7. 若仍无终态，强制把目标 assistant 消息标记为 `stopped`；
8. `converge_generation_facts(status='stopped')` 并释放租约；
9. 返回已落库的 message 快照。

停止接口不再为了等一个卡死的后台 generator 而阻塞。用户明确点击停止时，可见消息必须立即进入终态，租约也必须立即释放。


## 6. 前端：本地优先停止

`App.stop()` 的顺序改为：

1. 立即把当前 assistant 气泡置为 `stopped` 并写入 `run_finished_at`；
2. 立即 `abort()` 本地 SSE fetch；
3. 立即 `setStreaming(false)`，让 Composer 恢复可用；
4. **后台并行**调用 `/stop`，不阻塞 UI；
5. `/stop` 返回快照后合并进本地状态；
6. 250ms 后重新拉取消息与 Team 快照，修正服务端最终状态。

同时修复了一个停止后的竞态：旧 SSE 的 `finally` 只在 `genIdRef.current === genId` 时清空 `streaming` / `abortRef` / `streamSidRef`。否则用户停止后马上发下一条，上一条的 finally 会把新一轮的引用清掉，造成白屏或“输入无响应”。

TeamPanel 头部在 streaming 时增加了一个轻量的「停止」按钮，避免用户必须回到 Composer 才能终止。按钮只负责调用同一个本地优先 `stop()`。

### 6.1 为什么不是先等后端

“停止”是用户意图，不是需要服务端确认后才生效的请求。UI 的职责是立即恢复可控状态；服务端 `/stop` 负责实际取消与数据收敛。二者应当并行，而不是串行。

为了不丢已生成内容，停止前已有的本地文本/工具/图片块保持原样；服务端返回的权威快照会做合并式覆盖。

## 7. 子代理与进程级联

- `SubagentHost.stop_all()` 现在 cancel 后会 `asyncio.wait(tasks, timeout=1.5)`，让子代理任务有机会释放 quota lease、写侧链、发 `subagent_end`。
- 停止 endpoint 在任何情况下都会调用 `stop_code_runs()`，不再被 `if hub is not None and body.generation_id` 包住。
- `code_run` 自身在 `CancelledError` 路径里会 `_kill_tree()`；Windows 下使用 `taskkill /T /F` 杀掉整个进程树。

## 9. 风险与未决项

1. **强杀 task 的边界**：如果第三方 MCP 工具在自己的线程池里执行且不响应 asyncio cancellation，task cancel 只能让主协程退出，底层线程仍可能跑完。当前用「消息立即 stopped + 租约立即释放」保证用户可继续；后续可在 MCP 层增加 timeout/孤儿任务治理。
2. **1 秒等待窗口**：为保持停止响应，服务端最多等 1 秒让生成器落增量快照；极端情况下会走强制 `status=stopped` 回退，此时最后一个尚未被 `_persist` 的极小增量可能丢失。
3. **多进程部署**：当前 task registry 是单进程内存态。若未来使用多 worker，需把取消信号改为跨进程机制（Redis pub/sub 或每进程一致性哈希）。单进程 uvicorn（本项目当前形态）下设计成立。
4. **reservation TTL 过长**：30 秒是为了避免慢网络/冷启动误判。若未来发现客户端拿到响应却不消费，可结合请求断开事件提前释放。

## 0. 先给结论

**你的感觉是对的，但原因不是「多智能体开销」。**

| 你的三个候选解释 | 本次实测 | 判定 |
| --- | --- | --- |
| 它真的写那么多内容 | 正文 + 思考共 **7,564 帧**流式输出 | **部分成立** |
| 它响应的慢 | 有一段 **53 秒零事件**，且恰好卡在「开始写底稿」之后 | **成立** |
| 别的设计缺陷 | `wait_agent` 占 78%，但那是**真实依赖**（writer 等 researcher） | **不成立** |

真正的答案：**慢在「模型一次要吐出很长的内容」**，
而不是「多代理调度有额外开销」。这个区别很重要 —— 前者改任务拆分，
后者改编排代码，方向完全相反。

## 2. ★ 决定性证据：53 秒静默卡在「开始写底稿」之后

按 30 秒切桶统计（只统计流式帧）：

| 窗口 | 事件数 | 桶内最长静默 |
| --- | --- | --- |
| 30–60s | 399 | 2.1s |
| 60–90s | 1,121 | 3.4s |
| 90–120s | 1,024 | 0.6s |
| **120–150s** | **0** | **53.1s** |
| 150–180s | 284 | 2.0s |
| 210–240s | 1,569 | 1.7s |
| 240–270s | **2,148** | 0.3s |
| 330–360s | 143 | 3.8s |

**120–150s 整段一个事件都没有。** 前后两帧的原文：

```
t=104.8s  sub.text_delta   sub:researcher_t1  底稿。   ← 「现在开始写事实底稿。」
          ... 静默 53.1 秒 ...
t=157.9s  sub.tool_start   file_write path=research/trump.md
t=157.9s  sub.tool_result  file_write
```

### 2.1 这 53 秒花在哪，可以精确判断

关键在**紧邻的两个时间戳**：

| 时刻 | 事件 | 说明 |
| --- | --- | --- |
| 104.8s | 最后一条 text_delta：「…现在开始写事实底稿。」 | 模型说完「我要开始写了」 |
| **104.8 → 157.9s** | **零事件** | **模型在生成那一大段文件内容** |
| 157.9s | `file_write` 开始 | |
| **157.9s** | `file_write` 结束（同一秒） | **写入本身耗时 ≈ 0** |

⇒ **写文件不慢（0 秒），生成要写的内容慢（53 秒）。**

这条判据能区分两种完全不同的病因：

| 假设 | 会看到什么 | 本次实际 |
| --- | --- | --- |
| 文件 I/O 慢 | `tool_start` 与 `tool_result` 间隔大 | ❌ 两者在同一秒 |
| 模型生成慢 | 上一个 `text_delta` 与 `tool_start` 之间大静默 | ✅ 53.1s |

### 2.2 同样的模式在 writer 上重演

```
t=276s  sub.text_delta  sub:writer_t2 …文件…   ← 开始写报告
        ... 静默 36.6 秒 ...
```

writer 的窗口是 128 秒，其中 **36.6 秒**是同一形态的静默。

## 3. 所以「慢」到底是什么

### 3.1 不是这些

| 排除项 | 证据 |
| --- | --- |
| 文件 I/O | 所有 `file_write` 的 `tool_start` → `tool_result` 都是 **0.0s** |
| 工具（搜索） | exa 搜索 6 次，合计 **15.5s**，最长单次 3.4s |
| 多代理调度开销 | `wait_agent` 的 78% 是真实依赖（见 §1.1） |
| 沙箱 / 权限 | 本轮 0 次 507、0 次 PermissionError |
| prelude（首帧前奏） | `first_frame` 全程 **10 毫秒级**（见 §5） |

### 3.2 是什么：模型一次要吐太长的内容

用流式帧的内容长度估算吐字速率（活跃时段，即去掉 >10s 静默后）：

| 指标 | 值 |
| --- | --- |
| 流式帧总数 | 7,564 |
| 累计输出字符（含思考） | **58,385** |
| 总跨度 | 359.3s |
| 去掉 >10s 静默后的活跃时长 | 257.4s |
| **吐字速率** | **227 字符/秒** |
| >10s 的静默 | 3 段，合计 **101.8s（占 28%）** |

**227 字符/秒是正常的模型吐字速度**——说明不是上游限速，也不是网络问题。
慢的唯一原因是**要吐的字太多**：58,385 字符 ÷ 227 ≈ 257 秒，
与实测活跃时长 257.4s 几乎完全吻合。

按阶段拆，最长的两段单次生成：

| 时段 | 时长 | 字符数 | 速率 |
| --- | --- | --- | --- |
| t=216.8–312.4s（writer 写报告正文） | 95.6s | **27,495** | 287.6 字符/秒 |
| t=81.3–157.9s（researcher 写底稿） | 76.6s | **14,025** | 183.2 字符/秒 |

这两段**各自都是「一次 LLM 调用要输出上万字符」**。
按 227 字符/秒算，写 1 万字就需要 44 秒——这是物理下限，不是缺陷。

> **这条给了明确的优化方向**：想更快，只能让模型**分多次写**
> （每次写 2–3 千字），而不是让它一口气写完。
> 因为流式输出是串行的，字数是硬约束。

## 4. 与单智能体对比：多代理慢在哪，不慢在哪

| 环节 | 单代理 | 本项目的多代理 | 差异性质 |
| --- | --- | --- | --- |
| 读（搜索 + 读结果） | 串行 N 轮 | 子代理内部同样串行 | **无差异** |
| 写（生成文件内容） | 一次生成全文 | 子代理一次生成全文 | **无差异** |
| 调度 | 无 | 根代理 `wait_agent` 等子代理 | **有开销，但是真实依赖** |
| 上下文 | 全程同一份 | 每个子代理独立上下文 | **可能更省**（不用带全部历史） |

**关键发现：多代理本身没有引入显著的额外生成量。**
researcher 的 14,025 字符 + writer 的 27,495 字符 = 41,520 字符，
这些字在单代理场景下**同样要写**（调研结论 + 报告正文）。

所以「多智能体读写比单智能体慢」这个感觉，来源不是多代理，而是：

1. **任务本身长了**（调研 + 写作两件事，单代理场景常只做其中一件）
2. **串行**（writer 依赖 researcher 的产物，物理上不能并行）
3. **模型一次写太多**（单次 2 万字符的生成本身就是分钟级）

### 4.1 什么情况下多代理真的会更慢

有一个**真实的结构性风险**，本次没有触发但值得记：

| 风险 | 表现 | 本次是否触发 |
| --- | --- | --- |
| 子代理重复做同一件事 | 两个子代理都去搜同样的关键词 | 否（researcher 搜 6 次，writer 搜 0 次） |
| 根代理把子代理的结论再总结一遍 | 额外一次长生成 | 否（根代理最终消息仅 1,731 字） |
| 上下文重复注入 | 每个子代理都带完整系统提示 | 是，但这是必要成本 |

**如果将来出现「多代理明显更慢」，优先查第 1、2 条**——
它们是真正的浪费，而本次都没有。

## 6. 真正的优化方向（按收益排序）

### 6.1 P0：让大文件分段写

**依据**：本次最大的两段生成是 27,495 与 14,025 字符，
按 287 / 183 字符每秒算，各需 96 / 77 秒。这是**单次 LLM 调用的物理时长**。

`file_write` **已支持** `mode="append"`（`builtin_tools.py:261`），
所以分段写不需要改代码，只需要改**提示词引导**：

```
写大文件（预计超过约 3000 字）时，分多次写：
  第 1 次 file_write(path=..., content=第一部分)
  第 2 次 file_write(path=..., content=第二部分, mode="append")
  ...
这样每一次生成的等待都更短，用户能更早看到进展。
```

**预期收益**：不改总时长（字数不变），但
① 用户能更早看到第一批内容；② 中断时不会前功尽弃；
③ 每段的延迟更接近交互可接受范围。

> ⚠️ 这条改的是**体验**不是**总时长**。总时长由字数决定，分段不减少字数。

### 6.2 P1：把「调研」与「写作」的边界做得更明确

本次 writer 拿到了 researcher 的完整产物（14,025 字符），
但 writer 自己的报告里又重述了一遍政策要点（27,495 字符）。

如果产品目标是「报告要能独立阅读」，这是必要的；
如果只是「转述」，则有一半是重复劳动。

**这需要产品决策，不是技术问题。**

### 6.3 P2：给 wait_agent 加进度反馈

目前根代理 `wait_agent` 151.8s / 127.2s 期间，
用户界面上只有等待。子代理的流式事件其实已经到了
（15,377 条里 7,649 条是 `subagent_event`），但**不知道前端是否实时渲染**。

若没有，加上「子代理正在做什么」的实时显示，
能把「看起来卡住」变成「看到它在写」。

## 7. 结论一句话

**多智能体没有让你变慢；是你的任务本来就含 58,385 字符的生成量，
而模型吐字速度是 227 字符/秒。133 秒的字数 ÷ 227 ≈ 257 秒的活跃时间，
账是对得上的。**

真正的浪费只有可选的重复转述（§6.2），以及无法分段导致的长时间空白（§6.1）。

## 8. CC 是怎么处理「一次写太多」的（319 源码核验）

你提到「CC 里的写从来没有说一次性写」。我查了 319 源码，结论要分开说：

### 8.1 CC 的 Write 描述里**没有**「分段写」这句话

`reconstructed319/deminified/m0446_0x11a5dc93.js:16-27` 全文：

```
Writes a file to the local filesystem.

Usage:
- This tool will overwrite the existing file if there is one at the provided path.
- If this is an existing file, you MUST use the Read tool first ...
- Prefer the Edit tool for modifying existing files — it only sends the diff.
  Only use this tool to create new files or for complete rewrites.
- NEVER create documentation files (*.md) or README files unless explicitly requested.
- Only use emojis if the user explicitly requests it.
```

**没有任何字数分界，也没有「分段」字样。** 所以「CC 明确要求分段写」这个
说法不成立 —— 我把这条查清了再写，不按印象说。

### 8.2 但 CC 确实解决了同一个问题，用的是另一条路

关键是这一句：

> `Prefer the Edit tool for modifying existing files — it only sends the diff.`

CC 的策略是**按文件状态分流**：

| 场景 | CC 用什么 | 单次输出量 |
| --- | --- | --- |
| 新建文件 | `Write` 一次写完 | 大（无法避免） |
| **修改已有文件** | **`Edit` 只发 diff** | **小（只发差异）** |

`Edit` 的 schema 是 `old_string` / `new_string`（`m0591:212428-212440`），
且描述明确要求「`old_string` 保持最小，通常 1–3 行」。
所以**改 100 行里的 2 行，输出只有 2 行**，而不是整文件 100 行。

### 8.3 这对 Hlaudz 意味着什么

Hlaudz 的 `file_patch`（`old_content` / `new_content`）**等价于 CC 的 `Edit`**，
已经具备「只发 diff」的能力。所以 CC 那条路我们也有。

**真正缺的只有「新建大文件」这一半** —— 而本次 96 秒空白的场景
正好是新建（`file_write path=research/trump.md`，之前不存在）。

### 8.4 因此本次改动的定位

| 改动 | 对应 CC | 性质 |
| --- | --- | --- |
| `file_write` 描述加「长内容分段写」 | CC **没有**这条 | **Hlaudz 原创补充** |
| `file_patch` 只发 diff | 等价 CC 的 `Edit` | 已有，无需改 |

这条补充是**超出 CC 的**，因为：
- CC 是交互式 CLI，用户能看到流式输出滚动，50 秒空白不那么难受；
- Hlaudz 是 Web，中间只有 `.......` 占位（事故里见过 `content='.......'`）。

所以对 Hlaudz 来说，分段的**体感收益比 CC 更大**。

### 8.5 已落地的改动

`backend/app/builtin_tools.py` 的 `file_write` 描述新增：

```
**长内容请分段写**：正文超过 3000 字时，拆成多次调用——
第一次 mode=overwrite 写开头，之后每次 mode=append 追加一段（每段 2000–3000 字）。
原因：内容是在模型生成阶段产生的，一次性写完会让用户等几十秒只看到空白
（实测写 27,000 字需要约 96 秒）；分段写则每一段几千字就能落盘，
用户能更早看到进展，中途被打断也不会全部作废。
注意分段只改善体感，不减少总生成时间——总时间由字数决定。
```

测试：`backend/tests/test_write_chunked_guidance.py`（3 项，含反向确认）。

## 9. ★ 第二轮实测：抓到另一个慢源（exa 上游不稳）

第一轮（`co_891bb2fd3751`）359 秒，第二轮（`co_078dbecdd03e`）**1352 秒**，
慢 3.7 倍。时间轴直接指出了原因。

### 9.1 第二轮的三段 300 秒静默

工具耗时排名（第二轮）：

| 耗时 | 工具 | 次数 |
| --- | --- | --- |
| **426.2s / 420.0s / 300.0s** | `wait_agent` | 3（根代理等子代理，真实依赖） |
| **321.5s × 2** | `web_search_exa` | 2 |
| **301.5s × 2** | `web_search_exa` | 2 |
| **301.2s × 2** | `web_search_exa` | 2 |

**6 次 `web_search_exa` 各卡 300–321 秒。** 而 `MCP_CALL_TIMEOUT_S` 默认正是
**300 秒**（`mcp_client.py:131`）—— 是超时打满，不是正常返回。

### 9.2 但 exa 本身不慢

单独实测同一批搜索（`work/_exa_concurrent.py`）：

| 方式 | 6 次搜索 |
| --- | --- |
| 串行 | 10.6s（每次 1.5–2.0s） |
| 并发 | 1.0s |

⇒ **不是 exa 的吞吐问题。**

### 9.3 真实原因：exa 上游间歇性失败

连跑 12 轮（`work/_exa_reliability.py`，每轮独立建连 + 一次搜索）：

| 轮 | 结果 | 耗时 |
| --- | --- | --- |
| 0–4 | ok | 3.8–6.8s |
| **5** | **no_tools** `All connection attempts failed` | 21.3s |
| 6–7 | ok | 4.7–5.7s |
| **8** | **TimeoutError** | 30.0s |
| **9** | **TimeoutError** | 47.5s |
| 10–11 | ok | 4.0–4.6s |

**成功 9/12（75%），失败时卡 30–47 秒。** 失败形态两种：
- `All connection attempts failed`（连不上）
- `TimeoutError`（连上了但不返回）

这与 run2 的 300 秒卡死是同一现象的量级放大
（run2 里并发更多、且有 `GET stream disconnected` 重连，放大到打满 300 秒超时）。

### 9.4 结论：这是上游问题，不是我们的设计缺陷

| 判据 | 结果 |
| --- | --- |
| exa 单独调速 | 快（1.5–2s） |
| exa 连续调用成功率 | **75%** |
| 失败时的表现 | 连接失败 / 超时（网络层） |
| 我们的并发度（8/32） | 未触及上限 |

**exa 上游有约 25% 的请求失败**，失败时要么快速失败、要么卡到超时。
当模型并发发出 6 个搜索时，只要其中有 2 个失败，整轮就被拖 300 秒。

> ⚠️ 这条**不能通过改我们的代码修好**。可行的缓解：
> ① 把 `MCP_CALL_TIMEOUT_S` 从 300 降到 60（失败时快速放弃，让模型重试）；
> ② 或给 exa 加客户端重试（失败后立即重试一次，成功率提到 ~94%）。
> 这两条都需要产品决策，本轮未实施。

### 9.6 对「多代理更慢」的最终回答

| 候选原因 | 本次证据 | 是否成立 |
| --- | --- | --- |
| 内容真的多 | 58,385 字符 ÷ 227 字符/秒 = 257s | ✅ 成立（run1） |
| 模型生成慢 | 吐字速率正常 | ❌ 不成立 |

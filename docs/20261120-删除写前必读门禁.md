# 删除「写前必读」门禁（`ReadRegistry` 硬门禁）

日期：2026-11-20
影响：`backend/app/builtin_tools.py`、`backend/app/sandbox/manager.py`

## 1. 依据

### 1.2 ⚠️ 一处必须写清的差异

那条 override 只点名 **Edit**。同一份文件 `:3327` 里 **Write 的描述没被推翻**：

> When to use: creating a new file, or fully replacing one you've already Read.
> **Overwriting an existing file you haven't Read will fail.**

用户明确要求删除整个门禁（含覆盖写），按用户决定执行。这里记下差异，
免得将来有人拿「CC 只放开了 Edit」来质疑这次改动 —— 那是知情选择，不是误读。

## 2. 真机证据：这个门槛对大文件是**必然失败**

2026-11-20 跑 Agent Team（session `co_8abfb27422c8`），`writer_c` 的原话：

> 上一条 `file_write` 因为「只读了片段」被硬门禁拒绝，我不再赌一次性超长写入，
> 改成清空旧文件后分段 `file_write`。

根因在 `builtin_tools.py`：

```python
DEFAULT_READ_LINES = 200
...
registry.record(target, complete=(start == 1 and not keyword and end >= total))
```

子代理要覆盖的报告 22–45 KB（远超 200 行），**一次 `file_read` 永远读不全**
⇒ `complete` 恒为 `False` ⇒ 覆盖写恒被拒。

不是「偶尔不方便」，是**必然失败**。表现到用户那里就是「卡住」：

| 子代理 | 状态 | 轮次 |
| --- | --- | --- |
| researcher_a | stopped | 10 |
| writer_b | stopped | 4 |
| writer_c | stopped | 16 |

任务最终回到 `pending`，起了 3 个 writer。

## 3. 改了什么

| 位置 | 改动 |
| --- | --- |
| `builtin_tools._write_impl` | 删 `registry.check` |
| `builtin_tools._patch_impl` | 删 `registry.check` |
| `builtin_tools._read_impl` | 删 `registry.record`（门禁已无消费者） |
| `builtin_tools.build_builtin_tools` | 删 `ReadRegistry()` 与 4 处 `registry=` 实参 |
| `manager.write_file` / `patch_file` | 删 `registry` 参数与两处 `check` |
| `file_write` / `file_patch` 工具描述 | 「硬门禁」文案改为「不需要先读」 |

`read_registry.py` 文件**保留**（类仍正确、仍可测），只是不再接到工具上。
理由：将来若要做「你上次读之后文件被改过」的**提示**（不是硬拒绝），能直接复用。

## 4. 删掉之后靠什么保证安全

这是必须回答的问题 —— 门禁原本是在防「覆盖掉用户手写的东西」。

| 防线 | 是否仍在 | 说明 |
| --- | --- | --- |
| 路径安全层 | ✅ **一行未动** | `safe_workspace_path` / `resolve_in_workspace`：越界、`..`、绝对路径、软链逃逸全部照旧拒绝。这是**真正的安全边界** |
| `file_patch` 唯一匹配 | ✅ | `old_content` 命中 0 处或多处都报错。「改错地方」在语义上仍难发生 |
| 文件不存在即报错 | ✅ | `file_patch` 对不存在的文件仍返回「文件不存在」 |
| 覆盖前确认内容 | ⚠️ 降级为 **prompt 建议** | 工具描述里保留「要保留原内容就先读」，但不再是代码门禁 |

**代价（诚实记录）**：模型若在一个有内容的路径上误用 `overwrite`，
会静默覆盖。这条风险由 prompt 层承担，不再由代码兜底。
用户已知情并要求删除。

## 6. 这一轮的失误

| 失误 | 后果 | 怎么防 |
| --- | --- | --- |
| 清理脚本「遇到第一个不匹配就 SystemExit」 | 我在同一份文件上分两次跑，第二次前半已替换 → 立刻退出，**后半一处都没改**，留下「一半有门禁一半没有」的中间状态 | 批量替换必须**逐条幂等**：找不到就记录并继续，最后统一报告。中间状态比全有或全无都难查 |

| 以为删代码就够了 | 工具描述还写着「硬门禁」，模型会做无谓的额外步骤 | 行为改动必须同步**文案**，并写测试钉住（`test_tool_descriptions_do_not_claim_a_hard_gate`） |

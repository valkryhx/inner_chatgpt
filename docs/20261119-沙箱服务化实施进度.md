**池的关键语义（实现时发现的，方案里没写细）**

「queue 模式不淘汰」这个字面理解是**错的**，会导致永远等不到：

```
槽是专属的 → u1 release 之后，他的槽仍然是 u1 的，仍然占着 max_slots 名额
           → u2 等多久都不会有「空名额」
```

所以 queue 的正确语义是「等到**有机会腾出名额**」：
- 槽被 TTL 回收 / 显式销毁 → 名额空出
- 槽变成空闲 → **淘汰它**

区别在别处：**evict 在看到空闲槽时立刻淘汰；queue 也会淘汰**（否则死等）。
真正的差别是「全忙时」——两者都退化成一件事：等。

> 这条是测试 `test_queue_evicts_idle_slot_when_owner_released` 抓出来的。
> 该测试的期望值改过两次，两次都记在 docstring 里：
> 第一次写「u1 的槽应该还在」（会导致永远等），
> 第二次写「u1 忙碌时 u2 应该能拿到」（违反「忙碌槽永不淘汰」硬规则）。

**纯净 fork 的三条铁律（写进 `executor/bwrap.py` 的 `_DAEMON_SCRIPT` 注释）**

1. 父进程**绝不执行用户代码** —— 只 import + `fork`。
   这是「既快（8.8ms）又不泄漏」的唯一原因。
2. 子进程必须 `os._exit()` —— 正常 return 会跑父进程上下文注册的
   atexit / 第三方 cleanup，破坏父进程状态。
3. 预导入清单固定，不按请求动态 import —— 否则用户数据进父进程 → 跨租户泄漏。

**归档的稳定 key**

`<user_id>/<session_id>.tgz`，**不含实例 id / 时间戳**（照 Aivory 的坑）。
用实例 id 的话「回收后再唤起」永远恢复不到上次工作区。

**测试里修掉的两个自身错误**

1. `test_pack_respects_max_bytes` 用 `b"x" * 100_000` 造数据，
   gzip 压到几百字节 → 根本没超上限 → 假红。改用 `os.urandom`。
2. `test_slot_child_uses_exit_not_atexit` 检查错了文件
   （查 `pool.py` 而不是 `executor/bwrap.py`）——职责搞混了：
   池负责调度，执行器负责 fork。

### 联调中修掉的两个部署问题

**1. 沙箱服务是 uid 1000，写不进 appdata 卷**

```
PermissionError: [Errno 13] Permission denied: '/app/backend/data/workspaces'
```

根因：appdata 卷里的目录由 **app 容器以 root 创建**（`drwxr-xr-x root root`），
而沙箱服务按设计跑 uid 1000（非 root，否则 `RLIMIT_NPROC` 失效、fork 炸弹拦不住）。

三个选项，选了第 3 个：

| 选项 | 结论 |
| --- | --- |
| 服务跑 root | ❌ 否决：fork 炸弹拦不住（实测 root 下起满 60 个） |
| 卷 chmod 777 | ❌ 否决：appdata 里还有 memories/、logs/，放宽整卷是拿安全换方便 |
| **只把两个子树 chown 给 1000** | ✅ 采用：`workspaces/`、`sandbox/`、`sandbox-archives/` |

实现成独立的 `sandbox-perms` 一次性服务（`alpine` + `chown`），沙箱服务
`depends_on: condition: service_completed_successfully`。
没改沙箱镜像加 entrypoint——那会把权限逻辑和业务代码混在一起。

**2. Dockerfile 的 COPY 路径与构建上下文不匹配**

`COPY sandbox_service/` 在上下文是仓库根时找不到（应为
`backend/sandbox_service/`）。已修，并把探针里的构建命令同步成 `.` 上下文。

### ⚠️ 未完成项：池的「预热复用」没有接上（**已于同日补完，见本文末节**）

> 本节保留原文作为「当时的判断」，便于复盘。
> 实际修复时发现根因比这里写的更深：不只是「池没接 prewarm」，
> 而是 `get_executor()` 每次返回新实例 —— 详见文末
> 「2026-11-19 补完」一节的缺陷 1。

**事实**：`_DAEMON_SCRIPT`（纯净 fork 父进程）在 `executor/bwrap.py` 里
**只出现 1 次，即定义处**。`exec()` 每次都执行：

```python
argv = self._build_argv(workspace, code, code_type, cwd=cwd)   # bwrap python3 -c <code>
proc = await asyncio.subprocess.create_subprocess_exec(*argv, ...)
```

也就是说：**每次调用都是全新进程 + 全新 import**（683ms 就是 `import pandas` 的钱）。
`pool.py` 的槽调度逻辑是对的（建/复用/淘汰/上限都测过），
但它管的 `Slot.parent_proc` 只是个 `{"preload": ...}` 字典，**没有真的起进程**。

**影响**：

- 池的**并发控制、上限、OVERFLOW** 全部生效（这些测过、端到端验过）
- 池的**性能收益（8.8ms vs 1105ms）完全没拿到** —— 现在等价于方案 §4.2 的形态 A
- 单次调用性能和「不池」一样，方案 §4.5 的内存预算表因此偏高
  （槽没有常驻解释器，实际省内存但也省不到速度）

**为什么还没做**：真正的预热复用要满足三条铁律（父进程不执行用户代码、
子进程 `os._exit()`、预导入固定），需要在 bwrap 内维持一个常驻进程
并通过管道通信。这是**阶段 3.5**，不是本次联调的范围。

**下一步（按性价比）**：

1. 先让 `exec()` 支持「给一个已启动的 daemon 发代码、收结果」
   （`Slot.parent_proc` 变成真的 `asyncio.subprocess.Process`）
2. 槽创建时启动 daemon 并等 `READY`
3. 验证：第二次调用 <50ms（而不是 683ms）
4. 反向确认：把 daemon 复用去掉，第二条必须重新变回 ~680ms

**当前结论**：沙箱**能跑、隔离生效、多租户安全、并发受控**，
但**性能收益尚未兑现**。这不影响正确性，影响的是「每次调用多付 ~600ms」。

## 2026-11-19 补完：预热复用 + 进程组清理 + 空闲回收（三处缺口）

上一节列的「下一步」四条已全部完成，过程中又抓出**两个此前没记录的缺陷**。
三处缺口的共同点：**每一处单看代码都是对的**，断的是它们之间的接线。

### 一、预热复用接通（上一节的「下一步」1–4）

| 步骤 | 落点 |
| --- | --- |
| `exec()` 支持给已启动的 daemon 发代码收结果 | `executor/bwrap.py::_exec_via_daemon` |
| 槽创建时启动 daemon 并等 `READY` | `pool.py::_create` → `prewarm` 回调 |
| 销毁/淘汰/空闲回收时停 daemon | `pool.py::_drop_slot` → `on_destroy` 回调 |

**实测（容器内直连 `/v1/exec`，5 次复用）**：

```
first(incl prewarm): 771ms
reuse: 11ms, 15ms, 9ms, 8ms, 7ms
```

对比修复前每次 522–683ms。端到端探针第 5 项阈值从 500ms **收紧到 300ms**——
500ms 拦不住 567ms 那种"看起来像复用其实没有"的情况，阈值必须能区分两种机制。

### 二、⚠️ 新发现缺陷 1：`get_executor()` 每次返回新实例

**这是「预热接不上」的真正根因**，比"池没接 prewarm"更隐蔽：

```
建槽 → get_executor() 返回实例 A → start() 在 A 上起 daemon
exec → get_executor() 返回实例 B → B._daemons 是空的 → 走一次性模式
```

池的日志会显示「槽预热完成」，性能收益却是零。修法：`main.py` 加进程内单例
`_get_executor()`，四处调用点全部改用它。测试 `test_executor_is_singleton_across_calls`
钉死这一点，反向确认证明拆掉就变红。

**副产物**：单例带来跨测例污染（fake 执行器泄漏到下一个测例，症状是
`IndexError: list index out of range`）。在 `tests/conftest.py` 加 function 级
autouse fixture 重置 `_pool` / `_executor`。这与之前 `backends/base.py`
模块级缓存那次是同一类问题。

### 三、⚠️ 新发现缺陷 2：destroy 留下孤儿 bwrap 进程

**探针实测**（`docs/probes/20261119-daemon进程清理探针.py`，容器内跑）：

```
daemon pid(bwrap)=386
执行后: [386(ppid=380, S), 387(ppid=386, S)]      ← 两层！
destroy 返回，proc.returncode=-9
销毁后: [387(ppid=1, stat=S)]                     ← 内层被 init 收养，还活着
VERDICT: LEAK（有活进程）
```

**根因**：bwrap 会 fork 一个内层进程。`proc.kill()` 只对最外层发 SIGKILL，
而 SIGKILL **不可捕获**——外层死了就没机会转发给内层，内层随即被 init 收养继续跑。
它压着 `prlimit --as=2GB`，RSS 约 1.3MB。单看很小，但槽按 TTL 反复建/销，
累积几天就是容器 OOM。**日志永远看不出来**（照常打「daemon 已停」），只能数进程。

**修法**（两处必须成对）：`create_subprocess_exec(..., start_new_session=True)`
让 daemon 独占进程组；`_Daemon.kill()` 用 `os.killpg(pgid, SIGKILL)` 整组清理。

**反向确认**（`docs/probes/20261119-daemon进程清理反向确认.py`，容器内跑，2/2）：
破坏态（只 `proc.kill()`）必留孤儿，修复态 `VERDICT: CLEAN`。

> 探针第一版只输出 `orphans: 1` 就去改 kill，差点修错方向——
> **必须先分辨僵尸(Z)与活进程(S)**：僵尸要补 `wait()`，活进程要改信号投递方式。
> 这是本仓库「先确认信号本身有效」原则的又一例。

### 四、⚠️ 新发现缺陷 3：`reap_idle()` 有实现但没人调

`IDLE_TTL_S=300` 配了、`reap_idle()` 写对了，**服务里没有任何地方调它**。
后果：槽只涨不落，到 `max_slots` 就永远 queue 等下去——因为「TTL 回收腾出名额」
正是 queue 分支的出路之一（见 `pool.py::_wait_then_create` 注释）。

修法：`main.py::_reap_loop` 协程，lifespan 起、关闭时先 cancel 再归档
（避免与关闭归档并发操作同一批槽）。回收循环自己吞异常继续跑——
一次异常让循环退出，槽就再也不回收。

**实测（TTL 设 20s，等 95s）**：

```
INFO sandbox_service.pool: 销毁槽 user=u_ttl（空闲回收（44s））
INFO sandbox_service.main: 空闲回收 1 个槽（现有 0/3）
bwrap 进程数: 0
```

### 五、`InprocExecutor.start()` 返回 None 的坑

`inproc` 的 `start()` 返回 `None`（它没有 daemon 可起）。原来池里写
`if ok:` 判定，`None` 是 falsy ⇒ **off/inproc 模式每次建槽都打一条
「预热失败，退化到一次性模式」的假警告**，日志全是噪音，真问题反而淹了。

修法：池里统一 `_prewarm_ok(result)`，口径是**只有显式 `False` 算失败**，
`None` = "这个执行器不需要预热"。测试 `test_prewarm_none_counts_as_success` 钉死。

## 2026-11-19 修复：归档恢复把用户数据回滚（静默数据损坏）

### 一、症状

用户写的文件被旧归档覆盖，**不报错、不告警**。容器内实测：

```
disk: CURRENT
（放入旧归档）
after 2nd exec: STALE     ← 用户写的 CURRENT 没了
```

### 二、根因：docstring 写了「只一次」，代码里没有守卫

`_maybe_restore` 的 docstring：

> 槽的生命周期内 workspace 是活的文件系统，反复解包会把用户的
> 新改动覆盖掉。所以只在**新建槽**（= 之前被回收/淘汰过）时恢复一次。

而 `exec_code` 里是无条件 `await _maybe_restore(slot)` ——
**没有任何一次性守卫**，于是每执行一次代码就解包一遍。

### 三、为什么一直没被发现（这是最值得记的部分）

归档只在 `_evict` 时写，写的内容恰好等于当时的磁盘内容。
所以「解包回去」和「不动它」结果一样 —— **bug 被巧合掩盖了**。

只有归档比磁盘旧时才暴露。真实触发场景：

- 服务写归档时崩溃（部分写入）
- 将来接对象存储，从远端拉回旧版本
- 人工恢复了一份旧备份

这类 bug 的特征：**它是潜伏的**，不是"某天突然坏"，而是"某天开始坏"。
所以 docstring 的准确性不能替代代码守卫 —— 写对了描述不等于实现了它。

### 四、修法

`Slot` 加字段 `archived_restored: bool = False`，`_maybe_restore` 开头：

```python
if getattr(slot, "archived_restored", False):
    return
slot.archived_restored = True   # 先置位再解包
```

两个细节：

1. **标记挂在 Slot 上，不挂用户上**。槽被回收后再次 acquire 是新对象，
   那时**应该**恢复一次（这期间磁盘可能被动过）。挂用户上会让新槽永远不恢复 ——
   方向相反的同类问题。
2. **先置位再解包**。解包中途失败也不该下次重试：重试只会再失败一遍，
   而且可能把已写入的一部分文件和归档叠在一起。

| --- | --- |
| 新增测试 `test_sandbox_service_restore_once.py` | 6 条，全绿 |
| 反向确认（拆守卫 / 挪置位 / 归档时重置标记） | `docs/probes/20261119-归档恢复一次反向确认.py` **3/3** |
| 全量沙箱测试 | **214 passed** |

### 六、过程中自己写错的一条测试

`test_restore_flag_survives_archiving_on_evict` 第一版：恢复 → 写 CURRENT →
`_archive_slot` → 再恢复，断言仍是 CURRENT。

它在**拆掉守卫的情况下照样绿** —— 因为 `_archive_slot` 把 CURRENT 写进了归档，
再解包回来当然还是 CURRENT。断言与它声称防的事情没有因果关系。

改成直接盯字段（`slot.archived_restored` 必须恒为 True），
反向确认里加一条「归档回调里重置标记」才打得中它。

**教训**：反向确认不只是验证实现，也在验证**测试本身有没有盯住东西**。
这一轮两个 bug 都是反向确认抓出来的（另一个是上一节的
`test_reap_loop_is_started_by_lifespan`）。

## 2026-11-19 修复：strict 模式实际上没有拦截力（安全缺陷）

### 一、实测到的漏洞

`HLZ_SANDBOX_MODE=strict` + 沙箱不可用，代码仍然在 app 进程里执行成功：

```
OUT: [code_run python] exit=0 cwd=/app/backend/data/workspaces/u_strict_leak
file exists? True
```

用户看不到任何提示。**这比 auto 更危险** —— auto 至少会在结果首行标「本次未隔离」。

### 二、两个独立缺陷叠加

#### 缺陷 1：可用性探针探错了对象

`manager._degrade_reason()` 调 `probe.check(cfg)`，而 `probe.py` 里全是
`docker.from_env()`。当前部署是 `HLZ_SANDBOX_BACKEND=service`（HTTP 到独立服务），
根本不会用 Docker —— 探针检查的是一个**永远不会被使用的东西**。

实测两种错法都有（取决于环境，所以更难发现）：

- 容器里没装 docker SDK → 永远判「不可用」→ 每次都误降级
- 本机装了 docker SDK → 永远判「可用」→ 沙箱真挂了也当没事

**修法**：`Backend` 协议加 `health()`，由后端自己回答。
`ServiceBackend.health()` 打 `GET /v1/health`（2 秒超时）；
`InprocBackend.health()` 才用 Docker 探针（那条路确实用 Docker）；
`OffBackend.health()` 恒 True。

#### 缺陷 2：裸 except 把 strict 的异常吞了

`builtin_tools` 里三处沙箱分流（`code_run` / `file_write` / `file_patch`）：

```python
except Exception:  # noqa: BLE001 - 沙箱故障不能打断工具本身
    logger.warning("...回落进程内")
return _impl(...)   # ← 无隔离执行
```

`manager._handle_unavailable` 在 strict 下刻意 `raise SandboxUnavailable`
（意思就是「不许跑」），这个裸 except 把异常接住后照跑不误。

**修法**：新增 `_sandbox_bypass_allowed(tool)`，规则是
「**只有 strict 拒绝回落**」。三处 except 改为：

```python
except Exception as exc:
    if not _sandbox_bypass_allowed("code_run"):
        return f"[sandbox] 沙箱不可用，已按 strict 拒绝执行：{exc}"
    ...
```

注意是**返回失败结果**而不是向上抛：抛异常会打断 agent 循环，
让整个对话崩掉；用户需要的是「这次工具调用失败」这条信息。

### 三、三组真机对照（容器内，service 后端）

判据：**app 的环境变量有没有泄漏进用户代码**（`--clearenv` 是 bwrap 的关键一条）。

| 场景 | 输出 | `HLZ_DB_URL` 可见 | 判定 |
| --- | --- | --- | --- |
| 沙箱正常 + strict | `NET_BLOCKED / ENV_DB: False` | ❌ | **SAFE**（在沙箱里跑，已隔离） |
| 沙箱已停 + strict | `[sandbox] 沙箱不可用，已按 strict 拒绝执行：ConnectTimeout` | ❌ | **SAFE**（代码根本没跑） |
| 沙箱已停 + auto | `[sandbox] 本次未隔离：…` + `ENV_DB: True` | ✅ | **DEGRADED**（符合设计） |

第三组是关键对照：它证明守卫**没有过度收紧** —— auto 仍按设计降级执行。

### 四、探针换过两次判据（都失败了，记下来）

| 版本 | 判据 | 为什么错 |
| --- | --- | --- |
| 一 | 「写文件有没有成功」 | 容器内 `/ws` 不存在，代码抛 `FileNotFoundError`，什么也没写 → 看起来像 strict 拦住了，实际是代码跑失败 |
| 二 | 「网络是否 BLOCKED」 | **app 容器本身也没有外网**，两种执行环境网络状态一样，区分不出来 |
| 三 | 「app 环境变量有没有泄漏」 | ✅ 沙箱有 `--clearenv`，app 进程内继承环境 → 这是隔离生效的直接证据 |

这是「假信号」的又一例：判定前必须先确认**这个信号本身能不能区分两种情形**。

## 0. 结论

**Hlaudz 现在不需要做工具延迟披露，但需要在 MCP 工具变多时自动切换。**

实测数据（本机，2026-11-11）：

| 对象 | 工具数 | schema 字节 | 约 token |
| --- | --- | --- | --- |
| Hlaudz root（内置 6 + 编排 5 + team 8） | 19 | 8,731 | ≈ 2,200–2,900 |
| GA（`assets/tools_schema.json`） | 34 | 33,500 | ≈ 11,000 |
| CC 319 | 20+ 内置 + 任意 MCP | 未固定 | 可达 50K+ |

Hlaudz 的固定工具面只有 8.7 KB，**连 GA 的三分之一都不到**，全量注入完全合理。
真正的变量是**用户挂的 MCP server**——一个 sqlbot_mcp 就有 12 个工具，
挂三个就接近 GA 的量级。

## 1. 三个概念先分清

| 机制 | 延迟的是什么 | 谁有 |
| --- | --- | --- |
| **Skill 渐进式披露** | skill 正文（L1 索引常驻 → `load_skill` 取 L2 → 引用文件 L3） | CC、GA、**Hlaudz 已有** |
| **工具延迟披露（ToolSearch）** | tool schema（`shouldDefer: true` 的工具不进系统提示，模型检索后加载） | CC |
| **MCP 懒连接** | server 连接与工具列表（连接慢时不阻塞首轮） | CC、GA |

用户说的「CC 的延迟披露 / GA 最近刚加上」，需要区分：
**GA 11-10 加的「渐进式披露」是第一种（skill 层）**，
GA 的 `tools_schema.json` 仍是 34 个工具全量注入，**没有 `tool_search` 工具**
（本次已用 `git log` 与 schema 解析双重核实）。

所以本轮的判断对象只有第二、三种。

## 2. CC 319 的机制（复刻要点）

### 2.1 声明式：`shouldDefer`

每个工具可以带 `shouldDefer: true`，表示默认不进系统提示。
源码里 WebFetch、NotebookEdit 等标 `true`，Glob 等标 `false`（常驻）。
**关键：延迟与否是逐工具声明的，不是全局开关。**

### 2.2 模式判定：`efe()`

```
强制 standard（不 defer） → 环境变量 ENABLE_TOOL_SEARCH:
  "auto:N"  → 工具数超过 N% 预算时开始 defer
  "auto:0"  → 全 defer
  "auto:100"→ 全常驻
  "true"    → 全 defer
  "false"   → 全常驻
  未设置    → 默认 defer
另有 GRr()：只有 firstParty API 才默认 defer（第三方网关/Bedrock 不 defer）
```

### 2.3 检索语法与 `searchHint`

- `select:Read,Edit,Grep` —— 精确点名，一次可加载多个；
- 关键词检索、`+必须含` 语法；
- 每个工具有独立的 `searchHint`（短、面向检索），不拿完整 description 做索引；
- 提示词强调「**每个 ToolSearch 调用浪费一整个往返**，要批量加载」。

### 2.4 成本

每次 `ToolSearch` 是一次完整 LLM 往返。因此延迟披露的收益门槛是：
**省下的 schema token > 多花的往返成本**。工具少时这是负收益。

## 5. 决策

### 5.1 现在不做工具延迟披露

理由：

1. 8.7 KB 固定工具面 ≈ 2.2–2.9K token，延迟省不下多少；
2. 每次 `ToolSearch` 是一次完整往返，工具少时是**负收益**；
3. Hlaudz 的编排/team 工具是「当前阶段才注入」的（子代理没有），
   天然已经按角色裁剪过一轮；
4. 引入 `tool_search` 会让提示词多一条纪律，模型的选择负担变重。

### 5.2 但要预置「MCP 膨胀时的自动切换」

当 MCP 工具变多时，走与 CC 同构但更简单的方案：

| 规则 | 值 |
| --- | --- |
| 常驻 | 全部内置 + 编排 + team（19 个） |
| 可延迟 | **只有 MCP 工具**（`mcp__*`） |
| 触发阈值 | MCP schema 累计 > **20,000 字节** 或 MCP 工具数 > **24** |
| 低于阈值 | 与现在完全一致（全量注入，零变化） |
| 高于阈值 | 注入 `tool_search`，MCP 工具改为按需加载 |
| 检索语法 | 只支持 `select:a,b,c` 与关键词，不实现 `+必须含` |
| searchHint | 用 MCP 工具描述的前 80 字符，不额外维护 |

**为什么 MCP-only**：MCP 工具是唯一不可控的输入源；
内置工具是高频且 schema 小，把 `file_read` 也延迟会让模型每次都得先搜一次。

### 5.3 开关

```
HLZ_TOOL_DEFERRAL=auto      # 默认：按阈值自动
HLZ_TOOL_DEFERRAL=off       # 强制全量
HLZ_TOOL_DEFERRAL=on        # 强制延迟所有 MCP 工具
```

## 6. 实现要点（当阈值触发时才需要）

1. `ToolRegistry` 增加「deferred」集合；`schemas()` 只返回常驻 + 已加载；
2. `build_turn_runtime` 计算 MCP schema 字节，决定是否注入 `tool_search`；
3. `tool_search` 命中后把工具加入**本 generation 的已加载集合**（不跨回合，
   避免上下文里出现「模型记得加载过但其实没加载」）；
4. 已加载集合要写进 `summary.json` / 调试日志，便于复盘；
5. 子代理默认**继承父代理的已加载集合**，但不超过自身工具面。

## 8. 何时重新评估

出现以下任一情况就再评估：

1. 固定工具面超过 **30 个** 或 schema 超过 **20 KB**；
2. 默认 MCP 配置的工具 schema 超过 **20 KB**（本机 sqlbot 单个约 8–12 KB，还差得远）；
3. 上游上下文窗口被压到 64K 以下；
4. 实测发现「工具太多导致选错」的比例上升。

## 9. 顺带核实：skill 渐进式披露的差距

用户提到「GA 最近刚加上」，GA 11-10 那轮加的是**skill 层**。
Hlaudz 已经有 skill L1/L2，但参数落后于 GA 三处优化：

| 项 | Hlaudz | GA（优化后） | 影响 |
| --- | --- | --- | --- |
| 索引预算 | 8,000（`skill_store.py:514`） | 16,384 | 技能多时描述被挤掉 |
| 单条描述上限 | 250（`skill_store.py:501`） | 1,536 | 描述被截成半句 |
| 预算不足时的降级 | 保留 `- name`（已实现） | 保留**触发器句** | 只知道名字，无法判断相关性 |
| 压缩时是否保留索引 | 未核实 | 压缩时保留触发器句 | 压缩后模型想不起 skill |

这三条成本极低（改两个常量 + 一个截断策略），**建议随 P1 一起做**。

---

## 10. 一句话总结

- **工具延迟披露**：Hlaudz 现在不做（8.7 KB，收益为负），但把阈值与 MCP-only 方案写死，
  超过就自动切换；
- **skill 渐进式披露**：Hlaudz 已有，但预算和描述上限需要对齐 GA；
- GA 的「最近加上」是 skill 层，不是 tool_search——两者不能混为一谈。

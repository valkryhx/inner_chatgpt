
# 多租户 Agent 工具执行与 Sandbox 隔离架构方案

## 一、建设目标

当前 Agent Server 运行在 Docker 容器中，多个用户共用同一套 Agent 服务。

Agent 具有较高权限，能够调用文件读写、Python Code Run、Shell、HTTP 请求等工具。如果这些工具直接在 Agent Server 容器或宿主机环境中执行，就可能产生以下问题：

1. 用户 A 的 Agent 可能读取或修改用户 B 的文件。
2. 用户提交的代码可能访问其他用户的数据。
3. 恶意代码可能访问 Agent Server 的环境变量、内部服务或宿主机资源。
4. 单纯通过用户目录、工作目录或 Prompt 约束，无法形成真正的安全隔离。

因此，需要将工具执行环境与 Agent 服务分离，实现多租户隔离。

核心目标：

- Agent Server 多用户共享。
- 每个用户拥有独立的 Sandbox 容器。
- 文件读写、代码执行等高权限操作全部进入用户自己的 Sandbox。
- 用户身份由服务端认证，不允许 LLM 自行指定用户身份。
- 容器之间不能访问彼此的文件、进程和运行环境。
- 用户数据独立持久化，容器销毁或重建不影响数据。

## 二、总体架构

采用五个核心组成部分：

1. Agent Server：负责 Agent 运行、LLM 调用和工具编排。
2. Tool Router：负责工具调用路由，将不同工具分发给对应执行服务。
3. Sandbox Manager：负责用户身份验证、Sandbox 生命周期管理和工具调用转发。
4. User Sandbox：每个用户独立运行的 Linux 容器，负责实际执行工具。
5. MinIO：负责用户工作区的数据持久化、备份和同步。

整体架构：

```text
                  用户浏览器
                      |
                      v
              +---------------+
              |  Agent Server |
              |               |
              | 用户会话管理   |
              | LLM / Agent   |
              | Tool Calling  |
              +---------------+
                      |
                      v
              +---------------+
              |  Tool Router  |
              |               |
              | 工具分类与路由 |
              +---------------+
                      |
          +-----------+------------+
          |           |            |
          v           v            v
      Sandbox API  HTTP Service  DB Service
          |
          v
    +------------------+
    | Sandbox Manager  |
    |                  |
    | 身份认证         |
    | 权限校验         |
    | 容器映射         |
    | 生命周期管理     |
    | 执行结果返回     |
    +------------------+
          |
          v
    +---------------------------+
    |       Docker Engine       |
    +---------------------------+
          |
     +----+----------+----------+
     |               |          |
     v               v          v
 +---------+     +---------+  +---------+
 | User A  |     | User B  |  | User C  |
 | Sandbox |     | Sandbox |  | Sandbox |
 |         |     |         |  |         |
 | Python  |     | Python  |  | Python  |
 | Shell   |     | Shell   |  | Shell   |
 | Files   |     | Files   |  | Files   |
 |         |     |         |  |         |
 |/workspace|    |/workspace| |/workspace|
 +---------+     +---------+  +---------+
     |               |          |
     +---------------+----------+
                     |
                     v
                  MinIO
               用户数据持久化
```

注意：Sandbox Manager 是唯一能够管理 Docker 容器的组件。Agent Server 不直接持有 Docker Socket。

## 三、Agent Server：保留原有 Agent 能力

Agent Server 不需要重写整个 Agent 框架。

继续负责：

- 用户会话管理。
- LLM 请求和响应。
- Agent 思考与循环。
- Tool Calling。
- 工具参数解析。
- 工具结果返回给 LLM。
- 多轮对话上下文管理。

主要变化是：原本直接在 Agent Server 本地执行的工具，改成通过 API 调用外部执行服务。

例如原来：

```python
result = subprocess.run(
    ["python", "-c", code],
    capture_output=True
)
```

改造后：

```python
result = sandbox_client.execute(
    tool="python_execute",
    arguments={
        "code": code
    }
)
```

这里的 `sandbox_client` 通过内部 HTTP/RPC 接口与 Sandbox Manager 通信。

Agent 仍然使用原来的 Tool Calling 机制，只是底层执行方式发生了变化。

## 四、Tool Router：统一工具执行入口

建议将 Agent 的工具按执行环境分类。

| 工具类型     | 示例                                           | 执行位置                     |
| ------------ | ---------------------------------------------- | ---------------------------- |
| 文件操作     | read_file、write_file、list_files、delete_file | 用户 Sandbox                 |
| 代码执行     | python_execute、code_run                       | 用户 Sandbox                 |
| 命令执行     | shell_execute                                  | 用户 Sandbox                 |
| HTTP 请求    | http_get、http_post                            | 受控 HTTP 服务或用户 Sandbox |
| 数据库操作   | database_query                                 | 数据库服务                   |
| 网络搜索     | web_search                                     | 搜索服务                     |
| 其他业务工具 | MCP 工具、内部业务 API                         | 对应业务服务                 |

这里有一个原则：

**凡是需要操作用户工作区、执行用户代码或接触用户运行环境的工具，都应该进入用户自己的 Sandbox。**

HTTP 工具则需要根据用途决定执行位置：

- 如果是用户代码发起的 HTTP 请求，可以在 Sandbox 内执行。
- 如果是访问公司内部业务 API，应通过受控服务代理，并进行目标地址和权限校验。
- 如果是公共搜索服务，可以直接调用独立的搜索服务。

不能简单地把所有 HTTP 请求都放开，否则用户可能通过 SSRF 访问内网管理接口、云平台元数据服务等。

## 五、Sandbox Manager：多租户隔离的核心

Sandbox Manager 是整个方案中最重要的基础设施组件。

它主要负责五件事：

### 5.1 用户身份验证

用户登录 Agent Server 后，Agent Server 从可信的登录会话中获得用户身份。

例如：

```python
current_user = authenticated_session.user
```

当 Agent 需要执行工具时，Agent Server 使用经过授权的短期 Token 调用 Sandbox Manager。

Token 应包含或绑定：

- 用户身份。
- 允许访问的 Sandbox。
- 允许执行的操作范围。
- 有效期。
- 必要时绑定会话或任务 ID。

Sandbox Manager 验证 Token 后，才能确定操作对应的用户。

特别注意：

不能让 LLM 自己传入 `user_id`，也不能相信模型提供的 `container_id`。

用户身份必须来自可信认证上下文，而不是模型生成的工具参数。

### 5.2 用户与容器映射

Sandbox Manager 内部维护用户与容器之间的映射关系。

例如：

| 用户 ID | Sandbox ID | 容器 ID     | 状态    |
| ------- | ---------- | ----------- | ------- |
| user_A  | sandbox_A  | container_A | Running |
| user_B  | sandbox_B  | container_B | Running |
| user_C  | sandbox_C  | container_C | Stopped |

可以使用 PostgreSQL 保存元数据：

```text
sandbox_registry

id
user_id
sandbox_id
container_id
image_version
status
created_at
last_active_at
```

其中 user_id 应设置唯一约束，确保一个用户对应一个长期 Sandbox（如果后续支持多工作区，则改成 user_id + workspace_id）。

### 5.3 工具调用转发

Sandbox Manager 接收到请求后：

1. 验证用户身份。
2. 检查用户是否有权执行该工具。
3. 查询用户对应的 Sandbox。
4. 检查容器是否运行。
5. 将工具命令转发到对应容器。
6. 获取执行结果。
7. 返回 Agent Server。

例如：

```text
execute(user_A, python_execute, arguments)
```

实际执行：

```text
Sandbox Manager
       |
       | 查找 user_A
       v
   Container A
       |
       | 执行 Python
       v
   返回执行结果
```

### 5.4 Sandbox 生命周期管理

Sandbox Manager 负责：

- 创建用户容器。
- 启动用户容器。
- 停止用户容器。
- 销毁用户容器。
- 容器异常恢复。
- 资源限制。
- 容器镜像版本管理。

建议采用长期容器模式，不要每次 Tool Call 都创建一个新容器。

可以设置空闲超时时间：

```text
用户首次使用
    |
    v
创建 Sandbox
    |
    v
持续执行工具调用
    |
    v
空闲达到阈值
    |
    v
停止容器
    |
    v
用户再次使用
    |
    v
重新启动容器
```

用户数据保存在宿主机挂载目录或 MinIO 中，不依赖容器本身的可写层。

### 5.5 执行日志和资源管理

建议记录：

- 用户 ID。
- Sandbox ID。
- 工具名称。
- 执行时间。
- 执行耗时。
- 返回状态。
- CPU、内存使用情况。
- 超时或异常信息。

不要默认记录所有敏感文件内容和环境变量。

## 六、User Sandbox：每用户独立 Linux 环境

每个用户运行一个独立 Docker 容器。

建议使用预制的 Alpine Linux + Python 镜像。

容器内提供：

```text
/workspace
    |
    +-- project.py
    +-- data.csv
    +-- requirements.txt
    +-- output/
```

可以在容器内启动一个轻量级 Sandbox Worker，接收 Sandbox Manager 转发的工具命令。

例如：

```text
Sandbox Manager
       |
       | HTTP / RPC
       v
Sandbox Worker
       |
       +-- read_file
       +-- write_file
       +-- list_files
       +-- delete_file
       +-- python_execute
       +-- shell_execute
```

这样，文件操作和 Code Run 都在同一个用户环境中完成。

不需要再额外建立一套文件读写服务。

### 容器挂载方式

宿主机目录：

```text
/data/agent-workspaces/
    |
    +-- user_A/
    |
    +-- user_B/
    |
    +-- user_C/
```

创建用户 A 的容器时：

```bash
docker run -d \
  --name sandbox-user-a \
  --memory=2g \
  --cpus=2 \
  --pids-limit=128 \
  --network=none \
  --read-only \
  --security-opt=no-new-privileges \
  --cap-drop=ALL \
  --mount type=bind,src=/data/agent-workspaces/user_A,dst=/workspace \
  sandbox-python:latest
```

实际部署还需要配置非 root 用户、`/tmp` 等必要的临时可写目录，以及容器内 Worker 的通信方式。

用户 B 则挂载自己的目录：

```bash
--mount type=bind,src=/data/agent-workspaces/user_B,dst=/workspace
```

关键在于：

**不要将整个 `/data/agent-workspaces` 父目录挂载到用户容器中。**

每个容器只能挂载对应用户的目录。

Alpine 只是基础镜像，真正的隔离来自容器命名空间、权限、挂载边界和资源限制。对于运行不可信代码的场景，可以进一步评估 gVisor 或 Firecracker。

## 七、文件持久化：MinIO + 用户工作区

建议 MinIO 作为持久化存储，而不是直接让 Agent 操作 MinIO。

整体关系：

```text
                MinIO
                  |
           数据同步 / 备份
                  |
                  v
          Host Workspace
                  |
            Bind Mount
                  |
                  v
            User Sandbox
                  |
                  v
          文件读写 / Code Run
```

例如：

```text
MinIO Bucket
    |
    +-- user_A/
    |
    +-- user_B/
    |
    +-- user_C/
```

用户工作时：

1. 从 MinIO 加载用户工作区。
2. Sandbox 在 `/workspace` 中读写文件。
3. 定期或任务结束时同步数据到 MinIO。
4. 容器停止或重建后，从持久化数据恢复工作区。

建议通过受控同步服务完成 MinIO 同步，不要把 MinIO 管理员密钥放进 Sandbox。

如果需要 Sandbox 直接访问 MinIO，只能给它该用户专属、权限受限的凭证。

## 八、Docker Socket 安全设计

这是一个非常重要的边界。

Agent Server 本身也是 Docker 容器，但不应该挂载：

```text
/var/run/docker.sock
```

原因是 Docker Socket 几乎等同于宿主机管理权限。

如果 Agent Server 被攻击，攻击者就可能通过 Docker API 创建拥有宿主机目录挂载权限的容器，绕过原有隔离。

因此：

```text
Linux Host
    |
    +-- Docker Engine
    |
    +-- Sandbox Manager
    |       |
    |       +-- Docker Socket
    |
    +-- Agent Server Container
    |       |
    |       +-- Sandbox Manager API
    |
    +-- User Sandbox Containers
```

只有 Sandbox Manager 能访问 Docker Engine。

Agent Server 只能通过受限 API 请求 Sandbox Manager 执行预定义操作。

Sandbox Manager 也不能开放任意 Docker API 给 Agent Server。

例如只允许：

- 创建指定镜像的用户容器。
- 启动指定用户的容器。
- 停止指定用户的容器。
- 执行指定用户容器中的工具。
- 查询指定用户容器的状态。

不允许调用方任意指定宿主机挂载路径、镜像、特权模式和 Docker 参数。

## 九、网络安全设计

建议分开考虑 Sandbox 的网络权限。

### 默认环境

普通 Python 和文件操作不需要网络时：

```text
Sandbox Network = none
```

如果用户确实需要 HTTP 请求，可以通过受控网络代理提供访问能力。

例如：

```text
User Sandbox
     |
     v
HTTP Proxy
     |
     +-- 允许访问公网 API
     |
     +-- 拒绝访问宿主机
     |
     +-- 拒绝访问其他用户容器
     |
     +-- 拒绝访问云平台元数据地址
     |
     +-- 限制内部网络访问
```

不要因为需要访问 MinIO，就直接开放 Sandbox 到整个内网的网络访问权限。

网络代理需要限制目标域名和 IP，处理 DNS 解析及重绑定等问题。

## 十、一次完整工具调用流程

以用户 A 要求 Agent 读取文件并执行 Python 为例：

```text
1. 用户 A 登录
       |
       v
2. Agent Server 验证登录会话
       |
       v
3. LLM 决定调用 read_file
       |
       v
4. Agent Server 调用 Sandbox Manager API
       |
       v
5. Sandbox Manager 验证用户 A 的授权 Token
       |
       v
6. 查询 user_A 对应的 Sandbox
       |
       v
7. 找到 container_A
       |
       v
8. Sandbox Worker 执行 read_file
       |
       v
9. 返回文件内容
       |
       v
10. Agent Server 将结果交给 LLM
       |
       v
11. LLM 决定调用 python_execute
       |
       v
12. 继续在 container_A 中执行
       |
       v
13. 执行结果返回 Agent
```

整个过程中，Agent Server 不直接接触用户工作区文件，也不在自己的环境中执行用户代码。

## 十一、建议的技术选型

| 模块            | 推荐技术                       |
| --------------- | ------------------------------ |
| Agent Server    | 保留现有技术栈                 |
| Tool Router     | Python / TypeScript            |
| Sandbox Manager | Python FastAPI 或 Go           |
| 容器管理        | Docker Engine API / Docker SDK |
| 用户 Sandbox    | Alpine Linux + Python          |
| Sandbox Worker  | Python HTTP / RPC 服务         |
| 用户身份        | 现有 OIDC / JWT 认证体系       |
| Sandbox 元数据  | PostgreSQL                     |
| 文件持久化      | MinIO                          |
| 容器监控        | Docker Stats + Prometheus      |
| 日志            | 结构化日志                     |
| 更强隔离        | gVisor / Firecracker           |

## 十二、实施步骤

建议分阶段改造，不需要一次性重写全部 Agent。

### 第一阶段：完成基础 Sandbox

1. 构建 Alpine + Python 镜像。
2. 编写 Sandbox Worker。
3. 实现文件读写、Python 执行和 Shell 执行。
4. 实现每用户独立容器。
5. 实现宿主机独立工作目录挂载。

### 第二阶段：建设 Sandbox Manager

1. 实现用户与容器映射。
2. 实现容器创建、启动和停止。
3. 实现身份认证和授权。
4. 实现工具调用转发。
5. 实现资源限制和操作日志。

### 第三阶段：改造 Agent 工具层

1. 将原有文件工具改成 Sandbox API 调用。
2. 将 Code Run 改成 Sandbox API 调用。
3. 将 Shell 工具改成 Sandbox API 调用。
4. 对 HTTP、数据库和 MCP 工具进行分类路由。
5. 保持原有 Tool Calling 定义和参数格式，尽量减少 Agent 业务代码改动。

### 第四阶段：持久化和网络安全

1. 接入 MinIO。
2. 实现用户工作区同步和恢复。
3. 实现 HTTP 代理和网络访问控制。
4. 完成容器资源监控。
5. 增加异常恢复和审计机制。

### 第五阶段：安全测试

重点测试：

- 用户 A 能否读取用户 B 的文件。
- 用户 A 能否访问用户 B 的容器。
- 是否能通过 Shell 逃逸访问宿主机。
- 是否能访问 Docker Socket。
- 是否能通过 HTTP 请求访问内网敏感服务。
- 容器停止、重启后用户数据是否完整。
- Agent Server 被攻破后，是否能够直接控制 Docker Engine。

## 十三、最终架构原则

整个方案可以归纳为四句话：

1. **Agent 共享，Sandbox 独立。** 所有用户可以共用一套 Agent Server，但每个用户拥有自己的 Linux 执行环境。
2. **工具服务化，执行环境隔离。** Agent 通过 Tool Calling 发出命令，后端 API 负责将命令转发到正确的执行环境。
3. **身份决定路由，操作系统保证隔离。** 用户身份不能由 LLM 指定，容器挂载和权限边界负责阻止跨用户访问。
4. **数据独立持久化，容器可以随时重建。** 工作区数据与容器生命周期解耦。

最终实现的效果是：用户仍然像使用 Claude Code 或 Codex 一样使用 Agent，但每个人背后实际上都有一套独立的 Linux 工作环境。


## **我对这套方案的两个额外建议**

**第一，不要把 Sandbox Manager 做成一个通用 Docker API 转发器。**

它应该是一个受限的多租户执行服务。Agent 只能调用 `<span>python_execute</span>`、`<span>read_file</span>` 等预定义操作，不能接触 Docker 的底层管理能力。

**第二，长期来看可以把 Sandbox Worker 抽象成统一的工具执行协议。**

以后即使从 Docker 迁移到 gVisor、Firecracker，甚至 Kubernetes，每个用户的工具调用接口也不需要变化。只需要更换底层 Sandbox Provider。

这意味着你真正建设的不是一个 Docker 管理器，而是一个可替换执行后端的 **Multi-tenant Agent Tool Runtime（多租户 Agent 工具运行时）**。

## A.1 一句话结论：本方案的骨架是对的，只需三处校准

**"每用户独立容器"这个结论成立，且不可退让。** 依据不是"CC 没做所以不能做"，而是威胁模型：

> 工具里有 **Python Code Run 和 Shell**，执行的是**不可信的用户代码**。
> 裸 `runc` 与宿主**共享内核** —— 一次容器逃逸就是**全租户沦陷**，比跨用户读文件严重一个量级。

| 必需能力 | 为什么必需 | 裸 runc | gVisor | CC 的 bwrap / Seatbelt |
| --- | --- | --- | --- | --- |
| **独立内核攻击面** | 用户代码可能带内核 exploit | ❌ 共享宿主内核 | ✅ 用户态内核 | ❌ 共享宿主内核 |
| **uid / user ns 真正切换** | 跨租户文件权限边界 | ✅ | ✅ | ❌ `--unshare-user` 不带 `--uid` |
| **cgroup 资源上限** | 一条死循环拖垮全机器 | ✅ | ✅ | ❌ 全模块 0 处命中 |
| **独立 rootfs** | 不共享宿主 inode | ✅ | ✅ | ❌ `--ro-bind / /` 复用宿主根 |
| **独立 netns** | 跨租户网络不可达 | ✅ | ✅ | ✅（唯一对等的一项） |

**CC 那套沙箱不是"更轻的容器"，是另一个维度**：隔离单位是**一条命令一次 fork+exec**，
起点是毫秒级、无镜像、无 init。它解决的是「**同一用户，别让 agent 把机器搞坏**」，
**不是**「用户 A 别碰用户 B」。把它当容器替代品是错的；把它叠在容器里做第二层是对的（见 A.6）。

## A.2 校准一：运行时选型要把 gVisor 写进技术选型表

原方案 §11 把"更强隔离"列为 `gVisor / Firecracker`，属于"以后再说"。建议**提前到默认项**：

| 选项 | 隔离强度 | 运维成本 | 何时选 |
| --- | --- | --- | --- |
| **gVisor（`--runtime=runsc`）** | 高（用户态内核） | **架构改动低**（换个 runtime 名），**运行开销高于 runc** | **首选**，前提是宿主 Linux 且接受性能代价 |
| Firecracker / microVM | 最高（硬件虚拟化） | 中（自己管 VM 生命周期） | 强合规要求、高密部署 |
| 加固后的 runc | 中 | 低 | **只在"用户是信任的同事"时**够用 |

**两个必须说清的限定**，否则会误判：

1. **gVisor 只能在 Linux 宿主上跑**，没有 Windows 原生版本。
   本方案画的是 `Linux Host` + `Docker Engine`，**生产不受影响**；只影响本地开发（见 A.5）。
2. **gVisor 不比 Docker 轻，比 Docker 默认的 `runc` 重。** 它不是 Docker 的替代品，
   而是 Docker 的一个 OCI runtime（和 `runc` 平级）。多一个用户态内核进程（Sentry + Gofer），
   每次 syscall 被拦截再转发：启动更慢、常驻内存更多、**syscall 密集的 workload 明显变慢**。
   换来的是内核隔离——**这正是跑不可信代码时真正需要的那一项，值得。**

> 具体慢多少不给数字。谁给你"gVisor 只慢 5%"的通用结论都别信，它高度依赖 syscall 密度，
> 必须在同一台机器、同一份 workload 上压测。

**部署前两个会静默退化到最慢路径的坑**：

| 坑 | 症状 | 怎么办 |
| --- | --- | --- |
| `runsc` 的 **KVM platform 要 `/dev/kvm`** | 跑在 VM 里又没开嵌套虚拟化 → 退到 **ptrace platform**，性能差距进一步拉大 | 宿主开嵌套虚拟化并暴露 `/dev/kvm`；用 `runsc --platform=kvm` 验证 |
| **不实现全部 syscall** | 某些 ioctl / `/proc` 读取 / GPU 调用直接失败 | Python + shell 一般没问题；以后加 GPU 或特殊调用，先验证再上 |

## A.3 校准二：§4 工具路由表要补一条"文件工具自己也要过路径判定"

原方案 §4 把文件操作、代码执行、命令执行都归到"用户 Sandbox 执行"，方向对。但有个坑：

**CC 的沙箱只包 Bash / PowerShell 两条命令通道，Read / Write / Edit / Glob / Grep 都不走沙箱**，
它们靠**权限系统**（permission rules）单独管。两条线互补：沙箱管"命令里能碰到什么"，权限管"工具调用本身批不批"。

所以在本方案里：

- 如果你只把"文件工具"实现成"在容器里 open/read/write"，**它天然受容器边界保护，没问题**；
- 但如果你照抄 CC 的 sandbox 配置（`allowWrite` / `denyRead`）去约束它，**那是空的**——
  这些配置只对 bwrap 包住的命令生效，对进程内的文件 API 调用无效。

**结论**：文件工具必须在 Sandbox Worker 内**自己做路径校验**（规范化 + 前缀匹配 + 拒 `..` + 拒符号链接越界），
不能指望沙箱层的 `denyRead` 替你挡。

## A.4 校准三：§9 网络安全可以比"给个代理"细得多

原方案 §9 的思路（默认 `network=none` + 受控 HTTP 代理 + 拒内网/元数据地址）是对的。
CC 的实现提供了一个**更细且可直接复用的判定次序**，建议照抄这个顺序：

```
1. deniedDomains 命中           → 拒
2. strictAllowlist 开启         → 直接拒（不在 allowlist 一律拒，不再询问）
3. allowedDomains 命中          → 放
4. 该命令自己的临时白名单命中    → 放   ← 注意：排在第 5 步
5. 都不中                       → 交给用户/策略询问，答非布尔按拒绝处理
```

**最关键的是第 4 步的位置**：模型的"临时开口"能力（CC 里是 Bash 工具的 `allowed_domains` 参数，
上限 100 条、每条 260 字符）**只能排在 deny 和 strict 之后**，
所以它**只能收紧、不能突破**管理员策略。

> **这一条对多租户是硬要求。** 如果你的方案要给模型类似的"这条命令临时需要访问某域名"能力，
> 务必保证"临时放宽"在判定链的**最后**，否则模型一句"我需要访问 internal-admin.corp"
> 就把整个白名单绕过去了。

配套细节也值得抄：被挡住的响应带固定标记（CC 用 `blocked-by-sandbox-runtime`），
并且把"哪一条被挡、为什么"以**结构化块**（CC 的 `<sandbox_violations>`）回给模型——
让"被挡了"变成可解释反馈，而不是用户看到莫名失败。

## A.5 平台事实：Windows 上这些都不成立

**如果你的团队在 Windows 上开发，有三条必须先知道：**

1. **gVisor 没有 Windows 版**，`runsc` 不能当 Windows 容器 runtime。
   - 本地开发用 **WSL2 里独立安装 Docker + runsc**。注意：**Docker Desktop 自带的 daemon 加不了自定义 runtime**，
     必须用 distro 内独立安装的 engine。
   - 或本地用普通 runc 开发，隔离验证放 Linux CI / 预发。
2. **bwrap（bubblewrap）在 Windows 上跑不了。** 它依赖的原语全是 Linux 内核专有的
   （`--unshare-user/-pid/-net` 要对 namespace、`--cap-drop` 要对 POSIX capability、
   `--ro-bind/--bind/--tmpfs` 要对 mount namespace、`--die-with-parent` 要对 `PR_SET_PDEATHSIG`），
   **Windows 一个都没有**。CC 源码里也没有任何 Windows 版 bwrap。
3. **一个容易误会的点**：在 Windows 上用 Claude Code 能跑 Bash，**不代表它的沙箱在 Windows 上能用**。
   实测（`claude sandbox status`）本机 CC 的 Windows 沙箱是 **关闭**状态
   （`"enabled":false, "installed":false`），`sandbox.enabled` 默认就是 `false`——
   **命令是直接跑在宿主上的**。CC 在 Windows 走的是完全另一套 `srt-win.exe`
   （专用账户 + ACL + WFP 过滤器 + 一次 UAC 安装），且还挂在特性开关后面。

**对本方案的影响**：生产是 Linux Host，不受影响；**但别把 bwrap 当成 Windows 侧的方案**，
也别把"本地 Windows 能跑 CC"当成"生产边界已验证"。

## A.6 可选项：容器内再叠一层（不是隔离需求，是防误伤 + 体验）

容器已经解决了跨用户与资源边界。CC 这套在**容器内**仍有价值的，按性价比只有三样：

| 优先级 | 抄什么 | 解决什么 | CC 坐标 |
| --- | --- | --- | --- |
| 1 | `--unshare-net` + 域名白名单代理 + 上述判定次序 | 容器内再挡一次 SSRF / 内网扫描 / 云 metadata | `m0302:36402`（判定函数） |
| 2 | **凭据 mask**：给命令一个**等长假值**，出网时由代理换回真值 | token 进日志 / 进公网 | `m0302:31842`（`fake_value_` 哨兵） |
| 3 | **结构化违规上报**（`<sandbox_violations>`） | 让"被挡了"可解释 | `m0302:37495` |

**建议不要做的**：不要在容器里再套 bwrap 的**挂载遮罩**那套（`--ro-bind / /` + `--tmpfs` 挖洞 + `--ro-bind` 回填）。
理由：你的容器 rootfs 已经隔离，这层收益很小、复杂度很高（CC 为此写了大量边界处理，含符号链接替换攻击、
denyWrite 覆盖 allowWrite 时回填只读、JSON 参数超长改走 fd 等）。

## A.7 三个明确"不要照抄"的地方

1. **`enableWeakerNestedSandbox`**（CC 里为"非特权 Docker 容器里跑不了 /proc 挂载"准备的后门）。
   它会**保留宿主 `/proc` 可读**。你在容器里部署可能正好撞上这个需求，**但它削弱隔离**——
   宁可给容器足够的 user namespace 权限，也不要用这个开关。
2. **`dangerouslyDisableSandbox` 这个参数本身**。CC 里它是**模型可以传的**，靠
   `allowUnsandboxedCommands` / strict mode / 权限提示来兜底。
   **本方案的铁律是"用户身份与执行边界不能由模型决定"——这个参数是直接的反例，绝不能有。**
   （CC 自己也知道有问题，所以有个 strict mode 能把它彻底关死。）
3. **`--ro-bind / /` 复用宿主 rootfs**。单用户机器上很聪明（省镜像、启动快），
   多租户上**不可接受**：安全性全押在"遮罩表算得对"，而遮罩表的输入（home / cwd）**隐含只有一个用户**——
   共享容器里 A 的遮罩不会包含 B 的目录，B 的目录会**以只读方式暴露给 A**。
   **这也是"一个沙箱 for all users"明确不安全的直接机制证据。**

## A.8 对 §12 实施步骤的两条增量建议

在现有五阶段之上，加两条（都不改变骨架，只加一道纵深）：

- **第一阶段补一句**：镜像基线选 `gVisor 兼容`（跑 `runsc` 的最小验证：Python 起进程、pip install、
  `/proc` 读取、fork/exec）。**越早验证越便宜**，别等到第三阶段才发现某个依赖 syscall 不支持。
- **第三阶段之后加一个可选阶段**：**容器内 per-command 收口**（A.6 那三样，按性价比 1→2→3）。
  验收标准不是"装上了"，而是：
  1. 容器内 `curl` 到一个不在白名单的公网域名 → 被拒，且模型能用 `<sandbox_violations>` 说出被拒的 host；
  2. 把某个凭据写进环境变量 → 命令 `env` 看到的是等长假值，代理出网时换回真值；
  3. **反向确认**：把收口代码 stash 掉，上述 1、2 必须重新失败（否则这个验收是假的）。

## A.9 与本方案的差异汇总（一页对照）

| 本方案要点 | CC 的做法 | 结论 |
| --- | --- | --- |
| Agent Server 多用户共享 | 无此概念（单用户进程） | — 本方案的分层是对的 |
| 每用户独立容器 | 反向：一条命令一个沙箱 | ❌ 不适用；容器层照旧 |
| 文件工具全部进沙箱 | 只有 Bash 进，Read/Write 走权限系统 | ⚠️ 必须自己补路径校验（A.3） |
| 身份由服务端定，LLM 不能指定 | 沙箱完全不管身份；`dangerouslyDisableSandbox` 模型可传 | ✅ 本方案对；且要引以为戒（A.7-2） |
| 容器间不能互访 | Linux 下 uid 不变 ⇒ 挡不住 | ❌ CC 不能替代容器 |
| 数据持久化与容器解耦 | 沙箱用宿主 inode，天然不持久 | — |
| Docker Socket 只在 Manager | CC 里根本没有 Docker Socket | — |
| 网络默认 none + 受控代理 | `--unshare-net` + socat + 域名白名单 + 六步判定 | ✅ **强推荐照抄**（A.4） |
| 资源限制（CPU/内存/pids） | **完全没有** | ❌ 只能靠容器（A.1） |
| 结构化审计日志 | `<sandbox_violations>` + 遥测事件 | ✅ 推荐（A.6-3） |
| Sandbox Worker 统一协议 | `wrapWithSandbox` / `wrapWithSandboxArgv` 二选一 | ✅ 接口设计可抄 |

**最后一句**：本方案的"Agent 共享，Sandbox 独立 / 身份决定路由，操作系统保证隔离"是对的，
CC 源码从这个方向给出了反证——**它的沙箱之所以敢"一条命令一个、随便起"，是因为它默认整个进程只有一个人用**。
一旦拿去服务多用户，它挡不住跨用户读取。所以：**容器层（gVisor）负责跨用户与资源，CC 那套作为容器内的第二层收口。**

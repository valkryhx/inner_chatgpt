# 沙箱镜像的测试 target（2026-11-19）

> 方案：`docs/20261119-沙箱服务化方案-bwrap版.md`
> 代码：`backend/sandbox_service/Dockerfile`
> 测试：`backend/tests/test_sandbox_image_targets.py`（9 条静态断言）

## 1. 问题：8 条测试在任何环境都不会执行

`backend/tests/test_bwrap_daemon.py` 里有 **8 条 `requires_bwrap`** 测试
（现为 8 条真 daemon 用例 + 1 条进程组静态断言）：

- **Windows 开发机**：没有 `bwrap` → 全部 `skip`
- **生产沙箱镜像**：按设计**不带 pytest**（生产容器不跑测试，
  而且它能执行不可信代码，不该因此多装依赖）

于是这些测试实际上**一条都没跑过**。而它们覆盖的恰恰是 Windows 上
根本测不到的部分：进程组清理、PID namespace、bwrap 的 fork 内层进程。

这不是假设——本仓库真踩到过：`_Daemon.kill()` 只杀外层 bwrap，
内层被 init 收养继续活着（`prctl --as=2GB` 还压着），
日志照常打「daemon 已停」，只有数进程才发现（见 §4）。

## 2. 方案：多阶段构建里的独立 target

```
base        服务本体（= 生产镜像的全部能力）
test        base + pytest
production  空 stage，只引用 base；**必须是文件里最后一个**
```

### 为什么 production 必须最后

`docker build` 与 `docker compose build` 在**不指定 `--target`** 时构建
**最后一个** stage。

如果 `test` 放在最后，那么一次普通的 `docker compose build sandbox`
就会把 pytest 打进生产镜像。这个错误特别难发现：

- 构建日志完全正常
- 服务能起、隔离生效、多租户安全
- 唯一差别是 `pip list` 里多一行 pytest

所以顺序不能靠人记得，由
`test_production_is_last_stage` 静态钉死。

### 为什么 test 基于 base 而不是重来

从 `python:3.12-slim` 重装全部依赖会：① 构建多几分钟
② 装出来的版本可能和生产不一致 —— 那样测的就不是生产实际跑的东西了。

## 3. 怎么用

### 构建

```bash
# 测试镜像
docker build -f backend/sandbox_service/Dockerfile \
             --target test -t hlz-sandbox-test:latest .

# 生产镜像（不指定 --target 也一样，因为 production 是最后一个 stage）
docker build -f backend/sandbox_service/Dockerfile \
             -t hlz-sandbox-svc:latest .
```

### 跑测试

```bash
docker run --rm --user 1000:1000 \
  -v "$PWD/backend/tests:/app/tests:ro" \
  hlz-sandbox-test:latest \
  python -m pytest /app/tests/test_bwrap_daemon.py -q
```

实测结果：**17 passed**（对比 Windows 上的 9 passed + 8 skipped）。

⚠️ **必须 `--user 1000:1000`**。镜像默认 USER 是 `sandbox`(1000)，
但若用 `--user root`，`RLIMIT_NPROC` 会静默失效（实测 root 下起满 60 个进程
才拦、uid 1000 拦在第 18 个）——那时测出来的隔离结论是**假的**。

⚠️ **测试文件挂载进去，不 COPY 进镜像**。`.dockerignore` 已排除
`backend/tests/`，而且镜像要能拿去跑用户代码，不该带测试。

### 验收脚本

```bash
python docs/probes/20261119-镜像stage反向确认.py      # 3/3：stage 结构
python docs/probes/20261119-镜像内测试反向确认.py     # 2/2：真 daemon 测试有效性
```

第二个脚本做两件事，**两件都必须成立**：

1. 正常代码下测试**绿**（说明断言找得到进程，不是空过）
2. 拆掉 `killpg` 后测试**红**（说明它真在盯这条线）

第 1 条不能省：一个「永远找不到进程、于是 `left == []` 恒成立」的测试
会永远绿，对孤儿毫无感知。

## 4. 过程中抓到的两个真问题

### 4.1 bwrap 内层进程变孤儿（bug，已修）

探针实测（`docs/probes/20261119-daemon进程清理探针.py`）：

```
daemon pid(bwrap)=386
执行后: [386(ppid=380, S), 387(ppid=386, S)]      ← 两层！
destroy 返回，proc.returncode=-9
销毁后: [387(ppid=1, stat=S)]                     ← 内层被 init 收养
VERDICT: LEAK（有活进程）
```

**根因**：bwrap 会 fork 内层进程。`proc.kill()` 只对最外层发 SIGKILL，
而 SIGKILL 不可捕获 —— 外层死了没机会转发，内层被 init 收养继续跑。

**修法**（两处成对）：`start_new_session=True` 让 daemon 独占进程组
+ `os.killpg(pgid, SIGKILL)` 整组清理。

### 4.2 测试自己假红：`ps` 的 args 列会截断（测试 bug，已修）

第一版 `pids_for()` 用 `ps -eo pid=,args=` 做子串匹配，在 pytest 里**假红**：
`args` 列按输出宽度截断（实测截到约 80 字符），
`--bind <path> /ws` 在命令行尾部直接被切掉，于是报
「预热成功但找不到 bwrap 进程」。

**更麻烦的是它取决于调用环境**：容器里直接跑不截断、pytest 里截断 ——
同一断言在两种环境下结论不同，是典型假信号。

**修法**：读 `/proc/<pid>/cmdline`（内核里的原始 argv，NUL 分隔，没有宽度概念），
按 **argv 数组**比对（不能做子串匹配，子串里带空格永远匹配不上）。

## 5. 边界

- **不覆盖** `test_sandbox_service_wiring.py` 的接线断言（那些不需要 bwrap，
  Windows 上就能跑，也已经有反向确认）
- **不替代** `docs/probes/20261119-daemon进程清理探针.py`：探针输出
  `VERDICT: CLEAN / ZOMBIE / LEAK` 的分级诊断，比测试的 pass/fail 更适合排查。
  两者是「诊断」和「守门」的分工。
- 生产 `docker compose build` 行为**完全不变**（production 是最后一个 stage）

## 6. 这一轮的失误模式

| 失误 | 为什么会发生 | 怎么防 |
| --- | --- | --- |
| `ps -eo args=` 做子串匹配 | 不知道 args 列会随输出宽度截断 | 内核数据用 `/proc/<pid>/cmdline`，别解析 `ps` 文本 |
| `/proc/cmdline` 也用子串匹配 | 忘了它是 NUL 分隔，`--bind path /ws` 中间是 `\0` | 按 argv 数组逐项比对 |
| 破坏版反向确认靠手搓 | 手动跑一次就丢，下次没人复现 | 固化成 `docs/probes/20261119-镜像内测试反向确认.py` |

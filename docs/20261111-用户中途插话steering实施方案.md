# 用户中途插话（steering）：实施方案

> 日期：2026-11-11　状态：**P0 已实施并真机验证**
> 前置：`docs/20261111-Hlaudz-用户中途输入与wait异步化.md`（wait_agent 异步化已完成，
> 下半部分的 queued prompt 方案**至今未实施**）

## 1. 结论先说：你想的不是「wait_agent 阻塞」，是「用户消息没有入口」

你的观察是对的，但归因需要修正一处，否则会改错地方。

### 1.1 `wait_agent` 其实已经异步化了

提交 `140a6ba`（2026-11-10）已把它改过：

| | 改前 | 现在 |
|---|---|---|
| 默认条件 | `all_terminal`（必须等完） | `any_event`（等到第一个实质进展就返回） |
| 返回 | 只有 `timed_out` | 三态 `state`：`event` / `all_terminal` / `timeout` / `ready` |
| 实质进展 | — | `tool_start` / `tool_result` / `message_injected`（文本增量不算） |

`wait_agent` 的 `timeout_seconds` 默认 60，会返回 `state=timeout` 并明确标注
「这不是失败」。所以它**不是黑洞**了。

### 1.2 你那次实测里的真正现象

从 `msg_672c8bc406ac` 的块序列看（你刚才那次测试）：

```
spawn_teammate(counter) → wait_agent(timeout=120) → wait_agent(all_terminal, timeout=180)
  → [任务通知注入] → read_agent_result → ...
```

模型连续调了 **两次 `wait_agent`**，第二次还**显式传了 `condition=all_terminal`**。
这是模型自己的选择（它想一次等完），不是平台强制。异步化给了它选择权，
但它这次选了同步等 —— 这属于「模型偏好」，不是「平台阻塞」。

**你真正卡住的不是 wait_agent，是下面这两个硬拦截**：

| 层 | 现象 | 代码位置 |
|---|---|---|
| 前端 | 流式期间输入框 `disabled`，按 Enter 什么都不会发生 | `Composer.tsx:194` `disabled={streaming}`；`App.tsx:434` `if (... \|\| streaming) return` |
| 后端 | 第二条消息直接 `409 generation_active`，hint 写着「请先点击停止」 | `routers/chat.py:755` |

所以哪怕 `wait_agent` 立刻返回、母代理闲在那里，你也**没法把新 prompt 递进去**。
这才是和 CC / GA 的差距所在。

### 1.3 有没有「几天前的改动」把 steering 弄坏了

没有。查过全部提交：`steer_queue.py` 从未存在，`mode:"queue"`、`queued_turn_count`
等在代码里零命中。`140a6ba` 只做了 wait 异步化，queued prompt 那部分是**设计完整、
从未实施**。所以这是「漏做」，不是「退化」。

### 1.4 一个需要你知道的既有能力

`send_message` 工具（lead → 队友）和 `message_injector`（fold 注入点）**都已经存在**，
而且 `AgentLoop.message_injector` 每轮模型调用前都会被执行。
**缺的不是注入点，是「用户消息能写进那条队列」的通道。**

## 2. 对标：CC 319 与 GenericAgent 怎么做

### 2.1 CC 2.1.319

CC **不能**把新输入追加进已发出的 HTTP 请求。它做的是**命令队列**，在三个时机消费：

| 时机 | 行为 |
|---|---|
| 轮内 fold | 每个工具批次结束后，把 `priority=next` 的用户消息作为 `queued_command` 插进同一回合 |
| 轮末 | 当前回合结束，drain 队头开下一回合 |
| `priority=now` | 立刻 abort 当前回合，让这条消息马上开始 |

值得抄的：单一全局队列、三档优先级（`now`/`next`/`later`）、**模型看到的是包装过的
user 文本而非队列结构**、Esc 清队列、上箭头把排队消息拉回输入框、结果带 `queued_turn_count`。

### 2.2 GenericAgent

只做最小闭环，三处代码：

| 位置 | 作用 |
|---|---|
| `core/pending_input.py` | `PendingPromptQueue`：线程安全、`drain()` 原子、**故意跨回合存活** |
| `core/loop.py:_consume_queued_prompts` | 「工具批次之后、下一次 `chat()` 之前」把队列渲染成块注入 |
| `frontends/ink/bridge.py:480-515` | 回合在跑就 `queue.push()` 并 emit `prompt_queued`；回合已结束则提升为普通 submit |

GA 注释里点出的三个坑，Hlaudz 会原样踩到：

1. **队列不能挂在回合上**：「a message that arrives after the last fold point of turn N
   must survive into turn N+1, which is exactly the case a per-turn buffer gets wrong」。
2. **drain 必须原子**：UI 线程 push、回合线程 drain，读-清两步会丢中间到达的消息。
3. **注入文本必须能区分**：否则模型会重新回答原来那个问题。

### 2.3 Hlaudz 的形态差异（决定实现方式）

| | CC / GA | Hlaudz |
|---|---|---|
| 进程形态 | CLI/Ink，单进程内存队列 | FastAPI + 每请求一个 SSE 流 |
| 「忙碌」判定 | 进程内 `is_running` | DB 租约 + 进程内 `is_generation_live` |
| 第二条消息 | 入队 | **409** |
| 前端 | 自己就是进程 | 独立 SPA，`streaming` 时禁用输入框 |
| 注入点 | 已有 fold 点 | **已有**：`AgentLoop.message_injector` |

**结论：注入点不用新建；要新建的是「活着能写进去的队列」+「一个不返回 409 的入口」
+「让前端在流式期间可输入」。**

## 3. 实施方案

### 3.1 总体结构

```
前端 Composer（streaming 时可输入）
   │  POST /api/sessions/{sid}/messages  {text, mode:"queue"}
   ▼
routers/chat.py  ── is_generation_live? ──是──► steer_queue.push() → 202 {queued:true, depth:n}
   │                                           │
   │ 否（竞态：刚好结束）                        │
   └──► 降级为普通发送（返回流式响应）             │
                                                ▼
                        AgentLoop.message_injector（已有 fold 点，每轮模型调用前）
                                                │
                                    ┌───────────┴───────────┐
                                    ▼                       ▼
                            steer_queue.drain()     host.drain_notifications()
                            （用户消息，优先）        （子代理通知）
```

### 3.2 P0：最小闭环（本次实施范围）

#### (a) `backend/app/steer_queue.py`（新）

```python
class SteerQueue:
    """活着的 generation 才能写进去的用户插话队列。

    刻意挂在「进程内 generation 注册表」上而不是 TurnRuntime 上：
    回合结束前最后一条消息可能晚于最后一个 fold 点到达，必须跨回合存活
    （GA 的坑 1）。挂在 runtime 上会让它随回合一起消失。
    """
    def push(self, item) -> int       # 返回队列深度
    def drain(self, limit=5) -> list  # 原子：取走即清（GA 的坑 2）
    def snapshot(self) -> list        # 给 UI 回显，不消费
    def clear(self) -> int            # 用户停止/取消时清空
```

存放：模块级 `dict[(user_id, session_id, generation_id)] -> SteerQueue`，
挂在 `runtime.py` 的 generation 注册表旁边，`acquire`/`register` 时创建、
`unregister_generation` 时**延迟清理**（保留到下一次 drain 或超时 60s，
避免「回合刚结束、消息还在队列里」被丢掉）。

**并发安全**：两个写入方（HTTP handler 的线程/协程、SSE 生成器）都在同一个
事件循环里，`drain` 用「列表整体替换」而不是「for + pop」，天然原子。

#### (b) 后端入口 `POST /api/sessions/{sid}/messages`

新增 `SendMessageIn.mode: Literal["send","queue"] = "send"`：

- 请求前先看 `active = get_active_generation(...)`；
- `active` 且 `is_generation_live(...)` 且 `mode == "queue"` → **不抢租约**，
  `queue.push()`，返回 `202 {"queued": true, "queue_depth": n, "generation_id": active}`；
- `active` 但已不 live（陈旧租约）→ 走现有的自愈逻辑；
- 没有 active → 正常发送（`mode` 被忽略，避免前端多余判断）。

**权限与配额**：排队消息不消耗 generation 配额（它没有开新回合），但要限长
（`MAX_STEER_CHARS = 4000`）与限深（`MAX_QUEUE_DEPTH = 20`），超限返回 429。

#### (c) 组合注入器（`subagent/session.py`）

现有：

```python
async def _drain():
    injected = [...consume_inbox...]
    injected.extend(host.drain_notifications())
    return injected
```

改为**用户消息优先**：

```python
async def _drain():
    injected = []
    # 用户新指令优先于系统通知：用户的话是本轮要处理的新要求，
    # 通知是已经发生的事实，先给模型看指令更符合「边跑边改需求」的直觉。
    for item in steer_queue.drain():
        injected.append({"role": "user", "content": _wrap_user_steer(item["text"])})
    injected += [...consume_inbox...]
    injected.extend(host.drain_notifications())
    return injected
```

**包装文案**（照抄 CC，避免模型重新回答原问题）：

```text
[用户在你执行过程中补充的消息]
<原文>

这是用户在上一轮执行过程中补充的要求，请在本回合内一并处理，
不要当成一个新的对话回合，也不要重新回答最开始的问题。
```

非 team 场景（没有 `build_turn_runtime`）同样需要生效，所以在
`run_agent_stream` / 基础 runtime 路径上也接一次 —— 见 §3.3。

#### (d) 事件回显

| 事件 | 方向 | 内容 |
|---|---|---|
| `steer_queued` | 后端 → 前端（202 响应体，不是 SSE） | `{queued, queue_depth}` |
| `message_injected` | **已有**，复用 | 注入时推 `{"type":"message_injected","text":...}` |

复用 `message_injected` 的好处：前端已有处理逻辑（渲染成 `injected_message` 块，
可持久化），不用新加协议。`agent_loop` 在注入时已经 emit 了它。

#### (e) 前端

1. `Composer.tsx`：`disabled={streaming}` → 只在 `uploading` 时禁用；placeholder 改成
   「输入消息…（生成中发送会插入当前任务）」。
2. `App.tsx` `send()`：`streaming` 时不再 `return`，改为：

   ```ts
   if (streaming) { await queueSteer(text, attachments); return }
   ```

   `queueSteer` POST `{text, mode:"queue"}`，成功后：
   - 本地插入一条 `status: 'queued'` 的用户消息（灰显 + 「已插入」角标）；
   - 不新建 assistant 消息、不动 `abortRef`；
   - 收到 `message_injected` 且文本匹配时，把 `queued` 转成 `complete`。
3. `MessageList.tsx`：`status === 'queued'` 渲染成带角标的气泡。

### 3.3 非 team 路径也要生效

`run_agent_stream` 的普通路径（`turn is None`，没有 team）同样要接队列，
否则「没用 team 的普通对话」不能插话 —— 那是绝大多数使用场景。

实现：在 `sse.run_agent_stream` 里给 `ur.loop` 装一个**幂等的注入器组合**：

```python
def _install_steer_injector(loop, user_id, session_id, generation_id):
    if getattr(loop, "message_injector", None) is not None:
        return  # team 路径已经装过（它内部会 drain 用户队列）
    loop.message_injector = lambda: _drain_steer_only(user_id, session_id, generation_id)
```

注意：team 路径的注入器**已经**会 drain 用户队列（P0(c)），所以这里不能重复装，
否则同一条消息会被注入两次。用一个显式标记 `loop._steer_aware = True` 来判定。

### 3.4 P1（本次不做，写清楚边界）

| 能力 | 说明 |
|---|---|
| `priority: "now"` | 立即中止当前回合、这条消息开新回合。要走已有的 `request_stop` 链路，且 `stopped` 状态要带「因用户插话」的原因 |
| 队列可编辑 | 上箭头把排队消息拉回输入框；需要 `DELETE /messages/queue/{id}` |
| Esc 清队列 | 停止时清空人类排队消息、保留系统通知 |
| 持久化 | 落 `session_steer_queue` 表，刷新不丢 |

### 3.5 明确不做

- **把新内容追加进已发出的 HTTP 请求**：协议层做不到，CC 也没做；
- **让 `wait_agent` 变成「可被用户消息立即打断」**：`wait` 的语义是「等子代理」，
  它现在最长 60s 就会带着 `state=timeout` 返回，母代理自然会到 fold 点。
  强行让用户消息打断 `wait` 会引入「工具执行到一半被取消」的一致性风险，
  收益不抵成本。真正需要「立刻」的是 P1 的 `priority:"now"`，走停止链路才对。

## 4. 实施步骤（TDD）

| 步 | 内容 | 测试先写 |
|---|---|---|
| 1 | `SteerQueue`：push/drain/snapshot/clear、原子性、限深限长 | 并发 push 时 drain 不丢；超限拒绝 |
| 2 | 注册表挂载与延迟清理 | `register` 后能拿到队列；`unregister` 后仍可 drain 一次，超时后回收 |
| 3 | HTTP `mode:"queue"` | live → 202 且不进 SSE；非 live → 降级普通发送；超限 429 |
| 4 | 组合注入器顺序 | 用户消息在子代理通知之前；同一条不会被注入两次 |
| 5 | 非 team 路径注入 | 普通对话也能收到插话 |
| 6 | 前端 | `npm run build`；Playwright 截图确认流式期间能输入、有「已插入」角标 |

## 5. 验收（必须真实 LLM 跑）

| # | 场景 | 判据 |
|---|---|---|
| 1 | 长任务（sleep 60 的子代理）执行中投递第二个问题 | **同一次生成**内被读到并回应 |

> 第 2 条是关键判据：如果出现了第二个 generation，说明只是把 409 换成了串行排队，

## 6. 风险

| 风险 | 缓解 |
|---|---|
| 同一条消息被注入两次（team + 非 team 两个注入器都装） | 显式 `_steer_aware` 标记，只装一次；测试断言注入次数 == 1 |
| 队列随回合消失，最后一条消息丢失 | 队列挂在 generation 注册表、延迟清理；GA 坑 1 的针对性测试 |
| drain 读-清两步丢消息 | `drain` 用整体替换实现；并发 push 测试 |
| 模型把插话当成新问题重答 | 包装文案明确「不要重新回答最开始的问题」；e2e 判据里检查是否重答 |
| 排队消息无限堆积 | 限长 4000 字符、限深 20；超限 429 |

### 8.3 真机验证（runId `145738-1fee`，真实湛卢）

场景：派一个 sleep 40s 的 teammate，**流式过程中**投递第二个问题。

| 判据 | 结果 |
|---|---|
| 插话返回 | `202 {"queued": true, "queue_depth": 1}` |
| **generation 数量 = 1** | **通过**（关键判据：没有另起一轮） |
| 插话被注入 | 1 条，含完整包装文案 |
| 用户的问题被回答 | 「1+1 等于 2」出现在同一轮答复里 |
| 总耗时 | 94.7s（含 slowpoke 的 40s） |

最终答复里模型自己把插话排在前面回答，然后接着汇报原任务 —— 说明包装文案
「不要当成新的对话回合、不要重新回答最开始的问题」起了作用。

### 8.4 一个被真机顺带暴露的既有问题（不在本次范围）

slowpoke 的 `file_*` 工具沙箱根是 `backend/data/workspaces/<uid>`（空目录），
看不到仓库里的 `backend/app`；lead 只能在 message 里写路径，绕不过沙箱。
这不是 steering 的缺陷，但会影响「派 teammate 去读仓库」这类任务的可行性，
值得单独评估（要么把仓库暴露进 workspace，要么给一个只读入口）。

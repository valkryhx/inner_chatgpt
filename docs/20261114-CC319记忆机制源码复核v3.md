### 1.1 【高】`MEMORY.md` 进的**不是** system prompt，默认是 `instructions` attachment

**v2 原文**（§3.2、§3.3.1）：

> 即最终进 system 的那段是 `Contents of <path> (user's auto-memory, persists across conversations):`
> ……**所以「`MEMORY.md` 每次会话都进系统提示词」这条论断的证据是完整的**

**实测**：文本渲染函数（`Z$n`/`WQe`）没错，但**投递通道 v2 认错了**。

`m0591:71183-71187` 产出的 `blocks.claudeMd` 只是 `X9o()` 的**返回值之一**；它要经过渲染模式选择
才决定去处。真正分叉在 `m0848_0x124d7ee6.js:1227-1228`：

```js
let E = SUo(s.messages) ?? gm(s.messages);
if (E === "inline") return gl(S);        // ← 只有这条才把 claudeMd 留在 userContext
```

- `SUo`（`:1181`）= `n0n() ? cD(e)?.contextRendering : void 0`；`gm`（`:1189`）= `n0n() && L6t(e) !== void 0 ? "announced" : void 0`。

**逐分支穷举**：只有三种可能，都不利于 v2 的说法——

| `n0n()` | `contextRendering` | `E` | 结果 |
|---|---|---|---|
| false | — | `undefined`（`SUo` 与 `gm` 都返回 void） | **不是 `"inline"` → 走 announced** |
| true | `"inline"` | `"inline"` | `gl(S)`，claudeMd 留在 `userContext` |
| true | 其它 / 未设 | `gm` 给 `"announced"`（若 `L6t(e)` 有值）否则 `undefined` | **走 announced** |

即 **announced 是默认**，`inline` 需要一个显式的 `contextRendering === "inline"` 才成立。
（`gl()`（`:1197`）就是 inline 分支：保留 `claudeMd`、置 `bare: !0`、`rendering: "inline"`。）

- announced 分支（`:1249-1286`）把 `claudeMd` 从 `userContext` 里**删掉**，转成 `instructions` 列表：

```js
if (I.claudeMd !== void 0 && T !== void 0) {
  instructions = lhi(T);
  ...
  delete I.claudeMd;                       // ← 不再作为 system 段
}
```

- 然后作为 attachment 发出（`:1446-1456`）：

```js
let T = Wr(n.instructions, announcementWalk);
if (T && !(S && A)) {
  let re = dhi(T, A);
  if (re) { let Y = createRecord({ type: "instructions", ...re }, stamp); E.push({...}) }
}
```

- 渲染（`m0591:229034` → `kAt`，`:10977`）：

```js
instructions: (e) => { ... let r = kAt(n.data); ... return vu([Ie({ content: r, isMeta: !0 })]) }
// kAt: if (!e.changed) return WQe(e.files);   ← 同一个 WQe，同一段文字
```

**结论**：`MEMORY.md` 的**内容**每次会话确实进上下文（这条 v2 对），但它以
`instructions` attachment（`isMeta` 消息）的形式进，**标题仍是**
`Contents of <path> (user's auto-memory, persists across conversations):`。
只有 `rendering === "inline"` 时才是 v2 说的"进 system prompt / `blocks.claudeMd`"。

**为什么要改**：这直接决定 Hlaudz 的实现位置。若照 v2 去做"塞进 system prompt 的 claudeMd 段"，
在 CC 的默认形态下是**错的通道**——CC 选择 attachment 是因为它能在 `changed` 时只补发差异
（`kAt` 的 `e.changed` 分支发"这些指令文件变了，每条替换之前的副本"），而 system prompt 每次
全量重发会打掉 prompt cache。Hlaudz 若要做记忆索引注入，应优先落到既有的
`message_injector`/attachment 通道（AGENTS.md 已记录的 `agent_loop.py` 注入器），而不是 system prompt。

**v2 应改为**：「`MEMORY.md` 每次会话都进**上下文**；通道是 `instructions` attachment
（announced 渲染），`inline` 渲染下才进 system prompt 的 `blocks.claudeMd`。两种通道共用
`WQe`/`Z$n` 渲染，文本一致。」

### 1.3 【高】`Gee = 25000` 的单位是 **UTF-16 code unit**，不是字节

**v2 原文**（§0 表、§3.3、§13.1）：`200 行 / 25 KB`、`Gee = 25000 字节`、`先按 200 行切，再按 25000 字节回退到最后一个换行`。

**实测**（`m0194_0x11642aa3.js:15-23`）：

```js
function z2e(t) {
  let trimmed = t.trim();
  return { trimmed, lineCount: Dt(trimmed, "\n") + 1, byteCount: trimmed.length };  // ← .length 不是 Buffer.byteLength
}
```

`LEr()`（`m0293:4448`）用的是 `byteCount > Gee` 和 `w.length > Gee`，都是 JS 字符串长度，
即 **UTF-16 code unit 数**。源码自己把它命名成 `byteCount`，这个名字是误导，v2 照抄了它。

**为什么要改**：`byteCount` 是源码里**起错的名字**，而代码自己给的提示语说的是"字符"——
`LEr` 的超限文案（`m0293:4478`）：

```js
N = S === 0 ? `everything after the first ${w.length} characters of line 1 was cut off`
            : `${lineCount - S} of ${lineCount} lines were cut off, ...`
```

**面向用户的字符串说 `characters`，不是 `bytes`。** 按方法论 §1 的旁证优先级，这条属于
"提示词原文"级证据，可靠度高于 v2 据以判断的变量名。

```js
let Ce = await X0e(e, 0, W2e, Ibe, n, { truncateOnByteLimit: !0 });   // W2e=200 行 / Ibe=4096 字节
...
let Re = Y + ... + Buffer.byteLength(Ce);                            // ← 这里用 byteLength
if (Re > Ibe) { ke = !0; break }
```

**影响**：对中文记忆文件，25000 code unit ≈ 25000 个汉字（UTF-8 下 3 字节/字 ≈ 75 KB），
而不是 25 KB。若 Hlaudz 按"25 KB 字节"实现截断，**中文索引会在约 1/3 处被截**，与 CC 行为明显不同。
同时要注意 CC 内部两种口径并存：索引 cap 用 code unit，单文件召回 cap 用真字节。

**应改为**：「索引 cap = 200 行 / **25,000 个 UTF-16 code unit**（源码变量名 `byteCount` 但取的是
`.length`）；单文件召回 cap = 200 行 / **4,096 字节**（`Ibe`，用 `Buffer.byteLength` 计）。两个 cap 单位不同。」

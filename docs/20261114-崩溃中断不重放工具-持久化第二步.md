> 日期：2026-11-14　状态：**已完成**
> 前序：`docs/20261114-A2A中断现场-持久化第一步.md`（第一步：可观测）

---

## 0. 问题：`sanitize()` 在崩溃后会**真的重新执行**那个工具

`agent_loop.sanitize()` 修悬空 tool_call 有两种方式：

1. 把不完整的 assistant+tool 块删掉；
2. 如果缺结果的是**尾部**且工具名可解析，**真的 dispatch 一次**
   （`agent_loop.py:270-281`）：

```python
if not has_later_non_tool and can_replay:
    for tc in msg.get("tool_calls") or []:
        ...
        out = await self.registry.dispatch(name, args)   # ← 真的执行
```

方式 2 在「用户点停止」时是对的：那一轮用户主动打断，工具几乎肯定没跑完，
重放等于替用户把这一步补上。

**但进程崩溃时它是有害的**：那个 `code_run` 可能已经执行了 ——
写了半截文件、发了一条消息、调了一次外部接口。重放 = 重复副作用，
而且这些工具没有幂等保证。

而崩溃后我们**原理上无法确定**它执行到哪一步。所以唯一诚实的做法不是猜，
而是：**记下「这是崩溃」，修历史时补一条明确的「执行状态未知」让模型先核对。**

## 1. 实现

### 1.1 崩溃标记表（`backend/app/turn_marker.py`）

```sql
CREATE TABLE IF NOT EXISTS turn_crash_markers (
    session_id  TEXT PRIMARY KEY,
    last_tool   TEXT NOT NULL DEFAULT '',
    steps       INTEGER NOT NULL DEFAULT 0,
    marked_at   INTEGER NOT NULL
);
```

**必须落库**：标记的存在意义就是跨进程存活。放内存的话进程一死标记就没了，
等于没做。

标记的语义必须精确：**它只代表「上一进程没有走完这一轮就死了」**，
不代表「上一轮失败了」。失败是任务自己的状态，不需要特殊处理。

### 1.2 顺序：必须先标记，后收敛（这里踩过一次真 bug）

启动时 `db.init_db()` 里有一条既有的自愈：

```sql
UPDATE messages SET status='stopped' WHERE role='assistant' AND status='streaming'
```

**这条 UPDATE 会抹掉「这一轮没走完」的唯一证据。** 第一版我把标记逻辑写在
`main.py` 里、`db.init_db()` 之后调 —— 真机验证时标记永远是 0 条。

修法：把标记夹在那条 UPDATE **之前**，放在 `init_db` 内部：

```python
try:
    await _mark_crashed_before_converge(conn)   # ← 先标记
except Exception:
    logger.warning("崩溃标记建立失败", exc_info=True)
await conn.execute(
    "UPDATE messages SET status='stopped' WHERE role='assistant' AND status='streaming'"
)                                               # ← 后收敛
```

对应测试 `test_startup_marks_crashed_before_converging` 断言的是**源码里的顺序**，
不是「某个函数被调用」—— 因为后者在顺序写反时照样能通过。

### 1.3 `sanitize()` 的崩溃分支

```python
if self._crash_context is not None:
    for tc in msg.get("tool_calls") or []:
        ...
        history.append({
            "role": "tool", "tool_call_id": tid, "name": name,
            "content": _describe_unknown_tool_result(name),   # ← 不 dispatch
        })
    continue
```

补进去的结果文案（两处保持一致：`turn_marker.describe_unknown_result` 与
`agent_loop._describe_unknown_tool_result`，核心循环不 import 持久化模块）：

```text
[执行状态未知] code_run 在上一轮被进程中断，无法确定是否已执行完成。
它**可能已经产生了实际影响**（文件写入、命令执行、外部调用）。
重试前请先核对结果（例如读取目标文件、查看命令产物）；若已生效，不要再执行一次。
```

**刻意不标成 `is_error`**：它不是工具的失败，是观测的缺失。模型看到「错误」
会倾向重试，看到「未知」才会先去看一眼产物。

### 1.4 谁写、谁清

| 时机 | 动作 |
|---|---|
| 进程启动、`streaming` 收敛之前 | 有 streaming 消息的会话 → `mark_crashed` |
| 一轮走到正常出口（`complete` 或用户 `stopped`） | `clear_crash_marker` |
| 异常 / 进程死 | 走不到清标记，标记保留（正是要的） |

**「用户停止」也算正常出口**：那是显式动作，下一轮重放工具是安全的。
标记只代表「没走完就死了」。

### 2.2 L3 真机（`work/_probe_crash_resume.py`）

流程：让模型用 `code_run` 执行「sleep 45 秒后写哨兵文件」→ 中途 Kill 后端进程 →
重启 → 同一会话再发一句「先检查文件在不在，再告诉我该不该重做」。

结果 **6/6**：

| 检查 | 实测 |
|---|---|
| 重启后崩溃标记存在 | ✅ `co_b1a8c7acecc6` |
| 续轮工具序列 | `['file_glob', 'list_files', 'file_read']` ← **全是核对** |
| 先核对（有读取类工具） | ✅ |
| 未直接重跑 `code_run` | ✅ |
| 回答提到未知/中断/核对 | ✅「上一轮其实已经执行完成，不需要重做」 |
| 哨兵文件 | 存在、内容 `第一行`、**只有 1 行** |

**最后一条是最强证据**：文件没被重复写。如果发生重放，`code_run` 会再执行
一次写文件命令，内容就会翻倍。

### 2.3 两个必须记下来的调试教训

**① 探针的第一版把「崩溃」做成了「用户停止」**

我原本在探针里 `t.cancel()` 掉 SSE 连接。结果 `chat.py` 的 finally 把消息
收敛成 `stopped` —— 在库里和「用户主动停止」长得一模一样，重启时就再也
分不出崩溃了。

真实崩溃的形态是：**客户端还在等，服务端进程突然没了**。所以探针必须
保持连接开着，由外部命令杀服务端。

**② 顺序 bug 只有真机能发现**

单测里 `test_startup_marks_crashed_sessions` 当时断言「main.py 调了
`mark_all_unfinished_crashed`」—— 它是绿的。但真机上标记永远是 0，
因为标记跑在收敛之后。**「函数被调用了」和「在正确的时机被调用」是两件事。**

修正后的测试断言源码里的**位置关系**（`index(a) < index(b)`），
并补了一条端到端测试。

## 3. 还没做的

| 项 | 说明 |
|---|---|
| **真正的「续跑」** | 本步只做到「不重放 + 让模型自己核对」。真正的自动续跑（从第 N 步接着执行）还没做 —— 需要更细的 per-call 状态，而不只是「这一轮崩了」 |
| per-call 粒度 | 现在标记是会话级的（「这一轮崩了」），不知道该轮里**多个** tool_call 中具体哪个悬空。当前实现是按缺失的 id 逐个补「未知」，够用，但没法精确到「第 2 个调用其实已完成」 |
| SSE 断线续传 | 第三步，未开工 |
| 标记的 TTL | 目前标记会一直留到下一轮正常结束。如果会话再也不用了，标记会常驻（单条几十字节，可忽略；但没有清理） |

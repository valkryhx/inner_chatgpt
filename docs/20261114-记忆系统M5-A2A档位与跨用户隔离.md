## 0. 一句话结论

M5 名义上是「A2A 档位 + 跨用户 e2e」，实施时**抓到一个真实的越权缺陷**：

> **`read_only` / `chat_only` 的 A2A token 仍然会触发后台记忆写入。**

`tool_policy` 的保证是「运行期靠 registry 里没有该工具兜底」。但记忆有**四个**
进出点，只有第一个走 registry：

| 通道 | 走 registry？ | `tool_policy` 管得到？ |
|---|---|---|
| ① 模型调 `memory_list` / `memory_read` / `memory_write` | ✅ | ✅ |
| ② 读侧注入（`MemoryInjector` / 选择器预取） | ❌ | ❌ ← 本次补 |
| ③ 写侧后台提取（`AgentLoop.on_turn_end`） | ❌ | ❌ ← **本次抓到的缺陷** |
| ④ dream 巡检合并 | 服务端维护任务，与 token 无关 | — |

③ 尤其严重：它写入的内容会在**下一个会话**里被当成用户事实注入，
是一次用户看不见的持久副作用。这正是「只读」二字要禁止的事。

## 1. 三档的记忆语义（严格包含的阶梯）

先定语义再写代码。三档必须逐档收窄，否则「阶梯」不成立：

| 档位 | 工具面 | 记忆读 | 记忆写 | 理由 |
|---|---|---|---|---|
| `full` | 全部 | ✅ | ✅ | 与网页端完全一致 |
| `read_only` | `file_read` / `list_files` / `load_skill` / `memory_list` / `memory_read` | ✅ | ❌ | 「看得到的都看得到，但什么都别动」 |
| `chat_only` | 无 | ❌ | ❌ | 「什么都不碰」。文案是「不注入任何工具」，把记忆也算进来才自洽 |

**两个判断需要单独解释**：

**为什么 `read_only` 保留记忆读？** 记忆的读边界是 `user_id`，token 已经把它绑死了，
读**自己用户**的记忆不构成越权。掐掉它只会让 read_only 变成一个「不记得用户是谁」的
残缺代理，换不来任何安全收益。对照 CC：MCP 记忆库在只读场景同样可读不可写。

**为什么 `chat_only` 连读也要掐？** 如果最严的一档反而是唯一能看到用户最私人内容的档，
这个阶梯就断了。`chat_only` 的用户预期是「什么都不碰」，他大概率是在做外部评测或演示，
不该顺带把用户的记忆送过去。

> 这一条是 M5 的首版判断里**没有**的。首版我写的是「三档都保留读」，理由是
> 「读不是越权」。写测试时才发现它让 `chat_only` 变成最能看到私人数据的一档 ——
> 守住了字面安全（不越权），丢掉了产品语义（阶梯）。

## 2. 实现

### 2.1 `tool_policy.py`：把旁路判据集中到一处

```python
MEMORY_READ_POLICIES = frozenset({POLICY_FULL, POLICY_READ_ONLY})
MEMORY_WRITE_POLICIES = frozenset({POLICY_FULL})

def allows_memory_read(policy: str) -> bool: ...
def allows_memory_write(policy: str) -> bool: ...
```

**为什么集中在这里而不是各安装点自己判**：判据散开就迟早漏一处 —— 本次缺陷
正是「`session.py` 判了、`sse.py` 没判」这类散开的典型后果。集中成一个函数后，
安装点只负责「问一句」，语义只在这里定义一次。

同时更新 `describe()` 的两档文案（`read_only` 补「无记忆写入」，
`chat_only` 改成「不注入任何工具，也不注入记忆」）。

### 2.2 三个安装点

| 位置 | 改动 |
|---|---|
| `subagent/session.py`（team 路径） | 注入器按 `allows_memory_read` 决定是否构造；`on_turn_end` 按 `allows_memory_write` 决定是否挂 |
| `sse.py::_install_memory_injector`（非 team 路径） | 加读闸 |
| `sse.py::_install_memory_turn_end`（非 team 路径） | 加写闸（防御性，team 路径上 `_memory_aware` 已让它让位） |

`chat/router.py` 的 `_TurnUR` 补 `tool_policy` 字段 —— 否则 SSE 层拿不到档位，
那道闸永远只会看到默认 `full`。

### 2.3 一个刻意的设计选择：注入器本身不判档位

`MemoryInjector` **不**读 `tool_policy`，闸全在安装点。理由：

- 它是纯读组件，只该关心「有没有记忆可注入」；
- 做成档位敏感的，会让「直接构造注入器」这类正当用法（team 路径、测试、
  将来的其它入口）都要自己再传一次 policy，闸就会重新散开；
- 闸在安装点还天然覆盖了「这一轮到底装不装」这个问题 —— 不装就没有对象，
  比「装了但内部返回空」更干净。

对应测试 `test_read_injection_injector_itself_is_policy_agnostic` 钉住这一点。

|---|---|

### 3.3 L3 真机 e2e（`backend/tests/e2e/memory_a2a_cases.py`）

后端以 `work/_launch_m5.py` 启动（`HLZ_MEMORY_AUTO_WRITE=1` + `HLZ_MEMORY_SELECTOR=0`），
真 LLM（湛卢 deepseek），真 A2A JSON-RPC。

| 场景 | runId | 结果 | 证据 |
|---|---|---|---|
| **S-M4a** 只读 token 的工具面 | `1794658763-33de` | ✅ 5.5s | 模型回答只列出 `memory_list` / `memory_read`，**没有** `memory_write` |
| **S-M4b** 只读 token 零写入 | `1794658775-2c77` | ✅ 105.6s | 记忆 `0 → 0`；模型明确说「没有任何写入长期记忆的能力」 |
| **S-M4c** 正向对照（full token） | `1794658898-1827` | ✅ 105.9s | **同一句提示词**，记忆 `0 → 1` |
| **S-M3** 跨用户隔离 + 负对照 | `1794659010-26a5` | ✅ 16.5s | A 回答复述哨兵 `AM5c4e17`；B 回答「查不到…两个查询都返回 0 条」 |

**S-M4b 与 S-M4c 是一对，缺一不可**：没有正向对照，「零写入」可能只是
「这句提示词本来就不触发提取」的空断言。两条合起来才是「同样的输入，
full 会写、read_only 不写」—— 差别只可能来自档位闸。

## 4. 未覆盖 / 后续

| 项 | 说明 |
|---|---|
| **`chat_only` 的真实 e2e** | 只做了 L1。真机上「模型连记忆都看不到」没法用「它说了什么」来证明（它本来就看得到自己看不到），要验就得比对注入块是否出现在请求体里 —— 需要抓包或加临时日志 |
| **A2A 子代理路径的记忆档位** | `SubagentHost` 派生的子代理本来就拿不到记忆工具（`CHILD_EXCLUDED`），但它是否也受 `allows_memory_read` 影响未单独验 |
| **dream 巡检的档位无关性** | dream 是服务端维护任务（`lifespan` 里跑），与任何 token 无关，因此**不应**受档位影响。当前实现天然满足，但没有测试钉住 |
| **`describe()` 文案的后端断言** | 前端已同步改成「只读：…/ memory_list / memory_read（不写记忆）」，但 `describe()` 的输出没有测试锁住，文案漂移不会被发现 |

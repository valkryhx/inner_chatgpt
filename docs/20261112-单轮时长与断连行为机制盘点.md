# 单轮时长上限、切标签行为、连接池缺陷：机制盘点与修复

> 日期：2026-11-12　状态：已实测、已修复、含反向确认
> 涉及：`backend/app/agent_loop.py`、`backend/app/llm_client.py`

## 0. 四个问题的结论

| # | 问题 | 结论 |
|---|---|---|
| 1 | 单轮会不会无限等待？ | **不会无限，但确实没有时间上限**。有两个闸：`max_turns=300`（次数）+ 每次调用 `read_timeout=120s` + 重试等待预算 180s。缺的是**整轮墙钟**——300 轮理论上能跑几小时。已补 `AGENT_WALL_CLOCK_S`（默认 0=不限，显式打开才生效）。 |
| 2 | 切到别的标签/会话，旧的那轮还在跑吗？ | **不在跑，当场中断**。客户端断连 → Starlette 取消生成器 → 该轮 task 结束。实测：断开后 5 秒内 assistant 消息已被置为 `stopped`，内容不再增长。 |
| 3 | 断开时已经产生的输出会保留吗？ | **正文保留，工具执行中止**。实测断连时已产出的 93 字被持久化，但 blocks 停在被中断的位置，后续工具不再执行。 |
| 4 | 「大模型连接池用完了」是什么 bug？ | **是真的，且残留日志可证**。`httpx.Timeout(read, connect=…)` 没给 `pool`，池等待沿用 read 超时（120s）；池上限 8 又恰好等于并发子代理上限 8。已修：pool 单独设 10s，连接上限 32。 |

---

## 1. 单轮时长的现有闸门（盘清现状）

```
agent_loop.run_stream()                    backend/app/agent_loop.py:264
  while turn < self.max_turns:             ← 闸 1：模型往返次数（默认 300）
    llm_client.run()                       backend/app/llm_client.py:452
      重试循环（max_retries 默认 4，可到 8）
      每次请求 httpx read_timeout = 120s   ← 闸 2：单次连接读超时
      重试等待累计上限 RETRY_WAIT_BUDGET_S = 180s  ← 闸 3：重试等待预算
      PoolTimeout = read_timeout（缺陷，见 §4）
  agent_loop 的续跑预算：
    HLZ_AGENT_LLM_RETRIES = 2              ← 闸 4：调用彻底失败后续跑次数
    HLZ_LEAD_TEAM_GRACE_TURNS = 3          ← 闸 5：lead 等队友的宽限轮数
子代理另有墙钟：
    SUBAGENT_TIMEOUT_S = 1800              ← 只约束子代理，不约束主轮
```

**缺口**：没有「整轮最多跑多久」。闸 1 限次数、闸 2 限单次连接、闸 3 限重试等待，
三者的乘积可以很大：

```
300 轮 × (120s 读超时 × 最多 5 次尝试 + 180s 重试预算) ≈ 理论上 50 小时
```

实际当然到不了（多数轮次几秒），但**没有任何机制保证它一定结束**，
这就是你感觉「越跑越久」的来源——等待是有界的，但**上界离实际很远**。

## 2. 为什么没有无限等待，但体感像卡住

真机上观察到的长等待，主因不是 `max_turns`，而是这两条：

1. **连接池排队**（§4）：每次排队等 120s，日志里连续十几条 PoolTimeout，
   相邻重试间隔正好 2 分钟。
2. **单次调用慢**：长思考模型 + 长输出，一次往返 2–5 分钟是正常的。

两者都不违反任何闸门，所以「合法地慢」。CC319 的做法值得借鉴：它用
**idle timeout**（30s 内没有新进展就判 idle）而不是「总时长」——
判定标准是「有没有进展」，不是「跑了多久」。见 §5 的建议。

## 3. 切标签 / 切会话时的实际行为（已实测）

### 3.1 后端链路

```
客户端断开 TCP
  → Starlette StreamingResponse 走 spec_version 2.3 分支
    （uvicorn 0.41 上报 spec_version=2.3，所以是 create_collapsing_task_group）
  → listen_for_disconnect 收到 http.disconnect → cancel_scope.cancel()
  → guarded_stream() 的生成器被取消
  → _event_stream 的 finally：_cleanup_turn（同步释放租约 → 异步清理）
  → 消息状态收敛为 stopped
```

### 3.2 实测证据

脚本 `work/_probe_disconnect_20261112_D2.py`：读到 `thinking_delta` 后立刻
`resp.close()`，然后每 6 秒查一次 DB。

```
读到 374 字节，含 thinking_delta=True
断开前快照: {'status': 'streaming', 'n': 0}
已断开，开始观察
  断开后  6s: status=stopped  content=0
  断开后 12s: status=stopped  content=0（相对上次 +0）
  ...
  断开后 48s: status=stopped  content=0（相对上次 +0）
```

**结论：切走 = 中断本轮，不会在后台继续跑。**

### 3.3 已产出的内容会保留

`work/_probe_disconnect_20261112_D3.py`：读到 12 个 `text_delta` 后断开。

```
读到 text_delta 次数: 12
断开后 status: stopped
content 长度: 93
content 前 80 字: **1+2+…+800 = 320400**…
blocks 数: 6 | 类型: ['reasoning','tool','reasoning','tool','reasoning','text']
```

所以断连的语义是：
- **已经流给用户的正文保留**（不会白问一遍）；
- **后续工具不再执行**（blocks 停在中断处），任务不会在后台留残余副作用。

### 3.4 前端为什么通常不会"悄悄断流"

前端 `selectSession` 有 `if (streaming) return` 守卫（`App.tsx:357`）——
生成中切换会话会被直接拦掉。所以"切标签导致中断"主要发生在：
- 关掉标签页 / 浏览器把后台标签休眠；
- 网络切换（笔记本合盖、WiFi/4G 切换）；
- 反向代理空闲超时（nginx `proxy_read_timeout` 默认 60s）。

而**只切到别的浏览器标签页（同一页面不卸载）不会断连**，SSE 连接仍在。

## 4. 连接池缺陷：有确凿证据

### 4.1 缺陷形态

```python
# 修复前 backend/app/llm_client.py:349
self._client = httpx.AsyncClient(
    timeout=httpx.Timeout(self.s.timeout, connect=15.0),   # ← 没给 pool
    limits=httpx.Limits(max_connections=8, max_keepalive_connections=4),
)
```

`httpx.Timeout(read, connect=…)` 不给 `pool` 时，**pool 等待沿用 read 超时**。
验证：

```
修复前: Timeout(connect=15.0, read=120, write=120, pool=120)
修复后: Timeout(connect=15.0, read=120, write=120, pool=10.0)
```

### 4.2 为什么会被占满

`max_connections=8` 与 `USER_MAX_ACTIVE_SUBAGENTS=8` 数值相同。主轮 + 8 个
teammate/子代理**共享同一个 httpx client**（`subagent/runtime.py:58`：
`self.client = self.parent.model.client`），且每个流式请求在整段生成期间
一直占着连接。9 个并发就排队。

### 4.3 真机日志证据

`backend/data/logs/app.log` 里有 13 条 `PoolTimeout`，相邻重试间隔约 2 分钟：

```
12:05:37 LLM 请求失败，7.8s 后重试（第 4/4 次）：network error: PoolTimeout:
12:07:45 模型调用失败，续跑（2/2）：network error: PoolTimeout:
12:09:45 LLM 请求失败，1.0s 后重试（第 1/4 次）：network error: PoolTimeout:
12:11:46 LLM 请求失败，1.9s 后重试（第 2/4 次）：network error: PoolTimeout:
12:13:48 LLM 请求失败，3.5s 后重试（第 3/4 次）：network error: PoolTimeout:
12:15:51 LLM 请求失败，6.9s 后重试（第 4/4 次）：network error: PoolTimeout:
```

注意时间戳：**每次失败之间隔了整整 2 分钟**——不是重试退避（退避只有 1–8 秒），
而是每个请求都在池里等满了 120s。

### 4.4 修复

```python
timeout=httpx.Timeout(self.s.timeout, connect=15.0, pool=10.0),
limits=httpx.Limits(
    max_connections=_max_connections_from_env(),   # 默认 32
    max_keepalive_connections=8,
),
```

- `pool=10.0`：池满时最多等 10 秒就抛 `PoolTimeout`，而不是 120 秒。
  它会走已有的退避重试路径，用户看到的是「稍等一下」，不是「卡住两分钟」。
- `max_connections` 32：大于并发子代理上限，留出主轮 + 重试的余量。
  可用 `HLZ_LLM_MAX_CONNECTIONS` 覆盖（clamp 到 2–256）。

### 4.5 反向确认

撤掉 `pool=10.0` 后跑单测：

```
E  where 120 = Timeout(connect=15.0, read=120, write=120, pool=120).pool
FAILED tests/test_llm_resilience.py::test_pool_timeout_is_bounded_not_read_timeout
```

恢复后 15 passed。这条测试锁住了缺陷形态。

## 5. 新增：整轮墙钟兜底

### 5.1 设计取舍

**默认关闭（0 = 不限）**。理由：这是兜底闸，不是常规手段。
给个默认值（比如 1800s）会把「确实需要跑很久」的任务切坏——比如让它分析一个
大型仓库，20 分钟可能才刚热身。需要硬上限时显式打开：

```bash
AGENT_WALL_CLOCK_S=1800    # 30 分钟硬上限
AGENT_WALL_CLOCK_S=0       # 默认：不限
```

### 5.2 实现位置

检查点放在**每轮开头**（`agent_loop.py` 循环第一行内），保证超时后
不会先发起下一次模型调用再报错：

```python
if self.wall_clock_s > 0:
    elapsed = time.monotonic() - started_at
    if elapsed > self.wall_clock_s:
        yield {"type": "error",
               "error": f"本轮运行已超过 {self.wall_clock_s:.0f}s 上限，已停止"
                        f"（第 {turn} 轮）。可用 AGENT_WALL_CLOCK_S 调整，或设为 0 取消该上限。"}
        return
```

报错里必须带环境变量名，否则用户只会觉得「又卡住了」。

### 5.3 测试

`backend/tests/test_agent_loop_resilience.py` 新增 3 条：
默认关闭、超限停止且不再调用模型、报错里带 `AGENT_WALL_CLOCK_S`。

> 写测试时踩了个坑，值得记下：第一版把 `time.monotonic` 整体加偏移，
> 但**起点也是在循环开头读的**，两边同样被加，`elapsed` 恒为 0，闸门永远不触发。
> 必须用「首次给 0、之后给大值」的假时钟。

## 6. 对标 CC319：它怎么避免「无限等待」

| 机制 | CC319 | Hlaudz 现状 |
|---|---|---|
| 单次调用超时 | 有 | 有（read_timeout 120s） |
| 调用层重试 | 退避 + Retry-After + 非流式降级 | **已对齐**（见韧性文档） |
| 轮数上限 | 有 | 有（300） |
| **idle 判定** | **30s 没有新进展 → 判 idle 退出循环** | **无** |
| 整轮墙钟 | 无显式总时长 | 已补（默认关闭） |
| 用户在看就不超时 | 有（`viewingAgentTaskId`） | 无 |

**最值得学的是 idle timeout**（CC319 §10.6）。它的判定标准是
「**有没有进展**」而不是「跑了多久」：

```
500ms 轮询 ① 用户插话 ② 邮箱新消息 ③ 可认领任务
都没有 → 继续等
连续 30s 都没有 → 判 idle，退出循环
```

这比固定总时长更贴合真实需求：一个跑了 40 分钟但**每分钟都在出工具结果**的任务
是健康的；一个跑了 3 分钟但**一点动静都没有**的任务才该被杀。

### 6.1 建议的后续优化（未实施）

给主轮加「进展心跳」：每产生一次 `text_delta` / `tool_result` 就刷新时间戳，
连续 `HLZ_TURN_IDLE_S`（建议 180s）无任何进展才判失败。这比总时长精准得多，
而且能区分「慢但在动」和「真的卡死」。

**不做的理由（当下）**：目前已有 read_timeout 120s + 重试预算 180s 兜住
「完全没响应」，再加一层心跳属于优化而非修 bug。等真的出现「有响应但无进展」
的案例再做，避免过早加一层难以推理的机制。

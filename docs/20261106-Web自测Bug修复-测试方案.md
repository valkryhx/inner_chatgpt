### 3.4 Team 长任务：主动停止 + 续任务（`work/claude_test_and_review/_test_team_stop_resume.py`，18 项）

**当前怎么终止**（实测结论）：

- UI：输入框旁的「停止」按钮（生成中显示为停止），以及 Team 面板右上角的「停止」（仅 streaming 时出现）；两者都调用 `POST /api/sessions/{sid}/stop`。
- API：`POST /api/sessions/{session_id}/stop`，body 可带 `generation_id` / `message_id`；不带时服务端按 DB 活跃租约解析。
- 语义：**按整轮生成停止**——主代理 + 所有 teammate/subagent + `code_run` 子进程一起停；任务板里 `in_progress` 的任务回收为 `pending`，下一轮可恢复。
- 目前**没有「只取消某一个任务」的接口**（`task_update` 只有 claim/complete/reclaim）；要停单个长任务只能停整轮，或用消息让 Lead 停止该任务。

| 编号 | 步骤 | 断言 |
|---|---|---|
| A1/A2 | 真实模型建 Team、建任务、spawn teammate 写 8000 字；等到 60s（可 `--wait` 调整） | 打断瞬间生成仍在进行；已有 teammate 运行记录 |
| B1/B2 | `POST /stop` | 200 且 `subagents_stopped >= 1`；SSE 在 30s 内结束（实测约 0.1s） |
| C1..C8 | 停止后查 Team / 消息 / DB | Team=`stopped`；无 `in_progress`（回收为 `pending`）；最后一条 assistant=`stopped`；子代理块不再是 running（BUG-15）；无 running 子代理；teammate=`stopped`；无 active 生成租约 |
| D1..D6 | 同一会话发「继续」 | 出现 `team_start` + `team_resumed`（恢复任务数 ≥ 1）；新 Team 能看到恢复的任务；本轮正常完成（无 409/陈旧租约）；信息项记录是否再次派生 teammate 或更新任务 |

**本次实测（真实模型）**：

```text
--wait 60：A1–C8、D1–D5 全过；stop→SSE 结束 0.11s；Team=stopped；任务 pending；
           teammate=stopped；「继续」轮 86.9s 完成，team_resumed task_count=1，
           恢复后的任务被模型推进到 completed
--wait 30：18 checks 全过；stop→SSE 结束 0.14s；teammate turns=1（被取消时补记）
```

**结论**：停止是「整轮终止」，后端、DB、UI 三处一致；停止后可直接发「继续」，Team 会复制上一轮未完成任务并继续推进。该套件同时暴露并复验了 BUG-15（停止后子代理卡片残留「运行中」）。

**手动试用样例输入**（在 UI 里直接粘贴，需选择支持工具调用的模型，如「湛卢」）：

第一条（建 Team + 派长任务，约 1–3 分钟）：

```text
请作为 Team Lead 完成以下协作任务，必须真实调用工具，不要自己写：
1) 调用 task_create：subject=写一篇 8000 字长文（分 10 节），description=主题「AI 办公助手」，每节 800 字。
2) 调用 spawn_teammate：task_name=writer，team_task_id 用第 1 步返回的 task_id，
   message=请完成这个任务：先写第 1-5 节（每节至少 800 字）保存为 outline.md，
   再用 file_patch 追加第 6-10 节，然后 file_read 核对字数，最后写 summary.md；
   完成后调用 task_update(action=complete, task_id=<第 1 步的 task_id>, expected_version=1)。
3) 之后反复调用 wait_agent 等待 writer（等待超时是正常的，继续等）。
```

等 60 秒左右，在输入框旁点「停止」（或 Team 面板右上角「停止」），然后发：

```text
继续刚才没写完的任务：先看任务板，把未完成的任务重新派给 teammate 接着写，直到完成。
```

预期：停止后 Team 状态为「已停止」、任务变回「待处理」、子代理卡片显示「已停止」；发「继续」后出现「任务板已恢复」，任务被继续推进。

失败排查顺序：

1. 看该用例的 detail（脚本会把实际值打出来）；
2. API 层失败先确认后端是否已重载本次代码（`--reload` 生效）；
3. UI 层失败先确认 `frontend/dist` 是最新构建（旧 bundle 会出现「改了代码但断言旧行为」）；
4. F01 偶发失败通常是模型这一轮没有调用工具，脚本已内置一次更强指令的重试，仍失败才计 FAIL。

## 6. 已知限制与易波动点

1. **依赖真实模型**：F01/F06/F08/U-10/U-13/U-03 会产生真实调用（合计约 15–20 次），耗时约 2–3 分钟；网络或模型限流会导致超时，重跑即可。
2. **F06 的阈值**：用例把软线压到 1200 tokens 以放大问题；断言的是「压缩后必低于软线」，不是「每轮只触发一次」。极小窗口下隔轮触发属预期。
3. **配置复制**：`copy_llm_config` 取数据库中最新一条 `湛卢` 配置。若先跑过 F06，会复制到 8000 窗口的小配置；这不影响断言（只影响 UI 上显示的窗口数字）。
4. **playwright-cli 限制（当前版本实测）**：命名会话（`--session`）对 `eval` 不生效，套件使用默认会话并在开头清空本页 localStorage；`tab-new <url>` 只开 `about:blank`（套件已不使用多标签）。运行前请勿在同一条默认会话上做需要保留状态的操作。
5. **MCP 导入契约**：非法 JSON 仍返回 200 + `ok=false` + `errors`，UI 负责展示；如果未来改为 400，需要同步 F05 与 `_suite_api.py` 的期望。
6. **测试数据**：每次运行创建 2–4 个 `fx*/ui*` 账号、若干会话（含 `U03-hold-slot`）。可定期清理；不影响现有账号。
7. **U-13 依赖设计**：仍按「每轮 root 即 lead」的设计，只验证 0 任务时的文案，不验证是否应创建 Team。
8. **停止粒度**：目前只有整轮停止，没有单任务取消接口；`_test_team_stop_resume.py` 的时长取决于模型，若任务在打断前就完成，脚本会以 `INCONCLUSIVE`（退出码 3）提示调大任务量或减小 `--wait`。

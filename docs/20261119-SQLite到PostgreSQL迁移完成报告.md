## 1. 架构：为什么在驱动层适配而不是改 126 处调用点

全仓有 126 处 `aiosqlite.connect` 和 58 处 `PRAGMA`。两条路：

| 方案 | 问题 |
| --- | --- |
| 在 126 处逐个改 | 改动面巨大，每处都可能回归，1242 条测试兜不住 |
| **在驱动层做适配** | SQLite 路径零改动；PG 的方言差异有穷可枚举 |

选了后者。四个新模块：

```
app/dbselect.py       HLZ_DB_URL 决定后端 + 测试用的 schema 隔离
app/sqlcompat.py      后端无关接口 + 方言工具（占位符/语句拆分）
app/sqlitedriver.py   原样包装 aiosqlite（方言改写全关）
app/pgdriver.py       asyncpg + 连接池 + 方言翻译
```

调用方只改一行 import：

```python
import aiosqlite                    →  from . import sqlcompat
aiosqlite.connect(DB_PATH)          →  sqlcompat.connect(DB_PATH)
```

## 2. 方言翻译清单（都在 `pgdriver._prepare`）

| SQLite 写法 | PG 处理 | 实测 |
| --- | --- | --- |
| `?` 占位符 | 换成 `$1..$n`，**跳过字符串/注释/双引号标识符** | ✅ |
| `INSERT OR REPLACE` | `ON CONFLICT(<pk>) DO UPDATE SET x=EXCLUDED.x` | ✅ |
| `INSERT OR IGNORE` | `ON CONFLICT DO NOTHING` | ✅ |
| `PRAGMA table_info(t)` | `information_schema.columns`，还原成 SQLite 的 6 列形状 | ✅ |
| `PRAGMA journal_mode/busy_timeout/...` | 空操作 | ✅ |
| `rowid` | `ctid` | ✅ |
| `sqlite_master` | `pg_class + pg_namespace` 子查询 | ✅ |
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | ✅ |
| DDL 里的 `INTEGER` / `REAL` / `BLOB` | `BIGINT` / `DOUBLE PRECISION` / `BYTEA` | ✅ |
| `BEGIN IMMEDIATE` | `BEGIN` + `pg_advisory_xact_lock` | ✅ |
| NUL 字节参数 | 削掉 | ✅ |

## 3. 七个「只有真库才暴露」的坑

这部分是本文档最有价值的内容 —— 每一条都是实测踩出来的，
**看代码和跑单元测试都发现不了**。

### 3.1 `INTEGER` 不是 64 位（溢出）

SQLite 的 `INTEGER` 是 64 位，PG 的 `INTEGER` 是 32 位。项目里所有时间戳
都是毫秒（`int(time.time()*1000)` ≈ 1.7e12），直接
`invalid input for query argument: value out of int32 range`。

→ DDL 里的 `INTEGER` 全部映射成 `BIGINT`。

### 3.2 `information_schema` 是跨 schema 的

`PRAGMA table_info(t)` 翻译成 `information_schema.columns` 时，只按
`table_name` 过滤会把**别的 schema 里同名表**的列也捞出来。后果：旧库迁移
代码看到「`user_id` 已存在」，跳过 `ALTER TABLE ADD COLUMN`，然后所有查询
报 `column "user_id" does not exist`。

→ 必须加 `AND table_schema = current_schema()`。

这条在单 schema 生产环境下**不会出现**，但在「每用例一个 schema」的测试
隔离下 100% 命中（实测 57 条报错）。这正说明为什么测试隔离有价值。

### 3.3 语句拆分要逐字符扫

`split_statements` 一开始按 token 定位再切分号，结果「注释前面那一大段」
被整块塞进缓冲而不切分 —— `team_store` 的 12 条 DDL 被并成 8 条，
aiosqlite 报 `You can only execute one statement at a time`。

→ 改成逐字符扫描（单引号 / 双引号 / 行注释 / 块注释分别跳过）。

### 3.4 类型映射的前缀判断必须剥掉注释

`split_statements` 切出来的语句**带着前一句后面的注释**：

```sql
-- 名字钉住（CC319 的 sendMessagePins）：一个名字第一次送达时
-- 绑定到那个 agent。
CREATE TABLE IF NOT EXISTS team_name_pins ( ... pinned_at INTEGER ... );
```

`_DDL_HEAD.match()` 看到开头是 `--`，匹配不到 `CREATE TABLE`，整段类型映射
失效 → `pinned_at` 建成 `integer` → 插入毫秒时间戳溢出。

→ 判断前缀前先剥掉开头的注释行和空行。

### 3.5 `BEGIN IMMEDIATE` 不能简单降级成 `BEGIN`

SQLite 的 `BEGIN IMMEDIATE` **立刻拿库级写锁**，所以

```sql
BEGIN IMMEDIATE;
SELECT COALESCE(MAX(event_seq),0)+1 FROM team_events WHERE team_id=?;
INSERT INTO team_events(...) VALUES(...);
COMMIT;
```

是原子的。PG 的 `BEGIN` 不拿任何锁，两个并发事务读到同一个 MAX，
一个撞主键：

```
duplicate key value violates unique constraint "team_events_pkey"
DETAIL: Key (team_id, event_seq)=(t1, 3) already exists.
```

→ 用事务级 advisory lock（`pg_advisory_xact_lock`）还原「本事务独占写」。
语义完全一致，事务结束自动释放。代价是 6 处 `BEGIN IMMEDIATE` 事务串行，
但它们都是「读-改-写-提交」的短事务，可接受。

### 3.6 NUL 字节在 PG 协议层就被拒

`invalid byte sequence for encoding "UTF8": 0x00`。SQLite 能存。
用户把乱码粘进搜索框时应该「查不到」而不是 500。

→ 参数层削掉 NUL。

### 3.7 连接池会跨 event loop 泄漏

测试里每个用例 `asyncio.run()` 一个新 loop，asyncpg 的池绑定 loop，
于是每个用例建一个新池。`min_size=2` 时几百个用例 ×2 条连接直接把
PG 的 `max_connections(100)` 打爆（425 条 `TooManyConnectionsError`）。

→ `min_size=0`（空池不占连接）+ 新建池前回收「属于已关闭 loop」的池。

**另外**：这个坑引出一个真实的生产问题 —— PG 冷建连 ~200ms，而
`warm_pool()` 才是解法。记忆预取要求选择器在首轮模型调用的 50ms 内 settle，
冷建连会让它永远赶不上（SQLite 建连只要 0.17ms，所以这个成本在
SQLite 时代根本不存在）。→ 应用启动时预热池。

## 4. 测试隔离：路径 → schema

测试用 `monkeypatch DB_PATH -> tmp_path/app.db` 实现隔离，每个用例一个文件。
PG 里没有「文件」，如果所有用例共享一个库，30+ 个 `isolated_db` fixture
立刻互相污染。

解法：把 `DB_PATH` 的**路径字符串**哈希成一个 PG schema 名。

```python
HLZ_PG_SCHEMA_PER_PATH=1                  # 测试时打开
DB_PATH="/tmp/pytest-xxx/app.db"
  -> schema "hlz_3690dc4b916abbd9"
```

生产下不设这个开关，schema 恒为 `public`，行为不变。
这样 `connect(path)` 的签名一个字不用改，测试隔离自动成立。

## 5. 怎么用

### 5.1 只跑 SQLite（默认，什么都不用改）

```bash
cd backend && python -m pytest tests -q      # 1269 passed
```

### 5.2 切到 PostgreSQL

```bash
# 起库
docker run -d --name hlz-pg \
  -e POSTGRES_PASSWORD=<pw> -e POSTGRES_USER=hlz -e POSTGRES_DB=hlaudz \
  -p 5432:5432 --restart unless-stopped postgres:16-bookworm

# 迁数据（先 --dry 看 DDL，再真迁，再 --verify）
cd backend
python scripts/sqlite_to_pg.py --dsn "postgresql://hlz:<pw>@127.0.0.1:5432/hlaudz" --dry
python scripts/sqlite_to_pg.py --dsn "postgresql://hlz:<pw>@127.0.0.1:5432/hlaudz"
python scripts/sqlite_to_pg.py --dsn "postgresql://hlz:<pw>@127.0.0.1:5432/hlaudz" --verify

# 切后端
export HLZ_DB_URL="postgresql://hlz:<pw>@127.0.0.1:5432/hlaudz"
```

**回滚**：去掉 `HLZ_DB_URL` 即可，SQLite 文件一直没动过。

### 5.3 跑 PG 测试

```bash
export HLZ_TEST_PG_DSN="postgresql://hlz:<pw>@127.0.0.1:15432/hlz"
python -m pytest tests/test_pg_backend.py -q          # 18 条专项

export HLZ_DB_URL="$HLZ_TEST_PG_DSN" HLZ_PG_SCHEMA_PER_PATH=1
python -m pytest tests -q --ignore=tests/test_pg_backend.py   # 全量 1266
```

## 6. 性能

| 指标 | SQLite | PG（池） |
| --- | --- | --- |
| 单查询 | 0.097 ms | 1.5 ms |
| 建连 | 0.17 ms | 200 ms（冷）/ 池复用后 0 |

**1.5ms 是可接受的常数**，换来的是 SQLite 架构上给不了的东西：
多进程并发写（SQLite 单写者锁，两个进程同时写必然 `database is locked`）。

## 7. 已知限制

| 限制 | 影响 | 何时处理 |
| --- | --- | --- |
| `BEGIN IMMEDIATE` 用全局 advisory lock | 这些事务串行 | 多实例高并发时改成按 team_id 分键 |
| PG 下 `await connect(path)` 不支持 | 仅 SQLite 路径有这种写法，app 内 0 处使用 | 不需要 |
| 7 条测试在 PG 下跳过 | 都是 SQLite 专有场景（直读文件 / 旧版 schema 迁移） | 不需要 |
| 未验证 >100 并发 | 目前单机单进程 | 上多实例前做压测 |
| 连接池 `max_size=8` | 单进程够用 | 上多实例时按 PG `max_connections` 重新分配 |

日期：2026-11-20
前置：`docs/20261120-沙箱容器泄漏根因.md`（58 个 `hlz_sbx_*` 是 pytest 残留）

## 0. 一句话

`conftest` 的沙箱单例重置在 teardown 时**不销毁池里的容器**，
只把 `_manager` 置 None；每跑一轮走 Docker 路径的测试就在 Docker 里留一个
`sleep infinity` 容器。已改为经 `leak_guard` 带超时销毁，并补了挂死守卫。

| 文件 | 改动 |

| `backend/tests/conftest.py` | `_clear()` 先 `leak_guard.release_pool_sync(...)` 再置 None |

## 2. 为什么不能直接 `asyncio.run(pool.shutdown())`

第一版就是这么写的，能过测试、真机也不泄漏。但**它会挂死**。

`ContainerPool.shutdown()` 里是 `async with self._lock`。若锁在上一个
事件循环里被某个中途退出的协程持有（`acquire()` 之后没 `release`），
新循环的 `acquire()` 会**永久等待**。实测（`docs/probes/20261120-探针-Lock已持有挂死.py`）：

```
1) 上个循环结束：locked=True
2) 新循环 + wait_for(3s)： TIMEOUT
```

裸 await 的后果是整个 pytest 会话卡死 —— 比泄漏容器严重得多。

反向确认里把 `wait_for` 换成裸 await，测试进程**真的挂死了 180 秒**
（`docs/probes/20261120-沙箱泄漏修复反向确认.py` 反向 B），这就是这条守卫存在的理由。

## 3. 三个探针的结论（都实测，不是推断）

| 探针 | 问题 | 结论 |
| --- | --- | --- |
| `docs/probes/20261120-探针-Lock无竞争跨循环.py` | 无竞争的 Lock 能跨循环吗 | ✅ 能，`shutdown` 正常跑完 |
| `docs/probes/20261120-探针-Lock有竞争跨循环.py` | 有竞争、`_loop` 绑了旧（已关闭）循环呢 | ✅ 仍能 acquire —— 跨循环本身不是问题 |
| `docs/probes/20261120-探针-Lock已持有挂死.py` | 锁**已被持有**时呢 | ❌ `wait_for(3s)` TIMEOUT ⇒ 裸 await 永久挂死 |

所以 docstring 里写的「跨事件循环安全」是对的，但前提是**锁没被占住**。
真正的风险只有第二种，而它需要超时兜底。

## 6. 一个顺手排除掉的怀疑

全量跑完有 4 条 `RuntimeError: Event loop is closed`（aiosqlite）。
用 `git stash` 回退 conftest 后跑同一套，**仍然是 4 条** ⇒ 与本次改动无关，
是既有问题（`aiosqlite` 的后台线程在事件循环关闭后回调）。

## 7. 遗留

- `probe.cleanup_orphans` 仍然只在 `manager.start()` 里被调，且
  `backend != "inproc"` 时直接 return。如果将来出现「进程被 kill -9」
  这种 teardown 跑不到的情况，仍会留残留 —— 那时需要运维手动清或
  在 pytest 的 `session` teardown 里再兜一层。
  本轮没做：function 级 teardown 已覆盖正常路径，且多兜一层会变慢。
- `pool._pool` 单例在 teardown 后**不清空**（只清 entries）。
  这是有意的：清空会让 `get_pool()` 重新构造，而它内部持有 `runtime`，
  代价不必要。TEARDOWN 已把 entries 清干净，等价于空池。

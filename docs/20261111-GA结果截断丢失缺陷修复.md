# GA 结果截断丢失缺陷：根因与修复

> 日期：2026-11-11　状态：**已修复并真实环境验证**
> 现场：session `co_fa983ab2eef1`，agent_id `ga_c6a3683f`（用户查「金妍儿」）

## 1. 现象

用户让 GA 查金妍儿资料，模型拿到了结果但**只读到一半**，之后想补读全文时报错。

模型自己的反思：

> 「GA 的最终答复在我读取时被截断，而且我那次调用同时关闭了会话，没拿到全文」

## 2. 现场复原（数据库实读）

两次 `ga_result` 调用：

| 次序 | 参数 | 返回长度 | 结果 |
|---|---|---|---|
| 第 1 次 | `full=true, max_chars=8000, **close=true**` | 8898 | 截断到 8000（全文 **13223**），**会话被销毁** |
| 第 2 次 | `max_chars=14500`（想读全文） | **43** | `[工具执行错误] KeyError: 未知的 GA 会话: ga_c6a3683f` |

## 3. 根因：不是 max_chars 太小

**上调 `max_chars` 解决不了这个问题**，理由是：

1. `max_chars` 是**模型自己填的参数**，不是配置上限——它第一次自己填了 8000；
2. 真正的破坏来自 `close=true` 与 `truncated=true` **同时发生**：
   ```python
   if close:
       await self._close_session(agent_id)   # 内存记录直接删掉
   ```
3. GA 结果**从未落库**，`_close_session()` 只做 `_stop_entry` + `session.close()`，
   `_entries.pop()` 之后数据永久消失。

所以第二次调用的 43 字符错误就是证明：**问题不在上限，而在数据已经不存在**。

## 4. 修复（三条）

### 4.1 规则 1：截断与关闭互斥

```python
truncated = bool(limit and len(text) > limit)
if truncated and close and not force_close:
    raise ValueError(
        f"拒绝关闭：结果会被截断到 {limit} 字符，而全文 {len(text)} 字符。"
        "关闭会永久销毁未读部分。请先调大 max_chars（或传 full=true）读完，"
        "再单独用 ga_result(close=true) 关闭；确实要丢弃剩余部分就传 force_close=true。"
    )
```

逃生口 `force_close=true` 只给「明确知道剩余可丢弃」的场景用。

### 4.2 规则 2：结果落库，关闭后仍可读

新增 `backend/app/acp/store.py` + `ga_runs` 表：

| 字段 | 说明 |
|---|---|
| `agent_id` | 主键 |
| `user_id` / `session_id` / `generation_id` | owner 作用域（便于清理） |
| `status` / `result` / `full_text` | 会话终态与两份文本 |
| `tool_calls` / `prompts` / `stop_reason` | 记账 |
| `updated_at` | 时间戳 |

接进 manager：

- `_close_session()` 在销毁前先落库（**先写再删**，落库失败也照常关闭）；
- `result()` 查不到内存会话时回落到 `_load_persisted()`，返回 `source="db"`。

### 4.3 默认上限 20000 → 50000

与 `tool_budget.DEFAULT_MAX_RESULT_CHARS` 对齐。原值太小，
导致「明明能读全却读半截」，而且模型看到 `truncated` 时已经不知道全文多长。

## 5. 验证

### 5.1 单测（`backend/tests/test_acp_result_safety.py`，8 条）

| 用例 | 断言 |
|---|---|
| `test_refuses_close_when_result_truncated` | 截断 + close 抛 ValueError，**且会话仍在内存** |
| `test_truncation_alone_is_allowed` | 只截断不关闭 → 正常 |
| `test_force_close_bypasses_the_guard` | `force_close=true` 才真的关 |
| `test_close_without_truncation_still_works` | 不截断时 close 正常（不破坏既有用法） |
| `test_result_still_readable_after_close` | 关闭后读到 `source="db"` |
| `test_persisted_full_text_is_readable` | 落库保留全文 |
| `test_unknown_agent_still_raises` | 完全不存在的 id 仍报错 |
| `test_default_max_chars_matches_budget_layer` | 默认值与预算层对齐 ≥ 50000 |

### 5.2 反向确认（变异测试，两条都变红）

| 变异 | 结果 |
|---|---|
| 把 `if truncated and close and not force_close:` 改成 `if False:` | `test_refuses_close_when_result_truncated` 红（`DID NOT RAISE`） |
| 删掉落库回落分支 | `test_result_still_readable_after_close` / `test_persisted_full_text_is_readable` 红，错误正是 **`KeyError: 未知的 GA 会话`** |

### 5.3 真实环境复现（真 GA，非 mock）

用真实 GenericAgent 跑一次 7864 字符的长输出：

```text
[规则1] ga_result(close=true, max_chars=1000) 应被拒绝
  ✅ 已拒绝：拒绝关闭：结果会被截断到 1000 字符，而全文 7864 字符…
  会话仍在内存: True

[正常路径] 用默认上限读完，再关闭
  读到 7864 字符，truncated=None，closed=True

[规则2] 关闭后再读，应返回 source=db 而不是 KeyError
  ✅ source=db，读回 7864 字符
  内容一致（前200字符）: True
```

数据库确认：`ga_runs` 48 行，`ga_bb5965ed` 的 `result_text` 与 `full_text` 均为 7864 字符。

### 5.4 回归

全量 `backend/tests`：**647 passed, 4 skipped**。

两个既有用例按新默认值更新（`test_result_close_flag`、
`test_result_close_string_false_is_false`）：`max_chars` 20000 → 50000，
并补上 `force_close: False`。

## 6. 顺带发现（未修，留作后续）

`close_all()` 在 manager 销毁时直接 `_entries.clear()`，**不落库**。
这意味着轮次结束时仍然在跑的 GA 会话，其结果不会进 `ga_runs`。

本次修复只覆盖「显式 `ga_result(close=true)`」这条路径，
因为事故就发生在这里。要不要让 `close_all()` 也落库，需要单独评估
（涉及每轮多写 N 条记录的成本）。

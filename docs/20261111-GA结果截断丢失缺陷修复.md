# GA 结果截断丢失缺陷：根因与修复

> 日期：2026-11-11　状态：**已修复并真实环境验证**
> 现场：session `co_fa983ab2eef1`，agent_id `ga_c6a3683f`（用户查「金妍儿」）

## 1. 现象

用户让 GA 查金妍儿资料，模型拿到了结果但**只读到一半**，之后想补读全文时报错。

模型自己的反思：

> 「GA 的最终答复在我读取时被截断，而且我那次调用同时关闭了会话，没拿到全文」

## 2. 现场复原（数据库实读）

两次 `ga_result` 调用：

| 次序 | 参数 | 返回长度 | 结果 |
|---|---|---|---|
| 第 1 次 | `full=true, max_chars=8000, **close=true**` | 8898 | 截断到 8000（全文 **13223**），**会话被销毁** |
| 第 2 次 | `max_chars=14500`（想读全文） | **43** | `[工具执行错误] KeyError: 未知的 GA 会话: ga_c6a3683f` |

## 3. 根因：不是 max_chars 太小

**上调 `max_chars` 解决不了这个问题**，理由是：

1. `max_chars` 是**模型自己填的参数**，不是配置上限——它第一次自己填了 8000；
2. 真正的破坏来自 `close=true` 与 `truncated=true` **同时发生**：
   ```python
   if close:
       await self._close_session(agent_id)   # 内存记录直接删掉
   ```
3. GA 结果**从未落库**，`_close_session()` 只做 `_stop_entry` + `session.close()`，
   `_entries.pop()` 之后数据永久消失。

所以第二次调用的 43 字符错误就是证明：**问题不在上限，而在数据已经不存在**。

## 4. 修复（三条）

### 4.1 规则 1：截断与关闭互斥

```python
truncated = bool(limit and len(text) > limit)
if truncated and close and not force_close:
    raise ValueError(
        f"拒绝关闭：结果会被截断到 {limit} 字符，而全文 {len(text)} 字符。"
        "关闭会永久销毁未读部分。请先调大 max_chars（或传 full=true）读完，"
        "再单独用 ga_result(close=true) 关闭；确实要丢弃剩余部分就传 force_close=true。"
    )
```

逃生口 `force_close=true` 只给「明确知道剩余可丢弃」的场景用。

### 4.2 规则 2：结果落库，关闭后仍可读

新增 `backend/app/acp/store.py` + `ga_runs` 表：

| 字段 | 说明 |
|---|---|
| `agent_id` | 主键 |
| `user_id` / `session_id` / `generation_id` | owner 作用域（便于清理） |
| `status` / `result` / `full_text` | 会话终态与两份文本 |
| `tool_calls` / `prompts` / `stop_reason` | 记账 |
| `updated_at` | 时间戳 |

接进 manager：

- `_close_session()` 在销毁前先落库（**先写再删**，落库失败也照常关闭）；
- `result()` 查不到内存会话时回落到 `_load_persisted()`，返回 `source="db"`。

### 4.3 默认上限 20000 → 50000

与 `tool_budget.DEFAULT_MAX_RESULT_CHARS` 对齐。原值太小，
导致「明明能读全却读半截」，而且模型看到 `truncated` 时已经不知道全文多长。

## 6. 规则 3：`close_all()` 落库（已补）

**发现**：`close_all()` 在回合收尾时直接 `_entries.clear()`，**不落库**。
于是「回合结束时还没取过结果的 GA 会话」结果随内存一起消失，
下一轮 `ga_result` 只能拿到 `KeyError: 未知的 GA 会话`。

**影响面只在 ACP**，不是所有执行体：

| 执行体 | 结果落库 | 机制 |
|---|---|---|
| subagent（内部子代理） | ✅ | `host.py:314` 在 `finally` 里调 `sub_store.finish_run(...)` |
| teammate | ✅ | 本质是 subagent，走同一条 `_run_child → finish_run` |
| GA（ACP）显式关闭 | ✅ | 规则 2 已修（`_close_session` 先写再删） |
| **GA（ACP）回合收尾** | ⚠️ → ✅ | **本节补上** |

**修复**：`close_all()` 在 `_entries.clear()` **之前**逐条落库：

```python
await self.stop_all()                      # 先让在途 prompt 收敛成终态
entries = list(self._entries.items())
for agent_id, entry in entries:
    try:
        await self._persist_result(agent_id, entry.session.snapshot())
    except Exception as exc:
        logger.warning("GA 结果落库失败（close_all, agent_id=%s）：%s", agent_id, exc)
self._entries.clear()                      # 落库之后才清
```

顺序是关键：先 `stop_all()` 才会得到终态；先落库再 clear 才拿得到快照。

**验证**：

- 单测新增 3 条（`test_close_all_persists_running_session_result` /
  `test_close_all_persists_full_text` / `test_close_all_records_stopped_status`）
- 反向确认：移除这段落库代码 → 3 条全红，报错正是
  `KeyError: 未知的 GA 会话`
- 真实 GA 验证：spawn → 等完成 → **不取结果** → `close_all()` →

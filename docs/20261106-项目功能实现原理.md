# 项目功能实现原理（面向后续 Agent 开发者）

> 摘要：说明 Hlaudz 多用户 Web Agent 的真实运行链路、关键数据结构、隔离边界与扩展约束。
> 日期：2026-11-06
> 基线：`main@ab8dcb5`；本文以当前源码为准，不把历史设计稿当作已实现事实。

## 1. 先建立一张心智图

本项目不是“把 GenericAgent 包一层 FastAPI”，而是把 GenericAgent 中值得保留的机制拆成
可被 Web 服务复用的最小内核：

```text
认证与所有权
  └─ 会话 / 用户配置（模型、MCP、Skill、workspace）
      └─ RuntimeHub：按 (user_id, model_id) 懒加载 UserRuntime
          └─ 本轮 TurnRuntime：基础工具 + MCP + 5 个子代理编排工具
              └─ AgentLoop：模型 → 工具 → 工具结果 → 再模型
                  ├─ session_history：Agent 回放的唯一权威历史
                  ├─ messages：前端展示快照（文本/思考/工具/子代理块）
                  └─ subagent 侧链表：子代理独立过程与结果
```

最重要的两条“分界线”：

1. **控制面与数据面分离**：模型/MCP/Skill/用户配置决定“本轮能做什么”；`session_history`
   决定“模型下一轮看见什么”；`messages` 只决定“用户刷新页面后看见什么”。
2. **进程内运行时与持久化数据分离**：`RuntimeHub`、`AgentLoop`、子代理任务都只在当前进程内；
   SQLite 与文件系统才是跨请求、跨重启仍然存在的事实源。

## 2. 启动装配与请求主链路

### 2.1 进程启动

`backend/app/main.py` 的 lifespan 依次执行：

1. `db.init_db()`：建表、做幂等字段迁移、把上次进程遗留的 `streaming` 展示消息收敛为 `stopped`。
2. `subagent_store.init_tables()`：建立子代理侧链表，并把上次进程遗留的 `running` run 标为
   `errored`（原因记为 `server restart`）。
3. 创建 `RuntimeHub`，初始化共享 `HistoryStore`，放入模块级 `get_hub()` 供路由使用。
4. 关闭时先 `close_all()` 子代理，再关闭所有缓存的 `UserRuntime`。

因此，“重启后子代理任务还能继续跑”不是当前实现承诺；恢复能力只覆盖已经落库的过程与结果。

### 2.2 一次聊天请求

入口是 `POST /api/sessions/{session_id}/messages`，返回 `text/event-stream`：

```text
JWT 鉴权
→ get_session(session_id, user_id) 做所有权校验（越权按 404）
→ 取会话固定模型 sessions.model_id
→ RuntimeHub.get_user_runtime(user_id, model_id)
→ 软线自动压缩 → 硬线裁剪兜底 → 悬挂 tool_call 自愈
→ 写入 user 展示消息与空的 streaming assistant 展示消息
→ 派生本轮 TurnRuntime（挂载子代理宿主）
→ run_agent_stream 读取 session_history，追加本轮 user 文本
→ AgentLoop 调用 LLM 并执行工具
→ 主代理与子代理事件合并成同一条 SSE
→ 按事件顺序累积 assistant blocks，节流写 messages
→ 完成/停止/错误后落最终状态，清理本轮子代理宿主
```

一个容易忽略的顺序是：**压缩发生在把本轮 user 文本追加到 `session_history` 之前**。
软线计算会用 `pending_text=text` 计入本轮输入，但不会先污染历史；随后 `run_agent_stream`
才真正追加 user 消息并持久化。

## 3. Agent 主循环

### 3.1 核心循环

`backend/app/agent_loop.py` 的 `AgentLoop.run_stream()` 是一个显式的异步 while 循环：

```text
读取/接收 history
while turn < max_turns:
    调用 LLM（流式）
    如果用户请求停止 → done(stopped)
    如果没有 tool_calls → 追加 assistant 文本 → 持久化 → done(complete)
    如果有 tool_calls：
        追加 assistant(tool_calls, content, reasoning)
        逐个 dispatch 工具
        把每个结果作为 role=tool 追加
        再进入下一轮模型调用
```

设计上它不是 LangGraph 状态机，也没有隐藏在框架里的节点；每一步都对应源码中的一个显式分支。

### 3.2 LLM 客户端

`llm_client.py` 用 `httpx.AsyncClient` 直接请求模型，兼容两种线协议：

| `wire_api` | 请求地址 | 工具 schema 转换 |
|---|---|---|
| `openai_chat` | `{base_url}/v1/chat/completions`（若 base 已含版本则直接拼） | 原样发送 OpenAI `tools` |
| `openai_responses` | `{base_url}/v1/responses` | 转成 Responses API 的扁平 function 工具结构 |

流式处理会同时收集：

- 普通文本增量（`text_delta`）
- reasoning 增量（`thinking_delta`）
- 工具调用分片（按 index 合并 name/arguments）
- usage（不同协议的 token 字段统一规范化）

`max_retries` 只对“尚未收到任何流式内容”的可重试失败生效（网络错误、408/409/425/429/5xx 等）。
一旦已经收到增量，再丢流就不会自动重发，避免重复文本/重复工具调用的副作用。

### 3.3 工具抽象与自纠

`tools.py` 定义统一的最小工具模型：

```python
Tool(name, description, input_schema, async_callable(args) -> str)
```

`ToolRegistry` 负责：

- 生成模型所需的 OpenAI function schema；
- 按名字查找并 dispatch；
- **永不把异常抛给 AgentLoop**；异常统一转成 `[工具执行错误] ...` 文本回喂模型。

这是 ReAct 式自纠的关键：模型看到的是可读错误，而不是整个 SSE 流被 500 中断。参数校验失败时还会附加
schema 里的可用参数名，降低模型反复猜参数的概率。

### 3.4 悬挂 tool_call 自愈

如果上一轮进程崩溃/工具异常导致历史尾部出现：

```text
assistant(tool_calls=[...])
（缺少对应 tool 结果）
```

下一次请求会在 `sanitize()` 中处理：

- 若缺少的工具都还在当前 registry 中，且其后没有其它非 tool 消息：重放缺失工具，补齐 tool 结果；
- 否则删除那条悬挂 assistant 消息，避免模型服务因 tool_call 无配对结果直接 400。

新工具实现必须保持“一个 tool_call 对应一个 tool 结果”的历史不变量，否则会反复触发自愈分支。

## 4. 上下文持久化

### 4.1 两套数据，各自回答不同问题

| 数据 | 存储 | 回答的问题 | 是否喂给模型 |
|---|---|---|---|
| `session_history` | `session_history.history` JSON | 下一轮模型应该看到什么 | 是 |
| `messages` | `messages` 表 | 用户刷新页面时应该看到什么 | 否 |

`history_store.py` 维护 OpenAI 风格的 `list[dict]`：

```json
{"role":"user","content":"..."}
{"role":"assistant","content":"...","reasoning":"...","tool_calls":[...]}
{"role":"tool","tool_call_id":"...","name":"...","content":"..."}
```

`session_history` 每个 session 一行，使用 JSON 整体保存。`append()` 与 `set()` 都用 **session 级
asyncio.Lock** 串行化写入，避免同一会话的并发写覆盖；但不同会话之间没有全局锁。

`messages` 表保存展示块 `blocks`。当前块的类型包括：`text`、`reasoning`、`tool`、`chart`、
`summary`、`subagent`。`chat.py` 按真实事件顺序累积这些块，并做约 250ms 的节流快照写入；
停止或结束时强制落最终快照。

### 4.2 为什么不能只留一套

如果只留 `messages`：工具结果、assistant tool_calls、压缩摘要与精确回放格式会混进展示逻辑，
前端字段变化会反向破坏模型上下文。

如果只留 `session_history`：刷新页面会丢失可视化工具卡片、图表规格、子代理执行过程和“思考到一半”
的展示状态，且无法区分消息是完整/停止/错误。

因此必须维持“双轨”，但要让二者通过事件流同步推进；任何只更新其中一套的新功能都需要明确另一个视图如何投影。

## 5. 上下文压缩

### 5.1 三道防线

压缩实现在 `compaction.py`，只在一次新请求开始前或用户手动触发时执行：

| 防线 | 触发 | 方法 | 失败策略 |
|---|---|---|---|
| 自动软线 | 估算 token 超过 `auto_compact_tokens`（默认上下文 90%） | 调 LLM 把较早消息摘要成一条，保留近段 | 摘要失败则不压缩，继续原历史 |
| 硬线 | 仍超过 `hard_limit_tokens`（默认上下文 95%） | 不调 LLM，直接丢最旧消息 | 最少保留最近消息与一条裁剪提示 |
| 手动 | `POST /sessions/{id}/compact` | 可按补充要求生成摘要，默认保留最近 6 条 | 返回 `compacted:false` 与原因 |

注意软线与硬线是依次判断的：软线成功后会重新生成较低 token 的历史；硬线再检查是否仍超线。

### 5.2 摘要后的历史形状

摘要不是额外的 metadata，而是一条真正的 `role=user` 历史消息：

```json
{
  "role": "user",
  "content": "[上下文摘要（较早对话已压缩，trigger=auto）]\n...",
  "_source": "summarization",
  "id": "summary_..."
}
```

然后拼接保留的近期消息。硬线裁剪则放一条 `_source: "hard_trim"` 的 user 提示。

用户可见的摘要另写一条 `role=system`、`blocks=[{"type":"summary",...}]` 的展示消息；它**不进入**
`session_history`。前端刷新时会从消息历史中提取 summary 块，附加到当前 assistant 消息前显示。

### 5.3 必须保护的 tool 配对

`_safe_keep_from()` 会把保留起点向前移动，避免保留段从 `role=tool` 开始：

```text
assistant(tool_calls)   ← 若被摘要掉
tool(result)            ← 保留段孤立开头 → 非法历史
```

压缩任何新消息类型时也要维持这一配对不变量。硬线与软线都会保留最近消息；不要为了省 token 把
assistant tool_calls 与其 tool 结果拆散。

### 5.4 当前限制

- token 数是 `tokens.py` 的 CJK-aware 估算，不是模型 tokenizer 的精确计数。
- 摘要调用复用当前用户的同一个 `LLMClient`；摘要本身失败不会中断本轮对话。
- 摘要会丢失原消息的精确结构；工具调用链在较早历史中被压缩后不可回放。

## 6. 模型切换

### 6.1 选择顺序

`build_user_model()` 的优先级是：

```text
会话指定且可用的 LLM 配置
→ 用户默认配置（is_default=1）
→ 用户最早创建的可用配置（并自愈为默认）
→ 仓库内可选 llm.yaml 兜底
→ 都没有则 SSE error，提示去设置模型
```

“可用”要求同时具备 `api_key + model + base_url`。

### 6.2 会话级固定与 Runtime 缓存

- 新会话创建时会把默认模型 id 写入 `sessions.model_id`。
- 顶栏切换模型会 PATCH 会话；当前会话之后使用新的 `model_id`。
- `RuntimeHub` 的键是 `(user_id, model_id or "")`，因此同一用户的不同模型有独立
  `LLMClient + MCP 连接 + ToolRegistry + AgentLoop`。
- 修改 LLM/MCP 配置后会调用 `hub.invalidate(user_id)`，关闭该用户全部缓存 Runtime，
  下一次请求按新配置重建。
- 修改 Skill 只影响 system prompt 清单；用户私有 Skill 变更也只 invalidate 该用户。
- 导入公用 Skill 影响所有用户，调用 `hub.invalidate_all()`；已运行中的生成不会被强杀，
  但下一轮/下一次 Runtime 构建才会看到新技能。

这也解释了一个常见疑问：“公用技能导入后不会主动让已在运行的用户 Runtime 失效”是什么意思？
Runtime 的 system prompt 是在构建时拼好的；已经构建好的 Runtime 持有旧 prompt。导入后清掉缓存，
可保证下一次取 Runtime 时重建；若某个请求正在进行，它仍使用本轮已经拿到的旧 Runtime 直到本轮结束。

### 6.3 Runtime 重建的代价

重建会重新连接所有启用的 MCP server。`MCP_CONNECT_TIMEOUT` 默认 12 秒、逐个串行连接；
修改模型配置会造成下一次聊天首 token 延迟上升。后续若要优化，优先做 MCP 连接池或并发连接，
而不是让 Runtime 永久不失效。

## 7. MCP 接入

### 7.1 配置与规范化

`mcp_config.py` 接受标准 `mcp.json`：

```json
{
  "mcpServers": {
    "score": {"type": "http", "url": "http://127.0.0.1:8765/mcp"},
    "local": {"type": "stdio", "command": "npx", "args": ["-y", "pkg"], "env": {"KEY": "V"}}
  }
}
```

支持 `http / sse / stdio`。导入采用按 name upsert 的增量合并，不清空其它既有服务器；每个用户的
`user_mcp_servers` 表按 `user_id` 隔离。内部还支持 `builtin_demo`，这是仓库自带示例 server 的
特殊 transport，不应与外部标准 mcp.json 混为一谈。

### 7.2 连接、聚合与降级

`build_user_toolset(user_id)`：

1. 读取该用户所有 `enabled` server；
2. 每个 server 用 `fastmcp.Client` 连接并 `list_tools()`；
3. 单个 server 连接/发现失败则关闭该 toolset 并跳过，其它 server 继续；
4. 成功连接的工具通过 `MCPToolset.merge()` 聚合成一个父 toolset；
5. 用户没有配置 server 或全部失败时，回退到仓库内置 demo MCP。

MCP 工具在发现后会被包装成同一套自研 `Tool`，所以主循环不区分“内置工具”和“MCP 工具”。

### 7.3 工具优先级与错误语义

`UserRuntime.build()` 先注册全部内置工具，再把 MCP 工具中与内置工具同名的项过滤掉：

```text
builtin wins over MCP
```

这是硬性设计：任何 MCP 都不能遮蔽 `file_write`、`code_run`、`load_skill` 等安全边界工具。

MCP 调用异常由 `_call_tool_safe()` 捕获后返回 `[工具执行错误] ...` 文本；参数校验失败时会附上
schema 可用参数。连接失败则表现为该 server 的工具整体不存在，而不是每轮聊天报错。

### 7.4 生命周期与刷新

MCP 连接属于 `UserRuntime`，随 Runtime 创建/关闭。任何 MCP 配置的增删改都会
`hub.invalidate(user_id)`，下一次聊天重新发现工具。当前不支持热更新单个 server 而不重建 Runtime，
也不支持跨实例共享 MCP session。

## 8. Skill 接入

### 8.1 三层可见性

Skill 是文件系统目录，不是数据库条目：

```text
backend/skills_builtin/<name>/SKILL.md     # 只读内置，所有用户
backend/skills_shared/<name>/SKILL.md      # 只读公用，所有用户
backend/data/skills/<user_id>/<name>/...   # 用户私有，可读写
```

优先级从低到高：`builtin → shared → user`。同名用户 Skill 会覆盖公用/内置 Skill；只读层不能通过 API
修改或删除。Skill 名称经过正则校验，路径 resolve 后必须仍位于对应根目录。

### 8.2 渐进披露

模型 system prompt 只注入 L1 清单：

```text
[Available Skills]
- skill-name: 一行描述
```

正文不直接塞入 system prompt。模型命中任务时调用 `load_skill(name, args)`，该工具返回：

- Skill 名称、来源、基础目录；
- 展开 `${SKILL_DIR}` / `$ARGUMENTS` 后的完整正文；
- 可选的 `allowed_tools` 元数据。

`build_skill_prompt()` 对清单有 8000 字符预算，描述会压缩到约 250 字符；这是“15 万字符包袱”之后
避免把所有 Skill 正文塞进上下文的关键。

### 8.3 目录包导入

用户可上传 zip，`_safe_extract_zip()` 会防：

- 绝对路径与 `..` 穿越；
- symlink 成员；
- 解压炸弹（压缩/解压大小上限、文件数上限）；
- 多 Skill 同名冲突（默认报错，`overwrite=true` 才覆盖）。

导入后用户私有 Skill 会 invalidate 该用户 Runtime；公用 Skill 仅管理员可导入，并 invalidate 全量 Runtime。
Skill 目录内的脚本/参考文件不会自动执行，只有模型通过 `file_read`/`code_run` 等工具使用它们时才会发生动作。

### 8.4 文件工具读取 Skill

可见 Skill 目录被加入 `safe_read_roots()`，所以 `file_read` 能读 Skill 附带的 reference/script；
但 `file_write` 的根仍只有用户 workspace，不能改公用/内置 Skill。用户私有 Skill 目录也由 API 管理，
不是 `file_write` 的默认写根。

## 9. 用户隔离与 workspace

### 9.1 所有权过滤

所有会话与配置 DAO 都把 `user_id` 带进 SQL 条件：

```text
get_session(session_id, user_id)
delete_session(session_id, user_id)
list_messages 前先校验 session 属于当前 user
```

越权 id 的结果与不存在相同，路由返回 404。子代理侧链额外有 `(session_id, user_id)` 双重过滤。

### 9.2 文件系统布局

```text
backend/data/workspaces/<user_id>/          # 用户读写根
backend/data/workspaces/<user_id>/.tmp/     # code_run 临时目录
backend/data/workspaces/<user_id>/.subagents/<session>/<agent>/  # 子代理写根
backend/data/skills/<user_id>/              # 用户 Skill
```

`workspace.py` 的所有路径解析都先 `resolve()`，再用 `Path.relative_to` 等价逻辑确认仍在允许根内。
`file_read` 可读 workspace + Skill 根；`file_write` / `file_patch` 只能写 workspace（或子代理子根）。

### 9.3 code_run 的真实边界

`code_run` 是“受控子进程”，不是 OS 级安全沙箱：

- 进程 cwd 固定在用户 workspace；
- Python 通过 audit hook 拦截越界写文件、重命名、链接等；
- 环境变量把 `TMP/TEMP/TMPDIR` 指到 workspace/.tmp；
- 超时 1–600 秒，输出截断到 20000 字符；
- 明确拦截含 `frontend/dist` / `frontend/src` 的代码。

其中 Python 分支有进程内 audit hook；PowerShell / Bash 分支只继承 cwd、超时与输出限制，
**没有等价的写入审计**。因此当前 `code_run` 只能视为“降低误操作的受控执行”，不能视为
不可信代码隔离。生产级多租户必须依赖容器、独立系统账户、seccomp/AppArmor 或等价 OS 隔离。

## 10. Subagent（子代理）

### 10.1 为什么是“本轮派生 Runtime”

主 `UserRuntime` 按 `(user_id, model_id)` 缓存，可以跨 session/跨轮复用；但子代理宿主必须知道自己属于
哪一次 session、哪一条用户消息、哪一代生成。因此 `subagent/session.py` 在每轮请求中派生 `TurnRuntime`：

```text
UserRuntime（缓存）
  ├─ model.client / model_name / store        # 复用
  ├─ registry（builtin + MCP）
  └─ AgentLoop（基础）
       ↓ 每轮派生
TurnRuntime
  ├─ registry = builtin + 非同名 MCP + 5 个编排工具
  ├─ AgentLoop(同一 client, 派生 registry, 基础 system_prompt)
  ├─ EventBuffer
  └─ SubagentHost
```

这样避免把 session/generation 状态塞进跨会话缓存对象。

### 10.2 五个编排工具

只有 root agent 的本轮 registry 会注入：

| 工具 | 作用 |
|---|---|
| `spawn_agent` | 创建子代理并启动 asyncio 任务 |
| `wait_agent` | 等待目标完成，支持 `event / all_terminal / result_available` 条件与超时 |
| `read_agent_result` | 读取已终止子代理的最终文本结果 |
| `list_agents` | 列出本会话本轮子代理花名册 |
| `close_agent` | 停止并释放槽位，可级联关闭 |

子代理的 registry **根本不存在**这些工具，因此不能递归派生；prompt 里的“不要派生子代理”只是行为提示，
真正的硬边界是 schema 中没有对应工具。

### 10.3 子代理能力与继承

`SubagentRuntime.build()`：

- 复用父 `LLMClient`，不额外建连接池；
- 用父 `UserRuntime.registry` 的全部业务工具（文件、code_run、Skill、MCP）作为上限；
- 用 `build_capability_profile()` 去掉编排工具；
- 用当前用户的 Skill 根目录重建 L1 system prompt；
- 写类内置工具改为 `.subagents/<session_id>/<name>/` 子根，避免并发写同一文件；
- 默认 history 只有一条 user message（`fork_turns=none`），子代理看不到父对话。

`fork_turns=all|recent:N` 的实现读取 `parent._fork_source_history`，但当前主流程没有给 base runtime
设置这个字段。因此现阶段实际效果仍是“不继承父对话”；这是后续需要接线的明确缺口，而不是已完成能力。

### 10.4 生命周期、并发与停止

`SubagentHost` 每个 session/generation 一个实例；`SubagentRegistry` 默认：

- 最大深度 2（当前因不能递归，实际主要是未来 team 预留）；
- 每个 host 同时存活最多 4 个；
- 存活代理重名直接报错，不静默改名；
- 槽位满时先回收最早的已终止节点，再拒绝新 spawn。

用户点停止时，`RuntimeHub.stop_subagent_generation()` 会调用 host 的 `stop_all()`，把停止信号与
`asyncio.Task.cancel()` 同时施加到所有子代理。主循环结束时 `chat.py` 会 `host.close_all()`，
因此**主 agent 不等子代理就结束**时，子代理会被收尾停止；父 agent 必须显式 `wait_agent`。

`wait_agent` 的超时不等于失败：子代理继续跑，返回 `remaining_targets`，模型应继续等待而不是重复 spawn。

### 10.5 持久化与事件

子代理不使用主 `session_history`，而是侧链表：

```text
subagent_runs     一次 run 的元数据、任务、状态、最终结果
subagent_messages run_id + seq + message JSON 的增量侧链
```

`subagent_runs` 在启动时把上轮遗留的 running 收敛为 errored。当前没有面向用户的侧链读取 API；
结果主要通过 SSE 的 `subagent_end` 与展示块返回，重启后可从 run 表取最终结果，但需要后续补接口。

事件传播：

- 子代理内部同样运行 `AgentLoop`，产生 `text_delta / thinking_delta / tool_start / tool_result`；
- `SubagentHost._publish()` 把这些事件标成 `subagent_event` 放进同一 EventBuffer；
- `chat.py` 的 `_merged_events()` 把主代理生成器与子代理缓冲汇入同一个 asyncio.Queue；
- 前端按 `agent_id` 更新可折叠 `SubagentCard`，最终用 `subagent_end` 写入结果与状态。

在“同一队列单点消费”的意义上顺序是稳定的；但它不是一个全局事件溯源总线，跨进程/重连不会恢复
已经丢失的增量事件。`event_seq` 只存在内存环形缓冲（每节点最多 2000 条），重启即失效。

### 10.6 当前限制

- 子代理没有独立压缩：`AgentLoop(history_store=None)` 不触发 `enforce_soft_limit`，长任务可能触模型窗口。
- 子代理没有独立模型选择：统一继承父 Runtime 的模型。
- 子代理结果以最终 assistant 文本为准，不把完整侧链自动并入主上下文。
- 同名子代理在终止后可复用，但写根仍按名字命名，旧产物可能与新一轮同名任务混在一起。
- 子代理任务只在当前进程内；服务重启会中断，侧链表能保留已完成结果，但不能继续运行。

## 11. SSE 事件与前端投影

### 11.1 后端事件

`AgentLoop` 产生内部事件；`sse.py` 补上 artifact 检测；`chat.py` 再映射成前端协议：

| SSE 事件 | 关键字段 | 用途 |
|---|---|---|
| `message_start` | `message_id` | 绑定本轮 assistant 展示消息 |
| `text_delta` | `text` | 追加正文块 |
| `thinking_delta` | `text` | 追加 reasoning 块 |
| `tool_start` | `id, name, input` | 插入工具步骤 |
| `tool_result` | `id, name, content, is_error` | 回填工具结果 |
| `chart` | `spec` | 自描述 artifact 渲染 |
| `compaction` | 压缩统计 | 压缩提示 |
| `healed` | `repaired` | 悬空 tool_call 已修复 |
| `subagent_start/event/end` | `agent_id` 等 | 子代理卡片 |
| `team_event` | `event` | Team 任务/消息/事件（含 `team_unavailable`） |
| `done` | `message_id, status, model` | 终态 |
| `error` | `error` | 错误提示与错误状态 |

`tool_input / chart` 等历史文档里可能出现的名字要以当前 `sse.py` / `chat.py` 为准；前端 `types.ts`
是 SSE 契约的单一 TypeScript 定义。

### 11.2 图表 artifact

`detect_artifacts()` 不依赖具体工具名。只要工具输出是形如：

```json
{"type": "chart", "spec": {...}}
```

或者 MCP 的 `content[].text` 包装里出现该对象，就额外发出 `chart` 事件。新增 artifact 类型时，
应同时更新 `_ARTIFACT_TYPES`、后端投影和前端渲染组件。

### 11.3 停止与部分内容

停止流程分两层：

1. `AgentLoop` 检测 stop_event，尽快在模型流/工具循环边界结束；
2. `chat.py` 对已累积的 `blocks` 强制落库，`stop` 端点短等最多约 1.2 秒，返回已持久化的消息快照。

前端收到 abort 后不会立刻清空本地内容；它会等后端快照再合并刷新，因此“已经显示的内容”不会因停止
直接消失。展示快照与 `session_history` 的落点不同：如果模型在工具调用中途被取消，历史尾部可能出现
不完整状态，下一轮由 `sanitize()` 修复。

## 12. 多用户身份与运行时隔离

### 12.1 身份来源

认证使用 JWT access token + HttpOnly refresh cookie。`get_current_user()` 每次都从 DB 读取用户状态与
`token_ver`，不是只信任 JWT 里的 id；因此封禁/版本失效能立即生效。

所有需要用户上下文的调用都必须通过 `AgentContext` 或显式 `user_id` 传递：

- `AgentContext` 冻结保存 user/session/message/generation/agent/parent/depth；
- `build_builtin_tools(user_id)` 把用户身份闭包进文件工具；
- MCP/Skill/LLM 配置查询都从 `user_id` 出发；
- 子代理从父 context 派生，不读环境变量或模块级“当前用户”。

不要新增一个“全局 current_user”或从进程环境推断租户的实现，否则会在并发请求中串用户。

### 12.2 进程内状态

`RuntimeHub` 当前是单进程内存字典；`_stop_events` 也是进程内。它适合当前单副本部署，
但意味着：

- 不能靠增加 uvicorn worker 共享 Runtime 或停止信号；
- 停止请求必须落到持有该生成任务的同一进程；
- `SUBAGENT_MAX_ACTIVE` 是每 host 上限，不是全局配额；
- 进程重启会丢失运行中的生成与子代理事件。

若未来横向扩容，应把停止信号、事件流与会话租约改为 Redis/DB 等共享机制，或做 sticky session。

## 13. 扩展时必须守住的不变量

1. **不改双轨职责**：`session_history` 只放模型可回放消息；`messages` 只放展示快照。
2. **tool_call 必须配对 tool 结果**，压缩/裁剪/停止/自愈都不能产生孤立 tool 消息。
3. **内置工具优先**：任何 MCP/第三方工具都不得遮蔽 `file_*`、`code_run`、`load_skill`。
4. **权限靠 registry 闭世界表达**，不要只靠 prompt。子代理没有编排工具是结构约束，不是角色提示。
5. **用户身份显式传递**：新增工具、存储、事件、子代理能力都必须带 user_id，不能从全局取。
6. **Runtime 变更走 invalidate**：修改模型/MCP/Skill 配置后，必须让下一次取 Runtime 看到新配置。
7. **长输出有界**：工具输出、子代理结果、Skill 清单、read 内容都应有字符/条目预算。
8. **错误回喂而不是穿透**：普通工具异常转成可读观察；只有真正无法继续的 LLM/运行时错误才发 SSE error。
9. **停止要级联**：主代理停止必须同时停止子代理，避免后台继续花模型费用。
10. **安全边界诚实标注**：`code_run` 当前不是 OS 沙箱，不能宣称多租户强隔离。

## 18. Agent Team（P3，当前实现）

### 18.1 每轮一个隔离 Team

`build_turn_runtime()` 在每轮生成开始时生成服务端 `team_id`（`team_<uuid12>`），
`turn.team_id` 与 `TeamScope` 一起注入本轮 registry。模型只能操作本 scope 内的任务、消息，
**不能传 `team_id` 越权**；工具参数里出现的 id 只作为任务/消息 id 使用。

Team 是可选协作面：`prepare_turn_team()` 创建失败时释放已获取的生命周期租约，
发一条 `team_event{type:"team_unavailable"}`，普通子代理与对话链路继续工作。

### 18.2 四级作用域

`scope.py` 固定了四级身份：

```text
user_id -> session_id -> generation_id -> team_id
```

- `AgentScope`：root / lead / teammate 的统一身份，子代理从父 scope 派生；
- `TeamScope`：Team 工具、任务板、消息、事件的查询键；
- `RuntimeHub._subagent_hosts` 的 key 也包含 `user_id`，防止猜 `session/generation` 影响他人。

### 18.3 持久化表

`team_store.py` 在同一个 `app.db` 中建表（幂等）：

| 表 | 用途 |
|---|---|
| `team_runs` | 团队生命周期：generation/team、状态、lead agent |
| `team_tasks` | 持久任务板：状态、owner、`version`（CAS）、`blocked_by` 依赖 |
| `team_task_deps` | 任务依赖边 |
| `team_messages` | 团队消息（note/result/request，收件人隔离） |
| `team_events` | 单调 `event_seq` 的团队事件流（增量恢复） |
| `session_generations` | 每会话 active generation 唯一租约 |

启动时 `init_tables()` + `recover_stale_runtime("server restart")` 把上次进程遗留的 active 租约收敛掉，
否则一条陈旧行会永久阻塞该会话。

### 18.4 工具与能力边界

- **lead（root）**：`team_status / task_create / task_get / task_list / task_update / send_message / list_messages / spawn_teammate`（8 个）。
- **teammate**：`task_get / task_list / task_update / send_message / list_messages`（5 个）。
  管理类工具在 teammate 的 registry 里**根本不存在**，这是结构约束，不是 prompt 约束。
- `task_update` 必须带 `expected_version`（CAS），动作 `claim / complete / reclaim`；
  `spawn_teammate` 可绑定 `team_task_id + expected_version`，失败会回收任务。
- `spawn_teammate` 底层复用 `SubagentHost.spawn(..., role="teammate")`，因此 teammate 继承父代理的
  业务工具（file / code_run / Skill / MCP），但不能递归 spawn。

### 18.5 生命周期、跨轮恢复与停止

1. **生命周期租约**：`TeamHost.acquire_lifecycle()` 拿到 Team 配额；`release_lifecycle_now()` 是同步释放，
   在 `chat.py` 的取消安全清理里先执行，避免 anyio cancel scope 跳过 await 造成配额泄漏。
2. **跨轮恢复**：`team_resume.copy_resume_taskboard()` 在新 generation 开始时复制上一轮未完成任务板，
   发 `team_resumed` 事件，前端用快照替换旧任务板。
3. **停止级联**：主 stop → `request_stop` + `cancel_generation` → `hub.stop_subagent_generation()`
   → `process_registry.stop_generation()`（`code_run` 子进程）→ Team `converge_generation_facts(status="stopped")`。
4. **陈旧租约自愈**：`session_generations` 只是 DB 事实，是否真活着以进程内
   `_generation_tasks / _stop_events / _generation_reservations` 为准。读到 active 但进程内无 live task 时，
   自动 `converge_generation_facts(..., status="stale")` 后再允许新一轮。

### 18.6 容量闸门

`quota.py` 是四层 `asyncio.Semaphore`，顺序固定 `global -> user -> team -> agent`：

- Team：`GLOBAL_MAX_ACTIVE_TEAMS / USER_MAX_ACTIVE_TEAMS / SESSION_MAX_ACTIVE_TEAMS`；
- 子代理：`GLOBAL/USER/TEAM_MAX_ACTIVE_SUBAGENTS`；
- `code_run`：`GLOBAL/USER_MAX_CODE_RUNS`；
- MCP 调用：`GLOBAL/USER_MAX_MCP_CALLS`。

超时拿不到配额抛 `QuotaExceeded`；所有 lease 必须在 `finally` 释放。配额是**进程内**的，
与单副本部署假设一致。

### 18.7 前端投影

`TeamPanel` 消费同一条 SSE 里的 `team_event`：`team_start / task_created / task_updated /
team_message / team_end / team_resumed / team_unavailable`。刷新后 `GET /api/sessions/{id}/team` 返回完整快照；
`GET .../team/events?since_seq=` 支持增量补齐。面板展开状态按 `user_id` 存 `localStorage`，
且「展开壳」与「数据」解耦，不会因为暂无 Team 而反复收起。

## 19. 文件下载与工作区面板

### 19.1 三个端点

`routers/workspace_files.py` 只做下载，不做内联图片：

| 端点 | 作用 |
|---|---|
| `GET /api/me/workspace-file?path=&inline=` | 单文件下载；默认 attachment，`inline=1` 仅 MIME 白名单 |
| `GET /api/me/workspace-files?path=&depth=&limit=&include_hidden=` | 目录列表（目录优先、软链跳过、截断标记） |
| `POST /api/me/workspace-zip` | 多选打包 zip（数量/大小上限、条目名去重去 `..`） |

### 19.2 安全边界

1. 只解析 `backend/data/workspaces/<user_id>/`，不开放 Skill 目录；
2. `normalize_workspace_path` + `resolve()` + 包含关系校验，阻断 `..`、绝对路径越界、软链逃逸；
3. 非白名单类型一律 `attachment` + `nosniff`，HTML/SVG 不会以页面形式执行；
4. zip 条目名剥离 `/`、`..`，重名自动追加序号；
5. 图片仍走 `routers/media.py` 的 `/api/me/workspace-image`，与下载职责分开。

### 19.3 前端三个入口

- Markdown 本地文件链接 → `FileChip`（鉴权下载，失败内联提示）；
- `file_write / file_patch` 步骤行 →「下载」；`code_run` 步骤行 →「文件」；
- 顶栏「文件」→ `WorkspacePanel`（面包屑、目录浏览、单文件下载、多选打包、隐藏项标注）。

路径判定与请求封装集中在 `frontend/src/files.ts`，`MarkdownImage` 与 `FileChip` 共用同一套
`isWorkspaceLocal / isWorkspaceImage` 规则，避免「图片能显示但文件不能下载」的割裂。

## 20. 运行守卫与进程登记

### 20.1 `run_guard.py`

`code_run` 在 Linux/macOS 与 Windows 上共用同一个 Python 运行器：先安装 `sys.addaudithook`，
再 `runpy.run_path()`。审计钩子拦截 `open` 写模式、`os.mkdir/remove/rename/link/symlink` 等，
任何解析后落在 workspace 之外的路径都抛 `PermissionError`。同时：

- 代码文本里出现 `frontend/dist` / `frontend/src` 直接拒绝；
- `TMP/TEMP/TMPDIR` 固定到 `<workspace>/.tmp`；
- 这是**轻量防御层**，不是 OS 沙箱。

### 20.2 `process_registry.py`

按 `(user_id, session_id, generation_id)` 登记活跃 `code_run` 进程，停止时按 scope 级联 `kill`。
Windows 上 uvicorn `--reload` 会创建 `SelectorEventLoop`，其子进程 API 未实现；这里用
`_ThreadProcess` 包装 `subprocess.Popen`，保持 `pid/returncode/kill/communicate/wait` 同形接口，
再用 `taskkill /T /F` 杀进程树。

### 20.3 与停止链路的关系

`chat.py` 的 stop 端点依次执行：

```text
request_stop() -> cancel_generation() -> hub.stop_subagent_generation()
              -> process_registry.stop_generation() -> converge/release generation lease
```

即使 hub 不可用或 generation_id 缺失，`code_run` 清理也不会被跳过。

## 1. 设计上改掉的一处（相对设计文档）

设计文档 §4.2 写的是「sync 用**已落库快照** + 从 `blocks_seq` 补增量」。实现时否掉了它。

**问题**：`_persist` 有 250ms 节流，落库快照必然落后于 `blocks`。若缓冲恰好在这期间
把 `blocks_seq` 之后的帧挤掉，快照与缓冲之间就有一个**填不上的洞**（设计文档 §8.0 ②
记过这个隐患，当时的解法是「发 sync 前先强制持久化」）。

**更好的解法**：直接持有 `_event_stream` 里那个就地 append 的 `blocks` 列表引用，sync 时
序列化「此刻」的全部状态，`id` 也取「此刻」的 seq。两者出自同一个同步点，
**不存在落后，也就不存在洞**。于是：

- 「强制持久化」这一步整个不需要了；
- 缓冲淘汰变得自由 —— 任何 `after` 太老的客户端一律收到整份快照，永远正确。

代价是每次 sync 一次浅拷贝 `[dict(b) for b in blocks]`，但 `json.dumps` 在事件循环里
同步跑完，不存在「序列化到一半被别的协程改了」。这是净简化。

### 2.1 seq 由 job 拥有，不由 `_event_stream` 拥有

`_event_stream` 自己的编号**不连续**：`healed`（`chat.py:530`）与早退 error 走的是
**不带 id** 的 `sse_frame`。而续看游标必须单调、无洞、且与缓冲键一致。

所以 `TurnJob.publish()` 把任何帧的 `id:` 换成自己的 seq（没有就补一行）。
`test_seq_is_owned_by_job_and_contiguous` 钉住：外部给的 `id: 999` 会被覆盖成 `id: 2`。

### 2.2 `_event_stream` 的 `job` 参数必须可选

A2A 直接调 `chat._event_stream`（`a2a/service.py:193`），不传 job。
参数默认 `None`，为 `None` 时行为与阶段 1 完全一致。A2A 28/28 + 11/11 全绿证明没破坏它。

## 4. 三个只有真机能抓到的缺陷

### 4.1 R-2 第一版是假通过

第一版 R-2 断言「`after=0` 时收到 sync」。真机跑完显示 **0 个 sync 帧**，但测试**通过了**
——因为我的判据写了 `if syncs: ... else: ok = text >= 100`，把「没触发」当成了「走增量也正确」。

那个 else 分支本身说得没错，但**它不是我要验的东西**。要验降级就必须让缓冲溢出。
加法：给 `turn_job` 加上限环境变量，启动器设成 20 帧，确定性地触发。

### 4.2 UI 续看从未发生（真 bug，`messagesRef` 时序）

第一版 UI 测试报 `U-1b 刷新后内容继续增长: 9761 → 9761`。查库发现后端 job 明明还在跑
（streaming，7027 字），前端却没接上。

根因：`loadMessages(activeId).then(() => resumeIfRunning(activeId))`，而
`resumeIfRunning` 读的是 `messagesRef.current`。`loadMessages` 通过 `setMessages`
更新状态，**ref 要等下一次 render 后的 effect 才同步**。于是 `.then()` 里读到的
永远是刷新前的旧列表（空），直接 return —— 续看一次都没发生。

修法：`loadMessages` 返回消息数组，`resumeIfRunning(sid, msgs)` 用**调用方传入的那份**，
不读 ref。

**这个 bug 单测抓不到**（单测不经过 React 的 render 时序），HTTP 探针也抓不到
（探针直接调 `/stream`，不经过前端逻辑）。只有真浏览器 + 刷新才暴露。

### 4.3 测试时序假设错了两次

- 第一版等 6 秒再刷新 → 此时 5000 字已生成完，库里 `complete`，没有可续看的内容；
- 第二版仍然太慢：deepseek-flash 实测几千字只要十几秒。

最终改成「请求 12000 字 + 只等 3.5 秒」，保证刷新时这一轮仍在 streaming。

**教训**：真机测试里任何 `sleep` 都是在假设模型的速度。这类假设必须显式写进注释，
而且优先用「事件驱动」的等待条件（这里退而求其次，用超长请求拉大时间窗口）。

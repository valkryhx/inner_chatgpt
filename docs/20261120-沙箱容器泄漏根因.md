# 沙箱容器越积越多（57 个 running）：既不是「设计了没做」，也不是 Docker 显示问题

日期：2026-11-20
现象：`docker ps` 里 `hlz_sbx_*` 容器 59 个（57 running），
但内存没有明显变化，怀疑是回收机制没生效或者只是显示问题。

## 0. 结论（三个选项都不是）

用户给了三种可能，实测答案是**第四种**：

| 假设 | 实测 | 依据 |
| --- | --- | --- |
| 回收机制「设计了没做」 | ❌ 回收代码**完整实现且真的被启动** | `pool.reap_loop` 由 `manager.start():260` 起为 task |
| 「生效了，只是 Docker 显示问题」 | ❌ 容器**真的在运行**，不是残留记录 | `docker ps` 57 个 `Up`，`sleep infinity` 进程活着 |
| 符合预期 | ❌ 没有一个是有用的 | 58/59 指向**已删除的 pytest 临时目录** |
| **★ 真相：pytest 测试泄漏** | ✅ | 见下 |

**这些容器不是 18080（也不全是 8080）运行的产物，是跑测试留下的垃圾。**

## 1. 最硬的一条证据：容器挂载的宿主路径

```

C:\Users\drago\AppData\Local\Temp\pytest-of-drago\
    pytest-1711\test_write_file_inproc_does_no0\u1:/ws:rw

容器 1 GB 内存限制、`hlz-sandbox:2026-11-18` 镜像，挂的却是
**pytest 的 tmp_path**。58 个容器全部指向 `pytest-of-drago\pytest-NNNN\...`，
每轮 pytest 一个目录、一个容器。

统计（`work/_sbx_leak_verify.py`）：

```
容器总数 59（running 57）
  58  pytest 临时目录（测试残留）
   1  D:\sandbox\u_343a46896bff  ← 唯一一个真的
```

按测试名归因：

```

test_write_file_dispatches_to_0     6
test_write_file_inproc_still_u0     5

全部在 `backend/tests/test_sandbox_service_file_ops.py` 与

## 2. 第二条证据：owner 尾部是宿主机 PID，且 58 个全不相同

`backend/app/sandbox/identity.py:126`：

```python
def _instance_tag() -> str:
    raw = (os.environ.get("HLZ_INSTANCE_ID") or "").strip()
    if raw:
        return _tag_for(raw)
    return str(os.getpid())      # ← 默认走这里
```

容器名 `hlz_sbx_<user>_<owner>`，owner = `<hostname>:<pid>`。
`uniq -d` 检查 58 个 owner：**零重复**。

```
valkry:11248  valkry:12720  valkry:12988  ...  valkry:36884
```

`valkry` 是**宿主机主机名**（`hostname` 实测），而 probe 栈容器自己的
hostname 是容器 ID（`hlzsbxprobe-app-1` → `948f77b1f3e8`）。

⇒ **每个容器来自一个不同的后端进程，没有一个是同一进程复用的第二个用户。**
58 个容器、58 个不同 PID（一一对应），说明这 58 个进程都只建了 1 个容器
就退出了。
正常服务里池是 `max_containers=4`，PID 变化只发生在重启 —— 而这里是
**每跑一次测试就换一个 PID**。

## 3. 为什么回收机制没兜住：三重失效，都是测试路径特有的

### 3.1 `reap_loop` 只在 `manager.start()` 里创建，测试从不调它

```python
# backend/app/sandbox/manager.py:259
if self._reaper is None or self._reaper.done():
    self._reaper = asyncio.create_task(reap_loop(60.0))
```

唯一调用点：`backend/app/main.py:122` `await get_sandbox_manager().start()`。
测试从不经过 `main.py`（grep `.start()` 在 tests 下为 0 命中）。

⇒ **测试跑起来的进程里根本没有回收协程。**

### 3.2 `conftest` 的单例重置把池引用直接丢掉，不销毁

```python
# backend/tests/conftest.py
@pytest.fixture(autouse=True)
def _reset_app_sandbox_singletons():
    def _clear():
        sbx_config._cached = None
        sbx_manager._manager = None      # ← 只置 None，没有 shutdown()
    _clear()
    yield
    _clear()
```

`ContainerPool._entries` 里登记的容器 ID 随 manager 一起被丢弃。
`pool.shutdown()` 明明实现了（`pool.py:157`），但**没有任何人调它**。

⇒ 进程退出时容器没人删，Docker 里就留下来了。

### 3.3 泄漏量按「跑测试的次数」线性增长，与业务无关

`pytest-1711` 说明本机 pytest 的临时目录计数器已到 1711 轮。
58 个容器不是 58 轮全部泄漏 —— 只有命中那几个测例的轮次才泄漏，
其余轮次可能因为没走到 Docker 路径或提前失败。

## 4. 为什么内存看起来没变化（用户的第二个疑问）

每个容器 `docker ps --size` 显示 `4.1kB (virtual 562MB)`：

- **真实写入只有 4.1 kB**（只有几行临时文件）；
- 562 MB 是**镜像层的虚拟大小**，镜像层在宿主机上只有一份，被所有容器共享；
- 主进程是 `sleep infinity`，不跑任何东西。

所以 57 个容器 ≈ 57 × 几 MB 的进程开销（内核结构 + cgroup），
不是 57 × 562 MB。**用户观察到的「内存没大幅变化」是对的，
这也是泄漏能潜伏这么久没被发现的原因。**

但代价真实存在：
- 每个容器占一个 Docker 网络命名空间 / cgroup；
- `docker ps` 输出被污染，真实沙箱容器淹没在 58 个垃圾里；
- 出事时无法从容器列表判断「服务到底开了几个槽」。

## 5. 修法（本轮未实施，先给出方案）

用户当前问的是「为什么」，不是「修」。三条可选，按代价排序：

### A. 测试侧兜底（最低代价，必做）

`conftest` 的 `_clear()` 改成 `await` 一次 `shutdown()`，
或加一个 `session` 级 teardown 统一清。注意 `_clear()` 现在是同步函数，
要改成 async fixture 或在线程里跑。

### B. 给池加 `__del__` / `weakref.finalize`（防御）

`ContainerPool` 被 GC 时尽力销毁登记过的容器。但进程被 kill -9 时仍不生效，
只是「正常退出路径不漏」的补充。

### C. 已有的 `cleanup_orphans(same_machine=True)` 缺一个入口

它写得很完整（`probe.py:87`，含多实例 `live_owners` 保护），
但**只在 `manager.start()` 里被调用，且 `backend != inproc` 时直接 return**
（`manager.py:204-210`）。测试恰好走 inproc，永远不会触发。

最小改动：给一个 pytest 的 `session` teardown 调
`cleanup_orphans(all_owners=False, same_machine=True)`。

## 6. 立即可以做的清理（需用户确认）

58 个容器全部可由 owner 精确识别，删除是安全的：

```bash
# 只删 pytest 临时目录挂载的那些（不碰 D:\sandbox\ 那个真的）
docker ps -a --filter "name=hlz_sbx_" -q | ... # 逐个 inspect 过滤 bind
```

**不建议** `docker container prune` —— 会连 `D:\sandbox\u_343a46896bff`
那个也许还有用的容器一起删。按 bind 路径精确筛选更安全。

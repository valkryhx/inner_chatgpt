# 子代理卡死事故分析：MCP 工具调用无超时（2026-11-19）

> 用户报告：「多实例模式，用 hx / 12345678 登录后【你用2个子agent 搜搜特朗普和普京】为何卡住了？似乎subagent在多实例模式下有问题？」
>
> **结论：subagent 没问题，多实例也不是根因。根因是 `MCP 工具调用链上没有超时`**，
> 一个 MCP server 半死就让整轮生成永久挂住。`subagent` 只是把这个问题
> **放大成「看起来卡住」**（父代理在 `wait_agent` 上等，看不到卡在哪）。

---

## 1. 事故现象

用户让两个子代理并行搜「特朗普」和「普京」。观察到的现象：

| 现象 | 值 |
| --- | --- |
| 父消息 | `msg_850d86c4bccd` `status=streaming`，卡了约 30 分钟 |
| 两个子代理 | `status=running`，`turns=0`，`rounds=0` |
| 子代理侧链 | `subagent_messages` **0 条** |
| 父代理 `wait_agent` | 连续 4 次 `timed_out: true`（240s / 300s / 300s / 240s） |
| 事件游标 | 曾推进到 `event_seq=154`，之后**停住不动** |
| 实例进程 | `State: S (sleeping)`，`/api/health` **20ms** 返回 |
| 最终结局 | 子代理 `timeout: 超过 1800s`（`SUBAGENT_TIMEOUT_S` 默认值）才结束 |

**关键排除项：**

- 不是进程死锁 —— 事件循环健康（health 20ms），主线程 `py-spy` 显示 idle；
- 不是容器内没进程 —— `/proc` 里只有 tini + uvicorn，没有 code_run 子进程；
- 不是 subagent 机制本身 —— `spawn_agent` / `wait_agent` / `list_agents` 全部正常返回；
- 不是多实例粘性问题 —— 会话从头到尾落在同一个实例（`owner=c313894f180e:7`）。

## 2. 定位过程（每一步都是可复算的证据）

### 2.1 先证明「不是 code_run」

第一轮怀疑是 `code_run` 卡住（block 10 的 result 显示 `<没有结果>`）。
但后续重抓 blocks 发现 **block 10 已经有结果了**：

```
[code_run python] exit=0 cwd=D:\sandbox/u_c56b8337dd09
UTC now: 2026-11-19T09:17:49.107189+00:00
```

容器内直接调 `_run_code_impl` 也是 **0.12s** 返回。
反证：`/proc` 里**没有任何 Python 子进程**，根本没走到 `spawn_process`。

### 2.2 再看子代理的 `tool_start` / `tool_result` 配对

取 `subagent` block 的 `events` 字段（这是子代理的事件流）：

```
trump_search  143 个事件，末尾：
  reasoning       ". Let's search."
  tool_start      web_fetch_exa   {urls: ["https://apnews.com/article/trump-xi-putin-..."]}
  tool_start      web_search_exa  {objective: "Get the latest status of the US war with Iran..."}
  tool_start      web_search_exa  {objective: "Find the status of the Supreme Court case..."}
                                          ↑ 三条 tool_start，之后再无 tool_result

putin_search   11 个事件，末尾：
  tool_start      code_run        {...}
  tool_start      web_search_exa  {query: "最后一周围绕普京的重大活动..."}
  tool_start      web_search_exa  {query: "普京在乌克兰战场与和平谈判..."}
                                          ↑ 同样卡在 MCP 工具上
```

**两个子代理都停在 `tool_start` 之后，永远等不到 `tool_result`。**

### 2.3 排除「网络不通」

容器内直连 exa：

```
$ docker exec hlzscale-app-3 python -c "...urllib...https://mcp.exa.ai/mcp"
ERR HTTPError HTTP Error 403: Forbidden 0.69 s     ← GET 403 正常（MCP 要 POST）
```

走完整 MCP 协议调一次 `web_search_exa`：

```
$ python /tmp/probe_mcp_exa.py
error: None
tools: ['web_search_exa', 'web_fetch_exa']
CALL ok 0.9 s -> 'Title: Donald Trump | Breaking News ... AP News...'
```

**新建连接 0.9 秒就成功。** 并发两个也正常（0.86s / 0.85s）。
空闲 120 秒后再调也正常（0.96s）。

所以不是网络、不是 server、不是并发、不是连接自然衰变 ——
是**特定那条连接卡住之后，没有任何机制能把它截断**。

### 2.4 找到根因

```python
# app/mcp_client.py（修复前）
result = await client.call_tool(name, payload)            # ← 裸 await，第 375 行
...
result = await toolset._client.call_tool(name, payload)   # ← 重连后又一次裸 await，第 389 行
```

SDK 的默认值就是**无超时**：

```
fastmcp.Client.call_tool(name, arguments=None, *, timeout: timedelta | float | int | None = None, ...)
mcp.ClientSession.call_tool(name, arguments=None, read_timeout_seconds: timedelta | None = None, ...)
```

`timeout=None` 意味着**永远等**。server 收到请求但不回包时（半死连接、
中间设备吞包、服务端 hang），这个 `await` 永久挂住，协程永不恢复，
`tool_result` 永不发出。

**决定性反证**：同一个仓库的探活路径 `runtime.py:402` **是**包了超时的：

```python
await asyncio.wait_for(child._client.call_tool(tool.name, {}),
                       timeout=_LIVENESS_TIMEOUT_S)     # _LIVENESS_TIMEOUT_S = 8.0
```

而且它明确把超时判为「连接已死」：

```python
if isinstance(exc, (asyncio.TimeoutError, TimeoutError)):
    return False        # 当作死连接，触发重建
```

**说明设计上早就知道「MCP 调用会卡」，并且有超时判据 —— 只是真正执行工具的那条路径漏了这层保护。**

## 3. 为什么「多实例」让它更容易炸

这不是多实例引入的 bug，但多实例把它从「偶发」变成「常态」：

| | 单实例 | 多实例 |
| --- | --- | --- |
| 坏连接 | 用户重启进程可自救 | 连接在**某个实例**的进程内缓存里，用户无法感知 |
| 请求路由 | 总是同一个进程 | nginx 按 cookie 粘性路由，**坏连接会被反复命中** |
| 恢复手段 | 重启后端 | 需要知道是哪个副本、且不能影响其它用户 |

`UserRuntime` 是**进程级缓存**（`app/runtime.py:127` `self._runtimes[key]`），
里面握着 MCP 长连接。连接一旦半死，只要这个 runtime 不被重建，
**这个实例上这个用户的所有后续调用都会卡**。

而 TTL 刷新（`refresh_mcp_status`）有个关键跳过：

```python
if has_active_generation_for_user(user_id):
    return getattr(ur.toolset, "manifest", []) or []   # 有生成在跑就跳过重建
```

**正在卡着的那一轮，恰好就是「有生成在跑」—— 所以永远不会触发重建。** 死锁闭环。

## 4. 次生问题：`USER_MAX_MCP_CALLS=2` 让父代理被饿死

事故中间父代理试图自己搜索兜底（block 31/32），结果两次都失败：

```json
[block 33 reasoning] "Capacity exceeded — probably because the two subagents
are consuming MCP concurrency. So my hedge fails; I must rely on subagents."
```

```json
[block 34 text] "MCP 连接池被两个 agent 占满了（`capacity_exceeded`），
我暂时无法自己补搜，只能等两个子代理跑完。"
```

原因（`app/quota.py:38`）：

```python
user_mcp_calls: int = _env_int("USER_MAX_MCP_CALLS", 2)   # ← 用户级 MCP 并发上限 = 2
```

两个子代理各占一个槽位，且因为无超时**永久不释放** → 父代理拿不到第三个 →
`mcp_call(timeout_s=2.0)` 等 2 秒就抛 `QuotaExceeded`。

这是**次生问题，但危害很大**：它掐掉了唯一的自救路径。

## 5. 修复

### 5.1 已实施：MCP 调用超时（`backend/app/mcp_client.py`）

新增：

```python
_DEFAULT_MCP_CALL_TIMEOUT_S = 300.0          # 可用 MCP_CALL_TIMEOUT_S 覆盖
_MCP_CALL_TIMEOUT_MIN_S = 1.0                # 下限：0/负数等于没超时，必须拒绝
_MCP_CALL_TIMEOUT_MAX_S = 3600.0

def mcp_call_timeout_s() -> float:
    """坏配置（非数字 / 0 / 负数 / 超范围）一律退回默认值。"""
```

两条裸 `await` 全部改为 `_call_guarded`：

```python
async def _call_guarded(target_client) -> str:
    seconds = mcp_call_timeout_s()
    try:
        result = await asyncio.wait_for(
            target_client.call_tool(name, payload), timeout=seconds)
    except (asyncio.TimeoutError, TimeoutError):
        raise _McpCallTimeout(seconds) from None
    return _result_to_text(result)
```

超时**不向上抛异常**，而是转成可读的 tool observation：

```
[工具执行错误] MCP 工具 web_search_exa 调用超时（server=exa）：超过 300s 没有返回。
已放弃本次调用。该 server 可能已无响应，可以稍后重试，或换用其他数据源继续。
```

为什么用独立的 `_McpCallTimeout` 而不是直接抛 `asyncio.TimeoutError`：
外层还有一个 `except Exception` 会把它归到「业务错误」，
那会把「server 无响应」误报成「参数不对」，误导模型改参数重试。

## 6. 配额槽位与重建死角（§6.1 / §6.3 已修，§6.2 未修）

### 6.1 `USER_MAX_MCP_CALLS=2` + 硬编码 2 秒等待 —— ✅ 已修

原状态：

```python
# app/quota.py
user_mcp_calls: int = _env_int("USER_MAX_MCP_CALLS", 2)   # 只够 2 个并发
# app/mcp_client.py
async with get_quota().mcp_call(user_id, timeout_s=2.0):  # 2 秒拿不到就失败
```

两个问题叠加把用户自己锁死：

1. **槽位只有 2 个**，而子代理上限默认是 8（`USER_MAX_ACTIVE_SUBAGENTS`）——
   配置自相矛盾：允许开 8 个子代理，却只给 2 个 MCP 并发；
2. **槽位满 = 立刻失败**，而不是排队。事故里父代理连续两次 `capacity_exceeded`，
   **唯一的自救路径被掐掉**。

修复：

| 项 | 改前 | 改后 |
| --- | --- | --- |
| `USER_MAX_MCP_CALLS` 默认 | 2 | **8**（与 `USER_MAX_ACTIVE_SUBAGENTS` 对齐） |
| 槽位满时等待 | 硬编码 `2.0` 秒 | `mcp_call_queue_wait_s()`，默认 **30 秒**，`MCP_CALL_QUEUE_WAIT_S` 可覆盖 |
| 报错信息 | `capacity_exceeded after 2.0s` | 追加各闸门水位：`[全局 MCP 30/32，用户 MCP 0/8；user=u_xxx]` |

护栏没有丢：`GLOBAL_MAX_MCP_CALLS=32` 仍防单机打爆上游，单次调用 300s 超时
保证槽位不会无限占用。

测试：`backend/tests/test_mcp_quota_defaults.py`（8 条）。
反向确认做了两层：

- stash 掉实现 → 4 条变红；
- **保留函数只把默认值 8 改回 2** → 精确命中 `test_default_user_mcp_calls_fits_parallel_subagents` 1 条；
- **只把 `mcp_call_queue_wait_s()` 的返回值改成 2.0** → 精确命中 `test_wait_timeout_is_configurable` 1 条。

> ⚠️ 写测试时踩到一个假设错误：`Limits` 的字段默认值是 `_env_int(...)` 的求值结果，
> 而 dataclass 默认值在**类定义时**（模块导入时）就固定了。所以在本进程
> `monkeypatch.setenv` 之后再 `Limits()` **不会**看到新值。这不是 bug，是
> 「环境变量 = 进程启动时读一次」的既有语义。验证 env 生效必须用子进程。

### 6.2 `run_batched` 层没有统一超时兜底

`app/tool_batching.py:43` 的 `await dispatch(...)` 是裸 await。
MCP 现在自己有超时了，但 A2A / ACP / 内置工具都没有。
**统一兜底应该加在 `ToolRegistry.dispatch`**，那是所有工具的唯一出口。

风险：会改变所有工具的语义（长跑工具如 `code_run` 需要例外）。
本次**没有动**，因为超出事故范围，且需要单独设计。

### 6.3 `refresh_mcp_status` 在有生成时永不重建 —— ✅ 已修

原状态：

```python
if has_active_generation_for_user(user_id):
    return getattr(ur.toolset, "manifest", []) or []   # 连探测都不做
```

注释写的理由是「避免打断正在执行的那一轮」。这个本意**是对的**：
`invalidate` 会 `ur.close()`，把正在用的 toolset 和 LLM client 一起关掉。

但它同时造成三个后果，其中第一条是事故里最恶劣的一点：

1. **唯一的诊断入口给出错误信息**。用户发现卡住，打开设置页想看 MCP 是不是断了，
   设置页调的正是这个函数 —— 返回缓存的假「已连接」。用户完全无法自救。
2. **永远不重建**。卡住的那一轮「恰好就是有生成在跑」，所以这个分支永远命中，
   代码永远走不到重建。
3. **连探测都不做**，比「探测但不重建」更保守 —— 而探测是只读的
   （`_toolset_is_live` 只调一个无副作用的探针工具、不占 MCP 配额、不关任何东西），
   根本不会打断谁。

修法 —— **探测可以，重建不行；重建排队到生成结束**：

| 情形 | 修前 | 修后 |
| --- | --- | --- |
| 有生成 + 连接活着 | 直接返回缓存 | 探测 → 续 TTL、返回真实状态 |
| 有生成 + 连接已死 | 返回假「已连接」 | 探测 → **如实报断开** + 记 `_pending_rebuild`，**不 close** |
| 无生成 + 连接已死 | 立刻重建 | 立刻重建（不变） |
| 待重建 + 无生成 | — | 下次 `get_user_runtime` 消费标记、真的重建 |
| 待重建 + 仍有生成 | — | 继续不动，标记留着 |

关键点：**「不打断」和「最终会重建」现在不矛盾了**。原来那个分支是
「两者都放弃」，现在只是把重建推迟。

`_pending_rebuild` 是 `set[(user_id, model_key)]`，按 (user, model) 隔离，
不会误伤别人；`invalidate` / `invalidate_all` 清理时会同步 discard，
避免标记残留导致下一次白白 invalidate。

测试：`backend/tests/test_mcp_pending_rebuild.py`（8 条）。反向确认做了两层：

- stash 掉实现 → 6 条变红；
- **逐点变异 5 处**（退回「完全不探测」/ 不标记待重建 / 死连接仍报已连接 /
  不消费标记 / 消费时不检查活跃），每处都精确命中对应测试，
  恢复后 8 passed。脚本见 `work/mutate_pending_rebuild.py` 的思路。

> ⚠️ 这次改动让一条**旧测试失效**：`test_mcp_session_liveness.py` 的
> `test_refresh_still_skips_while_generation_active` 原本断言
> 「连接已死 + 有生成在跑 → `out[0]["ok"] is True`」，即明确锁定了
> 「设置页说谎」这个行为。已改为断言「不 close Toolset」+「如实报断开」
> +「标记待重建」。**这是行为变更，不是修 bug 顺手删测试** —— 改的理由写在
> 测试的 docstring 里。

## 7. 给复刻的启示

1. **任何 `await` 外部 I/O 的地方都必须有超时**，尤其是 SDK 默认 `None` 的。
   检查方法：`inspect.signature(Client.call_tool)` 看默认值。
2. **超时要转成可读的 observation，不是抛异常**。让模型能继续，而不是整轮失败。
3. **「探活有超时、执行没超时」是常见的漏改模式**。写新代码时如果看到
   同一层能力有两套路径（探测 / 执行），要检查保护是否一致。
4. **多实例子代理的等待应该是可观测的**。本次用了 30 分钟才发现卡在
   `tool_start` 之后 —— 因为 `wait_agent` 只报 `turns=0`，不报「卡在哪个工具」。
   建议在 `wait_agent` 结果里带「每个 agent 最后一次 tool_start 是什么 + 多久没动」。

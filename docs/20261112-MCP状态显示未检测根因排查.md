# MCP 状态显示「未检测 / 共 0 个可用工具」根因排查

> 日期：2026-11-12　状态：**根因已实测确认**（未改代码）
> 触发：用户反映 MCP 设置页经常显示「未检测 · 共 0 个可用工具」，但本地配的
> MCP server 实际是在线的；怀疑是 TTL 机制问题，或该学 CC 做定时心跳。

## 0. 结论

**不是 TTL 的问题，也不是缺心跳。是「冷启动串行连接耗时 30+ 秒，前端只请求一次且不重试」。**

| 怀疑方向 | 是否成立 | 真实情况 |
|---|---|---|
| TTL 太短/太长导致状态不刷新 | ❌ | TTL 只在 `_built_at` 之后生效；冷启动时**根本没有缓存**，走的是首次构建 |
| 需要定时心跳检测 | ❌ 不是当前的病根 | CC 也不做定时心跳（见 §4），它靠连接对象自身状态机 |
| 前端拿不到状态 | ✅ **这是病根** | 首次 `/api/me/mcp-effective` 实测 **32 秒**；前端只在登录时请求一次，失败静默吞掉 |

实测数据（真实后端，同一用户）：

```
第 1 次（冷启动，含 4 个 MCP server）: 32.075 s
第 2 次（缓存命中）                  :  0.045 s
差 700 倍
```

用户在这 32 秒里看到的就是「未检测 · 共 0 个可用工具」——因为 `servers` 还是初始的空数组。

---

## 1. 现场证据

### 1.1 后端接口本身是对的

三个不同配置的用户实测 `/api/me/mcp-effective`，**都在缓存命中后正确返回 `servers`**：

```
u_333928610085（exa + sqlbot 本地）:
  servers: [{"name":"exa","ok":true,"tool_count":2},
            {"name":"sqlbot","ok":true,"tool_count":12}]

u_f6ac05682e44（只有 demo）:
  servers: [{"name":"demo","ok":true,"tool_count":5}]

u_36679196feee（fetch + tavily + exa + context7）:
  servers: [{"name":"fetch","ok":false,"error":"TimeoutError: "},
            {"name":"tavily","ok":true,"tool_count":5},
            {"name":"exa","ok":true,"tool_count":2},
            {"name":"context7","ok":true,"tool_count":2}]
```

注意第三个：**`fetch` 确实是失败的**（stdio `npx` 起不来），而后端如实报了
`ok: false` + `TimeoutError`。所以「显示不出真实状态」不是后端在骗人。

### 1.2 慢在串行连接

`agent.py:196-212`：

```python
connect_timeout = float(os.environ.get("MCP_CONNECT_TIMEOUT", "12"))
for srv in servers:                      # ← 串行，不是并发
    ...
    await asyncio.wait_for(ts.__aenter__(), timeout=connect_timeout)
```

配 4 个 server，其中 `fetch` 走 stdio `npx` 起不来 → 吃满 12s 超时；
其他几个 http 握手也要时间。**串行叠加**就是 30 秒量级。

### 1.3 前端只在登录时请求一次，且静默吞失败

`App.tsx:282-291`：

```js
const refreshHealth = useCallback(async () => {
  const h = await api.health().catch(() => null)
  const eff = await api.mcpEffective().catch(() => null)     // ← 失败被吞成 null
  setHealth({
    model: h?.model || '',
    mcp_tools: eff ? eff.tools.length : h?.mcp_tools ?? 0,
    servers: eff?.servers || [],                             // ← null -> [] -> 显示"未检测"
  })
}, [])

useEffect(() => {
  if (!user) return
  refreshHealth()      // ← 只在 user 变化时跑一次，没有任何重试/轮询
  ...
}, [user, loadSessions, refreshHealth, loadModels])
```

三个问题叠在一起：

1. **只跑一次**。32 秒的请求期间界面一直是初始值 `servers: []` → 「MCP 未检测」。
2. **失败即空**。`.catch(() => null)` 把「还没回来」「超时」「500」都变成同一个
   空状态，用户无法区分。
3. **没有重试**。请求即便失败了，除非刷新页面（`user` 重新取到），否则永远是「未检测」。

设置页的 `load()` 是同样的模式（`SettingsModal.tsx:524-539`），
而且打开设置页时会再请求一次——所以用户**有时**能看到正确状态（第二次命中缓存，0.045s）。

### 1.4 「共 0 个可用工具」的第二个来源

`/api/health` 的 `mcp_tools` **是硬编码的 0**（`main.py:98`）：

```python
return HealthOut(ok=True, model=model, mcp_tools=0)
```

前端在 `eff` 为空时回退到它（`h?.mcp_tools ?? 0`）。所以「未检测」与「共 0 个工具」
会同时出现——两处都指向"没拿到数据"，但看起来像"确实没有工具"。

## 2. 为什么这不是 TTL 的问题

`refresh_mcp_status`（`runtime.py:135`）的逻辑：

```python
ur = self._runtimes.get(key)
if ur is None:
    return []                                    # ← 冷启动：没有缓存，直接返回空！

if not force:
    built = self._built_at.get(key, 0.0)
    if time.monotonic() - built < _MCP_STATUS_TTL_S:      # 60s
        return getattr(ur.toolset, "manifest", []) or []
```

TTL 是 60 秒（`runtime.py:282`）。但 TTL 只在**已经构建过**之后才有意义。
用户刚登录/刚重启后端时，`ur is None`，`refresh_mcp_status` 直接返回 `[]` ——
**状态的来源完全是随后那次 `get_user_runtime` 的首次构建**，而它要 30 秒。

所以调 TTL 完全没用：TTL 管的是"已连接之后多久重新验证"，而用户遇到的是
"第一次连接要 30 秒"。

---

## 3. 该不该加定时心跳

**不该作为第一优先级，而且单独加心跳解决不了这个问题。**

理由：

1. **心跳也是连同样的 server，也慢**。如果每 60 秒重新探测 4 个 server
   （其中 1 个要 12s 超时），那是在持续消耗资源，换来一个用户本来就能手动
   「重新检测连接」得到的结果。
2. **CC 本身不做定时心跳重连**（见 §4）。
3. **真正的病根是"首屏拿不到状态"**，不是"状态会过时"。先解决前者。

**心跳适合解决的场景**是"用户开着页面很久，MCP 中途挂了"。
这确实存在，但代价是持续的后台探测。更轻的做法见 §5.3（只在页面可见时低频探测）。

---

## 4. CC 2.1.319 是怎么做的

CC 的状态是**连接对象自身持有的状态机**，UI 直接读，不做定期重连：

```js
// m0165_0x1145c609.js:9486
connection: B(["connecting", "live", "reconnecting"]).optional()

// m0513_0x11b6abce.js:445-452
switch (e.type) {
  case "pending":   return { kind: "reconnecting", serverName };
  case "needs-auth":return { kind: "needs_auth",  serverName };
  case "failed":    ...
}
```

关键差异：

| | CC | Hlaudz 现状 |
|---|---|---|
| 状态的持有者 | **连接对象自己**（连上就 live，断了就 reconnecting） | `manifest` 快照，存在 toolset 上 |
| 派生方式 | 读连接状态，**零额外开销** | 需要**重新连接**才能知道（`probe_mcp_status`） |
| 首次连接慢怎么办 | 状态是 `connecting`，UI 显示"连接中" | **没有 connecting 态**，只有"未检测" |

**最值得抄的不是心跳，是 `connecting` 这个状态。** CC 把"还在连"如实表达出来，
而 Hlaudz 把"还没连完"和"没有配置"混成了同一个"未检测"。

---

## 5. 建议的修法（按性价比排序）

### 5.1 立刻做：给「未检测」一个真实的中间态

前端当前的三态其实是四态，漏了"正在连接"：

| 实际情况 | 现在显示 | 应该显示 |
|---|---|---|
| 请求还没回来 | 未检测 | **正在检测 MCP…**（带转圈） |
| 请求失败/超时 | 未检测（静默） | **检测失败：<原因>（点击重试）** |
| 真的没配 | 未检测 | 未配置 MCP |
| 配了、连完了 | N/M 个已连接 | 同左 |

改动很小，全在前端：

```ts
// App.tsx
const [mcpLoading, setMcpLoading] = useState(false)
const [mcpError, setMcpError] = useState<string | null>(null)

const eff = await api.mcpEffective()
  .then((r) => { setMcpError(null); return r })
  .catch((e) => { setMcpError(String(e)); return null })
  .finally(() => setMcpLoading(false))
```

**这一条就能消掉用户看到的大部分「未检测」**——因为它把 32 秒的空白变成了
"正在检测"，用户知道它在干活。

### 5.2 立刻做：MCP 连接并发化

`agent.py:204` 的 `for srv in servers` 改成 `asyncio.gather`。
4 个 server 里 1 个 12s 超时、3 个各 2s，串行是 18s，并发是 **12s**（取最大值）。
server 越多收益越大。

注意保留现有的两个不变量：
- **失败要进 manifest**（不能因并发丢结果）；
- **`ts.__aexit__` 要在失败时正确释放**（半开连接必须关掉）。

这条属于 AGENTS.md §2.1 的范围（改 `agent.py`），改完要跑真实 e2e。

### 5.3 可选：页面可见时的低频刷新

不需要定时器常驻。用 `document.visibilitychange` + 冷却时间：

```
用户切回页面 && 距上次检测 > 5 分钟 -> 刷新一次
```

这比定时心跳省得多，而且覆盖真实场景（用户离开又回来）。

**不建议做常驻定时心跳**：持续重连有真实成本（尤其有 server 连不上时，
每次都要吃满超时），而收益只是"页面开着时能更早发现掉线"。

### 5.4 顺带修正 `/api/health` 的 `mcp_tools: 0`

`main.py:98` 硬编码 0 是个陷阱：它看起来像"工具数就是 0"。
建议要么删掉这个字段（前端已经有 `eff.tools`），要么如实填（但那会让
`/api/health` 依赖用户身份，不合适）。

**建议删除**，前端 `mcp_tools` 的取值只从 `mcpEffective` 来；拿不到时显示
"检测中/失败"而不是 0。

## 6. 验证方法（修完怎么确认）

现有的探针足够，不需要新写：

```bash
# 冷启动耗时（改并发后应显著下降）
T=$(python -c "...签发 token...")
curl -s -o /dev/null -w "%{time_total}s\n" -H "Authorization: Bearer $T" \
  http://127.0.0.1:8000/api/me/mcp-effective

# 期望：4 server 场景从 32s 降到 ~12s（= 单个最大超时）
# 期望：第 2 次仍是 0.045s（缓存未被破坏）
```

前端验证（L3，AGENTS.md §2.4 要求 UI 改动必须有截图或持久化证据）：

1. 冷启动后端 → 打开页面 → **立刻**应看到「正在检测 MCP…」而不是「未检测」；
2. 32 秒（改并发后 12 秒）内应自动变成真实状态，**不需要手动点重新检测**；
3. 断网 → 应显示「检测失败：<原因>」，不是静默的「未检测」；
4. 负对照：真正没配 MCP 的用户应显示「未配置」，不能显示「检测失败」。

## 7. 一句话总结

- **不是 TTL 的问题**：冷启动时根本没有缓存，TTL 还没开始生效。
- **不是缺心跳**：CC 也不做定时心跳，它靠连接对象自己的状态机。
- **真因**：MCP 串行连接要 30+ 秒，前端只请求一次、失败静默成空、且没有
  「正在检测」这个中间态 → 用户长时间看到「未检测 · 共 0 个可用工具」。
- **修的顺序**：① 前端加「检测中 / 检测失败」两态（改动最小、收益最大）；
  ② MCP 连接并发化（把 32s 降到 12s）；③ 可选的低频可见性刷新。

### 8.2 修复 2：MCP 连接并发化（2026-11-12 完成）

`build_user_toolset` 的 `for srv in servers` 串行连接改为 `asyncio.gather` 并发。

**真机实测（4 个 server，其中 `fetch` stdio 起不来、吃满 12s 超时）**：

```
修复前  冷启动 32.075 s
修复后  冷启动 14.046 s      （≈ 单个最大超时，符合并发预期）
        热缓存  0.009 s
```

**并发安全性核实（改之前逐条确认，不是假设）**：

| 关注点 | 结论 |
|---|---|
| 连接是否占配额 | **不占**。`quota.mcp_call` 只在工具**调用**时用（`mcp_client.py:301`） |
| `__aenter__` / `_discover` 有无全局状态 | 只读自身字段，无锁无共享可变状态 |
| 单 server 失败会不会中断其他 | `gather(return_exceptions=True)` + 每个 `_connect_one` 内部 try/except |
| manifest 顺序 | `gather` 保留入参顺序；实测 `fetch/tavily/exa/context7` 与配置一致 |
| 取消是否留孤儿连接 | `CancelledError` 分支会先把已连的 `__aexit__` 再抛 |
| 20 个 server 会不会打满机器 | `MCP_CONNECT_CONCURRENCY`（默认 8）信号量限流 |

**新增 7 条单测**（`test_mcp_concurrent_connect.py`），锁住：
确实并发、最慢者决定总时长、manifest 顺序、失败隔离、全失败回退、
并发上限、取消不留孤儿。

**反向确认**：把 `gather` 改回 `for` 串行 → 2 条变红
（`test_connects_in_parallel_not_serial`、`test_slowest_server_dominates`）。

> 过程中发现 `test_slowest_server_dominates` 第一次**没变红**——阈值取了 0.5s，
> 而串行是 0.36s 也在阈值内。收紧到 0.33s 后才真正区分。阈值太松等于没断言。

**验证**：全量单测 829 → **836 passed**；e2e S0 / S1 / S5 全 PASS，
三个 runId 的 audit 均 `checks_failed: []`
（`1794548000-e6eb` / `1794548005-7f0b` / `1794548020-5537`）。

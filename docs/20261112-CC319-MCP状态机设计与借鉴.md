# CC 2.1.319 MCP 状态机：设计与借鉴

> 日期：2026-11-12　状态：源码调研（含 Hlaudz 对照与借鉴建议）
> 源码：`D:\git_codes\claudecode283_hack\reconstructed319\deminified\`
> 主模块：`m0513_0x11b6abce.js`（状态派生 `cat`/`re`）、`m0591_0x11be624e.js`（消费侧）
> 触发：排查 Hlaudz「MCP 状态显示未检测」时，对比 CC 的做法。

## 0. 结论先说

**CC 的 MCP 状态不是"探测定时刷新"，而是"从连接对象的实时状态派生出来的"。**
这套设计里最巧的三点是：

1. **状态是派生量，不是存储量**。没有 `manifest` 快照要维护，每次问"这个工具有没有
   效"都现场从连接对象算，所以**永远不会有"缓存里的状态是骗人的"这种问题**。
   Hlaudz 的 `refresh_mcp_status` 花一整套 TTL + 探活 + 重建来对抗的，正是这个病。

2. **状态不只有"通/不通"，而是 13 种失效原因**。每种原因对应**不同的处置动作**：
   有的是"去认证"，有的是"等它重连"，有的是"管理员封了别管了"。

3. **`rdo()` 这个谓词决定"要不要告诉模型"**。同样是"工具不能用"，
   `disconnected`（网络抖动，可能马上好）**告诉模型**，
   `not_configured`（用户就是没配）**不告诉**——避免模型对用户解释一堆不存在的故障。

这三条里，第 1 条是架构差异，第 3 条是产品判断。第 2 条是前两条能成立的前提
（不区分原因就没法分别处置，也没法分别决定告不告诉）。

## 1. 状态全集：13 种失效 + 2 种存活

`re()`（`m0513:419`）把连接对象的状态翻译成一个 `kind`：

```js

  case "pending":    return { kind: "reconnecting", serverName };
  case "needs-auth": return { kind: "needs_auth",   serverName };
  case "failed":
    if (y7t(e.error)) return { kind: "policy_blocked",   serverName };
    if (_7t(e.error)) return { kind: "reserved_address", serverName };
    return sD(e) ? { kind: "not_configured" } : { kind: "disconnected", serverName };
  case "disabled":
    return { kind: e.config.type === "sdk" ? "switched_off" : "disabled", serverName };
  case "connected":
  case "cached":
    if (R_e(e)) return { kind: "switched_off", serverName };
    return n === c0e || n === FIn
      ? { kind: "auth_completed", serverName }
      : { kind: "not_offered",      serverName };
}
```

另有几条在更外层判定（权限规则 / 组织策略 / 工具被替换）：

| kind | 含义 | 谁的问题 |
|---|---|---|
| `disconnected` | 连不上（网络、进程崩） | 环境 |
| `reconnecting` | 正在重连（连接对象 `pending`） | 环境，**会自愈** |
| `needs_auth` | 需要用户认证（OAuth 等） | **用户要动手** |
| `policy_blocked` | 被策略拦（如企业安全策略） | 管理员 |
| `reserved_address` | 目标地址保留/不可达 | 配置 |
| `org_blocked` | 组织级封禁 | 管理员 |
| `denied` | 权限规则拒绝该工具 | 用户配置 |
| `disabled` | server 被禁用 | 用户配置 |
| `switched_off` | SDK server 被关 / 运行时被关 | 调用方 |
| `not_configured` | **压根没配** | ——（不算错误） |
| `replaced` | 被同名工具替换了 | 模型行为 |
| `withdrawn` | 工具已从 server 撤回 | server 侧 |
| `not_offered` | server 在线但这个工具没提供 | server 侧 |
| `auth_completed` | 刚完成认证，工具待生效 | 过渡态 |

**关键观察**：这 14 个值里有 3 个（`not_configured` / `replaced` / `withdrawn`）
根本不算"故障"——它们是**正常状态**。Hlaudz 的三态（已连接 / 失败 / 未检测）
把它们全糊成一个"未检测"，用户当然会困惑。

## 2. 最巧的一点：三个谓词回答三个不同的问题

`m0513:322-344` 三个函数，各管一件事：

```js
// ① 这个工具「当前不可用」吗？
function rdo(e) {
  switch (e.kind) {
    case "policy_blocked": case "reserved_address": case "org_blocked":
    case "denied": case "disabled": case "switched_off":
    case "not_configured": case "replaced":
      return !0;                 // ← 8 种：不可用
    case "reconnecting": case "needs_auth": case "disconnected":
    case "auth_completed": case "not_offered": case "withdrawn":
      return !1;                 // ← 6 种：可用 / 过渡中
  }
}

// ② 这个工具名「还存在」吗？（被 replaced 的不算）
function odo(e) {
  return rdo(e) && e.kind !== "replaced";
}
```

```js
// ③ 消费侧：要不要把"没了"这件事**讲给模型听**（m0591:152812）
?.revoked.filter((h) =>
   h.cause !== "not_configured"      // 用户就是没配 —— 不该由模型向用户解释
   && h.cause !== "replaced"         // 被替换 —— 内部实现细节
   && h.cause !== BY                 // 其他内部原因
   && !Xur(s, {...}))
 .map((h) => h.name)
```

三层的关系：

| 谓词 | 回答 | 用途 |
|---|---|---|
| `rdo(kind)` | 工具**当前不可用**吗 | 是否计入 revoked 统计 |
| `odo(kind)` | 工具名**还值得保留**吗 | 工具列表里留不留这一项 |
| 消费侧 filter | **要不要讲给模型** | 上下文里说不说"你的某工具不可用" |

**三级分离为什么值钱**：

- 「用户没配这个 server」→ `rdo` 为真（确实不可用），但**不告诉模型**。
  模型不该对用户解释"你有个 MCP 没配"——那是 UI 该说的；
  让它去说只会得到一段编造的猜测。
- 「配了但断线」→ `rdo` 为真且**告诉模型**。模型必须知道自己"现在搜不了网"，
  否则它会假装调用成功或编造结果。
- 「工具被 replaced」→ `odo` 为假（从列表移除），但**不告诉模型**（内部细节）。

如果只用一个布尔"工具可用吗"，这三种情况就全糊在一起，模型要么对着一堆
不存在的故障长篇解释，要么对自己真实的能力缺失一无所知。

> 更细的一层：`rdo` 里 `not_configured` 和 `replaced` 返回 `!0`，
> 说明它们在"是否不可用"这个问题上**和断线一样是真的**——
> 只是"要不要告诉模型"由消费侧单独决定。这正是分离的价值：
> **同一个事实，对不同的消费方有不同的相关性。**

## 3. 第二巧：状态从连接对象派生，不是存快照

架构差异对比：

```
CC:
  mcpClients（活着的连接对象）
        │  每次问就现场算
        ▼
    re(row, upstream, denied?)  ──►  kind
        │
        ▼
   UI 直接读 / 告诉模型 / 决定工具列表

Hlaudz:
  连接 ──► 快照 manifest（一次性，存在 toolset 上）
                │
                │  快照会过时
                ▼
        需要 TTL + 探活 + 重建来"修复"过时
```

CC 的做法有一个直接好处：**不存在"缓存说已连接、实际已死"的状态**。
Hlaudz 的 `refresh_mcp_status` 花了一整套机制来对抗它（`runtime.py:137-152` 的
docstring 逐条解释了为什么不能只看 manifest）——而那些复杂度在 CC 的模型里
根本不需要，因为状态就是连接本身。

代价：每次查询要算一次。但 `re()` 是纯函数、无 IO、只读内存字段，
成本是一次 switch——比"重新连接一遍"低几个数量级。

> **这解释了为什么 CC 没有"定时心跳"**：心跳是为了修复"快照过时"，
> 而派生式状态压根没有快照可过时。CC 只在**连接真的断开时**触发重连
> （那是连接层自己的事），UI 只是如实显示。

## 4. 第三巧：一个工具可以有多个上游

`U(e, n, o)`（`m0513:391`）处理"工具名 -> 可能多个 server"的映射，并且**取最长前缀匹配**：

```js
let r = n.map(s => ({ row: s, prefix: to(s.name) }))
         .filter(({prefix}) => e.startsWith(prefix));
let i = Math.max(0, ...r.map(({prefix}) => prefix.length));   // ← 最长前缀
return r.filter(({prefix}) => prefix.length === i)...
```

这解决的是：server 名 `a` 和 `a-b` 都存在时，工具 `a-b_search` 该归谁。
朴素实现会两个都匹配上，产生歧义；**最长前缀**让它唯一。

然后 `CTe`（`m0513:345`）在多个候选里按优先级挑一个：

```js
let u = p.find(rdo)                                          // ① 优先报"真的坏了"的
     ?? p.find(x => x.kind === "not_offered"
                 || x.kind === "auth_completed")              // ② 其次报"过渡态"
     ?? p[0];                                                 // ③ 兜底
```

**优先级是「坏消息优先」**：如果同一个工具被两个 server 提供，一个挂了、一个好着，
它报"挂了的那个"而不是"好着的那个"。这个选择是对的——因为用户看到的工具行为
取决于**实际命中哪个**，而 dispatch 到挂掉的那个就是失败。

## 5. 与 Hlaudz 现状的对照

| 维度 | CC | Hlaudz | 差距 |
|---|---|---|---|
| 状态来源 | 连接对象派生（零 IO） | `manifest` 快照 | **架构级** |
| 状态粒度 | 14 种 | 2 种（ok / error 文本）+ "未检测" | 大 |
| 「正在连接」态 | `reconnecting` | **没有**（显示"未检测"） | **本次要修** |
| 是否告知模型 | 三级过滤（记录/告知/存在） | 只有"工具在不在列表里" | 中 |
| 过时问题 | 不存在 | 靠 TTL + 探活 + 重建对抗 | 架构级 |
| 心跳 | **没有** | 没有 | 一致 |

**结论：Hlaudz 不需要照抄 CC 的派生式架构**（那是大改，且 `manifest` 快照
对我们"一次装配、多次调用"的模型更省）。但有三件事**现在就该抄**：

1. **补 `connecting` 态**（对应本次 P1 修复）；
2. **把 `ok: false` 拆成原因分类**（至少区分"断线"vs"没配"vs"需要认证"）；
3. **"没配"不该显示成故障**（当前 `not_configured` 和 `disconnected` 在 UI 上
   长得一样）。

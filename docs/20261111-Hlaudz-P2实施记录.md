### 1.1 契约

`followup_task(target, message)`：

| 情况 | 返回 |
| --- | --- |
| 目标在跑 | `{"ok": true, "delivered": true}`，在下一次模型调用前注入 |
| 目标已结束 | `{"ok": false, "error": "...已结束（completed）..."}`，提示用 `read_agent_result` |
| 同内容重复 | `{"ok": true, "deduped": true}` |
| 超过 5 条 | `{"ok": false, "error": "已达上限"}` |
| 未知目标 | `{"ok": false, "error": "未知子代理: x"}` |

注入载荷固定前缀 `[来自父代理的追加指令]`，并以 `role=user` 追加到子代理 history。

### 1.2 通知

- 子代理进入终态时写入 `host._notifications`（含 agent / status / 结果预览 400 字符）；
- `peek_notifications()` 只读，`ack_notifications(ids)` 才删；
- `drain_notifications()` 一次最多 5 条，ack 后返回一条 `[任务通知]` user 消息，
  仍有剩余时追加「另有 N 个，可用 list_agents 查看」。

## 3. 真实 e2e

### 3.1 S4（steer）

```
runId=1794287857-d7b8  28.1s
tools = list_files, list_files, spawn_agent, followup_task, wait_agent, read_agent_result, close_agent
```

审计 `events.jsonl`：

- `followup_task` 返回 `{"ok": true, "delivered": true}`；
- 子代理事件流里出现 `message_injected`，内容是被追加的 `.ts` 统计要求；
- 子代理随后调用了 `file_glob` 统计（改动前它用 `code_run`）。

### 3.2 审计中发现并修掉的两个问题

这两个不是崩溃级缺陷，但都是**真实存在、只有跑链路才看得见**的问题：

| # | 现象 | 根因 | 修复 |
| --- | --- | --- | --- |
| 1 | 追加指令已注入，但前端/事件流完全看不到 | `host._drive` 的事件转发白名单只有 text/thinking/tool_*，`message_injected` 被丢弃 | 白名单加入 `message_injected`，并补测试 |
| 2 | 子代理统计文件数量时用 `code_run` 而不是 `file_glob` | `file_glob` 最多返回 100 条路径，模型以为统计不了；实际返回值里有 `total` | 工具描述写明「total 是完整数量，可直接统计」 |

第 1 个是**功能性缺陷**（用户看不到父代理追加了什么）；
第 2 个是**引导缺陷**（工具能做但没告诉模型）。

### 3.3 一个时序观察（非缺陷）

`wait_agent` 返回时子代理的 `status` 已是终态，但 `_run_child` 的 `finally` 里
`_notify()` 可能晚几毫秒执行。影响：`wait` 刚返回就 `drain_notifications()` 可能少一条。
处理：通知在下一轮模型调用前读取，天然有一轮工具执行的缓冲，实际不受影响；
测试里显式 `sleep(0.3)` 规避。

## 4. 为什么不做 `notify_when_idle`

需求来自 GA / CC：订阅「子代理闲下来」这一时刻（不是结束）。
GA 的子代理是**长期存活的进程**，一轮结束进入 idle，还能被 followup 唤醒；
CC 同理，teammate 可以空闲常驻。

Hlaudz 的子代理是**一次性任务**：`_run_child` 跑 `run_stream` 到没有 tool_calls 就结束，
状态直接从 `running` 到 `completed`，没有「空闲但仍存活」这一阶段。
对它做 `notify_when_idle` 只会等价于「完成时通知」——而完成通知已经默认发送。

**结论**：等将来支持「常驻 teammate」时再实现；现在加一个同义功能只会增加提示词负担。

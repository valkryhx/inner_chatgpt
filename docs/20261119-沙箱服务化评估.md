# 沙箱服务化评估：该不该把 sandbox 从 app 里拆出去

> 日期：2026-11-19　状态：**评估（未实施）**
> 前序：`docs/20261118-沙箱MVP设计与实施.md`（现行 MVP，明确写了「不引外部服务」）
> 触发：2026-11-19 hx 的「4 个 sub 先 2 并行后 2 串行」任务卡在 worker_c，
> 排查时发现三个结构性问题都指向同一处：sandbox 和 app 耦合在一起。
> 参考：`D:\git_codes\LibreChat` 的实际做法（本文 §3 有逐条源码坐标）。

---

## 0. 一句话结论

**该拆，但不是现在。** 当前 MVP 的「进程内 Sandbox Manager」是合理的**过渡形态**，
但它有三个**已经发生的**结构性代价（docker 权限、路径错位、多实例重复建容器），
在「容器化 + 多实例」这个部署形态下会持续放大。

LibreChat 提供了完整先例：**代码执行完全外置成独立的 Code Interpreter 服务**，
chat 主服务通过 HTTP 调它，主 compose 里根本没有这个服务（必须单独部署）。

本文给出：现状证据、LibreChat 对照、拆分边界、分阶段路线、以及**现在就该为拆分做的三件低成本准备**。

## 1. 现状：sandbox 是 app 里的一个库，不是服务

### 1.1 结构事实

```
app/sandbox/
  manager.py    ← 对外门面：should_use_sandbox / exec_code / 分流
  runtime.py    ← 真正的 docker 调用（docker.from_env() / containers.run / exec_run）
  pool.py       ← 容器池（进程内 dict）
  config.py / policy.py / probe.py / identity.py / errors.py
```

调用方向是**单向的**（app → sandbox），`app/sandbox/*` 不反向 import app 业务模块。
这说明它**本来就是一个边界清晰的模块**——这是服务化的有利条件。

但有一处例外，也是关键耦合点：

```python
# app/sandbox/manager.py:72
def _host_workspace(user_id: str, root: str = "") -> str:
    from ..workspace import write_root_for      # ← 反向依赖 app 的路径解析
    return str(write_root_for(user_id, root))
```

### 1.2 三个已经发生的问题

#### 问题 1：app 必须能访问 docker daemon

```python
# app/sandbox/runtime.py:65
def _client():
    import docker
    return docker.from_env()        # ← app 进程自己建容器
```

**后果**：app 容器化后，要开沙箱就得挂 `/var/run/docker.sock`。
`docker-compose.yml` 的注释自己就写了「容器里跑容器需要挂 docker socket，风险很大」。

**实测确认**（2026-11-19）：当前 app 容器里

```
/var/run/docker.sock   不存在
docker SDK            未安装
```

所以 `HLZ_SANDBOX_MODE=on` 现在**根本跑不起来**，不是配置问题，是能力缺失。

#### 问题 2：挂载路径跨层错位（最难缠）

沙箱要把「宿主机路径」挂进自己：

```python
# app/sandbox/runtime.py:133
volumes={host_workspace: {"bind": WORKSPACE_MOUNT, "mode": "rw"}},
```

而 `host_workspace` 是 **app 进程内**用 `write_root_for()` 算出来的。
app 跑在容器里时，它算出的是**容器内路径** `/app/backend/data/sandbox/<uid>`，
可 docker daemon 在**宿主机**上——宿主机没有这个路径。

这是 DinD（Docker in Docker）的经典问题。要么：
- 用宿主机 bind mount 目录（那就不能是 Docker 卷里的路径）
- 或者挂 socket 后用 `docker inspect` 反查路径映射（脆弱）

#### 问题 3：每个 app 实例各建各的容器

`pool.py` 的容器池是**进程内 dict**。3 个实例 = 3 份池，同一个用户在两个实例上
会各起一个沙箱容器。这既浪费，也让「用户的工作区」出现两处活跃写入点。

### 1.3 本次事故里这三个问题的表现

worker_c 执行的工作目录是：

```
/app/backend/D:\sandbox/u_c56b8337dd09/.subagents/co_xxx/worker_c
```

`D:\sandbox` 是 Windows 默认路径，在 Linux 容器里被当成相对路径拼到了
`/app/backend` 下面 —— **名字里带反斜杠的畸形目录**。它真的被创建了，
所以多数工具靠「能在里面读写」侥幸工作，直到 shell 的 `cd` 踩上去。

已修（`default_sandbox_root(is_windows)` 按平台分流 + compose 显式设
`HLZ_SANDBOX_WORKSPACES_DIR`），但**根因是「路径解析留在 app 里」**这件事本身。

## 2. 为什么当初选择进程内（这个决定不算错）

`docs/20261118-沙箱MVP设计与实施.md` §0 明确写了「不引外部服务」。理由（读下来是成立的）：

| 理由 | 是否仍成立 |
| --- | --- |
| MVP 要最小可验证，2 个白名单用户 | ✅ 仍成立 |
| 引入外部服务 = 多一套部署/健康检查/鉴权 | ✅ 仍成立 |
| 复用 `write_root_for()` 的路径逻辑，避免两套真相 | ✅ **仍然成立，且是拆分的主要难点** |
| 沙箱默认 off，关闭时行为逐字节一致 | ✅ 仍成立 |

所以：**不是当初选错了，是部署形态变了**。当初的隐含前提是「app 跑在宿主机上」，
那时 `docker.from_env()` 和 `D:\sandbox` 都天然成立。现在 app 跑进了容器、还要多实例，
这两个前提都不成立了。

## 3. LibreChat 怎么做（源码证据）

### 3.1 结论：代码执行是**独立服务**，主服务通过 HTTP 调它

主 compose 里**没有** code interpreter：

```
$ grep -n "^  [a-z-]*:" D:/git_codes/LibreChat/docker-compose.yml
5:  api:
40:  admin-panel:
56:  mongodb:
64:  meilisearch:
75:  vectordb:
99:  librechat-data:
```

只有 6 个服务：API、管理面板、Mongo、Meili、向量库、data。**代码执行不在里面**，
必须单独部署（`.env.example:802` 就指向官方文档的 "self-hosted" 一节）。

### 3.2 调用方式：HTTP + 鉴权头

```javascript
// api/app/clients/tools/util/handleTools.js:346
return createCodeExecutionTool({
  user_id: user,
  files,
  authHeaders: () =>
    codeExecutionAuthHeaders(
      (bridgeWorkerId) => getCodeApiAuthHeaders(options.req, bridgeWorkerId),
      codeExecutionContext,
    ),
  ...codeExecutionContext,
});
```

```javascript
// api/server/services/Files/Code/crud.js:135
const baseURL = codeApiBaseUrl ?? getCodeBaseURL();
// :156
axios.post(`${baseURL}/upload`, form, options),
// :241
axios.post(`${baseURL}/upload/batch`, form, options),
```

**接口契约**（从上面能看到的）：
- `POST {baseURL}/upload` —— 上传文件到代码环境
- `POST {baseURL}/upload/batch` —— 批量
- `/exec` —— 执行（`.env.example:836` 提到「single `/exec` response」）

### 3.3 配置项（`.env.example` 摘录）

```bash
LIBRECHAT_CODE_BASEURL=                    # Code Interpreter 服务地址
LIBRECHAT_CODE_API_KEY=
# Current self-hosted Code Interpreter deployments use per-user LibreChat JWTs
# outside local mode. Configure the matching public verifier on Code Interpreter
CODEAPI_AUTH_PROVIDER=librechat-jwt
CODEAPI_JWT_ENABLED=false
CODEAPI_JWT_PRIVATE_KEY=                   # 签名密钥
CODEAPI_JWT_ALGORITHM=EdDSA
CODEAPI_JWT_TTL_SECONDS=300                # 5 分钟短时令牌
CODEAPI_TENANT_ISOLATION_STRICT=true       # 多租户强制隔离

# 可选：有状态会话专用端点
LIBRECHAT_CODE_BASEURL_STATEFUL=
CODE_SANDBOX_PREWARM=true                  # 预热，与模型生成并行
CODE_SANDBOX_COLD_AFTER_MS=2100000         # 35 分钟算冷
LIBRECHAT_CODE_SANDBOX_OUTPUT_MAX_SIZE=65536
```

### 3.4 值得直接抄的四个设计

| 设计 | 为什么值得抄 |
| --- | --- |
| **短时 JWT（TTL 300s）** | app 不需要长期持有沙箱的信任凭证。每次执行现签，泄露窗口只有 5 分钟 |
| **`TENANT_ISOLATION_STRICT` fail closed** | 多租户下宁可拒绝执行，也不能跨租户跑 |
| **`PREWARM`** | 沙箱冷启动是**用户可感知的延迟**。预热与模型生成并行，用户看不到等待 |
| **`COLD_AFTER_MS=35min`** | 回收策略显式化，不用「猜」多久算不活跃 |

### 3.5 LibreChat 也有「浏览器 iframe 沙箱」，别搞混

`docs/mcp-apps.md:159` 的 "Required sandbox deployment" 讲的是 **MCP App 的浏览器
iframe 隔离**（不同 origin + CSP + `sandbox` 属性），和代码执行沙箱是**两回事**。
但它佐证了同一个设计倾向：**沙箱必须在独立 origin / 独立进程边界上**。

## 4. 拆分的边界该怎么划

### 4.1 该搬进服务的

| 能力 | 现在在哪 | 搬走后 |
| --- | --- | --- |
| docker 客户端 / 容器创建 / exec | `runtime.py` | 服务内 |
| 容器池与回收 | `pool.py` | 服务内（可跨实例共享） |
| 镜像/资源限制（mem/cpu/pids/caps） | `runtime.py` | 服务内 |
| 探测与健康检查 | `probe.py` | 服务内 |
| 用户→workspace 路径解析 | **`write_root_for()`（app 内）** | **服务内**（见 4.3） |

### 4.2 该留在 app 的

| 能力 | 为什么留下 |
| --- | --- |
| 是否启用沙箱的策略（`policy.py` 的白名单） | 这是**产品决策**，不是执行细节 |
| 工具 schema 与结果格式化 | 属于 agent 契约，不能让服务决定 |
| 预算/截断（`_with_budget`） | 与上下文管理耦合 |
| 降级决策（auto 模式下失败怎么办） | 影响用户可见行为，必须在 app |

### 4.3 最难的一点：路径解析怎么办

这是**唯一的实质性设计难题**，必须想清楚再动手。

现在：

```
app 算路径 (write_root_for) → 传给沙箱 → 沙箱拿去挂载
```

拆开后有三个方案：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 服务算路径** | app 只传 `user_id` + `root`，服务自己维护映射 | 路径知识集中在一处 | 映射逻辑要搬家；app 的 `file_read` 等工具也得知道路径 → **两套真相** |
| **B. app 传宿主机路径** | app 算好绝对路径传过去 | app 仍是唯一真相 | app 在容器里算不出宿主机路径（问题 2） |
| **C. 共享卷 + 约定路径** | 双方都挂同一个卷，约定 `/data/workspaces/<uid>` | 路径天然一致，无跨层推算 | 要求部署时两服务都挂同一卷 |

**推荐 C**，理由：

- 问题 2 的根源就是「两边看到的路径不同」。共享卷让它们**看到同一个路径**，
  跨层推算自动消失；
- LibreChat 的 `/upload` 接口本质也是这个思路——传**文件内容**而不是路径，
  彻底回避路径问题。我们的场景文件可能很大（用户 workspace），传内容不现实，
  但共享卷能达到同样效果；
- 实现代价最小：compose 里两个服务都挂 `appdata` 卷，约定子路径即可。

留给后续决策的点：`user_id` → 目录名要做**规范化**（现在 `_reject_unsafe_segment`
在做），这个函数要跟着搬到「谁算路径」的那一侧。

### 4.4 接口草案

```http
POST /v1/exec
Authorization: Bearer <短时 JWT>
Content-Type: application/json
{
  "user_id": "u_c56b8337dd09",
  "root": ".subagents/co_xxx/worker_c",   // workspace 内相对子目录
  "code": "print(1)",
  "code_type": "python",                   // python | sh
  "timeout_s": 60,
  "session_id": "...", "generation_id": "...", "agent_id": "..."
}
→ 200 {
  "exit_code": 0,
  "stdout": "...",
  "stderr": "...",
  "duration_ms": 1234,
  "truncated": false
}
```

关键约束（沿用现行 MVP 的铁律）：

1. **`user_id` 只能来自服务端认证上下文，不能来自请求体**——或者说，请求体里的
   `user_id` 必须与 JWT 里的 subject 一致，不一致直接 401。
2. **不静默降级**：服务不可用时，app 要么明确失败，要么在工具结果里写明「本次未隔离」。
3. **工具名/schema/返回格式不变**——对模型完全透明。

## 5. 分阶段路线

### 阶段 0（现在就该做，成本极低）

这三件事**无论最终拆不拆都有价值**：

1. ✅ **路径按平台分流**（已做）：`default_sandbox_root(is_windows)` +
   compose 显式 `HLZ_SANDBOX_WORKSPACES_DIR`
2. ✅ **镜像依赖补齐**（已做）：两个镜像同一套包 + CJK 字体 + `MPLCONFIGDIR`
3. ⬜ **`app/sandbox/` 的反向依赖清掉**：把 `_host_workspace` 里的
   `from ..workspace import write_root_for` 改成注入（构造函数传入一个 resolver）。
   这样该模块**零 app 依赖**，将来无论原地留还是搬走都容易。

### 阶段 1：先让沙箱在容器里能跑起来

不拆服务，但解决「打不开」：

- app 容器挂 `docker.sock` + 装 docker SDK
- workspace 根改成**宿主机 bind mount**（不能用 Docker 卷内路径）
- 评估挂 socket 的安全代价（这等于给了 app 容器 root 等价权限）

> ⚠️ 这一阶段的安全风险需要单独签字。挂 `docker.sock` 后，容器逃逸的
> 边界基本消失。这是「先跑起来」的必要代价，不是可以忽略的细节。

### 阶段 2：抽成独立服务

- 新服务复用 `app/sandbox/runtime.py` + `pool.py`（这两块本来就没依赖 app）
- 加 HTTP 门面 + 短时 JWT（照抄 LibreChat 的模型）
- app 侧把 `manager.py` 的分流改成 HTTP 客户端
- 共享卷约定路径（§4.3 方案 C）

### 阶段 3：多实例收益兑现

拆完之后才能做的事：

- 一份容器池服务多个 app 实例（现在 3 实例 = 3 份池）
- 沙箱独立扩缩容（沙箱是 CPU/内存密集，app 是 IO 密集，本来就该分开扩）
- 跨实例的沙箱状态可观测

## 6. 不建议现在拆的理由

1. **当前架构下沙箱根本没启用**（`HLZ_SANDBOX_MODE=off`），拆了也没有验证场景
2. 阶段 1 的 docker.sock 问题**拆服务也同样要面对**（服务也得能访问 docker）——
   所以拆分不能绕过这个前置问题
3. 本次事故的直接成因（缺包、路径错位）**已经用更低成本修掉了**
4. 多实例刚上线，还在修正确性问题（见 `20261119-多实例正确性审计.md`），
   同时引入新服务会放大排查面

**结论：把阶段 0 的第 3 项做掉（清反向依赖），其余按需推进。**

## 7. 运行时选型：docker.sock 不是必然，是个默认值

> 本节全部结论来自 `docs/probes/20261119-bwrap可行性实测.sh` 的 **25 项实测**
> （本机 Docker Desktop 4.37.1 / Engine 27.4.0 / 内核 6.18.58.1-WSL2，2026-11-19）。
> 重跑一条命令即可复核；换机器结果可能不同，必须重跑。

### 7.1 先厘清一个概念：隔离能力 ≠ 容器管理能力

| 你需要的是 | 谁提供 |
| --- | --- |
| **隔离**（mnt/pid/net/ipc/uts/cgroup 命名空间 + capabilities + seccomp） | **Linux 内核** |
| **容器管理**（建/删/挂载/exec/日志） | Docker daemon（要 sock）或别的工具 |

实测佐证——进容器看隔离的真实来源：

```
$ docker run --rm python:3.12-slim sh -c 'ls -l /proc/self/ns/'
cgroup -> cgroup:[4026533240]
ipc    -> ipc:[4026533137]
mnt    -> mnt:[4026533135]
net    -> net:[4026533139]
pid    -> pid:[4026533138]
```

这些不是 Docker 造的，是内核造的。Docker 只是**调用这些原语的调度器**。

**所以「沙箱服务要不要挂 docker.sock」取决于它选什么运行时，不是「服务化」的必然后果。**

### 7.2 三种运行时对比（都已实测或已有结论）

| | A. Docker + sock | B. bubblewrap（bwrap） | C. gVisor（runsc） |
| --- | --- | --- | --- |
| 要 docker.sock | **要** | **不要** | **不要** |
| 额外权限 | 挂 sock = root 等价 | userns（**容器内实测可用**） | `/dev/kvm` 或 SYS_PTRACE |
| 逃逸门槛 | **零**（一条 `docker run -v /:/host`） | 需要真内核漏洞 | 需要突破用户态内核 |
| 隔离强度 | 中 | 中 | 高 |
| 实现成本 | 低（Docker 管镜像/rootfs） | 中（自己准备挂载集） | 中高（要装 runsc） |
| 本机可用 | ✅ | ✅（apt 有包） | 未验证 |

对照 LibreChat：它选的是 **A 的变体**——独立的 Code Interpreter 服务，那服务自己管沙箱。
对应到我们这里，阶段 2 的「独立沙箱服务」**并没有规定它必须用 Docker**。

### 7.3 bwrap 实测结果（25/25 通过）

| 验证项 | 实测结果 |
| --- | --- |
| apt 可安装 | `bubblewrap 0.12.0-1~deb13u1`，二进制 80 KB |
| Docker 默认 seccomp 下建 userns | ✅ 拿到 7 个 namespace（cgroup/ipc/mnt/net/pid/user/uts） |
| 网络断开 | ✅ 只剩 `lo`；`create_connection(("1.1.1.1",443))` → `OSError` |
| 文件系统隔离 | ✅ 最小挂载集下 `ls /` 只有 `bin dev lib lib64 proc sbin tmp usr ws` |
| 写入边界 | ✅ `/ws` 可写；`/usr` → `Read-only file system` |
| `--cap-drop ALL` | ✅ `CapEff: 0000000000000000`；`mount`/`chroot`/`mknod` 全 EPERM |
| `NoNewPrivs` | ✅ `1` |
| 进程隔离 | ✅ 沙箱内见 2 个进程，容器内真实 23 个 |
| 启动开销 | ✅ **4~6 ms/次**（`/bin/true` 对照 0 ms） |
| 中文字体 | ✅ 最小挂载集 + `/etc/fonts` 下 matplotlib 见 21 个字体，含 `Noto Sans CJK JP` |
| pandas / matplotlib 真实跑通 | ✅ 生成 PNG 成功 |

**结论：bwrap 在本机容器里可用，不需要任何额外 privilege 参数，不需要 docker.sock。**

### 7.4 bwrap 的五个坑（全部实测踩到的，直接抄会出事）

#### 坑 1：`--ro-bind / /` 会把 app 的 `.env` 暴露给沙箱【严重】

```
$ bwrap --unshare-all --ro-bind / / ... sh -c 'cat /fakeapp/backend/.env'
DB_PASSWORD=leak-me        ← ✗ 只读，但读得到
```

这是最容易犯的错——`--ro-bind / /` 写起来最省事。模型只要 `cat` 一下，密钥就进了对话历史。

**必须用最小挂载集**：

```sh
--ro-bind /usr /usr --ro-bind /lib /lib --ro-bind /lib64 /lib64 \
--ro-bind /bin /bin --ro-bind /sbin /sbin \
--tmpfs /etc --ro-bind /etc/fonts /etc/fonts \
```

实测这样 `.env` 读不到，`ls /` 只剩 8 项。

#### 坑 2：`--ro-bind /etc/fonts /etc/fonts` 会让 `/etc` 变可写【易漏】

bwrap 会为挂载点**自动创建父目录 `/etc`**，而这个自动建的父目录**是可写的**：

```
$ bwrap ... --ro-bind /etc/fonts /etc/fonts ... sh -c 'echo x > /etc/hosts; echo $?'
0        ← /etc/hosts 凭空出现，写入成功
```

不是逃逸（写入只存在于本次 mnt namespace，另起一个沙箱就没有了，实测确认），
但**同一沙箱内派生的子进程会继承**——足够写 `/etc/ld.so.preload` 影响自己后续起的进程。

**修法**：先 `--tmpfs /etc` 占位，再往上叠分支。实测后 `ls /etc` 只剩 `fonts`。

#### 坑 3：不加 `--clearenv` 会把 app 的环境变量全漏给沙箱【严重】

```
不加 --clearenv:  DB_PASSWORD=[super-secret-db-pass] OPENAI_API_KEY=[sk-leak-me]
加   --clearenv:  DB_PASSWORD=[] OPENAI_API_KEY=[]
```

**必须 `--clearenv` + 显式 `--setenv PATH/LANG/HOME/...`。**

#### 坑 4：`--uid 1000` 是「假降权」，导致 `RLIMIT_NPROC` 静默失效【关键】

```
沙箱内 id        : uid=1000 gid=1000
/proc/self/uid_map: 1000  0  1      ← 内核视角的 uid 仍然是 0
```

bwrap 的 `--uid` 只在 userns **内部**改显示。于是：

| 容器以 root 跑 | 容器以 uid 1000 跑 |
| --- | --- |
| ✗ `RLIMIT_NPROC=20` 起了 **60** 个进程，限制形同虚设 | ✅ 拦在第 **18** 个（`BlockingIOError`） |

`RLIMIT_NPROC` 限的是「同一 real uid 的总进程数」，内核**不对 root 执行**这个限制。

**结论：防 fork 炸弹必须让 app 容器本身跑非 root（`user:` in compose），在 bwrap 里加 `--uid` 没用。**

#### 坑 5：`prlimit --as` 只管单进程，不是组总量

bwrap 自己**不做任何资源限制**（`bwrap --help` 里没有 mem/cpu/pids 参数），只能外挂 `prlimit`。但：

```
$ prlimit --as=500M  →  父进程占 300MB，再起 4 个子进程各占 300MB
子进程成功: 4/4    ← 共 1200MB，远超 500MB 限额
```

实际峰值是 `NPROC × AS`。防得住「单个进程吃爆内存」，防不住「fork 一批每个吃一点」。

- `RLIMIT_AS` → ✅ 单进程 `MemoryError`（实测）
- `RLIMIT_CPU` → ✅ `Killed rc=137`（实测）
- `RLIMIT_FSIZE` → ✅ `OSError`（实测）
- **组总量 → ❌ 需要 cgroup v2 `memory.max`**

这条是 bwrap 相对 Docker 的实质缺陷：Docker 的资源限制本来就是 cgroup 组总量。

### 7.5 逃逸难度对比（同一次会话里实测）

挂着 `docker.sock` 的容器，一条只读探测就看到宿主机全部容器：

```
$ curl -s --unix-socket /var/run/docker.sock http://localhost/containers/json
"Names":["/hlzscale-app-1"]  "Names":["/hlzscale-app-2"]
"Names":["/hlzscale-app-3"]  "Names":["/hlzscale-nginx-1"]
```

之后 `docker run -v /:/host alpine cat /host/etc/shadow` 就出去了——**不需要任何漏洞利用**。

bwrap 沙箱里同样的尝试：

```
ls /var/run/docker.sock  → 不存在（也没挂进来）
mount -t tmpfs           → rc=32 (EPERM)
chroot /                 → rc=127 (EPERM)
CapEff                   → 0000000000000000
NoNewPrivs               → 1
```

**「逃逸半径相同」不等于「逃逸难度相同」。** docker.sock 方案是「门没锁」，
bwrap 方案是「锁很结实」。

### 7.6 推荐

```
如果沙箱和 app 同机  →  选 B（bwrap），不挂 docker.sock
                        代价：自己准备挂载集；资源限制只能 per-process
如果要多租户强隔离    →  选 C（gVisor），见 20261112-gVisor多租户沙箱调研.md
如果只是先跑起来      →  选 A（Docker + sock），但必须承认逃逸门槛为零
```

**注意 B 的一个现实约束**：bwrap 复用**宿主进程的文件系统**，它本身不提供独立 rootfs。
所以沙箱能用的包必须装在 app 镜像里——这正是 `backend/requirements.txt` 与
`backend/sandbox/Dockerfile` 两份清单必须同步的原因（`tests/test_image_dependencies.py` 在双向校验）。
选 B 意味着**放弃「沙箱镜像是独立镜像」这个隔离层**，包清单只剩 app 镜像一份。

反过来，选 A 保留了独立沙箱镜像（`hlz-sandbox:2026-11-18`），但没有 sock 就用不了。

> 本节**未经生产验证**：所有实测都在「容器内跑 bwrap」这个形态下完成，
> 没验证过「沙箱服务作为独立容器、它的子进程是 bwrap」的部署形态。
> 也没验证 bwrap 在 Linux 原生内核（非 WSL2）上的行为差异。

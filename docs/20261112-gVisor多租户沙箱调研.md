# gVisor 调研：能否作为 Hlaudz 多租户代码执行沙箱

> 日期：2026-11-12　状态：调研 + 本机环境核查（gVisor 本身未在本机跑起来，原因见 §4.2）
> 前置：`docs/20261112-Anthropic沙箱方案调研与多租户适用性.md`（结论：srt 不能当多租户边界，指向 gVisor）
> 本文回答：gVisor 到底是什么、代价多大、能不能上、怎么接到 Hlaudz。

## 0. 结论

**方向是对的。gVisor 是目前「多租户不可信代码执行」最现实的起点**，理由：

1. **它真的是边界，不是护栏。** 用户态内核（Sentry）自己实现 Linux 系统调用，
   应用的系统调用不直达宿主内核。这与 srt（OS 原语、共享内核）有本质区别。
2. **有超大规模生产先例。** Google Cloud Run、DigitalOcean App Platform 都用它跑
   任意用户代码；蚂蚁（Ant）生产环境部署过 **10 万+** gVisor 实例。
3. **开销可接受，且不惩罚 CPU 密集型。** 蚂蚁的数据：**70% 应用开销 <1%，另 25% <3%**。
   CPU 指令原生执行，**零额外开销**。

**但有三个必须先解决的硬约束**：

| 约束 | 影响 |
|---|---|
| **只有 Linux**（Linux 5.6+，x86_64/ARM64） | 你的 Windows 开发机不能直接跑。要 WSL2 + 真 Docker Engine，或上 Linux 服务器 |
| **系统调用重负载会明显变慢** | 网络吞吐、小文件随机读、VFS 密集操作是弱项。Agent 的「写代码→跑脚本」恰好偏这类 |
| **syscall 兼容性有缺口** | `io_uring` 默认关、块设备不能挂、`KVM in sandbox` 不支持。Python/Node/Java/Go/PHP 官方跑回归测试，实践上多数能跑 |

不是「装上就完事」——它要求你把执行层从「本地起子进程」改成「每次起一个沙箱容器」，
架构上是一次真实改造。详见 §5。

## 1. gVisor 到底是什么

### 1.1 架构：Linux on Linux 的纵深防御

```
 应用进程（普通 Linux ELF，不改代码）
      ↓ 系统调用被拦截
 Sentry —— 用 Go 写的「用户态应用内核」，自己实现 Linux syscall
      ↓ 只发出约 55 个经过白名单的宿主系统调用
 宿主 Linux 内核
      ↑
   Gofer —— 独立进程，代理文件访问（9P 通道）
```

关键点（来自 USENIX HotCloud'19 论文与官方文档）：

- Sentry 暴露 319 个 Linux 系统调用中的 **211 个**，用宿主 **55 个**系统调用实现。
- **`open` 和 `socket` 特意不在白名单里**——它们是常见攻击面。gVisor 的存储栈与网络栈
  专门设计成不需要它们。
- 文件访问分三条路径：Sentry 内部文件系统（tmpfs/procfs/overlayfs）直接服务；
  外部文件由 **Gofer** 通过 9P 代开；拿到句柄后再读写宿主。
- **「Linux on Linux」的价值**：攻击者即使打穿 Sentry，也只拿到一个被 seccomp
  严限的用户态进程；而打穿 runc 容器可能直接拿到宿主 root。

### 1.2 三个平台（这是最影响选型的性能因素）

| 平台 | 机制 | 何时用 |
|---|---|---|
| **KVM** | Sentry 作为 guest OS 跑在 VM 里 | **裸金属**上性能最好。嵌套虚拟化下很差，官方不建议生产 |
| **systrap**（默认） | 用 `seccomp(SECCOMP_RET_TRAP)` 让内核给线程发 `SIGSYS`，交给 Sentry | **在 VM 里跑就用这个**，最灵活 |
| ptrace | 像调试器附加 | 已不再支持，计划移除 |

**实践含义**：如果你把 Hlaudz 部署在云主机（本身就是 VM）上，用默认的 `systrap`。
如果在裸金属上，切 KVM 能拿到明显更好的性能。

> 这一点对成本估算很关键：云上跑 = systrap = 比裸金属 KVM 慢一档，
> 但仍是「有边界」的可接受水平。

## 2. 开销到底多大（用数字说话）

### 2.1 CPU：零开销

> gVisor does not perform emulation or otherwise interfere with the raw execution
> of CPU instructions. Therefore, there is **no runtime cost imposed for CPU operations**.

sysbench CPU 与 TensorFlow CNN 训练都验证了这一点。**纯计算任务（数据处理、ML）
几乎不吃亏**——这对 agent 场景是好消息，因为模型生成的代码经常是计算密集的。

### 2.2 内存：小且固定

官方定位 **Sentry 基础内存约 15 MB**，是「小、且基本固定」的开销，
不随应用内存线性增长（会随打开的 socket / 文件数增长）。

对比：Agent SDK 官方建议 **每 agent 1 GiB RAM**。所以「gVisor 太重」这个印象是错的——
重的是 agent 运行时（Node/Python + 依赖），不是沙箱本身。

### 2.3 系统调用：结构性成本

| 指标 | 数字 | 来源 |
|---|---|---|
| 空 syscall 开销 | 原生 ~70ns，Sentry 内实现 ~800ns（**约 11×**） | Ant 生产博客 |
| `getpid` | native 62ns / runsc-KVM 830ns | 同上 |
| syscall 平均 | **2.2× 慢** | HotCloud'19 |
| ptrace 平台 | **42–232× 慢**（这就是它被弃用的原因） | 同上 |

注意：**「800ns vs 70ns」听起来吓人，但绝对值是微秒级**。对「跑一段 Python 脚本」
这种每次 syscall 之间都有实际计算量的负载，摊薄后影响很小。

### 2.4 真正的弱项（这三项对 agent 有影响）

| 场景 | 开销 | 对本项目的含义 |
|---|---|---|
| **文件 open**（外部 tmpfs） | **216× 慢** | 大仓库里逐个文件扫描会疼 |
| **小文件随机读** | 比 runc 慢约 11×（第三方复现） | `file_grep`/`file_glob` 这类操作会受影响 |
| **网络大流量下载** | 1GB 文件吞吐约 **34%**（KVM）/ 54%（ptrace） | 小下载（1MB）基本无差 |

**关键缓解**：Google 2023 年做的 **rootfs overlay** 优化，把 `fsstress` 从 262s 降到 3.18s
（官方同时强调这是微基准，别外推）。说明这块在持续改善。

**实践建议**：让 sandbox 内的热点文件走 Sentry 内部 tmpfs，而不是 bind mount 宿主目录。
官方也说「配置更激进的缓存策略」。

### 2.5 启动：毫秒级

官方首页明确写 **containers start up in milliseconds**，且**动态分配/释放宿主内存**
（不像微虚拟机有 ballast 与 guest boot）。

⚠️ 但注意：官方性能页的 startup benchmark 走 Docker，而**大部分时间耗在 Docker 本身**
（官方自己指出 empty runc 基准就很慢）。要规避这层开销，用 `runsc do` 或直接调 OCI runtime。

**对 Hlaudz 的含义**：如果你的 `code_run` 每次都起一个沙箱容器，走 Docker 路径会慢；
走 `runsc do` / OCI 直调才能拿到毫秒级。这是实现层面的关键选择。

## 3. 安全强度：它能挡住什么

| 威胁 | runc | gVisor |
|---|---|---|
| 应用利用内核漏洞提权 | 直通宿主内核，危险 | Sentry 拦截，最多打穿到一个 seccomp 严限进程 |
| 容器逃逸到宿主 | 可能 | 需先攻破 Sentry，再突破 55 个 syscall 的 seccomp |
| 读取其他租户数据 | 依赖 namespace 正确配置 | 独立用户态内核，天然隔离 |

**官方明确定位**：gVisor 首页现在的标题就是 **"The Sandbox Kernel for Agents"**，
明确面向 AI agent 场景，主打「container-native pod density, instant cold starts,
dynamic host memory allocation without requiring nested virtualization」。

### 3.1 但必须知道它不保证什么

官方 Compatibility 文档如实列了缺口：

- **资源限制在沙箱内不生效**：in-sandbox cgroup 可做记账，但**不能在同沙箱内的进程间执行限制**。
  要限资源得把 gVisor 放进宿主的 Linux cgroup（即外层限制）。
- 块设备文件系统（fat32/ext3/ext4）不能从沙箱内挂载——只能在宿主挂好再暴露。
- **`io_uring` 默认关闭**（开启也仅基本 I/O）。
- 沙箱内不能用 KVM；自定义硬件设备文件一般不支持（例外：NVIDIA GPU / TPU）。
- **当 K8s runtime 用时**还有额外功能缺口（GKE Sandbox 有一张不兼容清单）。

对本项目的实际影响：agent 跑的多是 Python 脚本 + 文件读写 + 偶尔网络请求，
**多数在兼容范围内**；但如果你要做「在沙箱里跑数据库」「跑需要 io_uring 的高性能服务」，
那不适合。

## 4. 本机（Windows）可行性

### 4.1 硬约束：gVisor 只有 Linux

官方 FAQ：**"Today, gVisor requires Linux."** 安装页要求 **Linux 5.6+**，
支持 x86_64 / ARM64。

**Docker Desktop 不行**——它的引擎跑在 Docker Desktop 自己的 VM 里，
你无法往那个引擎里注册 `runsc` 这个 OCI runtime。
正确做法：**在 WSL2 里装一个真正的 Docker Engine，再在里面装 gVisor**。

### 4.2 你这台机器的现状（已核查环境，未安装 gVisor）

```
Docker Desktop 27.4.0 已装，docker-desktop 发行版状态 Stopped（引擎当前没起）
WSL 版本 3.0.5.0，内核 6.18.58.1-microsoft-standard-WSL2  ← 满足 gVisor 要求（≥5.6）
WSL 里只有 docker-desktop 一个发行版，且它是 Alpine（只有 apk，没有 apt）
```

**结论：内核够，但没有可用的 Linux 发行版来做验证。** 有两个坑：

1. **不能往 `docker-desktop` 那个发行版里装 gVisor。** 它是 Docker Desktop 自己管的
   系统发行版，改动可能弄坏 Docker Desktop。而且它是 Alpine，官方 apt 源用不了。
2. **Docker Desktop 的引擎不能注册 `runsc`。** 它跑在 Desktop 自管的 VM 里，
   你无法往那个引擎加 OCI runtime。这是 Docker Desktop 的固有限制，不是配置问题。

所以要走一遍：新建一个独立 Ubuntu 发行版 → 装**真** Docker Engine → 装 gVisor。

```powershell
# 1) 装一个独立 Ubuntu 发行版（不要往 docker-desktop 里动）
wsl --install -d Ubuntu-24.04

# 2) 关键：关掉 Docker Desktop 对这个新发行版的 WSL 集成
#    Docker Desktop > Settings > Resources > WSL integration > 关掉 Ubuntu-24.04
#    否则 docker CLI 指向 Docker Desktop 的引擎（没有 runsc）

# 3) 在新 Ubuntu 里装 Docker Engine（不是 Docker Desktop）
sudo apt-get update
sudo apt-get install -y ca-certificates curl
sudo apt-get install -y docker-ce docker-ce-cli containerd.io

# 4) 装 gVisor
sudo apt-get install -y runsc
sudo runsc install
sudo systemctl restart docker

# 5) 验证
docker info --format '{{json .Runtimes}}'   # 应包含 "runsc"
docker run --rm --runtime=runsc hello-world
```

⚠️ 一个容易踩的坑：**代码要放在 Linux 文件系统里**（`/home/...`），
不要放 `/mnt/c/...`——后者是 Windows 文件语义，又慢又可能行为不一致。

⚠️ 上面这些步骤我**没有实际执行**。它们要做的是下载约 500 MB 发行版、
安装系统级服务、重启 Docker——属于会改动你机器状态的操作，应该由你决定是否做。

### 4.3 开发 vs 生产的现实建议

| 环境 | 建议 |
|---|---|
| 你的 Windows 开发机 | WSL2 + Docker Engine + runsc，够做功能验证 |
| 生产 | **Linux 服务器**（裸金属优先，可用 KVM 平台）；云主机用 systrap |

**不建议**在生产把 Windows + WSL2 + gVisor 当主线——多一层间接、多一层不确定性。
Hlaudz 后端本身是纯 Python，迁到 Linux 没有代码障碍（除了 Windows 特定的
`creationflags` / powershell 分支，那些只在 `code_run` 里）。

## 5. 如果要接进 Hlaudz：架构影响

### 5.1 现状

`code_run` 的实现（`backend/app/builtin_tools.py:195`）是：

```python
cmd = [sys.executable, "-X", "utf8", "-u", "-c", WORKSPACE_PYTHON_GUARD, tmp_path, str(cwd)]
proc = await spawn_process(cmd, cwd=str(cwd), env=workspace_env(cwd), ...)
```

即在**后端进程所在的机器上直接起子进程**，隔离靠 `run_guard.py` 的写入边界
（它自己注释写明「不是操作系统级沙箱」）。

### 5.2 改造点

要接 gVisor，最小改动是**替换 `spawn_process` 这一层**：

```python
# 伪代码：把「本地起进程」换成「起一个 runsc 沙箱」
cmd = [
    "docker", "run", "--rm", "--runtime=runsc",
    "--network=none",                        # 默认无网
    "-v", f"{user_workspace}:/work",         # 只挂该用户 workspace
    "-w", "/work",
    "--memory=512m", "--cpus=1",             # 资源限制靠外层（见 §3.1）
    "--read-only",                            # 只读根
    "hlaudz-sandbox:latest",                  # 自带 python 的镜像
    "python", "/work/<script>.py",
]
```

需要注意的具体问题：

1. **workspace 挂载的写权限**：`-v` 默认读写。要让 `file_write` 等工具产生的文件
   对沙箱可见，必须挂载；但挂载本身就是「沙箱能写宿主目录」——这削弱了隔离。
   gVisor 内部写文件仍然受 Sentry 管辖，但**写出去的文件落在宿主**，
   所以 `run_guard.py` 的路径校验**仍然需要保留**（两层防御）。
2. **网络**：gVisor 沙箱默认可以把网络全禁（`--network=none`），
   这对「只跑计算脚本」的 code_run 是合适的默认。需要联网时单独放开并按域名白名单。
3. **冷启动**：走 `docker run` 有 Docker 自身开销。要毫秒级得用 `runsc do` 或
   OCI 直调，或做**沙箱池**（预热 N 个，取用/归还）。
4. **文件交换**：脚本源码现在写 `tempfile.mkstemp`，Linux 上要写进挂载目录内。
5. **退出码 / stdout**：现有 `format_code_run_header` 与 `ProcessLease` 的语义可保持，
   只是 `proc` 变成 docker 客户端进程，`_kill_tree` 要改成 `docker kill`。
6. **停止级联**：现在的 `process_registry` 靠进程树 kill。容器要改成按容器名/ID kill，
   否则 `/stop` 会留下跑着的沙箱。

### 5.3 建议的落地顺序

1. **先在 WSL2 里验证可行性**（§4.2），确认 `docker run --runtime=runsc` 能跑
   你现有 `workspace_env` 那套 Python 脚本；
2. **做一个开关**（如 `CODE_RUN_BACKEND=docker|local`），两种并存，不破坏现状；
3. 先只在「不可信输入」路径上启用（比如 A2A 外部调用面，那里本来就有 `tool_policy` 分级）；
4. 做沙箱池再谈性能（否则每个 code_run 都吃一次启动开销）。

**不要一步到位**。这是安全基础设施，最怕「改了一半、两种路径语义不一致」。

## 6. 与其他方案对比（含 srt，把上一份文档的结论放这里对照）

| 方案 | 隔离 | Linux | Windows | 冷启动 | 开销 | 多租户 |
|---|---|---|---|---|---|---|
| 现状（进程内写边界） | 无 OS 边界 | ✅ | ✅ | 0 | 0 | ❌ |
| **srt** | OS 原语（共享内核） | ✅ | alpha | 进程级 | 近零 | ❌ 官方明确不建议 |
| Docker + seccomp/AppArmor | 容器（共享内核，加固） | ✅ | ✅ | 秒级 | 低 | ⚠️ 需严格配置 |
| **gVisor** | **用户态内核** | ✅ 仅 | ❌ | **毫秒级**（非 Docker 路径） | CPU 零开销，I/O 明显 | ✅ 生产验证 |
| 微虚拟机（Firecracker/libkrun） | 独立内核 | ✅ | ❌ | <100ms | 略高（guest boot） | ✅ 强 |
| 每租户独立 VM | 硬件级 | ✅ | ✅ | 秒—数十秒 | 高 | ✅ 最强 |

**gVisor 的位置**：在「足够安全」与「足够轻」之间，目前性价比最好的一档。
微虚拟机隔离更强但冷启动与内存更贵；srt 更轻但没有边界。

**Anthropic 自己的选择印证这点**：claude.ai 的代码执行用 **gVisor 容器**，
理由原文是「保护我们自己的基础设施和**租户彼此**」。他们不是随口选的。

## 7. 一句话总结与建议

- **gVisor 值得做**，它是「多租户不可信代码」的正确答案之一，有 Google Cloud Run /
  DigitalOcean / 蚂蚁 10 万实例背书。
- **但它是 Linux-only**，你的 Windows 开发机要靠 WSL2，生产应该直接上 Linux。
- **开销集中在 I/O 与网络**，CPU 与内存几乎不吃亏——这对 agent 的「跑计算脚本」
  场景是有利的。
- **不是装上就完事**：要把 `code_run` 从「本地子进程」改成「沙箱容器」，
  并且处理好挂载、`/stop` 级联、冷启动（沙箱池）。

**我的建议顺序**：先在 WSL2 做一次 `docker run --runtime=runsc` 跑通现有 Python 脚本
（半天工作量，能证伪也能证实），拿到真实数字再决定要不要投入生产改造。
不要凭 benchmark 直接拍板——那些数字来自 2019 年的论文和 2021 年的蚂蚁博客，
你的负载完全不同。

# 上游 LLM 偶发失败排查 Note

> 日期：2026-11-05
> 状态：初步排查，暂不实施
> 范围：`use 2 subagents 分别查询 2026年1月和2月的全国家宽用户数量`

## 1. 结论先行

**现有证据更支持“上游流式响应偶发未完整结束/网关错误”是主因，但还不能只归咎于上游。**

本次会话最终是成功的：两个 subagent 都 `completed`，主代理输出了 2026-01 / 2026-02 的完整结果。用户看到 `no complete response` 后关闭、重新输入“继续”，第二次请求成功，符合“临时性上游故障 + 当前没有完整重试兜底”的表现。

但代码侧确实有一个独立缺口：

- 当前只对 HTTP `408/409/425/429/5xx` 和连接/读取异常做有限重试；
- 重试还附加了 `not got_any` 条件，一旦已经收到任何文本/思考增量，就不会自动重试；
- 流正常结束但没有 `response.completed`、没有内容、没有 tool_call 时，没有“响应不完整”的判定；
- `AgentLoop` 会把这种空结果当作一轮成功，继续下一次模型调用，而不是立即重试同一请求。

因此：**上游不稳定是触发因素，重试覆盖不完整是放大因素。**

## 3. 已定位的代码缺口

### 3.1 重试范围过窄

`backend/app/llm_client.py::LLMClient.run()`：

```text
HTTP 可重试状态码       -> 最多 max_retries 次
连接/超时/读取异常       -> 最多 max_retries 次
但前提均为 not got_any
```

已有默认值：`LLMSettings.max_retries = 2`，用户配置层 `config.py` 默认为 3；数据库用户配置当前走 `llm.py` 默认 2。也就是说系统不是“完全没有重试”，而是重试条件和场景不完整。

### 3.2 “无完成语义”没有校验

Responses 线只在收到 `response.completed` 时记录 usage，但没有用“是否看到完成事件”作为成功条件。若上游：

- 返回 200 后流突然结束；
- 只发 keepalive / 空事件；
- 发送了 `[DONE]` 但没有内容；
- 网关把异常吞掉后关闭连接；

当前代码可能返回一个空的 `ChatResult`，随后由 agent loop 进行下一轮，最终表现为 `no complete response` 或空回复。

### 3.3 已输出内容后的重试策略需要谨慎

不能在已有 `text_delta` 后无条件重放同一请求，否则会：

- 前端重复显示半截内容；
- 工具调用重复执行（尤其是查询类工具虽然只读，但未来可能有写工具）；
- 账单重复计费。

因此重试需要区分：

1. **尚未产生任何可见增量**：可安全重试整个模型请求；
2. **已产生增量但链路异常**：可选择“保留已显示内容 + 提示中断 + 用户手动继续”，或做带幂等边界的安全续写；
3. **工具已开始执行**：不得盲目重放，除非工具具备幂等键。

## 4. 建议的明天实施方案

### P0：轻量、低风险

1. 在 `llm_client.py` 中增加响应完整性判定：
   - Responses 线：必须见到 `response.completed` 或合法 `response.failed/incomplete`；
   - Chat 线：必须见到 `[DONE]`，或至少在流结束后能确认有有效内容/tool_call；
   - 无内容且无工具调用时抛出可分类的 `LLMError`，不要静默当作成功。
2. 对所有“未产生任何增量”的上游异常增加指数退避重试：
   - `429/5xx/408`、连接失败、读取中断、空响应；
   - 尊重 `Retry-After`；
   - 退避建议：0.5s、1s、2s，带少量随机抖动。
3. 在错误信息中保留 provider / status / request-id / 阶段（connect、stream、empty、truncated），避免只看到一句 `no complete response`。

### P1：产品体验

1. SSE 增加“正在重试”状态（可选事件），让用户知道系统在处理，而不是卡住；
2. 已达到重试上限时，明确提示“上游模型暂时不稳定，本次已保留已生成内容”；
3. 前端提供“重试本轮”按钮，而不是要求用户关闭后重新输入“继续”；
4. 对子代理错误统一写入 `error` 和 `turns`，便于后续定位。

### P2：高级可靠性

1. 为工具调用引入幂等键，支持“已执行工具后安全重试”；
2. 主代理 / 子代理分别配置重试预算，避免 fanout 时把 2 个失败放大成多倍费用；
3. 按 provider 记录失败率、首字节延迟、流截断率，形成可观测指标；
4. 对长流增加 heartbeat/stall timeout，而不是只依赖总超时。

## 5. 暂不修改的原因

本次按要求只做排查和 note。当前代码已经提交稳定版本，明天应先补测试再改重试：

- 单元测试应覆盖 HTTP 429、连接失败、流截断、空响应、`response.failed`；
- 必须验证“未产生增量时重试”和“已产生增量时不重复输出”；
- 真实 LLM E2E 需要观察 subagent 并发下的行为。

## 6. 明确结论

**不是“重试机制完全没有”，而是“重试没有覆盖流式响应已建立后的失败，也没有把空/不完整响应判为失败”。**

明天建议优先做 P0 的“完整性校验 + 无增量安全重试”，暂不要做“任意阶段自动重放”，以免带来重复内容、重复工具执行和重复计费。

# 主 Agent 轮数上限从 48 提升到 300

> 日期：2026-11-06  
> 状态：已实施并验证  
> 影响范围：主 Agent、每轮 Team Runtime；子代理上限不变
> 后续修订（2026-11-06）：Agent Team 联调确认子代理默认 24 也会造成 writer/reviewer 过早停止；`SubagentRuntime` 默认已提升为 300，并打通 `spawn_teammate(max_turns=...)` 全链路。详见 `docs/20261106-AgentTeam轮次与跨轮任务恢复修复.md`。

## 背景

真实测试中复杂任务触发了：

```text
达到最大轮数 48，已停止
```

48 轮对需要大量文件读取、代码执行、子代理协作与校验的任务偏小，提前终止会掩盖“任务尚未完成但其实仍在正常推进”的情况。

## 本次调整

| 位置 | 原值 | 新值 | 说明 |
|---|---:|---:|---|
| `backend/app/agent.py` 主 Agent | 48 | 300 | `AGENT_MAX_TURNS` 环境变量仍可覆盖 |
| `backend/app/agent_loop.py` 构造默认值 | 48 | 300 | 与主 Agent 默认保持一致 |
| `backend/app/subagent/session.py` 每轮 Team Runtime | 48 | 300 | 保证 Team 派生 loop 不提前截断 |
| `backend/app/subagent/runtime.py` 子代理 | 24 | 24（不变） | 单子代理仍是独立资源闸门，避免无限消耗 |

优先级不变：

```text
AGENT_MAX_TURNS > AGENT_RECURSION_LIMIT > 代码默认值 300
```

子代理仍由 `SUBAGENT_MAX_TURNS`（默认 24）与墙钟超时双重约束。

## 设计考虑

- 主 Agent 的“轮数”不等于工具次数：一次模型回合可包含多个工具调用；
- 提高到 300 只是放宽上限，不改变 `max_turns` 到达时的错误语义与停止行为；
- 子代理不跟随提高到 300，是为了避免异常子任务长期占用用户/团队槽位；
- 如部署方需要更严格限制，仍可在环境中设置 `AGENT_MAX_TURNS`。

## 验证

- 后端全量测试：`119 passed, 1 warning`
- 运行时断言：
  - `AgentLoop default max_turns = 300`
  - `Team session default max_turns = 300`
- 8000 热加载已完成，`/api/health` 返回 200。

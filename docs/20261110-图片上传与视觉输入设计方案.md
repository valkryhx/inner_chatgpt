# 图片上传与视觉输入（多模态）设计方案

> 日期：2026-11-10
> 状态：**已实施**（见 `docs/20261110-changelog-图片上传与视觉输入.md`）
> 一句话：让用户能在对话里贴图/传图，后端把图存成文件、消息里只存引用，送模型时按需转成
> `image_url` / `input_image` 数据块。

---

## 1. 背景与目标

Hlaudz 现在能**展示**图片（workspace 产物 + `/api/me/workspace-image` 鉴权读取），但**不能接收**
用户上传的图片，也没有把图片送进模型的能力。

目标：

1. 用户能上传/粘贴/拖拽图片，随消息一起发送；
2. 模型能看到图（多模态输入），并能基于图片回答；
3. 历史消息回看时图片还在（多轮对话里模型也能再看到）；
4. 不破坏现有契约：`SendMessageIn.text` 仍是必填，旧客户端不受影响。

非目标（本阶段不做）：图片理解后的 OCR/检索索引、图片自动压缩重编码、A2A 传图、
跨用户共享图库。

---

## 2. 关键决策：图片存哪里

**决策：存文件系统，放该用户 workspace 下的 `uploads/` 子目录；数据库只存引用。**

```text
backend/data/workspaces/<user_id>/uploads/<uuid>.<ext>
```

理由：

| 方案 | 评价 |
| --- | --- |
| **文件系统 + workspace/uploads（选用）** | 复用现有用户隔离目录；复用现有 `/api/me/workspace-image` 鉴权读取（前端缩略图不需要新接口）；模型还能用 `code_run` 读它做二次处理；`backend/data/` 已在 `.gitignore` 里，不会进仓库 |
| 数据库 BLOB / base64 字段 | 25MB 上限 × 每轮 → DB 与 WAL 迅速膨胀，备份变慢；查询也要多一次解码 |
| 独立 `backend/data/uploads/<user>/` | 目录更"干净"，但要再写一套鉴权读取路由，等于重复 `media.py` |

代价（明确写出来）：workspace 里会多一个 `uploads/` 目录，模型的 `list_files` 能看到；
删除消息不会自动删文件（后续可加 GC，本轮不做）。

命名：`<uuid4>.<ext>`，扩展名从真实 MIME 推导，**不采用用户文件名**，避免路径穿越与重名。
用户原始文件名只作为展示字段存进消息引用里。

---

## 3. 数据模型

消息表 `messages.blocks` 里加一个用户消息块（不改表结构）：

```json
{
  "type": "attachments",
  "items": [
    {"path": "uploads/8f3c....png", "name": "截图.png", "mime": "image/png", "size": 182734}
  ]
}
```

`messages.content` 保持纯文本，不动。这样：

- 历史回看、token 估算、压缩逻辑全部沿用旧路径；
- 送模型时按 `blocks` 里的引用读文件、转 data URL。

`session_history` 里的 user 消息同样带 `attachments` 字段（与 blocks 同源），
供 `llm_client` 在构造请求时展开。

---

## 4. 接口

### 4.1 上传

```http
POST /api/me/uploads        (multipart/form-data, file=...)
→ 200 {"path":"uploads/x.png","name":"x.png","mime":"image/png","size":1234,"url":"/api/me/workspace-image?path=uploads/x.png"}
```

校验：仅图片 MIME（png/jpeg/gif/webp/bmp/avif/svg 之外的一律 415）、单文件 ≤ 25MB（413）、
落盘路径必须在该用户 workspace 内（越界 403）。

### 4.2 发送

```json
POST /api/sessions/{sid}/messages
{"text": "这张图里是什么？", "attachments": [{"path":"uploads/x.png"}]}
```

后端按 path 回到 `uploads/` 解析并校验属于当前用户，再写进消息块。

### 4.3 展示

前端直接用既有 `/api/me/workspace-image?path=uploads/x.png` 渲染缩略图与原图，
不新增读接口。

---

## 5. 送模型：两种 wire_api 的转换

只改 `llm_client.py` 的两个转换函数，不改协议层：

| wire_api | user content 结构 |
| --- | --- |
| `openai_chat` | `[{"type":"text","text":...}, {"type":"image_url","image_url":{"url":"data:image/png;base64,..."}}]` |
| `openai_responses` | `[{"type":"input_text","text":...}, {"type":"input_image","image_url":"data:image/png;base64,..."}]` |

规则：

- 只有 `role == "user"` 且带 `attachments` 时才展开；没有图时走原来的纯字符串路径，**逐字节不变**。
- 图片按文件读成 base64 data URL（不把 URL 暴露给外部，也不需要模型去拉取）。
- 单条消息最多 4 张图（可配置 `IMAGE_MAX_PER_MESSAGE`），超出直接 400，避免超大请求。
- 历史里过老的图片不重发：只带**最近 N=3 轮**用户消息里的图（`IMAGE_HISTORY_ROUNDS`），
  更早的图退化成 `[图片已省略]` 文本，控制上下文体积。

## 6. 兼容与安全

- `SendMessageIn.attachments` 可选，缺省 → 行为和现在完全一致。
- path 必须落在 `<user>/uploads/` 内（`resolve()` 后校验前缀），拒绝 `..`、绝对路径、符号链接越界。
- 复用 `media.py` 的 25MB 与 MIME 白名单，不另立标准。
- 图片不进 `session_history` 的纯文本，避免把 base64 写进历史导致上下文爆炸。

## 7. 实施步骤

1. `app/uploads.py`：落盘 + 校验 + 读取为 data URL。
2. `POST /api/me/uploads` 路由 + 测试（鉴权、MIME、大小、越界）。
3. `SendMessageIn.attachments` → `_event_stream(attachments=...)` → 消息块 + 历史字段。
4. `llm_client` 两种 wire_api 的图片展开 + 测试。
5. 前端 Composer：选择/粘贴/拖拽 → 立即上传 → 缩略图列表 → 随消息发送；MessageList 渲染用户附图。
6. 真实 E2E：上传一张本地生成的 PNG，问"图里是什么颜色/文字"。

## 8. 风险与未决

- **模型是否支持视觉**取决于用户配的 API；不支持时会收到上游 400，需要在 UI 上把错误原样透出，
  不要吞成"未知错误"。
- 图片不进上下文预算计算（token 估算仍按纯文本），超长图片可能触发上游拒绝；
  靠 §5 的"只带最近 3 轮"兜底。
- 删除消息不删文件（后续 GC）。
- A2A 暂不支持 `file` part 传图。

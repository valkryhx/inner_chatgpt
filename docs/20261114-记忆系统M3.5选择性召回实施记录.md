## 0. 一句话结论

关键词排序有个根本盲点：**它不知道用户在问什么**。用户问「上次那个报错怎么解决的」，
一条标题为「构建失败处理」的记忆应该命中，但两者没有共同词，`_hit_score` 给 0 分。

M3.5 把「记忆清单 + 本轮查询」送一次小模型判相关性。**实测收益 +37.5 个百分点
命中率，首帧开销 4.9 微秒级启动 + 183ms 后台计算（不进 TTFT）**。

**但仍保持默认关闭**，理由与 CC 一致：CC 的默认文件记忆形态根本不跑选择器
（`lSe()` 门控，`tengu_moth_copse` 默认 false），它是「工具存储 / MCP 记忆库」形态的
配套。Hlaudz 的默认形态对齐 CC 的默认形态。

## 1. 量化数据（S-M6 / S-M7）

### 1.1 S-M6 命中率对比

数据集：44 条记忆（12 条目标 + 32 条干扰项）、8 条查询。
**每条查询与目标记忆之间没有字面重合** —— 这是唯一能拉开差距的构造。

| 查询 | 理想 | 关键词 top5 | 选择器 |
|---|---|---|---|
| 上次那个装了新依赖之后就起不来的问题… | build-failure | ✅ 命中 | ✅ 命中 |
| 两个人同时保存的时候报的那个错… | db-lock | ❌ 未命中 | ✅ 命中 |
| 跟你讲技术方案的时候我希望你怎么组织内容 | user-tone | ✅ 命中 | ✅ 命中 |
| 以后你叫我什么来着 | user-call-name | ✅ 命中 | ✅ 命中 |
| 线上能不能下午再发版 | deploy-window | ❌ 未命中 | ✅ 命中 |
| 那个偶尔红一下的测试是哪个文件里的 | test-flake | ✅ 命中 | ✅ 命中 |
| 接口挂了会重试几次 | api-retry | ✅ 命中 | ✅ 命中 |
| 我们这轮要做什么，去哪儿看 | board-url | ❌ 未命中 | ✅ 命中 |

**关键词 62.5% / 选择器 100%（+37.5 个百分点）。**

> **方法论注记：12 条记忆时差距只有 +25%，44 条时是 +37.5%。**
> 原因是 top5 在 12 条里占 42%，关键词瞎排也有大概率撞上。记忆越多，
> 关键词越不够用 —— 这与直觉一致，也说明**批量小的时候不要急着下结论**。
> 第一版就是 12 条、跑出 +25%，我差点以为「提升有限」。

### 1.2 S-M7 首帧开销

| 指标 | 实测 |
|---|---|
| 预取**启动**耗时上限（进 TTFT 的只有这个） | **4.9 ms** |
| 选择器实际 settle 中位数 | 183 ms |
| 关键词路径排序耗时 | < 1 ms |

183ms 完全在后台跑。首轮模型调用时它多半还没算完 —— 那一轮就不注入，
工具步骤之后再看。这正是「不拖慢首 token」的全部秘密。

对比：一次模型调用 3–10 秒，所以 4.9ms 的启动开销是 1/600 – 1/2000。

## 2. 实现

### 2.1 新增 `backend/app/memory_prefetch.py`

| 组件 | 作用 |
|---|---|
| `PrefetchHandle` | 预取句柄：`promise` / `settled_at` / `consumed_on_iteration`（一一对应 CC 的 `Ivi` 返回对象） |
| `start_prefetch()` | 入口闸 + 启动。**不 await** |
| `PrefetchState` | 一个 generation 内的去重集合 / 调用计数 / 会话字节预算 |
| `select_slugs()` | 调小模型选 slug |
| `parse_selector_output()` | 解析 JSON，**只保留 allowed 里的 slug** |
| `SessionBudget` | 整会话累计召回字节记账（对齐 CC 的 `MAX_SESSION_BYTES=61440`） |
| `selector_client_for()` | 造独立小模型 client（用户配置 → llm.yaml → 显式 fallback） |
| `install_prefetch()` | 给 loop 装 factory |

### 2.2 `agent_loop.py` 的两个挂点

对齐 CC 的 `m0848:7294`（启动）与 `:10602`（消费）：

```python
# 轮循环之前 —— 只启动，不等待
self._start_prefetch(history)
while turn < self.max_turns:
    ...  # 模型调用、工具执行
    # 工具步骤之后 —— 已 settle 且未消费过，才注入
    for msg in await self._take_prefetch(turn):
        history.append(msg)
        yield {"type": "message_injected", "text": msg.get("content", "")}
```

**为什么不能合到一个点**：合在「模型调用前」就退化成同步等待（183ms 直接进 TTFT）；
合在「工具步骤后」则第一轮永远拿不到。

`prefetch_factory` 是**回调**而不是直接 import —— 与 `on_turn_end` 同理：
核心循环不该知道记忆模块存在，记忆关掉时也不在核心里留死代码。

### 2.3 六个入口闸（对齐 CC 的 `Ivi` 早退）

| 闸 | 判据 |
|---|---|
| 总开关 | `prefetch_enabled()` = 记忆开 + 选择器开 + **模型已指定** |
| 防自激 | `query_source in {extract_memories, auto_dream, memory_selector, compaction}` → 不跑 |
| 会话预算 | 累计召回 ≥ `SESSION_MAX_BYTES` → 不跑 |
| 成本闸 | 本代调用次数 ≥ `SELECTOR_MAX_CALLS`（默认 3）→ 不跑 |
| 查询可用 | 少于 2 字符 / 纯空白 → 不跑 |
| 有 client | 拿不到 LLM client → 不跑 |

> **CC 的 `aY()`（SDK 入口）与 `rr()`（远端能力）两道在 Hlaudz 没有对应物**，
> 对齐方案 D-10：Web 服务恒通过，不实现。

### 2.4 去重：slug 集合，与关键词路径**共用同一个对象**

预取是**每次模型调用一次**，不是每次 generation 一次。一个 10 步任务会启动 10 次。
若不按 slug 去重，同一条记忆会被 append 10 遍。

去重键用**集合**而不是布尔标志（与 M3 同一手法）：布尔标志会让「第三轮新写的 B」
永远注入不进去。

## 3. 真机 e2e 抓到并修掉的两个缺陷

### 3.1 缺陷一：同一条记忆被注入两遍（重复）

**现象**：`injected_count=2`，两条注入块内容完全相同，一条 `[记忆]`、一条 `[记忆·相关]`。

**根因**：两条路径各记一份去重集合。

- 关键词注入器由 `subagent/session.py:239` 构造，`MemoryInjector(team_ctx.user_id)`
  —— 没传共享集合，用自己的 `set()`；
- 选择器预取的 `PrefetchState` 也是自己的 `set()`；
- 两边都不知道对方注入过什么。

**关键点**：`build_turn_runtime` 是**普通网页会话也走**的路径（`chat.py:566`），
不只是 team。所以这个缺陷影响所有开着选择器的会话。

**修法**：
1. `MemoryInjector` 增加 `injected_slugs` 参数，允许外部注入集合；
2. `install_memory_injector` 每次新建集合并挂到 `loop._memory_injected_slugs`；
3. `session.py` 构造时传入同一个集合，并挂到 loop 上；
4. `_make_prefetch_factory` 从 loop 取这个集合传给 `PrefetchState`。

**回归测试**：`test_factory_wires_shared_set_from_loop`（直接测 factory 这一层，
因为前两个测试绕过 factory 测不到）、`test_shared_slugs_between_injector_and_prefetch`。

### 3.2 缺陷二：关键词路径抢走 slug，选择器白跑（互斥）

修完重复之后，`injected_count=1` —— 但注入的是 `[记忆]`，不是 `[记忆·相关]`。

**根因**：关键词注入器在**首轮模型调用之前**同步跑，选择器预取要到工具步骤之后
才消费。关键词必定先抢走 slug，选择器算完发现全被占用 —— **白跑一次模型调用，
S-M6 量出的 37.5% 优势在生产链路上一分也体现不出来**。

**修法**：两条路径**互斥**。依据是方案 §3.7 的原文：

> 选择器是「工具存储 / MCP 记忆库」形态的配套，与 `AutoMem` **互斥**

实现为 `memory_inject.keyword_injection_enabled()`：选择器真正启用时返回 False，
`MemoryInjector.__call__` 让位。

**为什么互斥而不是叠加**：
- 叠加的唯一好处是「选择器失败/超时那一轮还有关键词兜底」；
- 但代价是「选择器几乎永远抢不到 slug」，等于这个功能白做；
- 而且用户显式开了选择器，语义就是「用 LLM 判相关性」。悄悄退化成关键词
  会让他以为选择器在起作用 —— 那是更糟的误导。

互斥后 `injected_count=1`，注入块是 `[记忆·相关]`（带免责首句），符合预期。

## 4. 其他设计点

### 4.1 首句免责（照抄 CC）

```
[记忆·相关] 以下内容仅为**可能**相关，确实适用于用户当前问题才使用；
不适用就忽略，不要硬套。
```

CC 的 `Zoo.relevant_memories`（`m0591:229587`）第一句是硬约束。没有它，
模型倾向于把召回结果当既定事实全盘套用。

### 4.2 选择器提示词的三句硬约束（照抄 CC 的 `KGr`）

1. 最多 5 条；
2. **压制关键词撞车**（字面重合但语义无关的不选）；
3. 已选过的不重复选。

外加一句 `拿不准就不选。漏选一条的代价，远小于塞入无关记忆打断思路。`

### 4.3 解析必须过滤模型编造的 slug

`parse_selector_output` 只返回 `allowed` 里存在的 slug。理由：模型会编造 slug，
直接照单全收会让「删了记忆之后它还在被注入」这类幽灵引用发生在读侧。

同时兼容模型把 JSON 包在 markdown fence 里、或前后带解释文字（实测常见）。

### 4.4 `selector_client_for` 的三级兜底

1. 用户的默认 LLM 配置（`user_llm_configs`）；
2. **全局 `llm.yaml`** —— 单用户 / 本机部署里这是唯一来源（`user_llm_configs` 是空表）；
3. 调用方显式传入的 fallback。

第 2 条是 e2e 时发现的：一开始只查用户配置，结果 e2e 新建的用户没有配置
→ `client=None` → 预取静默不启用。表现是「配了却不生效」，很难查。

第 3 条**不自动用主模型** —— 否则「必须指定独立小模型」这条成本保护形同虚设。

### 4.5 会话级字节预算

`HLZ_MEMORY_SESSION_MAX_BYTES`（默认 61440）。超了就**不再召回**（不是召回后丢弃）。
防「越聊越多、越聊越慢」。设 0 表示不限。

## 6. 顺带回答：`AgentLoop` 为什么要每轮新建

有人会问「每轮新建 loop 开销大吗，能不能复用」。**结论：必须每轮新建，且开销可忽略。**

**为什么必须新建**：loop 里的工具闭包绑定了本轮的 `generation_id` / `team_id`
（team_id 每轮 `uuid4` 现生成），还有 `team_gate` / `on_turn_end` / 注入器组合
都是 per-generation 语义。跨轮复用会让工具打到上一轮的 team 上。

**开销实测**：`AgentLoop.__init__` 只是字段赋值，**9.9 微秒/次**（1000 次平均）。
对比一次模型调用的 3–10 秒，是 1/300000。

**真正贵的东西都在缓存的 `base_runtime` 里**：httpx client（`build_user_model`）、
MCP 连接（`build_user_toolset`）、系统提示词。这些每轮复用。

`RuntimeHub` 缓存的 `base_runtime.loop` 目前只被用来取 `system_prompt`，不直接跑。

## 7. 未覆盖 / 后续

| 项 | 说明 |
|---|---|
| **选择器用主模型时的真实成本** | S-M6/S-M7 都是借用已配置的模型。若用户把主模型填进 `SELECTOR_MODEL`，一个 10 步任务会多 3 次（受 `MAX_CALLS` 限制）主模型调用 —— 成本上升但未量化 |

| **多轮长会话的预算耗尽体验** | 预算耗尽后静默不再召回，用户不知道。可考虑在注入块末尾提一句 |
| **`memory_prefetch` 无 MCP 记忆库形态** | CC 的选择器配套「工具存储 / MCP 记忆库」，Hlaudz 只有文件记忆。当前实现是「在文件记忆上跑选择器」，是 CC 没有的形态 |

## 1. 先厘清一件事：CC 里有三套完全不同的「记忆」

这是上一版最大的认知缺口。三套东西共用「memory」这个词，但存储、注入方式、
生命周期全都不一样。混在一起谈必然会得出错误的借鉴结论。

| | A. 指令文件记忆 | B. 目录记忆（memdir） | C. 账号记忆库 |
|---|---|---|---|
| 载体 | `.md` 文件（`CLAUDE.md` 链 + `MEMORY.md`） | 记忆目录下的散落 `.md` | 远端 MCP server `memory` |
| 谁写的 | 用户 / `/init` / `auto_dream` / 提取代理 | 提取代理、主对话写文件 | 服务端（跨设备） |
| 怎么进上下文 | **装配期一次性**（`AutoMem` / `nested_memory`） | **每轮按相关性选**（`relevant_memories`） | **首帧前并发拉取**（`cowork_memory_context`） |
| 有预算吗 | 有（行数/字节截断） | 有（每 session 字节上限 + 扣留记账） | 有（版本化持有，超量撤回） |
| 关键标识 | `type: "AutoMem"` / `"nested_memory"` | `type: "relevant_memories"` | `type: "cowork_memory_context"` / `"account_memory_recall"` |

三者可以同时存在。**把它们当成一套来讲，是上一版文档最主要的失真来源。**

## 10. 记忆提示词的真实结构（上一版引错了来源）

### 10.1 四个类型 + 作用域（`m0293_0x1177df9f.js:3849`）

```js

```

完整定义在 `Qn`（`:3856`，含 private/team 作用域）与 `ml`（`:3857`，无作用域版本）。
摘出与产品决策最相关的三条：

| 类型 | 作用域 | `when_to_save` 要点 |
|---|---|---|
| `user` | **always private** | 「关于用户的角色、目标、责任、知识」；明确要求**避免负面评价**用户的记忆 |
| `feedback` | 默认 private；明确的团队级约定才 team | **纠正和确认都要记**（「只记纠正会让你偏离用户已认可的路径，并变得过度谨慎」） |
| `project` | private 或 team，**强烈倾向 team** | 「谁在做什么、为什么、到什么时候」；**必须把相对日期转绝对日期** |
| `reference` | 通常 team | 外部系统的指针（Linear 项目、Grafana 面板、Slack 频道） |

`feedback` 的完整语义（`:3856`）：

> Record from failure AND success: if you only save corrections, you will avoid past mistakes
> but drift away from approaches the user has already validated, and may grow overly cautious.

**「确认也算反馈」是这套提示词里最有价值的一句**，因为产品实现通常会漏掉它。
`when_to_save` 还给了三种确认的具体信号：`"yes exactly"` / `"perfect, keep doing that"` /
「接受了一个不寻常的选择且没有反对」。

理由写得很清楚：*Knowing why lets you judge edge cases instead of blindly following the rule.*

## 14. 对 Hlaudz 的借鉴（按性价比重排）

上一版给了 5 条建议。基于这次的完整梳理，重排并替换掉两条：

### 14.1 直接抄：`relevant_memories` 的整体形状（最高优先）

这是「记忆真能用起来」的核心，且**不需要向量库**：

```
1. 每轮起始：把「记忆清单（filename + description）」+ 本轮查询 送一次小模型
2. 要求 JSON schema 输出 { selected_ids: [...] }，≤5 条
3. 首帧 API 调用不 await 它（并发预取）
4. 第一轮工具步骤结束后再看：算完了就注入，没算完留到下一轮
5. 注入时首句固定：「仅为可能相关，确实适用才用」
6. 会话级字节上限（CC 是 61440），超了就不再加
7. 会话内不重复选（保留 selector 的私有对话状态）
8. selector 不触发自己：querySource 白名单排除
```

**Hlaudz 的落点**：`message_injector` 通道已有（`agent_loop.py:305`），
但需要新增「异步预取 + 延迟消费」能力 —— 现有注入器是同步的。
建议按 `AGENTS.md` §0.3 先补设计文档再动代码（这属于 P4 之后的新阶段）。

**降级路径**：首版可以同步算（阻塞首帧），但必须**带超时**（CC 的 first_look 是 20s，
selector 无显式超时但受 `abortController` 约束）。参考
`docs/20261112-Hlaudz首帧串行阻塞核实与优化设计.md` 的 300ms 硬指标 —— 同步算会直接冲突。

### 14.2 直接抄：`description` 的服务对象

CC 的 frontmatter `description` 注释写着「used to decide relevance **in future conversations**,
so be specific」（`m0293:3847`）。上一版设计里 `summary` 只写了「一行摘要，用于索引注入」，
没说它是**选择器的输入**。必须改：

- `description` 是**给选择器读的**，不是给人读的 → 要求「具体到能判断相关性」；
- 与之配套的提示词要**显式压制关键词撞车**（§5.3 第 2 条）。

### 14.3 直接抄：`feedback` 要记「确认」不只记「纠正」

上一版的 `kind` 枚举是 `fact | preference | feedback | project`，`feedback` 的描述是
「用户纠正过你的地方」。CC 的原文（`:3856`）明确要求**纠正和确认都记**，并给了理由：

> if you only save corrections, you will avoid past mistakes but drift away from approaches
> the user has already validated, and may grow overly cautious.

**这是一个产品级的行为差异，不是措辞问题。** 建议 Hlaudz 的写入提示词照抄这条，
并把 `user` / `feedback` / `project` / `reference` 四类都对齐（现在只有 4 个近似的 kind）。

### 14.4 直接抄：`withheld` 的「欠账」语义 + 三态状态

- `owed` 表按 session 记「扣留过谁」，下次有机会**优先还**；
- `injected / read / written` 三态分开记（`statusForKey`）；
- `recordSurfaced` 单独记「展示过」。

这三者合起来才能回答「这条记忆到底有没有被模型看见过」——
没有这三态，任何「命中率」统计都是错的。

### 14.5 直接抄：撤回要显式告知

`cowork_memory_context` 撤回时产出 `content: null` 的 attachment，渲染成
「The memory snapshot shown earlier has been removed … do not rely on anything it said.」

Hlaudz 若将来做「记忆被用户删除 / 被压缩掉」，必须发类似的显式告知，
**不能只是让它从上下文里消失**。

### 14.6 不建议照抄：`tengu_*` 旗标命名

见 §12.5。用可读的 `HLZ_MEMORY_*`。

### 14.7 需要修正上一版设计的三处

| 位置 | 上一版 | 应改为 |
|---|---|---|
| 实施方案 §2.1、§2.2 | 「personal / project 分开，亲和性来自 personal」 | 改为 **4 个类型 + private/team 作用域**；亲和性来自 `user` + `feedback` 两类 |
| 实施方案 §5 工具面 | `memory_list/read/write/delete` 四个自研工具 | **客户端只声明三个**（`Nji = ["memory_list","memory_read","memory_write"]`，`m0290:8`）；但工具闸白名单 `z$t`（`m0191:2338`）里还有 `memory_str_replace` / `memory_append` / `memory_delete` —— 属服务端可能下发、客户端未列入已知名单的操作。**保守做法：自研先只做三件套，删除通过 write 覆盖内容实现；不要把 delete 写进对外契约** |
| 实施方案 §4.2 闸门 | 「闸 3 first look 返回 False 才跳过」 | 补 `shadow` 模式（跑但不拦）与 **20s 超时 / 0 重试** |

### 14.8 一个需要产品决策的冲突

CC 的 `# Memory` 章节里有一整节「**不要保存什么**」（§10.4 的 `Zt`），其中第一条是
「代码模式、约定、架构、文件路径、项目结构 —— 这些读一下项目就知道了」。

而 Hlaudz 的实施方案 §4.5 写入提示词写的是「fact — 关于用户环境的稳定事实
（操作系统、常用工具路径、项目约定）」。

**「常用工具路径 / 项目约定」正好落在 CC 的禁止清单里。** 这不是笔误——
CC 的理由是「能读出来的就别记」。而 Hlaudz 现在的形态是 Web 多用户、每次会话
workspace 可能不同，模型读环境信息的成本比 CLI 高。

**建议**：Hlaudz 保留「环境事实」这一类（因为 Web 场景确实每次要重新交代），
但要把 CC 的禁止清单其余四项（git 历史、调试解法、CLAUDE.md 已写的、临时状态）
照抄进写入提示词。这是有意识的偏离，应写进设计文档的「与 CC 的差异」一节。

## 1. 🔴 最严重：新实例启动会杀掉所有在跑的会话

### 现象

```python
# backend/app/db.py:179-196（节选）
# 启动自愈：服务重启后，上一进程遗留的 assistant 消息会永远停在 streaming，
# 前端会一直显示"正在思考"。进程刚启动时不可能有真实生成在跑，全部收敛为 stopped。
await _mark_crashed_before_converge(conn)
await conn.execute(
    "UPDATE messages SET status='stopped' WHERE role='assistant' AND status='streaming'"
)
```

注释里的前提**在多实例下不成立**：「进程刚启动时不可能有真实生成在跑」只对
**本进程**成立，不对**整个集群**成立。

而 `init_db()` 在**每个实例的 lifespan 里都执行**：

```
backend/app/main.py:48    await db.init_db()
```

### 实测复现

`backend/tests/manual/probe_initdb_cross_instance_wipe.py`：

```
实例 A 正在跑：status = 'streaming'
实例 B 启动后：status = 'stopped'

FAIL：新实例启动把别的实例正在跑的生成标成了 stopped
      根因：db.py:194-196 的启动自愈没有 owner / leader 过滤
```

### 后果链

1. 扩容一个新副本 → 所有现存实例正在跑的 assistant 消息被改成 `stopped`
2. 生成其实还在跑，之后照常写 blocks —— 但状态字段已经判死
3. `stop_generation` / 续看 / 收敛逻辑全部基于这个字段 → 行为错乱
4. 用户看到「已停止」，而实际还在产 token

**这条比 cookie 严重**：cookie 失效只影响新连接，这条**主动改坏正在跑的数据**。
而且触发条件极其常见 —— **每次 `docker compose up -d --scale app=3` 都会触发**。

### 为什么 `recover_stale_runtime` 做对了、这条漏了

同一个仓库里已有正确范式：

```python
# backend/app/team_store.py:948-1002
async def recover_stale_runtime(reason="server restart", live_owners=None):
    """...
    原实现无差别 UPDATE ... WHERE status='active'。多实例时会杀掉另一个实例
    正在跑的 generation。现在每行都记了 owner（<host>:<pid>），
    恢复时只清 **owner 不在 live_owners 里**的行。
    """
    if alive:
        gen_where = f"status='active' AND (owner='' OR owner NOT IN ({ph}))"
```

`session_generations` / `team_tasks` 都有 `owner` 列（`team_store.py:215` 的
`_ensure_owner_columns` 补的）。**唯独 `messages` 没有**，所以那条 UPDATE
拿不到 owner，只能无条件全清。

### 修法（两个方向，后者更稳）

**方向 A：按 generation owner 过滤**

`messages` 表没有 owner，但可以通过会话关联：

```sql
UPDATE messages SET status='stopped'
WHERE role='assistant' AND status='streaming'
  AND session_id IN (
    SELECT session_id FROM session_generations
    WHERE status='active' AND (owner='' OR owner NOT IN (<live_owners>))
  )
```

缺点：`messages` 与 `session_generations` 靠 `session_id` 关联，而
`session_generations` 的键是 `(user_id, session_id, generation_id)` —— 一个会话
可能在另一个实例上刚开了新一轮。需要用「该会话没有**活着**的 active generation」
而不是「存在一个死掉的」。

**方向 B（推荐）：只收敛本实例自己的**

真正的判据是「**我这里**不可能有生成在跑」，那就是本进程的 `turn_job._JOBS` 为空。
但 `_JOBS` 只是内存表，重启后必然为空 —— 所以它无法区分「上一轮崩溃遗留」和
「别的实例正在跑」。

所以正确做法是：**启动自愈只在单实例模式下无条件执行；多实例下必须走 owner 过滤。**
即判断 `cluster_enabled()`：

- 未配 Redis（单实例语义）→ 保持现有行为，全清（这正是迁移前行为，不能改）
- 配了 Redis → 只清 `owner=''`（老库遗留）或 `owner NOT IN live_owners` 的行

这与 `recover_stale_runtime` 的判据**完全一致**，可以直接复用同一套参数。

**方向 C（最省事，但要产品决策）：把这条 UPDATE 从 `init_db()` 挪到
`recover_stale_runtime()` 里** —— 后者已经有 leader 租约 + `live_owners` 过滤，
而 `init_db()` 的职责应该只是「建表 + 迁移列」。这样不新增任何判据，只是
把「收敛」这件事交给本来就在做收敛的那个函数。

### 必须先确认的事

`_mark_crashed_before_converge` 也有同样问题（它扫全表的 streaming 会话标 crash）。
但它只是**建标记**，不直接改 messages —— 稍微轻一点，仍应一起收窄。

## 2. 🔴 粘性 cookie 只在 `/api/health` 下发

```python
# backend/app/main.py:253-274（全仓唯一调用点）
@app.get("/api/health", response_model=HealthOut)
async def health(request: Request, response: Response):
    _ensure_sticky_cookie(request, response)
```

### 没有 cookie 的场景（全部真实存在）

| 场景 | 后果 |
| --- | --- |
| 用户清空站点数据 | 无 cookie |
| curl / 脚本 / 第三方客户端直接打 `/api/...` | 从不访问 health，永远无 cookie |
| 前端首屏 health 失败（`App.tsx:337` 是 `catch(() => null)`，静默跳过） | 无 cookie |
| 扩缩容后 nginx 重启 | 见 §3 |
| 用户直接访问深链接 / 书签 | 前端会走 health，但一次性失败就没了 |

### 为什么这比「降级」更糟

`hash $cookie_hlz_sticky` 在没有 cookie 时，**所有无 cookie 请求落到同一个上游**
（不是随机打散，是全部压到一个实例）。所以：

- 不是「偶尔不粘」，是「一批用户集中压在一个实例」
- 而 `turn_job._JOBS` 是进程内的 → 这些用户的续看请求落到别处就查不到 job
- 查不到 job → 走 §4 分支 → 前端显示「已完成」，实际还在跑

### 修法

把 `_ensure_sticky_cookie` 挪进已有的中间件：

```python
# main.py:197 已有 _instance_header 中间件，已经 await call_next 拿到 response
@app.middleware("http")
async def _instance_header(request: Request, call_next):
    response = await call_next(request)
    _ensure_sticky_cookie(request, response)     # ← 加这一行
    ...
```

这样**任何一次成功响应都能种上 cookie**，暴露面从「必须先访问 health」
降到「至少成功请求过一次」。

## 3. 🟠 扩缩容后旧 cookie 会落到不同实例 —— 要不要处理？

这是本次会话的原始问题。**答案是：要处理，但优先级低于 §1 和 §4。**

### 先说事实：为什么不用 `consistent`

`nginx.conf:74-91` 的注释已经记录了实测：

- ketama 环按 **server 名字**建点
- `--scale app=3` 时 `server app:8000` 由 docker 内嵌 DNS 解析出 3 个 A 记录，
  但它们在环上**共用同一个名字** → 三个点重合 → 落点无法区分
- 实测：`hash ... consistent` 下同一 cookie 连发 6 次，命中 .4/.5/.6 各两次，**精确轮转**

所以去掉 `consistent` 是**正确的**（否则粘性完全失效）。代价是：**扩缩容时几乎所有
cookie 都要重排**（ketama 才能只迁一部分）。

### 那「旧 cookie 落到新实例」到底行不行

分三种情况，结论不同：

| 场景 | 行不行 | 为什么 |
| --- | --- | --- |
| **没有在跑的生成**（绝大多数请求） | ✅ 行 | 无状态请求，落到哪都一样 |
| **正在跑生成，然后扩容** | ❌ **不行** | 续看请求落到新实例 → 查不到 job → §4 分支 → 前端误判「已完成」 |
| **正在跑生成，然后缩容掉跑它的那个实例** | ❌ 不行 | 生成进程被杀，这是**真丢**，和 cookie 无关 |

所以答案是：**「旧 cookie 落到新实例」这件事本身没问题，问题是落到新实例后
如果那个会话正在跑，就会静默走错分支。**

换句话说：**§3 不是独立问题，它是 §2 和 §4 的放大器。** 如果 §4 修好了
（非 owner 实例明确说「我不知道，你连错实例了」而不是谎报 done），
§3 的后果就从「静默错误」降级为「显式失败 + 客户端自动重连」，那是可接受的。

### 但有一个前提必须先补齐

「客户端自动重连」目前**不存在**。前端收到 `done` 就当结束（`App.tsx:449-453`）。
所以修 §4 时必须同时给前端加一条：**收到「连错实例」的错误后，用新 cookie 重试一次**。

### 还有一条更彻底的路（但要动架构）

`nginx.conf:109-113` 的注释已经指出方向：

```nginx
# 需要 ketama 平滑迁移，或需要精确控制副本时改成显式列表
# （环上的名字必须各不相同，否则 consistent 又会退化成轮询）：
# server hlzscale-app-1:8000;
# server hlzscale-app-2:8000;
# server hlzscale-app-3:8000;
```

显式列出每个副本 + 加回 `consistent` → ketama 只迁 1/N 的键，扩容时**大部分会话不受影响**。
代价：副本名写死，扩容要改配置（但反正现在也要 `docker compose restart nginx`）。

**我的判断：先修 §1 和 §4，再考虑这条。** 因为 §1 现在会让每次扩容都改坏数据，
那才是立刻要止血的。

## 4. 🔴 非 owner 实例把「不知道」谎报成「已完成」

```python
# backend/app/routers/chat.py:1039-1052
job = turn_job.get_live_job_for_session(user["id"], session_id)
if job is None:
    async def _finished_stream():
        msgs = await db.list_messages(session_id)
        last = next((m for m in reversed(msgs) if m.get("role") == "assistant"), None)
        if last is not None:
            yield sse_frame("done", {"message_id": last["id"],
                                     "status": last.get("status", "complete"), ...})
    return StreamingResponse(_finished_stream(), ...)
```

`job is None` 有两种含义，代码当成一种：

1. **这一轮真的结束了**（正确）→ 发 `done`，`status` 取自 DB
2. **这一轮在别的实例上跑着**（错误）→ 也发 `done`

第 2 种情况下 `status` 取自 DB 的 `status`，而此时它很可能还是 `'streaming'`……
但前端 `App.tsx:451` 的映射是：

```ts
const status = ev.status === 'stopped' ? 'stopped' : ev.status === 'error' ? 'error' : 'complete'
```

**`'streaming'` 会掉进 `else` → 变成 `'complete'`**。于是前端把「正在跑」显示成
「已完成」，然后 `setStreaming(false)`（`:453`），不再重试。

这是本次审计里**最隐蔽的一条**：DB 里明明是 `streaming`，前端却显示完成。

### 修法

区分两个分支，判据用现成的 `generation_owner`：

```python
job = turn_job.get_live_job_for_session(user["id"], session_id)
if job is None:
    # 「我这没有」不等于「没人有」。先问集群。
    active = await team_store.get_active_generation(user["id"], session_id)
    if active and not await generation_owner.is_generation_dead_elsewhere(
            user["id"], session_id, active):
        # owner 还活着 -> 明确告诉客户端「你连错实例了」
        return JSONResponse(status_code=409, content={
            "error": "wrong_instance",
            "hint": "这一轮在另一个实例上运行。请刷新页面重试（会自动回到正确实例）。",
        })
    # 真的结束了
    ...
```

注意 `chat.py:937-951` 的 409 路径已经用了完全一样的判据（`is_generation_dead_elsewhere`），
**只是续看端点没用**。这是一处一致的遗漏。

前端配套（`App.tsx`）：收到 `wrong_instance` 时清掉缓存重新健康检查 + 重试一次。

断言的写法是二元且**双向**的：既断言「问题仍然存在」（修好后会红，提醒更新文档），
也断言「对照处已经做对」（比如 `recover_stale_runtime` 有 `live_owners` 过滤）。
所以 FAIL 不一定是代码坏了 —— 更可能是「修好了但文档没更新」，每条 FAIL 都带判断提示。

### 本轮挑刺自审抓出的自己的错

| # | 错在哪 | 怎么抓出来的 |
| --- | --- | --- |
| 1 | 断言「无条件收敛语句**仍在** db.py」，但模拟修法是「在末尾追加 owner 条件」—— needle 是新语句的**前缀**，仍然匹配 → 断言假绿 | 反向确认第一版跑出「期望变红，实际没红」 |
| 2 | 断言「`_ensure_sticky_cookie` **只在 1 处**被调用」，但修法是「挪动位置」—— 挪动不改次数，仍是 1 → 断言假绿 | 同上 |
| 3 | `recompute()` 用 `m.src()`，而 `src()` 的闭包读模块级 `BE`；我只改了 `m.HLAUDZ`，没改 `m.BE` → 读的还是真仓库 | 同上（两条一起失败才暴露出是同一类问题） |
| 4 | `load_module()` 直接 `exec_module`，被测脚本顶层会打 31 条结果并 `sys.exit()` → 淹没输出、杀掉进程 | 反向确认第一次跑，输出里全是主脚本的内容 |
| 5 | `add()` 的 `detail` 参数无条件打印，导致 PASS 的条目显示「已不再直接发 done，请更新文档」——与 PASS 自相矛盾 | 读输出时发现 |

**共同模式**：前三条都是「断言选错了靶子」。结论是**断言必须对着『问题的本质』写**，
而不是对着「问题的某一种表现」写：

- §1 的本质是「没有 owner 过滤」，不是「语句存在」
- §2 的本质是「只在 health 里下发」，不是「调用次数等于 1」

修正后，两种修法（内联过滤 / 删掉语句）都各有一条断言会红，覆盖才完整。

### 本文档的局限

- §1 / §4 / §2 都是**静态代码 + 单元级探针**确认的，**没有做真容器两副本的端到端验证**。
  要做的话：起 A、在 A 上开一轮生成、`--scale app=2` 起 B、观察 A 的消息 status 是否被改。
  （§1 已在 SQLite 与 PG 两种后端上验证，但那是同进程内连跑两次 `init_db`，
  不是两个真进程 —— 差别在于 PG advisory lock、心跳、leader 等真实多实例因素。）
- §3 的「扩缩容后 cookie 重排」是根据 `hash`（非 consistent）的语义 + 仓库里已有实测
  推出来的，**本轮没有重新实测**。已有实测记录在 `nginx.conf:82-84`（同一 cookie × 10 全同实例）。
- 未审计：沙箱（`sandbox/`）、A2A、ACP、记忆子系统的多实例行为。

### 探针本身踩的坑（值得记下来）

第一版 §1 探针用 `os.environ["HLZ_DB_PATH"]` 想隔离数据库 —— **这个环境变量不存在**。
`DB_PATH` 是 `app/config.py:25` 的模块级常量，import 时就定了。

后果：探针直接往真实库 `backend/data/app.db` 写进了 `u_test` / `s_test` / `m_test`
三条数据，还把那条 messages 改成了 `stopped`（已清理）。

**教训：验证代码必须能证明「我写的是哪个库」。** 现在探针做了两件事：

1. 用仓库里已有的隔离方式（`db.DB_PATH = tmp` + 同步 `team_store`/`turn_job` 等模块的 `DB_PATH`），
   不用凭空发明的环境变量；
2. 开跑前显式比对目标路径与真实库，相同就拒绝执行。

这类「探针自己造成事故」在 AGENTS.md §8.6 里归为「假信号」的一种 ——
表面上看探针跑出了结论，实际它污染了被观测对象。

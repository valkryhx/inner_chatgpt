# Team 偶现不可用 + 思考等级不生效：根因与修复

> 日期：2026-11-12　状态：已定位、已修复、真实 e2e 通过（含反向确认）
> 涉及：`backend/app/quota.py`、`backend/app/model_discovery.py`、`backend/app/routers/me.py`、
> `backend/app/schemas.py`、`frontend/src/reasoningLevels.ts`、`frontend/src/components/SettingsModal.tsx`

## 0. 三个问题的结论速览

| # | 现象 | 根因 | 性质 |
|---|---|---|---|
| 1 | 偶现 `Team 本轮不可用：QuotaExceeded: capacity_exceeded after 2.0s` | `USER_MAX_ACTIVE_TEAMS` 默认 1，同一用户开第二个会话时被用户级闸门挡住 | **Hlaudz 配置缺陷** |
| 2 | 湛卢 `moma/deepseek-latest-flash` 上思考等级「配了没效果」 | 湛卢网关**整段丢弃** `reasoning_effort` 字段，与档位取值无关 | **网关限制**，不是 Hlaudz 的 bug |
| 3 | 前端的思考等级少一档 `medium` | 前端 `REASONING_LEVELS` 漏了 `medium`，后端 `REASONING_LEVELS` 有 | **Hlaudz 缺陷** |

第 1 条**与 LLM API 稳定性无关**：它与模型是否超时、是否 403 完全没有关系，
纯粹是进程内信号量计数问题。你此前在湛卢 / xem 之间来回换模型，
只是恰好掩盖了触发条件（换模型后会话数、标签页数变了）。

## 1. Team 偶现不可用

### 1.1 报错链路

```
prepare_turn_team()                       # backend/app/subagent/session.py:323
  └─ TeamHost.create()                    # team_host.py:140
       └─ acquire_lifecycle(timeout_s=2.0) # team_host.py:108
            └─ QuotaManager.team_lease()   # quota.py
                 └─ _acquire_many([global, user, session], 2.0)
                      └─ 超时 → QuotaExceeded("capacity_exceeded after 2.0s")
  └─ except: 释放已拿到的租约 + buffer.put(team_unavailable)
                                          # session.py:329-350
```

`team_unavailable` 事件被前端 `App.tsx:668` 收到后，把 `payload.error` 原样显示成
「Team 本轮不可用：…」。所以那句报错**只是配额闸门的超时文案**，不是 LLM 的错。

### 1.2 默认值为什么必然撞车

```python
# backend/app/quota.py（修复前）
user_teams:    int = _env_int("USER_MAX_ACTIVE_TEAMS", 1)     # 每用户
session_teams: int = _env_int("SESSION_MAX_ACTIVE_TEAMS", 1)  # 每会话
```

`team_lease()` 三级闸门同时申请：global → user → session。
一个会话已经有活跃 Team 时，第二级和第三级都是满的。
**只要同一个用户同时有两个会话在跑，第二个会话就一定拿不到名额**，
等满 2 秒后报 `capacity_exceeded after 2.0s`。

这不是"偶现"，是"两个人的操作时序恰好错开才不触发"。触发条件：
- 同一用户开了两个标签页/两个会话；
- 或者第一个回合还没结束（含 teammate 还在跑、`TEAM_DRAIN_TIMEOUT_S` 最多 300s），
  就在另一个会话发消息。

### 1.3 为什么"偶现"而不是"必现"

`SESSION_MAX_ACTIVE_TEAMS=1` 的设计初衷是「一个会话只有一个活跃 Team」，
但 `user_teams=1` 把它扩大成了「一个用户只有一个活跃 Team」。
跨会话互斥只在**时间重叠**时发生，所以看起来是偶发。

### 1.4 修复

**改默认值**：`USER_MAX_ACTIVE_TEAMS` 1 → 4。

理由：会话级闸门（`SESSION_MAX_ACTIVE_TEAMS=1`）已经保证「一个会话一个 Team」，
用户级闸门的职责是**多用户之间的公平性**，不该把单用户的多个会话锁死。

**改报错文案**：配额失败时把三级闸门的实时水位一起带出来。

```text
修复前：capacity_exceeded after 2.0s
修复后：capacity_exceeded after 2.0s
        [全局 Team 15/16，用户 Team 0/1，会话 Team 1/1；user=u_x session=co_y]
```

这样用户一眼能看出是哪一级满了，不用再猜是不是泄漏。

### 1.5 验证（真实 LLM，真实后端）

**反向确认**：把默认值改回 1，用「A 建立 Team 后 B 才出发」的严格重叠场景：

```
A: text_delta=109, team_event=1, team_unavailable=[]
B: text_delta=1,   team_event=1, team_unavailable=[
     "{'error': 'QuotaExceeded: capacity_exceeded after 2.0s
       [全局 Team 15/16，用户 Team 0/1，会话 Team 1/1；
        user=u_45a469fa73d9 session=co_76ec48b71993]'}"]
→ FAIL（复现了用户报告的原始报错）
```

**修复后**同一场景：

```
A: text_delta=88, team_event=1, team_unavailable=[]  (7.1s)
B: text_delta=1,  team_event=1, team_unavailable=[]  (4.0s)
→ PASS
```

**配置仍然生效**：用 `USER_MAX_ACTIVE_TEAMS=1` 覆盖后重启，同一场景再次 FAIL
（复现同一报错），证明改的是「默认值」而不是「取消闸门」。

**同会话保护未破坏**：同一会话连发两条，第二条走 steer 队列返回 409/202，
不会开第二个 Team。

### 1.6 单测

`backend/tests/test_quota.py` 新增两条：

- `test_default_user_team_limit_allows_two_sessions` —— 默认配置下同一用户
  两个会话都能开 Team；
- `test_team_quota_error_names_the_full_gate` —— 报错里必须出现
  `用户 Team 0/1` 与 `session=s2`。

## 2. 湛卢上思考等级「配了没效果」

### 2.1 结论：网关整段丢弃该字段

用**决定性实验**判定，而不是看 HTTP 200：

> 传一个**绝对非法**的档位 `hlaudz_invalid_probe`。
> - 若端点真的解析这个字段 → 必然 400/422；
> - 若端点根本不看清这个字段 → 照样 200。

实测结果（2026-11-12）：

| 端点 | 模型 | 传非法档位的结果 | 判定 |
|---|---|---|---|
| 湛卢 chat | `moma/deepseek-latest-flash` | 200 | **整段丢弃** |
| 湛卢 chat | `zhanlu/qwen3.7-max` | 200 | **整段丢弃** |
| 湛卢 chat | 其余 32 个模型 | 200 | **整段丢弃** |
| xem responses | `deepseek-v4.1-flash` 等 14 个 | 200 | **整段丢弃** |
| 官方 DeepSeek chat/responses | `deepseek-flash`、`deepseek-v4-pro` | **422**，并在正文列出枚举 | **校验**，认 |

官方 DeepSeek 的 422 正文（权威清单，不是我们猜的）：

```text
reasoning_effort: unknown variant `hlaudz_invalid_probe`,
expected one of `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `ultra`, `max`
```

所以：
- 在湛卢 / xem 中转上，思考等级**选哪一档都不会改变上游行为**，这是网关侧限制；
- Hlaudz 本身没有"配置错误"——它把字段按协议发出去了，是网关忽略了；
- 官方 DeepSeek 端点上档位是**真的生效**的，且合法枚举就是 Hlaudz 已有的那 8 档。

### 2.2 为什么之前看不出来

`llm_client.py:462` 只在 **400/422** 时补充「思考等级不匹配」提示。
静默丢弃型网关永远返回 200，所以既没有报错、也没有效果——用户只能凭感觉。

### 2.3 修复：把「认不认」变成可判定的结论

新增后端探测：`POST /api/me/llm-reasoning-probe`

```json
// 请求
{"config_id": "llm_xxx"}       // 或 base_url + api_key + model + wire_api
// 响应（三态，绝不混用）
{"supported": true,  "levels": ["none","minimal","low","medium","high","xhigh","ultra","max"]}
{"supported": false, "levels": [], "hint": "端点接受了非法档位，说明它整段忽略 reasoning_effort…"}
{"supported": null,  "error": "HTTP 401: …", "hint": "探测请求被拒绝，无法判断…"}
```

- `supported=true` 时 `levels` 是从端点 422 正文里解析出的**它自己声明的枚举**；
- `supported=null` 与 `false` 严格区分：网络/鉴权/模型名错误不能当成"不支持"。

前端「设置 → 我的模型」的 `reasoning_effort` 旁新增「测支持」按钮，
结果直接显示三种结论之一。

### 2.4 验证

真实后端（新进程 + 真实密钥）：

```
官方 deepseek deepseek-flash → supported=True, levels=[none,minimal,low,medium,high,xhigh,ultra,max]  (0.8s)
湛卢 moma/deepseek-latest-flash → supported=False                                              (0.5s)
缺 model                      → supported=None, error="缺少 model"                              (0.0s)
```

### 2.5 相关：前端少一档 `medium`

前端 `REASONING_LEVELS` 是 7 档（缺 `medium`），后端 `reasoning.py` 是 8 档。
后果：用户选了 `medium` 能保存（后端认），但前端下拉里再选不出来，
回显时 label 是裸字符串 `medium`。已补齐并统一。

## 3. 你需要知道的两件事（非缺陷）

1. **湛卢/xem 上思考等级无效是网关行为**，不是 Hlaudz 能修的。
   想真控思考量，要么换官方 DeepSeek 端点，要么在提示词层面约束。
2. **`USER_MAX_ACTIVE_TEAMS` 可以用环境变量覆盖**：
   ```bash
   USER_MAX_ACTIVE_TEAMS=8   # 想同时开更多会话
   USER_MAX_ACTIVE_TEAMS=1   # 只想一人一 Team（会重新引入跨会话互斥）
   ```

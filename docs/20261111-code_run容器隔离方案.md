# code_run 容器隔离方案（P1）：从进程内审计换到容器边界

> 日期：2026-11-11　状态：**方案待评审，未实施**
> 前置：`docs/20261111-workspace沙箱逃逸修复方案.md` §10（进程内审计路线已判定不可行并回退）

## 1. 背景：为什么必须换边界

### 1.1 现状

`code_run` 的用户代码跑在**平台进程的子进程**里，与平台同一个 OS 账户、同一个文件系统命名空间。
用户之间只靠目录约定（`workspaces/<user_id>/`）区分。

已实测的后果（`u_probe_cap` 身份，2026-11-11）：

```text
读他人 workspace 目录  -> ['.subagents', '.tmp']      ← A 能看到 B 的目录结构
连平台数据库           -> (348,)                       ← 查出全部 348 个用户
读 .env                -> 平台所有 api_key
```

而进程内审计钩子（`run_guard.py`）**一行 `subprocess` 就能整体绕过**，加 `-S` 跳过 `site` 也一样穿透。

### 1.2 为什么不能继续加固审计

§10 已实测：那套读校验付出了能力代价（agent 读不了仓库、读不了家目录），却没换到隔离。
继续叠加规则是**成本递增、收益递减**，且越加越难用。

**结论：换隔离边界，不是加限制。**

### 1.3 本方案要同时满足的两个目标

| 目标 | 说明 |
|---|---|
| **A 读不到 B** | 物理隔离，不依赖代码怎么写 |
| **不限制 Hlaudz 能力** | 容器内读仓库、读家目录、pip install、跑任意 python **全部可用** |

关键认知：**容器不是「限制 hlaudz」，而是「给 hlaudz 一个自己的完整世界」。**
今天被审计钩子拦掉的能力在容器内全部回来，而容器外是别的租户，物理上碰不到。

## 2. 路线选择：每用户一容器（而非每会话）

### 2.1 实测量化（本机 Docker 27.4.0，`python:3.12-slim`）

| 场景 | 耗时 / 占用 |
|---|---|
| 一次性容器 `docker run --rm` | **698 ms** |
| 常驻容器 + `docker exec` | **121 ms** |
| 并发 20 个 `docker run` | 单次涨到 **2695 ms**，整批 3.8 s |
| 并发 20 个 `exec`（同一容器） | 墙钟 379 ms，平均 322 ms |
| 并发 50 个 `exec`（同一容器） | 墙钟 891 ms，平均 675 ms |
| 空闲容器内存 | **4.4 ~ 4.5 MiB / 个** |
| 串行启动 20 个容器 | 7.9 ~ 8.1 s（约 400 ms/个） |

**关键发现：开销的大头是「创建容器」，不是「使用容器」。** 一次 `exec` 只要 120 ms，
一次 `docker run` 要 700 ms，高并发下还会互相排队（2.7 s）。

### 2.2 为什么是「每用户」而不是「每会话」

决定性事实：**Hlaudz 的 workspace 本来就按 user_id 划分**

```python
# backend/app/workspace.py
def user_workspace(user_id, *, create=True) -> Path:
    return WORKSPACES_DIR / user_id          # workspaces/<user_id>/
```

会话只在用户 workspace 下开子目录（`.subagents/<session>/<agent>/`）用于隔离子代理产物。
**会话之间本来就共享同一个用户 workspace** —— 这是产品既有语义，不是本方案引入的。

因此容器边界与数据边界天然对齐：

| 路线 | 100 会话 / 20 用户 | 容器数 | 内存 | 共享符合语义？ |
|---|---|---|---|---|
| 每会话一容器 | 100 个容器 | 100 | ~440 MiB | ❌ 会话间被迫隔离状态，但 workspace 本来就共享 |
| **每用户一容器** | 20 个容器 | **20** | **~90 MiB** | ✅ 与 `workspaces/<user_id>/` 一一对应 |

实测佐证（§2.1 的 I/J/K 组）：

- 20 个用户容器共 **90 MiB**（4.5 MiB/个）；
- 同一用户 5 个会话并发 exec：墙钟 163 ms，平均 143 ms —— **无退化**；
- 同一用户 20 个会话并发 exec（含计算）：墙钟 313 ms，平均 262 ms —— 仍然可用。

### 2.3 每用户容器的副作用（必须承认）

同一用户的多会话共享一个容器，因此：

| 共享的东西 | 后果 | 是否可接受 |
|---|---|---|
| `/tmp` | 会话 A 写的临时文件，会话 B 能读到（实测：写 `marker-A`，另一会话读到） | ✅ 同一用户的数据，非跨租户 |
| 全局 pip 安装 | 会话 A 装的包，会话 B 能 import | ✅ 同用户，反而省重复安装 |
| 后台进程 | A 起的常驻进程对 B 可见 | ⚠️ 需要回收策略 |

对照：**跨用户仍然完全隔离**（不同容器），这是唯一真正的安全边界。

> 若将来产品要求「同用户不同会话也隔离」，再升级为每会话一容器，
> 届时把容器生命周期从 user 挂到 session 即可，架构不变。

### 2.4 候选路线对比

| 路线 | 隔离粒度 | 容器数 | 首次延迟 | 单次延迟 | 判定 |
|---|---|---|---|---|---|
| 每次执行起容器 | 最强 | 0（用完即删） | 698 ms → 高并发 2.7 s | 698 ms | ❌ 每次都等 |
| **每用户一容器（懒创建）** | A/B 隔离达标 | = 活跃用户数 | 一次性 ~400 ms | **121 ms** | ✅ **采纳** |
| 每会话一容器 | 更强 | = 活跃会话数 | 一次性 ~400 ms | 121 ms | 备选，成本 5~100 倍 |
| 预热池 | A/B 隔离达标 | 池大小 | ~0 | 121 ms | 暂不做（内存常驻） |

## 3. 设计

### 3.1 生命周期：懒创建 + 空闲回收 + 全局上限

```text
code_run 请求
   │
   ├─ 该 user 有 live 容器？ ── 是 ──> docker exec（~120 ms）
   │
   └─ 否
        ├─ 全局容器数已达上限？ ── 是 ──> 淘汰最久未用（LRU）→ 再创建
        └─ docker run -d（~400 ms）→ 记录 last_used → docker exec
```

三个参数（写进配置，带默认值）：

| 参数 | 默认 | 说明 |
|---|---|---|
| `CODE_SANDBOX_IDLE_TTL_S` | 900（15 分钟） | 空闲多久销毁容器 |
| `CODE_SANDBOX_MAX_CONTAINERS` | 64 | 全局同时存活上限，超出 LRU 淘汰 |
| `CODE_SANDBOX_CREATE_TIMEOUT_S` | 30 | 创建超时，超时按失败处理 |

**内存估算**：64 × 4.5 MiB ≈ 288 MiB（空闲容器），加上容器内实际跑的任务内存（受 `--memory` 限制）。

### 3.2 容器规格

```python
args = [
    "run", "-d", "--rm",
    "--name", f"hlz_sbx_{user_id_safe}",
    # —— 隔离 ——
    "--network", "none",                    # 默认无网（见 §3.3）
    "--cap-drop", "ALL",
    "--security-opt", "no-new-privileges",
    # —— 资源 ——
    "--memory", "2g", "--memory-swap", "2g",
    "--cpus", "1",
    "--pids-limit", "256",
    # —— 文件系统 ——
    "-v", f"{user_workspace(user_id)}:/ws",
    "--tmpfs", "/tmp:size=512m,mode=1777",
    # —— 环境 ——
    "-e", "HOME=/tmp", "-e", "TMPDIR=/tmp",
    "-e", "PYTHONPATH=/ws/.pylib",
    "-w", "/ws",
    IMAGE, "sleep", "infinity",             # 常驻待命
]
```

**不做 `--read-only`**：实测（§4.2）它在 pip 场景下会因临时目录问题失败，
而 `--cap-drop ALL` + 非 root + `--tmpfs` 已经足够。**能力优先**，这是产品目标决定的。

### 3.3 网络策略：默认无网，按需放开

实测：`--network none` 下 `pip install` 失败（无法解析域名），
但**预装依赖 + 从 workspace 加载**（`PYTHONPATH=/ws/.pylib`）可以正常工作。

| 档位 | 网络 | 适用 |
|---|---|---|
| **默认** | `--network none` | 绝大多数代码执行、数据处理，不需要联网 |
| 放开 | 桥接网络 | 明确需要联网时（`code_run(network=True)` 参数） |

放开网络的判定要**记审计日志**（谁、哪个会话、什么代码要联网）。

> 待定：是否需要「出站白名单」（只允许 pypi）。这属于 P1.5，不在本次范围。

### 3.4 文件挂载边界

**只挂当前用户的 workspace**，不挂平台目录。实测验证：

```text
/ws/../app.db          -> No such file or directory
/d/git_codes           -> No such file or directory      ← 宿主 D 盘不可见
/c/Users               -> No such file or directory      ← 宿主家目录不可见
```

容器内 `/` 是容器自己的 rootfs。**A 的容器里根本没有 B 的 workspace 挂载点** ——
这是物理隔离，与代码怎么写无关（`subprocess`、`ctypes`、`os.system` 全部无效）。

### 3.5 workspace 与宿主路径映射

| 容器内 | 宿主 |
|---|---|
| `/ws` | `backend/data/workspaces/<user_id>/` |
| `/tmp` | tmpfs（容器销毁即消失） |
| `/ws/.pylib` | 第三方库安装目录（跨会话复用，避免重复 pip） |

**Windows 挂载实测**：`-v D:/.../workspaces/u_x:/ws` 可正常读写，
容器内显示为 `root:root 777`。宿主机 `drago` 账户能正常访问。

> ⚠️ **Windows 特有坑**：Docker Desktop on Windows 的挂载是 9p/virtiofs，
> 权限模型与 Linux 不同。`--user 1000:1000` 在本机实测会导致 pip 报
> `Read-only file system: '/D:'`。**本方案不使用 `--user`**，改由容器内默认 root +
> `--cap-drop ALL` 来约束。这削弱了「非 root」这一层，属于已知取舍，
> 部署到 Linux 时应恢复 `--user 1000:1000`。

### 3.6 环境变量必须显式给全

实测发现一个真实陷阱：Docker Desktop 下 `HOME` 会被继承为**宿主路径**
（`C:/Users/drago/AppData/Local/Temp`），而容器内该路径不存在，导致 pip/makedirs 失败。

**因此必须显式设置**（不能依赖镜像默认）：

```python
"-e", "HOME=/tmp",
"-e", "TMPDIR=/tmp",
"-e", "XDG_CACHE_HOME=/tmp/.cache",
```

> 另注：用 Git Bash 测试时 `-e HOME=/tmp` 会被 MSYS 路径转换成宿主路径，
> 需要 `MSYS_NO_PATHCONV=1`。**后端用 Python `subprocess` 直接传 argv，不经过 shell，不受此影响。**

### 3.7 与现有代码的接缝

改动集中在 `builtin_tools._run_code_impl`，保持 `code_run` 的工具契约不变：

```python
async def _run_code_impl(...):
    if sandbox_enabled():
        return await _run_in_sandbox(user_id, code, code_type, timeout, ...)
    return await _run_in_process(...)          # 保留现有路径作为降级
```

新增 `backend/app/sandbox/`：

| 文件 | 职责 |
|---|---|
| `config.py` | 镜像名、TTL、上限、超时（环境变量 + 默认值） |
| `runtime.py` | 容器创建/执行/销毁、`exec` 包装、输出解码 |
| `pool.py` | 每用户容器注册表、LRU 淘汰、空闲回收 |
| `probe.py` | 启动自检：Docker 可用？镜像存在？权限够？ |

**失败策略（重要）**：

| 情况 | 行为 |
|---|---|
| Docker 不可用 | **降级到进程内**（保持现状），并在结果里明确告知 agent「当前未启用隔离」 |
| 镜像不存在 | 尝试拉取，失败则降级 + 告警 |
| 容器创建超时 | 返回错误，不降级（避免静默退回不安全路径） |

> 设计取向：**默认不阻断产品可用性**（降级），但**绝不静默降级** ——
> 每次降级都要在工具结果和日志里留痕，让「现在没有隔离」这件事可见。

### 3.8 停止与清理的级联

现有 `process_registry` 的 `ProcessLease` 机制要延伸到容器：

| 场景 | 现有行为 | 容器方案 |
|---|---|---|
| 用户点停止 | `_kill_tree(proc)` | `docker exec ... kill` → 超时后 `docker kill` |
| 生成结束 | 进程自然退出 | 容器保留（复用），只结束本次 exec |
| 空闲 TTL 到 | — | `docker rm -f` |
| 后端重启 | 进程全部丢失 | 启动时清理残留 `hlz_sbx_*` 容器 |

**容器内进程的停止**：`docker exec` 起的进程在容器内，宿主 `kill` 够不到。
需要 `docker exec <cid> pkill -f <marker>`，或在 exec 命令前后包一层 PID 文件。

## 4. 实测证据（本次已完成）

### 4.1 性能

| 项 | 数据 |
|---|---|
| 常驻容器 exec | 121 ms（5 次平均） |
| 一次性容器 | 698 ms（5 次平均） |
| 20 用户容器内存 | 90 MiB（4.5 MiB/个） |
| 同用户 5 会话并发 | 163 ms 墙钟 |
| 同用户 20 会话并发 | 313 ms 墙钟 |

### 4.2 能力（关键：证明「不限制 Hlaudz」）

在 `--network none --cap-drop ALL --security-opt no-new-privileges` + workspace 挂载下：

```text
workspace 内读写        -> ✅ 正常
纯计算                  -> ✅ 4950
第三方库 import         -> ✅ requests 2.34.2
pip install 到 workspace -> ✅ 成功（--target /ws/.pylib）
```

**这四项正是进程内审计方案会砍掉或很脆的部分，容器方案下全部正常。**

### 4.3 隔离

```text
/ws/../app.db    -> No such file or directory
/d/git_codes     -> No such file or directory
/c/Users         -> No such file or directory
```

资源限制：

```text
--memory 256m + 申请 600 MiB  -> docker exit 137 (OOM SIGKILL)
```

## 5. 实施步骤

| 步 | 内容 | 验证 |
|---|---|---|
| 1 | `sandbox/config.py` + `probe.py`：探测 Docker/镜像，不可用则明确报告 | 单测：无 Docker 时返回不可用，不抛异常 |
| 2 | `sandbox/runtime.py`：单容器创建/exec/销毁 | 单测 + 真机跑通 `print(1)` |
| 3 | `sandbox/pool.py`：每用户注册表 + LRU + TTL 回收 | 单测：上限触发淘汰、TTL 到期销毁 |
| 4 | `builtin_tools` 接缝：`HLZ_CODE_SANDBOX=1` 开关，默认关 | 开关关时行为与现在完全一致 |
| 5 | 停止级联：`/stop` 能终止容器内进程 | 单测 + 真机：跑死循环，stop 后 3s 内进程消失 |
| 6 | 后端重启清理残留容器 | 单测 |
| 7 | 真实 e2e：两个用户各跑一段读 `app.db` 的代码 | 必须都失败（`No such file`） |
| 8 | 真实 e2e：同一用户跑数据处理 + pip install + 画图 | 必须全部成功 |

## 6. 风险与未决项

| 风险 | 缓解 |
|---|---|
| Windows Docker Desktop 是单机的 | 多机部署需会话粘性或按机器分区；本方案先按单机做 |
| 容器内 root 身份（因 Windows 权限模型） | `--cap-drop ALL` + `no-new-privileges`；Linux 部署恢复 `--user` |
| 同用户多会话共享 `/tmp` 与全局包 | 接受（同租户）；文档写清；必要时升级为每会话容器 |
| 容器创建慢（400 ms）影响首次体验 | 懒创建，只在会话首次 `code_run` 付一次 |
| Docker 不可用时降级到进程内 | **降级必须留痕**（工具结果 + 日志 + 前端提示） |
| pip install 无网时失败 | 预装常用依赖到镜像；或放开网络（记审计） |
| 磁盘占用（镜像 + 容器层） | `--rm` + TTL 回收；定期 `docker system prune` |

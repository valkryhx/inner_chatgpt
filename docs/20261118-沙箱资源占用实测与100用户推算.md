# 沙箱资源占用实测与 100 用户容量推算

> 全部数字为**本机实测**（2026-11-18），不是估算。
> 复现脚本：`backend/tests/manual/resource_profile.py`
> 原始数据：`backend/work/resource_profile.json`
> 设计文档：`docs/20261118-沙箱MVP设计与实施.md`

## 0. 一句话

**单容器内存从 1.7 MiB（空闲）到 330 MiB（分配 300MB 数组），
推行性已验证（5 与 20 并发数字一致）。
本机 15.3 GB 内存撑不住 20 个并发用户——瓶颈是 Docker Desktop 固定吃 1.6 GB，
不是容器本身。**

## 1. 宿主机规格（测量基线）

| 项 | 值 |
| --- | --- |
| CPU | 16 核 |
| 内存 | 15.3 GB（可用仅 **2~3 GB**） |
| D 盘 | 272 GB 总，剩 **40 GB** |
| C 盘 | 215 GB 总，剩 **17 GB** |
| Docker | Desktop 4.37.1 / Engine 27.4.0 / WSL2 |
| 镜像 | `hlz-sandbox:2026-11-18`（733 MB） |

> ⚠️ 可用内存只有 2~3 GB 是因为**本机同时在跑别的项目**
> （`jiake-public-poc-portal` 等）。裸机可用会更多。

## 2. 单容器内存：五档实测

关键方法：**必须在进程存活期间采样**。第一版在 `docker exec` 返回后读
cgroup，那时进程已退出、内存已释放，测到的永远是空闲的 2~3 MiB —— 完全错误的数字。
正确做法是 `docker exec -d` 后台跑 + 内部 `sleep` 保持存活，期间读
`/sys/fs/cgroup/memory.current`。

| 场景 | 平均 | 最大 | 说明 |
| --- | --- | --- | --- |
| 1. 空闲（`sleep infinity`） | 1.70 MiB | 1.95 MiB | 只有容器运行时开销 |
| 2. 跑过 python | 4.82 MiB | 5.16 MiB | 解释器已加载 |
| 3. `import pandas` | 44.98 MiB | 46.90 MiB | 主要成本在这里 |
| 4. 分配 300MB numpy 数组 | 327.93 MiB | 331.33 MiB | 接近 1 GiB 上限的 1/3 |
| 5. pandas 读 30 万行 + 分组聚合 | 59.00 MiB | 128.68 MiB | 最常见的数据任务形态 |

**推行性验证**：5 容器与 20 容器的数字几乎完全一致
（45 vs 44.98 MiB、328 vs 327.93 MiB），说明容器之间无相互干扰，
内存随容器数**线性增长**。

### 2.1 10 容器全载 pandas+numpy+matplotlib（2026-11-18 补充实测）

这一档最接近真实生产：10 个容器**同时**加载三个大包并保持存活，
内存上限按建议配置设为 **512m**。

| 容器 | 内存 |
| --- | --- |
| load_1 | 98.2 MiB |
| load_2 | 73.2 MiB |
| load_3~10 | 68.8~69.3 MiB |
| **合计** | **723 MiB = 0.71 GiB** |
| 平均 | **72.3 MiB/容器** |
| 最大 | 98.2 MiB |

**结论**：
- 10 个容器全载三包 = **0.71 GiB**，全部远低于 512m 上限（最大仅 98 MiB，占用率 19%）
- 无一个触发 OOM
- 宿主可用内存从 2.50 → 1.94 GiB，即 **10 个满载容器只吃掉约 0.56 GiB**
- 清理后回到 1.84 GiB，无内存泄漏
- Docker daemon 在 10 容器下响应正常（`docker stats` 无超时）

> 这一档验证了「`memory=512m` 够用」这个建议：实测峰值 98 MiB 只用了上限的 19%，
> 留了 5 倍余量。即使模型跑重任务到 330 MiB（见第 4 档），512m 也还够。

## 4. 推算 100 用户

### 4.1 内存（关键约束）

**前提：不是 100 个容器常驻，而是「活跃用户数」个。**
`pool.py` 有 LRU 淘汰 + 15 分钟 TTL 回收，所以实际容器数由
`HLZ_SANDBOX_MAX_CONTAINERS`（当前 **4**）和真实并发决定。

| 场景 | 每容器 | 容器数 | 容器总计 | + Docker 1.6G | 结论 |
| --- | --- | --- | --- | --- | --- |
| 全部空闲 | 2 MiB | 100 | 0.2 GB | **1.8 GB** | 完全够 |
| 全部 import pandas | 45 MiB | 100 | 4.5 GB | **6.1 GB** | 24GB 机器够 |
| 都跑中等数据任务 | 60 MiB | 20 | 1.2 GB | **2.8 GB** | 本机勉强 |
| 半数跑大数据 | 165 MiB | 20 | 3.3 GB | **4.9 GB** | 本机不够 |
| 全部跑大数据 | 330 MiB | 100 | 33 GB | **34.6 GB** | 需 48GB+ |

**瓶颈在 Docker Desktop 的 1.6 GB 固定开销**：本机 15.3 GB，系统与其它项目
占掉 12 GB 后只剩 2~3 GB，装不下几个容器。

### 4.2 磁盘

| 项 | 100 用户 | 位置 |
| --- | --- | --- |
| 镜像 | 733 MB（**一份**） | C 盘 WSL2 vhdx |
| 容器可写层 | 100 × 4 kB ≈ 0.4 MB | C 盘 vhdx |
| 用户数据（人均 100 MB） | **10 GB** | D 盘 `<SANDBOX_WORKSPACES_DIR>` |
| Docker 构建缓存 | 当前 1.5 GB，可 `prune` | C 盘 |

⚠️ **C 盘只剩 17 GB**，Docker 的镜像层和可写层都在那里。
D 盘的 40 GB 放用户数据够，但 Docker 那边要留意。

### 4.3 CPU

- 每容器限 1 核，16 核最多同时跑 16 个满负载任务
- 实测矩阵乘法单容器能吃满一核（97~99%）
- 但真实任务多是秒级，不会持续满载
- 100 用户同时跑满不现实，需要排队或提高容器数上限

## 5. 建议

### 5.1 硬件（如果要支撑 100 注册 / 20~30 并发）

| 项 | 需求 |
| --- | --- |
| 内存 | **32 GB 起**（20 并发中等任务）、**64 GB** 舒适 |
| CPU | 16 核够用 |
| C 盘 | 至少 **50 GB** 空闲（Docker 镜像层 + 缓存） |
| D 盘 | **200 GB+**（用户数据） |

### 5.2 配置调整

| 参数 | 当前 | 建议 | 理由 |
| --- | --- | --- | --- |
| `HLZ_SANDBOX_MAX_CONTAINERS` | 4 | **20~30** | 空闲容器只占 2 MiB，很便宜；4 太少会频繁 LRU 淘汰导致反复重建（每次 350ms） |
| `HLZ_SANDBOX_MEMORY` | 1g | **512m** | 实测真任务峰值 330 MiB，512 够；避免单个容器 OOM 时拖垮整机 |
| `HLZ_SANDBOX_IDLE_TTL_S` | 900 | 保持 | 15 分钟对交互式够用 |

### 5.3 不需要做的事

- **不要为了省内存换瘦镜像**：pandas 的 45 MiB 是它自己的开销，
  不是镜像的；镜像大小只影响磁盘和创建时间
- **不要给每个容器分配更多 CPU**：实测 1 核能跑满，加核只用得上并发

## 6. 复现方法

```bash
cd backend
python tests/manual/resource_profile.py --n 5    # 5 个并发
python tests/manual/resource_profile.py --n 20   # 20 个并发
```

脚本会：创建 N 个容器 → 分五档加载负载（后台 + 存活期间采样）→
测 CPU 利用率 → 清理，最后把数据写到 `backend/work/resource_profile.json`。

## 7. 测量方法上的两个坑（记录下来避免重犯）

### 7.1 内存必须在进程存活时采样

第一版写的是：

```python
run(["docker", "exec", nm, "python", "-c", "import numpy; a = np.ones(...)"])
time.sleep(2)
mem = mem_mib(nm)   # ← 错的：进程已退出，内存已释放
```

测出来「分配 300MB 后只占 2.75 MiB」，明显矛盾。
改为 `docker exec -d` + 内部 `sleep(30)` 保持存活，期间采样，才得到真实的 329.79 MiB。

**教训**：`docker exec` 返回 ≠ 进程还在。同步 exec 的副作用在返回时已经消失。

### 7.2 cgroup 路径

容器内是 cgroup v2，读 `/sys/fs/cgroup/memory.current`。
不要试 v1 的 `/sys/fs/cgroup/memory/memory.usage_in_bytes`（返回 no v1）。

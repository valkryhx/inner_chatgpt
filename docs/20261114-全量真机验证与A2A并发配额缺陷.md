## 1. 抓到的缺陷：A2A 并发配额 TOCTOU

### 1.1 现象

G 组首次跑：并发提交 3 个长任务，默认上限 2，期望至少 1 个 429，实测 **0 个 429**。

### 1.2 定性（用探针分开「没生效」与「竞态」）

`work/_probe_quota.py` 分别测串行与并发：

| 场景 | 结果 |
|---|---|
| 串行提交 3 个 | 200 / 200 / **429** ← 配额逻辑本身是对的 |
| 并发提交 3 个 | 200 / 200 / 200 ← 全部放行 |

结论：**不是"配额没生效"，是并发竞态**。

### 1.3 根因

原实现：

```python
await _enforce_quota(identity)   # SELECT COUNT(*) —— 有 await
...
row = await store.create_task(...)   # 另一处 await
```

两个 `await` 之间是换手点。三个并发请求**同时**读到 `count=0`，
于是全部通过检查再各自建行 —— 配额在并发下等于没有。

这是典型 TOCTOU（check-then-act）。单测 `test_active_task_quota_is_enforced`
只验串行，所以一直没暴露。

### 1.4 修法

把「查数 + 建行」放进同一个进程内临界区：

```python
_QUOTA_LOCK = asyncio.Lock()

async with _QUOTA_LOCK:
    await _enforce_quota(identity)
    row = await store.create_task(...)
```

**为什么用进程内锁而不是 DB 级约束**：部署是单 worker（`run.py` 未传 `workers=`），
进程内锁足够且没有跨进程开销。多 worker 部署需要换成 DB 级方案（唯一约束 + 重试，
或事务内 `SELECT ... FOR UPDATE` 的 SQLite 等价物）—— 这一点已记入未覆盖项。

**临界区只包「查数 + 建行」两步**，不含前面的会话创建与后面的 `_spawn`：
那两步不改变活跃计数，包进来只会拉长锁持有时间。

### 1.5 验证

- **L1 红灯测试** `test_quota_holds_under_concurrent_submissions`：
  3 个并发、上限 1，必须恰好 1 个成功。修前 3 个全成功（红），修后通过（绿）。
- **真机复验**（`_probe_quota.py`）：串行 200/200/429；**并发 200/429/200**。
- **不误伤幂等**：真机验证「占满配额 → 新建第 3 个 429 → 重放已存在 messageId 仍 200」，
  PASS。这条很重要：修配额最容易顺手把幂等重放一起拦掉。

## 3. 顺带核实：RuntimeHub 是池子吗

用户问到这一点，做了只读探针 `work/_probe_runtime_pool.py`（把真贵的 `build`
换成假实现，只测缓存结构）：

| 特性 | 实际 |
|---|---|
| 复用 | ✅ 按 `(user_id, model_id)` 缓存，同一对象 |
| 并发去重 | ✅ per-key `asyncio.Lock`，5 并发只 build 1 次 |
| **上限 / 淘汰 / LRU** | ❌ **没有**。200 个新用户 → 202 条（实测） |
| 空闲超时 | ❌ 没有 |
| 回收 | 只有显式 `invalidate` / `invalidate_all`（配置变更、skill 导入时触发） |

准确说法：**惰性创建的进程内缓存**，不是池子（无 prewarm / 无上限 / 无淘汰），
也不是「自动扩容」——只是「首次访问建一个，之后一直留着」。

每条持有 httpx client + MCP 连接 + registry + AgentLoop。当前真实库 54 个用户，
规模安全；但**用户数上去后是确定的单向增长点**（不是泄漏，是只增不减）。
要改需加 LRU + 上限 + 空闲过期，属独立设计，本次未动。

## 4. 未覆盖 / 后续

| 项 | 说明 |
|---|---|
| **多 worker 下的配额锁** | `_QUOTA_LOCK` 是进程内的。单 worker 部署正确；多 worker 需换 DB 级方案。与记忆 dream 的多 worker 问题是同一类 |

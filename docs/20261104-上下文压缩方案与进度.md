## 1. 现状排查结论（改代码前）

### 1.1 已有实现

| 位置 | 现状 |
|---|---|
| `backend/app/agent.py` | `create_agent(..., middleware=[SummarizationMiddleware(model, trigger=("tokens", soft_limit), keep=("messages", 20), token_counter=message_token_counter)])` |
| `backend/app/config.py` | 从 `llm.yaml` 读取 `auto_compact_tokens`(软线) / `hard_limit_tokens`(硬线)，缺失时按 `auto_compact_ratio`(0.90) / `hard_limit_ratio`(0.95) 派生 |
| `backend/app/sse.py` | 监听 `on_chain_end` 且 name 含 `Summarization` → 发 `compaction` 事件 |
| `backend/app/compaction.py` | `manual_compact()`：把早期消息用 LLM 摘要替换，写 LangGraph checkpoint |
| `POST /api/sessions/{id}/compact` | 手动压缩接口 |
| `frontend` 顶栏按钮 | 调 `api.compact()`，仅当 `compacted=true` 时把本地 `autoCompacted` 计数 +1 |

### 1.2 定位到的问题（根因）

1. **手动压缩“没反应”= 设计缺陷，不是接口挂掉**：
   - `manual_compact()` 只改 LangGraph **checkpoint**（`update_state`），**不改 `messages` 展示表**。
   - 前端压缩后 `loadMessages()` 拉的是 `messages` 表 → 内容与压缩前完全一样。
   - 页面唯一变化是小徽标「压缩 未触发→已启用」+ 一个自动消失的 banner 计数，**用户几乎感知不到**。
   - 且会话消息数 `<= keep(6)` 时直接返回 `compacted=false`，前端连计数都不加 → 表现为「点了完全没反应」。

2. **自动压缩“几乎不生效”**：默认阈值来自 `llm.yaml` 软线 `auto_compact_tokens: 115200`（deepseek 256k 窗口的 0.9）。正常演示对话远达不到，用户永远看不到自动压缩。此前台账里的「✅ 自动压缩」是用环境变量 `AGENT_SOFT_LIMIT` 临时调低阈值测的，**真实阈值下未验证**。

3. **自动压缩的 SSE 事件识别是脆弱的字符串匹配**（`"Summarization" in name`），未做真实事件链路验证；若节点名不含该串则前端永远收不到 `compaction`。

4. **无 `/compact` 输入框指令**。

5. **无硬线裁剪兜底**：只有软线摘要，万一摘要失败或单条消息超大，没有像 GenericAgent `trim_messages_history` 那样的硬线丢最旧消息的安全网。

6. `llm.yaml` 阈值在 `config.py` 里**解析了但没进用户级配置**：用户自建 LLM 配置（`user_llm_configs` 表）只有 `context_window`，`agent.py` 直接用 `ctx*0.9` 硬算，无法按用户配置单独调阈值。

## 2. 参考 GenericAgent 的做法

| 机制 | GenericAgent 位置 | 要点 |
|---|---|---|
| 软线（摘要式压缩） | `genericagent/core/context.py: should_auto_compact_agent()` | 估算「当前上下文 token + 本次待发 pending_text」> `auto_compact_tokens`(软线) 即触发 |
| 手动 `/compact` | `genericagent/core/app.py: _manual_compact()` | `/compact [自定义指令]` 用 LLM 摘要替换长历史，输出新历史（`summary + 保留的近段`） |
| 硬线（裁剪兜底） | `genericagent/llm/core.py: trim_messages_history()` | 超 `hard_limit_tokens` 时丢弃最旧消息，压到 `hard_limit * recover_ratio`，作为安全网 |
| 压缩后历史结构 | `_summary_history_pair()` | 变成「一条摘要消息 + 最近若干条」 |
| 失败回滚 | `compact_agent_context()` | 摘要失败时恢复旧历史，返回失败信息 |

**核心启发：**
- 软线（摘要、保信息）与硬线（裁剪、防溢出）**两级阈值**，软线 < 硬线。
- 手动 `/compact` 与自动压缩**走同一套摘要逻辑**，只是触发器不同。
- 压缩**必须有可见结果**：历史被替换 → 前端要能感知。

## 3. 本项目改造方案

> 原则：**能用 LangChain/LangGraph 原生的就用原生**（`SummarizationMiddleware` 负责软线自动摘要），在其上补「硬线裁剪」「手动 /compact」「可视化」「阈值可配」四件事。

### 3.1 阈值来源与派生（backend/app/config.py + db）

- `LLMSettings` 已有 `soft_limit_tokens` / `hard_limit_tokens`：优先读 `auto_compact_tokens` / `hard_limit_tokens`，否则按 `auto_compact_ratio` / `hard_limit_ratio` 从 `context_window` 派生 —— 保持。
- **用户级配置对齐**：`user_llm_configs` 增加 `auto_compact_tokens`、`hard_limit_tokens` 两列（可空）。
  - 有值 → 直接用；
  - 空 → 按 `context_window * 0.90` / `* 0.95` 派生。
- 兼容旧库：`init_db()` 里做 `ALTER TABLE ... ADD COLUMN`（`try/except` 幂等），并对既有表补列。

### 3.2 自动压缩（软线，发送前按 token 阈值判断；2026-11-04 二次修正）

- **不再使用 `SummarizationMiddleware`**。原因（实测）：
  1. 它按「模型上报的总 token」判定。本机 responses 线短对话的 `usage_metadata.total_tokens` 就有 ~487–743
     （含 system prompt + 工具 schema），而 `message_token_counter` 只计对话文本 token，两套口径不一致；
  2. 它会把「已是摘要」的上下文再次摘要；
  3. 更严重：手动 `/compact` 写入的摘要消息带 `lc_source=summarization`，旧 `sse.py` 在每轮 `on_chain_end`
     只要看到它就把本轮判定为「又压缩了一次」→ **手动压缩后每轮都误报一次 auto 压缩、并多写一条 system 摘要**。
- **改为发送前自研判定**：`backend/app/compaction.py: enforce_soft_limit(user_id, session_id, pending_text)`，
  对齐 GenericAgent `should_auto_compact_agent`：
  - 每轮发送前估算 `message_token_counter(checkpoint 消息) + estimate_tokens(本轮输入)`；
  - `> 软线 auto_compact_tokens` 才调用 `model.ainvoke` 摘要较早消息，替换为「摘要 + 最近若干条」；
  - 摘要后回落目标 `soft_limit × SOFT_LINE_RECOVER_RATIO(0.5)`，且**至少保留最近 2 条**（`AUTO_MIN_KEEP_MESSAGES`），
    避免把最近一问一答也摘要掉；
  - 未超阈值时返回 `None`（不落库、不向前端报 compaction）；
  - 由 `chat.py: _event_stream` 在 agent 运行前调用，命中则 `yield compaction(trigger=auto)`。
- `compaction` 事件携带 `trigger="auto"`、`summary_tokens`、`kept_messages`、`before/after` tokens。

### 3.3 硬线裁剪（兜底安全网，参考 GenericAgent `trim_messages_history`）

- 新增 `backend/app/compaction.py: enforce_hard_limit(user_id, session_id, ...)`：
  - 估算 checkpoint 现有 token；超过 `hard_limit_tokens` → 保留最近 `keep` 条 + 用一条 `[已裁剪 N 条较早消息]` 占位摘要替换最旧部分（与软线不同：**不调用 LLM**，纯裁剪，成本低、必定成功）。
  - 由 `chat.py` 的 `_event_stream` 在 **agent 运行前**调用一次（本地兜底，避免依赖中间件内部时机）。
- 与软线配合：软线先尝试摘要保信息；硬线在溢出前强制裁剪，保证请求**绝不超窗**。

### 3.4 手动 `/compact`（输入框指令）

- 前端 `Composer` 检测输入以 `/compact` 开头（或等于 `/compact`）→ 不发普通消息，调用压缩接口。
- 支持 `/compact 自定义指令`（传给摘要 prompt，增强压缩方向控制，如「重点保留代码」）。
- 顶部「压缩上下文」按钮保留（等价于 `/compact`）。
- **后端扩展** `POST /api/sessions/{id}/compact` 接收可选 `instructions` 与 `keep`。
- `manual_compact()` 改进：
  - 用 `compress` 思路：摘要早期消息 + 保留最近 `keep` 条 → 替换 checkpoint；
  - **同时写一条可见的 system/summary 消息到 `messages` 表**（`role='system'`, `status='complete'`, `blocks=[{type:'summary'}]`），让前端历史里真实出现「已压缩」条目，而不是只有小徽标。

### 3.5 前端可视化

- 历史里渲染 `summary` 类型 block：一张浅色卡片「上下文已压缩（摘要 X tokens，保留最近 Y 条）」并可展开看摘要正文。
- 顶栏徽标显示「压缩：N 次（最近 X tokens）」。
- `/compact` 结果用 toast/banner 反馈：成功「已压缩 N 条 → 摘要 M tokens」，失败「压缩失败：原因」。
- Composer 占位提示补充：`输入 /compact 可手动压缩上下文`。

### 3.6 配置页

- `SettingsModal` 的 LLM 表单新增两个可空数字框：`auto_compact_tokens`、`hard_limit_tokens`（留空=按窗口比例自动派生），并给出派生提示。

## 4. 验收标准

1. 输入框输入 `/compact` → 历史中出现「上下文已压缩」摘要卡片，早期消息被折叠/摘要；顶部徽标计数 +1。
2. 顶栏「压缩上下文」按钮与 `/compact` 行为一致。
3. 自动压缩：用可调低阈值（测试用 env 或配置）验证一次真实对话触发 → 收到 `compaction` 事件 + 前端横幅。
4. 硬线：构造超硬线 token 的会话，发消息时不报 context overflow（被裁剪）。
5. 阈值：`llm.yaml` 与用户配置的 `auto_compact_tokens/hard_limit_tokens` 都生效；留空按 `0.90/0.95` 派生。
6. 旧库升级不报错（幂等 ALTER）。

### 6.4 自动压缩误报修复验证（2026-11-04）

- **复现**：新建会话 → 聊 4 轮 → 手动 `/compact` 成功 → 再连发 3 轮：修复前每轮都收到

  触发后 `after_tokens` 回落，需再累积若干轮才二次触发（锯齿），不再「每轮一次」。
- **回归**：`e2e_compact.cjs` 与 `e2e_browser.cjs` 全部 PASS。

## 7. 已知遗留 / 待处理（TODO，勿遗忘）

### 7.1 单轮超大回复会导致「连续二次压缩」

- **现状**：`enforce_soft_limit` 在发送前判断 `checkpoint_token + 本轮输入 > 软线阈值` 时压缩，摘要后
  会保留最近 `AUTO_MIN_KEEP_MESSAGES`(=2) 条。**如果某一条消息本身非常大**（例如用户要求「详细讲」，
  模型一次输出一两万 token），那么：
  1. 该轮结束时 `checkpoint_token` 已接近/超过软线阈值；
  2. 下一轮发送前判定超阈值 → 触发自动压缩；
  3. 但摘要后仍要保留「最近 2 条」，其中就包含这条超大回复 → `after_tokens` 仍可能 > 软线阈值；
  4. 于是下一轮**再次触发**自动压缩……在被压掉之前会连续触发若干次。
- **是否算 bug**：不是误报（确实超阈值），是当前「保留最近 N 条」策略与「单条超大」冲突的取舍。
  功能上不会超窗（硬线兜底仍在），但会连续多次摘要、摘要次数偏多，且把这条超大便回复也摘要掉会丢失近期细节。
- **复现**：小阈值实例 `AGENT_SOFT_LIMIT=4000` 下，发一句「请详细讲 400 字」类长输出请求，
  观察连续两轮 `compaction(trigger=auto)` 且第一次 `after_tokens > soft_limit`（2026-11-04 实测出现过
  `before=19434 / after=16926 / soft=4000`）。
- **待处理候选方案（择一或组合，尚未实施）**：
  1. **截断超大单条**：单条消息 token 超「软线的一定比例」时，为该条单独生成摘要/占位（或截断），不再整条保留；
  2. **保留窗口按 token 自适应**：`AUTO_MIN_KEEP_MESSAGES` 改为「保留最近 K 条且累计 ≤ 某 token 上限」的 token 兜底，
     而非纯条数，避免必须保留超大单条；
  3. **有界循环压缩**：摘要一次后若仍超阈值，继续摘要直到低于阈值（限定最大次数，防死循环），确保「一轮内收敛」；
  4. **超大工具结果单独治理**：对超大 `tool` 消息（如网页抓取全文）单独截断/摘要，避免污染整体窗口。

> 状态图例：✅完成 / 🟡进行中 / ⏳待办 / ❌受阻

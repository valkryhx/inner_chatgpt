# 文件工具走沙箱服务（方案 B）+ 共享组权限（2026-11-20）

> 涉及：`backend/app/sandbox/manager.py`、`backends/service.py`、
> `backend/sandbox_service/main.py`、`workspace.py`、
> `backend/app/workspace.py`、`Dockerfile`、`docker-compose.yml`
> 测试：`test_sandbox_service_file_ops.py`（7）、`test_sandbox_service_file_api.py`（19）、
> `test_shared_group_permissions.py`（10，其中 3 条 POSIX-only）
> 反向确认：`docs/probes/20261120-文件工具分发反向确认.py`（4/4）

## 1. 起因：Agent Team 的子代理全都写不出文件

真机现象（2026-11-20）：

- 子代理跑了 82 秒后状态是 `stopped` 而不是 `completed`
- 最后一个结果是「写入被沙箱阻塞。我先确认工作区状态，再换路径重试」
- 对应的两个 team task 一直是 `pending`、`owner_agent_id` 为空

app 日志：

```
WARNING app.builtin_tools: 沙箱分流失败且 mode=strict：不回落进程内（tool=file_write）
SandboxUnavailable: 未安装 docker SDK（ModuleNotFoundError）
```

## 2. 缺陷一：`write_file` / `patch_file` 从来没接 backend 分发

对比 `manager.py`：

| 方法 | backend 分发 |
| --- | --- |
| `exec_code` | ✅ 有（`:343`） |
| `write_file` | ❌ **没有**，直接 `self.pool.acquire()`（Docker） |
| `patch_file` | ❌ **没有** |

`HLZ_SANDBOX_BACKEND=service` 时 app 容器里没装 docker SDK，于是每次
`file_write` 都抛 `SandboxUnavailable`；strict 模式不回落 ⇒ 子代理卡死。

**这个缺陷一直存在，只是被降级掩盖了**：修复前 strict 允许回落进程内，
`write_file` 默默无隔离地写成功了。上一轮修 strict 语义后才现形。

### 修法

`write_file` / `patch_file` 加 backend 分发，与 `exec_code` 同构。
新增 `_workspace_rel()` 把绝对路径换算成相对 workspace 根（子代理的
`write_root` 也在里面），服务侧契约只接受相对路径。

## 3. 方案 B：服务侧新增 `/v1/write` 与 `/v1/patch`

「文件工具留在 app 进程内」这个说法出处有误 —— 方案的 §3.3
「该留在 app 的」列的是 policy / 工具 schema / 预算 / 降级决策 / 总开关，
**没有文件工具**。`ServiceBackend.write_file` 里的注释归给 §4.2，
但 §4.2 讲的是池的设计。

走沙箱的收益是防御纵深：写操作也在沙箱 mount namespace 里，
路径校验万一有漏洞还有容器兜底。

### 服务侧自己校验路径（关键）

app 已经用 `safe_workspace_path()` 校验过，但服务侧**不能因此跳过**：
app 可能被攻破、可能有别的入口直连、将来会加新调用方。
`workspace.resolve_in_workspace()` 的规则：

- 只接受**相对路径**（绝对路径直接拒）
- `resolve()` 后必须仍在 workspace 内（挡 `..` 与符号链接）

## 4. 缺陷二：两个容器 uid 不同，目录写不进去

| 容器 | 用户 | 为什么 |
| --- | --- | --- |
| app | `root` | 现状 |
| sandbox | `uid 1000` | 必须非 root，否则 `RLIMIT_NPROC` 静默失效、fork 炸弹拦不住 |

app 创建的 `workspaces/<uid>/` 属主 root、属组 root → 沙箱服务写不进去：

```
PermissionError: [Errno 13] Permission denied:
  '/app/backend/data/workspaces/u_perm_check/xxx.txt.hlz-tmp'
```

### 方案：共享组 + setgid（分两层）

**第一层（顶层目录）**：`sandbox-perms` 建组 1000、`chgrp -R 1000`、
`chmod 2775`。app 服务加 `group_add: ["1000"]`。

**第二层（运行时新建的子目录）** —— 这一层才是真正的坑：

`sandbox-perms` 只在启动时跑一次，追不上之后新建的目录。
实测当时的状态：

```
drwxr-sr-x 2 root hlz  .../u_perm_check      ← 组有 r-x，没有 w
touch: cannot touch '...': Permission denied
```

setgid 解决了「组继承」，但没解决「组可写」—— 因为 umask 0755 给的是 `rwxr-xr-x`。

**修法**：`app/workspace.py::ensure_dir_shared()`，
所有建目录的地方都走它（`mkdir` + 强制 `| 0o2000 | 0o020`）：

- `user_workspace()` —— 用户根目录
- `write_root_for()` —— 子代理的 `.subagents/<s>/<a>`

不依赖 umask（不同部署/CI 可能不同，靠它等于靠运气）。

> `.subagents/...` 这层是最后发现的：顶层和用户目录都修好之后，
> 子代理仍然 507 —— 因为它的 write_root 是**运行时**新建的。
> `test_user_workspace_and_write_root_use_same_helper` 用静态检查钉住
> 「这两处都不许再出现裸 mkdir」。

### 第三、四层（2026-11-20 真机追出来的，前两层修完还 507）

前两层修完、镜像重建部署后，hx 重测 Agent Team **仍然 507**，路径是：

```
PermissionError: [Errno 13] Permission denied:
  '/app/backend/data/workspaces/u_c56b8337dd09/.subagents/co_8d8bd184324a/writer/trump'
```

#### 第三层：遗留目录是旧代码建的，连 `mkdir` 都不允许

`stat` 出来：

```
755 root:1000  .../u_c56b8337dd09/.subagents
755 root:root  .../u_c56b8337dd09/.subagents/co_8d8bd184324a   ← 旧代码时代建的
```

`ensure_dir_shared` 第一版是「先 `mkdir(parents=True)` 再 chmod」。

- 对**新**目录没问题（父级已被修好）
- 对**遗留**目录直接死在第一步：uid 1000 在 `755 root:root` 里没有 `w`，
  `mkdir` 抛 `PermissionError`，**根本没走到 chmod**

**修法**：改成「从 `boundary` 往下逐级：每层先修权限、再建下一层」。
历史遗留目录会被顺手修好，不需要单独的数据修复脚本。

`boundary` 是必须的参数，不能无脑往上 chmod（会改到系统目录）。
所有调用点都传了它 —— 有 AST 守卫钉住（见下）。

#### 第四层：`chmod` 改不了属组，而且 uid 1000 连 `chmod` 都没权限

把顺序改对之后，错误从 `PermissionError` 变成了 `FileNotFoundError` ——
看着像"更进一步"，其实是**第二处根因**露出来了。

在容器里实测 uid 1000 对那个目录能做/不能做什么：

```bash
$ docker exec hlzsbxprobe-sandbox-1 sh -c 'id; chmod 2775 $D; mkdir $D/writer'
uid=1000(sandbox) gid=1000(hlz) groups=1000(hlz)
chmod: changing permissions of '...': Operation not permitted
```

两个事实：

1. **`chmod` 要求「是属主或 CAP_FOWNER」**。uid 1000 既不是属主（root）、
   也没有 CAP_FOWNER ⇒ **它连修都修不了**。
   「让服务侧顺手修祖先」这条思路**根本不成立**，只能是 app（root）来做。
2. **`chmod` 只能改权限位，改不了属组**。就算 chmod 成功，
   `755 root:root` → `2775 root:root` 里 uid 1000 仍然**不在组里**，照样写不进去。
   必须先 `chgrp`（或 `chown -1:gid`）。

**修法（两处一起）**：

| 位置 | 改什么 |
| --- | --- |
| `app/sandbox/manager.py::write_file` / `patch_file` | **分发到服务前**先 `ensure_dir_shared`（app 是 root，只有它能修） |
| `app/workspace.py::_mkdir_and_fix` | 加 `chgrp`：属组不对就 `os.chown(p, -1, gid)` |
| `sandbox_service/workspace.py` | 同上，保持两侧一致（服务侧多半改不动，但幂等无害） |

共享组取**边界自己**的 `st_gid`，不是父目录 —— 遗留目录的父级本身可能是坏的，
照抄会一路传染。部署里边界是 `sandbox-perms` 已经 `chgrp 1000` 过的那一层。

> 为什么这个修复必须在 app 侧：第三层靠「顺序」能在服务侧修好，
> 第四层不行 —— 服务侧没有权限。**能修的人只有 root。**
> 这也解释了为什么前两层修完真实用户仍然卡住：写文件的起点是 app 的
> `write_file`，而它在分发时**完全没建目录**，直接发请求给服务。

### 第五层：`code_run` 的产物组不可写（**当前代码仍有，已修**）

hx 的自述里还有一句关键的话：

> `file_write` 整体返回 507 …… 它确认目录为空后重建同名目录（现为 1000:1000），
> **改用 python 写入，文件因此正常生成**。

也就是说：真实用户绕过 `file_write`，用 `code_run` 完成了工作。
这暴露了 `ensure_dir_shared` 覆盖不到的**第三个创建者**。

| 创建者 | 受什么控制 | 谁保证 `g+w` |
| --- | --- | --- |
| app 服务 | `ensure_dir_shared` | ✅ |
| 沙箱服务（`/v1/write`） | `ensure_dir_shared` | ✅ |
| **`code_run` 里的用户代码** | **进程 umask** | ❌ 之前没人管 |

实测（修复前，真机）：

```
mkdir       → 0o2755    ← setgid 从父目录继承，但组不可写
write_text  → 0o100644  ← 组不可写
```

根因：bwrap 子进程的 umask 是默认的 `022`。`022` 会清掉组写位。

为什么这个缺陷**不容易被发现**：用户自己写的文件，他自己是属主，
能改能删 —— 表面上一切正常。hx 的现场就是这样，他看到"文件正常生成"，
以为问题解决了。真正的代价在后面：workspace 的契约是「每一层都对
共享组可写」，一条不满足的路径会在某次看似无关的操作里炸出来
（`file_patch`、归档淘汰、任何换 uid 的动作）。

**修法**：`executor/bwrap.py` 两条执行路径都显式 `umask 002`。

- daemon 模式 → `_child_run` 里 `os.umask(0o002)`
- 一次性模式 → argv 前缀 `sh -c 'umask 002; exec python3 -c "$0"' code`

`002` 而不是 `022`：只放开组写位，不动 other —— 与 `ensure_dir_shared`
的 `| 0o020` 是同一条不变量。

修复后同一探针：

```
DIR  0o2775 组可写=True
FILE 0o664  组可写=True
```

> 这条也解释了 hx 说的「`/ws/research` 属主 65534」为什么能出现：
> `65534` 是 Linux 的 **overflow uid** —— bwrap 的用户命名空间里某个
> uid 没被映射到宿主时的产物。属主是外来 uid + 目录组不可写 ⇒ 双杀。
> 本栈当前已无 65534 文件（`find -uid 65534 | wc -l` = 0），但代码对
> 这种目录的处理能力已单独验证（见下探针 2）。

### 权限测试为什么有 POSIX-only

`setgid` / `g+w` 在 Windows 上不存在（`st_mode` 恒 `0o40777`），
断言必然假红。所以那几条标了 `@posix_only`，真正验证靠容器里的真机跑。

**但这带来一个反向确认的陷阱**（本轮实际踩到）：把 `chown(...)` 换成 `pass`，
POSIX 断言在 Windows 上被 skip，于是**三个注入全绿**，看起来像"断言没有因果力"。
实际是**本地根本没跑到那条断言**。

修法：补两条**跨平台可观察**的断言 —— mock 掉 `os.chown` / `Path.chmod`，
只看「有没有调、调成什么」，与平台无关：

- `test_mkdir_and_fix_calls_chown_when_gid_differs`
- `test_mkdir_and_fix_calls_chmod_when_mode_differs`

为此把 `stat` 抽成 `_stat_mode(p) -> (mode, gid)`，测试可注入任意值。

## 6. 这一轮的失误

| 失误 | 后果 | 怎么防 |
| --- | --- | --- |
| 静态测试误加 `@posix_only` | 反向确认第 4 例永远绿（ok 停在 3/4） | 静态检查与平台无关，不该跳过 |
| 反向确认的破坏点写错（改函数名） | 破坏不生效，测试不变红 | 破坏必须是**语义**破坏（把 `ensure_dir_shared` 换成裸 `mkdir`），不是改名字 |
| **静态守卫只查「存在的调用缺 boundary」** | 把整个调用**删掉**反而通过（没有调用就没有违规） | 守卫必须同时钉「有多少处」和「在 backend 调用之前」，用 AST 按函数作用域限定 |
| **只靠 POSIX 断言做反向确认** | Windows 上被 skip ⇒ 注入缺陷后仍全绿，误判成「断言无因果力」 | 关键行为必须有**平台无关**的可观察断言（mock 掉系统调用） |
| **`_mkdir_and_fix` 吞掉 chmod 异常且不检查是否真的成功** | 错误从 PermissionError 变成 FileNotFoundError，掩盖了「uid 1000 无权 chmod」这个真根因 | 吞异常可以（非 POSIX 环境必须容错），但**必须把「修不动」这件事在调用链另一头暴露**——本轮靠真机 stat 逐级核对才发现 |
| 只修顶层目录权限就以为完事 | 子代理仍 507 | 真机验证每一步，不靠推断 |
| **只盯 `file_write`，没想到用户会绕道 `code_run`** | 真实用户"绕开"了 507 并自称成功，于是以为修好了；实际 `code_run` 的产物组不可写，把坑往后推 | 权限契约要按**创建者**逐个数，不是按「工具」数。`ensure_dir_shared` 只管两个创建者，第三个（用户代码）受 umask 管 |
| **umask 测试第一版数 `umask` 出现次数** | 注释里反复出现这个词，去掉一处仍然绿 | 计数数的是「文本提过几次」，不是「代码设过几次」。逐条锚定真实代码形态 |
| **umask 测试第二版只查一个锚点覆盖两支** | sh 分支满足断言，去掉 python 分支仍然绿 | 一个锚点覆盖两支代码 = 没区分。逐支断言 |
| **反向确认的注入串反斜杠转义对不上** | `replace` 静默不动，「注入失败」被记成「测试仍绿」。这已经是本轮第二次同类 | 锚点要短、只此一处；`_inject_and_run` 必须单独区分「注入失败」与「仍绿」|
| **探针读历史文件** | 改了 umask 仍报 `2755`，看起来像修复无效，其实是上一轮的目录（`mkdir(exist_ok=True)` 不改已存在的目录） | 探针在造现场前先删干净 |
| **探针的断言串与实际写入串不一致** | `patch_file` 明明成功，探针却报 FAIL（`"# 已被…改过"` vs `"# code_run（已被…改过）"`）| 断言串直接复用变量，不手抄 |

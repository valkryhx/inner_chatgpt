## 0. 结论（先纠正一个关键预期）

**不是 hook 实现的。** 记忆走的是 **attachment（上下文附件）** 机制——与
`skill_listing`、`plan_mode`、`todo_reminders` 并列的同级管线，在每一轮组装
上下文时按需计算并注入。

**读和写是两条不同的管线**，这一点很多调研会漏：

| | 管线 | 位置 | 是不是 hook |
|---|---|---|---|
| **读**（注入上下文） | attachment producers | `m0591:151783` | 否 |
| **写**（把记忆写出来） | 后台 fork 子代理 `[extractMemories]`，注册为 `post_turn_memory` 任务 | `m0832` | 否（全文唯一提到 hook 的地方是**拒绝**写入） |

所以「记忆是 hook 实现的」这个说法，在读侧和写侧都不成立。详见 §1.5 与 §2.3。

### 0.1 先定义：什么是 attachment 管线

这是理解整份调研的前提，所以单独说清。

**attachment 管线 = 「每轮把"此刻该补充给模型的上下文"按需算出来，再拼成一条附件消息
附在对话里」的那条通道。**

它不是提示词，不是工具结果，也不是 hook——是第四种东西：**平台主动塞给模型的
补充材料**。你在 CC 里见到的 `<system-reminder>` 那类内容，大部分就走这条管线。

它解决的核心问题是：**有些上下文不该常驻 system prompt，但模型在特定时刻需要。**

拿 `changed_files` 举例：模型改了几个文件，平台需要提醒它「这一轮你动过这些文件」。
这段信息：
- 不该写进 system prompt（每轮都不同，且会随会话膨胀）；
- 不该作为工具结果（它不是某次工具调用的返回值）；
- 应该在**这一轮**出现在上下文里。

attachment 管线就是干这个的。

**一次计算的完整形状**（`m0591:151808`）：

```js
async function dc(e, n) {           // e = 标签名, n = 异步产出函数
  let r = Date.now(), s = performance.now(), h = Sso();
  h?.producerBegan();
  let y = Math.random() < 0.05;      // 5% 采样打点
  try {
    let S = await n();               // ← 真正算附件内容
    let w = Date.now() - r;

        label: f(e), duration_ms: w,
        attachment_size_bytes: N, attachment_count: S.length
      });
    }
    return S
  } catch (S) { ... }

```

要点：
1. **每个 producer 是惰性的**（传的是函数而非值），只有被 `await n()` 才真正计算；
2. **有标签**（`"nested_memory"`、`"changed_files"`…），可单独计量与关闭；
3. **有耗时与体积遥测**，说明这条管线的成本是被官方盯着的；
4. **单个 producer 抛异常不影响其他**（内部 try/catch）。

**一轮里所有 producer 怎么汇聚**（`m0591:151790` 与 `151792`）：

```js
Ce?.mark("ambient_start");
let [Jt, fn] = await Promise.all([Promise.all(Ut), Promise.all(sn)]);
Ce?.mark("ambient_wait");
return azr(Akn([...At.flat(), ...Jt.flat(), ...fn.flat()]
    .filter((Sn) => Sn !== void 0 && Sn !== null)))
```

- 数组里是**几十个 `dc(...)`**，按分组塞进 `Ut` / `sn` / `At` 三个集合；
- `Promise.all` **并行**计算（不是串行）；
- 拍平、滤空、再过 `Akn`（顺序调整）与 `azr`（去重，见 §1.5）；
- 返回**一个 attachment 数组**。

**单个 attachment 长什么样**（`m0591:154466`，包装函数 `an`）：

```js
function an(e, n = {...}) {
  let r = nae(e);
  return {
    attachment: e,               // ← 本体（type: "nested_memory" 等）
    type: "attachment",          // ← 外层的消息类型
    uuid: n.uuid(),
    timestamp: ...,
    ...r
  }
}
```

即：`attachment` 是**消息层的一个 `type`**，本体放在 `.attachment` 字段里。
所以它最终是以「一条带 attachment 类型的消息」进入对话历史/上下文的，
而不是拼进 system prompt。

**为什么这个设计值得学**（对 Hlaudz 尤其）：

| 特性 | 好处 |
|---|---|
| producer 惰性函数 | 不需要的东西完全不计算，零成本关闭 |
| 并行 + 耗时遥测 | 上下文组装慢在哪一眼可查，可单独优化 |
| 有标签 | 能按 `nested_memory` 单独统计/关停/AB |
| 单点失败隔离 | 一个 producer 挂了不影响整轮 |
| 输出是「消息」不是「提示词」 | 天然进历史、可持久化、可按消息裁剪 |

对比「把所有东西拼进 system prompt」的做法：system prompt 每轮重算、无法
按需关闭、无法计量、内容一多就挤爆上下文且难以裁剪。attachment 管线是把
这件事**结构化了**。

**和 hook 的区别**（最容易混的一点）：

| | attachment 管线 | hook |
|---|---|---|
| 谁来算 | 平台内部的 JS producer | **用户/插件配置的外部进程** |
| 数据来源 | 平台自己的状态与文件系统 | hook 进程的 stdout |
| 能否写脚本干预 | 不能（除非改源码） | **能**（改 `settings.json`） |
| 在源码里的位置 | 几十个 `dc(label, fn)` | 单独一条 `async_hook_responses` |

**关键**：hook 的输出**也是通过 attachment 管线进入上下文的**
（`dc("async_hook_responses", ...)`）。所以两者不是并列关系，而是
「hook 是数据源之一，attachment 是运输通道」。

这也正是「记忆是 hook 实现的」这个误传的由来——确实是同一条通道，
但记忆的内容**不是任何 hook 产的**。

### 1.5 层五：写入管线 `[extractMemories]`（记忆是怎么被写出来的）

前面四层都是**读**。真正让记忆「长出来」的是这条独立的写入管线，它不在
`m0591`（读管线主模块）里，而在 `m0832_0x124c3af6.js`。**这是整份调研里
最容易被忽略、也最值得抄的一层**——因为绝大多数「记忆」实现只做了读，没做写。

#### 它不是一个 hook，是一个后台 forked 子代理

这里的否定证据非常硬：`m0832` 全文只有一处出现 "hook"，而且是**拒绝**：

```js

  "a PreToolUse hook requires confirmation for this call, and the memory agent "
  + "runs headless with no user to answer — the call is denied", "hook_ask");
```

即：写入代理是**无人值守（headless）**的，一旦某个 PreToolUse hook 要求确认，
它没有用户可以问，只能**放弃这次写入**。所以 hook 在这里的角色是「可能阻断写入的
外部约束」，不是「触发写入的机制」。

真正的触发是一次 **fork**（`:1079`，另有 `:1176` 走非 fork 路径）：


`skipTranscript: !0` 是关键：**这次子代理跑的完整过程不会污染主对话历史**。
这与 Hlaudz P2 里「子代理写侧链 history、不写 `session_history`」是同一个决策。

#### 三道闸门，顺序很重要

写入不是「每轮都跑」，要连过三关（任一处 skip 都会记一条 telemetry）：

| 闸门 | 位置 | 作用 |
|---|---|---|
| **成本闸**：`first_look` | `:461` `querySource: "extract_memories_first_look"` | 先花一次（便宜的）模型调用来判断「这一轮有没有值得写的东西」，只输出 `{"write_likely": true\|false}`。答 false 就整轮跳过 |
| **prose 闸**：`proseGate: "chat"` + `minProseWords` + `reviewWindow` | `:946` | 要求最近窗口内有**足够多的自然语言**（纯工具调用轮次不值得记） |
| **权限闸** | `:978` / `:1006` / `:1035` | 权限规则拒绝写、`when_overage: skip` 时超额、first look 说不写 |

`first_look` 的实现（`:461-466`）读得很清楚：


注意最后一句的**失败方向是保守的**：模型没答出布尔值 → **不跳过**（继续跑），
而不是跳过。因为漏存一条记忆的代价，比多花一次模型调用高。

#### prose 计数是 CJK 友好的（这条对中文产品直接可用）

`:127-135`：

```js

  kr = /[\p{Script=Han}\p{Script=Hiragana}\p{Script=Katakana}\p{Script=Thai}
        \p{Script=Lao}\p{Script=Khmer}\p{Script=Myanmar}\p{Script=Tibetan}]/gu;

function Tt(e) { return e.match(kr)?.length ?? 0; }          // CJK 字符计数
```

`Et = 2` 即**一个汉字算两个词**。为什么必须这么做：中文没有空格分词，
`split(/\s+/)` 会把整段中文算成 1 个"词"。如果照英文的 `minProseWords` 直接判，
**任何中文对话都会被判「没内容」，记忆永远不写**。

对 Hlaudz 是直接后果：我们主要面向中文用户，这条**不是可选项，是必需品**。


两个动作合成一件事：
1. **`readFileState` 重新同步**——注意 `requireReadBeforeWrite: !0`，与 Hlaudz
   `read_registry.check()` 的「写前必读」是同一个约束。后台写入必须**绕过也算数**地
   刷新读记录，否则主代理下次写这个文件会被自己的门禁拦住；
2. **`enqueuePendingMemoryUpdate`** 把「我刚写了什么」排进队列，下一轮
   `dqr()`（§1.3）就把它变成 `memory_update` attachment 告知模型。

**所以读写是闭环的**：后台写 → 刷新读缓存 → 排通知 → 下一轮 attachment 注入 → 模型知道「我刚记了这些」。
少了任何一环，模型就会重复记同一件事，或者不知道自己记过。

#### 这里没有的东西（同样重要）

- **没有向量库**。记忆是 `.md` 文件，检索靠路径触发（§1.2）+ 模型显式读（§2.1）。
- **没有每次对话都跑**。三道闸门 + `everyNTurns` + `idleFlushSeconds` 在压频率。
- **没有让主对话等**。它是 `post_turn` 后台任务，且有 `tengu_extract_memories_coalesced`
  （`:1286`）——上一次还没跑完时，新的合并成一次尾随执行，不叠加。

### 2.3 记忆根目录怎么解析（这是「隔离」的真实落点）

所有记忆路径最终都收敛到 `vl()`（`m0191_0x1155a4cc.js:2751`）：


2. **`qyt()` 允许「没有文件夹」这种状态**（`canLackAFolder()`），此时 `Dz()` 返回

`root in parents`），只是 CC 用字符串前缀，Hlaudz 用 `Path` 语义（后者更稳，
不会把 `/a/bc` 误判成 `/a/b` 的子路径）。

## 4. 为什么"hook"这个印象会成立

不怪误传，因为**两者确实在同一个注入点汇合**——都是 attachment。区别在数据来源：

| | 数据来源 | 是否可被用户脚本改写 | 触发时机 |
|---|---|---|---|
| `nested_memory` | 文件系统里的 `.md` | 是（改文件） | 读写路径触发 |
| `memory_update` | 进程内 app state | 否 | 记忆写入后 |
| `async_hook_responses` | **hook 进程的 stdout** | **是（改 hook）** | hook 完成时 |

所以「记忆可以靠 hook 扩展」这个说法**方向对、机制错**：
- 你**不能**通过 hook 让 CC 加载一份记忆文件（记忆加载不走 hook）；
- 但你**可以**用 hook 往上下文里塞东西（走 `async_hook_responses`），
  效果上"像记忆"，但那是 hook 通道，语义不同（它不被记忆的去重/扣留/索引机制管理）。

而 `SessionStart` hook 在这里的角色是：`uqr` 里判断「有 SessionStart 的 hook 响应」
才去取 session 启动时的 attachment（`:154699`）。**它是 hook 侧的逻辑，不是记忆侧。**

## 5. 对 Hlaudz 的借鉴价值（按可用性排序）

### 5.1 立刻可借鉴：attachment 管线 vs 无条件塞提示词

Hlaudz 现在的 `SYSTEM_PROMPT` 是 7 节固定文本 + skill L1 索引（见 P8 记录）。
**记忆类内容一旦变多，无条件塞进 system prompt 会失控。**

CC 的做法值得抄：
- 每条内容是一个有 `type` 的 attachment，**按需计算**（`dc(label, fn)`）；
- 有 **trigger 机制**（读写路径才触发，不是每轮全量）；
- 有**上限 + 扣留 + 记账**（`withheld_memory` / `owed`），防止挤爆上下文；
- 有**去重**（`azr`：已作为 nested_memory 注入的不再重复出现在 withheld 里）；
- 有 **`inContextPaths`** 区分「原文是否已在上下文」。

Hlaudz 的 `builtin_tools.py` 已经有「统一结果预算 + 超限落盘」，思路一致，
但**上下文注入侧还没有这套预算/去重**。这是真正该学的部分。

### 5.2 可借鉴：延迟加载（NO_WAIT）

`CLAUDE_CODE_MEMORY_CONTEXT_NO_WAIT` + `late_memory_context` 这个组合很实用：
**记忆检索慢时不阻塞首 token**，等工具步骤后再补。

Hlaudz 现在的 `build_turn_runtime` 是同步装配（`subagent/session.py:73`），
记忆检索如果接进来，会直接吃掉首字延迟。这个模式正好解决。

### 5.3 可借鉴：agent-memory 与 agent-memory-local 分离

主 agent 与子代理的记忆目录分开（`:76049`）。
Hlaudz 的子代理已经用侧链 history 隔离（P2 决策），
但**如果将来加记忆，必须同样按 agent 隔离**，否则子代理会污染主对话的记忆。

### 5.4 不建议照抄：环境变量的数量

CC 有 15+ 个记忆相关环境变量。那是多年线上问题累积的补丁，
每个 `DISABLE_MEMORY_*` 背后都是一次事故。**新系统不该一上来就长这样**——
应该先有清晰的模型（trigger → 计算 → 上限 → 扣留 → 去重），再按需加开关。

### 5.5 关于「让 AI 更亲和」

你的判断是对的，但要说准：**亲和来自「记住关于用户的事」，不是来自 hook。**

具体到 Hlaudz 的可落地点（按性价比）：

1. **用户偏好记忆**（称呼、语气、语言习惯）——最直接的亲和来源；
2. **项目工作记忆**（这套代码的约定、上次做到哪）——减少重复交代；
3. **反馈记忆**（用户纠正过什么）——避免重犯（这正是 Hlaudz 现在
   `.claude/memory/` 那套 `feedback` 类型在做的事）。

关键是**注入必须是有预算、有去重、有触发的**，否则"亲和"会变成"上下文污染"。

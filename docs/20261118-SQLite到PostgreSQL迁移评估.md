# SQLite → PostgreSQL 迁移评估（真实实测，非估算）

> 2026-11-18。目标：为横向扩容做地基（SQLite 在共享/多进程下不可用）。
> 所有结论都有实测支撑，复现脚本见 §7。

## 0. 结论先说

**技术上可行，成本主要在「改代码」而不是「迁数据」。**

| 项 | 结论 |
| --- | --- |
| 数据量 | **21,262 行 / 27 表 / 98 MB** —— 很小，迁移是秒级 |
| 类型映射 | 只有 3 种（TEXT / INTEGER / BLOB），**没有需要人工判断的类型** |
| 真实迁移 | 实测 3 张代表表（2629+2947+51 行）**6/6 成功** |
| SQL 兼容 | **4 处需改**（`INSERT OR REPLACE/IGNORE`），7 处 `ON CONFLICT` 已兼容 |
| PRAGMA | **58 处**，这是最大的改动面（SQLite 专有的表结构/状态查询） |
| 连接方式 | **126 处 connect**，必须全部改成连接池（否则每次 33ms） |
| 性能 | PG 单查询慢 ~16x（1.5ms vs 0.097ms），但**并发能力是 SQLite 没有的** |

**真正的阻塞不是数据，是 126 处 connect + 58 处 PRAGMA 的改造量。**

## 2. 类型映射：只需 3 条规则

| SQLite | 列数 | PG |
| --- | --- | --- |
| TEXT | 186 | TEXT |
| INTEGER | 73 | BIGINT |
| BLOB | 3 | BYTEA |

**没有 NUMERIC / REAL / DATETIME 等需要判断的类型** —— 时间戳全部是 INTEGER
（毫秒时间戳），这也是个好消息：排序语义不会因类型转换而变。

### 2.1 需要处理的：自增主键

4 张表用了 `INTEGER PRIMARY KEY`，其中 `a2a_audit` 显式写了 `AUTOINCREMENT`：

| 表 | 列 | 是否 AUTOINCREMENT |
| --- | --- | --- |
| `a2a_audit` | `id` | ✅ |
| `subagent_messages` | `seq` | 否（行号由代码给） |
| `team_events` | `event_seq` | 否（行号由代码给） |
| `writes` | `idx` | 否（行号由代码给） |

PG 里对应 `BIGINT GENERATED BY DEFAULT AS IDENTITY`。
迁移时要**保留原值**并用 `setval()` 把序列推到 max，否则新插入会撞主键。

后 3 张表的序列值其实是调用方显式传入的（`max+1`），迁到 PG 后可以保留这个
写法不动 —— 只要不改成依赖 IDENTITY 自增，连 `setval` 都不需要。
真正需要 `setval` 的只有 `a2a_audit.id`。

## 4. SQL 兼容性：实测哪些要改

在真实 PG 上逐条跑现有写法：

| 写法 | 结果 | 说明 |
| --- | --- | --- |
| `INSERT OR REPLACE` | ❌ **FAIL** | `syntax error at or near "OR"` |
| `INSERT OR IGNORE` | ❌ **FAIL** | 同上 |
| `ON CONFLICT ... DO UPDATE SET x=excluded.x` | ✅ OK | 两库通用 |
| `ON CONFLICT ... DO NOTHING` | ✅ OK | 两库通用 |
| `123 = '123'` | ✅ OK | 都宽松（但**不要依赖**） |
| `'10' > '9'` | ✅ 但结果 `False` | 文本字典序，不是数值序 |
| `GROUP BY 主键 + 选非聚合列` | ✅ OK | PG 允许函数依赖 |

### 4.1 需要改的 4 处

| 文件 | 行 | 现状 |
| --- | --- | --- |
| `history_store.py` | 95 | `INSERT OR REPLACE` |
| `team_resume.py` | 106 | `INSERT OR IGNORE` |
| `subagent/store.py` | 202 | `INSERT OR REPLACE` |
| `subagent/store.py` | 282 | `INSERT OR IGNORE` |

改法统一：`INSERT ... ON CONFLICT(<pk>) DO UPDATE SET ...` / `DO NOTHING`。

### 4.2 已兼容的 7 处 `ON CONFLICT`

`history_store.py`×2、`memory_dream.py`×2、`memory_store.py`、
`turn_marker.py`、`acp/store.py` —— **不用改**。

## 5. 最大的改动面：126 处 connect + 58 处 PRAGMA

### 5.1 connect 调用分布

| 文件 | connect 次数 |
| --- | --- |
| `db.py` | 34 |
| `team_store.py` | 28 |
| `a2a/store.py` | 21 |
| `subagent/store.py` | 14 |
| `memory_dream.py` | 9 |
| `history_store.py` | 6 |
| `turn_marker.py` | 5 |
| `acp/store.py` / `memory_store.py` | 各 4 |
| `routers/team.py` | 1 |
| **合计** | **126** |

### 5.2 为什么必须改成连接池（实测数据）

```
SQLite  打开+查询+关闭: 0.175 ms
PG      打开+查询+关闭: 35.8 ms      ← 205 倍
```

如果直接替换驱动而保留「每次 connect」，**每次数据库操作多 ~35ms**。
按一个对话轮次 10 次数据库操作算，就是 **350ms 的纯开销**。

用连接池后：
```
SQLite         : 0.097 ms/query
PG（池复用）   : 1.534 ms/query     ← 约 16x，但是可接受的常数
```

这个差距**不是网络**：容器内 `psql` 同一条 `select count(*)` 只花
**0.3~1.0 ms**（`\timing on` 实测三次：0.968 / 0.336 / 0.477 ms）。
也就是说 35 倍的连接开销全在「建 TCP + 认证握手」上，用池就能消掉。

### 5.3 PRAGMA 的 58 处

主要用于：表结构查询、journal_mode、foreign_keys、busy_timeout 等。
PG 全都没有对应语法，需要按用途分类替换：

| 用途 | PG 对应 |
| --- | --- |
| `PRAGMA table_info(x)` | `information_schema.columns` |
| `PRAGMA journal_mode=WAL` | 不需要（PG 自带 MVCC） |
| `PRAGMA foreign_keys=ON` | 默认开启 |
| `PRAGMA busy_timeout` | 用连接池 + 语句超时替代 |

## 6. 性能：要注意什么

### 6.1 单查询变慢是正常的

| 指标 | SQLite | PG（池） | 比值 |
| --- | --- | --- | --- |
| 单查询 50 行 | 0.097 ms | 1.534 ms | 约 16x |
| count(*) | 2.10 ms | 4.84 ms | 2.3x |
| 连接成本（无池） | 0.175 ms | 35.8 ms | 205x |

**这 35ms 全是建连握手，不是查询慢**：容器内 `psql` 同一条查询 0.3~1.0 ms。
所以「用连接池」不是优化项，是**能否上线的前提**。

**这个延迟有一部分是 Windows + Docker 端口映射的固有开销**（实测容器内
`psql` 查同一条 `select count(*)` 只用 0.3~1.0 ms，说明 **查询本身不慢**；
慢的是从 Windows 进程建立 TCP 连接 + PG 认证握手这一步）。
用连接池把这一步摊掉之后，1.5 ms/query 是新的基线。

### 6.2 但并发能力是 SQLite 没有的

```
PG 连接池：10 并发 × 20 查询 = 198 ms（约 1011 qps）
```

**SQLite 的写操作是全局串行的**（单写者锁）。多进程部署时：
- 两个进程同时写 → 一个必然 `database is locked`
- 这不是调参数能解决的，是 SQLite 的架构限制

这才是必须迁移的根本原因。

## 8. 迁移路线建议（分三步，每步可独立验证）

### 第 1 步：抽象数据访问层（不改数据库）

这是最关键的准备工作，也是唯一的大工程：

- 把所有 `aiosqlite.connect` 收拢到一个 `Database` 抽象
- 引入**连接池**（PG 必需，SQLite 可空实现）
- 把 `PRAGMA` 按用途替换成标准 SQL（`information_schema`）
- 4 处 `INSERT OR REPLACE/IGNORE` 改成 `ON CONFLICT`

**这一步完成后，SQLite 仍然是生产库，但代码已经与数据库解耦。**

验证方式：**全部测试在 SQLite 上继续绿**。1215 条现有测试就是回归网。

### 第 2 步：加 PG 实现，双跑验证

- 实现 `PostgresDatabase`（asyncpg + 连接池）
- 用环境变量切换（`HLZ_DB_URL`）
- 同一套测试在 PG 上跑一遍

验证方式：**同一批测试在 PG 上也要绿**。这一步能抓出所有 SQL 方言问题。

### 第 3 步：数据迁移 + 切换

- 一次性迁移脚本（21k 行，秒级）
- 迁移后 `setval()` 修正序列
- 切换开关 + 回滚方案（保留 SQLite 文件）

## 9. 风险与注意

| 风险 | 应对 |
| --- | --- |
| 126 处 connect 漏改 | 用静态守卫测试（AST 扫描）禁止裸 connect |
| 自增序列没对齐 | 迁移脚本末尾 `setval`，并写测试验证新插入不撞 |
| `PRAGMA` 遗漏 | 按用途建对照表，逐条替换 |
| 时区问题 | 现有时间戳是 INTEGER 毫秒，不受影响（不引入 TIMESTAMP 类型） |
| 事务隔离差异 | SQLite 默认串行化，PG 默认 read committed。需要检查跨表一致性逻辑 |
| 性能回退感知 | 用连接池；把「单查询 1ms」当成新基线，别拿 SQLite 的 0.1ms 比 |

## 10. 一句话

**数据和 schema 不是问题（21k 行、3 种类型、6/6 实测通过）；
问题是 126 处 connect 和 58 处 PRAGMA 的改造，以及必须先做的那层数据访问抽象。**

# 本地 MCP 被系统代理拦成 502（2026-11-19 真机排查）

> 起因：hx 用户报告 exa 的 3 个工具全部失败，`code_run` 里 DNS 解析不了，
> 用户推断「MCP 与沙箱共用同一个网络出口，一断全断」。
> 这个推断**不成立** —— 查源码 + 实测后查出两个独立的真 bug。

---

## 0. 结论速览

| 说法 | 是否成立 | 实际 |
| --- | --- | --- |
| MCP 走沙箱 | ❌ **不成立** | MCP 在**后端主进程**里连，与容器完全无关 |
| 沙箱没网络 | ✅ 成立，但**是设计** | `network_mode="none"`，故意的隔离 |
| MCP 与沙箱共用出口 | ❌ 不成立 | 两条完全独立的链路 |
| `Client is not connected` 是网络错 | ❌ 不成立 | fastmcp 的**本地会话状态**错 |
| sqlbot / falcomm 的 `502` 是服务挂了 | ❌ 不成立 | **系统代理假象**（服务确实也没起） |

查出并修掉两个真 bug：

| # | Bug | 影响 |
| --- | --- | --- |
| 1 | `Client is not connected` 不在重连白名单 | 连接失败过的 MCP server **永久不可用**，重试也没用 |
| 2 | 本地 MCP 请求被系统代理拦 | 「服务没起」被伪装成「服务返回 502」，误导排查方向 |

## 1. MCP 不走沙箱（源码证据）

### 1.1 分流表

`app/sandbox/policy.py:19`：

```python
SANDBOXED_TOOLS = frozenset({"code_run", "file_write", "file_patch"})
```

只有这三个走容器。MCP 工具**不在里面**，所以 `should_use_sandbox()` 恒返回
`False`。

### 1.2 MCP 在哪连

`app/agent.py:208/230/240`：

```python
ts = MCPToolset(target, user_id=user_id, server_name=name)
```

`MCPToolset` 是 FastAPI 进程内的对象，底层 `fastmcp.Client` 用 httpx 直接建连。
**与 Docker 完全无关。**

### 1.3 沙箱确实没网络（但这是故意的）

`app/sandbox/runtime.py:124`：

```python
network_mode="none",
```

实测（真起容器）：

```
docker run --rm --network none hlz-sandbox:2026-11-18 python -c "..."
DNS FAIL: gaierror: [Errno -3] Temporary failure in name resolution
HTTPS FAIL: URLError: <urlopen error [Errno -3] ...>
```

用户看到的 `code_run` DNS 失败就是这个 —— **沙箱的**，不是 MCP 的。

## 2. Bug 1：`Client is not connected` 不触发重连

### 2.1 症状

hx 用户的 exa 三个工具全报：

```
RuntimeError: Client is not connected.
Use the 'async with client:' context manager first.
```

重试 3 次都一样（用户原话「同样报错，非偶发」）。

### 2.2 根因

这条错误**不在** `_SESSION_DEAD_MARKERS` 里：

```python
_SESSION_DEAD_MARKERS = (
    "session terminated", "connection closed", "connection reset",
    "server disconnected", "clientconnectorerror", "connecterror",
    "all connection attempts failed", "broken pipe", "transport closed",
    "stream closed", "no active session",
)
# 没有 "client is not connected"
```

于是 `_looks_session_dead()` 返回 `False` → `_invoke` 跳过 `reconnect()` →
直接走 `_format_call_error`（还会对模型说「请严格按工具参数定义调用」，
**完全误导**，模型会反复改参数而永远调不通）。

实测：

```
Client is not connected -> 判定会话已断？ False     ← 不重连
Session terminated      -> True
All connection attempts failed -> True
```

### 2.3 为什么后果比「会话断了」更严重

`Client is not connected` 意味着这个 Client 对象**从没成功 `__aenter__` 过**。
它不会随时间自愈 —— 整个进程生命周期内该 server 都不可用，日志里也没有任何
重连尝试。用户只能重启后端。

### 2.4 修法

加进白名单：

```python
"client is not connected",
"not connected",
```

恢复手段与「会话断了」完全相同（重建 client），所以归到同一类。

## 3. Bug 2：本地 MCP 被系统代理拦成 502

### 3.1 症状

hx 的 `sqlbotmcp`（`http://127.0.0.1:8765/mcp`）与 `falcomm`
（`http://127.0.0.1:8889/client/mcp`）都报：

```
HTTPStatusError: Server error '502 Bad Gateway'
```

看起来像「MCP 服务返回了 502」，会让人去查服务日志 —— **方向完全错了**。

### 3.2 根因

本机 Windows 系统代理开着：

```
reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings"
  ProxyEnable   0x1
  ProxyServer   127.0.0.1:7897
```

httpx 默认 `trust_env=True`，**把 127.0.0.1 的请求也送进代理**。
代理连不上那个本地端口，就返回 502。

实测对照（对同一个**不存在**的端口 9999）：

| 配置 | 结果 |
| --- | --- |
| 走代理（默认） | `502 Bad Gateway` ← **假象** |
| `trust_env=False` | `ConnectError: [WinError 10061] 目标计算机积极拒绝` ← 真相 |

### 3.3 修法

本地地址（`127.0.0.0/8` / `localhost` / `::1`）的连接**显式绕过代理**，
外网地址保持默认（需要代理才能访问外网的环境不受影响）。

fastmcp 的 transport 没有直接暴露 `trust_env`，只能通过
`httpx_client_factory` 定制：

```python
def _httpx_factory_for(url: str):
    if not _is_local_url(url):
        return None                      # 外网：用 fastmcp 默认
    def _factory(*args, **kwargs):
        merged = {**kwargs, "trust_env": False}
        merged.setdefault("follow_redirects", True)      # MCP 依赖
        merged.setdefault("timeout", httpx.Timeout(30.0))  # httpx 默认 5s 太短
        return httpx.AsyncClient(*args, **merged)
    return _factory
```

> ⚠️ 不能用 `mcp.shared._httpx_utils.create_mcp_http_client` —— 它只接受
> `headers / timeout / auth`，传 `trust_env` 会
> `TypeError: got an unexpected keyword argument 'trust_env'`（实测）。
> 所以自己造 `AsyncClient`，并把 MCP 依赖的两个默认值照抄过来。

**只判 loopback，不判私有网段**：`192.168.x` / `10.x` 可能是局域网里
真正需要经代理访问的服务，误判会让它们断掉。

## 6. 给运维的排查清单

MCP 报错时按这个顺序查，别急着怀疑网络：

| 错误信息 | 真实含义 | 下一步 |
| --- | --- | --- |
| `Client is not connected` | 这个 server 从没连上过（**已修**：现在会自动重连一次） | 看 `ts.error` 里的原始连接错误 |
| `502 Bad Gateway` 且 URL 是 `127.0.0.1` | **系统代理假象**（**已修**） | 修后应变成 `All connection attempts failed` |
| `All connection attempts failed` | 服务真的没起 / 端口不对 | `netstat` 看端口；`curl` 直连 |
| `ClientConnectorError` | 同上 | 同上 |
| `Session terminated` | 会话断了（服务重启 / 空闲超时） | 已有自动重连；仍失败看服务端日志 |
| `MCP error -32602: Input validation error` | **模型参数给错了**，不是连接问题 | 看提示里的可用参数 |

**最重要的一条**：`502` 且指向 `127.0.0.1` 时，先怀疑代理，别怀疑服务。

## 9. 同一主题的另一半：容器内 `127.0.0.1` 连不到宿主机（2026-11-19 补充）

> 多实例部署后，`sqlbotmcp` / `falcomm` 在设置页显示
> `RuntimeError: Client failed to connect: All connection attempts failed`。
> 上面 §1–§8 修的是「**代理**把本地请求拦成 502」；这一节是「**容器网络**让
> `127.0.0.1` 指向了错误的机器」。两者都表现为「连不上」，但根因完全不同，
> 排查方向也不一样 —— 所以放在一起对照。

### 9.1 根因

| 运行方式 | `127.0.0.1` 指的是谁 | 结果 |
| --- | --- | --- |
| 后端直接跑在宿主机 | 宿主机自己 | ✅ 能连到同机的 MCP 服务 |
| 后端跑在容器里 | **容器自己** | ❌ 容器里没有那个服务，`Connection refused` |

`docker inspect` 确认容器内 `127.0.0.1:8765` 无监听；而宿主机
（`netstat -ano`）上 `127.0.0.1:8765`（PID 40456）、`127.0.0.1:8889`（PID 48080）
都在正常 LISTENING。服务本身没问题，**是地址写法在容器里不成立**。

### 9.2 容器内实测：哪些地址能通

```
$ docker exec hlzscale-app-1 python -c "socket.create_connection(...)"
  FAIL  127.0.0.1:8765                 容器自身 loopback
  OK    host.docker.internal:8765      docker 内置主机名      ← 用这个
  FAIL  172.17.0.1:8765                docker0 网关
  OK    192.168.65.254:8765            Docker Desktop 主机
```

`host.docker.internal` 是 Docker Desktop 提供的固定主机名，跨平台最稳。

### 9.3 修复：改配置，不动代码

```sql
UPDATE user_mcp_servers
   SET url = replace(url, '127.0.0.1', 'host.docker.internal')
 WHERE user_id = '<目标用户>' AND url LIKE 'http://127.0.0.1:%';
```

> ⚠️ **直接改库不会触发缓存失效**。正常走 `PUT /api/me/mcp-servers` 会自动调
> `hub.invalidate_cluster()`；直接 SQL 改必须**重启实例**（或调一次 API）才生效，
> 否则进程里还握着旧 URL 的 toolset。

### 9.4 验证（不只看端口，走完整 MCP 协议）

只测 HTTP 状态码不够 —— `406` / `401` 只证明端口活着，不证明 MCP 握手成功。
用项目的 `MCPToolset` 走完整连接 + 列工具：

| server | 容器内结果 |
| --- | --- |
| `sqlbotmcp` (`:8765/mcp`) | ✅ 12 个工具 |
| `falcomm` (`:8889/client/mcp`) | ✅ 23 个工具（**必须带** `Authorization: Bearer ...`，否则 401） |

设置页 `/api/me/mcp-effective` 复查：4 个 server 全部 `ok: true`，
工具总数从 18 → **53**。

端到端真调一次 `health`：`is_error=False`，返回了真实 sqlite 表结构，`done: complete`。

### 9.5 为什么没改成「代码自动映射」

考虑过在 `mcp_client` 里检测容器环境、把 loopback 自动改写成
`host.docker.internal`。**没有采用**，理由是：

- 用户照常填 `127.0.0.1`，在宿主机和容器里都能跑 —— 听起来更好，但这是**隐式行为**：
  出问题时要在「配置看起来对的」和「代码偷偷改了地址」之间多查一层；
- 「本机直跑」和「容器化」是两种明确的部署形态，地址本来就该不同，
  显式写清楚比自动猜更好排查。

所以选择改配置。**代价要记住**：以后如果后端改回直接在宿主机跑，
这两个 URL 要改回 `127.0.0.1`（或宿主机也能解析 `host.docker.internal`）。

### 9.6 还有一个坑没动：测试账号里的 loopback 配置

全库共 **28 条** loopback 配置，绝大多数是测试账号
（`mcp3_*` / `mcpui_*` / `mcpchk_*` 等），其中还有**故意配死的端口**
（`127.0.0.1:9`、`127.0.0.1:8799`）用于测「连接失败」路径。
本次**只改了实际使用的账号**，没动这些测试数据 —— 批量替换会把那些
负向测试用例一起改坏。

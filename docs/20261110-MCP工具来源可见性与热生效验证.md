# MCP 工具来源可见性与热生效验证

> 日期：2026-11-10　状态：已完成　分支：当前工作区

## 1. 问题

hx（`u_c56b8337dd09`）在会话里声称「没有 sqlbot 工具」，但同一条回复里它**实际调用了**
`health` / `dimensions`（都属于 sqlbot mcp），且 `metric_search` 可用。

根因不是 MCP 接入失败，而是**工具来源信息在装配时丢失**：

- `mcp_client.MCPToolset._wrap()` 只把 MCP 工具的 `name` / `description` / `inputSchema`
  包成 `Tool`，不记录来自哪个 server；
- 多个 server 的工具被拍平进同一个 `ToolRegistry`，工具名没有命名空间；
- 模型只能按名字猜归属。`exa` 恰好因工具名带 `_exa` 后缀被认出，sqlbot 的
  `metric_*` / `health` / `dimensions` 则完全无标识。

附带发现两个放大该问题的缺陷：

1. 连接失败被**静默丢弃**（`build_user_toolset` 里 `continue`），模型只看到「工具列表里没有」，
   就编造「本来就没有这个 MCP」；
2. `/api/me/mcp-effective` 用 `model_id=""` 取 runtime，而对话轮次用会话的 `model_id`，
   两者是**不同缓存实例**，各自独立连一遍 MCP —— 设置页显示「已连接」，对话里却是 `TimeoutError`。

## 2. 改动

### 2.1 工具来源可见（`backend/app/tools.py`、`backend/app/mcp_client.py`）

- `Tool` 新增 `source: str = ""` 字段与 `describe_for_model()`；
  来源以 `[MCP: <server>]` 前缀写进 **description**，工具名不变（工具名是 SSE / 前端 / 历史契约）。
- `MCPToolset` 新增 `server_name` 参数、`server_name` / `manifest` 属性、`status()`；
  `merge()` 保留各子 toolset 的来源。

### 2.2 失败可见 + 权威清单（`backend/app/agent.py`）

- `build_user_toolset()` 记录每个已配置 server 的连接结果到 `manifest`
  （`name` / `ok` / `tool_count` / `error` / `tools`），失败不再静默消失。
- 新增 `format_mcp_manifest()`，把清单写进 system prompt 的
  `## MCP servers connected this turn (authoritative)` 一节，明确告知模型：
  清单里有的 server 就是已连接；工具缺失只可能是该 server 本轮连接失败；
  不要用 `code_run` 手搓协议，也不要把旧脚本注释当当前事实。
- `UserRuntime.build()` 改为**先建 toolset、再建 model**，以便清单进入提示词。

### 2.3 状态一致性（`backend/app/routers/me.py`）

- `/api/me/mcp-effective` 改用该用户最近会话的 `model_id` 取 runtime，与对话轮次共用同一实例；
  响应新增 `servers` 字段（各 server 的连接状态）。

### 2.4 前端（`SettingsModal.tsx`、`api.ts`、`types.ts`、`index.css`）

- 设置页每个 MCP server 下显示「已连接 · N 个工具」或「连接失败 · 原因」。

### 3.3 已知限制

- exa（`https://mcp.exa.ai/mcp`）是公网免费服务，连接不稳定，实测多次 `TimeoutError`。
  这属于上游可用性问题，非平台缺陷；现在会明确显示为「连接失败 + 原因」，而不是假装没有。
- `/mcp-effective` 取「最近会话」的 `model_id` 作为缓存键。同一用户若在不同会话使用不同模型，
  设置页反映的是最近会话所用的那一份 runtime；MCP 工具本身与模型无关，
  差异仅限各实例独立连接导致的瞬时状态。

## 5. 补强：用户可见的 MCP 连接状态（2026-11-10 追加）

### 5.1 问题

第一版只在「设置 → 我的 MCP」的 server 卡片里显示状态，实际使用中不够：

1. **入口太深**：用户不进设置就完全不知道 MCP 断没断；
2. **runtime 无 TTL**：`RuntimeHub._runtimes` 按 `(user, model)` 永久缓存，只有
   `invalidate`（配置增删改）才会重建。MCP 中途断开后，界面会一直显示「已连接」，
   用户永远看不到真实状态；
3. 没有手动重测入口。

### 5.2 改动

- **后端** `POST /api/me/mcp-servers/probe`：绕开 runtime 缓存，现场调用
  `build_user_toolset()` 真实重连全部已启用 server，返回实时 manifest。
- **侧栏常驻状态条**（`Sidebar.tsx`）：身份区上方一条可点击的 `MCP 正常 · N 工具` /
  `N 个 MCP 断开`，红/绿圆点区分；点击直接打开设置。数据来自 `/mcp-effective`，
  与对话轮次共用同一份 runtime。
- **设置页汇总条**（`SettingsModal.tsx`）：
  - `全部 N 个 server 已连接` / `M/N 个 server 已连接`，带红绿状态点；
  - 失败时逐条列出 `server（失败原因）`；
  - 「重新检测连接」按钮，调用 probe 接口获取实时结果。

## 6. 软 TTL：状态自动刷新（2026-11-10 追加）

### 6.1 为什么是软 TTL 而不是定时重建

runtime 重建要 `close()` 旧 toolset 与 LLM client，然后重连**全部** MCP server
（三个 server 实测约 11 秒）。如果按固定间隔无条件重建，纯属浪费，还可能打断
正在执行的轮次。所以约束是三条：

1. TTL 内直接返回缓存状态，不探测；
2. TTL 过期后探测一次，**状态没变就不重建**，只续期；
3. 用户有任何会话正在生成时，一律不重建（否则那一轮的 toolset 会被关掉）。

### 6.2 实现

- `runtime._MCP_STATUS_TTL_S`：默认 60 秒，可用环境变量 `MCP_STATUS_TTL_S` 覆盖。
- `_same_manifest()`：按 `(name, ok, tool_count)` 排序比较，忽略顺序与错误文案差异。
- `RuntimeHub._built_at`：记录每份 runtime 的建立时间；`invalidate*` 时一并清理。
- `RuntimeHub.refresh_mcp_status(user_id, model_id, force=False)`：
  判 TTL → 判活跃 → 探测 → 比较 → 必要时 `invalidate` + 重建。
- `agent.probe_mcp_status()`：现场建 toolset、取 manifest、立刻关闭，不留常驻连接；
  「重新检测」按钮与 TTL 刷新共用。
- `runtime.has_active_generation_for_user()`：按 owner 隔离的活跃判定。
- `GET /api/me/mcp-effective` 现在先走 `refresh_mcp_status()`。

### 6.3 验证（真实后端 + hx / 湛卢 / sqlbot+exa+tavily）

| 观测 | 结果 |
| --- | --- |
| 连续两次读状态（TTL 内） | 0.02s / 0.03s，直接命中缓存 |
| 超过 60s 后读状态 | 11.30s，真实重连探测；状态未变 → 不重建 |
| 绕过 `invalidate` 直接把 tavily 指向不可达端口，再等过 TTL | 状态变为 `tavily: False`，工具数 27 → 20，**自动重建** |
| 恢复 URL 后 `probe` | 三个 server 全部 `ok=True`，共 19 工具 |

`backend/tests/test_mcp_status_ttl.py`（10 项）：manifest 比较（顺序/错误文案/数量）、
TTL 内不探测、过期后未变不重建、过期后变化则重建、活跃轮次跳过、

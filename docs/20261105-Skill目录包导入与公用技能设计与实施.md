# Skill 目录包导入 + 公用技能层 —— 设计与实施

> 日期：2026-11-05 · 状态：已实施
> 关联：`docs/20261105-Skill与基础工具设计与实施.md`（P1 基础版，仅单文件 SKILL.md）
> 本文解决的问题：**真实 Skill 往往是一个目录**（脚本 / 参考资料 / 模板），单文件编辑器装不下；且需要一层「所有人可用」的公用技能。

## 1. 背景与问题

P1 的 Skill 只有一个 `SKILL.md` 文本，前端只能编辑正文。但 Codex / Claude Code / Aivory 生态里的
Skill 普遍是**目录**：

```
skill-creator/
├── SKILL.md              # 指令正文（frontmatter + body）
├── scripts/init_skill.py # 可执行脚本
├── references/*.md       # 参考资料
├── agents/openai.yaml    # 元数据
└── assets/*.png
```

这类技能靠 `SKILL.md` 里写 `${SKILL_DIR}/scripts/xxx.py` 让模型去读/执行附属文件。
本项目 `skill_store.load_skill_content()` **早已支持**把 `${SKILL_DIR}` 替换成技能目录的绝对路径，
`file_read` 的安全读根也把技能目录算作可读范围 —— 缺的只是：

1. 没有**导入目录**的入口（前端只能贴正文）。
2. 没有**公用层**：`skills_builtin` 属于仓库内置，用户无法贡献；缺一层「大家都能用、但不可随意改」的公共目录。

## 2. Aivory 的做法（对齐参考）

| 层 | 表 / 位置 | 是否支持附属文件 |
|---|---|---|
| 管理员公共技能 | `skills` 表：`instructions` + `assets`(JSON: filename/storage_path/mime/size) | 支持，`use_skill` 时把 assets 落到沙箱 `/workspace/skills/<name>/` |
| 用户私有技能 | `user_skills` 表：**仅 instructions** | 不支持，代码注释明确 "no assets, storage paths, or sandbox staging surface" |

结论：Aivory 把「带文件的复杂技能」放在**公共层**，用户侧只给纯文本。
本项目采纳同样的分层，但用**文件系统 + zip 导入**实现（无 DB、无沙箱存储，改动面更小）。

## 3. 本项目的三层模型（实施后）

| 层 | 根目录 | 来源 | 可写 |
|---|---|---|---|
| 内置 builtin | `backend/skills_builtin/` | 随仓库发布 | 否 |
| **公用 shared（新增）** | `backend/skills_shared/` | 运维/管理员 zip 导入；也可直接放仓库 | 否（API 只读） |
| 私有 user | `backend/data/skills/<user_id>/` | 用户自助上传 / 编辑 | 是 |

**同名优先级（后者覆盖前者）**：`builtin` → `shared` → `user`。
用户在 UI 里「以同名新增」即可覆盖公用技能，而不用改动公共目录。

## 4. 目录包导入设计

### 4.1 支持的 zip 结构

```
# A. 单个技能，SKILL.md 在根
SKILL.md
scripts/...

# B. 多个技能，各自一级子目录（推荐）
alpha/SKILL.md
alpha/refs/...
beta/SKILL.md
beta/scripts/...

# C. 多包一层（git archive 常见）
repo-main/alpha/SKILL.md   ← 自动向下找两级
```

`_locate_skill_dirs()` 按 A → B → C 逐级尝试；找不到任何 `SKILL.md` 直接报错。

### 4.2 安全约束（重点）

zip 上传是**不可信输入**，`_safe_extract_zip()` 逐条校验：

| 攻击 | 防护 |
|---|---|
| 路径穿越 `../../etc/passwd` | 拒绝含 `..` 段、绝对路径 |
| 符号链接逃逸 | `external_attr` 高 16 位判定 `0o120000` 直接拒绝 |
| zip 炸弹 | 压缩包 <=20MB；解压总量 <=60MB；文件数 <=500 |
| 同名覆盖 | 默认**报错**，需显式 `overwrite=true` 才替换 |
| 非法技能名 | `validate_skill_name()`：只允许 `[a-z0-9._-]`，拒绝分隔符 |

**额外处理**：Codex 技能的 frontmatter 常写中文 `name: 技术报告撰写`，但技能目录名是 slug。
`validate_skill_name` 只接受 ASCII slug，导致「能列出、加载不了」。
`_normalize_skill_frontmatter()` 在**复制落地之后**把 frontmatter 的 `name:` 改写为目录 slug，
其余字段原样保留。

### 4.3 未包装目录的命名

若 zip 根目录本身就是技能（结构 A），用**上传文件名**推导 slug：
`技术报告.zip` → `_upload_default_name()` → 非 ASCII 折叠为 `-` → 回退 `skill`。
调用方也可显式传 `default_name`（本机批量导入脚本就是这么做的）。

## 8. 风险与未决项

1. ~~公用技能导入后不逐用户失效缓存~~ —— **已修复**（2026-11-05）。
   原因：`UserRuntime.build()` 会把 L1 技能索引**烤进 system prompt**，而 `RuntimeHub` 按
   `(user_id, model_id)` 缓存整个 UserRuntime，命中即复用、不会重读技能目录。
   注意缓存 key **与 session 无关**，所以「开新会话」也不会重建 —— 只有 `invalidate`、重启或 key 淘汰才行。
   修复：新增 `RuntimeHub.invalidate_all()`，`POST /api/skills/shared/import` 成功后清空**所有**用户的
   Runtime，响应里返回 `runtimes_invalidated` 数字。已用真实服务验证：导入后返回 `runtimes_invalidated: 2`，
   公用列表立即出现新技能。
2. **zip 里未做扩展名白名单**：当前只做体积 / 路径校验。若担心可执行文件，可在
   `_safe_extract_zip` 增加扩展名白名单（Aivory 的做法：20MB + 扩展名 allowlist）。
3. **`code_run` 执行技能脚本时 cwd 是用户 workspace**：脚本读 `${SKILL_DIR}` 绝对路径没问题，
   但脚本内部若用相对路径写文件会落到用户 workspace —— 预期行为，不额外处理。
4. **无删除公用技能的 API**：公用层视为「随仓库 / 运维管理」，删改走文件系统或重新导入覆盖。

## 9. 用户侧操作方式

1. 把技能目录打成 zip（保留目录结构，`SKILL.md` 在根或一级子目录）。
2. 设置 → 我的 Skills → 勾选「覆盖同名」（可选）→ 选择 zip 导入。
3. 列表出现该技能，标签显示「我的 / N 个文件」。
4. 同名时会覆盖公用技能，且可编辑 / 删除。

## 10. 缓存失效机制（补充说明）

「失效」指**进程内 Runtime 缓存失效**，不是技能文件损坏。

```
UserRuntime.build(user_id)
  └── build_skill_prompt(user_id)   # 读技能目录 -> L1 索引文本
  └── system_prompt = SYSTEM_PROMPT + skill_block   # 之后固定不变
  └── AgentLoop(..., system_prompt)                 # 长期复用

RuntimeHub._runtimes[(user_id, model_id)] = UserRuntime   # 命中即返回，不重建
```

| 变更 | 需要的失效范围 | 现有实现 |
|---|---|---|
| 用户改模型 / MCP / 私有技能 | 该用户 | `hub.invalidate(user_id)` |
| **导入公用技能** | **所有用户** | `hub.invalidate_all()` |
| 进程重启 | 天然清空 | — |

补充：`load_skill` 工具本身是**实时读磁盘**的，所以只要模型知道技能名就能加载；
缓存只影响「模型在 system prompt 里看不看得见这个技能的索引」。

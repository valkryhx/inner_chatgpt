## 0. 一句话

现在**关掉或刷新页面会杀死正在跑的生成**，因为生成的生命周期直接绑在 HTTP 请求上。
本步把生成从请求上摘下来，并让刷新后能接着看。

---

## 1. 实测：这不是「看不见」，是「把活掐死」

### 1.1 四版探针，前两版都不可用

**第一版（`work/_probe_disconnect.py`）有歧义。** 它让模型在 `code_run` 里分 6 次睡 36 秒，
25 秒内没有正文产出，所以「content 长度不增长」既可能是「生成停了」也可能是
「还没开始写」。它报的「被租约拦住=True」也是坏的判据：那是拿响应文本里有没有
`generation` 这个词猜的，而正常回复里也可能出现该词。后来用状态码复测，
断开后立刻重发是 **HTTP 200**，租约根本没拦。

**第二版（`_probe_disconnect2.py` 首跑）也有歧义。** 它把所有 `data:` 行的长度
累加当正文，但事件序列里混着 `team_event`，所谓「收到 287 字符」里没有一个是正文。

**第三版**只统计 `text_delta` 且等累计 ≥200 字才断开，得到决定性证据：

```text
请求：写一篇 6000 字长文（分 20 小节）
收到 200 字正文 → 断开 SSE
断开时：status=streaming  len=51
+2.0s ：status=stopped    len=73        ← 停在这里，此后 33 秒无增长
末尾：'…「这段逻辑该做成状态机还是走事件总线」几乎每次'
```

**正文 73 字、句子写在一半。** 6000 字的请求 vs 73 字的产出，不是「提前结束」。

### 1.2 机制

`chat.py:943` 返回 `StreamingResponse`。Starlette 的 `StreamingResponse` 把
`stream_response` 和 `listen_for_disconnect` 放在同一个 anyio task group 里，
收到 `http.disconnect` 就取消整个组。于是 `_event_stream` 这个**生成器本身**
被取消，它的 `finally`（`chat.py:805+`）把消息收敛成 `stopped`。

**所以「进度丢」和「生成被杀」是同一处**：生成器就是生成。这也是为什么它不能
靠「加个事件日志回放」解决——得先把生成从请求上摘下来。

### 1.3 当前事实清单

| 问题 | 实测 |
|---|---|
| 断开后生成继续多久 | 约 **2s**（服务端断开检测延迟），随后终止 |
| 已产出内容 | 保留，但截断在断开那一刻 |
| 被掐断消息的状态 | `stopped`，与「用户主动停止」在库里完全一致 |
| 断开后能否立刻重发 | 能，HTTP 200 |
| 刷新后能否续看 | 不能：前端无任何 reconnect 逻辑 |
| SSE 是否发 `id:` | **发**（`sse.py:21`） |
| 前端是否解析 `id:` | **不解析**：`api.ts:383` 的 `parseFrame` 只看 `event:` 和 `data:` |
| SSE 是否有心跳 | 无 |

## 2. 与 LibreChat / Aivory 的对照：收敛什么、不收敛什么

### 2.1 必然收敛的部分（不是抄，是问题决定的）

要满足「断线不影响生成 + 刷新能接着看」，任何实现都必须有：

1. **生成不挂在请求上**；
2. **事件可重放**。

两家独立走到同一个骨架，是它能成立的旁证，不是要照抄的理由。

### 2.2 存储：按部署选，不按流行选

| | 生成载体 | 事件存储 |
|---|---|---|
| LibreChat | 进程内 job map（`maxJobs=1000`） | 进程内，`ttlAfterComplete` |
| Aivory | 独立 job | Redis Stream，2h TTL |
| Hlaudz（本文） | `asyncio.create_task` 的 turn job | **进程内环形缓冲 + `messages.blocks` 兜底** |

Aivory 需要 Redis Stream，是因为它的 Stream 要跨网关实例共享。本节 §4.4 会说明
我们的方案在多实例下退化成什么样，以及为什么仍不需要 Redis。

### 2.3 必须一起带过来的：上界与回收

两家都给保留态设了上界：LibreChat `maxJobs=1000` + `evictOldest()` + 60s `cleanup()`，
Aivory 每用户 16 条 SSE 连接 + evict-oldest + 2h TTL。

**这不是性能优化，是必需项。** 而本项目正好有一个反面现状：`RuntimeHub` 实测
200 用户 → 202 条目，**没有上限、没有淘汰、没有空闲超时**。在一个已知缺陷旁边
再种一个同类缺陷是不可接受的，所以本文的缓冲从第一天就带上界（§4.5）。

### 2.4 刻意不收敛的：把日志当真相来源

Aivory 的 Redis Stream 是对客户端的真相来源，所以要存 2 小时。

我们不一样：`messages.blocks` 已经每 **250ms** 增量持久化（`chat.py:562` 的节流），
**已完成轮次的真相在数据库里**。所以缓冲只需要覆盖「还在 streaming」这一个窗口，
天然有界、天然短、天然可删。

## 3. 关键取舍：不要落一张事件日志表

我最初的想法是「事件日志存 SQLite」。核对写入粒度后这个想法被否掉了。

### 3.1 写入放大

`text_delta` 是 **token 级**事件。一次 6000 字的回答约产生数千条 delta。逐条写
SQLite 意味着单轮几千次 `INSERT`，而 `blocks` 目前是 250ms 一次全量快照（一轮
几十次）。这是两个数量级的差距，而且换来的是**没有任何额外保证**——因为下一节。

### 3.2 真相只有一份：`blocks`

`blocks` 已按事件真实顺序累积（`chat.py:539` 注释），覆盖：

| 进 `blocks` | 类型 |
|---|---|
| ✅ | `text` / `reasoning` / `tool` / `chart` / `subagent` / `injected_message` |
| ❌ | `team_event` / `llm_retry` / `team_wait` / `healed` / `message_start` / `done` / `error` |

不在 `blocks` 里的两类：

- **`team_event`**：失真有别的来源——TeamPanel 刷新时本来就走 REST 恢复，
  不需要从 SSE 重放；
- **`llm_retry` / `team_wait` / `healed`**：瞬态提示，重放没有意义（「3 秒前重试过
  一次」现在再显示一遍是噪音）。

### 3.3 于是方案变成

> **续看 = 拿 `blocks` 快照对齐到某个 seq，再从该 seq 之后接上实时事件。**

缓冲只是「把快照之后到此刻之间的增量补上」的一小段，不是一份完整日志。这个
构造有个很好的性质：**缓冲溢出时降级为「整份快照重发」，永远正确，不会输出错误
状态**——因为 `blocks` 是权威且单调的。

## 4. 设计

### 4.1 总体：turn job 与 SSE 订阅解耦

```text
POST /messages
   ├─ 抢 generation 租约（team_store，走 DB，不变）
   ├─ 建 turn job（asyncio.create_task，detached）
   │     └─ 跑 run_agent_stream → 每个事件：写 blocks（250ms 节流）+ 进环形缓冲
   └─ 返回 StreamingResponse = 「订阅者」

GET /stream?after=<seq>（新增）
   └─ 订阅者：对齐快照 → 补缓冲增量 → 续跑实时事件
```

**已有范式可以直接对齐**：A2A 就是这么做的（`a2a/service.py:273` 的
`_spawn` → `asyncio.create_task`，任务独立于 RPC 请求）。chat 路径缺这一层，
不是没有先例可循。`_spawn_background`（`chat.py:176`）也是同类的取消安全写法。

**关键约束（自查发现，见 §8.0 ①）**：A2A 直接调用 `chat._event_stream`
（`a2a/service.py:193`）。所以解耦**不能**动 `_event_stream` 的签名或产出语义，
必须包在 `guarded_stream`（`chat.py:923`，只有一个调用方）外层：

```text
guarded_stream()                                  # StreamingResponse 的 body = 订阅者
   └─ job = create_task(_run_turn_job(...))       # job 跑真正的生成
        └─ async for chunk in _event_stream(...)  # 原样不动，A2A 仍可直接用
```

改动要点：

- `register_generation`（`runtime.py:394`）现在捕获 `asyncio.current_task()`，
  那是**请求任务**；要改成在 **job 任务内部**调用，否则 `/stop` 取消的还是请求
  （`cancel_generation` 读的正是 `_generation_tasks[key]`）。见 §8.0 ③。
- `_event_stream` 里的 `finally` 收敛逻辑从「请求被取消」改为「job 结束」。
  断开不再触发收敛 → **断开不再把消息写成 `stopped`**。
- 租约释放（`_cleanup_turn` / `release_generation`）跟着 job 走，不跟请求走。

### 4.2 事件序号与快照对齐

每个事件在 job 内分配**单调递增 seq**（沿用现有的 `event_id` 计数器语义，但它
现在随请求生灭，要提到 job 上）。

`_persist` 记下 `blocks_seq` = 本次快照已折叠进去的最大 seq。于是：

```text
客户端带 after=k 连接
  latest   = 当前最大 seq
  buf_oldest = 缓冲最老 seq（空缓冲时 = latest + 1）

  若 k + 1 >= buf_oldest  且  k <= latest:
       # k 落在缓冲覆盖范围内 —— 纯增量
       重放 seq > k 的事件，然后接实时

  否则:
       # k 太老 / 首次连接 / 缓冲已溢出
       若 blocks_seq < buf_oldest - 1:
           强制 _persist(force=True)          # ← 让快照追上缓冲边界
       发 sync {blocks, blocks_seq}
       重放 seq > blocks_seq 的事件，然后接实时
```

**第 3 段那个 `force` 是必需的，不是优化（自查发现，见 §8.0 ②）**：
`_persist` 有 250ms 节流，盘上快照可能比缓冲还要旧。若不强制刷新就发 `sync`，
「快照覆盖到 `blocks_seq`」与「缓冲从 `buf_oldest` 开始」之间会漏掉一段事件，
用户看到的内容凭空少一截。

所以真正的不变量是：

> **只有当 `blocks_seq >= buf_oldest - 1` 时，「快照 + 增量」才无缝拼接。**

第二种分支显式保证了这个前提。三段首尾相接，无缝隙。

**双标签页同时看**：每个订阅者维护自己的读游标，共享同一份缓冲，互不影响。

### 4.3 状态语义：不需要新状态值

解耦之后，断开不再产生终态，所以 `stopped` 的语义**自动收窄**回它本来的意思：
用户主动停止。进程死掉那一路由第二步的 `turn_crash_markers` 区分。

于是前端契约 `'streaming' | 'complete' | 'error' | 'stopped' | 'queued'`
（`types.ts:212`）不用改。

### 4.4 多实例扩展性：三档部署

| 部署 | 续看需要什么 | 现状够不够 |
|---|---|---|
| 单实例（现在） | 环形缓冲 + blocks 兜底 | ✅ 本方案直接够 |
| 多实例 + 会话粘性 | 同上 | ✅ 同上，粘性保证落在同一实例 |
| 多实例 + 无粘性 | 共享缓冲 + 共享 pub/sub + owner 路由 | ❌ 需扩展 |

关键是**第三档的退化行为是安全的**：实例 B 即使拿不到实例 A 的实时增量，
也能从共享的 `messages.blocks`（在 SQLite 里）发出 `sync`，客户端至少能对齐到
当前状态，不会看到错误内容。缺的只是「接着实时看」。

### 4.5 唯一的预留：`owner_instance`

在 `session_generations` 行上记 `owner_instance`（进程启动时生成一个 id）。

**写入点是 `team_store.acquire_generation`（`team_store.py:210`），不是 chat 路由**
（自查发现，见 §8.0 ⑥）。该表现有 `PRIMARY KEY (user_id, session_id, generation_id)`
和 `UNIQUE INDEX ... WHERE status='active'`，加一列 `TEXT NOT NULL DEFAULT ''` 即可。

- 现在加：只是写入时多带一个值，零成本；
- 将来补：已有行没有 owner，得写迁移 + 「owner 未知怎么办」的兜底，
  而那条兜底路径正是最容易出 bug 的地方（同 `recover_stale_runtime` 那类收敛逻辑）。

有了它，「停止要打到哪个实例」将来有答案；没有它，`request_stop` 永远是单实例语义。

### 4.6 上界与回收（从第一天就有）

| 项 | 策略 |
|---|---|
| 每 job 缓冲 | 按事件条数上限（建议 2000）/ 字节上限（建议 2 MB），溢出丢最老，靠 `sync` 兜底 |
| job 存活 | 跟生成走；结束时（complete/stopped/error）立即释放缓冲 |
| 无订阅者的 job | **不杀**，跑到自然结束（结果照样落库，符合预期）；总时长由既有轮数/超时上限约束 |
| 订阅者 | 每 job 订阅者数设上限（建议 8），超出拒绝并提示刷新 |

「无订阅者不杀」是有意选择：用户关标签页不等于取消任务。LibreChat 也是这个语义。

## 6. 实施步骤（每阶段可独立验证）

### 阶段 1：解耦（本步真正的地基）

**硬约束：不改 `_event_stream` 的签名和产出语义**（A2A 依赖它，见 §8.0 ①）。
job 包在 `guarded_stream` 外层。

- 新增 turn job 注册表（进程内）：`job_id` → task / stop_event / 缓冲 / seq 计数。
- `guarded_stream` 改为「建 job → 订阅」。
- `register_generation` 在 **job 任务内部**调用（不是请求任务里）。
- `_event_stream` 的收敛/清标记逻辑移到 job 结束点。
- **验收**：断开后 `messages.content` 继续增长，最终状态 `complete`；
  且 A2A 的 13 项测试全绿（证明没有破坏第二个调用方）。

### 阶段 2：环形缓冲 + `sync` 帧

- 每 job 一条有界缓冲（条数 + 字节双上限）。
- `_persist` 记 `blocks_seq`。
- `sync` 前做 `blocks_seq < buf_oldest - 1` 检查，必要时强制持久化（§4.2）。
- **验收**：单测覆盖「k 在窗口内 / k 太老 / 首次连接」三条分支，以及溢出降级。

### 阶段 3：`GET /stream` 续看 + 前端接入

- 新增订阅端点；`parseFrame` 解析 `id:`，记录 `lastSeq`。
- 前端在 `resume` 时用 `GET /stream?after=lastSeq` 接上；页面加载时若发现
  消息是 `streaming` 且 job 还活着，自动接上。
- **验收**：真机刷新后正文继续增长，且最终内容完整。

### 阶段 4（可选，独立）：心跳

长时间无事件（如 36s 的 `code_run`）时发 `: ping` 注释行，避免中间代理按空闲超时
断连。目前这条链路实测能撑过 36s，所以列为可选。

## 8. 风险与未决项

### 8.0 评审自查发现的问题（会阻塞实施，必须先解决）

写完后逐条回源核对，找出 6 处。前三条是真 bug，不是措辞问题。

#### ① `_event_stream` 有两个调用方，A2A 是第二个（**最严重**）

`a2a/service.py:193` 直接 `async for raw in chat._event_stream(...)`。A2A 的
`_run_task` 本身就是 `asyncio.create_task`（`service.py:273`），也就是说
**A2A 早就是「job 跑生成、请求订阅」的结构**。

后果：如果按 §6 阶段 1 把 `_event_stream` 改成「建 job 并返回」，A2A 会被套两层
job，而且它会拿到一个「订阅流」而不是原始事件——`_parse_frame` 全部失配。

**修法**：阶段 1 必须是**纯内部重构，不改 `_event_stream` 的签名和产出语义**。
「解耦」应该发生在 `guarded_stream` 这一层（它只有一个调用方），具体为：

```
guarded_stream()            # StreamingResponse 的 body —— 变成订阅者
   └─ turn_job = create_task(_run_turn_job(...))    # job 跑真正的生成
        └─ async for chunk in _event_stream(...)     # 原样不动
```

这样 A2A 仍然直接调 `_event_stream`，拿到的东西一字不差。**这是阶段 1 的硬约束。**

#### ② 「ring buffer 溢出 → 发 sync」是错的时序

§4.2 写的降级路径有 bug：如果真的按字面实现（缓冲丢了最老的，然后「发 sync 从
`blocks` 重来」），`sync` 里的 `blocks` 是**盘上的快照**，而缓冲里剩下的是**更新的
事件**。如果盘上快照正好比缓冲还旧（`_persist` 250ms 节流，完全可能），那么
「`blocks` 到 `blocks_seq`」和「缓冲从 `blocks_seq+1` 开始」之间就会**漏掉一段**。

正确的不变量不是「`blocks` 一定覆盖到缓冲起点」，而是：

> **只有当 `blocks_seq >= 缓冲最老 seq - 1` 时，才允许「快照 + 增量」拼接。**

否则必须走另一条路：**先强制持久化一次（`_persist(force=True)`），再发 sync**，
让 `blocks_seq` 追上缓冲边界。文档 §4.2 需要按这个改写，并加一条单测
`test_sync_forces_persist_when_buffer_older_than_snapshot`。

#### ③ 前端「停止」是 abort + `/stop` 并行，解耦后仍成立，但有一个副作用

`App.tsx:457-490` 的 `stop()` 先本地置 `stopped`、`abortRef.current?.abort()`，
再调 `api.stop()`。解耦之后 abort 不再杀 job，`/stop` 才是唯一终止手段 ——
这正好符合预期，**但停止的及时性完全压在 `/stop` 上**了。

现在 `/stop` 的链路是 `request_stop` → `cancel_generation`（`task.cancel()`）。
而 `cancel_generation` 读的是 `_generation_tasks[key]`，`register_generation`
存的是 `asyncio.current_task()`。**阶段 1 必须确保这里登记的是 job task**，
否则 `/stop` 会去 cancel 一个已经返回的请求任务，停止按钮变成没反应。

这条我原来在 §4.1 提过一句，但没意识到它和前端 abort 解耦是**同一个**风险点，
严重性被低估了。补一条单测 `test_stop_cancels_job_task`。

#### ④ `_persist` 的 250ms 节流失效点

`_persist` 有 `if not force and now - last_persist_at < 0.25: return`
（`chat.py:562`）。解耦后 job 在无人订阅时**仍在跑**，如果这时 `_persist` 因为
节流被跳过，盘上状态就会落后于真实进度——而 `mark_stale_streaming_stopped`
之类的地方会读到旧快照。

需要确认：无人订阅时 `_persist` 的调用频率是否受影响。目前它是事件驱动的，
与订阅者无关，所以**理论上没问题**，但阶段 1 要加一条真机断言：
「断开 60s 后盘上 content 长度持续增长」。这条本来就是 §7 的 D-1，补一句
「且中间没有长时间停滞」。

#### ⑤ `healed` 帧不在缓冲里，位置会乱

`chat.py:530` 的 `healed` 是在 `try` 块里 `yield sse_frame(...)`，用的是
**不带 `id:` 的 `sse_frame`**（不是 `frame()`），并且发生在 `event_id = 0`
（`chat.py:423`）**之前**。也就是说它天生没有序号。

对续看无影响（`healed` 是瞬态提示，不重放），但**它验证了一件事**：
管道里已经存在「无序号帧」，所以前端解析 `id:` 时必须容忍缺失，不能假定每帧都有。

#### ⑥ 多实例那节漏了 `session_generations` 的唯一索引

§4.5 说加 `owner_instance`。核对表结构（`team_store.py:157-167`）发现
`session_generations` 有 `PRIMARY KEY (user_id, session_id, generation_id)`
和 `UNIQUE INDEX ... WHERE status='active'`。加列本身简单，但要记下：
**这个表在 `team_store`，不在 chat 层**，所以 `owner_instance` 的写入点在
`acquire_generation` 里，而不是在 chat 的路由里。

# 家客指标查询手册

本 Skill 是**家客业务口径 + sqlbot MCP 工具用法**的静态操作手册。
它与具体 agent、具体部署解耦：只描述「业务语义 → 工具参数」的映射规则，
不假设调用方是谁。真正查数由 sqlbot MCP（12 个工具）完成。

数据与工具的当前快照见 `references/`：

- `references/data-shape.md` —— 三张表、粒度、区域层级、全国编码、数据区间
- `references/metric-catalog.md` —— 635 个指标的检索方法与典型清单
- `references/tool-contract.md` —— 12 个工具的入参/出参/边界（含已知缺陷）
- `references/playbooks.md` —— 常见问法的完整工具链剧本
- `assets/metric-catalog.csv` —— 全量指标 `id,metric_name_cn` 快照

> 本 Skill 不含任何可执行脚本：所有查询都通过 MCP 工具完成。
> 若「本轮工具列表」里没有 `metric_series` 等工具，说明 sqlbot MCP 本轮未连接，
> 应当如实告知用户，**不要**改用 code_run 手写 SQL 或编造数据。

## 1. 三步固定流程

**先定位指标 → 再定区域与时间 → 最后选工具。**

### 第 1 步：把业务词落到指标 id

用户说的是业务话术（"宽带用户""千兆占比""FTTR 渗透"），工具要的是 `metric_ids`（整数）。
必须用 `metric_search` 把话术转成 id，**禁止凭印象编 id**：

```
metric_search(keyword="宽带")        → [{id:1, 家庭宽带用户数}, {id:2, 300M以下宽带用户数}, ...]
```

- 一次搜不到就换关键词再搜（"FTTR" → "光纤到房间"；"渗透" → "占比"）。
- 命中多条时挑与问题最贴切的；不确定就**同时查多个 id**再在回答里说明各自含义。
- `references/metric-catalog.md` 与 `assets/metric-catalog.csv` 是静态快照，可用于**猜测关键词**，
  但落参数前仍要用 `metric_search` 确认 id 未被变更。

### 第 2 步：确定区域口径

| 用户说法 | 参数 |
|---|---|
| 全国 / 集团 / 整体 | `zone_ids=[99]` |
| 某省（广东、浙江…） | `zone_names=["广东"]`（LIKE 模糊）或先 `zone_list(level=1)` 取 id 后用 `zone_ids=[106]` |
| 所有省份排名 | `level=1`（一次返回 32 个省级区域） |
| 某市（广州、深圳…） | 先 `zone_list(level=2, keyword="广州")` 取 id，再用 `zone_ids=[1008]` |
| 所有城市 | `level=2`（16 个城市） |
| 多个区域对比 | `zone_ids=[106,108]`（**推荐**：明确、可控） |

> `zone_names` 传多个值是 **OR**（这几个区域都要，2026-11-11 已在 sqlbot 侧修复；
> 更早版本是 AND，会返回 0 行）。两种写法都可用：
> `zone_names=["广东","浙江"]` 或 `zone_ids=[106,108]`。
> 名称是 LIKE 模糊匹配（`%`/`_` 已转义按字面量处理），精确匹配仍建议先 `zone_list` 取 id。

### 第 3 步：确定时间口径

| 用户说法 | 参数 | 说明 |
|---|---|---|
| 最新 / 当前 / 现在 | 不传时间参数 | `metric_latest` 默认取最新一期 |
| 某年某月 | `month="2026-07"` | 格式固定 `YYYY-MM` |
| 某段区间 | `start_month`/`end_month` 或 `month="2026-01"` + 同月 | 见 `metric_series` |
| 近 N 个月 | 先 `time_options()` 拿 `latest_data_time`，再按最新月往前推 N 个月 | **不要用系统当前日期**，数据有滞后 |

> 数据区间必须先确认：`time_options()` → `earliest_data_time` / `latest_data_time`。
> 这个库**只有月粒度有数据**（`gran=1` 天、`gran=3` 季度在演示数据中均为 0 行）。
> 用户问「某天」时，要说明只能给到月度。

## 2. 工具选择矩阵

| 问题形态 | 首选工具 | 关键参数 |
|---|---|---|
| 某指标某月某区域的**一个值** | `metric_latest` | `metric_ids`, `zone_ids`, `month` |
| 某指标**一段时间的走势** | `metric_series` | `start_month`/`end_month` 或 `month` |
| **环比 / 同比** | `metric_compare` | `month_a`(本期), `month_b`(对比期) |
| **多区域排名 / 占比分布** | `metric_series` + `level=1` 或 `level=2` | 拿到全部行后自行排序 |
| 不知道叫什么指标 | `metric_search` | 多次换关键词 |
| 指标字典整体情况 | `metric_list` / `dimensions` | 慎用大 `limit` |
| 看真实表结构、写 SQL 前 | `table_schema` | 无参 |
| 数据最新到几月 | `time_options` | 无参 |
| 模板全覆盖不了的复杂查询 | `run_readonly_sql` | 见 §4 |
| 已有数据要出图 | `chart_spec` | 见 §5 |

**优先级铁律：模板工具优先。** `metric_series` / `metric_latest` / `metric_compare`
的 SQL 由服务端确定性生成，口径正确、跨方言安全。只有当模板参数表达不了需求
（多表自连接、窗口函数、复杂条件聚合）才用 `run_readonly_sql`。

## 3. 口径陷阱（必须主动交代）

这些是家客数据最常见的误读来源。回答时**主动**说明，不要让用户以为数据有问题：

1. **单位字段是空的。** `ads_jk_business_metric_dictionary` 只有 `id` 与 `metric_name_cn`
   两列（`unit` 在逻辑 schema 里有、实际库中不存在），`metric_search` 返回的 `unit` 恒为 `null`。
   `metric_value` 的量级要靠常识判断（家庭宽带用户数 ≈ 1.14 亿 → 单位是「户」）。
   **回答里要写清「库内未登记单位，按量级判断为 X」**，不要假装有权威单位。

2. **`metric_compare` 的 delta 符号以 `month_a` 为基准。**
   实测：`month_a=2026-06, month_b=2026-07` → `delta = value_a - value_b = -164879`。
   即 **delta = A − B**。要做「7 月环比 6 月」的常规表述，应把**本期放 A、对比期放 B**：
   `month_a="2026-07", month_b="2026-06"` → `delta=+164879, delta_pct=+0.1447`。
   如果符号看起来反了，先检查 A/B 有没有传反，不要在回答里下"工具算错了"的结论。

3. **占比类指标是比率，量纲是 0–1（不是 0–100）。**
   `千兆用户占比`、`FTTR用户占比`、`家庭宽带用户活跃率` 这类指标的 `metric_value`
   实测是 `0.397312` 这种小数。换算成百分比要 **×100**（→ 39.73%），
   **不要**再乘第二次，也不要把小数直接说成"0.4%"。

4. **演示数据是模拟数据，业务恒等式不成立。**
   实测：`家庭宽带用户数 = 114,124,518`，但 `300M以下 + 300M~1000M + 1000M及以上 = 348,871,509`；
   `1000M及以上 = 116,447,173` 甚至**大于**总用户数；省级层面「三档之和 / 全省总数」
   在 1.20 倍（北京）~ 8.50 倍（安徽）之间乱跳。四个指标的量级都锚在 1.1–1.2 亿，
   像是各自独立生成的平滑随机序列。这**不是**工具算错。
   - ❌ 不要用「分档之和 = 总数」「子业务 ≤ 主业务」这类恒等式去校验数据；
   - ❌ 不要因此在回答里断言"数据有问题/工具出错"；
   - ✅ 若用户要正式汇报，应提示「当前为演示数据集，口径关系不代表生产实际」；
   - ✅ 生产库换数据后，这些恒等式**可能**成立，但也需实测确认，不要先入为主。

   **比率指标与绝对数指标之间也不自洽**：`千兆用户占比 = 0.397312`（39.7%）乘总用户数
   应得约 4,534 万，而 `1000M及以上宽带用户数` 直接给 1.1645 亿，差 2.57 倍。
   所以：**结构分析优先用比率指标**（`千兆用户占比`、`FTTR用户占比` 等），
   绝对数指标适合做**趋势与省内排名**，不适合做结构拆解。

5. **层级不要混用，但省级汇总确实等于全国。**
   `zone_ids=[99]`（全国）与 `level=1`（各省）是两种查询口径，回答里要说清用的是哪个。
   实测：32 省之和**精确等于**全国值（每个指标都分毫不差），说明**区域汇总链路是正确的**。
   但"档位之间"的关系不成立（见上一条）——别把这两件事混为一谈：
   **省级加总可信，档位拆分不可信。**

   ⚠️ **市级不能用来加总**：库里只有 16 个重点城市（`level=2`），
   2026-07 家庭宽带用户数市合计 2,103 万，而省级合计 1.14 亿 —— 差一个量级。
   这是**覆盖不全**（不是数据错误），所以：
   - ❌ 不要用市级加总去核对省级或全国；
   - ✅ 城市级问题只能回答"该市有/无数据"，不能推断全省城市分布。

6. **数据有滞后。** 以 `time_options().latest_data_time` 为准，
   不要用「今天」推断最新月份。

7. **空结果先怀疑口径，不是先怀疑没数据。**
   返回 `row_count: 0` 时按顺序排查：
   `time_options` 看区间 → 指标 id 是否正确 → 区域 id 是否该层有值 → 粒度是否选错。
   排查完确实无数据，再如实说「该口径下无数据」。

## 4. `run_readonly_sql` 逃生口

只有模板表达不了时才用。**用前必做 `table_schema()`**，避免猜列名。

已知表名（白名单，只能用这三张）：
`ads_jk_business_metric_dictionary`、`ads_jk_business_metric_values`、`d_zone_info`

约束（违反会被直接拒绝，返回 `rejected: true` 与原因）：

| 约束 | 说明 |
|---|---|
| 单语句 | 分号拼接多语句直接拒绝 |
| 只读 | INSERT/UPDATE/DELETE/CREATE/DROP 等一律拒绝（含 CTE 夹带） |
| 表白名单 | 只能用上面三张表 |
| 自动 LIMIT | 没写 LIMIT 时会自动补（返回 `appended_limit: true`） |
| 方言 | 按实际连接的库自动适配，不要手写 `DATE_FORMAT` 等方言函数 |

写法要点：

- 表连接：`values.dictionary_id = dictionary.id`、`values.zone_id = zone.zone_id`
- 月粒度过滤：`time_granularity = 2`，`data_time = '2026-07-01'`（**每月 1 日**）
- 全国：`zone_id = 99`；省份：`zone.zone_level = 1`；城市：`zone_level = 2`
- 复杂查询先在小范围验证（`LIMIT 5`），确认列名与口径正确后再跑全量

**返回体积**：`max_rows` 默认 1000。平台侧对 MCP 结果有统一预算（约 5 万字符），
超限会被裁剪并落盘到 workspace 的 `.hlaudz/tool_results/`，可用 `file_read` 回读。
所以**不要一次 select * 全表**，先在 SQL 里做聚合。

## 5. 图表产出

需要图时用 `chart_spec`，它是**纯转换**工具：不查库、只把你整理好的数据结构转成前端可渲染规格。

步骤：

1. 先用 `metric_series` / `run_readonly_sql` 取到数据；
2. 整理成 `categories`（x 轴：月份或省份名）与 `series`（`[{name, values:[...]}]`）；
3. 调 `chart_spec(categories=..., series=..., type=..., title=..., unit=...)`。

硬约束：

- `series[i].values` 长度 **必须等于** `categories` 长度，否则返回 `ok:false` 与具体错误；
- 缺失值用 `null`（折线会断开，**不要填 0**，填 0 会造成"跌到零"的误读）；
- `type` 可选 `line`/`bar`/`pie`/`table`，省略时自动推断；
- 时间序列用 `line`，区域排名用 `bar`，占比构成用 `pie`，明细用 `table`。

调用成功后**不要再把 option JSON 贴进正文**——前端已经渲染图表，正文只写文字解读。

## 6. 回答结构

家客数据是业务汇报素材，回答应能被直接引用：

1. **结论先行**：一句话给数值或排名结论（带单位与口径）；
2. **口径交代**：指标全名（含 id）、区域层级、时间点/区间、单位来源；
3. **数据表**：3 行以上用表格，数值加千分位；
4. **变化说明**：有对比就说明 delta 的方向与基准期（注意 §3 第 2 条的 A/B 陷阱）；
5. **不确定项**：单位未登记、口径可能有别、数据滞后，都要写明。

禁止：

- 编造指标 id、区域 id 或数值；
- 用 `code_run` 直接连数据库或手写 SQL 绕过 MCP（MCP 未连接时如实说明）；
- 把静态快照（`assets/metric-catalog.csv`）当成"当前数据库状态"来断言；
- 只给数字不交代口径。

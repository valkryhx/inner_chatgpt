# 技术报告撰写参考

## 写作定位

技术报告面向内部技术负责人、架构师、研发管理者和项目决策人员。报告的核心任务不是宣传技术，而是说明事实、解释原因、给出判断依据，并帮助读者做工程决策。

默认读者关心：

1. 该技术或模型解决了什么问题。
2. 关键指标、数据和来源是否可靠。
3. 它适合哪些场景，不适合哪些场景。
4. 引入成本、部署成本、维护成本和风险在哪里。
5. 对现有研发流程、基础设施和业务系统有什么影响。

## 表达方式

推荐写法：

> 该模型在代码生成和多步工具调用任务上表现较强，可能降低部分重复开发工作的人工投入，但在复杂业务系统中的稳定性仍需要结合项目场景验证。

不推荐写法：

> 该模型彻底颠覆了现有软件工程范式。

## 风险描述

风险要具体说明来源，不只写“风险较大”。

推荐写法：

> 该模型的拒绝率较低，部署到企业内部系统时需要额外配置输入过滤、输出审核和敏感数据防泄露策略，否则可能增加越权生成、提示词注入和合规审计风险。

## 表格要求

表格用于承载密集数据，不作装饰。表头应清晰、字段可比较，数字保留单位，不混用美元、人民币、Token、显存等单位。表格中的引用同样使用上标 `[x]` 样式。

常用字段：

- 模型名称
- 架构类型
- 上下文长度
- 输入成本
- 输出成本
- 主要优势
- 主要限制
- 适用场景

## 数据与事实要求

涉及数据时尽量说明：

1. 数据来源。
2. 测试条件。
3. 时间范围。
4. 指标含义。
5. 是否为第三方评测、官方披露或社区实测。

不应把单一基准测试结果直接推导为全场景结论。

## 交付前清单

1. 是否存在营销化、夸张化、抒情化表达。
2. 是否存在中英对照括号堆叠。
3. 是否存在绝对化判断且缺少条件边界。
4. 所有关键数据是否有引用来源。
5. 正文引用是否统一为上标 `[x]` 样式。
6. 是否存在版本号和引用编号粘连的问题。
7. 表格中的单位是否一致。
8. 结论是否回到工程决策。
9. 信源列表是否完整，正文引用是否能对应到信源。
10. Word 版本是否保留标题、表格、上标格式、首行缩进和仿宋字体。
